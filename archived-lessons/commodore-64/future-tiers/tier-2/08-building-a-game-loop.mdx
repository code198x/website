## The Core Game Loop

Every game revolves around its main loop. This is the heartbeat that keeps everything running, updating 50 or 60 times per second, creating the illusion of smooth motion and responsive controls.

### Basic Game Loop Structure

```text
; Professional Game Loop
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
main:
        jsr initialize_game
        
game_loop:
        ; 1. Timing
        jsr wait_frame
        
        ; 2. Input
        jsr read_input
        
        ; 3. Update
        jsr update_game_logic
        
        ; 4. Collision
        jsr check_collisions
        
        ; 5. Render
        jsr render_frame
        
        ; 6. Check state
        lda game_state
        cmp #STATE_GAME_OVER
        bne game_loop
        
        jsr cleanup_game
        rts
```

This structure is universal. Whether you're making Pac-Man or Call of Duty, the core loop follows this pattern: wait for the right time, gather input, update the world, check interactions, draw everything, repeat. The order matters - you read input before updating so changes happen this frame, you update before rendering so you draw the current state.

```text
wait_frame:
        ; Sync to 50Hz PAL or 60Hz NTSC
        lda #251               ; Raster line at bottom of screen
wait:   cmp $d012
        bne wait
        
        ; Frame counter
        inc frame_counter
        rts

frame_counter: !byte 0
```

The wait_frame routine is crucial. By waiting for raster line 251 (near the bottom of the visible screen), we ensure our game runs at a consistent speed. On PAL C64s, this gives us exactly 50 frames per second. NTSC machines run at 60 FPS. This timing synchronization is what prevents games from running too fast or slow.

The frame counter is surprisingly useful. It's a heartbeat we can use for animations (change sprite every 4 frames), timed events (spawn enemy every 60 frames), and debugging (how many frames does this routine take?).

### Timing and Frame Rate

Not everything needs to update every frame. Smart timing makes games feel better and run faster:

```text
; Frame-independent timing
update_with_timing:
        ; Update timers
        ldx #0
update_timers:
        lda timers,x
        beq skip_timer
        dec timers,x
skip_timer:
        inx
        cpx #NUM_TIMERS
        bne update_timers
```

This timer system is elegant. Each timer counts down to zero, then stops. You might use timer 0 for invincibility after taking damage, timer 1 for a power-up duration, timer 2 for enemy spawn delay. Just set a timer to a value and check when it hits zero.

```text
        ; Animation timing (every 4 frames)
        lda frame_counter
        and #$03               ; Mask gives us 0,1,2,3,0,1,2,3...
        bne skip_animation
        jsr update_animations
skip_animation:
        
        ; Game speed (every 2 frames)
        lda frame_counter
        and #$01               ; Mask gives us 0,1,0,1,0,1...
        bne skip_movement
        jsr update_movement
skip_movement:
        
        ; Slow events (every 16 frames)
        lda frame_counter
        and #$0f               ; Mask gives us 0-15 cycle
        bne skip_slow
        jsr update_slow_events
skip_slow:
        rts

NUM_TIMERS = 8
timers: !fill NUM_TIMERS, 0
```

Using AND masks with the frame counter is a classic trick. AND #$03 gives us a 4-frame cycle, AND #$01 gives us every other frame, AND #$0F gives us every 16 frames. This technique costs almost nothing but lets us control the speed of different game elements independently.

## Game State Management

Professional games use state machines to manage different modes. You're never "just running the game" - you're in the menu, or playing, or paused, or showing game over.

### State System

```text
; Game states
STATE_MENU      = 0
STATE_PLAYING   = 1
STATE_PAUSED    = 2
STATE_GAME_OVER = 3
STATE_LEVEL_COMPLETE = 4

game_state: !byte STATE_MENU

; Main state handler
handle_game_state:
        lda game_state
        asl                    ; x2 for word addresses
        tax
        lda state_handlers,x
        sta jump_vector
        lda state_handlers+1,x
        sta jump_vector+1
        jmp (jump_vector)

state_handlers:
        !word handle_menu
        !word handle_playing
        !word handle_paused
        !word handle_game_over
        !word handle_level_complete

jump_vector: !word 0
```

This is a jump table-based state machine. Instead of a massive IF-THEN-ELSE chain, we use the state value as an index into a table of handler addresses. It's fast, clean, and scales perfectly. Want to add a new state? Just add an entry to the table.

The ASL (arithmetic shift left) doubles the state value because addresses are 2 bytes. State 0 points to bytes 0-1 of the table, state 1 to bytes 2-3, etc.

```text
; Individual state handlers
handle_menu:
        jsr draw_menu
        jsr check_menu_input
        lda menu_selection
        cmp #START_GAME
        bne menu_done
        
        ; Start game
        lda #STATE_PLAYING
        sta game_state
        jsr init_gameplay
menu_done:
        rts
```

Each state handler is self-contained. The menu handler draws the menu, checks for input, and transitions to playing when START is selected. Notice it calls init_gameplay when transitioning - this is crucial for clean state changes.

```text
handle_playing:
        jsr update_player
        jsr update_enemies
        jsr check_collisions
        jsr update_score_display
        
        ; Check pause
        lda last_key
        cmp #KEY_SPACE
        bne check_death
        lda #STATE_PAUSED
        sta game_state
        rts
        
check_death:
        lda player_lives
        bne playing_done
        lda #STATE_GAME_OVER
        sta game_state
        
playing_done:
        rts

handle_paused:
        jsr draw_pause_text
        lda last_key
        cmp #KEY_SPACE
        bne paused_done
        lda #STATE_PLAYING
        sta game_state
paused_done:
        rts
```

The playing state is where the actual game happens. It updates all game entities, checks for pause, and monitors for game over conditions. The pause state is minimal - it just draws "PAUSED" and waits for the player to unpause. This is the beauty of state machines - each state only worries about its own concerns.

### State Transitions

Clean state transitions prevent bugs:

```text
; Clean state transitions
transition_to_state:
        ; Exit current state
        lda game_state
        asl
        tax
        lda exit_handlers,x
        sta jump_vector
        lda exit_handlers+1,x
        sta jump_vector+1
        jsr jump_to_vector
        
        ; Enter new state
        lda new_state
        sta game_state
        asl
        tax
        lda enter_handlers,x
        sta jump_vector
        lda enter_handlers+1,x
        sta jump_vector+1
        jsr jump_to_vector
        
        rts

jump_to_vector:
        jmp (jump_vector)

exit_handlers:
        !word exit_menu
        !word exit_playing
        !word exit_paused
        !word exit_game_over
        !word exit_level_complete

enter_handlers:
        !word enter_menu
        !word enter_playing
        !word enter_paused
        !word enter_game_over
        !word enter_level_complete

new_state: !byte 0
```

This two-phase transition system ensures clean state changes. When leaving the playing state, exit_playing might stop music and hide sprites. When entering the menu state, enter_menu might display the title screen and reset the cursor position. This prevents visual glitches and state pollution.

## Complete Game Structure

Here's how it all comes together in a real game framework:

```text
; Complete C64 Game Framework
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        jsr system_init
        jsr game_init
        
main_loop:
        ; Frame timing
        jsr wait_vblank
        inc frame_counter
        
        ; Handle current state
        jsr handle_game_state
        
        ; Always check for reset
        lda last_key
        cmp #KEY_RUN_STOP
        bne main_loop
        
        jsr game_cleanup
        rts
```

This is the top level - clean and simple. Initialize everything, then loop forever handling whatever state we're in. The RUN/STOP key check gives players a way to exit cleanly.

```text
; ==================
; System Initialize
; ==================
system_init:
        ; Clear screen
        lda #147               ; Clear character
        jsr $ffd2              ; CHROUT kernal routine
        
        ; Set colors
        lda #$00
        sta $d020              ; Border
        sta $d021              ; Background
        
        ; Initialize sprites
        lda #$00
        sta $d015              ; All sprites off
        sta $d017              ; No Y expansion
        sta $d01b              ; Priority
        sta $d01c              ; No multicolor
        sta $d01d              ; No X expansion
```

System initialization puts the hardware in a known state. This is crucial - you don't know what state the previous program left things in. Clear the screen, reset colors, turn off all sprites. Start from a clean slate.

```text
        ; Initialize sound
        lda #0
        ldx #0
clear_sid:
        sta $d400,x
        inx
        cpx #25
        bne clear_sid
        
        rts
```

The SID chip has 25 registers ($D400-$D418). Clearing them all ensures no stuck notes or leftover noise from previous programs. This loop writes 0 to each register, silencing the chip.

```text
; ==================
; Game Initialize
; ==================
game_init:
        ; Game variables
        lda #3
        sta player_lives
        lda #0
        sta score
        sta score+1
        sta current_level
        
        ; Start at menu
        lda #STATE_MENU
        sta game_state
        
        jsr init_sprites
        jsr init_level
        
        rts
```

Game initialization sets up your specific game's starting state. Three lives, zero score, level 1, start at the menu. This separation between system init (hardware) and game init (software) keeps code organized.

The complete framework continues with state handlers for menu, playing, paused, game over, and level complete states. Each state is self-contained with its own update routine:

```text
; ==================
; Menu State
; ==================
update_menu:
        ; Draw menu if needed
        lda menu_drawn
        bne check_menu_keys
        jsr draw_main_menu
        lda #1
        sta menu_drawn
        
check_menu_keys:
        ; Check for start
        lda $dc00              ; Joystick
        and #$10               ; Fire button
        bne menu_done
        
        ; Start game!
        lda #STATE_PLAYING
        sta game_state
        lda #0
        sta menu_drawn
        jsr start_new_game
        
menu_done:
        rts
```

The menu_drawn flag prevents redrawing the menu every frame - a common optimization. We only draw once, then just check for input. When fire is pressed, we transition to playing state and call start_new_game to set everything up.

```text
; ==================
; Gameplay State
; ==================
update_gameplay:
        ; Input
        jsr read_joystick
        
        ; Update entities
        jsr update_player
        jsr update_enemies
        jsr update_bullets
        
        ; Physics
        jsr apply_gravity
        jsr check_collisions
        
        ; Game logic
        jsr check_win_condition
        jsr check_lose_condition
        
        ; Display
        jsr update_hud
        jsr animate_sprites
        
        rts
```

The gameplay update is where your game lives. Notice the order: input first (so it affects this frame), then entity updates, then physics and collisions, then game logic, finally display updates. This ordering prevents visual glitches and logic errors.

```text
update_player:
        ; Movement from joystick
        lda joy_state
        lsr
        bcs no_up
        dec player_y
no_up:
        lsr
        bcs no_down
        inc player_y
no_down:
        lsr
        bcs no_left
        dec player_x
no_left:
        lsr
        bcs no_right
        inc player_x
no_right:
        
        ; Apply to sprite
        lda player_x
        sta $d000
        lda player_y
        sta $d001
        
        rts
```

Player update reads the cached joystick state and updates position. Keeping player_x and player_y as separate variables (rather than directly modifying sprite registers) lets us do collision checking before committing the movement.

## Level Management

Games need structure beyond just one screen:

```text
; Level system
init_level:
        ; Get level data
        lda current_level
        asl                    ; x2 for word pointers
        tax
        lda level_pointers,x
        sta level_ptr
        lda level_pointers+1,x
        sta level_ptr+1
        
        ; Load level
        jsr load_level_data
        jsr spawn_enemies
        jsr reset_player_position
        
        rts
```

This flexible level system uses pointers to level data. Each level can have completely different enemy counts, positions, and properties. The pointer table makes it easy to add new levels.

```text
load_level_data:
        ldy #0
        
        ; Enemy count
        lda (level_ptr),y
        sta enemies_remaining
        iny
        
        ; Enemy positions
        ldx #0
load_enemies:
        lda (level_ptr),y
        sta enemy_x,x
        iny
        lda (level_ptr),y
        sta enemy_y,x
        iny
        lda #1
        sta enemy_active,x
        inx
        cpx enemies_remaining
        bne load_enemies
        
        rts

; Level data
level_pointers:
        !word level_1_data
        !word level_2_data
        !word level_3_data

level_1_data:
        !byte 2                ; 2 enemies
        !byte 200,100          ; Enemy 1 position
        !byte 180,120          ; Enemy 2 position

level_2_data:
        !byte 3                ; 3 enemies
        !byte 200,80
        !byte 180,100
        !byte 160,120

level_3_data:
        !byte 3                ; 3 enemies
        !byte 220,90
        !byte 200,110
        !byte 180,130

level_ptr: !word 0
```

The level data format is simple but extensible. First byte is enemy count, then pairs of X,Y positions. You could easily add enemy types, power-up locations, or any other level-specific data.

## Score and HUD System

Players need feedback about game state:

```text
; HUD management
update_hud:
        ; Display score
        jsr display_score
        
        ; Display lives
        jsr display_lives
        
        ; Display level
        jsr display_level
        
        rts

display_score:
        ; Convert score to decimal
        lda score+1            ; High byte
        ldx score              ; Low byte
        jsr hex_to_decimal
        
        ; Display digits
        ldx #0
display_digits:
        lda decimal_digits,x
        ora #$30               ; Convert to screen code
        sta $0400,x            ; Top-left corner
        inx
        cpx #5
        bne display_digits
        
        rts
```

Displaying numbers requires converting from binary to decimal. The OR #$30 converts a digit (0-9) to its screen code ('0'-'9'). Screen codes are different from ASCII - '0' is code $30 on the C64.

```text
display_lives:
        ; Show heart symbols for lives
        ldx #0
        lda #83                ; Heart character
life_loop:
        cpx player_lives
        beq lives_done
        sta $0400+39-3,x       ; Top-right corner
        inx
        jmp life_loop
lives_done:
        rts
```

Visual life display using heart symbols is more intuitive than numbers. The math $0400+39-3 puts hearts in the top-right corner: $0400 is screen start, +39 is right edge, -3 gives room for 3 hearts.

## Performance Optimization

Every cycle counts in a game loop:

```text
; Optimized game loop
optimized_loop:
        ; Use unrolled loops for speed
        ldx #0
fast_sprite_update:
        lda sprite_x,x
        sta $d000
        lda sprite_y,x
        sta $d001
        lda sprite_x+1,x
        sta $d002
        lda sprite_y+1,x
        sta $d003
        lda sprite_x+2,x
        sta $d004
        lda sprite_y+2,x
        sta $d005
        lda sprite_x+3,x
        sta $d006
        lda sprite_y+3,x
        sta $d007
        ; All 4 sprites updated
```

Loop unrolling trades code size for speed. Instead of looping 4 times, we write the code 4 times. No loop overhead, no branch penalties. This technique was crucial for smooth action games.

```text
        ; Batch collision checks
        lda $d01e              ; Read once
        sta collision_cache
        beq no_sprite_collision
        jsr handle_all_collisions
no_sprite_collision:
        
        rts

sprite_x: !byte 0,0,0,0
sprite_y: !byte 0,0,0,0
collision_cache: !byte 0
```

Reading collision registers clears them, so read once and cache the value. The BEQ after the store is a clever optimization - if no bits are set (no collisions), skip the handler entirely.

## Common Issues and Solutions

### "Game feels sluggish"
- Profile your code - which routines take the most time?
- Optimize inner loops first - they run most often
- Use lookup tables instead of calculations
- Consider updating different systems on alternate frames

### "State transitions are buggy"
- Always clean up when leaving states (hide sprites, stop sounds)
- Always initialize when entering states (reset positions, clear flags)
- Clear all temporary flags during transitions
- Use enter/exit handlers consistently

### "Timing is inconsistent"
- Always sync to raster for frame timing
- Use frame counters, not delay loops
- Account for PAL/NTSC differences (50Hz vs 60Hz)
- Test on real hardware or accurate emulators

## Quick Reference

### Game Loop Order
1. Wait for frame sync (PAL: 50Hz, NTSC: 60Hz)
2. Read input (cache for this frame)
3. Update game logic (move, spawn, destroy)
4. Check collisions (read registers once!)
5. Update display (sprites, score, lives)
6. Check state changes (game over? level complete?)

### Common States
- **Menu/Title**: Show options, wait for start
- **Playing**: The actual game
- **Paused**: Freeze gameplay, wait for resume
- **Game Over**: Show score, offer restart
- **Level Complete**: Celebrate, load next level
- **Loading**: For games that load from disk

### Timing Guidelines
- 50Hz (PAL) = 20ms per frame = 19,656 cycles
- 60Hz (NTSC) = 16.67ms per frame = 16,380 cycles
- Keep updates under frame time or you'll drop frames
- Use counters for slower events (animation, spawning)

Remember: Good architecture makes everything else easier! A well-structured game is easier to debug, extend, and optimize. The patterns you've learned here scale from simple arcade games to complex adventures.
