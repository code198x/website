## Linear Interpolation (Lerp)

Linear interpolation is the foundation of smooth motion. Instead of jumping directly to a target position, you gradually move toward it. Each frame, you travel a fraction of the remaining distance. This creates natural, fluid movement that feels organic rather than mechanical.

### Basic Interpolation

```text
; Simple interpolation
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        ; Setup sprite
        lda #$80
        sta $07f8
        lda #%00000001
        sta $d015
        lda #$07               ; Yellow
        sta $d027

        ; Starting position
        lda #50
        sta current_x
        sta $d000
        lda #100
        sta current_y
        sta $d001

        ; Target position
        lda #200
        sta target_x
        lda #150
        sta target_y
```

We're setting up a yellow sprite with both current and target positions. The magic happens in how we move between them.

```text
interpolate_loop:
        ; Wait for frame
        lda #250
wait:   cmp $d012
        bne wait

        ; Interpolate X
        lda target_x
        sec
        sbc current_x          ; Distance to target
        beq x_done             ; Already there

        ; Move 1/8 of distance
        lsr                    ; /2
        lsr                    ; /4
        lsr                    ; /8
        bne apply_x
        lda #1                 ; Minimum 1 pixel
apply_x:
        clc
        adc current_x
        sta current_x
        sta $d000
```

The interpolation formula is elegant: new_position = current + (target - current) / 8. We calculate the distance to the target, divide by 8 (using three LSR instructions), and add that to our current position. This moves us 1/8th of the way to the target each frame.

The beauty is in the behavior: movement starts fast when far from the target, then naturally slows as we approach. This creates an organic "easing" effect that feels natural to the eye. The check for zero with a minimum of 1 pixel ensures we always make progress, preventing infinite approach.

```text
x_done:
        ; Interpolate Y
        lda target_y
        sec
        sbc current_y
        beq y_done

        lsr
        lsr
        lsr
        bne apply_y
        lda #1
apply_y:
        clc
        adc current_y
        sta current_y
        sta $d001

y_done:
        ; Check for new target (joystick)
        lda $dc00
        and #$10               ; Fire button
        bne interpolate_loop

        ; Set new random target
        lda $d012              ; Use raster as random
        sta target_x
        lda $d012
        sta target_y

        jmp interpolate_loop

current_x:  !byte 50
current_y:  !byte 100
target_x:   !byte 200
target_y:   !byte 150
```

Using the fire button to set a new random target (based on the current raster line for randomness) creates an interactive demo. The sprite smoothly glides to each new position, never jerking or jumping.

### Smooth Following

Make sprites follow targets smoothly - perfect for cameras or companion characters:

```text
; Smooth follow camera/cursor
smooth_follow:
        ; Calculate X difference
        lda target_x
        sec
        sbc follower_x
        sta x_diff

        ; Check direction
        bpl moving_right

        ; Moving left (negative)
        eor #$ff
        clc
        adc #1                 ; Make positive (two's complement)
        lsr
        lsr                    ; Divide by 4 for smoothing
        beq follow_y           ; Too small to move

        ; Subtract from position
        sta temp
        lda follower_x
        sec
        sbc temp
        sta follower_x
        jmp follow_y
```

Handling negative numbers requires two's complement conversion (EOR #$FF, then ADD #1). This converts our signed difference to an absolute value we can work with. Dividing by 4 (two LSR instructions) creates a following speed - smaller divisors follow more quickly, larger divisors create more lag.

```text
moving_right:
        lsr
        lsr                    ; Divide by 4
        beq follow_y

        clc
        adc follower_x
        sta follower_x

follow_y:
        ; Same for Y coordinate
        lda target_y
        sec
        sbc follower_y
        sta y_diff

        bpl moving_down

        eor #$ff
        clc
        adc #1
        lsr
        lsr
        beq update_sprite

        sta temp
        lda follower_y
        sec
        sbc temp
        sta follower_y
        jmp update_sprite

moving_down:
        lsr
        lsr
        beq update_sprite

        clc
        adc follower_y
        sta follower_y

update_sprite:
        lda follower_x
        sta $d000
        lda follower_y
        sta $d001
        rts

follower_x: !byte 100
follower_y: !byte 100
x_diff:     !byte 0
y_diff:     !byte 0
temp:       !byte 0
```

This creates a natural "lag" effect where the follower smoothly tracks the target. Games used this for camera systems (the camera follows the player with slight delay) and companion AI (Tails following Sonic).

## Sub-Pixel Precision

The C64 displays pixels as integers, but internally tracking fractional pixels creates ultra-smooth movement. This is the secret behind the smoothest C64 games.

### 16-Bit Precision Movement

```text
; Sub-pixel precision system
; Position stored as 16-bit fixed point (8.8)
; High byte = pixel position
; Low byte = sub-pixel fraction

sub_pixel_movement:
        ; Initialize 16-bit position
        lda #100
        sta x_pos_hi           ; 100 pixels
        lda #0
        sta x_pos_lo           ; .0 fraction

        ; Velocity with fraction
        lda #1
        sta x_vel_hi           ; 1 pixel
        lda #$40               ; + 0.25 pixels (64/256)
        sta x_vel_lo
```

Fixed-point arithmetic treats a 16-bit value as having 8 bits for the integer part and 8 bits for the fraction. $0140 represents 1.25 pixels. The high byte (1) is the pixel count, the low byte ($40 = 64/256 = 0.25) is the fractional part.

```text
move_with_precision:
        ; Add velocity to position
        clc
        lda x_pos_lo
        adc x_vel_lo
        sta x_pos_lo
        lda x_pos_hi
        adc x_vel_hi
        sta x_pos_hi

        ; Apply to sprite (only high byte)
        sta $d000
```

The magic happens in the 16-bit addition. The low byte accumulates fractional movement. When it overflows (crosses 256), the carry flag adds 1 to the high byte, moving exactly one pixel. This lets us move at speeds like 0.75 pixels per frame, creating smooth motion at any speed.

```text
        ; Acceleration example
        clc
        lda x_vel_lo
        adc #$08               ; Tiny acceleration (0.03125 pixels)
        sta x_vel_lo
        lda x_vel_hi
        adc #0                 ; Carry if needed
        sta x_vel_hi

        rts

x_pos_hi:   !byte 100
x_pos_lo:   !byte 0
x_vel_hi:   !byte 1
x_vel_lo:   !byte $40
```

Adding #$08 to the velocity's low byte increases speed by 8/256 = 0.03125 pixels per frame. Over many frames, this creates smooth, gradual acceleration. This technique enabled the precise physics in games like "Thrust" and "Exile."

### Fixed-Point Math

Understanding fixed-point representation:

```text
; 8.8 fixed point arithmetic
; $0100 = 1.0
; $0080 = 0.5
; $0040 = 0.25

multiply_fixed:
        ; Multiply two 8.8 numbers
        ; Result in 16.16, extract middle 16 bits

        ; Example: 1.5 * 2.25
        lda #$01
        sta multiplicand_hi
        lda #$80               ; 1.5 = 1 + 128/256
        sta multiplicand_lo

        lda #$02
        sta multiplier_hi
        lda #$40               ; 2.25 = 2 + 64/256
        sta multiplier_lo

        ; (Multiplication routine here)
        ; Result: $0340 = 3.25

        rts
```

Multiplying fixed-point numbers requires special handling. The result of multiplying two 8.8 numbers gives a 16.16 result. We extract the middle 16 bits to maintain the 8.8 format. This complexity is why many games pre-calculated values in lookup tables.

```text
; Sine table in fixed point
sine_table_fixed:
        !byte $00,$00  ; 0.0
        !byte $00,$32  ; 0.195
        !byte $00,$61  ; 0.383
        !byte $00,$8E  ; 0.556
        !byte $00,$B5  ; 0.707
        !byte $00,$D4  ; 0.831
        !byte $00,$EC  ; 0.924
        !byte $00,$FA  ; 0.981
        !byte $01,$00  ; 1.0
```

Fixed-point sine tables enabled smooth circular and wave motion. Each entry represents the sine value in 8.8 format. For example, $00B5 = 181/256 = 0.707, which is sine(45°).

## Acceleration and Physics

Natural movement requires acceleration and deceleration. Real objects don't instantly reach top speed or stop immediately - they build momentum.

### Acceleration System

```text
; Physics-based movement
physics_movement:
        ; Apply acceleration
        lda input_x            ; -1, 0, or 1 from joystick
        beq apply_friction

        ; Accelerate
        bmi accel_left

        ; Accelerate right
        clc
        lda velocity_x
        adc #ACCELERATION
        cmp #MAX_VELOCITY
        bcc store_vel
        lda #MAX_VELOCITY      ; Cap at max speed
        jmp store_vel

accel_left:
        sec
        lda velocity_x
        sbc #ACCELERATION
        cmp #256-MAX_VELOCITY  ; Negative max (two's complement)
        bcs store_vel
        lda #256-MAX_VELOCITY  ; Cap at negative max

store_vel:
        sta velocity_x
        jmp apply_velocity
```

This system adds acceleration when there's input, creating gradual speed changes. The velocity is capped at MAX_VELOCITY in both directions. Using two's complement for negative values (256-MAX_VELOCITY) keeps the math simple while supporting bidirectional movement.

```text
apply_friction:
        ; No input - apply friction
        lda velocity_x
        beq apply_velocity     ; Already stopped
        bmi friction_left

        ; Moving right - slow down
        sec
        sbc #FRICTION
        bcs store_friction     ; Still positive
        lda #0                 ; Stopped
        jmp store_friction

friction_left:
        ; Moving left - slow down
        clc
        adc #FRICTION
        bcc store_friction     ; Still negative
        lda #0                 ; Stopped

store_friction:
        sta velocity_x

apply_velocity:
        ; Add velocity to position
        lda position_x
        clc
        adc velocity_x
        sta position_x
        sta $d000

        rts

ACCELERATION = 2
MAX_VELOCITY = 8
FRICTION = 1

input_x:    !byte 0
velocity_x: !byte 0
position_x: !byte 100
```

Friction naturally slows movement when there's no input. The sprite gradually comes to rest rather than stopping instantly. This feels natural - like ice with low friction or sand with high friction. These constants define the feel of movement: higher acceleration = more responsive, higher friction = tighter control.

### Gravity and Jumping

Realistic jumping requires proper gravity simulation:

```text
; Smooth jumping physics
jump_physics:
        ; Check jump input
        lda $dc00
        and #$01               ; Up = jump
        bne apply_gravity

        ; Can we jump?
        lda on_ground
        beq apply_gravity      ; Must be on ground

        ; Start jump
        lda #JUMP_VELOCITY     ; Negative = upward
        sta y_velocity
        lda #0
        sta on_ground          ; Now airborne

apply_gravity:
        ; Always apply gravity
        lda y_velocity
        clc
        adc #GRAVITY           ; Positive = downward
        sta y_velocity

        ; Terminal velocity check
        cmp #MAX_FALL_SPEED
        bcc apply_y_vel
        lda #MAX_FALL_SPEED
        sta y_velocity
```

Gravity constantly accelerates the sprite downward. The jump gives an initial upward velocity (negative in screen coordinates), and gravity gradually overcomes it, creating a parabolic arc. Terminal velocity prevents infinite acceleration, simulating air resistance.

```text
apply_y_vel:
        ; Apply to position
        lda y_position
        clc
        adc y_velocity
        sta y_position

        ; Check ground collision
        cmp #GROUND_LEVEL
        bcc not_on_ground

        ; Hit ground
        lda #GROUND_LEVEL
        sta y_position
        lda #0
        sta y_velocity         ; Stop falling
        lda #1
        sta on_ground          ; Can jump again

not_on_ground:
        ; Update sprite
        lda y_position
        sta $d001

        rts

JUMP_VELOCITY = 256-12  ; Negative (up), about -12 pixels/frame
GRAVITY = 1             ; Acceleration downward
MAX_FALL_SPEED = 10     ; Terminal velocity
GROUND_LEVEL = 200      ; Floor position

y_velocity:  !byte 0
y_position:  !byte 200
on_ground:   !byte 1
```

The constants define the jump feel. JUMP_VELOCITY controls height, GRAVITY affects arc shape, MAX_FALL_SPEED prevents frustrating deaths. This same system powered platformers from "Impossible Mission" to "Mayhem in Monsterland."

## Smooth Scrolling

Professional scrolling requires careful coordination between hardware registers and screen memory.

### Pixel-Perfect Scrolling

The VIC-II chip provides hardware fine scrolling:

```text
; Smooth horizontal scroll
smooth_scroll:
        ; Fine scroll register (0-7 pixels)
        lda scroll_x_fine
        sta $d016              ; Hardware scroll register

        ; Scroll one pixel
        inc scroll_x_fine
        lda scroll_x_fine
        and #$07               ; Wrap at 8
        sta scroll_x_fine
        bne scroll_done

        ; Wrapped - shift characters
        jsr shift_screen_left

scroll_done:
        rts
```

The $D016 register provides fine scrolling in 1-pixel increments (0-7 pixels). After scrolling 8 pixels, we need to shift the entire character screen one position and reset the fine scroll. This creates endless smooth scrolling.

```text
shift_screen_left:
        ; Move all characters left
        ldx #0
shift_row:
        ldy #0
shift_char:
        lda $0401,y            ; Get next char
        sta $0400,y            ; Move left
        iny
        cpy #39                ; 39 chars per row (one hidden)
        bne shift_char

        ; New character on right
        lda new_column_data,x
        sta $0400+39           ; Rightmost position

        ; Next row (self-modifying code for speed)
        clc
        lda shift_row+1        ; Low byte of address
        adc #40                ; Next row
        sta shift_row+1
        lda shift_row+2        ; High byte
        adc #0                 ; Add carry
        sta shift_row+2
```

Self-modifying code updates the load/store addresses for each row. This is faster than indexed addressing across multiple rows. After processing all 25 rows, we reset the addresses for the next frame.

```text
        inx
        cpx #25                ; 25 rows
        bne shift_row

        ; Reset self-mod code
        lda #<$0401
        sta shift_row+1
        lda #>$0401
        sta shift_row+2

        rts

scroll_x_fine: !byte 0
new_column_data: !fill 25, 32  ; Space characters
```

The new_column_data array defines what appears on the right edge as we scroll. This would typically come from level data, creating the illusion of a vast scrolling world from just 1000 bytes of screen memory.

### Parallax Scrolling

Multiple layers moving at different speeds creates depth:

```text
; Multi-layer parallax
parallax_scroll:
        ; Background layer (slow)
        inc frame_counter
        lda frame_counter
        and #$03               ; Every 4 frames
        bne skip_bg

        inc bg_scroll
        lda bg_scroll
        and #$07
        sta $d016              ; Fine scroll

skip_bg:
        ; Midground (medium)
        lda frame_counter
        and #$01               ; Every 2 frames
        bne skip_mid

        jsr scroll_midground

skip_mid:
        ; Foreground (fast)
        jsr scroll_foreground  ; Every frame

        rts

frame_counter: !byte 0
bg_scroll:     !byte 0
```

Different scroll speeds create the parallax effect. Background moves every 4 frames, midground every 2, foreground every frame. This technique, used masterfully in "Shadow of the Beast" and "Turrican," creates a convincing sense of depth with minimal resources.

## Complete Smooth Motion Demo

Here's everything working together in a professional physics system:

```text
; Professional Motion Demo
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        jsr init_motion

main_loop:
        ; Timing
        jsr wait_frame

        ; Input
        jsr read_smooth_input

        ; Physics
        jsr update_physics
        jsr apply_acceleration
        jsr apply_velocity

        ; Interpolation
        jsr interpolate_position

        ; Rendering
        jsr update_display

        jmp main_loop

update_physics:
        ; Horizontal movement with 16-bit precision
        lda input_x
        beq apply_x_friction

        ; Accelerate (16-bit)
        asl                    ; x2 for acceleration
        clc
        adc velocity_x_lo
        sta velocity_x_lo
        lda velocity_x_hi
        adc input_x
        sta velocity_x_hi

        ; Clamp velocity
        jsr clamp_velocity
        jmp vertical_physics
```

The physics system uses 16-bit fixed-point for all calculations, providing sub-pixel precision. Input affects acceleration, not position directly, creating natural momentum.

```text
apply_x_friction:
        ; Friction reduces velocity by 1/16
        lda velocity_x_hi
        bmi negative_friction

        ; Positive velocity
        lda velocity_x_lo
        sec
        sbc #$10               ; Subtract 0.0625
        sta velocity_x_lo
        lda velocity_x_hi
        sbc #0
        sta velocity_x_hi
        bpl vertical_physics   ; Still moving right

        ; Stopped
        lda #0
        sta velocity_x_hi
        sta velocity_x_lo
        jmp vertical_physics
```

Friction is subtle but crucial. Subtracting a small fixed-point value (#$10 = 16/256 = 0.0625) gradually slows movement. This creates natural deceleration that feels right.

The complete demo continues with vertical physics, velocity application, and interpolated display positions, creating movement that rivals commercial games. Every calculation maintains precision, every update maintains smoothness.

## Common Issues and Solutions

### "Movement still feels jerky"

- Ensure consistent frame timing (always wait for raster)
- Use interpolation for display position separate from physics position
- Increase sub-pixel precision (16-bit or even 24-bit)

### "Acceleration feels wrong"

- Tune acceleration/friction values (small changes have big effects)
- Use non-linear curves (acceleration tables)
- Add momentum caps at different speeds

### "Scrolling tears"

- Sync scroll updates to raster beam
- Update during vertical blank period
- Use double buffering for complex scrolls

## Quick Reference

### Interpolation Formula

```text
new_pos = current_pos + (target_pos - current_pos) / smoothing_factor
```

### Fixed Point (8.8)

```text
$0100 = 1.0
$0080 = 0.5
$0040 = 0.25
$0010 = 0.0625
```

### Physics Constants

- **Gravity**: 0.125-0.25 pixels/frame²
- **Friction**: 0.0625-0.125 reduction/frame
- **Max velocity**: 4-8 pixels/frame
- **Jump velocity**: -6 to -12 pixels/frame
