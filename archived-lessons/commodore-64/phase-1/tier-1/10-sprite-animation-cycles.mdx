## Animation Fundamentals

Animation on the C64 is an illusion created by showing different sprite images in rapid succession. Like a flipbook, each "frame" is a complete 24×21 pixel sprite image stored in memory. By changing which image the sprite displays, we create movement.

### Basic Frame Animation

```text
; Simple animation cycle
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        ; Initialize
        lda #%00000001
        sta $d015              ; Enable sprite 0
        lda #$05               ; Green
        sta $d027
        
        ; Position
        lda #160
        sta $d000
        lda #125
        sta $d001
        
        ; Animation setup
        lda #0
        sta anim_frame
        sta anim_timer
```

Setting up is straightforward - enable a sprite, position it, and initialize our animation variables. The real magic happens in the animation loop.

```text
animation_loop:
        ; Wait for frame
        lda #250
wait:   cmp $d012
        bne wait
        
        ; Update animation timer
        inc anim_timer
        lda anim_timer
        and #$07               ; Every 8 frames
        bne animation_loop
        
        ; Next animation frame
        inc anim_frame
        lda anim_frame
        and #$03               ; 4 frames total (0-3)
        sta anim_frame
        
        ; Update sprite pointer
        clc
        adc #$80               ; Base sprite at $2000
        sta $07f8              ; Sprite 0 pointer
        
        jmp animation_loop

anim_frame:  !byte 0
anim_timer:  !byte 0
```

The animation timer controls speed. By checking `and #$07`, we advance the animation every 8 screen refreshes (about 6 times per second on PAL). The frame counter cycles through 4 frames using `and #$03`. The sprite pointer calculation adds the frame number to the base sprite address ($80 = $2000/64).

```text
; Sprite data at $2000, $2040, $2080, $20C0
*=$2000
; Frame 0 - Arms down
        !byte %00000001,%11111000,%00000000
        !byte %00000001,%11111000,%00000000
        ; ... rest of sprite

*=$2040
; Frame 1 - Arms mid
        !byte %00000001,%11111000,%00000000
        !byte %00001111,%11111111,%10000000
        ; ... rest of sprite

*=$2080
; Frame 2 - Arms up
        !byte %00001111,%11111111,%10000000
        !byte %00001111,%11111111,%10000000
        ; ... rest of sprite

*=$20c0
; Frame 3 - Arms mid (return)
        !byte %00000001,%11111000,%00000000
        !byte %00001111,%11111111,%10000000
        ; ... rest of sprite
```

Each frame is exactly 63 bytes (21 rows × 3 bytes). The VIC-II requires sprites to be aligned on 64-byte boundaries, wasting 1 byte per sprite. This seemingly inefficient design actually simplifies the math - sprite N is always at address (base + N×64).

### Walking Animation

Creating believable walk cycles requires understanding how walking actually works:

```text
; Walking character animation
walk_animation:
        ; Check if moving
        lda velocity_x
        bne is_walking
        
        ; Standing still - idle frame
        lda #$80
        sta $07f8
        rts
        
is_walking:
        ; Determine direction
        bmi walk_left
        
walk_right:
        ; Right-facing animation
        inc walk_timer
        lda walk_timer
        lsr                    ; Slow down (/2)
        lsr                    ; Slow down more (/4)
        and #$03               ; 4 frames (0-3)
        tax
        lda walk_frames_right,x
        sta $07f8
        rts
```

The walking animation ties directly to movement. When velocity is zero, we show an idle frame. When moving, we cycle through walking frames. The double LSR slows the animation to 1/4 speed, preventing the "Benny Hill" effect of too-fast animation.

```text
walk_left:
        ; Left-facing animation
        inc walk_timer
        lda walk_timer
        lsr
        lsr
        and #$03
        tax
        lda walk_frames_left,x
        sta $07f8
        rts

walk_timer:  !byte 0
velocity_x:  !byte 0

; Animation frame tables
walk_frames_right:
        !byte $80,$81,$82,$83  ; Right-facing sprites

walk_frames_left:
        !byte $84,$85,$86,$87  ; Left-facing sprites
```

Using lookup tables for frame sequences is crucial. It lets you easily adjust animations without changing code. Professional games often had separate tables for walk, run, sneak, and other movement speeds.

## Animation State Management

Real characters need multiple animation states. Walking, jumping, attacking - each requires different frame sequences and timing. This is where state machines become essential.

### State Machine Architecture

```text
; Animation states
ANIM_IDLE     = 0
ANIM_WALK     = 1
ANIM_JUMP     = 2
ANIM_FALL     = 3
ANIM_ATTACK   = 4
ANIM_HIT      = 5

current_anim_state: !byte ANIM_IDLE

update_animation:
        ; Determine state based on game logic
        lda on_ground
        beq check_airborne
        
        ; On ground
        lda velocity_x
        bne set_walk
        
        ; Standing still
        lda #ANIM_IDLE
        jmp apply_anim_state
        
set_walk:
        lda #ANIM_WALK
        jmp apply_anim_state
        
check_airborne:
        ; In air
        lda velocity_y
        bmi set_jump           ; Negative = going up
        lda #ANIM_FALL
        jmp apply_anim_state
        
set_jump:
        lda #ANIM_JUMP
```

The state determination logic looks at game physics to decide which animation to play. This automatic state selection means animations always match what the character is actually doing.

```text
apply_anim_state:
        ; Check if state changed
        cmp current_anim_state
        beq update_current_anim
        
        ; State changed - reset animation
        sta current_anim_state
        lda #0
        sta anim_frame
        sta anim_timer
        
update_current_anim:
        ; Update based on current state
        lda current_anim_state
        asl                    ; ×2 for word table
        tax
        lda anim_handlers,x
        sta jump_addr
        lda anim_handlers+1,x
        sta jump_addr+1
        jmp (jump_addr)

anim_handlers:
        !word handle_idle
        !word handle_walk
        !word handle_jump
        !word handle_fall
        !word handle_attack
        !word handle_hit

jump_addr: !word 0
```

When states change, we reset the animation to frame 0. This prevents jarring mid-frame transitions. The jump table dispatches to specific handlers for each animation type, keeping code organized and efficient.

### Individual Animation Handlers

Each animation state has unique requirements:

```text
handle_idle:
        ; Idle animation - subtle breathing
        inc anim_timer
        lda anim_timer
        and #$1f               ; Every 32 frames
        bne idle_done
        
        inc anim_frame
        lda anim_frame
        and #$01               ; 2 frames only
        sta anim_frame
        
        clc
        adc #$80               ; Idle base sprite
        sta $07f8
idle_done:
        rts
```

Idle animations add life to standing characters. The slow update (every 32 frames) creates a subtle breathing effect. Even this small movement makes characters feel alive rather than frozen.

```text
handle_walk:
        ; Walking animation
        inc anim_timer
        lda anim_timer
        and #$03               ; Every 4 frames (fast walk)
        bne walk_done
        
        inc anim_frame
        lda anim_frame
        and #$07               ; 8 frames total
        sta anim_frame
        
        ; Choose direction
        lda velocity_x
        bmi walk_left_anim
        
        ; Right walk
        lda anim_frame
        clc
        adc #$88               ; Right walk base
        sta $07f8
        rts
        
walk_left_anim:
        lda anim_frame
        clc
        adc #$90               ; Left walk base
        sta $07f8
walk_done:
        rts
```

Walking uses more frames (8) and updates faster (every 4 frames) than idle. The direction check selects between left and right sprite sets. Games like "The Last Ninja" used 12 or more frames for ultra-smooth walks.

```text
handle_jump:
        ; Single jump frame (no animation)
        lda velocity_x
        bmi jump_left
        lda #$98               ; Right jump sprite
        jmp set_jump_sprite
jump_left:
        lda #$99               ; Left jump sprite
set_jump_sprite:
        sta $07f8
        rts

handle_fall:
        ; Falling animation
        lda velocity_x
        bmi fall_left
        lda #$9a               ; Right fall sprite
        jmp set_fall_sprite
fall_left:
        lda #$9b               ; Left fall sprite
set_fall_sprite:
        sta $07f8
        rts
```

Jump and fall often use single frames rather than animations. The key is choosing sprites that convey the action clearly. Arms up for jumping, arms out for falling - these poses communicate state instantly.

```text
handle_attack:
        ; Attack animation sequence
        inc anim_timer
        lda anim_timer
        lsr                    ; Faster animation
        and #$03               ; 4 frames
        sta anim_frame
        
        cmp #3
        bne show_attack_frame
        
        ; Attack complete - return to idle
        lda #ANIM_IDLE
        sta current_anim_state
        
show_attack_frame:
        clc
        adc #$9c               ; Attack base
        sta $07f8
        rts
```

Attack animations are typically fast and don't loop. The animation plays once, then automatically returns to idle. This one-shot behavior is perfect for actions like attacking, jumping, or taking damage.

## Advanced Animation Techniques

Professional games used sophisticated techniques to create fluid, responsive animations.

### Smooth Transitions

Jarring switches between animations break immersion. Smooth transitions maintain flow:

```text
; Smooth animation transitions
transition_animation:
        ; Check if transitioning
        lda transition_active
        beq no_transition
        
        ; Blend between old and new
        dec transition_timer
        bne show_transition
        
        ; Transition complete
        lda #0
        sta transition_active
        lda new_state
        sta current_state
        rts
        
show_transition:
        ; Alternate between states
        lda transition_timer
        and #$02
        beq show_old_state
        
        ; Show new state
        lda new_state
        jmp show_state
        
show_old_state:
        lda current_state
        
show_state:
        ; Display appropriate frame
        tax
        lda state_frames,x
        sta $07f8
        rts
```

This creates a brief "blend" by rapidly alternating between old and new animations. While simple, it prevents the jarring "pop" of instant transitions.

### Animation Timing Tables

Different animations need different speeds. Tables provide flexible control:

```text
; Variable animation speeds
update_timed_animation:
        ; Get timing for current animation
        ldx current_anim
        lda anim_speeds,x      ; Frames between updates
        sta anim_speed
        
        ; Update timer
        inc anim_counter
        lda anim_counter
        cmp anim_speed
        bcc timing_done        ; Not time yet
        
        ; Reset counter and advance frame
        lda #0
        sta anim_counter
        
        ; Next frame
        inc current_frame
        lda current_frame
        cmp anim_lengths,x     ; Check max frames
        bcc update_sprite_frame
        
        ; Animation complete - loop or stop?
        lda anim_loop_flags,x
        bne loop_anim
        
        ; One-shot animation done
        lda #ANIM_IDLE
        sta current_anim
        rts
        
loop_anim:
        lda #0
        sta current_frame
        
update_sprite_frame:
        ; Calculate sprite pointer
        lda anim_bases,x       ; Starting sprite
        clc
        adc current_frame      ; Add current frame
        sta $07f8
        
timing_done:
        rts

; Animation data tables
anim_speeds:
        !byte 8,4,2,2,3,6     ; Frames per update

anim_lengths:
        !byte 2,8,1,1,4,2     ; Total frames in animation

anim_loop_flags:
        !byte 1,1,0,0,0,0     ; 1=loop, 0=one-shot

anim_bases:
        !byte $80,$88,$98,$9a,$9c,$a0  ; Starting sprite for each animation
```

Table-driven animation provides incredible flexibility. Want to make walking faster? Change one byte in anim_speeds. Need more frames in the attack? Update anim_lengths. This data-driven approach was essential for tuning gameplay.

## Complete Character System

Here's everything integrated into a full animated character:

```text
; Complete Animated Character
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        jsr init_character
        
game_loop:
        ; Timing
        lda #250
wait:   cmp $d012
        bne wait
        
        ; Input
        jsr read_input
        
        ; Update
        jsr update_physics
        jsr update_animation_state
        jsr update_animation_frame
        jsr update_position
        
        jmp game_loop
```

The main loop orchestrates everything. Note the order: input → physics → animation state → animation frame → position. This ensures animations always reflect the current game state.

```text
init_character:
        ; Sprite setup
        lda #%00000001
        sta $d015
        lda #$07               ; Yellow
        sta $d027
        
        ; Initial position
        lda #100
        sta char_x
        sta $d000
        lda #180
        sta char_y
        sta $d001
        
        ; Initial state
        lda #ANIM_IDLE
        sta anim_state
        lda #0
        sta anim_frame
        sta anim_timer
        
        rts
```

Initialization sets everything to known values. Starting in ANIM_IDLE with frame 0 ensures the character appears correctly from the first frame.

The complete implementation continues with input handling that triggers state changes:

```text
read_input:
        lda $dc00
        sta joy_input
        
        ; Horizontal movement
        lsr
        lsr
        lsr
        bcc move_left
        lsr
        bcc move_right
        lda #0
        sta input_x
        jmp check_jump
        
move_left:
        lda #$ff               ; -1
        sta input_x
        jmp check_jump
        
move_right:
        lda #1
        sta input_x
        
check_jump:
        lda joy_input
        and #$01               ; Up = jump
        bne no_jump
        lda grounded
        beq no_jump
        
        ; Jump!
        lda #$f8               ; -8 velocity
        sta vel_y
        lda #0
        sta grounded
        
no_jump:
        ; Attack
        lda joy_input
        and #$10               ; Fire button
        bne no_attack
        lda anim_state
        cmp #ANIM_ATTACK
        beq no_attack          ; Already attacking
        
        ; Start attack
        lda #ANIM_ATTACK
        sta anim_state
        lda #0
        sta anim_frame
        sta anim_timer
        
no_attack:
        rts
```

Input directly triggers certain animations (like attack), while others (walk, idle) are derived from physics state. This mixed approach gives precise control where needed while keeping common animations automatic.

## Optimization Tips

Sprite animation can consume significant memory. These techniques help:

### Sprite Memory Layout

```text
; Efficient sprite organization
; Group by animation, not by frame number

*=$2000
idle_frames:
        !fill 64, 0            ; Idle 1
        !fill 64, 0            ; Idle 2

*=$2080
walk_right_frames:
        !fill 64, 0            ; Walk R1
        !fill 64, 0            ; Walk R2
        !fill 64, 0            ; Walk R3
        !fill 64, 0            ; Walk R4
```

Grouping sprites by animation keeps related frames together. This improves cache locality (even on the C64!) and makes the memory layout logical.

### Animation Compression

Not every frame needs to be unique:

```text
; Share similar frames between animations
; Walk frame 2 might work as run frame 1
walk_to_run_table:
        !byte $81,$83,$82,$84  ; Reuse walk frames for run
```

Many animations share frames. The transition from walk to run might reuse walking frames in a different order or speed. This technique saved precious memory in games with many characters.

## Common Issues and Solutions

### "Animation looks choppy"
- Ensure consistent frame timing (always sync to raster)
- Add more in-between frames for smoother motion
- Adjust animation speed (maybe it's too slow or too fast)
- Use interpolation for position while animating

### "Transitions are jarring"
- Add transition frames between major pose changes
- Implement blend techniques between states
- Ensure first frame of new animation follows naturally from last frame of previous

### "Running out of sprite memory"
- Share common frames between animations
- Use sprite mirroring for left/right (though this requires runtime processing)
- Consider reducing animation frames for less important characters
- Pack multiple smaller sprites into one 24×21 frame
