Previous lessons drew graphics using immediate values—constants written directly in code. Real games need **variables**: named memory locations storing values that change during gameplay. Player coordinates, enemy health, score counters, animation frames—all require variables.

The NES has 2KB of RAM organized for efficiency. The 6502 CPU provides special addressing modes making certain memory regions faster. This lesson explores NES memory layout, zero page advantages, and using variables to build a simple scene.

## The One-Minute Tour

- **6502 CPU** runs at 1.79 MHz with three registers: A, X, Y
- **Zero page** ($00-$FF) provides fastest memory access—use for hot variables
- **Stack** at $0100-$01FF for subroutine calls and temporary storage
- **OAM buffer** conventionally at $0200-$02FF for sprite data
- **General RAM** at $0300-$07FF for game state
- **PRG-ROM** at $8000-$FFFF holds program code (read-only)
- `.segment "ZEROPAGE"` declares variables in fast zero page memory
- **Zero page instructions are smaller and faster** than absolute addressing

## Scene from Variables

Create `variables.asm`:

```nasm
.segment "HEADER"
    .byte "NES", $1A
    .byte 2
    .byte 1
    .byte $01, $00

.segment "ZEROPAGE"
sky_color:    .res 1         ; Color for sky background
ground_color: .res 1         ; Color for ground tiles
sun_color:    .res 1         ; Color for sun tile
horizon_row:  .res 1         ; Which row the ground starts
sun_x:        .res 1         ; Sun X position (in tiles)
sun_y:        .res 1         ; Sun Y position (in tiles)
row_counter:  .res 1         ; Current row being drawn

.segment "CODE"
Reset:
    SEI
    CLD

    ; PPU warmup (2 VBlanks)
    BIT $2002
:   BIT $2002
    BPL :-
:   BIT $2002
    BPL :-

    ; Initialize stack
    LDX #$FF
    TXS

    ; Initialize PPU
    LDA #$00
    STA $2000               ; PPUCTRL - disable NMI
    STA $2001               ; PPUMASK - disable rendering

    ; Initialize scene variables
    LDA #$21                ; Light blue sky
    STA sky_color
    LDA #$28                ; Green ground
    STA ground_color
    LDA #$38                ; Yellow sun
    STA sun_color
    LDA #12                 ; Horizon at row 12
    STA horizon_row
    LDA #24                 ; Sun at column 24
    STA sun_x
    LDA #4                  ; Sun at row 4
    STA sun_y

    ; Set palette colors from variables
    LDA #$3F
    STA $2006
    LDA #$00
    STA $2006
    LDA sky_color           ; Color 0: sky (background)
    STA $2007
    LDA ground_color        ; Color 1: ground
    STA $2007
    LDA sun_color           ; Color 2: sun
    STA $2007

    ; Clear attribute table
    LDA #$23
    STA $2006
    LDA #$C0
    STA $2006
    LDX #64
    LDA #$00
:   STA $2007
    DEX
    BNE :-

    ; Draw sky (rows 0 to horizon_row - 1)
    LDA #$20
    STA $2006
    LDA #$00
    STA $2006

    LDA #$00                ; Tile $00 for sky
    LDX #$00
    STX row_counter

DrawSkyLoop:
    LDY #32                 ; 32 tiles per row
:   STA $2007
    DEY
    BNE :-

    INC row_counter
    LDX row_counter
    CPX horizon_row         ; Reached horizon?
    BNE DrawSkyLoop

    ; Draw ground (rows horizon_row to 29)
    LDA #$01                ; Tile $01 for ground
    LDX row_counter

DrawGroundLoop:
    LDY #32                 ; 32 tiles per row
:   STA $2007
    DEY
    BNE :-

    INX
    CPX #30                 ; 30 rows total
    BNE DrawGroundLoop

    ; Draw sun at (sun_x, sun_y)
    ; Address = $2000 + (sun_y * 32) + sun_x
    LDA sun_y
    ASL                     ; Multiply by 32
    ASL
    ASL
    ASL
    ASL
    CLC
    ADC sun_x               ; Add X offset
    TAY                     ; Save low byte in Y

    ; Calculate high byte
    LDA #$20
    LDX sun_y
    CPX #8
    BCC :+
    LDA #$21
:   CPX #16
    BCC :+
    LDA #$22
:   CPX #24
    BCC :+
    LDA #$23
:
    ; Set address and draw sun
    STA $2006
    TYA
    STA $2006
    LDA #$02                ; Tile $02 (sun)
    STA $2007

    ; Reset scroll
    LDA #$00
    STA $2005
    STA $2005

    ; Enable rendering
    LDA #%00001010          ; Enable background + leftmost 8 pixels
    STA $2001

Forever:
    JMP Forever

NMI:
    RTI

IRQ:
    RTI

.segment "VECTORS"
    .word NMI
    .word Reset
    .word IRQ

.segment "CHARS"
    ; Tile $00: Blank (shows background color)
    .byte $00, $00, $00, $00, $00, $00, $00, $00
    .byte $00, $00, $00, $00, $00, $00, $00, $00

    ; Tile $01: Solid color 1 (ground)
    .byte $FF, $FF, $FF, $FF, $FF, $FF, $FF, $FF
    .byte $00, $00, $00, $00, $00, $00, $00, $00

    ; Tile $02: Solid color 2 (sun)
    .byte $00, $00, $00, $00, $00, $00, $00, $00
    .byte $FF, $FF, $FF, $FF, $FF, $FF, $FF, $FF

    .res 8192 - 48, $00
```

**Assemble and run** to see a simple scene: blue sky, green ground, yellow sun.

## How This Works

### Declaring Zero Page Variables

```nasm
.segment "ZEROPAGE"
sky_color:    .res 1         ; Color for sky background
ground_color: .res 1         ; Color for ground tiles
sun_color:    .res 1         ; Color for sun tile
horizon_row:  .res 1         ; Which row the ground starts
sun_x:        .res 1         ; Sun X position (in tiles)
sun_y:        .res 1         ; Sun Y position (in tiles)
row_counter:  .res 1         ; Current row being drawn
```

The `.segment "ZEROPAGE"` directive tells ca65 to allocate these variables in zero page ($00-$FF). `.res 1` reserves 1 byte without initializing it. The assembler assigns sequential addresses starting from $00:

- `sky_color` → $00
- `ground_color` → $01
- `sun_color` → $02
- `horizon_row` → $03
- `sun_x` → $04
- `sun_y` → $05
- `row_counter` → $06

You reference them by name. The assembler translates to zero page addresses automatically.

### Initializing Variables

Variables contain random values at power-on. Always initialize before use:

```nasm
LDA #$21                ; Light blue
STA sky_color
LDA #$28                ; Green
STA ground_color
LDA #$38                ; Yellow
STA sun_color
LDA #12                 ; Horizon at row 12
STA horizon_row
```

**Never assume zero.** Real hardware and flash carts power on with random RAM contents.

### Using Variables

Once initialized, load values from variables and use them:

```nasm
; Set palette from variables
LDA sky_color           ; Load from variable
STA $2007               ; Write to PPU
LDA ground_color
STA $2007
LDA sun_color
STA $2007
```

Compare this to immediate values:

```nasm
; Without variables
LDA #$21
STA $2007
LDA #$28
STA $2007
LDA #$38
STA $2007
```

Variables make code readable and flexible. Change one initialization value, and the entire scene changes.

### Variables in Control Flow

The `horizon_row` variable controls where sky ends and ground begins:

```nasm
DrawSkyLoop:
    LDY #32                 ; 32 tiles per row
:   STA $2007
    DEY
    BNE :-

    INC row_counter
    LDX row_counter
    CPX horizon_row         ; Compare against variable
    BNE DrawSkyLoop
```

Loop continues until `row_counter` reaches `horizon_row`. Changing `horizon_row` from 12 to 15 moves the horizon down three rows—no code changes required.

### Coordinate Variables

The sun position uses `sun_x` and `sun_y` to calculate nametable address:

```nasm
LDA sun_y
ASL                     ; Multiply by 32
ASL
ASL
ASL
ASL
CLC
ADC sun_x               ; Add X coordinate
```

Address = $2000 + (sun_y × 32) + sun_x. Variables make positioning flexible—modify initialization values to move the sun anywhere on screen.

## 6502 CPU Architecture

The 6502 is an 8-bit processor with minimal internal state:

**Accumulator (A):** Primary register for arithmetic, logic, and memory operations. Most instructions involve A.

**Index Register X:** Counter, array index, offset calculations.

**Index Register Y:** Counter, array index, different addressing modes than X.

**Stack Pointer (SP):** Points into $0100-$01FF. Grows downward (decrements with push).

**Program Counter (PC):** Current instruction address. Modified by jumps, branches, subroutines.

**Status Register (P):** Flags: Negative, oVerflow, Break, Decimal, Interrupt, Zero, Carry.

That's it. No caches, no floating point, no multiplication/division hardware, no registers for general data storage. **Everything uses RAM.**

### Why This Matters

With only three registers (A, X, Y) for calculations, the 6502 constantly loads from and stores to memory. A typical operation:

```nasm
LDA playerX             ; Load from memory
CLC
ADC playerVelocity      ; Add from memory
STA playerX             ; Store back to memory
```

Every instruction accessing memory costs cycles. **Fast memory access is critical.**

## NES Memory Map

The 6502 can address 64KB ($0000-$FFFF). The NES organizes this space:

```
$0000-$07FF: 2KB Internal RAM
  $0000-$00FF: Zero Page (256 bytes)
  $0100-$01FF: Stack (256 bytes)
  $0200-$02FF: OAM Buffer (256 bytes, conventional)
  $0300-$07FF: General Purpose (1280 bytes)

$0800-$1FFF: Mirrors of $0000-$07FF

$2000-$2007: PPU Registers
$2008-$3FFF: Mirrors of $2000-$2007

$4000-$4017: APU and I/O Registers

$6000-$7FFF: Cartridge SRAM (battery-backed save RAM)

$8000-$FFFF: PRG-ROM (program code from cartridge)
  $8000-$BFFF: First 16KB bank
  $C000-$FFFF: Second 16KB bank (contains vectors)
```

**Key insight:** Only $0000-$07FF is writable RAM. Everything else is read-only ROM, hardware registers, or mirrors.

### RAM Regions Explained

**Zero Page ($0000-$00FF):** 256 bytes of fastest RAM. Special addressing modes make access 25% faster than general RAM. Use for frequently accessed variables.

**Stack ($0100-$01FF):** 256 bytes for subroutine calls (JSR/RTS) and temporary storage (PHA/PLA). Grows downward.

**OAM Buffer ($0200-$02FF):** 256 bytes conventionally used for sprite data. Not hardware-enforced, but every NES library uses this location. Reserve it.

**General RAM ($0300-$07FF):** 1280 bytes for game state, level data, buffers, arrays. Slower than zero page but plenty of space.

**Mirrors ($0800-$1FFF):** Hardware repeats $0000-$07FF four times. Ignore these—use original addresses.

## Why Zero Page is Special

The 6502 has different addressing modes for memory access:

**Absolute addressing:** 3-byte instruction with full 16-bit address.
```nasm
LDA $0300               ; 4 cycles, 3 bytes
```

**Zero page addressing:** 2-byte instruction with 8-bit address (assumes $00XX).
```nasm
LDA $00                 ; 3 cycles, 2 bytes
```

Zero page instructions are **1 byte smaller** and **1 cycle faster** than absolute addressing.

### The Real-World Impact

Consider a game loop that runs 60 times per second, reading player X/Y coordinates 10 times per frame:

**Using absolute addressing:**
- 10 reads × 4 cycles = 40 cycles per frame
- 40 cycles × 60 frames = 2,400 cycles per second wasted

**Using zero page:**
- 10 reads × 3 cycles = 30 cycles per frame
- 30 cycles × 60 frames = 1,800 cycles per second
- **Savings: 600 cycles per second**

That's time for additional enemies, smoother animation, more complex AI. In a 1.79 MHz system where every cycle counts, zero page makes the difference between possible and impossible.

### Choosing What Goes in Zero Page

**Good candidates for zero page:**
- Player coordinates (X, Y, velocity)
- Current frame counter
- Controller input state
- Temporary calculation variables
- Loop counters used frequently

**Not worth zero page:**
- Level data arrays (too large)
- Infrequently accessed configuration
- One-time initialization values

Rule of thumb: if accessed in an inner loop or multiple times per frame, use zero page.

## Memory-Mapped Hardware

Addresses $2000-$2007 (PPU) and $4000-$4017 (APU/IO) aren't RAM—they're hardware registers. Writing to them controls hardware; reading reports hardware state.

```nasm
STA $2006               ; Write to PPU address register
LDA $2002               ; Read PPU status (VBlank flag)
```

This is **memory-mapped I/O**. The 6502 has no special I/O instructions—everything uses LDA/STA. Hardware appears as memory locations.

**Important:** Reading from some hardware registers has side effects. Reading $2002 clears the VBlank flag. Reading $2007 increments the PPU address pointer. Always check documentation before reading hardware registers.

## The Stack

The stack at $0100-$01FF handles subroutine calls and temporary storage:

```nasm
JSR Subroutine          ; Push return address to stack, jump
; ... subroutine code ...
RTS                     ; Pull return address, return
```

**Manual stack operations:**

```nasm
PHA                     ; Push A to stack
TXA
PHA                     ; Push X (via A, since no PHX instruction)
; ... do work ...
PLA
TAX                     ; Restore X
PLA                     ; Restore A
```

The stack grows downward. Each push decrements SP; each pull increments SP. Stack overflow (too many pushes without corresponding pulls) wraps to $01FF and corrupts RAM.

**Avoid deep recursion.** Balance pushes with pulls. The 6502 has no stack overflow detection—corruption happens silently.

## The INC Instruction

```nasm
INC row_counter
```

`INC` increments a memory location directly—no need to load into A, add one, and store back:

```nasm
; Slow way (5 instructions, 11 cycles)
LDA row_counter
CLC
ADC #$01
STA row_counter

; Fast way (1 instruction, 5 cycles)
INC row_counter
```

**INC** modifies memory in place. Works with zero page and absolute addressing. The 6502 also provides:

- `INC addr` - increment memory
- `INX` - increment X register (2 cycles)
- `INY` - increment Y register (2 cycles)
- `DEC addr` - decrement memory
- `DEX` - decrement X register
- `DEY` - decrement Y register

Use register increments (INX/INY) when possible—they're faster than memory increments.

### 6502 Registers

| Register | Purpose | Size |
|----------|---------|------|
| A | Accumulator (arithmetic/logic) | 8-bit |
| X | Index register | 8-bit |
| Y | Index register | 8-bit |
| SP | Stack pointer ($0100-$01FF) | 8-bit |
| PC | Program counter | 16-bit |
| P | Status flags (NVBDIZC) | 8-bit |

### Variable Declaration

```nasm
.segment "ZEROPAGE"
varName: .res 1             ; 1 byte in zero page

.segment "BSS"
arrayName: .res 256         ; 256 bytes in general RAM

.segment "RODATA"
tableData: .byte 1,2,3,4    ; Read-only data in ROM
```
