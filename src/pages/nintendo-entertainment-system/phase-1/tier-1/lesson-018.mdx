Your ball sprite exists—now make it move. This lesson implements automatic ball movement by adding velocity to position each frame. The ball moves smoothly at 60fps using signed arithmetic that works for both positive (right/down) and negative (left/up) direction.

Unlike paddles (player-controlled), the ball moves on its own every frame.

## The One-Minute Tour

- **UpdateBall routine**—runs every frame to move ball
- **Position += velocity**—add VX to X, VY to Y
- **Signed arithmetic**—ADC works for both positive and negative
- **8-bit wrap**—overflow naturally handles negative movement
- **60fps smooth**—ball moves consistently every frame
- **Call order**—update position before rendering sprites
- **No boundaries yet**—ball flies off screen (fixed next lesson)

## Your Moving Ball

```asm
.segment "CODE"
; Update ball position based on velocity
UpdateBall:
    ; Update X position
    LDA ball_x
    CLC
    ADC ball_vx         ; Add signed velocity
    STA ball_x

    ; Update Y position
    LDA ball_y
    CLC
    ADC ball_vy         ; Add signed velocity
    STA ball_y

    RTS

; Main game loop (add UpdateBall)
MainLoop:
    ; Wait for VBlank
:   LDA nmi_ready
    BEQ :-
    LDA #$00
    STA nmi_ready

    ; Game logic during rendering
    JSR ReadController
    JSR UpdatePaddle
    JSR UpdateBall          ; ← Add this (ball moves automatically)

    ; Update sprites for next VBlank
    JSR UpdatePaddleSprites
    JSR UpdateBallSprite

    JMP MainLoop
```

**Run this**—ball moves diagonally and flies off screen! (We'll add boundaries next lesson.)

## How This Works

### Velocity Application

Each frame, add velocity to position:

```asm
LDA ball_x          ; Load current X position
CLC                 ; Clear carry for addition
ADC ball_vx         ; Add velocity (signed)
STA ball_x          ; Store new position
```

**Example:** If ball_x = 100 and ball_vx = 2, new ball_x = 102. Ball moved 2 pixels right.

### Signed Arithmetic

ADC works for both positive and negative velocities:

**Moving right (+2):**
```
ball_x = 100 ($64)
ball_vx = +2 ($02)
$64 + $02 = $66 (102) ← moved right
```

**Moving left (-2):**
```
ball_x = 100 ($64)
ball_vx = -2 ($FE in two's complement)
$64 + $FE = $162
8-bit overflow wraps: $62 (98) ← moved left
```

**Why this works:** Two's complement representation makes signed addition use same ADC instruction as unsigned. CPU handles it automatically via 8-bit overflow.

### Different Speeds

Change velocity for different ball behavior:

```asm
; Slow horizontal
LDA #$01
STA ball_vx
LDA #$00
STA ball_vy

; Fast diagonal
LDA #$02
STA ball_vx
LDA #$02
STA ball_vy

; Moving left and up
LDA #$FE            ; -2 in signed byte
STA ball_vx
LDA #$FF            ; -1 in signed byte
STA ball_vy
```

### Frame-Based Movement

Ball updates every frame (60 times per second):

```
Frame 1: X=128, Y=120
Frame 2: X=129, Y=119  (moved +1, -1)
Frame 3: X=130, Y=118
Frame 4: X=131, Y=117
...
```

**Consistent speed** because we call UpdateBall every frame in main loop.

## Call Order Matters

Update position *before* rendering:

```asm
MainLoop:
    ; 1. Wait for VBlank
    ; 2. Update game state (positions)
    JSR UpdatePaddle
    JSR UpdateBall      ← Update position
    ; 3. Render (write to OAM buffer)
    JSR UpdatePaddleSprites
    JSR UpdateBallSprite ← Use new position
    JMP MainLoop
```

**Why?** UpdateBall changes ball_x/ball_y. UpdateBallSprite reads those values to write OAM. Must update data before using it.

## Building Your Game

### Add UpdateBall to Main Loop

After UpdatePaddle, before rendering:

```asm
MainLoop:
:   LDA nmi_ready
    BEQ :-
    LDA #$00
    STA nmi_ready

    JSR ReadController
    JSR UpdatePaddle
    JSR UpdateBall          ; ← Add this line

    JSR UpdatePaddleSprites
    JSR UpdateBallSprite
    JMP MainLoop
```

### Change Ball Direction

In InitBall, set starting velocity:

```asm
InitBall:
    LDA #128
    STA ball_x
    LDA #120
    STA ball_y
    LDA #$01            ; Moving right (+1)
    STA ball_vx
    LDA #$FF            ; Moving up (-1)
    STA ball_vy
    RTS
```

Try different values:
- `ball_vx = $02`: Faster horizontal
- `ball_vy = $01`: Moving down instead of up
- `ball_vx = $FE`: Moving left (-2)

## Common Pitfalls

**Ball doesn't move:**
- Forgot to call UpdateBall in main loop
- ball_vx and ball_vy are both $00 (no velocity)
- UpdateBall after UpdateBallSprite (wrong order)

**Ball moves wrong direction:**
- Check signed byte values ($FF = -1, not +255)
- Verify InitBall sets correct VX/VY
- Remember: positive = right/down, negative = left/up

**Ball moves too fast/slow:**
- Velocity is in pixels per frame
- At 60fps: velocity of 1 = 60 pixels per second
- Typical Pong speed: 1-3 pixels per frame

**Ball position wraps unexpectedly:**
- This is normal! No boundaries yet
- X wraps at 255 → 0
- Y wraps at 255 → 0
- Fixed in next lesson with boundary collision

## Quick Reference

### Velocity Values
```
$00 =   0 (no movement)
$01 =  +1 (slow right/down)
$02 =  +2 (medium)
$03 =  +3 (fast)
$FE =  -2 (medium left/up)
$FF =  -1 (slow left/up)
```

### Frame Rate Calculation
```
Velocity 1 = 1 pixel per frame
At 60fps = 60 pixels per second
Screen width = 256 pixels
256 ÷ 60 = 4.27 seconds to cross screen
```

### Update Order
```
1. Wait for VBlank
2. Read controllers
3. Update paddle (player input)
4. Update ball (automatic movement)
5. Render all sprites (OAM buffer)
6. Loop
```
