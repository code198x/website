Lesson 1 displayed a solid colour. This lesson brings tiles to the screen—actual graphics built from 8×8 pixel patterns. You'll write tile data to the **nametable** and see how the PPU assembles the screen from these building blocks.

Every NES game draws graphics using tiles. Backgrounds are grids of tiles, sprites are tiles that move independently, and even text is made of tiles. Master this, and you understand how every NES visual works.

## The One-Minute Tour

- **Tiles are 8×8 pixels** stored in CHR-ROM (the graphics bank)
- **Nametable** at $2000-$23FF defines which tiles appear where (32×30 grid)
- **Attribute table** at $23C0-$23FF controls which palette each tile uses
- **PPUADDR** ($2006) sets where to write, **PPUDATA** ($2007) writes the data
- **Each tile is 16 bytes**—two 8-byte bitplanes defining 2 bits per pixel
- **PPUMASK bit 1** must be set to show the leftmost 8 pixels of the screen

## Your First Tiles

Create `top-border.asm`:

```nasm
; Understanding PPU - Top Border
; Draws a white stripe across the top of the screen

.segment "HEADER"
    .byte "NES", $1A        ; iNES identifier
    .byte 2                  ; 32KB PRG-ROM
    .byte 1                  ; 8KB CHR-ROM
    .byte $01, $00          ; Mapper 0, vertical mirroring

.segment "CODE"

Reset:
    SEI                     ; Disable interrupts
    CLD                     ; Clear decimal mode

    ; Wait for PPU warmup (2 VBlanks)
    LDX #$00
VBlank1:
    BIT $2002
    BPL VBlank1

VBlank2:
    BIT $2002
    BPL VBlank2

    ; Initialize stack
    LDX #$FF
    TXS

    ; Initialize PPU registers
    LDA #$00
    STA $2000               ; PPUCTRL - disable NMI
    STA $2001               ; PPUMASK - disable rendering

    ; Set palette colours
    LDA #$3F
    STA $2006
    LDA #$00
    STA $2006
    LDA #$02                ; Dark blue background
    STA $2007
    LDA #$30                ; White for tiles
    STA $2007               ; Auto-increments to $3F01

    ; Clear nametable and attributes
    LDA #$20
    STA $2006
    LDA #$00
    STA $2006

    LDX #$04                ; 4 × 256 = 1024 bytes
    LDY #$00
    LDA #$00
ClearLoop:
    STA $2007
    INY
    BNE ClearLoop
    DEX
    BNE ClearLoop

    ; Clear attribute table explicitly
    LDA #$23
    STA $2006
    LDA #$C0
    STA $2006

    LDX #64                 ; 64 bytes
    LDA #$00
ClearAttr:
    STA $2007
    DEX
    BNE ClearAttr

    ; Draw top border - 32 tiles across row 0
    LDA #$20
    STA $2006
    LDA #$00
    STA $2006

    LDX #32                 ; 32 tiles wide
    LDA #$01                ; Tile $01 (solid white)
DrawTop:
    STA $2007
    DEX
    BNE DrawTop

    ; Reset scroll position
    LDA #$00
    STA $2005
    STA $2005

    ; Enable rendering
    LDA #%00001010          ; Enable background + leftmost 8 pixels
    STA $2001

MainLoop:
    JMP MainLoop

NMI:
    RTI

IRQ:
    RTI

.segment "VECTORS"
    .word NMI
    .word Reset
    .word IRQ

.segment "CHARS"
    ; Tile $00: Blank
    .byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 0
    .byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 1

    ; Tile $01: Solid white (colour 1)
    .byte $FF, $FF, $FF, $FF, $FF, $FF, $FF, $FF  ; Plane 0
    .byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 1

    .res 8192 - 32, $00
```

**Assemble this** with ca65 and ld65, then load in Mesen.

![Top border example](/images/nintendo-entertainment-system/phase-1/tier-1/lesson-002/top-border.png)

A white stripe appears across the top. Simple, but this demonstrates the entire tile rendering pipeline: CHR-ROM defines tile shapes, nametable says where they go, palette assigns colours.

## How This Works

### Tile Data in CHR-ROM

```nasm
.segment "CHARS"
    ; Tile $00: Blank
    .byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 0
    .byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 1

    ; Tile $01: Solid white
    .byte $FF, $FF, $FF, $FF, $FF, $FF, $FF, $FF  ; Plane 0
    .byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 1
```

**Tiles are 16 bytes** divided into two 8-byte planes. Each byte represents one row of 8 pixels. The PPU combines both planes to get 2 bits per pixel (4 colours per tile).

- **Plane 0 = 0, Plane 1 = 0**: Colour 0 (background colour from $3F00)
- **Plane 0 = 1, Plane 1 = 0**: Colour 1 (from $3F01)
- **Plane 0 = 0, Plane 1 = 1**: Colour 2 (from $3F02)
- **Plane 0 = 1, Plane 1 = 1**: Colour 3 (from $3F03)

Tile $01 has all bits set in plane 0 and all bits clear in plane 1. This makes every pixel colour 1, which we set to white ($30) at palette address $3F01.

### Writing to the Nametable

```nasm
LDA #$20                ; Nametable high byte
STA $2006               ; PPUADDR
LDA #$00                ; Nametable low byte
STA $2006               ; PPUADDR

LDX #32                 ; 32 tiles wide
LDA #$01                ; Tile $01
DrawTop:
    STA $2007           ; Write tile index
    DEX
    BNE DrawTop
```

The nametable at $2000-$23BF is a 32×30 grid. Each byte is a tile index referencing CHR-ROM. Writing $01 to address $2000 displays tile $01 at screen position (0, 0). Writing to $2001 displays tile $01 at position (1, 0). The loop writes 32 tiles across row 0.

**PPUADDR requires two writes**: high byte first, then low byte. After each write to PPUDATA ($2007), the address auto-increments (controlled by PPUCTRL bit 2, default +1).

### The Attribute Table

```nasm
LDA #$23
STA $2006
LDA #$C0
STA $2006

LDX #64                 ; 64 bytes
LDA #$00
ClearAttr:
    STA $2007
    DEX
    BNE ClearAttr
```

Every nametable has a 64-byte **attribute table** at $23C0-$23FF. Each byte controls a 32×32 pixel area (4×4 tiles), selecting which of the four background palettes each quadrant uses.

If you don't initialize this, garbage data causes tiles to use the wrong palette. Setting all attributes to $00 means every tile uses palette 0 (colours from $3F00-$3F03).

**Why clear both nametable and attributes?** At power-on, PPU memory contains random data. Explicitly clearing ensures consistent behaviour across emulators and real hardware.

### PPUMASK Bit 1

```nasm
LDA #%00001010          ; Enable background + leftmost 8 pixels
STA $2001
```

Lesson 1 used `%00001000` (only bit 3 = enable background). This **hides the leftmost 8 pixels** on each scanline. Real NES games use this to hide glitches during scrolling, but for our border, we need those pixels visible.

**Bit 1 = 1**: Show background in leftmost 8 pixels
**Bit 3 = 1**: Enable background rendering

Setting both (`$0A` = `%00001010`) displays the full screen width.

## Experiment: Complete Frame

Extend the border to all four edges. Create `frame-border.asm` by adding:

```nasm
; Draw bottom border (row 29)
LDA #$23                ; $2000 + (29 × 32) = $23A0
STA $2006
LDA #$A0
STA $2006

LDX #32
LDA #$01
DrawBottom:
    STA $2007
    DEX
    BNE DrawBottom

; Draw left side (rows 1-28, column 0)
LDY #1

DrawLeft:
    ; Calculate address high byte based on row
    LDA #$20
    CPY #8
    BCC :+
    LDA #$21
:   CPY #16
    BCC :+
    LDA #$22
:   CPY #24
    BCC :+
    LDA #$23
:   STA $2006

    ; Calculate address low byte: Y × 32
    TYA
    ASL                     ; Multiply by 32
    ASL
    ASL
    ASL
    ASL
    STA $2006

    LDA #$01
    STA $2007

    INY
    CPY #29
    BNE DrawLeft

; Draw right side (rows 1-28, column 31)
LDY #1

DrawRight:
    LDA #$20
    CPY #8
    BCC :+
    LDA #$21
:   CPY #16
    BCC :+
    LDA #$22
:   CPY #24
    BCC :+
    LDA #$23
:   STA $2006

    TYA
    ASL
    ASL
    ASL
    ASL
    ASL
    CLC
    ADC #31                 ; Add column offset
    STA $2006

    LDA #$01
    STA $2007

    INY
    CPY #29
    BNE DrawRight
```

![Frame border example](/images/nintendo-entertainment-system/phase-1/tier-1/lesson-002/frame-border.png)

Now a complete white frame surrounds the screen. This demonstrates **nametable address calculation**: address = $2000 + (row × 32) + column.

**Why the high byte checks?** When calculating `row × 32` in an 8-bit register, values above 255 wrap around. Rows 8-15 need high byte $21, rows 16-23 need $22, rows 24-29 need $23. This is a common NES programming pattern for multi-byte address arithmetic.

## Experiment: Different Patterns

Try modifying tile $01 in CHR-ROM:

```nasm
; Checkerboard pattern
.byte $AA, $55, $AA, $55, $AA, $55, $AA, $55  ; Plane 0
.byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 1

; Horizontal stripes
.byte $FF, $00, $FF, $00, $FF, $00, $FF, $00  ; Plane 0
.byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 1

; Diagonal pattern
.byte $80, $40, $20, $10, $08, $04, $02, $01  ; Plane 0
.byte $00, $00, $00, $00, $00, $00, $00, $00  ; Plane 1
```

Each creates a different border texture. The pattern shows how 8 bytes encode 8 rows of 8 pixels each.

## Emulator Notes

**Mesen**: Shows full screen correctly by default.

**FCEUX**: NTSC mode crops top/bottom edges (simulating real TV overscan). Use PAL mode (`Config → Region → PAL`) to see full screen during development.

**Real hardware**: CRT TVs hide 8-16 pixels around all edges (overscan). Commercial NES games avoid placing important UI elements near screen edges. Our borders work for learning, but production games would inset them 1-2 tiles.

## Quick Reference: PPU Memory Map

| Address Range | Purpose |
|--------------|---------|
| $0000-$0FFF | Pattern table 0 (256 tiles) |
| $1000-$1FFF | Pattern table 1 (256 tiles) |
| $2000-$23BF | Nametable 0 (960 bytes) |
| $23C0-$23FF | Attribute table 0 (64 bytes) |
| $2400-$27FF | Nametable 1 |
| $2800-$2BFF | Nametable 2 |
| $2C00-$2FFF | Nametable 3 |
| $3F00-$3F0F | Background palettes (16 bytes) |
| $3F10-$3F1F | Sprite palettes (16 bytes) |

## Quick Reference: Nametable Addressing

```nasm
; Formula: address = $2000 + (row × 32) + column
; Example: row 10, column 5
; Address = $2000 + (10 × 32) + 5 = $2000 + 320 + 5 = $2145
```

**Rows 0-7**: High byte = $20
**Rows 8-15**: High byte = $21
**Rows 16-23**: High byte = $22
**Rows 24-29**: High byte = $23

## Quick Reference: PPUMASK ($2001)

| Bit | Function |
|-----|----------|
| 0 | Greyscale (1 = greyscale mode) |
| 1 | Show background in leftmost 8 pixels |
| 2 | Show sprites in leftmost 8 pixels |
| 3 | Enable background rendering |
| 4 | Enable sprite rendering |
| 5-7 | Colour emphasis (BGR) |

**Common values:**
- `$00`: Rendering disabled (during setup)
- `$08`: Background only, leftmost 8 pixels hidden
- `$0A`: Background only, full screen width
- `$1E`: Background + sprites, full screen (typical gameplay value)

## What You've Learnt

- **Tiles are 16 bytes**—two 8-byte bitplanes encoding 2 bits per pixel
- **Nametable** at $2000-$23BF defines which tiles appear at each screen position
- **Attribute table** at $23C0-$23FF controls which palette each tile area uses
- **PPUADDR** ($2006) sets address with two writes (high byte, then low byte)
- **PPUDATA** ($2007) writes data and auto-increments address
- **PPUMASK bit 1** controls whether leftmost 8 pixels display
- **Address arithmetic** requires multi-byte calculations for rows beyond 7
- **Always clear nametable and attributes** to avoid garbage data
