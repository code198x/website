The NES renders graphics using 8×8 pixel tiles stored in CHR-ROM (Character ROM). Understanding how tiles are encoded and creating your first tile graphics is essential to building any NES game. This lesson introduces pattern tables, the 2-bit pixel format, and designing basic tiles for Pong.

Previous lessons established the game loop architecture. This lesson focuses on graphics data: how tiles are stored, how pixels are encoded, and how to create tiles that will form the Pong playfield.

## The One-Minute Tour

- **Pattern tables**—two 4KB banks ($0000-$0FFF, $1000-$1FFF) holding 512 tiles total
- **8×8 pixels per tile**—each tile covers 64 pixels arranged in 8 rows
- **2 bits per pixel**—supports 4 colours (0-3) from assigned palette
- **16 bytes per tile**—8 bytes for plane 0 (bit 0) + 8 bytes for plane 1 (bit 1)
- **CHR-ROM**—graphics stored in cartridge ROM chip, defined with `.segment "CHARS"`
- **Tile encoding**—draw pixel pattern, convert to hex bytes for both planes
- **$0000 table**—typically used for background tiles
- **$1000 table**—typically used for sprite tiles

## Your First Tiles

Create `basic-tiles.asm`:

```asm
.segment "HEADER"
    .byte "NES", $1A
    .byte 2
    .byte 1
    .byte $01, $00

.segment "CODE"
Reset:
    SEI
    CLD
    BIT $2002
:   BIT $2002
    BPL :-
:   BIT $2002
    BPL :-
    LDX #$FF
    TXS

    ; Set palette
    LDA #$3F
    STA $2006
    LDA #$00
    STA $2006
    LDA #$0F
    STA $2007

    LDA #%10000000
    STA $2000
    LDA #%00001000
    STA $2001

Forever:
    JMP Forever

NMI:
    RTI

IRQ:
    RTI

.segment "VECTORS"
    .word NMI
    .word Reset
    .word IRQ

.segment "CHARS"
    ; Tile $00: Blank
    .byte $00,$00,$00,$00,$00,$00,$00,$00
    .byte $00,$00,$00,$00,$00,$00,$00,$00

    ; Tile $01: Solid block
    .byte $FF,$FF,$FF,$FF,$FF,$FF,$FF,$FF
    .byte $FF,$FF,$FF,$FF,$FF,$FF,$FF,$FF

    ; Tile $02: Top border
    .byte $FF,$FF,$00,$00,$00,$00,$00,$00
    .byte $FF,$FF,$00,$00,$00,$00,$00,$00

    ; Tile $03: Center line
    .byte $18,$18,$18,$18,$18,$18,$18,$18
    .byte $18,$18,$18,$18,$18,$18,$18,$18

    ; Fill remaining tiles with blank
    .res 508*16, $00
```

This defines four tiles in CHR-ROM: blank, solid block, top border, and center line for Pong.

## How This Works

### Pattern Tables in PPU Memory

The PPU has 8KB of pattern table space divided into two 4KB banks:

```
$0000-$0FFF: Pattern table 0 (256 tiles)
$1000-$1FFF: Pattern table 1 (256 tiles)
```

Each bank holds 256 tiles. Each tile is 16 bytes, so 256 tiles × 16 bytes = 4096 bytes (4KB).

**Background vs sprites:** $2000 register (PPUCTRL) bit 4 selects which pattern table the background uses. Bit 3 selects which table sprites use. Both can use the same table or different tables. Pong uses pattern table 0 ($0000) for both.

### Tile Structure: 16 Bytes

Each tile consists of 8 rows. Each row is encoded in 2 bytes:
- **Plane 0** (byte 0-7): Provides bit 0 of each pixel
- **Plane 1** (byte 8-15): Provides bit 1 of each pixel

**Example: Solid white tile ($01)**

```
Plane 0: $FF,$FF,$FF,$FF,$FF,$FF,$FF,$FF
Plane 1: $FF,$FF,$FF,$FF,$FF,$FF,$FF,$FF

Each row: 11111111 in both planes
Result: All pixels = 3 (bit 1 = 1, bit 0 = 1)
```

### 2-Bit Pixel Encoding

Each pixel uses 2 bits to select one of 4 palette colours:

```
Pixel value = (Plane 1 bit << 1) | Plane 0 bit

Examples:
  Plane 0 bit = 0, Plane 1 bit = 0 → Pixel value = 0
  Plane 0 bit = 1, Plane 1 bit = 0 → Pixel value = 1
  Plane 0 bit = 0, Plane 1 bit = 1 → Pixel value = 2
  Plane 0 bit = 1, Plane 1 bit = 1 → Pixel value = 3
```

Pixel value 0-3 selects colour 0-3 from the tile's assigned palette (set in attribute table).

### Drawing the Center Line Tile

The center line in Pong is a dashed vertical line. Let's design tile $03:

**Pixel pattern (3 pixels wide in center):**
```
. . . 3 3 3 . .
. . . 3 3 3 . .
. . . 3 3 3 . .
. . . 3 3 3 . .
. . . 3 3 3 . .
. . . 3 3 3 . .
. . . 3 3 3 . .
. . . 3 3 3 . .
```

**Convert to binary (3 = bits 11):**
```
Row: 00011100 (plane 0) and 00011100 (plane 1)
Hex: $1C for both planes
```

But the example uses $18 (00011000), which creates a 2-pixel wide line:
```
. . . 3 3 . . .
```

**All 8 rows identical:**
```asm
.byte $18,$18,$18,$18,$18,$18,$18,$18  ; Plane 0
.byte $18,$18,$18,$18,$18,$18,$18,$18  ; Plane 1
```

### Top Border Tile Design

Top border tile ($02) has 2 solid rows at top, empty below:

```
3 3 3 3 3 3 3 3  → $FF,$FF (both planes)
3 3 3 3 3 3 3 3  → $FF,$FF
. . . . . . . .  → $00,$00
. . . . . . . .  → $00,$00
. . . . . . . .  → $00,$00
. . . . . . . .  → $00,$00
. . . . . . . .  → $00,$00
. . . . . . . .  → $00,$00
```

```asm
.byte $FF,$FF,$00,$00,$00,$00,$00,$00  ; Plane 0
.byte $FF,$FF,$00,$00,$00,$00,$00,$00  ; Plane 1
```

### CHR-ROM Segment

The `.segment "CHARS"` directive tells ca65 to place this data in the CHR-ROM section of the ROM file. The iNES header specifies 1 CHR-ROM bank (8KB).

```asm
.segment "CHARS"
    ; Tile data here (8192 bytes total)
```

**Important:** CHR-ROM is read-only. Once assembled into the ROM, tiles can't change at runtime (without mapper support for CHR-RAM). All graphics must be designed before assembly.

### Filling Remaining Tiles

```asm
.res 508*16, $00
```

This reserves 508 tiles worth of space (8128 bytes) filled with zeros. Blank tiles for now—next lessons will add more graphics.

**Math:** 512 total tiles - 4 defined tiles = 508 remaining tiles. 508 × 16 bytes = 8128 bytes.

## Designing Your Own Tiles

**Process:**
1. Draw 8×8 pattern on graph paper or pixel editor
2. Number pixels 0-3 (palette colours)
3. Convert each row to two bytes (plane 0 and plane 1)
4. Write as `.byte` directives in CHARS segment

**Example: "X" pattern**

```
Pixel pattern:
3 . . . . . . 3
. 3 . . . . 3 .
. . 3 . . 3 . .
. . . 3 3 . . .
. . . 3 3 . . .
. . 3 . . 3 . .
. 3 . . . . 3 .
3 . . . . . . 3
```

**Convert to binary:**
```
Row 0: 10000001 (plane 0) + 10000001 (plane 1) = $81,$81
Row 1: 01000010 + 01000010 = $42,$42
Row 2: 00100100 + 00100100 = $24,$24
Row 3: 00011000 + 00011000 = $18,$18
Row 4: 00011000 + 00011000 = $18,$18
Row 5: 00100100 + 00100100 = $24,$24
Row 6: 01000010 + 01000010 = $42,$42
Row 7: 10000001 + 10000001 = $81,$81
```

**In CHR-ROM:**
```asm
; Tile: "X" pattern
.byte $81,$42,$24,$18,$18,$24,$42,$81  ; Plane 0
.byte $81,$42,$24,$18,$18,$24,$42,$81  ; Plane 1
```

## Pixel Value vs Colour

Important distinction:

**Pixel value (0-3):** Encoded in tile data (pattern table).

**Colour:** Determined by palette entry. Pixel value indexes into palette.

Tile says "this pixel is value 3." Palette says "value 3 displays as colour $12 (blue)." Change the palette, same tile displays different colours. This separation enables colour cycling, palette swaps, and efficient graphics reuse.

## Quick Reference: Pattern Tables

### Memory Layout

| Address Range | Contents |
|---------------|----------|
| $0000-$0FFF | Pattern table 0 (256 tiles) |
| $1000-$1FFF | Pattern table 1 (256 tiles) |

### Tile Format

- **Size:** 8×8 pixels
- **Storage:** 16 bytes per tile
- **Encoding:** 2 bits per pixel (4 colours)
- **Structure:** 8 bytes plane 0 + 8 bytes plane 1

### Pixel Value Calculation

```
For each pixel:
  bit0 = (plane0_byte >> bit_position) & 1
  bit1 = (plane1_byte >> bit_position) & 1
  pixel_value = (bit1 << 1) | bit0

Result: 0-3 (indexes into palette)
```

### CHR-ROM Declaration

```asm
.segment "CHARS"
    ; Tile 0 (16 bytes)
    .byte $00,$00,$00,$00,$00,$00,$00,$00  ; Plane 0
    .byte $00,$00,$00,$00,$00,$00,$00,$00  ; Plane 1

    ; Tile 1 (16 bytes)
    .byte $FF,$FF,$FF,$FF,$FF,$FF,$FF,$FF
    .byte $FF,$FF,$FF,$FF,$FF,$FF,$FF,$FF

    ; ... more tiles ...
    .res (512-2)*16, $00  ; Fill remaining tiles
```
