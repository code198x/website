## Managing Multiple Entities

The player is simple — one `player_x`, one `player_y`. But what about 4 enemies?

We could create `enemy1_x`, `enemy2_x`, `enemy3_x`, `enemy4_x`... but that leads to copy-pasted code for each enemy. Tedious and error-prone.

The better approach: **parallel arrays**.

Now enemy 0's position is at `enemy_x+0` and `enemy_y+0`. Enemy 1 is at `enemy_x+1` and `enemy_y+1`. And so on.

The magic: we use the **X register as an index** to access all enemies with the same code.

## Indexed Addressing

The 6502's indexed addressing modes let us access array elements:

<CodeFromFile src="nintendo-entertainment-system/game-01-neon-nexus/unit-04/snippets/02-indexed-addressing.asm" lang="asm" />

The instruction `lda enemy_x, x` means "load from address (enemy_x + X)". If `enemy_x` is at $0010 and X is 2, it loads from $0012.

This is the key to processing multiple entities with a single loop.

## Moving Enemies

Now the interesting part. A single loop processes all 4 enemies:

<CodeFromFile src="nintendo-entertainment-system/game-01-neon-nexus/unit-04/snippets/04-moving-enemies.asm" lang="asm" />

**`inc enemy_y, x`** — Increment the byte at address (enemy_y + X). This single instruction moves whichever enemy X points to.

The loop:
1. Increments enemy Y position
2. Checks if enemy went off screen (Y >= 232)
3. If so, wraps back to Y = 0 (top of screen)
4. Moves to next enemy
5. Repeats until all 4 are processed

## Updating Sprites

Our `update_player` routine handles the player sprite at OAM position 0. Now we need to update enemy sprites at positions 1-4.

Each sprite uses 4 bytes in OAM:
- Sprite 0: bytes 0-3 ($0200-$0203) — the player
- Sprite 1: bytes 4-7 ($0204-$0207) — enemy 0
- Sprite 2: bytes 8-11 ($0208-$020B) — enemy 1
- Sprite 3: bytes 12-15 ($020C-$020F) — enemy 2
- Sprite 4: bytes 16-19 ($0210-$0213) — enemy 3

We need two indices: X for the enemy array (0-3) and Y for OAM (4, 8, 12, 16).

<CodeFromFile src="nintendo-entertainment-system/game-01-neon-nexus/unit-04/snippets/05-updating-sprites.asm" lang="asm" />

Notice we use **both X and Y as indices** simultaneously:
- X indexes into enemy arrays (0, 1, 2, 3)
- Y indexes into OAM (4, 5, 6, 7, 8, 9, ...)

After each sprite, Y advances by 4 bytes automatically (we `iny` four times), perfectly aligning with the next OAM slot.

## What You've Learnt

- **Parallel arrays** store related data at matching indices
- **Indexed addressing** (`lda table, x`) accesses array elements
- **Loops with indices** process multiple entities efficiently
- **OAM layout** maps sequential 4-byte blocks to sprites
- **Multiple indices** (X and Y) handle offset calculations
