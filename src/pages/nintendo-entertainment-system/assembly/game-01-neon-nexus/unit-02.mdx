## Hardware Sprites

The NES handles moving objects differently from the background. While backgrounds use nametables and attribute tables, sprites live in a special 256-byte area inside the PPU called **OAM** (Object Attribute Memory).

OAM holds data for 64 sprites. Each sprite uses exactly 4 bytes:

| Byte | Purpose | Range |
|------|---------|-------|
| 0 | Y Position | 0-239 (top to bottom) |
| 1 | Tile Index | 0-255 (which graphic) |
| 2 | Attributes | Palette, flip, priority |
| 3 | X Position | 0-255 (left to right) |

The attribute byte packs several options into 8 bits:

```
76543210
||||||||
||||||++- Palette (0-3) — which of the 4 sprite palettes
|||+++--- Unused
||+------ Priority: 0 = in front of background, 1 = behind
|+------- Flip horizontally
+-------- Flip vertically
```

## The Shadow OAM Problem

Here's a catch: you can only write to PPU memory during **vertical blank** — the brief pause between frames when the screen isn't being drawn. If you try to write while the PPU is rendering, you get garbage.

Writing 256 bytes one at a time during vblank is slow. The NES solves this with **DMA** (Direct Memory Access).

DMA works like this:
1. Keep a copy of sprite data in CPU RAM (the "shadow OAM")
2. During vblank, write a single byte to register $4014
3. The CPU halts while hardware copies all 256 bytes to PPU OAM

The byte you write to $4014 is the **high byte** of your shadow OAM address. If your buffer is at $0200, you write $02. The hardware copies $0200-$02FF to OAM automatically.

This is why we reserved $0200-$02FF when setting up memory — it's our shadow OAM buffer.

## Clearing Shadow OAM

Before we use sprites, we need to initialise shadow OAM. If we leave it as zeros, all 64 sprites appear at position (0, 0) — a mess of overlapping graphics in the top-left corner.

The trick: set all Y positions to $FF (255). Since the visible screen is only 240 lines tall, Y=$FF pushes sprites off the bottom where they're invisible.

## The DMA Transfer

In the NMI handler, we trigger the DMA copy every frame:

<CodeFromFile src="nintendo-entertainment-system/game-01-neon-nexus/unit-02/snippets/04-the-dma-transfer.asm" lang="asm" />

**New instructions:**

**`pha`** — "Push Accumulator." Saves A to the stack. We preserve registers at the start of the interrupt handler so we don't corrupt whatever the main program was doing.

**`txa`** / **`tya`** — "Transfer X/Y to Accumulator." We can't push X and Y directly, so we move them to A first, then push.

**`pla`** — "Pull Accumulator." Pops a value from the stack into A. We restore registers in reverse order (last pushed = first pulled).

The DMA sequence:
1. Write $00 to OAMADDR to reset the OAM write pointer
2. Write $02 to OAMDMA to copy $0200-$02FF to OAM

This happens every frame, even though our sprite isn't moving yet. When we add movement later, shadow OAM will update between frames, and DMA will push those changes to the PPU.

## The Ship Graphic

We need a tile for our player. NES tiles are 8×8 pixels with 2 bits per pixel (4 colours). Each tile uses 16 bytes: 8 for bit plane 0, 8 for bit plane 1.

The two planes combine to select colours:
- Plane 0 = 0, Plane 1 = 0 → Colour 0 (transparent for sprites)
- Plane 0 = 1, Plane 1 = 0 → Colour 1
- Plane 0 = 0, Plane 1 = 1 → Colour 2
- Plane 0 = 1, Plane 1 = 1 → Colour 3

## What You've Learnt

- **OAM** holds 64 sprites, 4 bytes each (Y, Tile, Attributes, X)
- **Shadow OAM** at $0200 lets us manipulate sprites in CPU RAM
- **DMA** via $4014 copies 256 bytes to PPU OAM in one operation
- **$FF for Y** hides sprites by pushing them off-screen
- **Sprite tiles** use 2-bit planar format, same as background tiles
- **Register preservation** (pha/pla) protects the main program during interrupts
