You've learnt about raster synchronization (L57) and built racing games with side-by-side players (L50). Now let's attempt something that seems logical: a split-screen racing game where each player gets a full horizontal view instead of being cramped side-by-side.

**This lesson reveals BASIC's synchronization precision limit**—raster splits. Commercial C64 games like International Karate and Pitstop II have clean split-screen effects with different views for each player. When you try to replicate that in BASIC, you'll discover why: BASIC's ~10ms execution overhead means register changes happen 157 scanlines late, causing splits to wander randomly between frames.

The key discovery: **Raster splits require cycle-accurate timing**. BASIC can read $D012 (raster position) but can't wait for specific scanlines reliably. By the time PEEK checks and conditional branches execute, the raster beam has moved far past your target line. This isn't a speed problem you can optimise—it's a synchronisation precision boundary.

---

## The One-Minute Tour

**Split-Screen Concept:**
- **Top half** shows player 1's view of the track
- **Bottom half** shows player 2's view of the track
- **Mid-screen register change** at line 125 to switch scroll offsets
- **Each player** gets full 40-column horizontal view (better than cramped side-by-side)

**The Timing Problem:**
- **Target scanline 125** mid-screen split point
- **BASIC overhead** ~10ms (10,000µs) to PEEK, check, and POKE
- **Scanline duration** 63.5µs window for register change
- **Delay calculation** 10,000µs ÷ 63.5µs = 157 scanlines late!

**What You'll See:**
- **Split wanders** appears at line 138, 142, 129, 155, 131 (inconsistent)
- **Border colours chase** colour changes happen 30-50 lines late
- **Screen tearing** top/bottom views tear into each other
- **Completely unusable** worse than cramped side-by-side layout

## The Scanline Timing Problem

**What split-screen needs:**
```
Frame 1:
Line 100: <- Change registers for player 1 HERE (blue border)
Line 125: <- Change registers for player 2 HERE (red border)
Result: Clean split at line 125 every frame
```

**What BASIC does:**
```
Frame 1:
Line 100: BASIC starts checking PEEK(53266)
Line 135: BASIC finally POKEs blue border (35 lines late!)
Line 170: BASIC finally POKEs red border (45 lines late!)
Result: Split at line 170 (not 125)

Frame 2:
Line 100: BASIC starts checking PEEK(53266)
Line 142: BASIC finally POKEs blue border (42 lines late!)
Line 176: BASIC finally POKEs red border (51 lines late!)
Result: Split at line 176 (not 125)

Frame 3: Split at line 163
Frame 4: Split at line 151
...
Result: Split "wanders" up and down screen
```

**The timing maths:**
```
One scanline duration: 63.5µs
BASIC PEEK overhead: ~5,000µs (5ms)
BASIC IF comparison: ~2,000µs (2ms)
BASIC POKE overhead: ~3,000µs (3ms)
Total: ~10,000µs (10ms)

Delay in scanlines: 10,000µs ÷ 63.5µs = 157 scanlines!

Target line: 100
Actual line: 100 + 157 = 257 (wraps to ~line 135-170)
```

By the time BASIC finishes checking `IF PEEK(53266)<100`, the raster has drawn 157 more lines. The split appears **far past your target line** and at **different positions each frame**.

## Why $D012 Reading Fails

**VIC-II register $D012 (53266):**
- Current raster line (0-311)
- Bit 8 stored in $D011 bit 7 for lines 256-311
- Updates every 63.5µs as raster draws

**Attempt to wait for specific line:**
```basic
100 REM WAIT FOR LINE 125
110 IF PEEK(53266)<>125 THEN 110
120 REM UPDATE REGISTERS
130 POKE 53270,SCROLL_VALUE
```

**Problems:**
1. **PEEK overhead** ~5ms to read and compare
2. **Missed window** by time condition is false, raster at line 130+
3. **Inconsistent** sometimes catches 126, sometimes 135, sometimes 142
4. **No way to pause** can't freeze execution until exact moment
5. **Race condition** reading → checking → branching → POKE all take time

The fundamental issue: **BASIC can read raster position but can't synchronise to it**. Reading $D012 tells you where the raster **was**, not where it **is now** (by the time you've read and acted on it).

## The Border Colour "Chase" Effect

**Visible symptom of late timing:**
```basic
100 REM ATTEMPT COLOUR SPLIT
110 IF PEEK(53266)<100 THEN 110
120 POKE 53280,6:REM BLUE
130 IF PEEK(53266)<125 THEN 130
140 POKE 53280,2:REM RED
```

**What you see:**
```
Raster draws line 100: Border is still previous colour
Raster draws line 101: Border is still previous colour
...
Raster draws line 135: BASIC finally POKEs blue
Raster draws line 136: Border is blue NOW (35 lines late!)
...
Raster draws line 170: BASIC finally POKEs red
Raster draws line 171: Border is red NOW (45 lines late!)

Result: You see a blue "bar" from line 135-170
        You see a red "bar" from line 170-250
        The colours "chase" the raster down the screen
        Every frame they appear at different positions
```

This visible "chase" effect proves the timing problem. You can **see** the delay as coloured bars that wobble frame-to-frame.

## What Commercial Games Do

**Games with split-screen (International Karate, Pitstop II):**
```assembly
; Pseudocode (assembly)
; Set raster interrupt at line 125
LDA #125
STA $D012        ; Raster line for interrupt
LDA #<IRQ_SPLIT
STA $0314        ; IRQ vector low
LDA #>IRQ_SPLIT
STA $0315        ; IRQ vector high

IRQ_SPLIT:
  ; CPU interrupted at EXACT line 125
  LDA PLAYER2_SCROLL
  STA $D016      ; Change scroll instantly (4 cycles = ~4µs)
  LDA #2
  STA $D020      ; Change border colour
  RTI            ; Return from interrupt
```

**Key differences from BASIC:**
- **Raster interrupt** CPU automatically jumps to code at exact line
- **Assembly speed** register updates take 2-4 cycles (~2-4µs, not 10,000µs)
- **Cycle-accurate** happens at same cycle every frame (not 157 lines late)
- **Multiple interrupts** can chain splits at lines 125, 150, 175, etc.
- **BASIC has none** no interrupts, too slow, no cycle accuracy

The 4µs assembly timing fits comfortably in the 63.5µs scanline window. BASIC's 10,000µs timing misses the window by 157x.

## Hardware Limitation Summary

**What BASIC can do:**
- Read $D012 raster position ✓
- POKE to $D016, $D020 registers ✓
- Create split-screen layout in memory ✓

**What BASIC can't do:**
- Wait for exact scanline reliably ✗
- Update registers in ~63.5µs window ✗
- Set raster interrupts (requires machine code) ✗
- Achieve consistent frame timing ✗

**Conclusion:** Can access raster position but can't synchronise with it. This is a **precision limit**, not a speed limit. No optimisation makes 10,000µs fit in a 63.5µs window.

## Common Pitfalls

1. **Think reading $D012 is enough** can read position but not sync to it
2. **Optimise the waiting loop** no optimisation makes 10ms → 63.5µs
3. **Add delay with FOR loops** makes it worse (even more inconsistent)
4. **Try different target lines** fundamental limit applies to all lines
5. **Think it "almost works"** inconsistent splits are unusable, not "close"

The problem isn't your code—it's BASIC's ~10ms overhead versus the ~63.5µs window.

## What You've Learnt

- **Split-screen racing** needs mid-frame register changes at exact scanlines
- **Raster position reading** $D012 tells you where raster was, not where it is now
- **Timing precision** 10,000µs BASIC overhead vs 63.5µs scanline window = 157 line delay
- **Wandering splits** appear at different positions each frame (unusable)
- **Border colour chase** visible proof of timing delay (30-50 lines late)
- **Assembly interrupts** only way to achieve cycle-accurate raster synchronisation
- **Precision boundary** this is synchronisation precision, not execution speed

**The Discovery:** "I attempted split-screen racing to give each player a full horizontal view. I could read the raster position with PEEK($D012) and wait for line 125, but by the time BASIC checked and updated registers, the raster had moved 157 lines past my target. The split appeared at inconsistent positions (138, 142, 129, 155) and border colours chased the raster down the screen 30-50 lines late. The single-screen side-by-side racing was cramped but consistent. This split-screen attempt is broken and unusable. Split-screen effects need raster interrupts to synchronise register changes with scanline timing, which requires assembly."

**The Lesson:** Reading hardware registers ($D012) and writing to registers ($D016) isn't enough for raster effects. Split-screen needs to synchronise updates with the raster's position, requiring register changes in a ~63.5µs window. BASIC's interpreter overhead (~10,000µs) misses this window by 157 scanlines, causing splits to wander. Raster interrupts (assembly only) allow the CPU to execute code at exact scanlines, achieving clean splits. This is a synchronisation precision limit—no optimisation bridges the 157x timing gap.

## Quick Reference

**Raster Position:**
```
$D012 (53266): Current raster line (0-255)
$D011 bit 7: Raster line bit 8 (for 256-311)

Read with: LINE=PEEK(53266)
Full line: LINE=PEEK(53266) OR ((PEEK(53265) AND 128)*2)
```

**Horizontal Scroll:**
```
$D016 (53270): Horizontal fine scroll
Bits 0-2: Scroll offset (0-7 pixels)
Bits 3-7: Other VIC-II settings

Update with: POKE 53270,(PEEK(53270) AND 248) OR OFFSET
```

**Border Colour:**
```
$D020 (53280): Border colour (0-15)

Update with: POKE 53280,COLOUR
```

**Timing Problem:**
```
Scanline duration: 63.5µs
BASIC PEEK: ~5,000µs (5ms)
BASIC conditional: ~2,000µs (2ms)
BASIC POKE: ~3,000µs (3ms)
Total BASIC overhead: ~10,000µs (10ms)

Result: 10,000µs ÷ 63.5µs = 157 scanlines of delay
        Misses target by 157 lines!
```

**Split-Screen Technique (Assembly):**
```assembly
; Set interrupt at line 125
LDA #125
STA $D012

; Interrupt handler runs at exact line
IRQ:
  LDA PLAYER2_SCROLL
  STA $D016        ; 4 cycles (~4µs)
  RTI

Result: Updates in 4µs window (not 10,000µs)
```

**Border Colour Test:**

```basic
- Red bar from ~165-180 (not 125-150)
- Blue bar from ~185-250 (not 150-end)
- Bars "wobble" position frame-to-frame
```
