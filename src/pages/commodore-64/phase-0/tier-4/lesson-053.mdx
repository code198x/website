You've built RPGs with multiple rooms. You've created inventory systems and quest tracking. Now let's attempt something that feels achievable: a Metroidvania-style game with 50 interconnected rooms, backtracking, and exploration.

**This lesson reveals BASIC's data overhead limitation**—as world complexity grows, the overhead of checking, loading, and processing room data creates visible delays. Commercial Metroidvanias like Super Metroid manage massive interconnected worlds smoothly. When you try to replicate that scope in BASIC, you'll discover why: every room transition requires checking dozens of arrays, making navigation feel slow.

The key discovery: **Scale compounds overhead exponentially**. Each new room, item, or enemy adds more arrays to initialise, more data to read, more conditions to check. This isn't a problem you can optimise away—it's a fundamental limitation of BASIC's interpreted nature working with large datasets.

---

## The One-Minute Tour

**Metroidvania Mechanics:**
- **50-room interconnected world** with north/south/east/west navigation
- **Backtracking** revisit earlier rooms with new abilities or keys
- **Items to collect** scattered across rooms (keys, upgrades, quest items)
- **Enemies to defeat** blocking progress or guarding treasure
- **Map system** tracks visited rooms and shows connections

**The Scale Problem:**
- **20-30 second load time** reading 1000+ DATA statements into arrays
- **Visible delays** (300-500ms) entering each room as code checks all systems
- **No actual room graphics** just text descriptions (graphics would be slower)
- **Overhead compounds** each feature (items, enemies, quests) multiplies delay

**What Large-Scale Games Need:**
- **Fast data loading** from disk or pre-compiled memory structures
- **Efficient lookup** hash tables or indexed arrays (BASIC has linear search only)
- **Compiled code** assembly executes lookup/check logic instantly
- **Optimised rendering** hardware sprites and character sets (not BASIC PRINT)

## Why Scale Creates Overhead

**Data initialisation cost:**
- **50 room names** = 50 string reads from DATA
- **50 descriptions** = another 50 string reads
- **200 exit values** = 50 rooms × 4 directions each
- **150 enemy values** = 50 rooms × 3 enemies each
- **Total:** 1000+ READ operations taking 20-30 seconds

**Per-room overhead:**
- Check if item collected: `IF IC(CR)=0 AND RI(CR)<>0`
- Loop through 3 enemy slots checking defeat status
- Loop through 4 exit directions to display available paths
- Each check takes milliseconds, but they compound

**Map display overhead:**
```basic
7050 FOR I=1 TO 50
7060 IF RF(I)=1 THEN PRINT I;": ";RN$(I)
7070 NEXT I
```
This loops through 50 rooms, checking the "visited" flag for each. On a fast C64, this takes 500-800ms. In a compiled language or assembly, it would be instant.

## The Optimisation Attempts

You might try reducing the overhead:

**1. Fewer rooms:**
```basic
REM REDUCE TO 25 ROOMS
```
**Result:** Load time drops to 10-15 seconds, but you've cut world size in half. Still not "smooth."

**2. Lazy loading:**
```basic
REM ONLY READ DATA FOR CURRENT ROOM
```
**Result:** Reduces startup, but each room entry reads DATA (even slower per-room)

**3. Compressed data:**
```basic
REM USE SHORTER STRINGS, CODES INSTEAD OF NAMES
```
**Result:** Saves memory, but READ/parsing still slow

**The lesson:** Optimisations reduce the problem but don't eliminate it. BASIC's interpreted nature means every array lookup, string comparison, and loop iteration has overhead. Commercial Metroidvanias use compiled code with optimised data structures.

## Commercial Metroidvanias

**Super Metroid (SNES, 1994):**
- Hundreds of interconnected rooms
- Instant room transitions
- Complex enemy AI and physics
- Assembly language throughout

**Metroid (NES, 1986):**
- 256 rooms in interconnected grid
- Smooth scrolling between rooms
- Multiple item upgrades unlocking backtracking
- 100% assembly language

**What they have in common:**
- **Compiled code** instant array lookups and conditionals
- **Optimised data structures** room data pre-loaded into memory
- **Hardware scrolling** VIC-II/PPU smooth pixel scrolling
- **Fast rendering** sprite hardware, not PRINT loops

## Alternative: Smaller Scopes Work

**What works well in BASIC:**
```basic
REM 8-10 ROOM ADVENTURE (TIER 3 SCOPE)
100 DIM RN$(10),RD$(10),EX(10,4)
110 CR=1
120 REM INSTANT LOADING, INSTANT NAVIGATION
```

**Result:**
- Loads in 2-3 seconds
- Room transitions feel instant
- All features (items, enemies, quests) work smoothly
- Tier 3 RPG (Lesson 46) proved this scope is BASIC's sweet spot

**The boundary:**
- 8-10 rooms: Works perfectly
- 20-30 rooms: Noticeable delays starting
- 50+ rooms: Navigation feels sluggish

## From the Vault

**C64 Memory Constraints:**
- **38911 bytes** available for BASIC program and variables
- String arrays consume memory rapidly (50 room names ≈ 2KB)
- Each DIM statement allocates memory upfront
- Large worlds quickly approach memory limit

**Programming Reference:**
- Appendix F: "String memory management and garbage collection"
- Appendix G: "OUT OF MEMORY errors typically occur with large string arrays"

**Commercial game technique:**
- Procedural generation (create rooms algorithmically, not store all data)
- Compression (pack multiple values into single bytes)
- Bank switching (swap memory banks to access more data)

## Quick Reference

**Data Loading Overhead:**
```basic
REM 50 ROOMS × 20 VALUES EACH = 1000 READS
9000 FOR I=1 TO 50
9010 READ RN$(I),RD$(I)
9020 NEXT I
REM Result: 20-30 seconds on C64
```

**Room Transition Overhead:**
```basic
1000 REM DISPLAY ROOM - THIS TAKES TIME
1010 PRINT CHR$(147)             :REM Clear screen
1020 PRINT "LOADING...";         :REM User sees delay
1030 FOR I=1 TO 500:NEXT I       :REM Simulate overhead
1040 REM Check items, enemies, exits...
REM Result: 300-500ms per room
```

**Array Lookup Cost:**
- Single lookup: `X=EX(CR,N)` - instant
- Loop through 50: `FOR I=1 TO 50` - 500-800ms
- String operations: Slower than numeric (parsing overhead)
