You've built RPGs with multiple features. You've created games with NPCs, quests, and inventory. Now let's attempt something ambitious: an open world game with time, weather, NPC schedules, quest triggers, and combat—all running simultaneously.

**This lesson reveals BASIC's system interaction overhead**—when multiple features need to check and update each other (weather affects combat, time moves NPCs, quests trigger on location), the interactions compound. Commercial open world games like Ultima manage dozens of interacting systems smoothly. When you try to replicate that in BASIC, you'll discover why: each system adds overhead, and interactions multiply the cost.

The key discovery: **Systems don't just add—they multiply**. A time system alone is cheap. A weather system alone is cheap. But time affecting weather, weather affecting combat, NPCs moving based on time, quests checking location and time—that's exponential overhead. This isn't fixable through optimisation—it's the cost of complex state management in interpreted BASIC.

---

## The One-Minute Tour

**Open World Systems:**
- **8-room world** with interconnected navigation
- **Time system** clock advances, day/night cycle
- **Weather system** random changes (sunny, rain, night)
- **NPC schedules** 3 NPCs move between rooms based on time
- **Quest system** 2 active quests with progress tracking
- **Inventory** 5 item slots
- **Combat** simple enemy encounters

**The Interaction Problem:**
- **300-500ms delays** entering rooms (all systems update)
- **Every action checks multiple systems** move room → check quests → update NPCs → advance time
- **Systems cross-reference** weather affects combat, NPCs check time, quests check location
- **No single bottleneck** overhead distributed across all interactions

**What Open World Games Need:**
- **Event-driven updates** only run systems when state changes (not every loop)
- **Optimised state checks** hash tables, not linear array scans
- **Compiled logic** instant conditional evaluation
- **Memory-efficient state** packed data structures (BASIC uses separate arrays for everything)

**What happens when you run this:**

1. **Every loop updates world state** (lines 1000-1095): time, weather, NPC movement
2. **Entering rooms takes 300ms** "LOADING..." delay visible (line 2020)
3. **Moving triggers quest checks** (line 4190): room change cross-checks quest state
4. **Combat checks weather** (line 5050): systems interact, adding conditionals
5. **NPC dialogue checks time/quests/friendship** (lines 6130-6190): three system interactions

**The interaction revelation:** No single system is slow. But:
- Time system checks → weather system
- Weather system affects → combat outcomes
- NPC positions checked → every room display
- Quest triggers checked → every room change
- All running → every main loop iteration

Each interaction adds overhead. With 7 systems interacting, overhead compounds.

## Why System Interactions Compound Overhead

**Every main loop iteration:**
```basic
350 GOSUB 1000:REM UPDATE WORLD STATE
1030 IF TM-LT<30 THEN 1060    :REM Check timer
1040 GOSUB 1100                :REM Time events
1100   IF HR>=20 THEN WE=3    :REM Time → weather
1220 IF RND(1)<0.02 THEN WE=2 :REM Random weather
1320 FOR I=1 TO 3              :REM Move NPCs
1390   IF EX(R,D)<>0...        :REM Check exits
```

**Every room change:**
```basic
4170 CR=EX(CR,DR)              :REM Move to new room
4190 GOSUB 4210                :REM Check quests
4220   IF QS(1)=1 AND CR=5... :REM Quest trigger
2000 GOSUB 2000                :REM Display room
2140 FOR I=1 TO 3              :REM Check NPCs
2150   IF NR(I)=CR...          :REM Is NPC here?
2180 FOR I=1 TO 2              :REM Check enemies
```

**Every combat:**
```basic
5050 IF WE=2 THEN...           :REM Weather affects combat
5070 IF RND(1)<0.5...           :REM Combat resolution
5080 HP=HP-5:XP=XP+10          :REM Update stats
```

None of these alone are expensive. But running all of them every action creates cumulative overhead. BASIC interprets every IF, every array lookup, every GOSUB—it adds up.

## The Optimisation Attempts

You might try reducing interactions:

**1. Update systems less frequently:**
```basic
1030 IF TM-LT<300 THEN 1060:REM UPDATE EVERY 5 SECONDS
```
**Result:** Reduces overhead slightly, but NPCs/weather feel frozen. Doesn't solve root problem.

**2. Remove a system:**
```basic
REM REMOVE WEATHER SYSTEM ENTIRELY
```
**Result:** Improves performance marginally, but world feels static. You wanted rich interactions.

**3. Simplify interactions:**
```basic
REM WEATHER DOESN'T AFFECT COMBAT
5050 REM IF WE=2 THEN...
```
**Result:** Faster, but less immersive. The interactions are what make an open world feel alive.

**The lesson:** You can reduce features or simplify interactions, but you can't build a richly interactive open world in BASIC without hitting overhead walls. Turn-based games avoid this (Tier 3's RPG worked perfectly) because only one system runs at a time.

## Commercial Open World Games

**Ultima IV (C64, 1985):**
- 256 towns and dungeons
- NPC schedules (move based on time)
- Weather, moon phases affecting magic
- Complex quest system
- **Mostly assembly language** with BASIC menu system

**Elite (C64, 1984):**
- Procedurally generated galaxy
- Trading, combat, reputation systems
- All systems interact (combat affects reputation, reputation affects prices)
- **100% assembly language**

**What they have in common:**
- **Compiled code** instant conditional checks
- **Optimised state management** packed data structures
- **Event-driven updates** systems only run when triggered (not every loop)
- **Memory efficiency** single bytes store multiple state flags

## What You've Discovered

**Today you learnt:**

- **System interactions multiply overhead** time → weather → combat = 3× checks
- **No single bottleneck** overhead distributed across all system interactions
- **300-500ms delays** entering rooms because all systems update/check
- **Optimisation requires removing features** can't keep rich interactions and smooth performance
- **Turn-based avoids problem** Tier 3's RPG ran one system at a time (perfect performance)

**The boundary:**
- BASIC: Focused games (2-3 systems), turn-based sequencing
- Assembly: Open worlds (many systems), real-time interactions

**Why this matters:**
- Tier 3's RPG (8 rooms, quests, inventory) felt instant
- This open world (8 rooms, time, weather, NPCs, quests) feels sluggish
- Same room count—difference is system interactions
- Pattern: BASIC handles depth (complex single systems) better than breadth (many interacting systems)

## From the Vault

**State Management in BASIC:**
- Each system requires separate arrays (time, weather, NPCs, quests)
- Every interaction requires array lookups and conditionals
- No built-in hash tables or optimised data structures
- String operations (time parsing) add overhead

**C64 Performance Guidelines:**
- Keep game loops under 100ms for 10 fps feel
- Each GOSUB adds ~1-2ms overhead
- String operations 5-10× slower than numeric
- Array lookups fast, but checking all elements slow

**Commercial technique:**
- Bit packing (store 8 flags in 1 byte, not 8 variables)
- Event queues (trigger updates, don't poll every loop)
- State machines (clear transitions, not continuous checks)
