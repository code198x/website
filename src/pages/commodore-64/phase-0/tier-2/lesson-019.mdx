## Bringing Sprites to Life

Static sprites are useful for testing, but games need movement. The VIC-II updates sprite positions every frame—change the position registers, and the sprite moves instantly. This lesson shows how to animate sprites through X/Y coordinate updates and handle the full horizontal screen range using the MSB (most significant bit) register.

---

### The One-Minute Tour

- X position: $D000 (53248) stores values 0-255 (low byte)
- Y position: $D001 (53249) stores values 0-255 (full range)
- X MSB register: $D010 (53264) extends X to 0-511
- Bit 0 of $D010 controls sprite 0's ninth X bit
- Movement loop: read position → add velocity → write position
- Delay loops control animation speed

---

### Example Program

```basic
10 REM MOVE SPRITE HORIZONTALLY
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM ENABLE SPRITE
70 POKE 2040,13:POKE 53287,7:POKE 53269,1
80 X=50:Y=120
90 REM MAIN LOOP
100 POKE 53248,X:POKE 53249,Y
110 X=X+2
120 IF X>255 THEN X=50
130 FOR D=1 TO 50:NEXT D
140 GOTO 100
150 DATA 0,24,0,0,60,0,0,126,0
160 DATA 0,255,0,1,255,128,3,255,192
170 DATA 7,255,224,15,255,240,31,255,248
180 DATA 3,255,192,3,255,192,3,255,192
190 DATA 3,255,192,3,255,192,3,255,192
200 DATA 1,255,128,0,255,0,0,126,0
210 DATA 0,60,0,0,24,0,0,0,0
```

![Yellow arrow sprite moving across the screen](/images/commodore-64/phase-0/tier-2/lesson-019/example-1.png)

**Line 80** initializes position variables (X=50, Y=120). **Line 100** updates sprite position registers. **Line 110** increments X by 2 pixels per frame. **Line 120** wraps X back to 50 when it exceeds 255. **Line 130** delay loop controls speed (higher value = slower).

> **Note:** This example only moves within X=0-255 range. For full-screen movement (X=0-511), you need the MSB register covered in the next example.

**Lines 100-110** handle MSB logic: when X < 256, clear bit 0 of $D010 (MSB=0) and write X directly. When X >= 256, set bit 0 of $D010 (MSB=1) and write X-256 to the low byte. This allows the sprite to traverse the full 0-511 X range.

### Concept Expansion

**The VIC-II Coordinate System**

The VIC-II uses different coordinate systems for sprites versus the character screen:

- Character screen: 40 columns × 25 rows (fixed grid)
- Sprites: X=0-511, Y=0-255 (pixel coordinates)
- Visible screen area: roughly X=24-344, Y=50-250
- Sprites can move partially off-screen (hardware clips them)

**Why 9 Bits for X?**

The C64 screen is wider than 256 pixels. To support positions 256-511, the VIC-II needs a ninth bit for each sprite's X coordinate. Since registers are 8 bits, the designers used $D010 as a shared MSB register:

- Bit 0 = sprite 0 MSB
- Bit 1 = sprite 1 MSB
- Bit 2 = sprite 2 MSB
- ... (up to bit 7 = sprite 7 MSB)

**MSB Register Logic**

When X >= 256:
1. Set sprite's MSB bit: `POKE 53264,1` (for sprite 0)
2. Write low 8 bits: `POKE 53248,X-256`

When X < 256:
1. Clear sprite's MSB bit: `POKE 53264,0`
2. Write X directly: `POKE 53248,X`

For multiple sprites, use OR logic to combine MSB bits: `POKE 53264, (sprite0msb) OR (sprite1msb*2) OR (sprite2msb*4)` etc.

**Movement Patterns**

Common velocity patterns:

- **Constant velocity**: `X=X+2` (steady horizontal movement)
- **Acceleration**: `VX=VX+1:X=X+VX` (speed increases over time)
- **Bouncing**: `X=X+VX:IF X>320 OR X<24 THEN VX=-VX` (reverse direction at edges)
- **Sine wave**: Use SIN() for smooth curves (covered in later lessons)

**Frame Rate and Timing**

The delay loop (`FOR D=1 TO 50:NEXT D`) controls how many BASIC interpreter cycles pass between position updates. The VIC-II updates the screen 50 times per second (PAL) or 60 times per second (NTSC), but BASIC is much slower. Without the delay, sprites would move too fast to see.

### How Games Use This

**Impossible Mission** (1984, Epyx): Your agent's horizontal movement used this exact X/Y update pattern. When running left/right, the game incremented X by 2-4 pixels per frame depending on whether you were walking or running.

**Paradroid** (1985, Hewson): The player droid's movement combined X/Y updates with joystick input. Each frame read the joystick, calculated new X/Y coordinates, handled MSB for wide screens, then updated position registers.

**Uridium** (1986, Hewson): Your spaceship's smooth horizontal scrolling required precise MSB handling as it moved across massive battleship landscapes wider than 511 pixels (multiple screen widths).

**Boulder Dash** (1984, First Star): Rockford's walking animation combined sprite movement (X/Y updates) with sprite shape changes (switching between walking frames). The game used a fixed velocity of 2 pixels per frame for consistent movement speed.

### Quick Reference

**Sprite 0 Position Registers:**
```
$D000 (53248) : X position low byte (0-255)
$D001 (53249) : Y position (0-255)
$D010 (53264) : X position MSB (bit 0 for sprite 0)
```

**X Coordinate Ranges:**
| X Value | MSB Bit | Low Byte | Screen Position    |
|---------|---------|----------|-------------------|
| 0-255   | 0       | 0-255    | Left side         |
| 256-511 | 1       | 0-255    | Right side        |
| 24      | 0       | 24       | Left edge visible |
| 344     | 1       | 88       | Right edge visible|

**Movement Pattern Examples:**
```basic
REM Horizontal movement
X=X+2:POKE 53248,X

REM Vertical movement
Y=Y+1:POKE 53249,Y

REM Diagonal movement
X=X+2:Y=Y+1
POKE 53248,X:POKE 53249,Y

REM Bounce at edges
X=X+VX
IF X<24 OR X>320 THEN VX=-VX
```

### What You've Learnt

- Sprite animation works by updating position registers
- X coordinate range is 0-511 (9 bits total)
- Y coordinate range is 0-255 (8 bits)
- $D010 (53264) holds MSB for all 8 sprites
- X < 256: clear MSB, write X directly
- X >= 256: set MSB, write X-256 to low byte
- Delay loops control animation speed
- Movement patterns combine position updates with logic
