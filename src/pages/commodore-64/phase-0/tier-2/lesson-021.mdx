## Hardware-Assisted Hit Detection

Position-based collision detection requires comparing X/Y coordinates and sprite sizes—complex mathematics in BASIC. The VIC-II provides dedicated hardware collision registers that automatically detect when sprites overlap each other or background graphics. This lesson shows how to read these registers for instant, accurate collision detection without calculations.

---

### The One-Minute Tour

- Sprite-to-sprite register: $D01E (53278) reports which sprites have collided
- Sprite-to-background register: $D01F (53279) reports sprites hitting foreground pixels
- Each bit represents one sprite (bit 0 = sprite 0, bit 1 = sprite 1, etc.)
- Reading the register clears it for next frame
- Collision detection happens automatically every frame
- No complex coordinate math required

### Example Program

```basic
10 REM SPRITE COLLISION DETECTION
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM SETUP TWO SPRITES
70 POKE 2040,13:POKE 2041,13
80 POKE 53287,7:POKE 53288,2
90 POKE 53269,3
100 X0=50:Y0=120:X1=250:Y1=120
110 VX0=2:VX1=-2
120 REM MAIN LOOP
130 X0=X0+VX0:X1=X1+VX1
140 IF X0<24 OR X0>255 THEN VX0=-VX0:X0=X0+VX0
150 IF X1<24 OR X1>255 THEN VX1=-VX1:X1=X1+VX1
160 POKE 53248,X0:POKE 53249,Y0
170 POKE 53250,X1:POKE 53251,Y1
180 C=PEEK(53278)
190 IF C>0 THEN POKE 53280,C:GOTO 210
200 POKE 53280,6
210 FOR D=1 TO 30:NEXT D
220 GOTO 130
230 DATA 0,24,0,0,60,0,0,126,0
240 DATA 0,255,0,1,255,128,3,255,192
250 DATA 7,255,224,15,255,240,31,255,248
260 DATA 3,255,192,3,255,192,3,255,192
270 DATA 3,255,192,3,255,192,3,255,192
280 DATA 1,255,128,0,255,0,0,126,0
290 DATA 0,60,0,0,24,0,0,0,0
```

![Two sprites moving towards each other with border changing colour on collision](/images/commodore-64/phase-0/tier-2/lesson-021/example-1.png)

**Line 180** reads the sprite collision register ($D01E). **Lines 190-200** change the border colour when collision detected (C>0) or restore it to blue (6) when no collision. **Lines 140-150** ensure positions stay within 0-255 range by reversing velocity and immediately correcting position when bounds hit. The act of reading the register (line 180) automatically clears it for the next frame.

> **Note:** The collision register uses bit flags—sprite 0 colliding sets bit 0 (value 1), sprite 1 sets bit 1 (value 2), both colliding sets bits 0+1 (value 3). For simple detection, just check if the value is greater than zero.

### Concept Expansion

**Collision Register Architecture**

The VIC-II maintains two 8-bit collision registers:

```
$D01E (53278): Sprite-to-Sprite Collision
- Bit 0 = sprite 0 collided with another sprite
- Bit 1 = sprite 1 collided with another sprite
- ...
- Bit 7 = sprite 7 collided with another sprite

$D01F (53279): Sprite-to-Background Collision
- Bit 0 = sprite 0 hit foreground pixel
- Bit 1 = sprite 1 hit foreground pixel
- ...
- Bit 7 = sprite 7 hit foreground pixel
```

These registers update automatically every frame. The VIC-II compares sprite pixel positions during raster scanning and sets bits when overlaps occur.

**Reading Clears the Register**

CRITICAL: `PEEK(53278)` or `PEEK(53279)` automatically resets the register to zero. This means:

1. You must store the value: `C=PEEK(53278)`
2. Check the stored value: `IF C>0 THEN...`
3. Don't PEEK twice in the same frame—you'll get zero the second time

**What Counts as a Collision?**

- **Sprite-to-sprite**: Any non-transparent sprite pixels overlap
- **Sprite-to-background**: Sprite pixel overlaps any character with foreground colour set (not background colour 0)
- Sprite priority (behind/in front of background) doesn't affect collision detection
- Sprite colour doesn't matter—transparent vs. solid is all that counts

**Bit Flag Logic**

For advanced collision checking:

```basic
REM Check if sprite 0 collided
IF (C AND 1) > 0 THEN PRINT "SPRITE 0 HIT"

REM Check if sprite 1 collided
IF (C AND 2) > 0 THEN PRINT "SPRITE 1 HIT"

REM Check if sprite 2 collided
IF (C AND 4) > 0 THEN PRINT "SPRITE 2 HIT"
```

The AND operator masks specific bits. Sprite N uses bit N, which has value 2^N.

**Collision Response Patterns**

Common game responses to collisions:

1. **Reverse direction**: Bullets bounce, player stops
2. **Destroy sprite**: Disable sprite (clear bit in $D015)
3. **Score update**: Increment score variable
4. **State change**: Set flag for game logic
5. **Sound effect**: POKE sound registers

**Performance Advantage**

Manual collision detection in BASIC:

```basic
REM Check if two 24x21 sprites overlap
IF X0<X1+24 AND X0+24>X1 AND Y0<Y1+21 AND Y0+21>Y1 THEN...
```

This is complex, slow, and error-prone. Hardware detection is instant and accurate—one PEEK operation per frame.

### Common Mistakes

**Problem 1: Collision Always Returns Zero**
```basic
IF PEEK(53278)>0 THEN PRINT "HIT"  REM Never detects!
IF PEEK(53278)>0 THEN POKE 53280,2 REM Still never works!
```
**Diagnosis:** Two PEEKs in same frame. First PEEK clears the register, second PEEK reads zero.

**Fix:** Store the PEEK result once, then check the variable:
```basic
C=PEEK(53278)
IF C>0 THEN PRINT "HIT"
IF C>0 THEN POKE 53280,2  REM Now it works!
```
**Why:** Reading collision registers automatically clears them to zero. Store the value in a variable (C) so you can test it multiple times without re-reading the register.

**Problem 2: Collision Detection Intermittent**
```basic
C=PEEK(53278)
IF C=1 THEN PRINT "SPRITES HIT"  REM Sometimes misses collisions!
```
**Diagnosis:** Checking for exact value 1. When sprite 1 collides, C=2. When both sprites collide, C=3.

**Fix:** Check if C is greater than zero for any collision:
```basic
C=PEEK(53278)
IF C>0 THEN PRINT "SPRITES HIT"  REM Catches all collisions
```
**Why:** Collision register uses bit flags (sprite 0=1, sprite 1=2, sprite 2=4, etc.). Value depends on which sprites collided. Use `C>0` for "any collision" or `(C AND n)>0` for specific sprite n.

**Problem 3: Background Collision Never Triggers**
```basic
REM Draw wall with background colour
FOR I=0 TO 21
  POKE 1024+I,160:POKE 55296+I,0  REM Colour 0!
NEXT
C=PEEK(53279)  REM Always zero!
```
**Diagnosis:** Character cells use background colour 0. Sprite-to-background only detects foreground pixels.

**Fix:** Use non-zero colour for wall characters:
```basic
FOR I=0 TO 21
  POKE 1024+I,160:POKE 55296+I,1  REM Colour 1 (white)
NEXT
C=PEEK(53279)  REM Now detects collision!
```
**Why:** $D01F detects sprite pixels overlapping character foreground colour. Colour 0 is treated as background/transparent—no collision detected. Use any colour 1-15 for solid walls.

**Problem 4: Sprites "Stick Together" After Collision**
```basic
C=PEEK(53278)
IF C>0 THEN VX0=-VX0:VX1=-VX1  REM Sprites stuck!
```
**Diagnosis:** Sprites still overlapping after reversing velocity. Collision register stays set every frame, velocity keeps reversing.

**Fix:** Push sprites apart immediately after collision:
```basic
C=PEEK(53278)
IF C>0 THEN VX0=-VX0:VX1=-VX1:X0=X0+VX0*2:X1=X1+VX1*2
```
**Why:** Reversing velocity isn't enough if sprites still overlap. Move sprites 2 pixels in new direction (VX*2) to separate them before next frame. Otherwise collision register stays set and velocities oscillate every frame.

### How Games Use This

**Impossible Mission** (1984, Epyx): Used sprite-to-background collision to detect when the agent touched platforms, lifts, and furniture. Falling was disabled when standing on solid objects detected via $D01F.

**Paradroid** (1985, Hewson): Sprite-to-sprite collisions triggered the "influence device" transfer game when your droid touched an enemy. The collision register identified which enemy droid for the puzzle difficulty.

**Boulder Dash** (1984, First Star): Rockford (sprite 0) used sprite-to-sprite collision to collect diamonds (sprites 1-4) and sprite-to-background collision to detect wall impacts. The game checked specific bit patterns to identify which diamond was collected.

**Uridium** (1986, Hewson): Player ship used sprite-to-sprite for bullet hits on enemies and sprite-to-background for crashing into the battleship surface. Different collision types triggered different visual effects and scoring.

### Quick Reference

**Collision Registers:**
```
$D01E (53278): Sprite-to-Sprite Collision
$D01F (53279): Sprite-to-Background Collision
```

**Bit Values:**
| Sprite | Bit | Value |
|--------|-----|-------|
| 0      | 0   | 1     |
| 1      | 1   | 2     |
| 2      | 2   | 4     |
| 3      | 3   | 8     |
| 4      | 4   | 16    |
| 5      | 5   | 32    |
| 6      | 6   | 64    |
| 7      | 7   | 128   |

**Detection Pattern:**
```basic
REM Read collision register
C=PEEK(53278)    REM or 53279

REM Simple check (any collision)
IF C>0 THEN PRINT "COLLISION!"

REM Specific sprite check
IF (C AND 1)>0 THEN PRINT "SPRITE 0"
IF (C AND 2)>0 THEN PRINT "SPRITE 1"
```
