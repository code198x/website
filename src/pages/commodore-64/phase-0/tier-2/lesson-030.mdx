You've mastered momentum physics where movement is in any direction. Now discover rotation—the ability to face different directions and thrust in the direction you're facing. This is Asteroids-style control: rotate left/right, thrust forward, and momentum carries you through space. The VIC-II doesn't rotate sprites in hardware, so you'll learn the classic technique of pre-drawing rotated sprite frames and switching between them.

**Rotation transforms movement from grid-based to true 2D navigation.** The difference is thinking in angles rather than just X/Y velocities.

## The One-Minute Tour

- **Rotation tracks facing direction** using an angle variable (0-2π radians) that changes with left/right joystick input
- **Sprite frames create rotation illusion** with 8 pre-drawn sprites (0°, 45°, 90°, etc.) switched by changing sprite pointer
- **Trigonometry converts angle to direction** using COS(angle) for horizontal and SIN(angle) for vertical components
- **Thrust accelerates in facing direction** adding velocity components: VX=VX+THRUST×COS(AN), VY=VY+THRUST×SIN(AN)
- **Velocity magnitude limits speed** using Pythagoras (V=√(VX²+VY²)) to clamp maximum speed whilst preserving direction
- **Screen wrapping creates infinite space** with sprites exiting left appearing right, creating classic Asteroids feel
- **Physics parameters combine** rotation speed, thrust power, and friction to define ship handling characteristics

## How Sprite Rotation Works

**The VIC-II limitation:**
The VIC-II can flip sprites horizontally or vertically (via register 53277), but it cannot rotate them to arbitrary angles. There's no "rotate sprite by 45 degrees" register.

**The classic solution:**
```basic
100 REM DRAW 8 SPRITE FRAMES (DONE ONCE)
110 REM FRAME 0: ARROW POINTING UP
120 REM FRAME 1: ARROW POINTING UP-RIGHT (45°)
130 REM FRAME 2: ARROW POINTING RIGHT (90°)
140 REM ... UP TO FRAME 7 (315°)
```

Each sprite frame is 63 bytes (21 rows × 3 bytes). Store 8 frames sequentially in memory, then switch between them by changing the sprite pointer at address 2040 (for sprite 0).

**Angle to frame conversion:**
```basic
100 F=INT((AN/(2*PI))*8)  :REM ANGLE TO FRAME
110 POKE 2040,13+F         :REM CHANGE SPRITE POINTER
```

If angle AN=0 (pointing up), frame F=0, pointer=13 (sprite at 832).
If angle AN=π (pointing down), frame F=4, pointer=17 (sprite at 1088).
The calculation divides the full circle (2π radians) into 8 equal segments.

## Understanding Trigonometry

**BASIC's SIN and COS functions** convert an angle into X/Y components. On a unit circle:

```
COS(angle) = horizontal component (-1 to +1)
SIN(angle) = vertical component (-1 to +1)
```

**Key angles (in radians):**
- 0 rad (0°): COS=1, SIN=0 → pointing right
- π/2 rad (90°): COS=0, SIN=1 → pointing down
- π rad (180°): COS=-1, SIN=0 → pointing left
- 3π/2 rad (270°): COS=0, SIN=-1 → pointing up

**Wait, why is 0° pointing right?**
Because that's how the unit circle works in mathematics. In our sprite frames, we've drawn frame 0 pointing up for visual clarity, but mathematically, angle 0 corresponds to "east" on a compass. The maths and visuals don't have to match perfectly—we're using trigonometry for direction vectors, not screen angles.

**The screen coordinate gotcha:**
On the C64 screen, Y increases downward (Y=50 at top, Y=229 at bottom). In maths, Y typically increases upward. This means SIN gives you downward motion when you might expect upward. You can invert with `-SIN(AN)` if needed, but for space games like Asteroids, the direction doesn't matter—as long as thrust goes forward relative to the ship.

## Adding Thrust

Now combine rotation with momentum physics:

```basic
10 REM ROTATION AND THRUST
20 PRINT CHR$(147)
30 PRINT "ROTATE WITH JOYSTICK LEFT/RIGHT"
40 PRINT "THRUST WITH FIRE BUTTON"
50 PRINT
60 PRINT "PRESS ANY KEY TO START"
70 GET K$:IF K$="" THEN 70
80 PRINT CHR$(147)
90 GOSUB 9000
100 REM SETUP SPRITE
110 POKE 53248,160:POKE 53249,100
120 POKE 53269,1:POKE 53287,1
130 REM PHYSICS VARIABLES
140 X=160:Y=100
150 VX=0:VY=0
160 AN=0
170 RO=0.1
180 TH=0.08
190 FR=0.99
200 PI=3.14159
210 REM MAIN LOOP
220 GOSUB 1000
230 GOSUB 2000
240 GOSUB 3000
250 GOSUB 4000
260 GOSUB 5000
270 GOTO 220
1000 REM JOYSTICK CONTROLS
1010 J=PEEK(56320)
1020 IF (J AND 4)=0 THEN AN=AN-RO
1030 IF (J AND 8)=0 THEN AN=AN+RO
1040 IF AN<0 THEN AN=AN+2*PI
1050 IF AN>=2*PI THEN AN=AN-2*PI
1060 IF (J AND 16)=0 THEN GOSUB 1500
1070 RETURN
1500 REM APPLY THRUST
1510 VX=VX+TH*COS(AN)
1520 VY=VY+TH*SIN(AN)
1530 V=SQR(VX*VX+VY*VY)
1540 IF V>3 THEN VX=VX*3/V:VY=VY*3/V
1550 RETURN
2000 REM APPLY FRICTION
2010 VX=VX*FR:VY=VY*FR
2020 IF ABS(VX)<0.05 THEN VX=0
2030 IF ABS(VY)<0.05 THEN VY=0
2040 RETURN
3000 REM UPDATE POSITION
3010 X=X+VX:Y=Y+VY
3020 IF X<24 THEN X=X+296
3030 IF X>320 THEN X=X-296
3040 IF Y<50 THEN Y=Y+179
3050 IF Y>229 THEN Y=Y-179
3060 RETURN
4000 REM UPDATE SPRITE
4010 SX=INT(X)
4020 IF SX>255 THEN POKE 53264,1:SX=SX-256
4030 IF SX<=255 THEN POKE 53264,0
4040 POKE 53248,SX
4050 POKE 53249,INT(Y)
4060 RETURN
5000 REM UPDATE SPRITE ROTATION
5010 F=INT((AN/(2*PI))*8+0.5)
5020 IF F>=8 THEN F=0
5030 POKE 2040,13+F
5040 RETURN
```

*[Lines 9000-9650 contain sprite data as in example 1]*

**Run this** and use the joystick to rotate (left/right) and thrust (fire button). The ship rotates in place, and thrust accelerates in the direction it's facing. Release the fire button and the ship continues drifting—classic Asteroids physics.

![Asteroids-style ship with rotation and thrust control](/images/commodore-64/phase-0/tier-2/lesson-030/screenshot-1.png)

The key is subroutine 1500 (lines 1510-1520): thrust adds velocity components based on current angle. Rotation (lines 1020-1030) changes the angle variable AN, which determines where thrust points. Physics (friction, position update) remains separate from rotation—they're independent systems that combine to create realistic ship control.

## Breaking Down the Thrust System

**Rotation control (lines 1020-1050):**
```basic
1020 IF (J AND 4)=0 THEN AN=AN-RO  :REM LEFT
1030 IF (J AND 8)=0 THEN AN=AN+RO  :REM RIGHT
1040 IF AN<0 THEN AN=AN+2*PI       :REM WRAP NEGATIVE
1050 IF AN>=2*PI THEN AN=AN-2*PI   :REM WRAP POSITIVE
```

Variable RO (rotation speed) is 0.1 radians per frame. Joystick left/right changes angle AN. Wrapping (lines 1040-1050) keeps angle in range 0-2π. Without wrapping, AN could become -5 or 10, breaking the frame calculation.

**Thrust application (lines 1510-1520):**
```basic
1510 VX=VX+TH*COS(AN)  :REM HORIZONTAL THRUST
1520 VY=VY+TH*SIN(AN)  :REM VERTICAL THRUST
```

This is **vector addition**. Thrust TH (0.08 pixels/frame²) splits into horizontal (COS) and vertical (SIN) components. These add to existing velocity VX/VY, allowing thrust in one direction whilst drifting in another—the essence of momentum-based space flight.

**Velocity clamping (lines 1530-1540):**
```basic
1530 V=SQR(VX*VX+VY*VY)            :REM SPEED MAGNITUDE
1540 IF V>3 THEN VX=VX*3/V:VY=VY*3/V  :REM SCALE TO MAX
```

Without clamping, repeated thrust builds infinite velocity. Line 1530 calculates total speed using Pythagoras. If speed exceeds maximum (3 pixels/frame), line 1540 scales both VX and VY proportionally, preserving direction but limiting speed. This is magnitude-based clamping—better than clamping VX and VY independently, which creates diamond-shaped movement boundaries.

**Screen wrapping (lines 3020-3050):**
```basic
3020 IF X<24 THEN X=X+296     :REM WRAP LEFT
3030 IF X>320 THEN X=X-296    :REM WRAP RIGHT
3040 IF Y<50 THEN Y=Y+179     :REM WRAP TOP
3050 IF Y>229 THEN Y=Y-179    :REM WRAP BOTTOM
```

Instead of bouncing or stopping at edges, the ship wraps to the opposite side. Exit left at X=24, appear right at X=320. This creates infinite space—the signature feel of Asteroids. Velocity doesn't change during wrapping, so momentum carries across the seam.

## Physics Parameter Tuning

**Change these variables to alter ship feel:**

```basic
170 RO=0.1     :REM Rotation speed (radians/frame)
180 TH=0.08    :REM Thrust power (pixels/frame²)
190 FR=0.99    :REM Friction multiplier (0.90-0.99)
```

**Fast rotation (RO=0.15):** Ship spins quickly, easier to aim but less precise.
**Slow rotation (RO=0.05):** Ship turns slowly, feels heavy or damaged.
**Strong thrust (TH=0.15):** Accelerates rapidly, good for chase games.
**Weak thrust (TH=0.04):** Feels underpowered, good for fuel-limited gameplay.
**High friction (FR=0.90):** Ship slows quickly, feels like flying through atmosphere.
**Low friction (FR=0.99):** Ship drifts for ages, feels like deep space.

**Try this:** Set RO=0.2, TH=0.15, FR=0.85. Now the ship is nimble and responsive with strong braking—perfect for obstacle courses or tight spaces.

## Why 8 Frames?

**More frames = smoother rotation:**
- 4 frames: Rotation looks chunky (90° jumps)
- 8 frames: Good balance of smoothness and memory (45° jumps)
- 16 frames: Very smooth (22.5° jumps) but uses 1008 bytes

**8 frames is the sweet spot** for most games. It looks smooth enough, uses 504 bytes (8 sprites × 63 bytes), and leaves memory for other sprites (bullets, asteroids, explosions).

**Frame storage layout:**
```
Frame 0 (0°):   Memory 832-894   (pointer 13)
Frame 1 (45°):  Memory 896-958   (pointer 14)
Frame 2 (90°):  Memory 960-1022  (pointer 15)
Frame 3 (135°): Memory 1024-1086 (pointer 16)
Frame 4 (180°): Memory 1088-1150 (pointer 17)
Frame 5 (225°): Memory 1152-1214 (pointer 18)
Frame 6 (270°): Memory 1216-1278 (pointer 19)
Frame 7 (315°): Memory 1280-1342 (pointer 20)
```

Each pointer increments by 1, each memory block increments by 64 (sprite size including padding byte).

## Common Mistakes

**Mistake 1: Forgetting angle wrapping**
```basic
1020 IF (J AND 4)=0 THEN AN=AN-0.1
```
Without wrapping (lines 1040-1050), angle becomes negative after rotating left. Frame calculation breaks, giving garbage sprite pointers. Always wrap angle to 0-2π range.

**Mistake 2: Using degrees instead of radians**
```basic
1510 VX=VX+TH*COS(AN)  :REM AN IN DEGREES - WRONG!
```
BASIC's SIN/COS expect radians (0-6.28), not degrees (0-360). Conversion: RADIANS = DEGREES × π / 180. For rotation games, work in radians throughout—it's simpler.

**Mistake 3: Clamping VX and VY independently**
```basic
1540 IF VX>3 THEN VX=3   :REM SQUARE BOUNDARY
1550 IF VY>3 THEN VY=3
```
This creates a diamond-shaped maximum speed zone. Use magnitude clamping (√(VX²+VY²)) for circular speed limits—diagonal thrust should have same maximum speed as horizontal thrust.

**Mistake 4: Applying thrust every frame**
```basic
220 GOSUB 1500  :REM THRUST ALWAYS ON
```
Thrust should only apply when fire button is pressed. Otherwise the ship accelerates continuously, never slowing down. Check joystick port (IF (J AND 16)=0) before calling thrust subroutine.

**Mistake 5: Wrong sprite pointer arithmetic**
```basic
140 POKE 2040,F  :REM FRAME 0-7 DIRECTLY
```
Frame numbers (0-7) aren't sprite pointers. Sprite pointers are memory addresses divided by 64. Frame 0 at memory 832 needs pointer 13 (832÷64=13). Add frame to base: POKE 2040,13+F.

## Expanding the System

**Add thrust animation:**
```basic
1510 VX=VX+TH*COS(AN)
1520 VY=VY+TH*SIN(AN)
1530 POKE 53269,3  :REM ENABLE SPRITES 0 AND 1
1540 REM POSITION SPRITE 1 BEHIND SHIP FOR EXHAUST FLAME
```

**Implement hyperspace (instant teleport):**
```basic
1080 IF (J AND 16)=0 AND K=1 THEN X=RND(1)*255:Y=RND(1)*180+50
```

**Add rotation inertia:**
```basic
160 AN=0:AV=0  :REM ADD ANGULAR VELOCITY
1020 IF (J AND 4)=0 THEN AV=AV-0.01
1030 IF (J AND 8)=0 THEN AV=AV+0.01
1040 AN=AN+AV:AV=AV*0.95  :REM APPLY AND DECAY
```

**Create reverse thrust (braking):**
```basic
1500 IF (J AND 2)=0 THEN VX=VX-TH*COS(AN):VY=VY-TH*SIN(AN)
```

## From the Vault

**Asteroids (1979):** The granddaddy of rotation-and-thrust games. Used vector graphics (beam drawn on oscilloscope monitor) but same physics: rotate ship, thrust forward, momentum carries you. The C64 port used sprite rotation like our example.

**Thrust (1986):** Added gravity and fuel limits. Thrust consumed fuel, running out meant drifting helplessly. Rotation was instant (no frames), but momentum physics were identical—thrust in facing direction, friction slowed you down.

**Gravitar (1982):** Combined rotation-thrust with planetary gravity. Each planet pulled your ship toward its centre, requiring constant thrust corrections. Vector maths (COS/SIN) calculated gravity direction just like our thrust code.

## What You've Learnt

- **Sprite rotation** through frame switching creates rotation illusion without hardware rotation capability
- **Trigonometry** (SIN/COS) converts angles into direction vectors for realistic 2D physics
- **Directional thrust** accelerates in facing direction, independent of current velocity (momentum)
- **Magnitude clamping** limits total speed whilst preserving direction vector
- **Angle wrapping** keeps rotation angle in valid range (0-2π) for frame calculations
- **Screen wrapping** creates infinite play area by teleporting sprites across edges
- **Physics parameters** (rotation speed, thrust power, friction) define gameplay feel and balance
