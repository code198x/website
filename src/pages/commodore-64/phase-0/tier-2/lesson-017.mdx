## Beyond Characters

In Tier 1, you drew graphics using screen memory—characters and PETSCII symbols arranged on a 40×25 grid. This works for static layouts and text adventures, but action games need something faster: **hardware sprites**. The VIC-II chip can display up to 8 independent graphical objects that move smoothly across the screen without touching screen memory at all.

---

### The One-Minute Tour

- VIC-II has 8 hardware sprites (24×21 pixels each)
- Sprites overlay the character screen—they don't erase or move text
- Position controlled by dedicated registers ($D000-$D00F)
- Enable register ($D015) turns sprites on/off
- Sprite pointers (2040-2047) define which sprite data to display
- Default sprite data exists at block 13 (memory 832)

---

### Example Program

```basic
10 REM ENABLE SPRITE 0
20 REM FIRST, CREATE SIMPLE SPRITE DATA
30 FOR I=0 TO 62:POKE 832+I,255:NEXT
40 REM NOW POSITION AND ENABLE SPRITE
50 POKE 53248,160:POKE 53249,120
60 POKE 2040,13
70 POKE 53269,1
80 GET A$:IF A$="" THEN 80
```

![White sprite block displayed center-screen](/images/commodore-64/phase-0/tier-2/lesson-017/example-1.png)

**Line 30** fills sprite data with 255 (all pixels on) creating a solid block. **Lines 50** position sprite 0 at X=160, Y=120 (center screen). **Line 60** points sprite 0 to data block 13 (memory 832). **Line 70** enables sprite 0 (bit 0 of $D015). **Line 80** waits for keypress.

> **Note:** Sprite coordinates are different from character positions. X ranges 0-511 (needs 9 bits), Y ranges 0-255. The screen visible area is roughly X=24-344, Y=50-250.

### Experiment Section

Try these variations:

- **Different positions**: Change lines 50 to move the sprite around
- **Top-left corner**: `POKE 53248,24:POKE 53249,50`
- **Bottom-right**: `POKE 53248,320:POKE 53249,229` (see Extended Positioning below)
- **Sprite visibility**: What happens if you set Y to 0 or 255?

Now add colour to your sprite:

```basic
10 REM COLORED SPRITE
20 REM CREATE SIMPLE SPRITE SHAPE
30 FOR I=0 TO 62:POKE 832+I,255:NEXT
40 REM POSITION SPRITE CENTER SCREEN
50 POKE 53248,160:POKE 53249,120
60 POKE 2040,13
70 POKE 53287,7:REM SPRITE 0 COLOR = YELLOW
80 POKE 53269,1:REM ENABLE SPRITE 0
90 GET A$:IF A$="" THEN 90
```

![Yellow sprite block displayed center-screen](/images/commodore-64/phase-0/tier-2/lesson-017/example-2.png)

**Line 70** sets sprite 0's colour to yellow (7). Each sprite has its own colour register at $D027-$D02E (53287-53294).

### Concept Expansion

**Why Sprites Instead of Screen Memory?**

In Tier 1, moving an @ character meant:
1. POKE 32 (space) to erase old position
2. Calculate new screen address (1024 + Y\*40 + X)
3. POKE character code to new position

For smooth animation, this is slow. **Hardware sprites**:
- VIC-II draws them automatically every frame
- No screen memory calculations needed
- Move independently of the 40×25 character grid
- Overlay everything (characters, graphics, background)

**The VIC-II Sprite System**

The VIC-II chip has dedicated circuitry for sprites. When you POKE a position register, the chip immediately starts drawing that sprite at the new location on the next frame. This happens in hardware—no BASIC interpreter overhead.

**8 Sprites Maximum**

The VIC-II can display 8 sprites simultaneously (numbered 0-7). Each has:
- X/Y position registers (2 bytes each)
- Colour register (1 byte, 16 colours)
- Sprite pointer (tells which data to display)
- Enable bit (in $D015 register)

**Sprite Data Format**

Each sprite is 24×21 pixels (3 bytes wide × 21 rows = 63 bytes). Plus 1 padding byte = 64 bytes per sprite. The C64 stores sprite data in 64-byte blocks. Block 13 starts at memory 832 (13 × 64 = 832).

Filling sprite data with 255 creates a solid block because 255 in binary is 11111111 (all 8 pixels on in that byte).

**Extended Positioning (X > 255)**

X positions above 255 require the most significant bit (MSB) register at $D010 (53264). We'll cover this in Lesson 19 when sprites move horizontally across the entire screen.

### How Games Use This

**Pac-Man** (1983, Atarisoft): Pac-Man, ghosts, and fruits were all sprites moving independently over the maze background (which was screen characters).

**Impossible Mission** (1984, Epyx): Your agent was sprite 0. Enemy robots were sprites 1-3. The platforming environment was drawn with screen memory, but all moving objects were sprites.

**Uridium** (1986, Hewson): Your ship, enemy fighters, and bullets were sprites. The scrolling landscape underneath was bitmap graphics, but sprites overlaid it all.

**Boulder Dash** (1984, First Star): Rockford (the player) was a sprite. Falling boulders and diamonds were sprites. The dirt and walls were character graphics that sprites moved through.

### Quick Reference

**Sprite 0 Registers:**
```
$D000 (53248) : X position low byte
$D001 (53249) : Y position
$D010 (53264) : X position MSB (bit 0 for sprite 0)
$D015 (53269) : Sprite enable (bit 0 for sprite 0)
$D027 (53287) : Sprite 0 colour
2040 (screen+$3F8) : Sprite 0 pointer
```

**Sprite Data Location:**
```
Block 13 = Memory 832-895 (13 × 64)
Pointer value: 13
63 bytes of pixel data + 1 padding byte
```

**Colour Values:**
| Value | Colour      | Value | Colour       |
|-------|-------------|-------|--------------|
| 0     | Black       | 8     | Orange       |
| 1     | White       | 9     | Brown        |
| 2     | Red         | 10    | Light Red    |
| 3     | Cyan        | 11    | Dark Grey    |
| 4     | Purple      | 12    | Grey         |
| 5     | Green       | 13    | Light Green  |
| 6     | Blue        | 14    | Light Blue   |
| 7     | Yellow      | 15    | Light Grey   |

### What You've Learnt

- VIC-II sprites are hardware-accelerated graphical objects
- 8 sprites available (numbered 0-7)
- Position registers control X/Y coordinates
- Enable register ($D015) turns sprites on/off
- Colour registers ($D027-$D02E) set individual sprite colours
- Sprite pointers (2040-2047) select which data block to display
- Sprites overlay character screen without erasing it
- Default sprite data exists at block 13 (memory 832)
