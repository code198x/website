## Beyond One Sprite

Single-sprite programs teach the mechanics, but games need multiple moving objects: players, enemies, bullets, power-ups. The VIC-II supports up to 8 sprites—this lesson shows how to manage 2-4 sprites with independent positions and movements, building toward complete sprite-based games.

---

### The One-Minute Tour

- Each sprite has its own position registers (X, Y)
- Sprite 0: $D000-$D001, Sprite 1: $D002-$D003, etc.
- Enable register ($D015) controls all sprites with bit flags
- Each sprite needs its own sprite pointer (2040-2047)
- Track positions with separate variables (X0, Y0, X1, Y1, etc.)
- Update all sprites each frame in sequence

---

### Example Program

```basic
10 REM TWO SPRITES IN FORMATION
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM SETUP SPRITES 0 AND 1
70 POKE 2040,13:POKE 2041,13
80 POKE 53287,7:POKE 53288,14
90 POKE 53269,3
100 X=50:Y=100
110 REM MAIN LOOP
120 POKE 53248,X:POKE 53249,Y
130 POKE 53250,X+30:POKE 53251,Y
140 X=X+2
150 IF X>240 THEN X=50
160 FOR D=1 TO 50:NEXT D
170 GOTO 120
180 DATA 0,24,0,0,60,0,0,126,0
190 DATA 0,255,0,1,255,128,3,255,192
200 DATA 7,255,224,15,255,240,31,255,248
210 DATA 3,255,192,3,255,192,3,255,192
220 DATA 3,255,192,3,255,192,3,255,192
230 DATA 1,255,128,0,255,0,0,126,0
240 DATA 0,60,0,0,24,0,0,0,0
```

![Two yellow and light blue sprites moving in formation](/images/commodore-64/phase-0/tier-2/lesson-020/example-1.png)

**Line 70** sets both sprite pointers to block 13 (same shape for both). **Line 80** sets sprite 0 yellow (7), sprite 1 light blue (14). **Line 90** enables both sprites (bits 0 and 1 = binary 11 = decimal 3). **Lines 120-130** update positions—sprite 1 is offset 30 pixels right from sprite 0.

> **Note:** This uses a single X/Y variable pair since the sprites move together. For independent movement, each sprite needs its own position variables.

Try these variations:

- **Different colours**: Line 80 — try different colour combinations
- **Vertical offset**: Line 130 — `POKE 53251,Y+20` puts sprite 1 below sprite 0
- **More sprites**: Add sprite 2 by including `POKE 2042,13`, `POKE 53289,2`, change line 90 to `POKE 53269,7` (binary 111 = sprites 0,1,2)

### Concept Expansion

**Sprite Register Organization**

The VIC-II organizes sprite registers in pairs:

```
Sprite 0: $D000 (X), $D001 (Y)
Sprite 1: $D002 (X), $D003 (Y)
Sprite 2: $D004 (X), $D005 (Y)
...
Sprite 7: $D00E (X), $D00F (Y)
```

This sequential layout allows FOR loops to set up sprites: `POKE 53248+S*2,X(S)` updates sprite S's X position.

**Enable Register Bit Flags**

$D015 (53269) controls which sprites are visible using 8 bits (one per sprite):

- Bit 0 = sprite 0 (value 1)
- Bit 1 = sprite 1 (value 2)
- Bit 2 = sprite 2 (value 4)
- Combined: sprite 0+1 = 3, sprites 0+1+2 = 7, all 8 sprites = 255

To enable sprites 0, 1, and 3: `POKE 53269, 1+2+8` (binary 00001011 = decimal 11).

**Variable Naming Patterns**

For 2-4 sprites, individual variables (X0, Y0, X1, Y1...) work well. Beyond 4 sprites, arrays become necessary: `DIM X(7),Y(7)`. This lesson avoids arrays to keep complexity manageable—arrays appear in later lessons.

**Independent vs. Coordinated Movement**

Two movement patterns emerge:

1. **Formation flying** (Example 1): Sprites share position logic, offsets create formation
2. **Independent movement** (Example 2): Each sprite has unique position, velocity, and behavior

Most games mix both: player ship in formation with wingmen, enemies moving independently.

**Performance Considerations**

BASIC can comfortably manage 4 sprites at 50 FPS (one update per frame). Beyond 4 sprites, BASIC's interpreter overhead becomes noticeable—animation slows down. Assembly language programs handle all 8 sprites smoothly, but BASIC games typically use 4-6 sprites maximum.

### How Games Use This

**Impossible Mission** (1984, Epyx): Used 4 sprites simultaneously—player (sprite 0), 3 enemy robots (sprites 1-3). Each robot had independent AI and movement patterns, all managed through position arrays.

**Paradroid** (1985, Hewson): Player droid (sprite 0) plus 2-3 enemy droids (sprites 1-3). Each droid type had different movement algorithms—some patrolled, some chased the player, all tracked independently.

**Boulder Dash** (1984, First Star): Rockford (sprite 0), plus falling boulders and diamonds (sprites 1-4). The game tracked up to 4 moving objects simultaneously, prioritizing which falling objects got sprite slots.

**Uridium** (1986, Hewson): Player ship (sprite 0), enemy fighters (sprites 1-3), bullets (sprites 4-7). The game reused sprite slots—when bullets hit targets, those sprites became explosions, then recycled for new bullets.

### Quick Reference

**Sprite Position Registers:**
```
Sprite 0: $D000-$D001 (53248-53249)
Sprite 1: $D002-$D003 (53250-53251)
Sprite 2: $D004-$D005 (53252-53253)
Sprite 3: $D006-$D007 (53254-53255)
```

**Enable Register Values:**
| Sprites Enabled  | Binary   | Decimal |
|------------------|----------|---------|
| 0                | 00000001 | 1       |
| 0,1              | 00000011 | 3       |
| 0,1,2            | 00000111 | 7       |
| 0,1,2,3          | 00001111 | 15      |
| 0,1,2,3,4,5,6,7  | 11111111 | 255     |

**Setup Pattern:**
```basic
REM Setup sprites 0-3
FOR S=0 TO 3
  POKE 2040+S,13        REM sprite pointer
  POKE 53287+S,S+2      REM color
NEXT
POKE 53269,15           REM enable all 4
```

### What You've Learnt

- Each sprite has dedicated X/Y position registers
- Position registers are sequential (every 2 bytes)
- Enable register uses bit flags (1=sprite 0, 2=sprite 1, etc.)
- Multiple sprites need separate position variables
- Formation movement uses shared position + offsets
- Independent movement tracks each sprite separately
- Bouncing uses velocity reversal at screen edges
- BASIC comfortably manages 4 sprites simultaneously
