## From Input to Movement

In Lesson 026, you read joystick state through the CIA chip. Now you'll use that input to control sprite movement—creating the foundation for every C64 action game. This lesson combines joystick reading with sprite positioning, boundary checking, and variable speed control.

---

###  The One-Minute Tour

- Same joystick reading technique as Lesson 026 (PEEK(56320) AND 31)
- Position updated each frame based on joystick state
- Boundary checking prevents sprite from leaving visible screen area
- X boundaries: 24 (left edge) to 320 (right edge, safe from MSB issues)
- Y boundaries: 50 (top edge) to 229 (bottom edge)
- MSB register at 53264 automatically handled when X exceeds 255
- Speed variable controls pixels moved per frame
- Fire button can trigger speed boost or other actions
- Movement delay loop controls overall responsiveness
- Same pattern scales to multiple player-controlled sprites

### Example Programme

```basic
10 REM JOYSTICK SPRITE CONTROL
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM SETUP SPRITE 0
70 POKE 2040,13:POKE 53269,1:POKE 53287,7
80 X=160:Y=100
90 REM MAIN LOOP
100 POKE 53248,X:POKE 53249,Y
110 IF X>255 THEN POKE 53264,1 ELSE POKE 53264,0
120 J=PEEK(56320) AND 31
130 IF (J AND 1)=0 AND Y>50 THEN Y=Y-2
140 IF (J AND 2)=0 AND Y<229 THEN Y=Y+2
150 IF (J AND 4)=0 AND X>24 THEN X=X-2
160 IF (J AND 8)=0 AND X<320 THEN X=X+2
170 FOR D=1 TO 3:NEXT D
180 GOTO 100
190 DATA 0,24,0,0,60,0,0,126,0
200 DATA 0,255,0,1,255,128,3,255,192
210 DATA 7,255,224,15,255,240,31,255,248
220 DATA 3,255,192,3,255,192,3,255,192
230 DATA 3,255,192,3,255,192,3,255,192
240 DATA 1,255,128,0,255,0,0,126,0
250 DATA 0,60,0,0,24,0,0,0,0
```

**Lines 30-50** load sprite data into memory at block 13 (832-893). **Line 70** sets up sprite 0: pointer to block 13, enable bit, colour white. **Line 80** initialises position at screen centre. **Lines 100-110** update sprite position and handle MSB for X>255. **Line 120** reads joystick Port 2 with AND 31 to isolate joystick bits. **Lines 130-160** check each direction and update position if within boundaries, moving 2 pixels per frame. **Line 170** adds brief delay for movement control.

> **Note:** Boundary checks (`Y>50`, `Y<229`, `X>24`, `X<320`) prevent the sprite from moving outside the visible screen area. The MSB check at line 110 automatically handles the transition when X coordinate exceeds 255.

- **Different colour**: Line 70 — change `7` (white) to `2` (red), `5` (green), or `14` (light blue)
- **Tighter boundaries**: Lines 130-160 — change to `Y>100`, `Y<180`, `X>50`, `X<270` for confined area

```basic
10 REM VARIABLE SPEED MOVEMENT
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62

50 NEXT
60 REM SETUP SPRITE 0
70 POKE 2040,13:POKE 53269,1:POKE 53287,14
80 X=160:Y=100:SP=1
90 REM MAIN LOOP
100 POKE 53248,X:POKE 53249,Y
110 IF X>255 THEN POKE 53264,1 ELSE POKE 53264,0
120 J=PEEK(56320) AND 31
130 IF (J AND 16)=0 THEN SP=3 ELSE SP=1
140 IF (J AND 1)=0 AND Y>50 THEN Y=Y-SP
150 IF (J AND 2)=0 AND Y<229 THEN Y=Y+SP
160 IF (J AND 4)=0 AND X>24 THEN X=X-SP
170 IF (J AND 8)=0 AND X<320 THEN X=X+SP
180 FOR D=1 TO 2:NEXT D
190 GOTO 100
200 DATA 0,24,0,0,60,0,0,126,0
210 DATA 0,255,0,1,255,128,3,255,192
220 DATA 7,255,224,15,255,240,31,255,248

250 DATA 1,255,128,0,255,0,0,126,0

```

**Line 80** adds `SP` variable for speed (starts at 1). **Line 130** checks fire button: if pressed (bit 16=0), set speed to 3; otherwise set to 1. **Lines 140-170** now use variable `SP` instead of fixed value, making speed change dynamically. **Line 180** reduced delay since faster speed needs more responsive control.

### Concept Expansion

**Boundary Coordinate Reference**

The C64 visible screen area requires specific boundary values:

```
X axis: 24 pixels (left edge) to 344 pixels (right edge)
  Safe range: 24-320 (avoids MSB complexity at far right)
  MSB transition: When X>255, must set bit in register 53264

Y axis: 50 pixels (top edge) to 229 pixels (bottom edge)
  No MSB needed for Y (never exceeds 255)

Sprite dimensions: 24×21 pixels
  Add sprite width to calculate true right boundary
  Example: X=320 means sprite right edge at 344
```

**MSB Register Management**

When X coordinate exceeds 255, the MSB (Most Significant Bit) register tracks the overflow:

```basic
IF X>255 THEN POKE 53264,1 ELSE POKE 53264,0
```

This simple approach works for single sprites. For multiple sprites, each needs its own bit:

```
Sprite 0: Bit 0 (value 1)
Sprite 1: Bit 1 (value 2)
Sprite 2: Bit 2 (value 4)
Sprite 3: Bit 3 (value 8)
```

**Movement Speed Patterns**

Different speed values create different gameplay feels:

```basic
SP=1  : Precise control, slow movement (puzzle games)
SP=2  : Standard action game speed
SP=3  : Fast action, difficult precision (racing games)
SP=4+ : Very fast, hard to control (avoid unless intentional)
```

**Boundary Checking Logic**

The pattern `IF (J AND direction)=0 AND position<boundary THEN position=position+speed` combines three checks:

1. **Joystick check**: Is this direction pressed? (`(J AND direction)=0`)
2. **Boundary check**: Are we within safe limits? (`position<boundary`)
3. **Update**: Only modify position if both true

This prevents sprite from moving outside visible area even when joystick is held.

**Diagonal Movement**

Current code allows diagonal movement automatically:

```
Pressing UP+RIGHT simultaneously:
  Line 130: Y decreases by SP
  Line 160: X increases by SP
  Result: Sprite moves diagonally up-right
```

Diagonal speed is faster (√2 times) than cardinal directions. Lesson 028 will show how to normalize this.

### Common Mistakes

**Problem 1: Sprite Escapes Screen Boundaries**
```basic
IF (J AND 1)=0 THEN Y=Y-2     REM No boundary check!
IF Y<50 THEN Y=50             REM Too late - sprite already gone!
```
**Diagnosis:** Boundary check happens after position update. Sprite moves outside boundary for one frame before being corrected, causing visible glitching.

**Fix:** Check boundary condition in same IF statement as movement:
```basic
IF (J AND 1)=0 AND Y>50 THEN Y=Y-2    REM Check before update
```
**Why:** The AND operator combines joystick check with boundary check in single condition. Position only updates if BOTH joystick pressed AND position within boundary. This prevents sprite from ever exceeding limits. Checking boundary after update creates one-frame escape.

**Problem 2: MSB Register Not Updated, Sprite Disappears at X=255**
```basic
POKE 53248,X:POKE 53249,Y    REM Position updated
REM Forgot to update MSB register!
```
**Diagnosis:** When X exceeds 255, sprite disappears or appears at wrong position. MSB register (53264) still set to 0.

**Fix:** Always update MSB register every frame:
```basic
POKE 53248,X:POKE 53249,Y
IF X>255 THEN POKE 53264,1 ELSE POKE 53264,0    REM Update MSB
```
**Why:** VIC-II sprite X position is 9 bits (0-511) split across two registers: lower 8 bits in 53248, highest bit (bit 8) in 53264 bit 0. When X>255, you're writing values like 256, 257, 258 to POKE—BASIC accepts these because they fit in a 16-bit variable, but hardware only sees lower 8 bits (0, 1, 2). Must set MSB bit in 53264 to tell VIC-II "this sprite is at 256+value".

**Problem 3: Sprite Movement Too Fast or Unresponsive**
```basic
IF (J AND 1)=0 AND Y>50 THEN Y=Y-8    REM Speed too high!
FOR D=1 TO 100:NEXT D                 REM Delay too long!
```
**Diagnosis:** Movement either too fast to control precisely or too sluggish to feel responsive. Speed value 8+ makes sprite jump across screen, delay >30 creates noticeable lag.

**Fix:** Use moderate speed (1-3 pixels) and minimal delay:
```basic
IF (J AND 1)=0 AND Y>50 THEN Y=Y-2    REM Speed 2 pixels
FOR D=1 TO 3:NEXT D                   REM Small delay
```
**Why:** Speed determines pixels per frame. At 50 FPS, speed 2 = 100 pixels/second (smooth control), speed 8 = 400 pixels/second (too fast). Delay loop controls frame rate—delay 3 runs ~50 FPS, delay 100 drops to ~15 FPS (sluggish). Balance speed and delay for responsive but controllable movement.

**Problem 4: Boundary Values Wrong for Sprite Size**
```basic
IF (J AND 8)=0 AND X<344 THEN X=X+2    REM Sprite escapes screen!
```
**Diagnosis:** Using absolute screen edge (344) as boundary. Sprite is 24 pixels wide, so X=344 puts sprite's right edge at pixel 368 (off screen).

**Fix:** Use safe boundary accounting for sprite width:
```basic
IF (J AND 8)=0 AND X<320 THEN X=X+2    REM Safe boundary
```
**Why:** Sprites are 24×21 pixels. Sprite X/Y registers position the top-left corner. Right edge is at X+24, bottom edge at Y+21. Visible screen area is ~24-344 horizontally, but using X=320 as boundary keeps sprite fully visible (320+24=344). Going beyond 320 risks MSB complexity and partial off-screen rendering. See Concept Expansion for full boundary calculations.

### How Games Use This

**Uridium** (1986, Hewson): Used extremely tight joystick control for the Manta fighter ship. The code checked boundaries every frame and adjusted sprite position immediately, creating the precise control that made navigating narrow corridors possible.

**Paradroid** (1985, Hewson): Implemented variable speed control where holding fire while moving made the droid move faster but with less precise control—exactly like the second example program. This added strategic depth to navigation.

**Impossible Mission** (1984, Epyx): Combined joystick sprite control with platform collision detection. The boundary checking wasn't just screen edges but also platform surfaces, using the same `IF position<boundary` pattern extended to game object positions.

**Boulder Dash** (1984, First Star): Used the MSB technique for scrolling environments where the player sprite could move beyond X=255. The same register 53264 management allowed Rockford to explore the full 40×22 character map.

### Quick Reference

**Sprite Position Registers:**
```basic
53248 ($D000): Sprite 0 X position (low byte)
53249 ($D001): Sprite 0 Y position
53264 ($D010): Sprite X MSB (bit 0 for sprite 0)
```

**Boundary Constants:**
```basic
X: 24 (left) to 320 (right, safe)
Y: 50 (top) to 229 (bottom)
```

**Basic Control Pattern:**
```basic
J=PEEK(56320) AND 31
IF (J AND 1)=0 AND Y>50 THEN Y=Y-SP   : REM UP
IF (J AND 2)=0 AND Y<229 THEN Y=Y+SP  : REM DOWN
IF (J AND 4)=0 AND X>24 THEN X=X-SP   : REM LEFT
IF (J AND 8)=0 AND X<320 THEN X=X+SP  : REM RIGHT
```

**MSB Management:**
```basic
IF X>255 THEN POKE 53264,1 ELSE POKE 53264,0
```

**Speed Control:**
```basic
SP=1                                    : REM Normal speed
IF (J AND 16)=0 THEN SP=3 ELSE SP=1    : REM Fire button boost
```

### What You've Learnt

- Joystick input drives sprite position through direct variable updates
- Boundary checking uses `IF position<boundary AND joystick THEN update` pattern
- X coordinates beyond 255 require MSB register management at 53264
- Safe visible boundaries: X=24-320, Y=50-229
- Speed variables enable dynamic movement control (1=slow, 2=normal, 3=fast)
- Fire button can trigger speed changes or other state modifications
- Diagonal movement occurs automatically when multiple directions pressed
- Movement delay loop controls overall responsiveness
- Same technique scales to multiple sprites with separate position variables
- MSB register uses one bit per sprite (0-7) to track X overflow
