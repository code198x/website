You've moved sprites directly by changing their X and Y positions. Now discover a more powerful approach—velocity-based movement. Instead of jumping pixels, your sprite gains velocity that updates position smoothly. This separation unlocks physics simulation: momentum, acceleration, and realistic motion.

**Position isn't movement—velocity is.** When you separate the two, physics becomes possible.

## The One-Minute Tour

- **Velocity-based movement separates concerns** with velocity variables (VX, VY) controlling how fast position changes
- **Position variables use floating-point** allowing sub-pixel precision (1.5 pixels per frame creates smooth motion)
- **Joystick updates velocity, not position directly** making it easy to add acceleration or momentum later
- **8-direction movement emerges naturally** when VX and VY are combined (diagonals work automatically)
- **INT() converts floats to integers** when writing to VIC-II registers (hardware needs whole pixels)
- **This pattern scales to full physics** including momentum, friction, thrust, and gravity

## First Example: Velocity-Based Movement

Type this to see smooth velocity-controlled sprite movement:

```basic
10 REM SMOOTH VELOCITY-BASED MOVEMENT
20 PRINT CHR$(147)
30 PRINT "SMOOTH MOVEMENT DEMO"
40 PRINT
50 PRINT "USE JOYSTICK TO MOVE SPRITE"
60 PRINT "WITH VELOCITY-BASED SYSTEM"
70 REM SPRITE SETUP
80 POKE 53248,160:POKE 53249,100
90 POKE 2040,13:POKE 53269,1:POKE 53287,1
100 REM POSITION AND VELOCITY
110 X=160:Y=100
120 VX=0:VY=0
130 SP=1.5
140 REM MAIN LOOP
150 GOSUB 1000
160 GOSUB 2000
170 GOSUB 3000
180 GOTO 150
1000 REM JOYSTICK CONTROLS VELOCITY
1010 J=PEEK(56320)
1020 VX=0:VY=0
1030 IF (J AND 1)=0 THEN VY=-SP
1040 IF (J AND 2)=0 THEN VY=SP
1050 IF (J AND 4)=0 THEN VX=-SP
1060 IF (J AND 8)=0 THEN VX=SP
1070 RETURN
2000 REM UPDATE POSITION
2010 X=X+VX:Y=Y+VY
2020 IF X<0 THEN X=0
2030 IF X>255 THEN X=255
2040 IF Y<50 THEN Y=50
2050 IF Y>229 THEN Y=229
2060 RETURN
3000 REM UPDATE SPRITE
3010 POKE 53248,INT(X)
3020 POKE 53249,INT(Y)
3030 RETURN
```

**Run this** and move the joystick. Notice how the sprite glides smoothly.

![Smooth velocity-based sprite movement](/images/commodore-64/phase-0/tier-2/lesson-028/screenshot-1.png)

The sprite moves at 1.5 pixels per frame—smooth and responsive. The float variable X accumulates fractional movement (100.0, 101.5, 103.0, 104.5...) whilst INT() converts to whole pixels for the VIC-II. This sub-pixel precision creates the smoothness you feel.

## Why Velocity Matters

**The old way** (direct position change):
```basic
100 J=PEEK(56320)
110 IF (J AND 1)=0 THEN POKE 53249,PEEK(53249)-2
```
Joystick pressed → sprite jumps 2 pixels instantly.

**The new way** (velocity-based):
```basic
100 J=PEEK(56320)
110 IF (J AND 1)=0 THEN VY=-1.5
120 Y=Y+VY
130 POKE 53249,INT(Y)
```
Joystick pressed → velocity changes → position updates → sprite moves smoothly.

**Why this matters:** The velocity variable creates a separation that enables physics. Want momentum? Don't reset VY to 0 each frame. Want acceleration? Increase VY gradually. Want friction? Multiply VY by 0.95 each frame. All physics emerges from this pattern.

## 8-Direction Movement

Velocity-based movement creates diagonal motion automatically:

**Press UP:** VY=-1.5, VX=0 → Sprite moves up
**Press RIGHT:** VX=1.5, VY=0 → Sprite moves right
**Press UP+RIGHT:** VY=-1.5, VX=1.5 → Sprite moves diagonally

Both velocity components apply simultaneously. No special diagonal code needed—it emerges from the pattern.

**The diagonal speed problem:** Diagonal movement is actually √2 (≈1.414) times faster than horizontal/vertical. With VX=1.5 and VY=1.5, the actual speed is 2.12 pixels per frame. Most games ignore this, but if you want precise control, normalise diagonal velocities.

## Second Example: Normalised Diagonal Movement

Type this to see speed-corrected diagonal movement:

```basic
10 REM NORMALIZED DIAGONAL MOVEMENT
20 PRINT CHR$(147)
30 PRINT "NORMALIZED DIAGONAL MOVEMENT"
40 PRINT
50 PRINT "DIAGONAL SPEED NOW MATCHES"
60 PRINT "HORIZONTAL AND VERTICAL SPEED"
70 REM SPRITE SETUP
80 POKE 53248,160:POKE 53249,100
90 POKE 2040,13:POKE 53269,1:POKE 53287,1
100 REM POSITION AND VELOCITY
110 X=160:Y=100
120 VX=0:VY=0
130 SP=2
140 REM MAIN LOOP
150 GOSUB 1000
160 GOSUB 2000
170 GOSUB 3000
180 GOTO 150
1000 REM JOYSTICK WITH NORMALIZATION
1010 J=PEEK(56320)
1020 VX=0:VY=0
1030 IF (J AND 1)=0 THEN VY=-SP
1040 IF (J AND 2)=0 THEN VY=SP
1050 IF (J AND 4)=0 THEN VX=-SP
1060 IF (J AND 8)=0 THEN VX=SP
1070 REM NORMALIZE DIAGONAL
1080 IF VX<>0 AND VY<>0 THEN VX=VX*0.707:VY=VY*0.707
1090 RETURN
2000 REM UPDATE POSITION
2010 X=X+VX:Y=Y+VY
2020 IF X<0 THEN X=0
2030 IF X>255 THEN X=255
2040 IF Y<50 THEN Y=50
2050 IF Y>229 THEN Y=229
2060 RETURN
3000 REM UPDATE SPRITE
3010 POKE 53248,INT(X)
3020 POKE 53249,INT(Y)
3030 RETURN
```

**Run this** and test diagonal movement—it now matches horizontal speed exactly.

![Normalised diagonal movement with speed correction](/images/commodore-64/phase-0/tier-2/lesson-028/screenshot-2.png)

Line 1080 checks if both VX and VY are non-zero (diagonal movement), then multiplies each by 0.707 (which is approximately 1/√2). This reduces the combined velocity from 2.83 to 2.0, matching horizontal/vertical speed. Most arcade games skip this optimisation, but simulation games (space flight, racing) need precise speed control.

## The Three-Layer Pattern

Velocity-based movement uses three distinct layers:

**Layer 1: Input → Velocity (GOSUB 1000)**
Joystick reading updates VX and VY. Input doesn't touch position directly.

**Layer 2: Velocity → Position (GOSUB 2000)**
Position variables (X, Y) accumulate velocity each frame. Boundary checking happens here.

**Layer 3: Position → Hardware (GOSUB 3000)**
Float positions convert to integers for VIC-II POKEs. Hardware sees only whole pixels.

This separation means you can:
- Change input (keyboard instead of joystick) without touching physics
- Modify velocity (add friction) without touching rendering
- Update position logic (add wrapping) without touching input

**Each layer has one job.** This structure scales to complex physics systems.

## Float Precision and Sub-Pixel Movement

Why use float variables for position?

**With integers (X=100, VX=1):**
- Frame 1: X=101 (POKE 101)
- Frame 2: X=102 (POKE 102)
- Frame 3: X=103 (POKE 103)

Movement is smooth but limited to 1-pixel-per-frame increments.

**With floats (X=100.0, VX=0.5):**
- Frame 1: X=100.5 (POKE 100)
- Frame 2: X=101.0 (POKE 101)
- Frame 3: X=101.5 (POKE 101)
- Frame 4: X=102.0 (POKE 102)

The sprite appears to move at half-speed smoothly. VX=1.5 gives you speeds between 1 and 2 pixels per frame. This precision matters when you add acceleration—velocity changes by 0.1 each frame create smooth speed-ups.

## Boundary Handling: Clamp vs Wrap

**Clamping** (example uses this):
```basic
2020 IF X<0 THEN X=0
2030 IF X>255 THEN X=255
```
Sprite stops at screen edges. Good for most games.

**Wrapping** (alternative):
```basic
2020 IF X<0 THEN X=255
2030 IF X>255 THEN X=0
```
Sprite appears on opposite side when leaving screen. Perfect for Asteroids-style games (next lesson arc).

Choose the boundary behaviour that matches your game's feel.

## What You Can Build

With velocity-based movement as your foundation, you can now add:

**Momentum:** Don't reset velocity to 0 each frame—let it persist when joystick releases
**Acceleration:** VX=VX+0.1 when thrust pressed (gradual speed increase)
**Friction:** VX=VX*0.95 each frame (slow deceleration when no input)
**Gravity:** VY=VY+0.2 each frame (constant downward pull)
**Bouncing:** VY=-VY when hitting floor (velocity reversal)
**Maximum speed:** IF ABS(VX)>5 THEN VX=SGN(VX)*5 (speed limiter)

All of these patterns emerge from the velocity-position separation. The next four lessons build a complete physics-based Asteroids game using exactly these techniques.

## Speed Constants

Choosing the right speed value:

**Slow (0.5-1.0):** Deliberate, tank-like control (puzzle games, strategy)
**Medium (1.5-2.0):** Responsive arcade feel (shooters, most action games)
**Fast (2.5-3.5):** Quick reflex gameplay (bullet hell, racing)
**Very fast (4.0+):** Extreme speed, hard to control (experimental)

The examples use SP=1.5 and SP=2.0—the sweet spot for most arcade-style games. Experiment to find what feels right for your project.

## Common Pitfalls

**Forgetting INT():** Writing floats to VIC-II registers causes "?ILLEGAL QUANTITY ERROR". Always use INT(X) when POKEing to 53248/53249.

**Speed too high:** Values above 5 create jerky movement where the sprite jumps multiple pixels. Keep speeds under 4 for smooth visuals.

**Not resetting velocity:** If you don't reset VX=0:VY=0 at the start of input reading, old velocity persists when joystick is centred—sprite keeps moving.

**Boundary gaps:** If position goes negative without clamping (X=-5), the sprite disappears off screen. Always clamp or wrap positions.

**Diagonal speed difference:** Without normalisation, diagonals are 41% faster. Playtest to see if this bothers you—many successful games ignore it.
