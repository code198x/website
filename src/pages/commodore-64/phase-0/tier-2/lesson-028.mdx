## From Direct to Velocity-Based Movement

In Lesson 027, you updated sprite position directly from joystick input. This works but creates rigid movement patterns. This lesson introduces velocity variables—separating input reading from position updates—creating smoother, more flexible movement systems that form the foundation of professional game engines.

---

###  The One-Minute Tour

- Velocity variables (dx, dy) store movement direction, not position
- Set dx/dy to 0 each frame, then update based on joystick state
- Position update happens in one place: X=X+DX, Y=Y+DY
- Diagonal movement happens automatically when both dx and dy are non-zero
- Diagonal speed problem: √2 times faster than cardinal directions
- Speed normalization: Reduce diagonal speed to match cardinal movement
- Boundary checks move after position update but before display
- Same pattern scales to acceleration, friction, momentum
- Separating input from movement enables AI enemies using same code
- Professional game technique: separates "what to do" from "how to move"

### Example Programme

```basic
10 REM SMOOTH 8-WAY MOVEMENT
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM SETUP SPRITE 0
70 POKE 2040,13:POKE 53269,1:POKE 53287,14
80 X=160:Y=120
90 REM MAIN LOOP
100 J=PEEK(56320) AND 31:DX=0:DY=0
110 IF (J AND 1)=0 THEN DY=-2
120 IF (J AND 2)=0 THEN DY=2
130 IF (J AND 4)=0 THEN DX=-2
140 IF (J AND 8)=0 THEN DX=2
150 REM UPDATE POSITION
160 X=X+DX:Y=Y+DY
170 REM BOUNDARY CHECKS
180 IF X<24 THEN X=24
190 IF X>320 THEN X=320
200 IF Y<50 THEN Y=50
210 IF Y>229 THEN Y=229
220 REM UPDATE SPRITE
230 POKE 53248,X:POKE 53249,Y
240 IF X>255 THEN POKE 53264,1 ELSE POKE 53264,0
250 FOR D=1 TO 2:NEXT D
260 GOTO 100
270 DATA 0,24,0,0,60,0,0,126,0
280 DATA 0,255,0,1,255,128,3,255,192
290 DATA 7,255,224,15,255,240,31,255,248
300 DATA 3,255,192,3,255,192,3,255,192
310 DATA 3,255,192,3,255,192,3,255,192
320 DATA 1,255,128,0,255,0,0,126,0
330 DATA 0,60,0,0,24,0,0,0,0
```

**Line 100** initialises velocity to zero each frame—critical pattern that prevents velocity accumulation. **Lines 110-140** set velocity based on joystick state; multiple directions can both be active creating diagonal movement automatically. **Line 160** updates position in single operation—separation of input reading from position update is the key architectural change. **Lines 180-210** boundary checks constrain position after movement calculation. **Lines 230-240** display the final position with MSB handling.

Try these variations:

- **Acceleration**: Lines 110-140 — change to `DY=DY-1` and `DY=DY+1` (accumulate velocity)

### Concept Expansion

**Velocity vs. Direct Position Updates**

The architectural difference between Lesson 027 and Lesson 028:

```basic
REM Lesson 027: Direct position modification
IF (J AND 1)=0 AND Y>50 THEN Y=Y-2  : REM Coupled: input, boundary, movement

REM Lesson 028: Velocity-based movement
IF (J AND 1)=0 THEN DY=-2            : REM Input reading
X=X+DX:Y=Y+DY                        : REM Position update
IF Y<50 THEN Y=50                    : REM Boundary check
```

**Why This Matters:**

```
Direct approach:
  - Input and movement tightly coupled
  - Boundaries checked per direction
  - Hard to add acceleration/friction
  - Can't reuse for AI movement

Velocity approach:
  - Input sets velocity, position update separate
  - One position update line handles all directions
  - Easy to add forces, acceleration, friction
  - AI can set velocity same way joystick does
```

**The Diagonal Speed Problem**

Mathematical explanation:

```
Cardinal movement (Up):     dy=-2, dx=0  → Distance = 2 pixels
Cardinal movement (Right):  dy=0,  dx=2  → Distance = 2 pixels
Diagonal movement (Up-Right): dy=-2, dx=2 → Distance = √(4+4) = √8 = 2.83 pixels

Diagonal moves 41% faster due to Pythagorean theorem
```

**Speed Normalization Approaches**

```basic
REM Approach 1: Reduce diagonal speed (simple, integer math)
IF DX<>0 AND DY<>0 THEN S=1 ELSE S=2
X=X+DX*S:Y=Y+DY*S
REM Cardinal: 0*2 + 2*2 = 2 pixels
REM Diagonal: 1*1 + 1*1 = √2 = 1.41 pixels (closer to 2)

REM Approach 2: Scale by 0.7 (closer to √2 but needs floating point)
REM √2 = 1.414... so 1/√2 ≈ 0.707
IF DX<>0 AND DY<>0 THEN S=SP*0.7 ELSE S=SP
REM BASIC V2 supports this but slower than integers

REM Approach 3: Separate cardinal and diagonal speeds
IF DX<>0 AND DY<>0 THEN SP=1:REM Diagonal base
IF DX<>0 AND DY=0 THEN SP=2:REM Cardinal horizontal
IF DX=0 AND DY<>0 THEN SP=2:REM Cardinal vertical
```

**Movement Pattern Table**

| Joystick | DX | DY | Movement | Speed (SP=2) |
|----------|----|----|----------|--------------|
| Up | 0 | -1 | North | 2 pixels |
| Down | 0 | 1 | South | 2 pixels |
| Left | -1 | 0 | West | 2 pixels |
| Right | 1 | 0 | East | 2 pixels |
| Up+Left | -1 | -1 | Northwest | 1.41 pixels |
| Up+Right | 1 | -1 | Northeast | 1.41 pixels |
| Down+Left | -1 | 1 | Southwest | 1.41 pixels |
| Down+Right | 1 | 1 | Southeast | 1.41 pixels |
| None | 0 | 0 | Stationary | 0 pixels |

**Extending to Game Physics**

The velocity pattern enables advanced movement:

```basic
REM Acceleration (gradual speed up)
IF (J AND 1)=0 THEN DY=DY-0.5  : REM Accumulate velocity
IF DY<-4 THEN DY=-4            : REM Maximum speed cap

REM Friction (gradual slow down)
DX=DX*0.9:DY=DY*0.9            : REM Decay velocity each frame
IF ABS(DX)<0.1 THEN DX=0       : REM Stop when very slow

REM Gravity (platformer physics)
DY=DY+0.5                      : REM Constant downward acceleration
X=X+DX:Y=Y+DY                  : REM Apply velocity
```

**AI Movement Using Same Code**

```basic
REM Player uses joystick to set velocity
J=PEEK(56320) AND 31:DX=0:DY=0
IF (J AND 1)=0 THEN DY=-2

REM Enemy AI sets velocity same way
REM Chase player: move toward player position
IF EX<PX THEN DX=2 ELSE DX=-2  : REM Enemy velocity
IF EY<PY THEN DY=2 ELSE DY=-2

REM Both use same position update
X=X+DX:Y=Y+DY                  : REM Universal movement system
```

**Frame-Based vs. Time-Based Movement**

Current approach is frame-based:

```
Frame-based (our code):
  - Moves fixed pixels per frame
  - Speed tied to frame rate (50Hz on PAL, 60Hz on NTSC)
  - Simple but speed varies on different systems

Time-based (advanced):
  - Multiplies velocity by delta time
  - Consistent speed regardless of frame rate
  - Requires time measurement (complex in BASIC)
```

### How Games Use This

**The Last Ninja** (1987, System 3): Used velocity-based isometric movement. The smooth diagonal walking required velocity accumulation and separate movement axes—exactly the pattern in Example 2. The game's fluid animation relied on velocity interpolation.

**Jumpman** (1983, Epyx): Implemented perfect diagonal movement for ladder climbing. The velocity system allowed smooth transitions between cardinal and diagonal directions without visible speed changes.

**Impossible Mission** (1984, Epyx): Used velocity for running, jumping, and falling. Separating input from physics allowed gravity, momentum, and collision to modify the same velocity variables that joystick input set.

**Laser Squad** (1988, Target Games): Diagonal movement in tactical grid-based combat required speed normalization. Moving diagonally across grid squares took the same action points as cardinal movement—implemented using velocity scaling similar to Example 2.

### Quick Reference

**Velocity Pattern:**
```basic
REM Each frame: reset, read input, update position, constrain
DX=0:DY=0                             : REM Reset velocity
IF (J AND 1)=0 THEN DY=-SP            : REM Set velocity from input
X=X+DX:Y=Y+DY                         : REM Apply velocity
IF X<24 THEN X=24                     : REM Constrain position
```

**Diagonal Detection:**
```basic
IF DX<>0 AND DY<>0 THEN ...           : REM Moving diagonally
IF DX=0 AND DY=0 THEN ...             : REM Stationary
IF DX<>0 OR DY<>0 THEN ...            : REM Moving (any direction)
```

**Speed Normalization:**
```basic
REM Simple integer approach (close enough for games)
IF DX<>0 AND DY<>0 THEN S=1 ELSE S=2
X=X+DX*S:Y=Y+DY*S

REM Floating point approach (more accurate)
IF DX<>0 AND DY<>0 THEN S=SP*0.7 ELSE S=SP
X=X+DX*S:Y=Y+DY*S
```

**Velocity Variables:**
```
DX: Horizontal velocity (-n = left, +n = right, 0 = stationary)
DY: Vertical velocity (-n = up, +n = down, 0 = stationary)
SP: Speed multiplier (pixels per frame)
S:  Temporary speed for calculations
```

**Movement Speeds:**
```basic
SP=1  : Slow, precise (puzzle games)
SP=2  : Standard action game speed
SP=3  : Fast action (racing, shoot-em-ups)
SP=4+ : Very fast, difficult to control
```

### What You've Learnt

- Velocity variables (dx, dy) separate input reading from position updates
- Reset velocity to 0 each frame, then accumulate from input
- Position update happens once: X=X+DX, Y=Y+DY
- Diagonal movement occurs automatically when both dx and dy are non-zero
- Diagonal speed is √2 faster without normalization (2.83 vs 2 pixels)
- Speed normalization: reduce diagonal multiplier or use directional scaling
- Boundary checks move after position update, before display
- Velocity pattern enables acceleration, friction, momentum extensions
- Same movement code works for player (joystick) and AI (logic)
- Professional architecture: "set velocity" → "apply physics" → "update position"
