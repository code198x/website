## Bringing Sprites to Life

Static sprites work for bullets and cursors, but games need walking characters, rotating ships, and flapping enemies. Sprite animation works by rapidly switching between different sprite shapes—the same principle as film or cartoon animation. This lesson shows how to create smooth animated sprites using frame cycling and timing control.

---

### The One-Minute Tour

- Animation = switching sprite pointers to display different shapes
- Load multiple frames to consecutive memory blocks (832, 896, 960...)
- Change sprite pointer (POKE 2040, block_number) to cycle frames
- Timing methods: FOR loops (simple) or TI variable (smooth)
- TI = system timer, increments 60 times per second (NTSC)
- Memory safety: Blocks 13-15 safe (832-959), block 16 overlaps screen memory
- Two frames minimum for animation (walk cycle, blink, etc.)

### Example Program

```basic
10 REM SPRITE FRAME CYCLING
20 REM LOAD 2 ANIMATION FRAMES
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 FOR I=0 TO 62
70 READ B:POKE 896+I,B
80 NEXT
90 REM SETUP SPRITE
100 POKE 53287,7:POKE 53269,1
110 X=150:Y=120:F=0
120 POKE 53248,X:POKE 53249,Y
130 REM MAIN LOOP
140 F=1-F
150 POKE 2040,13+F
160 FOR D=1 TO 30:NEXT D
170 GOTO 140
180 REM FRAME 0 - CIRCLE
190 DATA 0,0,0,0,126,0,1,255,128
200 DATA 3,255,192,7,255,224,7,255,224
210 DATA 15,255,240,15,255,240,15,255,240
220 DATA 7,255,224,7,255,224,3,255,192
230 DATA 1,255,128,0,126,0,0,0,0
240 DATA 0,0,0,0,0,0,0,0,0
250 DATA 0,0,0,0,0,0,0,0,0
260 REM FRAME 1 - DIAMOND
270 DATA 0,0,0,0,24,0,0,60,0
280 DATA 0,126,0,1,255,128,3,255,192
290 DATA 7,255,224,15,255,240,15,255,240
300 DATA 7,255,224,3,255,192,1,255,128
310 DATA 0,126,0,0,60,0,0,24,0
320 DATA 0,0,0,0,0,0,0,0,0
330 DATA 0,0,0,0,0,0,0,0,0
```

![Yellow sprite alternating between circle and diamond shapes](/images/commodore-64/phase-0/tier-2/lesson-022/example-1.png)

**Lines 30-80** load two sprite frames: frame 0 to block 13 (832-894), frame 1 to block 14 (896-958). **Line 140** toggles F between 0 and 1 using `F=1-F` (when F=0, becomes 1; when F=1, becomes 0). **Line 150** changes the sprite pointer to display the current frame (13+0=13 or 13+1=14). **Line 160** delays 30 loops for visible frame duration.

> **Note:** Each sprite = 63 bytes. Block 13 starts at 832, block 14 at 896 (832+64), block 15 at 960 (896+64). Don't use block 16 (1024)—that's screen memory!

![Yellow sprite walking across screen with alternating leg positions](/images/commodore-64/phase-0/tier-2/lesson-022/example-2.png)

**Line 130** initializes T with current timer value (TI). **Line 180** waits until 5/60ths of a second (5 jiffies) have passed before continuing—creates consistent timing regardless of BASIC execution speed. **Line 190** resets T for next frame. This separates movement (every loop) from animation (every 5 jiffies), so the sprite walks smoothly even if animation frames change.

### Concept Expansion

**Memory Layout for Multiple Frames**

The C64's memory map determines safe sprite storage locations:

```
0-1023:     BASIC/system variables
1024-2023:  Screen memory (40×25 characters)
2024-2039:  Sprite pointers
...
832-894:    Block 13 (sprite frame 0)
896-958:    Block 14 (sprite frame 1)
960-1022:   Block 15 (sprite frame 2)
1024+:      SCREEN MEMORY - DON'T USE!
```

Loading a sprite to block 16 (1024) overwrites screen characters, causing corruption. For BASIC programs, blocks 13-15 provide space for 3 sprite frames. More frames require higher memory (blocks 192+ at 12288+) or complex memory management.

**Frame Cycling Techniques**

Two common patterns for cycling through N frames:

```basic
REM Toggle between 2 frames
F=1-F          REM F alternates 0,1,0,1...

REM Cycle through 3+ frames
F=F+1:IF F>2 THEN F=0     REM F cycles 0,1,2,0,1,2...
```

The sprite pointer formula: `POKE 2040, BASE_BLOCK+F` where BASE_BLOCK is your first frame (typically 13) and F is the current frame index (0, 1, 2...).

**Timing Methods Compared**

**FOR loop delays:**
```basic
FOR D=1 TO 30:NEXT D    REM ~1/2 second (varies with program)
```
- Simple to implement
- Duration varies with program complexity
- Same code elsewhere runs at different speeds
- Good for learning, less reliable in complex programs

**TI variable timing:**
```basic
T=TI                          REM Save current time
IF TI-T<5 THEN GOTO line     REM Wait 5 jiffies
T=TI                          REM Reset for next frame
```
- Consistent frame rate (60 jiffies per second on NTSC, 50 on PAL)
- Independent of program complexity
- Allows simultaneous actions (movement + animation at different rates)
- Essential for game-quality timing

TI increments automatically every 1/60th second (NTSC) or 1/50th second (PAL). One "jiffy" = one TI increment. Common animation speeds: 3-5 jiffies (12-20 FPS), 6-10 jiffies (6-10 FPS).

**Design Considerations for Animation Frames**

Effective sprite animation requires:

1. **Consistent sprite size**: All frames should occupy similar visual space
2. **Smooth transitions**: Adjacent frames should differ by small changes
3. **Loop continuity**: Last frame should transition smoothly to first
4. **Pixel symmetry**: Walking legs, spinning objects need balanced shapes
5. **Motion exaggeration**: Larger changes read better at low frame rates (2-4 frames)

Two-frame animations work well for: walking (alternating legs), blinking (open/closed), spinning (45° rotations), breathing (expand/contract). Three-frame animations add: smoother rotation, middle positions (walk with both legs down), anticipation poses.

**TI Variable Limitations**

Critical TI facts:

- Resets to 0 at power-on
- Resets to 0 after 24 hours (86400 jiffies = 1440000)
- Stops incrementing during BASIC's GET, INPUT, and STOP statements
- Can be manually reset: `TI=0`

For frame timing, these limitations rarely matter—games typically run for minutes, not 24 hours. If TI resets during gameplay, animations might freeze for one frame when crossing the zero point.

### How Games Use This

**Impossible Mission** (1984, Epyx): Player character used 8-frame running animation, cycling through frames based on horizontal movement speed. Standing still displayed frame 0; moving cycled frames 1-8 at speeds proportional to velocity.

**Paradroid** (1985, Hewson): Enemy droids used 2-frame animations for patrol movement (alternating antenna positions), 4-frame explosion sequences when destroyed. The game synchronized animation timing with droid movement patterns.

**Boulder Dash** (1984, First Star): Rockford's 8-frame walking animation cycled through elaborate leg and arm movements. Diamonds used 2-frame sparkle animations. All animations used TI-based timing for consistent speed across gameplay.

**Uridium** (1986, Hewson): Player ship exhaust used 3-frame animation (flame cycles), enemy fighters used 2-frame wing animations. The game updated animation frames independently from movement, allowing smooth rotation while maintaining flicker effects.

### Quick Reference

**Memory Blocks for Sprite Storage:**
```
Block 13: 832-894   (safe)
Block 14: 896-958   (safe)
Block 15: 960-1022  (safe)
Block 16: 1024+     (SCREEN MEMORY - avoid!)
```

**Frame Cycling Patterns:**
```basic
REM 2-frame toggle
F=1-F
POKE 2040, 13+F

REM 3-frame cycle
F=F+1:IF F>2 THEN F=0
POKE 2040, 13+F

REM 4-frame cycle
F=F+1:IF F>3 THEN F=0
POKE 2040, 13+F
```

**Timing Methods:**
```basic
REM FOR loop (simple, variable speed)
FOR D=1 TO 30:NEXT D

REM TI variable (smooth, consistent)
T=TI
IF TI-T<5 THEN GOTO loop_line
T=TI
```

**Common Animation Speeds:**
| Jiffies | FPS (NTSC) | Use Case |
|---------|------------|----------|
| 2       | 30         | Very fast (explosions) |
| 3       | 20         | Fast (running) |
| 5       | 12         | Medium (walking) |
| 10      | 6          | Slow (breathing) |

### What You've Learnt

- Sprite animation works by cycling through multiple sprite shapes
- Load frames to consecutive memory blocks (832, 896, 960)
- Change sprite pointer (POKE 2040, block) to display different frames
- FOR loops provide simple timing, TI variable provides consistent timing
- TI increments 60 times per second (NTSC), 50 times per second (PAL)
- Block 16 (1024) is screen memory—causes corruption if used for sprites
- Frame cycling uses toggle (F=1-F) or increment (F=F+1 with reset)
- Effective animation requires consistent size and smooth transitions
