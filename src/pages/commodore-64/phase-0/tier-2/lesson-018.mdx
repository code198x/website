## Designing Your Own

In Lesson 17, you filled sprite data with 255 to create a solid block. That's useful for testing, but games need recognizable shapes: spaceships, characters, enemies, projectiles. The VIC-II's 24×21 pixel format lets you design custom graphics. This lesson shows how to create sprite shapes using DATA statements.

---

### The One-Minute Tour

- Sprites are 24 pixels wide × 21 pixels tall = 504 bits
- 24 pixels = 3 bytes per row (8 bits each)
- 21 rows × 3 bytes = 63 bytes total sprite data
- Each byte controls 8 horizontal pixels (1 = on, 0 = off)
- DATA statements store sprite pattern as decimal values
- READ and POKE transfer DATA into sprite memory

---

### Example Program

```basic
10 REM SIMPLE ARROW SPRITE
20 REM READ SPRITE DATA FROM DATA STATEMENTS
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM POSITION AND ENABLE SPRITE
70 POKE 53248,160:POKE 53249,120
80 POKE 2040,13
90 POKE 53287,14:REM LIGHT BLUE
100 POKE 53269,1
110 GET A$:IF A$="" THEN 110
120 DATA 0,24,0,0,60,0,0,126,0
130 DATA 0,255,0,1,255,128,3,255,192
140 DATA 7,255,224,15,255,240,31,255,248
150 DATA 3,255,192,3,255,192,3,255,192
160 DATA 3,255,192,3,255,192,3,255,192
170 DATA 1,255,128,0,255,0,0,126,0
180 DATA 0,60,0,0,24,0,0,0,0
```

![Light blue arrow sprite pointing upward](/images/commodore-64/phase-0/tier-2/lesson-018/example-1.png)

**Lines 30-50** read 63 bytes from DATA statements and POKE them into sprite memory at 832. **Lines 120-180** contain the sprite pattern—each line represents 3 rows of the sprite (3 bytes × 7 lines = 21 rows). The values are decimal representations of binary pixel patterns.

> **Note:** Line 120 starts the sprite pattern. `0,24,0` means: first byte = 0 (00000000 binary = all pixels off), second byte = 24 (00011000 binary = two center pixels on), third byte = 0 (all pixels off). This creates the arrow's tip.

### Concept Expansion

**Understanding the 24×21 Format**

The VIC-II reads sprite data as 63 consecutive bytes. Each byte represents 8 horizontal pixels. Since sprites are 24 pixels wide, each row needs 3 bytes:

- Byte 1: Pixels 0-7 (leftmost)
- Byte 2: Pixels 8-15 (middle)
- Byte 3: Pixels 16-23 (rightmost)

21 rows × 3 bytes = 63 bytes total. The 64th byte is padding (unused).

**Binary to Decimal Conversion**

Each byte is a binary pattern where 1 = pixel on, 0 = pixel off. For example:

- Binary `00011000` = decimal 24 (two center pixels)
- Binary `11111111` = decimal 255 (all pixels on)
- Binary `10000001` = decimal 129 (left and right pixels only)

You design sprites by drawing them on graph paper (24×21 grid), then converting each row of 3 bytes to decimal values for DATA statements.

**Why DATA Statements?**

BASIC V2 has no built-in binary literals. DATA statements let you store sprite patterns as decimal values. The FOR/READ/POKE loop transfers these values into sprite memory at runtime. This pattern appears in nearly every C64 sprite program.

**Sprite Design Tools**

Professional C64 developers used sprite editors like SpritePad or GIME to draw sprites visually and export DATA values. For learning, graph paper works fine—draw your design, convert each 8-pixel row to binary, then to decimal.

**Memory Organization**

Block 13 (memory 832) is the default sprite data location because it's in the "safe" area between BASIC program and screen memory. You can store sprite data anywhere, but 832-895 is standard for single-sprite programs.

### How Games Use This

**Impossible Mission** (1984, Epyx): Your agent sprite was designed using this exact technique—DATA statements storing the character's pixels. Different animation frames were separate sprite patterns.

**Boulder Dash** (1984, First Star): Rockford, the player character, had 8 different sprite shapes for walking animations (left, right, idle). Each was stored in DATA statements and loaded at program start.

**Paradroid** (1985, Hewson): The player's droid and all 24 enemy droid types were custom sprites. The game loaded different sprite patterns from DATA based on which droid type you encountered.

**Uridium** (1986, Hewson): Your spaceship had multiple sprite frames for banking left/right. The smooth turning effect came from switching between sprite shapes, all stored in DATA statements.

### Quick Reference

**Sprite Data Format:**
```
24 pixels wide × 21 pixels tall = 63 bytes
3 bytes per row × 21 rows
Each byte = 8 horizontal pixels (binary pattern)
64th byte = padding (unused)
```

**Common Decimal Values:**
| Decimal | Binary    | Pattern        |
|---------|-----------|----------------|
| 0       | 00000000  | ········       |
| 24      | 00011000  | ···**···       |
| 60      | 00111100  | ··****··       |
| 126     | 01111110  | ·******·       |
| 255     | 11111111  | ********       |
| 129     | 10000001  | *······*       |
| 195     | 11000011  | **····**       |

**DATA Pattern:**
```basic
120 DATA byte1,byte2,byte3  REM row 1
130 DATA byte4,byte5,byte6  REM row 2
...
180 DATA byte61,byte62,byte63  REM row 21
```

### What You've Learnt

- Sprites are 24×21 pixels (63 bytes of data)
- Each byte represents 8 horizontal pixels
- 3 bytes per row (24 pixels ÷ 8 bits)
- DATA statements store sprite patterns as decimal values
- FOR/READ/POKE loop transfers DATA to sprite memory
- Binary patterns convert to decimal (1=pixel on, 0=off)
- Custom sprite shapes define game characters and objects
- Sprite memory at 832 (block 13) is standard location
