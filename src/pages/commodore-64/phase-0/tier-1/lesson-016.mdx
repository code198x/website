# Crystal Caverns

You've learnt variables, loops, conditionals, arrays, DATA statements, screen POKEing, sound effects, player input, collision detection, scoring, and countdown timers. Fifteen separate lessons, each teaching one concept.

Now it's time to put them all together.

**Crystal Caverns** is a complete text adventure game. You're trapped in a collapsing cave system with two minutes to find the legendary blue crystal and escape. Every concept you've learnt combines into one playable game—and you're going to build it from scratch.

## The One-Minute Tour

- **Room-based navigation:** Five connected rooms, each with its own description
- **Text parser:** Player types N/S/E/W to move, GET to collect items, INV for inventory
- **Inventory system:** Array stores collected items (the crystal)
- **Countdown timer:** TI tracks elapsed time, cavern collapses after 120 seconds
- **Win condition:** Return to entrance with crystal before time expires
- **Sound effects:** Pickup sound, victory fanfare, collapse rumble
- **Game state:** Tracks current room, has-crystal flag, timer, inventory count
- **Complete game loop:** Title → gameplay → win/lose screen → END

This is what a synthesis lesson does: you already know how each piece works. Now you learn how they fit together to create something greater than the sum of its parts.

## Breaking It Down: The Title Screen

**Lines 20-80** create the title screen and wait for a keypress. This is standard game structure: show what the game is about, explain the objective, wait for the player to be ready.

Line 20 uses CHR$(147) to clear the screen and POKEs 53280/53281 to set the border and background to blue/black—creating atmosphere before the game even starts.

Lines 30-60 print the title and premise. Notice how we build tension: "THE CAVERN IS COLLAPSING!" immediately establishes urgency. "YOU HAVE 2 MINUTES" tells the player exactly what kind of challenge they're facing.

Line 80 is a waiting loop: `GET A$:IF A$="" THEN 80`. It sits here until any key is pressed, then continues. This gives the player control over when to start—essential for a timed game.

## The Initialisation: Setting Up Game State

**Line 90:** `DIM I$(3)` creates a string array for inventory. We only need space for 3 items (though this game only has one). String arrays store text like "CRYSTAL", "KEY", "TORCH".

**Line 100** initialises all game variables in one line:
- `II=0`: Inventory index (how many items carried)
- `R=1`: Current room (starting at room 1, the entrance)
- `TI$="000000"`: Reset timer to midnight (0 hours, 0 minutes, 0 seconds)
- `TL=120`: Time limit (120 seconds = 2 minutes)
- `HC=0`: Has-crystal flag (0 = don't have it, 1 = carrying it)

This is efficient BASIC: rather than writing five separate lines, we pack related initialisations together. The C64 lets you separate multiple statements with colons.

## The Main Game Loop: Where Everything Happens

**Lines 110-220** form the core loop that runs until the game ends. Let's trace one complete cycle:

1. **Line 110:** Clear screen
2. **Line 120:** GOSUB 1000—display current room description
3. **Line 130:** Print remaining time (total time minus elapsed jiffies converted to seconds)
4. **Line 140:** Print available commands
5. **Line 150:** INPUT C$—wait for player to type a command
6. **Lines 160-180:** Check command and GOSUB appropriate handler
7. **Lines 190-200:** Calculate elapsed time, check if time is up
8. **Line 210:** Check win condition (in entrance hall WITH crystal)
9. **Line 220:** GOTO 110—loop back to start

This structure is fundamental to all adventure games. The loop displays state, accepts input, processes that input, checks win/lose conditions, and repeats.

## Room Display: Creating the World

**Lines 1000-1060** are the room descriptions. Each room has a number (1-5) and two lines of text: what the room is, and what exits are available.

Line 1010: "ENTRANCE HALL" with "PASSAGES LEAD N AND E" tells the player they can go north or east from here.

Line 1030: "CRYSTAL CHAMBER" with "A BLUE CRYSTAL GLOWS!" signals that this room contains the goal object. The exclamation mark adds excitement—this is the room you've been searching for.

Line 1050: "COLLAPSED PASSAGE" with "RUBBLE BLOCKS THE WAY" creates a dead end. The player can go north from room 4 to room 5, but room 5 only has one exit (south). This prevents the map from feeling too linear—some exploration is required.

**Why not use DATA statements?** We could store room descriptions in DATA and READ them. But with only 5 rooms, the IF...THEN approach is clearer and easier to modify. DATA becomes worthwhile when you have 20+ rooms.

## Movement Handler: Connecting the Rooms

**Lines 2000-2120** handle navigation. This is where the room connectivity map lives.

Line 2010: `IF C$="N" AND R=1 THEN R=2:RETURN` means "if player typed N and is in room 1, move to room 2 and return."

Notice the pattern: each valid move checks both the command (N/S/E/W) and the current room. If both match, change R to the new room number and RETURN immediately.

Line 2110 catches invalid moves: if none of the earlier conditions matched, we print "YOU CAN'T GO THAT WAY!" and add a delay so the player actually sees the message before the screen refreshes.

**The room map:**
```
        3 (Crystal)
        |
    2 (Tunnel)
   / \
  1   4
(Entrance) (Storage)
      |
      5
  (Collapsed)
```

Room 1 connects to 2 (north) and 4 (east). Room 2 connects to 1 (south) and 3 (north). And so on. Players must explore to discover this layout.

## Inventory System: Tracking What You Carry

**Lines 3000-3030** handle item pickup. Line 3010 checks three things:
- Are you in room 3? (where the crystal is)
- Have you not already taken it? (HC=0)
- Did you type GET?

If all three are true: increment inventory count (II=II+1), store "CRYSTAL" in the array, set HC=1 (has crystal), play pickup sound, return.

**Lines 4000-4040** display inventory. If II=0, you're not carrying anything. Otherwise, loop through I$(1) to I$(II) and print each item name. Simple, but effective—players can type INV to check what they've collected.

**Why use both II and HC?** II tracks how many items total, HC specifically tracks whether you have the crystal. For win detection (line 210), we only care about HC. If we added more items (keys, torches), HC would remain the crystal-specific flag.

## Sound Effects: Audio Feedback

**Lines 5000-5050:** Pickup sound uses triangle wave (ADSR 0/240) with a pleasant middle-range frequency. The sound reinforces that you've accomplished something important—you've found the crystal.

**Lines 8000-8040:** Collapse sound uses noise (waveform 128) with low frequency to create a rumbling, ominous effect when time runs out.

**Lines 9000-9060:** Victory fanfare plays two notes in sequence (150→200 frequency), creating a cheerful ascending melody. This is your reward for winning.

Every significant game event gets audio feedback. It's the difference between a sterile simulation and something that feels alive.

## Win and Lose Conditions: Ending the Game

**Line 200:** `IF RE<=0 THEN GOSUB 6000` checks if remaining time has reached zero. If so, jump to the collapse handler.

**Lines 6010-6040:** Time-up screen clears to red border (POKE 53280,2), prints defeat message, plays collapse sound, and ENDs. Game over.

**Line 210:** `IF R=1 AND HC=1 THEN GOSUB 7000` checks win condition: are you in room 1 (entrance) AND carrying the crystal?

**Lines 7010-7050:** Victory screen clears to green border (POKE 53280,5), prints success message, shows how much time remained, plays fanfare, and ENDs.

Both conditions are checked every loop iteration. The timer counts down every frame—you can't pause the collapse. The pressure never stops.

## What Makes This a Complete Game

Crystal Caverns isn't just 60 lines of code. It's a **game system** where multiple mechanics interact:

**Exploration vs Time:** You want to explore every room (curiosity), but the timer punishes dawdling. Finding the crystal quickly means a higher "time remaining" score.

**Navigation puzzles:** Room 5 is a dead end. Going north from room 4 wastes time—you have to backtrack. Smart players mentally map the layout on their first playthrough.

**Goal clarity:** From the title screen, you know exactly what to do: find crystal, return to entrance. No ambiguity.

**Risk/reward:** Do you type INV to check your inventory, wasting precious seconds? Or do you trust your memory?

**Failure states:** You can lose by running out of time. This creates tension—every command matters.

**Victory feedback:** The green border, remaining time display, and two-note fanfare make winning feel rewarding.

This is game design. Every lesson in Tier 1 contributed to making this work.

## Extending the Game

Once you've typed and played Crystal Caverns, try these modifications:

**Add more rooms:** Extend lines 1000-1060 with rooms 6-10. Add corresponding movement rules in lines 2000-2120. More rooms = more exploration = more challenge.

**Add multiple items:** Change line 3010 to check different room numbers for different items. Maybe room 4 has a torch, room 5 has a key. Store them in I$(1), I$(2), I$(3).

**Add locked doors:** Before allowing certain movements, check if the player has the key. `IF C$="N" AND R=2 AND [doesn't have key] THEN PRINT "DOOR LOCKED!":RETURN`.

**Add room-specific hazards:** Some rooms could damage you (health points system) or require certain items to enter (torch for dark rooms).

**Add enemies:** Random encounters (IF RND(1)&lt;.2 THEN GOSUB [combat]) that reduce health or consume time.

**Multiple endings:** Different escape routes with different time bonuses. Maybe there's a secret exit in room 5 behind the rubble if you have explosives.

**Save the best time:** Store the fastest completion in a variable and display it on the title screen as "RECORD: 38 SECONDS". Challenge players to beat their personal best.

## From the Vault

**Text adventures dominated early computing.** Colossal Cave Adventure (1976), Zork (1977), The Hobbit (1982)—all built on this same foundation. Room numbers, item arrays, command parsing, win conditions. Crystal Caverns is simpler, but it's the same genre.

**Parser evolution:** Early adventures used two-word commands (GET LAMP, GO NORTH). Later games added three-word commands (PUT COIN IN SLOT) and even natural language parsing. But the core loop—describe, input, process, check—never changed.

**The golden age of text adventures:** 1978-1985 saw hundreds of commercial text adventures. Infocom alone published over 35 games. Why? Because you could create vast worlds with just text. Graphics required memory—text required imagination.

**Modern descendants:** Choice-based games, visual novels, walking simulators—they all trace back to text adventures. The room-based navigation of Crystal Caverns is the ancestor of every 3D game with interconnected spaces.

## Quick Reference

**Room Navigation Pattern:**
```basic
10 R=1                              :REM Current room
20 IF C$="N" AND R=1 THEN R=2       :REM Move north from room 1 to room 2
30 IF C$="S" AND R=2 THEN R=1       :REM Move south from room 2 to room 1
```

**Simple Inventory:**
```basic
10 DIM I$(10)                       :REM Item array
20 II=0                             :REM Item count
30 II=II+1:I$(II)="CRYSTAL"        :REM Add item
40 FOR I=1 TO II:PRINT I$(I):NEXT I :REM List items
```

**Timer Integration:**
```basic
10 TI$="000000":TL=120              :REM Reset clock, set 2-minute limit
20 E=INT(TI/60):RE=TL-E            :REM Elapsed and remaining seconds
30 IF RE<=0 THEN [game over]        :REM Out of time
```

**Win Condition:**
```basic
10 IF R=1 AND HC=1 THEN [victory]  :REM In entrance with crystal
```
