# Completing the Game

Over the last three lessons, you've built all the pieces of a proper arcade game: a player character you can move, falling objects streaming down the screen, and satisfying sound effects when things happen. But they've all been separate demonstrations. Now it's time to make them *talk to each other*.

That's what **collision detection** does—it's the moment your program realises the player has touched a star, caught a power-up, or crashed into an enemy. It's the point where all your separate systems suddenly become a *game*.

**The One-Minute Tour:**
- Collision detection compares player position (PX, PY) with each object's position (FX(I), FY(I))
- When positions match, immediately call a collision handler with GOSUB
- The handler updates game state (score or lives), plays a sound effect, and respawns the object
- Game state variables (SC for score, LV for lives) control when the game continues or ends
- Win condition: SC&gt;=20 (caught 20 stars)
- Lose condition: LV=0 (all lives lost)
- Different object types (FT array) mean good stars give points, bad asteroids cost lives

## Example Programme: Basic Star Catcher

Let's start with the simplest possible collision detection—catch falling stars and watch your score increase:

```basic
10 REM BASIC STAR CATCHER
20 PRINT CHR$(147)
30 PRINT "STAR CATCHER"
40 PRINT
50 PRINT "A/D TO MOVE, CATCH STARS!"
60 PRINT
70 DIM FX(5),FY(5)
80 FOR I=1 TO 5
90 FX(I)=INT(RND(1)*40):FY(I)=INT(RND(1)*10)
100 NEXT I
110 PX=20:PY=23:SC=0
120 REM MAIN LOOP
130 POKE 1024,SC+48
140 POKE 1024+(PY*40)+PX,32
150 GET K$
160 IF K$="A" AND PX>0 THEN PX=PX-1
170 IF K$="D" AND PX&lt;39 THEN PX=PX+1
180 FOR I=1 TO 5
190 POKE 1024+(FY(I)*40)+FX(I),32
200 FY(I)=FY(I)+1
210 IF FY(I)>24 THEN FY(I)=0:FX(I)=INT(RND(1)*40)
220 IF FX(I)=PX AND FY(I)=PY THEN GOSUB 1000
230 POKE 1024+(FY(I)*40)+FX(I),42
240 POKE 55296+(FY(I)*40)+FX(I),3
250 NEXT I
260 POKE 1024+(PY*40)+PX,81
270 POKE 55296+(PY*40)+PX,7
280 FOR D=1 TO 15:NEXT D
290 GOTO 130
1000 REM COLLISION
1010 SC=SC+1
1020 GOSUB 2000
1030 FY(I)=0:FX(I)=INT(RND(1)*40)
1040 RETURN
2000 REM COIN SOUND
2010 POKE 54296,15
2020 POKE 54277,0:POKE 54278,240
2030 POKE 54274,0:POKE 54275,8
2040 POKE 54272,100:POKE 54273,30
2050 POKE 54276,65
2060 FOR T=1 TO 50:NEXT T
2070 POKE 54276,64
2080 RETURN
```

![Star Catcher basic version running](/images/commodore-64/phase-0/tier-1/lesson-014/example-1.png)

**What's happening here:**

Line 130 displays the current score in the top-left corner of the screen. We add 48 to SC because screen code 48 displays as '0', 49 as '1', and so on. Without the +48, a score of 1 would display as 'A', 2 as 'B', etc.—because those are what screen codes 1 and 2 represent.

Line 220 is where the magic happens: `IF FX(I)=PX AND FY(I)=PY THEN GOSUB 1000`. This checks whether the star at position I has exactly the same position as the player. If they match, we've got a collision.

The collision handler at line 1000 does three things: increases the score, plays a satisfying "coin collected" sound, and respawns the star at the top of the screen. Without that respawn on line 1030, you'd catch the star once and it would vanish forever.

## Experiment: Adding Danger

Right now, catching stars is consequence-free. Let's add a second type of object—red asteroids that cost you a life when you hit them:

```basic
10 REM STAR CATCHER COMPLETE
20 PRINT CHR$(147)
30 PRINT "   STAR CATCHER"
40 PRINT
50 PRINT "CATCH 20 CYAN STARS"
60 PRINT "AVOID RED ASTEROIDS"
70 PRINT
80 PRINT "A/D TO MOVE"
90 PRINT
100 PRINT "PRESS ANY KEY"
110 GET K$:IF K$="" THEN 110
120 PRINT CHR$(147)
130 DIM FX(8),FY(8),FT(8)
140 FOR I=1 TO 8
150 FX(I)=INT(RND(1)*40):FY(I)=INT(RND(1)*12)
160 FT(I)=INT(RND(1)*3)
170 NEXT I
180 PX=20:PY=23:SC=0:LV=3
190 REM MAIN LOOP
200 POKE 1024,SC+48
210 POKE 1030,LV+48
220 POKE 1024+(PY*40)+PX,32
230 GET K$
240 IF K$="A" AND PX>0 THEN PX=PX-1
250 IF K$="D" AND PX&lt;39 THEN PX=PX+1
260 FOR I=1 TO 8
270 POKE 1024+(FY(I)*40)+FX(I),32
280 FY(I)=FY(I)+1
290 IF FY(I)>24 THEN FY(I)=0:FX(I)=INT(RND(1)*40):FT(I)=INT(RND(1)*3)
300 IF FX(I)=PX AND FY(I)=PY THEN GOSUB 1000
310 IF FT(I)=0 THEN C=42:CL=3
320 IF FT(I)=1 OR FT(I)=2 THEN C=90:CL=2
330 POKE 1024+(FY(I)*40)+FX(I),C
340 POKE 55296+(FY(I)*40)+FX(I),CL
350 NEXT I
360 POKE 1024+(PY*40)+PX,81
370 POKE 55296+(PY*40)+PX,7
380 IF LV=0 THEN 500
390 IF SC>=20 THEN 600
400 FOR D=1 TO 12:NEXT D
410 GOTO 200
500 REM GAME OVER
510 POKE 1024+240,71:POKE 1024+241,65
520 POKE 1024+242,77:POKE 1024+243,69
530 POKE 1024+245,79:POKE 1024+246,86
540 POKE 1024+247,69:POKE 1024+248,82
550 FOR D=1 TO 500:NEXT D
560 END
600 REM YOU WIN
610 POKE 1024+240,89:POKE 1024+241,79
620 POKE 1024+242,85:POKE 1024+244,87
630 POKE 1024+245,73:POKE 1024+246,78
640 FOR D=1 TO 500:NEXT D
650 END
1000 REM COLLISION
1010 IF FT(I)=0 THEN SC=SC+1:GOSUB 2000
1020 IF FT(I)>0 THEN LV=LV-1:GOSUB 3000
1030 FY(I)=0:FX(I)=INT(RND(1)*40)
1040 RETURN
2000 REM COIN SOUND
2010 POKE 54296,15
2020 POKE 54277,0:POKE 54278,240
2030 POKE 54274,0:POKE 54275,8
2040 POKE 54272,100:POKE 54273,30
2050 POKE 54276,65
2060 FOR T=1 TO 50:NEXT T
2070 POKE 54276,64
2080 RETURN
3000 REM EXPLOSION SOUND
3010 POKE 54296,15
3020 POKE 54277,0:POKE 54278,240
3030 POKE 54272,255:POKE 54273,255
3040 POKE 54276,129
3050 FOR T=1 TO 50:NEXT T
3060 POKE 54276,128
3070 RETURN
```

Now we've got a proper game. The FT array (line 130) stores the *type* of each object: 0 means a good cyan star, 1 or 2 means a bad red asteroid. Lines 310-320 choose the character and colour based on FT(I).

The collision handler (line 1000) now checks the object type before deciding what to do. Good stars (FT(I)=0) increase your score and play a pleasant coin sound. Bad asteroids (FT(I)&gt;0) decrease your lives and play a harsh explosion sound.

Lines 380 and 390 check for game-over conditions. If lives reach zero, we jump to the GAME OVER screen at line 500. If score reaches 20, we jump to the YOU WIN screen at line 600. Notice how we POKE screen codes directly to write the messages—screen code 71 is 'G', 65 is 'A', and so on.

**Collision detection timing is critical.** We check for collisions (line 300) *after* the object has moved (line 280) but *before* we draw it (line 330). This ensures we're checking the object's new position, not where it was last frame. If you check before moving, you'll miss collisions. If you check after drawing, you'll see the collision visually but the code won't detect it until next frame—creating a frustrating one-frame delay.

**Screen code arithmetic is your friend.** Rather than looking up that screen code 48='0', 71='G', etc., remember that digits start at 48 and capital letters start at 65. So SC+48 converts a number to its digit representation, and you can spell words with POKE statements by adding offsets to 65.

**The FT array demonstrates object-oriented thinking in BASIC.** Even though BASIC has no classes or objects, we're treating each "object" as having properties: FX(I) is its X position, FY(I) is its Y position, FT(I) is its type. Keeping the same index (I) across all three arrays means we're describing the *same object*. This pattern scales to more complex games where objects might have speed, health, direction, animation frame, etc.—just add more parallel arrays.

## How It Works: The Collision Detection Dance

When line 220 executes `IF FX(I)=PX AND FY(I)=PY THEN GOSUB 1000`, the C64 is doing exact coordinate matching. Both X positions must be identical AND both Y positions must be identical. This is called **pixel-perfect collision** (well, character-perfect in this case).

Here's what happens when the player moves into a star:

1. **Line 150:** GET K$ reads that you pressed 'A'
2. **Line 160:** PX decreases from 20 to 19
3. **Line 190:** We erase the star at its old position
4. **Line 200:** The star falls (FY increases)
5. **Line 220:** Check: is FX(3)=19 AND FY(3)=23? Yes! Collision detected
6. **GOSUB 1000:** Jump to collision handler
7. **Line 1010:** Increase score (SC=SC+1)
8. **GOSUB 2000:** Play coin sound
9. **Line 1030:** Respawn star at top (FY(3)=0, new random FX)
10. **Line 1040:** RETURN to line 230 (continue the FOR loop)
11. **Line 230:** Draw the star at its new position

The whole sequence takes about 1/60th of a second. From the player's perspective, they moved into the star and it instantly vanished with a satisfying *ping*.

## What Game Designers Know

Every arcade game uses collision detection, but they all make different choices about *when* to check and *what counts* as a hit.

**Generous collision (player advantage):** Some games check if the player is *within 2 pixels* of the object rather than exactly on it. This makes the game feel more forgiving, especially with joystick controls where precision is difficult.

**Strict collision (challenge):** Other games check the exact position, or even make the hitbox *smaller* than the sprite. Classic "bullet hell" shooters often make your ship's hitbox just a single pixel at the centre—you can graze bullets without dying.

**Collision layers:** Professional games don't check *every* object against *every* other object. They use layers: "player vs enemies", "player vs power-ups", "bullets vs enemies". Our program only checks "player vs falling objects" (line 220)—we never check if stars collide with each other because that doesn't matter for gameplay.

**One collision per frame:** Notice that even if the player is touching three stars simultaneously, only one collision is processed per frame (whichever one the FOR loop hits first). This prevents the score from jumping by 3 in a single instant, which would feel wrong.

## From the Vault

**Hardware collision detection:** The VIC-II chip has built-in sprite collision detection registers at $D01E and $D01F. When sprites overlap, the chip automatically sets bits in these registers. You can read them to detect collisions without any coordinate checking—the hardware does it for you. We'll explore this in Tier 2 when we learn sprite programming.

**Classic collision games:** Pac-Man (1980) checks for collision between Pac-Man and dots, ghosts, and power pills. Space Invaders (1978) checks bullets against invaders and shields. Asteroids (1979) checks the ship against asteroids and against screen boundaries. Every single arcade game you've ever played is built on variations of `IF X1=X2 AND Y1=Y2`.

**The Curse of the Missing ELSE:** Some programmers try to optimise collision detection by writing `IF FX(I)=PX THEN IF FY(I)=PY THEN GOSUB 1000`. This creates nested IF statements instead of using AND. It's actually *slower* because BASIC has to process two separate IF commands. Always use AND for multi-condition checks.

## Quick Reference

**Collision Detection Pattern:**
```basic
220 IF FX(I)=PX AND FY(I)=PY THEN GOSUB 1000
```

**Collision Handler Template:**
```basic
1000 REM COLLISION
1010 SC=SC+1              :REM Update game state
1020 GOSUB 2000           :REM Audio feedback
1030 FY(I)=0:FX(I)=INT(RND(1)*40) :REM Respawn object
1040 RETURN
```

**Game State Variables:**
| Variable | Meaning | Typical Range |
|----------|---------|---------------|
| SC | Score | 0-999 |
| LV | Lives remaining | 0-9 |
| PX, PY | Player position | PX: 0-39, PY: 0-24 |
| FX(I), FY(I) | Object I position | FX: 0-39, FY: 0-24 |
| FT(I) | Object I type | 0=good, 1+=bad |

**Win/Lose Conditions:**
```basic
380 IF LV=0 THEN 500      :REM Out of lives = game over
390 IF SC>=20 THEN 600    :REM Hit target score = you win
```

**Screen Code Conversion:**
```basic
130 POKE 1024,SC+48       :REM Display score as digit (48='0')
210 POKE 1030,LV+48       :REM Display lives as digit
```

**Standard Game Flow:**
```
Title Screen (lines 20-100)
    ↓
Wait for Key Press (line 110)
    ↓
Initialize Game State (line 180)
    ↓
Main Game Loop (lines 190-410)
    ↓
Check Win Condition (line 390) → YOU WIN (line 600)
Check Lose Condition (line 380) → GAME OVER (line 500)
```

## What You've Learnt

You can now:
- Detect when the player touches an object using coordinate comparison (IF PX=FX AND PY=FY)
- Respond to collisions with multiple effects (sound, score, respawn)
- Track game state across multiple variables (SC, LV)
- Implement win and lose conditions that end the game
- Use object type arrays (FT) to create different collision behaviours
- Display numeric variables as screen digits using +48 conversion
- Structure a complete game loop from title to game-over
- Use GOSUB to keep collision handlers separate and readable
- Create feedback loops where one event (collision) triggers multiple systems (score, sound, visual)

This is the foundation of every action game ever written. You've completed the Dodge & Catch arc—you can now create complete arcade-style games with movement, falling objects, collision detection, scoring, and sound. Everything from Space Invaders to Tetris to modern mobile games uses these same principles.
