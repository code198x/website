You've learnt gravity, platform collision, animation, scrolling, enemy AI, collectibles, and polish across seven lessons. Now it's time to **synthesise everything** into a complete production-quality platformer.

**This lesson builds Crystal Caverns**—a complete action platformer comparable to early 1980s commercial games like Miner 2049er or Jumpman Jr. You'll integrate all systems from lessons 33-39 into a cohesive, playable game with professional presentation. This is your first complete game in Tier 3.

The key insight: **Synthesis is about system integration and state management**. Each system (physics, enemies, collectibles, camera) operates independently but coordinates through shared game state. The main loop orchestrates these systems in the right order. Success comes from careful testing of system interactions—does the camera follow during scrolling? Do enemies respect platforms? Does the HUD update when collecting items?

---

## The One-Minute Tour

**Complete Game Structure:**
- **State machine (GS):** Title screen → gameplay → game over/victory → title
- **Main game loop:** HUD → input → physics → enemies → collectibles → camera → draw → sprites
- **System integration:** Eight independent systems coordinated through shared variables
- **Data-driven design:** Platforms, enemies, and items defined in DATA statements

**Core Systems Integrated:**
- **Physics (L33):** Gravity + jumping with ground detection
- **Platforms (L34):** Multi-platform collision for player and enemies
- **Animation (L35):** Multi-state sprite animation (idle/walk/jump)
- **Scrolling (L36):** Camera-based horizontal scrolling across 3 screens
- **Enemies (L37):** Patrol/chase AI with platform awareness
- **Collectibles (L38):** Gems for score, key for door unlock
- **Polish (L39):** Title screen, HUD, lives system, sound effects

**Performance Characteristics:**
- **During scrolling:** ~8-10 fps (screen redraw bottleneck)
- **Stationary scenes:** ~12-15 fps (animation + physics + AI)
- **Discovery:** Playable and fun, but noticeably choppy during scrolling

Let's start with a simplified version showing how the main systems connect:

```basic
10 REM SIMPLE PLATFORMER INTEGRATION
20 PRINT CHR$(147)
30 REM SET UP SPRITES
40 POKE 53269,3:REM ENABLE SPRITES 0-1
50 REM PLAYER SPRITE
60 FOR I=0 TO 62:POKE 832+I,0:NEXT I
70 POKE 832,24:POKE 833,60:POKE 834,126
80 POKE 835,219:POKE 836,255:POKE 837,126
90 POKE 838,60:POKE 839,24
100 POKE 2040,13:POKE 53287,7
110 REM ENEMY SPRITE
120 POKE 2041,13:POKE 53288,2
130 REM HUD SETUP
140 FOR I=1 TO 5:POKE 1024+I,83:POKE 55296+I,2:NEXT I
150 POKE 1024+28,19:POKE 1024+29,3:REM "SC"
160 REM GAME VARIABLES
170 PX=100:PY=150:VX=0:VY=0:OG=1
180 EX=200:EY=150:SC=0:HP=3
190 REM MAIN LOOP
200 GOSUB 1000:REM INPUT
210 GOSUB 2000:REM PHYSICS
220 GOSUB 3000:REM UPDATE SPRITES
230 GOTO 200
1000 REM JOYSTICK INPUT
1010 J=PEEK(56320)
1020 VX=0
1030 IF (J AND 4)=0 THEN VX=-2
1040 IF (J AND 8)=0 THEN VX=2
1050 IF (J AND 16)=0 AND OG=1 THEN VY=-5:OG=0
1060 RETURN
2000 REM PHYSICS
2010 VY=VY+0.3:IF VY>8 THEN VY=8
2020 PX=PX+VX:PY=PY+VY
2030 IF PX<0 THEN PX=0
2040 IF PX>320 THEN PX=320
2050 REM GROUND COLLISION
2060 IF PY>=180 THEN PY=180:VY=0:OG=1
2070 RETURN
3000 REM UPDATE SPRITES
3010 POKE 53248,PX:POKE 53249,PY+50
3020 POKE 53250,EX:POKE 53251,EY+50
3030 RETURN
```

**What's happening:**
- **Line 40-120:** Sprite setup for player (sprite 0, white) and enemy (sprite 1, red)
- **Line 130-150:** HUD setup with hearts (health) and score label at top of screen
- **Line 190-230:** Main loop calls input → physics → sprite update in sequence

This demonstrates the **core integration pattern**: independent systems (input, physics, rendering) coordinated through shared variables (PX, PY, VX, VY) and called in sequence each frame.

## The Complete Game: Crystal Caverns

Now let's look at the complete game structure integrating all eight systems from lessons 33-39. This is approximately 180 lines implementing:

### Game Architecture

**State Machine (Lines 10-80):**
```basic
10 REM CRYSTAL CAVERNS PLATFORMER
20 REM COMPLETE SYNTHESIS GAME
30 PRINT CHR$(147)
40 REM GAME STATE: 0=TITLE,1=PLAY,2=GAMEOVER,3=WIN
50 GS=0:LV=3:SC=0:HP=3:KY=0
60 REM MAIN LOOP
70 ON GS+1 GOSUB 1000,2000,8000,9000
80 GOTO 70
```

The `ON GS+1 GOSUB` pattern routes to different game states:
- **GS=0 (Title):** Line 1000 shows title screen, waits for fire button
- **GS=1 (Play):** Line 2000 runs main game loop with all systems
- **GS=2 (Game Over):** Line 8000 shows game over screen, returns to title
- **GS=3 (Victory):** Line 9000 shows victory screen, returns to title

**Main Game Loop (Lines 2000-2098):**
```basic
2000 REM PLAY GAME
2010 GOSUB 2100:REM HUD
2020 GOSUB 2220:REM INPUT
2030 GOSUB 2300:REM PHYSICS
2040 GOSUB 2500:REM ANIMATION
2050 GOSUB 3000:REM CAMERA
2060 GOSUB 3100:REM DRAW SCREEN
2070 GOSUB 4000:REM ENEMIES
2080 GOSUB 5000:REM COLLECTIBLES
2090 GOSUB 6000:REM GOALS
2095 GOSUB 7000:REM UPDATE SPRITES
2098 RETURN
```

Each frame executes these systems in order:
1. **HUD (2100):** Update health/score/key display if changed
2. **Input (2220):** Read joystick, set velocity, handle jump
3. **Physics (2300):** Apply gravity, move player, check platforms
4. **Animation (2500):** Update sprite frame based on state (idle/walk/jump)
5. **Camera (3000):** Calculate camera position following player
6. **Draw Screen (3100):** Redraw visible portion of level if camera moved
7. **Enemies (4000):** AI, movement, platform collision, player collision
8. **Collectibles (5000):** Check player proximity to gems/keys
9. **Goals (6000):** Check door unlock and level completion
10. **Sprites (7000):** Position player and enemy sprites on screen

### System Details

**HUD with Change Detection (Lines 2100-2217):**
```basic
2100 REM HUD UPDATE
2110 IF HP<>LH THEN GOSUB 2150
2120 IF SC<>LS THEN GOSUB 2180
2130 IF KY<>LK THEN GOSUB 2200
2140 RETURN
2150 REM DRAW HEALTH HEARTS
2155 LH=HP
2160 FOR I=1 TO 5
2165 IF I<=HP THEN POKE 1024+I,83:POKE 55296+I,2
2170 IF I>HP THEN POKE 1024+I,32:POKE 55296+I,0
2175 NEXT I
2177 RETURN
```

Only redraws HUD elements when values change (HP&lt;&gt;LH compares health to last health). This avoids redrawing every frame, reducing overhead. Similar patterns for score (LS) and key (LK).

**Platform Collision with Arrays (Lines 2400-2460):**
```basic
2400 REM PLATFORM COLLISION
2410 OG=0:IF VY<0 THEN RETURN
2420 FOR I=1 TO NP
2430 IF PY<PP(I,1)-8 OR PY>PP(I,1)+8 THEN NEXT I:RETURN
2440 IF PX<PP(I,0) OR PX>PP(I,0)+PP(I,2) THEN NEXT I:RETURN
2450 PY=PP(I,1):VY=0:OG=1
2460 RETURN
```

Platforms stored in `PP(6,2)` array: PP(I,0)=X position, PP(I,1)=Y position, PP(I,2)=width. Checks if player is near platform Y (±8 pixels) and within platform X range. If so, lands player on platform and sets OG=1 (on ground).

**Enemy AI State Machine (Lines 4100-4140):**
```basic
4100 REM ENEMY AI
4110 DS=ABS(PX-EX(I))
4120 IF DS<80 THEN ES(I)=1:RETURN  :REM CHASE
4130 ES(I)=0  :REM PATROL
4140 RETURN
```

Simple distance-based AI: if player within 80 pixels, chase (ES=1). Otherwise patrol (ES=0). Enemy movement routine (4200-4290) uses this state to set velocity—patrol moves slowly, chase moves faster toward player.

**Camera Follow with Redraw Threshold (Lines 3000-3190):**
```basic
3000 REM CAMERA FOLLOW
3010 CX=PX-160
3020 IF CX<0 THEN CX=0
3030 IF CX>640 THEN CX=640
3040 RETURN
3100 REM DRAW SCREEN
3110 IF ABS(CX-LX)<8 THEN RETURN
3120 LX=CX
3130 OF=INT(CX/8)
3140 FOR Y=2 TO 24
3150 FOR X=0 TO 39
3160 LI=OF+X
3170 IF LI<LEN(LV$(Y-2)) THEN C=ASC(MID$(LV$(Y-2),LI+1,1)):POKE 1024+Y*40+X,C
3180 NEXT X:NEXT Y
3190 RETURN
```

Camera centres on player (CX=PX-160). Only redraws screen if camera moved more than 8 pixels (ABS(CX-LX)&lt;8) to avoid constant redrawing. When redrawing, calculates character offset (OF=INT(CX/8)) and extracts visible portion of level string (LV$) using MID$.

**Collectibles with Type System (Lines 5000-5095):**
```basic
5000 REM COLLECTIBLES
5010 FOR I=1 TO NI
5020 IF IC(I)=1 THEN 5090
5030 DX=PX-IX(I):DY=PY-IY(I)
5040 IF SQR(DX*DX+DY*DY)>20 THEN 5090
5050 IC(I)=1
5060 IF IT(I)=1 THEN SC=SC+5:GOSUB 6400
5070 IF IT(I)=2 THEN KY=1:GOSUB 6500
5090 NEXT I
5095 RETURN
```

Items stored in arrays: IX/IY (position), IT (type: 1=gem, 2=key), IC (collected flag). Checks distance from player (line 5040). If close enough, marks collected and triggers effect based on type—gems add score, key sets KY=1.

**Sound Effects (Lines 6100-6550):**
```basic
6100 REM JUMP SOUND
6110 POKE 54296,15:POKE 54272,150:POKE 54273,8
6120 POKE 54278,17:FOR T=1 TO 50:NEXT T:POKE 54278,16
6130 RETURN
```

Each sound effect is a subroutine: set SID volume (54296), frequency (54272-54273), waveform (54278), delay with FOR loop, then gate off (54278 bit 0). Non-blocking—quick enough not to disrupt gameplay.

**Data-Driven Level Design (Lines 9700-10290):**
```basic
9700 REM PLATFORM DATA
9710 NP=6
9720 DIM PP(6,2)
9730 REM X,Y,WIDTH
9740 PP(1,0)=0:PP(1,1)=200:PP(1,2)=160
9750 PP(2,0)=200:PP(2,1)=200:PP(2,2)=160
...
10070 DATA "############################..."
10080 DATA "#                          ..."
```

Level defined through DATA: platform positions/sizes, enemy starting positions, item locations, level layout strings. Easy to modify without changing logic—just update DATA statements for new levels.

## Integration Patterns

**System Coordination Through Shared State:**

Different systems coordinate by reading/writing shared variables:

| Variable | Written By | Read By | Purpose |
|----------|-----------|---------|---------|
| PX, PY | Physics (2300) | Camera (3000), Enemies (4000), Items (5000), Sprites (7000) | Player position |
| VX, VY | Input (2220), Physics (2300) | Physics (2300), Animation (2500) | Player velocity |
| OG | Physics (2400) | Input (2220), Animation (2500) | On ground flag |
| CX | Camera (3000) | Draw (3100), Sprites (7000) | Camera X position |
| HP, SC, KY | Enemies (4500), Items (5000) | HUD (2100), Goals (6000) | Health, score, key |
| GS | Title (1000), Enemies (4600), Goals (6000) | Main loop (70) | Game state |

**Order Dependencies:**

The main loop order matters:
1. **HUD first** (2100) so it updates before other systems change HP/SC/KY
2. **Input before physics** (2220→2300) so VX/VY set before movement applied
3. **Physics before animation** (2300→2500) so OG updated before state determined
4. **Camera before draw** (3000→3100) so CX calculated before screen drawn
5. **Sprites last** (7000) so all positions finalised before rendering

Wrong order causes visual glitches or incorrect behaviour.

## Testing System Interactions

When integrating systems, test these interactions carefully:

**Physics + Platforms:**
- Can jump and land on all platforms?
- No falling through platforms when moving fast?
- Gravity feels appropriate (not too floaty/heavy)?

**Camera + Drawing:**
- Screen scrolls smoothly as player moves right?
- No visible tearing or incomplete updates?
- HUD stays fixed at top (doesn't scroll)?

**Enemies + Platforms:**
- Enemies walk on platforms without falling through?
- Enemies don't fly off platform edges?
- Chase behaviour works when player nearby?

**Player + Enemies:**
- Stomping from above kills enemy?
- Touching from side takes damage?
- Respawn works correctly after death?

**Collectibles + HUD:**
- Collecting gem increases score immediately in HUD?
- Key appears in HUD when collected?
- Items disappear after collection?

**Goals + State:**
- Door unlocks only when holding key?
- Victory triggers when reaching exit after door unlocked?
- Game over triggers when lives reach zero?

These interaction tests find bugs that unit testing individual systems wouldn't catch.

## Performance Analysis

**Measured frame times (approximate):**

| System | Time per Frame | Impact |
|--------|----------------|--------|
| HUD update (change detection) | ~2ms | Minimal |
| Joystick input | ~1ms | Minimal |
| Player physics | ~3ms | Minimal |
| Animation update | ~5ms | Minimal |
| Camera calculation | ~1ms | Minimal |
| **Screen redraw (scrolling)** | **~100ms** | **Major** |
| Enemy AI + physics (3 enemies) | ~10ms | Minor |
| Item collision checks (8 items) | ~5ms | Minimal |
| Goal checks | ~2ms | Minimal |
| Sprite positioning | ~3ms | Minimal |
| **Total (scrolling)** | **~132ms** | **~7-8 fps** |
| **Total (stationary)** | **~32ms** | **~31 fps** |

**Key discovery:** Screen redraw dominates performance when scrolling. Character-based scrolling requires copying 23 rows × 40 columns = 920 characters, taking ~100ms. When stationary (no redraw), game runs at acceptable ~30 fps. During scrolling, drops to ~7-8 fps.

**This reveals BASIC's action game limit:** The FOR Y/FOR X loop in screen redraw (3140-3180) is the bottleneck. Assembly language could redraw in &lt;1ms, enabling 60 fps smooth scrolling. But for BASIC platformers, character-based scrolling creates noticeable choppiness.

**Your discovery:** "My platformer works and is fun to play! The gameplay mechanics feel solid—jumping, landing on platforms, stomping enemies. But during scrolling, I notice frame skips and choppiness. It's playable but not arcade-smooth. I understand now why many 1980s BASIC games used flip-screen navigation instead of scrolling."

## From Simple to Complex

**Lesson 033 starting point:**
```basic
100 REM GRAVITY
110 VY=VY+0.3:IF VY>8 THEN VY=8
120 PY=PY+VY
```
Simple gravity—just add velocity each frame.

**Lesson 040 integration:**
```basic
2300 REM PHYSICS
2310 VY=VY+0.3:IF VY>8 THEN VY=8
2320 PX=PX+VX:PY=PY+VY
2330 REM BOUNDARIES
2340 IF PX<0 THEN PX=0:VX=0
2350 IF PX>960 THEN PX=960:VX=0
2360 REM PLATFORM COLLISION
2370 GOSUB 2400
```

Now gravity is **one part** of physics system that also handles:
- Horizontal movement (PX=PX+VX)
- Boundary checking (world edges)
- Platform collision (GOSUB 2400)

The principle: **simple concepts combine into complex systems**. Each lesson taught one concept. The synthesis lesson shows how they work together.

## Code Organisation at Scale

At 180 lines, organisation matters:

**Line number ranges:**
- **100-999:** Initialisation, main loop, state machine
- **1000-1999:** Title screen and menu
- **2000-2999:** Player systems (input, physics, animation, HUD)
- **3000-3999:** Camera and screen drawing
- **4000-4999:** Enemy systems (AI, physics, collision)
- **5000-5999:** Collectibles
- **6000-6999:** Goals and sound effects
- **7000-7999:** Sprite rendering
- **8000-8999:** Game over/victory screens
- **9000-9999:** Initialisation and data loading
- **10000+:** Level data

**Comment blocks separate systems:**
```basic
2000 REM ===== PLAYER SYSTEMS =====
...
4000 REM ===== ENEMY SYSTEMS =====
```

**Subroutine hierarchy:**
```
2000 (Play game)
├─ 2100 (HUD)
│  ├─ 2150 (Draw hearts)
│  ├─ 2180 (Draw score)
│  └─ 2200 (Draw key)
├─ 2220 (Input)
├─ 2300 (Physics)
│  └─ 2400 (Platform collision)
└─ ...
```

Organisation prevents chaos at this scale. Without structure, debugging becomes impossible.

## Extensions and Variations

**After completing the base game, try:**

1. **Multiple levels:** Create second level with different platform layout, enemy positions. Load from DATA based on level number.

2. **Moving platforms:** Add platform velocity (PPV array). In physics, update PP(I,0)=PP(I,0)+PPV(I). Handle player standing on moving platform.

3. **Power-ups:** Temporary invincibility (flashing sprite, ignore enemy collision for 100 frames). Speed boost (increase VX multiplier).

4. **Boss fight:** Large enemy with health bar, attack patterns, defeat condition for level completion.

5. **Vertical scrolling:** Add camera Y (CY) following player Y. Redraw screen when CY changes. Taller levels (50+ rows).

6. **Parallax background:** Second scrolling layer at different speed. Creates depth illusion.

7. **Timer challenge:** Add countdown timer. Victory requires reaching exit before time expires. High score based on time remaining.

8. **High score save:** Use lesson 45 disk operations to save/load high scores. Display at title screen.
