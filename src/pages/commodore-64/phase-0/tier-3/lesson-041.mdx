You've just built Crystal Caverns—an action platformer running at 8-10 fps during scrolling. The BASIC interpreter's speed was the bottleneck. Now you're starting a new arc: **Turn-Based RPG**. Here's the revelation: when you eliminate continuous movement and screen redraws, BASIC's speed limitations **disappear completely**.

**This lesson builds room-based dungeon navigation**—the foundation of text RPGs and dungeon crawlers like Zork, Adventure, and early Ultima games. You'll create a 6-12 room dungeon with directional movement (NSEW), room descriptions, and exit validation. Every input feels instant (&lt;10ms response). BASIC is perfect for this.

The key insight: **Turn-based games play to BASIC's strengths**. No sprite updates, no physics loops, no screen redraws. Just text output, input handling, and game logic. The player moves from room to room instantly. Games feel incredibly responsive compared to real-time platformers.

---

## The One-Minute Tour

**Room-Based Navigation:**
- **Room data structure:** Name, description, exits (N/S/E/W), contents
- **Movement system:** GET input (N/S/E/W), validate exit, teleport to new room
- **Graph-based design:** Rooms as nodes, exits as edges in directed graph
- **Text display:** Clear screen, print room info, show available exits
- **Instant response:** No rendering delay, pure text output

**Data Storage:**
- **Arrays:** `RN$(12)` for room names, `RD$(12)` for descriptions
- **Exit array:** `EX(12,4)` maps room + direction to destination room number
- **Direction constants:** N=1, S=2, E=3, W=4 for array indexing
- **Current room:** `CR` variable tracks player location (starts at 1)

**Performance Discovery:**
- **Response time:** &lt;10ms per action (effectively instant)
- **No speed bottlenecks:** Text-only, no graphics to redraw
- **After platformers:** Feels incredibly smooth and professional
- **Reality:** Turn-based design eliminates BASIC's weaknesses entirely

## Room Data Structure Explained

The three arrays work together to define your dungeon:

### Room Names: `RN$(12)`
Short titles displayed at top of screen:
```basic
RN$(1) = "ENTRANCE HALL"
RN$(2) = "GUARD ROOM"
RN$(3) = "ARMORY"
```

**Design guidelines:**
- Keep under 20 characters (fits on screen with === borders)
- Descriptive but concise
- Title case for readability

### Room Descriptions: `RD$(12)`
Atmospheric text shown when entering room:
```basic
RD$(1) = "STONE WALLS SURROUND YOU. TORCHES FLICKER."
RD$(2) = "RUSTY WEAPONS HANG ON WALLS. A GUARD SLEEPS."
```

**Writing good descriptions:**
- **2-3 short sentences** (under 80 characters total)
- **Sensory details:** What do you see, hear, smell?
- **Hints about purpose:** Armory has weapons, throne room has seat
- **Atmospheric:** Create mood (dark, scary, grand, dusty)

**Avoid:**
- Long paragraphs that scroll off screen
- Generic descriptions ("A room. It has walls.")
- Excessive detail unnecessary for gameplay

### Exit Array: `EX(12,4)`
Two-dimensional array mapping room + direction to destination:
```basic
EX(1,N) = 2  :REM ROOM 1 NORTH EXIT LEADS TO ROOM 2
EX(1,S) = 0  :REM ROOM 1 HAS NO SOUTH EXIT (WALL)
EX(1,E) = 0  :REM ROOM 1 HAS NO EAST EXIT
EX(1,W) = 5  :REM ROOM 1 WEST EXIT LEADS TO ROOM 5
```

**Key insight:** Zero means blocked/no exit. Non-zero is room number to teleport to.

**Building bidirectional connections:**
```basic
REM CONNECT ROOM 1 AND 2 (TWO-WAY)
EX(1,N) = 2  :REM 1 → 2 GOING NORTH
EX(2,S) = 1  :REM 2 → 1 GOING SOUTH
```

**Common mistake:** Asymmetric exits—room 1 north leads to 2, but room 2 south doesn't lead back to 1. This creates one-way passages (which can be intentional for trapdoors or secret passages, but usually it's a bug).

## Movement System Deep Dive

The movement subroutine (line 3000) performs three critical checks:

### Step 1: Parse Input Direction
```basic
3010 DR=0:REM DIRECTION
3020 IF A$="N" THEN DR=N
3030 IF A$="S" THEN DR=S
3040 IF A$="E" THEN DR=E
3050 IF A$="W" THEN DR=W
3060 IF DR=0 THEN PRINT "INVALID DIRECTION":FOR I=1 TO 500:NEXT I:RETURN
```

If player presses any key other than N/S/E/W, `DR` remains 0 and error message displays. The `FOR I=1 TO 500:NEXT I` loop creates a brief pause so player sees the message before screen clears.

### Step 2: Check Exit Exists
```basic
3070 REM CHECK EXIT EXISTS
3080 IF EX(CR,DR)=0 THEN PRINT "WALL BLOCKS PATH":FOR I=1 TO 500:NEXT I:RETURN
```

Even if direction is valid (N/S/E/W), the exit might be blocked. `EX(CR,DR)=0` means wall. Player sees feedback and stays in current room.

### Step 3: Teleport to New Room
```basic
3090 REM MOVE TO NEW ROOM
3100 CR=EX(CR,DR)
3110 RETURN
```

If exit exists, simply update `CR` (current room) to destination room number. Next loop iteration displays new room. **Instant teleportation**—no animation, no transition delay.

**This is why turn-based games feel so responsive in BASIC:** Movement is just changing a variable. No sprite updates, no screen scrolling, no collision detection loops.

## Graph-Based Level Design

Think of your dungeon as a **directed graph**:
- **Nodes:** Rooms (1-12)
- **Edges:** Exits (directional connections between rooms)
- **Properties:** Room name, description, contents

### Design Principles

**1. Hub-and-Spoke Layout**
Central room (hub) with multiple branches:
```
    [2]
     |
[3]--[1]--[4]
     |
    [5]
```
**Advantage:** Easy navigation, clear choices, good for tutorial areas.

**2. Linear Progression**
One main path with side branches:
```
[1]--[2]--[3]--[4]
      |
     [5]
```
**Advantage:** Guides player forward, good for story-driven dungeons.

**3. Maze Layout**
Interconnected rooms with multiple paths:
```
[1]--[2]--[3]
 |    |    |
[4]--[5]--[6]
```
**Advantage:** Exploration challenge, multiple solutions, replayability.

**4. Tower/Descent**
Vertical progression (use N/S as up/down):
```
[1]  Ground
 |
[2]  Level 2
 |
[3]  Level 3
```
**Advantage:** Clear progression sense, works well for castle towers or mine shafts.

### Common Design Mistakes

**Unreachable rooms:**
```basic
EX(1,N) = 2  :REM 1 CONNECTS TO 2
EX(3,E) = 4  :REM 3 CONNECTS TO 4
REM BUT NO CONNECTION TO ROOM 3—IT'S UNREACHABLE!
```

**Asymmetric exits (unintentional one-way):**
```basic
EX(1,N) = 2  :REM 1 NORTH → 2
EX(2,S) = 0  :REM 2 SOUTH BLOCKED (PLAYER TRAPPED IN ROOM 2!)
```

**Exit to non-existent room:**
```basic
DIM RN$(6)  :REM ONLY 6 ROOMS
EX(1,N) = 10  :REM EXIT LEADS TO ROOM 10 (DOESN'T EXIST!)
```

**Testing strategy:** Draw your map on paper first. Trace paths from entrance to all rooms. Verify all connections are bidirectional (unless intentionally one-way). Test in-game by visiting every room.

## Input Methods Compared

### Method 1: GET (Current Implementation)
```basic
2010 PRINT "WHICH WAY? (N/S/E/W): ";
2020 GET A$:IF A$="" THEN 2020
2030 RETURN
```
**Pros:** Instant response, single keypress, no RETURN needed
**Cons:** Exact match required (lowercase "n" won't work), easy to mistype

### Method 2: INPUT with LEFT$
```basic
2010 INPUT "DIRECTION";D$
2020 IF D$="" THEN 2030
2030 A$=LEFT$(D$,1)
2040 RETURN
```
**Pros:** Accepts "NORTH" or "N", more forgiving, shows what player typed
**Cons:** Requires pressing RETURN, slower, more code

### Method 3: Number Keys
```basic
2010 PRINT "1=N, 2=S, 3=E, 4=W: ";
2020 GET A$:IF A$="" THEN 2020
2030 IF A$="1" THEN A$="N"
2040 IF A$="2" THEN A$="S"
2050 IF A$="3" THEN A$="E"
2060 IF A$="4" THEN A$="W"
2070 RETURN
```
**Pros:** Number keys in consistent positions, fast to type
**Cons:** Less intuitive than compass directions, requires translation

**Recommendation:** Start with GET method (current implementation). It's fastest and most responsive. For commercial games, consider INPUT method for better usability.

```basic
1045 IF IT$(CR)<>"" THEN PRINT "YOU SEE: ";IT$(CR)
```

Check for key before allowing movement:
```basic
3075 REM CHECK FOR LOCKED DOOR
3076 IF CR=3 AND DR=E AND KY=0 THEN PRINT "DOOR IS LOCKED":RETURN

```

Chance of enemy encounter on movement:
```basic
3105 REM RANDOM ENCOUNTER CHECK
3110 IF RND(1)<0.3 THEN PRINT "MONSTER ATTACKS!":GOSUB 4000
```

### Room Visited Tracking
Remember which rooms player has been to:
```basic
70 DIM VT(12):REM VISITED FLAG
1005 IF VT(CR)=0 THEN PRINT "FIRST VISIT":VT(CR)=1
```

Show ASCII map of visited rooms:
```basic
5000 REM DISPLAY MAP
5010 PRINT CHR$(147)
5020 FOR I=1 TO 12
5030 IF VT(I)=1 THEN PRINT "[";I;"]";
```

## Performance Insight

Let's compare turn-based navigation to your platformer from L40:

**Crystal Caverns Platformer (L40):**
- Continuous main loop running 50-60 times per second
- Screen redraw every frame (8-10 fps during scrolling)
- Sprite updates, physics calculations, collision detection
- Frame rate bottleneck: BASIC interpreter speed
- Player feels: Choppy, laggy, waiting for screen updates

**Room-Based Dungeon (L41):**
- Event-driven: Only updates on player input
- Single screen clear + text print per action
- No continuous loop overhead
- Response time: &lt;10ms (limited only by keyboard scan)
- Player feels: Instant, professional, no waiting

**The revelation:** When you eliminate continuous rendering, BASIC's speed isn't a limitation anymore. Turn-based games can feel as responsive as assembly language programs because the bottleneck (screen updates) only happens once per player action.

**This is why so many successful C64 games were turn-based RPGs, adventure games, and strategy games.** Developers discovered BASIC was perfect for these genres. Games like Wizard's Crown, Temple of Apshai, and Telengard sold thousands of copies despite being written in BASIC.
