Your platformer works brilliantly—within the confines of one screen. But great platform games like **Miner 2049er** and **Impossible Mission** feature sprawling multi-screen worlds. The player character explores vast levels that scroll horizontally as they move.

**This lesson introduces horizontal scrolling**—the technique that expands your game world beyond the screen boundaries. You'll learn to implement camera systems that follow the player, store and render multi-screen level data efficiently, and understand the fundamental limitations of character-based scrolling in BASIC.

The key discovery: **BASIC scrolling is character-based, not pixel-based**. The VIC-II chip has hardware registers for smooth scrolling, but accessing them requires assembly language. In BASIC, scrolling moves in 8-pixel jumps—visibly jerky but functionally playable. You'll experience this limitation firsthand and discover another boundary of BASIC programming.

---

## The One-Minute Tour

**Camera System Basics:**
- **Camera position (CX)** tracks horizontal view offset in pixels
- **Camera follows player** by centering them on screen (CX = PX - 160)
- **Camera boundaries** prevent showing beyond level edges
- **Sprite positions become relative** to camera (screen X = world X - camera X)

**Character-Based Scrolling:**
- **8-pixel jumps** because screen memory is character-based (1 char = 8 pixels)
- **Full screen redraw** when camera moves beyond threshold (typically 8 pixels)
- **Visible "pop"** as screen jumps to new position
- **No smooth pixel scrolling** without VIC-II hardware control (assembly required)

**Performance Impact:**
- **Screen redraw costs ~100ms** (redrawing 1000 characters)
- **Frame rate drops** from ~14 fps to ~6 fps when scrolling
- **Playable but sluggish** movement during scrolling moments
- **Discovery moment:** Experience the performance wall of BASIC rendering

**What happens:**

```
Without this check: Screen redraws every frame, causing constant flicker
```

**Why this works:** Camera tracks player position, screen redraw shows the appropriate section of the level data, and sprite position is adjusted relative to camera for correct on-screen placement.

**What's different:**
- Lines 170-190: Full physics system (gravity, velocity, jump force, grounded flag)

**The sprite positioning formula:**
```
Screen X = World X - Camera X + 24

World X (PX): Absolute position in level (0-959 pixels)
Camera X (CX): Current view offset (0-639 pixels)
Screen X (SX): Where to draw sprite (24-320 pixels typically)
+24: Border offset to prevent sprite clipping at left edge
```

**Why this matters:** Without camera adjustment, sprite would stay at absolute world position, moving off-screen as camera scrolls. Subtracting camera X makes sprite position relative to viewport.

## How Camera Following Works

**Direct center following (used in examples):**
```
Camera X = Player X - 160

When player at PX=200:
  CX = 200 - 160 = 40 (camera offset 40 pixels into level)
  Screen shows characters 5-44 (40÷8=5 character offset)
  Player sprite at SX = 200-40+24 = 184 (centered on screen)
```

**Camera boundaries:**
```
IF CX<0 THEN CX=0           (Left edge: don't scroll past level start)
IF CX>639 THEN CX=639       (Right edge: 960 pixels wide - 320 screen = 640 max)
```

**Alternative: Dead zone following:**
```
IF PX > CX+200 THEN CX=PX-200  (Player near right edge? Scroll right)
IF PX < CX+120 THEN CX=PX-120  (Player near left edge? Scroll left)
```

This creates a "comfort zone" where player can move without camera following immediately. Only when reaching zone edge does camera catch up. Many professional games use this approach for less aggressive camera movement.

## Why Character-Based Scrolling Is Jerky

**The fundamental limitation:**

VIC-II has hardware registers (**$D016**) that control fine horizontal scrolling in 1-pixel increments. Setting these registers smoothly scrolls the entire screen without redrawing. But these are hardware registers—assembly language territory.

**What BASIC can do:**
- Read and write screen memory (1024-2023) character by character
- Each character is 8×8 pixels
- "Scrolling" means shifting which characters are visible
- Movement happens in 8-pixel jumps—one full character at a time

**What you'll see:**
- Player moves smoothly (sprite position updates in 2-pixel steps)
- Every ~4 steps, screen "pops" to new position (8-pixel threshold reached)
- Brief freeze during screen redraw (~100ms to POKE 1000 characters)
- Visible jerkiness but still playable

**Discovery moment:** You've hit BASIC's rendering performance wall. Smooth scrolling exists on the C64—games like **Boulder Dash** and **Trailblazer** prove it—but it requires assembly language to manipulate VIC-II registers directly.

## Performance Impact: The Numbers

**Without scrolling (static screen):**
- Input: ~10ms
- Physics: ~20ms
- Sprite update: ~10ms
- **Total: ~40ms per frame = 25 fps**

**With character-based scrolling:**
- Input: ~10ms
- Physics: ~20ms
- Camera update: ~5ms
- Screen redraw (when triggered): ~100ms
- Sprite update: ~10ms
- **Total with redraw: ~145ms = 6-7 fps**
- **Total without redraw: ~45ms = 22 fps**

**What this means:**
- Every 4 player steps triggers a screen redraw
- Brief stutter as screen updates
- Movement still responsive between redraws
- Playable but noticeably sluggish compared to assembly scrollers

**Optimisation attempts:**
- Increase threshold (line 3010): Scroll less often, longer jumps (even jerkier)
- Partial updates: Only redraw changed columns (complex, still slow)
- Reduce level detail: Fewer characters to POKE (less visual interest)

None solve the fundamental problem: **BASIC is too slow for smooth scrolling**. The C64 hardware can do it—BASIC can't access it efficiently.

## Level Data Storage Strategies

**Method 1: String arrays (used in examples)**
```basic
DIM LV$(25)
FOR Y=0 TO 24:READ LV$(Y):NEXT Y
DATA "######## ########..."
```
**Pros:** Easy to visualise and edit, straightforward to read with MID$
**Cons:** Memory-intensive (1 byte per character + string overhead)

**Method 2: Numeric arrays**
```basic
DIM LV(25,120)
FOR Y=0 TO 24:FOR X=0 TO 119:READ LV(Y,X):NEXT X:NEXT Y
DATA 35,35,35,32,32...  (35='#', 32=space)
```
**Pros:** More memory-efficient, faster array access
**Cons:** Hard to visualise level layout in code, tedious to type

**Method 3: Run-length encoding**
```basic
DATA 20,35,10,32,5,64  (20×'#', 10×space, 5×'@')
```
**Pros:** Very compact for levels with repeated patterns
**Cons:** Slower decode, more complex to implement and edit

For BASIC projects, **string arrays** offer the best balance of simplicity and readability. Memory isn't tight for 3-screen levels (~3KB). Professional games use compressed formats, but those require significant decoding overhead.

## Common Pitfalls

**1. Redrawing every frame**
```basic
REM WRONG: No threshold check
3000 REM DRAW SCREEN
3010 OF=INT(CX/8)
3020 FOR Y=0 TO 24:FOR X=0 TO 39...
```
**Result:** Constant screen flicker, unplayable

**Fix:** Add threshold check: `IF ABS(CX-LX)<8 THEN RETURN`

**2. Forgetting to initialise LX**
```basic
REM WRONG: LX starts at 0
120 CX=0:PX=160
```
**Result:** ABS(0-0)&lt;8 is true, screen never draws initially!

**Fix:** Set LX to impossible value: `LX=-999`

**3. Sprite position still absolute**
```basic
REM WRONG: Using world coordinates
3100 POKE 53248,PX
```
**Result:** Sprite moves off-screen when camera scrolls

**Fix:** Calculate screen position: `SX=PX-CX+24`

**4. Level data too short**
```basic
REM WRONG: Only 80 characters wide (2 screens)
9000 DATA "###...###"  (80 chars, but CX can reach 639)
```
**Result:** MID$ accesses beyond string length, garbage characters or errors

**Fix:** Ensure level data width ≥ (CX_MAX+320)/8 characters

**5. Camera boundaries wrong**
```basic
REM WRONG: No right boundary
2030 IF CX<0 THEN CX=0
```
**Result:** Camera scrolls past level end, showing undefined memory

**Fix:** Add max boundary: `IF CX>LEVEL_WIDTH-320 THEN CX=LEVEL_WIDTH-320`

Scrolls less often (every 16 pixels instead of 8). Bigger jumps, less frequent stutters. Which feels better?

**3. Add vertical scrolling**

```basic

```

Update camera vertically:
```basic
3005 CY=PY-100:IF CY<0 THEN CY=0:IF CY>100 THEN CY=100
```

Draw with Y offset:

Now the level scrolls vertically too! (But even slower with more redraws.)

Before line 3040, add:
```basic

```
This draws a static top row whilst the level scrolls. Simple parallax effect—background moves slower (or not at all) compared to foreground.

Add after line 3130:

## What You've Learnt

**Camera Systems:**
- Camera position determines viewport into larger world
- Camera follows player by centering them on screen
- Boundaries prevent showing beyond level edges
- Sprite positions must be relative to camera, not world

**Character-Based Scrolling:**
- BASIC scrolling moves in 8-pixel jumps (character width)
- Full screen redraw required when threshold reached
- Visible "pop" and performance hit during scrolling
- Smooth pixel scrolling requires VIC-II hardware access (assembly)

**Performance Reality:**
- Screen redraw costs ~100ms for 1000 POKEs
- Scrolling drops frame rate from ~25 fps to ~6 fps
- Playable but noticeably sluggish compared to assembly
- You've discovered BASIC's rendering performance wall

**Level Data:**
- Multi-screen levels stored as wide character arrays
- String arrays balance memory usage and readability
- Character offset calculation maps camera to level data
- Proper length checking prevents accessing beyond data bounds

Character-based scrolling in BASIC is functional but sluggish. Professional action games require assembly.

## Quick Reference

**Camera following:**
```basic
CX=PX-160                        REM Center player on screen
IF CX<0 THEN CX=0                REM Left boundary
IF CX>LEVEL_WIDTH-320 THEN CX=LEVEL_WIDTH-320  REM Right boundary
```

**Screen redraw with threshold:**
```basic
IF ABS(CX-LX)<8 THEN RETURN      REM Skip if moved < 8 pixels
LX=CX                            REM Update last position
OF=INT(CX/8)                     REM Character offset
FOR Y=0 TO 24:FOR X=0 TO 39
  LI=OF+X                        REM Level index
  C=ASC(MID$(LV$(Y),LI+1,1))     REM Get character
  POKE 1024+Y*40+X,C             REM Draw to screen
NEXT X:NEXT Y
```

**Sprite position relative to camera:**
```basic
SCREEN_X = WORLD_X - CAMERA_X + 24
POKE 53248,SCREEN_X
```

**Level width calculation:**
```
1 screen = 320 pixels = 40 characters
3 screens = 960 pixels = 120 characters
5 screens = 1600 pixels = 200 characters
```

|-----------|------|--------|

| Screen redraw | ~100ms | Severe |
| Sprite update | ~10ms | Minimal |
