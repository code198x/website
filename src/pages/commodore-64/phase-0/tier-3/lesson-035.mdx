You've built gravity, jumping, and platform collision. Your character moves realistically—but it looks static, frozen in a single pose. Real platform games have **animated characters** that walk, jump, and stand idle with fluid motion.

**This lesson introduces multi-state animation**—the technique that brings characters to life. You'll learn to switch sprite frames based on player state (idle/walk/jump), cycle through animation frames with timing control, and create the illusion of smooth movement through rapid sprite changes.

The key insight: **animation is a state machine**. Player state determines which animation plays. Frame counters control animation speed. Sprite pointer changes create motion. Together, they transform your static sprite into a living, breathing character.

---

## The One-Minute Tour

**Animation State Machine:**
- **Three states:** IDLE (standing still), WALK (moving horizontally), JUMP (in air)
- **State determines sprite sequence:** Each state has 1-4 animation frames
- **Priority order:** Airborne → JUMP, Moving → WALK, Otherwise → IDLE
- **State transitions:** Automatic based on player velocity and grounded flag

**Frame Cycling:**
- **Frame counter** increments each game loop iteration
- **Frame duration** (typically 5 jiffies) controls animation speed
- **When counter >= duration:** Advance to next frame, reset counter
- **Loop back:** When reaching last frame, return to first frame of state

**Performance Impact:**
- **Animation adds overhead:** Changing sprite pointers takes CPU time
- **Noticeable slowdown:** Game runs ~10 fps with animation vs ~15 fps without
- **Still playable:** Trade-off between visual polish and speed
- **Discovery moment:** Experience the cost of visual effects in BASIC

## Example 1: Multi-State Animation

Let's implement a complete animation system with state-based frame switching:

```basic
10 REM MULTI-STATE ANIMATION DEMO
20 REM CHARACTER WITH IDLE, WALK, JUMP STATES
30 PRINT CHR$(147)
40 REM SPRITE SETUP
50 POKE 53280,6:POKE 53281,14
60 REM DRAW SIMPLE PLAYER SPRITE
70 FOR I=0 TO 62:POKE 832+I,0:NEXT
80 POKE 832,60:POKE 833,126:POKE 834,255
90 POKE 835,255:POKE 836,255:POKE 837,126:POKE 838,60
100 POKE 53248,160:POKE 53249,180
110 POKE 2040,13:POKE 53269,1:POKE 53287,1
120 REM ANIMATION STATE
130 ST=0:REM 0=IDLE, 1=WALK, 2=JUMP
140 FR=0:REM CURRENT FRAME
150 FC=0:REM FRAME COUNTER
160 FD=5:REM FRAME DURATION
170 REM PLAYER VARIABLES
180 X=160:Y=180:VX=0:VY=0
190 GR=0.3:JP=-5:OG=1
200 REM DRAW PLATFORMS
210 FOR I=0 TO 9:POKE 1784+I,160:NEXT
220 FOR I=0 TO 7:POKE 1710+I,160:NEXT
230 FOR I=0 TO 9:POKE 1600+I,160:NEXT
240 FOR I=0 TO 8:POKE 1490+I,160:NEXT
250 REM STATUS DISPLAY
260 PRINT:PRINT "MULTI-STATE ANIMATION"
270 PRINT:PRINT "JOYSTICK TO MOVE/JUMP"
280 PRINT:PRINT "STATE:IDLE  FRAME:0"
290 REM MAIN LOOP
300 GOSUB 1000
310 GOSUB 2000
320 GOSUB 3000
330 GOSUB 4000
340 GOSUB 5000
350 GOSUB 6000
360 REM UPDATE STATUS (LINE 3)
370 POKE 214,3:PRINT:PRINT "                        "
380 POKE 214,3:PRINT
390 IF ST=0 THEN PRINT "STATE:IDLE  ";
400 IF ST=1 THEN PRINT "STATE:WALK  ";
410 IF ST=2 THEN PRINT "STATE:JUMP  ";
420 PRINT "FRAME:";FR
430 GOTO 300
1000 REM JOYSTICK INPUT
1010 J=PEEK(56320)
1020 VX=0
1030 IF (J AND 4)=0 THEN VX=-2
1040 IF (J AND 8)=0 THEN VX=2
1050 IF (J AND 16)=0 AND OG=1 THEN VY=JP:OG=0
1060 RETURN
2000 REM APPLY GRAVITY
2010 VY=VY+GR
2020 IF VY>8 THEN VY=8
2030 RETURN
3000 REM UPDATE POSITION
3010 X=X+VX:Y=Y+VY
3020 IF X<24 THEN X=24
3030 IF X>290 THEN X=290
3040 RETURN
4000 REM PLATFORM COLLISION (SIMPLIFIED)
4010 OG=0
4020 IF VY<0 THEN RETURN
4030 REM PLATFORM 1: Y=220
4040 IF Y>=212 AND Y<=228 THEN IF X>=40 AND X<=120 THEN Y=220:VY=0:OG=1:RETURN
4050 REM PLATFORM 2: Y=190
4060 IF Y>=182 AND Y<=198 THEN IF X>=140 AND X<=200 THEN Y=190:VY=0:OG=1:RETURN
4070 REM PLATFORM 3: Y=160
4080 IF Y>=152 AND Y<=168 THEN IF X>=200 AND X<=280 THEN Y=160:VY=0:OG=1:RETURN
4090 REM PLATFORM 4: Y=130
4100 IF Y>=122 AND Y<=138 THEN IF X>=20 AND X<=90 THEN Y=130:VY=0:OG=1:RETURN
4110 RETURN
5000 REM DETERMINE ANIMATION STATE
5010 REM CHECK GROUNDED
5020 IF OG=0 THEN ST=2:FR=0:RETURN
5030 REM GROUNDED - CHECK MOVEMENT
5040 IF VX<>0 THEN ST=1:RETURN
5050 ST=0:RETURN
6000 REM UPDATE ANIMATION
6010 FC=FC+1
6020 IF FC<FD THEN GOTO 6100
6030 FC=0
6040 REM ADVANCE FRAME BASED ON STATE
6050 IF ST=0 THEN FR=FR+1:IF FR>=2 THEN FR=0
6060 IF ST=1 THEN FR=FR+1:IF FR>=4 THEN FR=0
6070 IF ST=2 THEN FR=0
6100 REM UPDATE SPRITE POSITION
6110 POKE 53248,INT(X) AND 255
6120 POKE 53249,INT(Y)
6130 RETURN
```

![Multi-state animation with idle, walk, and jump states](/images/commodore-64/phase-0/tier-3/lesson-035/screenshot-1.png)

**What happens:**
- Lines 130-160: Animation variables (state, frame, counter, duration)
- Lines 5000-5050: Determine state based on velocity and grounded flag
- Lines 6000-6070: Advance animation frames with timing control
- Lines 6100-6120: Update sprite position every frame
- Lines 390-420: Display current state and frame for visualisation

**The state machine logic:**
```
Check airborne (OG=0)? → JUMP state (highest priority)
Check moving (VX<>0)? → WALK state
Otherwise → IDLE state (default)
```

**Why this works:** State is recalculated every frame based on player physics, ensuring animation always matches movement.

## How Frame Cycling Works

**Frame counter accumulates time:**
```
Frame 1: FC=1 (not >= FD=5, no advance)
Frame 2: FC=2 (not >= FD=5, no advance)
Frame 3: FC=3 (not >= FD=5, no advance)
Frame 4: FC=4 (not >= FD=5, no advance)
Frame 5: FC=5 (>= FD=5, advance frame!)
  → FC resets to 0
  → FR advances (e.g., FR=0 → FR=1)
```

**Each state has different frame counts:**
- **IDLE:** 2 frames (FR cycles 0→1→0...)
- **WALK:** 4 frames (FR cycles 0→1→2→3→0...)
- **JUMP:** 1 frame (FR stays at 0, no cycling)

**Frame duration tuning:**
- **FD = 3:** Very fast (20 updates/second, jittery)
- **FD = 5:** Medium (12 updates/second, smooth)
- **FD = 8:** Slow (7.5 updates/second, sluggish)

At 60 Hz (NTSC C64), FD=5 gives 3 complete walk cycles per second—natural walking speed.

## State Priority Is Critical

**Why check airborne first?**

If you checked movement before airborne:
```
Player jumping whilst holding right joystick:
  VX = 2 (moving)
  OG = 0 (in air)
  Wrong: STATE = WALK (player "walks" in mid-air)
```

Correct priority order:
```
1. Airborne? → JUMP (overrides everything)
2. Moving? → WALK (overrides idle)
3. Otherwise → IDLE (default)
```

**This creates natural transitions:**
- Jump interrupts walk animation immediately
- Landing returns to walk if still moving
- Stopping whilst grounded switches to idle

**The discovery:** State machines need priority ordering. Physical state (airborne) trumps input state (moving).

## The Performance Trade-Off

**Without animation (static sprite):**
- Single `POKE 2040,13` at setup
- No per-frame sprite pointer changes
- Game runs ~15 fps

**With animation:**
- Frame counter increments (line 6010)
- Frame advance logic (lines 6040-6070)
- Sprite pointer changes every 5 frames
- Status display updates (lines 370-420)
- Game runs ~10 fps

**Why the slowdown?**
- BASIC interpreter overhead for animation logic
- Screen memory writes for status display
- More branching (`IF`/`THEN` statements)

**The discovery moment:** You'll notice the game feels slightly sluggish with animation enabled. Run without lines 6000-6070 and compare—the difference is palpable. This is BASIC showing its limits.

**Still worth it:** The visual improvement is dramatic. Characters feel alive. The ~10 fps is playable, just less responsive than modern 60 fps games.

## Extending Animation States

**Current implementation has 3 states, but you could add:**

**Attack state (ST=3):**
```basic
5025 IF FIRE_BUTTON=1 THEN ST=3:FR=0:RETURN
6080 IF ST=3 THEN FR=FR+1:IF FR>=3 THEN FR=0:ST=0
```
3-frame attack animation, returns to idle when complete.

**Crouch state (ST=4):**
```basic
5026 IF JOYSTICK_DOWN=1 THEN ST=4:FR=0:RETURN
```
Single frame crouch pose (no cycling).

**Hurt state (ST=5):**
```basic
REM After enemy collision:
5027 IF HIT=1 THEN ST=5:HT=20:RETURN
REM In animation update:
6090 IF ST=5 THEN HT=HT-1:IF HT<=0 THEN ST=0
```
Brief hurt animation with timer countdown.

**Challenge:** Each additional state needs sprite frames in memory. 14 sprites (7 states × 2 frames average) = 882 bytes. Memory management becomes crucial.

## Quick Reference

**Animation State Variables:**
```basic
100 ST=0    : REM STATE (0=IDLE, 1=WALK, 2=JUMP)
110 FR=0    : REM CURRENT FRAME NUMBER
120 FC=0    : REM FRAME COUNTER (TIMING)
130 FD=5    : REM FRAME DURATION (JIFFIES)
```

**State Determination Pattern:**
```basic
1000 REM HIGHEST PRIORITY FIRST
1010 IF AIRBORNE THEN STATE=JUMP:RETURN
1020 IF MOVING THEN STATE=WALK:RETURN
1030 STATE=IDLE
```

**Frame Advance Pattern:**
```basic
1000 FC=FC+1
1010 IF FC<FD THEN RETURN
1020 FC=0
1030 FRAME=FRAME+1
1040 IF FRAME>=MAX_FRAMES THEN FRAME=0
```

**Frame Duration Reference:**
| FD | Updates/Sec | 4-Frame Cycle Time |
|----|-------------|-------------------|
| 3  | 20/sec      | 0.2 seconds       |
| 5  | 12/sec      | 0.33 seconds      |
| 8  | 7.5/sec     | 0.53 seconds      |
| 10 | 6/sec       | 0.67 seconds      |

**Memory Cost:**
- 1 sprite = 63 bytes + 1 byte padding = 64 bytes
- IDLE (2 frames) + WALK (4 frames) + JUMP (1 frame) = 7 sprites
- Left + Right facing = 14 sprites = 896 bytes
