# Box Pusher: Sokoban Clone

Welcome to the **Puzzle Collection** arc! After mastering action platformers and turn-based RPGs, you're ready to explore BASIC's perfect domain: **pure logic puzzles**. Sokoban demonstrates that puzzle games require no graphics overhead—just clever algorithms and instant response times.

## What You're Building

**Box Pusher** is a Sokoban clone where you:
- Navigate an 8×8 grid with walls, boxes, and goals
- Push boxes (never pull) to target locations
- Complete levels by placing all boxes on goals
- Progress through 8 increasingly difficult levels
- Reset puzzles when you make mistakes

This ~100-line game proves that **logic puzzles are BASIC's sweet spot**—complex rules, unlimited levels, perfect response time, and zero graphics burden.

## Why Sokoban Works Perfectly in BASIC

**The reality:** Turn-based puzzle games have **no performance constraints**. Every move waits for player input, every rule is pure logic, and display updates happen instantly. No real-time graphics, no physics calculations, no timing issues.

**What you get:**
- Instant moves (no animation overhead)
- Complex logic (nested IF statements, grid scanning)
- Unlimited levels (just DATA statements)
- Perfect gameplay (every move is deliberate)

Sokoban is proof that **BASIC excels at what matters most**: making puzzles that feel amazing to solve.

## Understanding Sokoban Mechanics

### Tile Types

The grid uses numeric codes for each tile type:

```basic
10 REM TILE CODES:
20 REM 0 = EMPTY FLOOR
30 REM 1 = WALL (IMPASSABLE)
40 REM 2 = BOX (PUSHABLE)
50 REM 3 = GOAL (TARGET)
60 REM 4 = PLAYER
70 REM 5 = BOX ON GOAL (CORRECTLY PLACED)
```

Each tile displays as a different character:
- Space (` `) = Empty floor
- Block (`█` / CHR$(160)) = Wall
- `O` = Box on floor
- `.` = Empty goal
- `@` = Player
- `*` = Box correctly placed on goal

### The Push Rules

Sokoban has deceptively simple rules:

1. **Player pushes, never pulls** - You can only push boxes forward
2. **One box at a time** - Can't push two boxes together
3. **Boxes can't enter walls** - Blocked by walls and other boxes
4. **Player walks over goals** - Goals stay visible under the player
5. **Level complete** - All boxes must be on goals simultaneously

### Movement Validation Algorithm

Every move requires three checks:

```basic
3200 REM ATTEMPT MOVE
3210 NX=PX+DX:NY=PY+DY
3220 IF NX<1 OR NX>8 OR NY<1 OR NY>8 THEN RETURN
3230 TG=GR(NX,NY)
3240 IF TG=1 THEN RETURN
3250 IF TG=2 OR TG=5 THEN GOSUB 3400:IF PU=0 THEN RETURN
```

1. **Bounds check** - Ensure target is inside grid (lines 3220)
2. **Wall check** - Can't move into walls (line 3240)
3. **Box check** - If box present, validate box can also move (line 3250)

Only after all checks pass does the player actually move.

## Building the Grid System

### Defining the Grid

Use two arrays: one for the current level, one for all level data:

```basic
30 DIM GR(8,8):REM CURRENT GRID
40 DIM LV(2,8,8):REM 2 LEVELS
```

- `GR(X,Y)` = Current game state (changes as you play)
- `LV(LEVEL,X,Y)` = Original level data (reset source)

This separation lets you reset levels easily: just copy `LV` back into `GR`.

### Loading Level Data

Levels are stored as DATA statements:

```basic
9100 REM LEVEL 1 (TUTORIAL)
9110 DATA 1,1,1,1,1,1,1,1
9120 DATA 1,0,0,0,0,0,0,1
9130 DATA 1,0,0,0,3,0,0,1
9140 DATA 1,0,0,2,0,0,0,1
9150 DATA 1,0,0,4,0,0,0,1
9160 DATA 1,0,0,0,0,0,0,1
9170 DATA 1,0,0,0,0,0,0,1
9180 DATA 1,1,1,1,1,1,1,1
```

This creates a simple tutorial level:
```
########
#      #
#    . #
#   O  #
#   @  #
#      #
#      #
########
```

One box, one goal, trivial solution: push up once.

### Displaying the Grid

Loop through all tiles and print the appropriate character:

```basic
2050 FOR Y=1 TO 8
2060 FOR X=1 TO 8
2070 T=GR(X,Y)
2080 IF T=0 THEN PRINT " ";
2090 IF T=1 THEN PRINT CHR$(160);
2100 IF T=2 THEN PRINT "O";
2110 IF T=3 THEN PRINT ".";
2120 IF T=4 THEN PRINT "@";
2130 IF T=5 THEN PRINT "*";
2140 NEXT X
2150 PRINT ""
2160 NEXT Y
```

The semicolons (`;`) prevent spacing between characters, creating a solid grid.

## Implementing Push Mechanics

### Checking If Box Can Move

When the player pushes a box, validate the box's target location:

```basic
3400 REM CHECK PUSH BOX
3410 PU=0
3420 BX=NX+DX:BY=NY+DY
3430 IF BX<1 OR BX>8 OR BY<1 OR BY>8 THEN RETURN
3440 BT=GR(BX,BY)
3450 IF BT=1 OR BT=2 OR BT=5 THEN RETURN
3460 PU=1
```

1. Calculate box's new position (line 3420)
2. Check bounds (line 3430)
3. Check if blocked by wall or another box (line 3450)
4. Set `PU=1` flag if push is valid (line 3460)

Only when `PU=1` does the actual push happen.

### Moving the Box

The box movement must preserve goals underneath:

```basic
3470 REM MOVE BOX
3480 IF GR(NX,NY)=5 THEN BG=BG-1
3490 IF GR(NX,NY)=5 THEN GR(NX,NY)=3:GOTO 3520
3500 IF GR(NX,NY)=2 THEN GR(NX,NY)=0
3520 IF BT=3 THEN GR(BX,BY)=5:BG=BG+1:RETURN
3530 GR(BX,BY)=2
```

Key insights:
- **Leaving a goal** (line 3490): Box-on-goal (5) becomes empty goal (3)
- **Leaving floor** (line 3500): Box-on-floor (2) becomes empty floor (0)
- **Entering a goal** (line 3520): Set tile to 5 (box-on-goal), increment counter
- **Entering floor** (line 3530): Set tile to 2 (box-on-floor)

### Tracking Goal State

Use a counter to track how many boxes are correctly placed:

```basic
90 BG=0:REM BOXES ON GOALS
```

- Increment `BG` when pushing box onto goal
- Decrement `BG` when pushing box off goal
- Win condition: `BG = NG` (boxes on goals = total goals)

This avoids scanning the entire grid every frame.

## Win Conditions and Level Progression

### Checking for Victory

After every move, test if puzzle is solved:

```basic
4000 REM CHECK WIN
4010 WN=0
4020 IF BG=NG THEN WN=1
4030 RETURN
```

Simple: if all goals have boxes, the level is complete.

### Advancing to Next Level

When a level is won:

```basic
5000 REM NEXT LEVEL
5010 PRINT ""
5020 PRINT "LEVEL COMPLETE!"
5030 PRINT "MOVES: ";MV
5040 FOR I=1 TO 2000:NEXT I
5050 CL=CL+1
5060 IF CL>2 THEN GOSUB 5100:END
5070 GOSUB 1000
5080 RETURN
```

1. Display completion message with move count
2. Wait briefly (line 5040)
3. Increment level counter (line 5050)
4. Check if all levels complete (line 5060)
5. Otherwise, load next level (line 5070)

### Resetting Levels

Players often trap boxes in corners. Let them reset:

```basic
3070 IF K$="R" THEN GOSUB 1000:RETURN
```

The `GOSUB 1000` reloads the current level from `LV` array, resetting all positions.

## Example 1: Two-Level Tutorial

Let's build a minimal Sokoban with two tutorial levels:

```basic
10 REM SOKOBAN CLONE
20 REM GRID-BASED PUZZLE GAME
30 DIM GR(8,8):REM CURRENT GRID
40 DIM LV(2,8,8):REM 2 LEVELS
50 PX=0:PY=0:REM PLAYER POSITION
60 CL=1:REM CURRENT LEVEL
70 NB=0:REM NUMBER OF BOXES
80 NG=0:REM NUMBER OF GOALS
90 BG=0:REM BOXES ON GOALS
100 MV=0:REM MOVES COUNT
110 WN=0:REM WIN FLAG
120 GOSUB 9000:REM LOAD LEVELS
130 GOSUB 1000:REM START LEVEL
140 REM MAIN LOOP
150 GOSUB 2000:REM DISPLAY
160 GOSUB 3000:REM INPUT
170 GOSUB 4000:REM CHECK WIN
180 IF WN=1 THEN GOSUB 5000
190 GOTO 150
```

This sets up the core game loop: display → input → check win → repeat.

### Starting a Level

Loading a level requires copying data and finding initial positions:

```basic
1000 REM START LEVEL
1010 NB=0:NG=0:BG=0:MV=0:WN=0
1020 FOR Y=1 TO 8
1030 FOR X=1 TO 8
1040 GR(X,Y)=LV(CL,X,Y)
1050 IF GR(X,Y)=4 THEN PX=X:PY=Y
1060 IF GR(X,Y)=2 THEN NB=NB+1
1070 IF GR(X,Y)=3 OR GR(X,Y)=5 THEN NG=NG+1
1080 NEXT X:NEXT Y
1090 RETURN
```

This routine:
- Resets counters (line 1010)
- Copies level data into current grid (line 1040)
- Finds player starting position (line 1050)
- Counts boxes and goals (lines 1060-1070)

### Processing Input

Handle movement keys plus reset and quit:

```basic
3000 REM INPUT
3010 GET K$:IF K$="" THEN 3010
3020 DX=0:DY=0
3030 IF K$="I" THEN DY=-1
3040 IF K$="K" THEN DY=1
3050 IF K$="J" THEN DX=-1
3060 IF K$="L" THEN DX=1
3070 IF K$="R" THEN GOSUB 1000:RETURN
3080 IF K$="Q" THEN END
3090 IF DX=0 AND DY=0 THEN RETURN
3100 GOSUB 3200:REM ATTEMPT MOVE
3110 RETURN
```

Uses IJKL for direction (common in C64 games since those keys are centrally located and easy to reach).

**Try it:** Type in the code, run it, and try solving level 1. Push the box onto the goal with the `I` key (up). Notice how the box changes to `*` when correctly placed, and the counter updates to "BOXES: 1 / 1". Instantly, the game detects victory!

## Common Patterns and Pitfalls

### Pattern: Preserving Goals

**Problem:** When removing a box from a goal, the goal disappears.

**Solution:** Check tile type when removing box:

```basic
3490 IF GR(NX,NY)=5 THEN GR(NX,NY)=3:REM REVEAL GOAL
3500 IF GR(NX,NY)=2 THEN GR(NX,NY)=0:REM CLEAR FLOOR
```

Tile 5 (box-on-goal) must become tile 3 (empty goal), not 0 (floor).

### Pattern: Player on Goals

**Problem:** Player walks over goal and goal disappears.

**Solution:** Don't place player tile on goals:

```basic
3290 IF GR(PX,PY)=3 THEN GR(PX,PY)=4:MV=MV+1:RETURN
```

When player moves onto goal, set tile to 4 (player), but remember there's a goal underneath. When player leaves, restore it.

**Better approach:** Use separate player position variables (`PX`, `PY`) instead of storing player in grid. This avoids conflicts entirely.

### Pitfall: Pushing Two Boxes

**Problem:** Player pushes one box into another box.

**Solution:** Check target tile for other boxes:

```basic
3450 IF BT=1 OR BT=2 OR BT=5 THEN RETURN
```

This blocks pushes into walls (1), boxes on floor (2), and boxes on goals (5).

### Pitfall: Forgetting Bounds Checks

**Problem:** Player or box moves outside grid.

**Solution:** Always validate coordinates:

```basic
3220 IF NX<1 OR NX>8 OR NY<1 OR NY>8 THEN RETURN
3430 IF BX<1 OR BX>8 OR BY<1 OR BY>8 THEN RETURN
```

Check both player destination and box destination.

### Pitfall: Incorrect Win Detection

**Problem:** Game declares victory when only some boxes are on goals.

**Solution:** Compare boxes-on-goals count to total goals:

```basic
4020 IF BG=NG THEN WN=1
```

Only when `BG` (boxes on goals) equals `NG` (number of goals) is puzzle solved.

## Extension Ideas

### Undo Move System

Track move history in an array:

```basic
10 DIM MH(100,5):REM MOVE HISTORY (UP TO 100 MOVES)
```

Each entry stores: player X/Y, box X/Y, box moved flag. Press `U` to restore previous state.

### Optimal Solution Counter

Store minimum moves for each level:

```basic
10 DIM OP(8):REM OPTIMAL MOVES FOR EACH LEVEL
20 OP(1)=1:OP(2)=6:OP(3)=12:REM ETC.
```

After completing level, compare player's moves to optimal. Display "OPTIMAL!" if matched.

### Level Editor

Let players design custom puzzles:

```basic
1000 REM LEVEL EDITOR
1010 CX=4:CY=4:REM CURSOR POSITION
1020 GOSUB 1100:REM DISPLAY GRID
1030 GET K$:IF K$="" THEN 1030
1040 REM IJKL TO MOVE CURSOR
1050 REM 0-5 TO PLACE TILES
```

Save created levels to disk for sharing.

### Larger Grids

Expand to 12×12 or 16×16 grids for more complex puzzles:

```basic
30 DIM GR(16,16)
```

Requires scrolling viewport or smaller character set.

**Display Characters:**
```

```

**Grid Operations:**
```basic
DIM GR(8,8)              :REM CURRENT GRID
GR(X,Y)=TILE_TYPE        :REM SET TILE

```

**Movement Validation:**
```basic
NX=PX+DX:NY=PY+DY                        :REM NEW POSITION
IF NX<1 OR NX>8 THEN RETURN              :REM BOUNDS CHECK
IF GR(NX,NY)=1 THEN RETURN               :REM WALL CHECK
IF GR(NX,NY)=2 OR GR(NX,NY)=5 THEN ...   :REM BOX CHECK
```

**Win Condition:**
```basic
IF BOXES_ON_GOALS=TOTAL_GOALS THEN WIN
```

**Level Reset:**
```basic
FOR Y=1 TO 8:FOR X=1 TO 8
  GR(X,Y)=LV(CURRENT_LEVEL,X,Y)
NEXT X:NEXT Y
```
