# Creating Visual Depth

Your sprites can move smoothly and animate beautifully, but they always appear **in front** of everything on screen. Real games create depth by making characters walk behind scenery—think of Rockford passing behind rocks in *Boulder Dash*, or the ninja moving behind bamboo in *The Last Ninja*.

The VIC-II's sprite priority system lets you control whether each sprite appears in front of or behind the screen's background graphics. This single register unlocks convincing depth effects that make your games feel layered and three-dimensional.

---

## The One-Minute Tour

**Priority Fundamentals:**
- **Register $D01B** (53275) controls all 8 sprites' priority
- **Bit = 0**: Sprite in front of background (default)
- **Bit = 1**: Sprite behind background colours 1-15
- **Sprites always in front of** background colour 0 (border/empty space)
- **Individual control**: Each sprite has its own priority bit

**Visual Rules:**
- Sprites with priority=1 appear behind any non-zero screen character
- Screen colour 0 (black/border) is always behind everything
- Sprite-to-sprite priority is determined by sprite number (0 = front, 7 = back)
- Priority only affects sprite-to-background, not sprite-to-sprite

**Common Uses:**
- Platform games: Walking behind platforms or pillars
- Adventure games: Passing behind furniture or walls
- Isometric games: Depth sorting for 3D-looking scenes
- Vertical games: Elevator shafts, tower interiors

## Example 1: Basic Priority Demonstration

Let's create a simple demo that shows the difference between foreground and background sprites:

```basic
10 PRINT CHR$(147):REM CLEAR SCREEN
20 REM DRAW SOME OBSTACLES ON SCREEN
30 FOR I=1 TO 5
40 POKE 1024+(I*40)+10,81:REM VERTICAL BARS
50 POKE 55296+(I*40)+10,5:REM GREEN COLOUR
60 NEXT
70 REM LOAD TWO SPRITES
80 FOR I=0 TO 62
90 READ B:POKE 832+I,B:REM SPRITE 0
100 NEXT
110 FOR I=0 TO 62
120 READ B:POKE 896+I,B:REM SPRITE 1
130 NEXT
140 REM SETUP SPRITE 0 (FOREGROUND)
150 POKE 2040,13:REM SPRITE DATA
160 POKE 53269,3:REM ENABLE SPRITES 0 AND 1
170 POKE 53287,7:REM SPRITE 0 = YELLOW
180 POKE 53248,100:POKE 53249,80:REM POSITION
190 REM SETUP SPRITE 1 (BACKGROUND)
200 POKE 2041,14:REM SPRITE DATA
210 POKE 53288,3:REM SPRITE 1 = CYAN
220 POKE 53250,100:POKE 53251,140:REM POSITION
230 POKE 53275,2:REM PRIORITY: SPRITE 1 BEHIND (BIT 1=1)
240 REM MOVE BOTH SPRITES
250 X0=PEEK(53248):X1=PEEK(53250)
260 X0=X0+1:X1=X1+1
270 IF X0>200 THEN X0=50
280 IF X1>200 THEN X1=50
290 POKE 53248,X0:POKE 53250,X1
300 FOR D=1 TO 50:NEXT:REM DELAY
310 GOTO 250
320 REM SPRITE DATA (SIMPLE CIRCLE)
330 DATA 0,126,0,1,255,128,3,255,192
340 DATA 7,255,224,7,255,224,15,255,240
350 DATA 15,255,240,15,255,240,15,255,240
360 DATA 7,255,224,7,255,224,3,255,192
370 DATA 1,255,128,0,126,0,0,0,0
380 DATA 0,0,0,0,0,0,0,0,0
390 DATA 0,0,0,0,0,0,0,0,0
400 REM SECOND SPRITE (SAME DATA)
410 DATA 0,126,0,1,255,128,3,255,192
420 DATA 7,255,224,7,255,224,15,255,240
430 DATA 15,255,240,15,255,240,15,255,240
440 DATA 7,255,224,7,255,224,3,255,192
450 DATA 1,255,128,0,126,0,0,0,0
460 DATA 0,0,0,0,0,0,0,0,0
470 DATA 0,0,0,0,0,0,0,0,0
```

![Basic priority demonstration showing foreground and background sprites](/images/commodore-64/phase-0/tier-3/lesson-034/example-1-screenshot.png)

**What's Happening:**
- Lines 30-60: Draw 15 green vertical bars on screen (full height)
- Lines 150-180: Setup sprite 0 (yellow) as normal foreground sprite
- Lines 200-220: Setup sprite 1 (cyan) at different Y position
- Line 230: **POKE 53275,2** sets bit 1 = sprite 1 goes behind screen graphics
- Lines 250-310: Both sprites move horizontally
- **Result**: Yellow sprite passes IN FRONT of bars, cyan sprite passes BEHIND them

`★ Insight ─────────────────────────────────────`
Register $D01B is a bitmask: bit 0 controls sprite 0, bit 1 controls sprite 1, etc. Value 2 = %00000010 = only sprite 1 is behind. Value 255 = %11111111 = all 8 sprites behind. Calculate with: value = 2^sprite_number (sprite 0 = 1, sprite 1 = 2, sprite 2 = 4, sprite 3 = 8, etc).

## Example 2: Walking Behind Obstacles

Now let's create a more game-like scenario where a character can walk behind obstacles:

```basic
10 PRINT CHR$(147):REM CLEAR SCREEN
20 REM DRAW SCENERY
30 FOR Y=0 TO 4
40 FOR X=5 TO 7
50 POKE 1024+(Y*40)+X,160:REM SOLID BLOCK
60 POKE 55296+(Y*40)+X,13:REM LIGHT GREEN
70 NEXT:NEXT
80 FOR Y=0 TO 4
90 FOR X=15 TO 17
100 POKE 1024+(Y*40)+X,160:REM SOLID BLOCK
110 POKE 55296+(Y*40)+X,9:REM ORANGE
120 NEXT:NEXT
130 REM LOAD SPRITE
140 FOR I=0 TO 62
150 READ B:POKE 832+I,B
160 NEXT
170 REM SETUP SPRITE 0
180 POKE 2040,13:POKE 53269,1
190 POKE 53287,14:REM LIGHT BLUE
200 X=160:Y=100:REM CENTRE POSITION
210 POKE 53275,0:REM START IN FRONT
220 REM GAME LOOP
230 POKE 53248,X:POKE 53249,Y
240 REM READ JOYSTICK
250 J=15-PEEK(56320)AND15
260 IF J=8 THEN X=X-2:REM LEFT
270 IF J=4 THEN X=X+2:REM RIGHT
280 IF J=1 THEN Y=Y-2:REM UP
290 IF J=2 THEN Y=Y+2:REM DOWN
300 REM CHECK IF BEHIND OBSTACLES
310 REM OBSTACLE 1: X=160-224 (CHARS 5-7)
320 REM OBSTACLE 2: X=472-536 (CHARS 15-17)
330 IF X>140 AND X<200 THEN POKE 53275,1:GOTO 230
340 IF X>200 THEN POKE 53275,0
350 GOTO 230
360 REM SPRITE DATA (SIMPLE PERSON)
370 DATA 0,126,0,1,255,128,3,231,192
380 DATA 3,231,192,3,231,192,1,255,128
390 DATA 1,255,128,0,126,0,0,126,0
400 DATA 0,126,0,0,60,0,0,60,0
410 DATA 0,24,0,0,24,0,0,24,0
420 DATA 0,60,0,0,102,0,0,195,0
430 DATA 0,0,0,0,0,0,0,0,0
```

![Walking behind obstacles with dynamic priority switching](/images/commodore-64/phase-0/tier-3/lesson-034/example-2-screenshot.png)

**Key Concepts:**
- Lines 30-120: Draw two coloured obstacles (pillars)
- Line 210: Start with sprite in front (priority = 0)
- Lines 320-330: **Dynamic priority switching** based on X position
  - When X is between 140-200: sprite goes behind (POKE 53275,1)
  - When X is above 200: sprite comes back in front (POKE 53275,0)
- **Result**: Character can walk behind the first pillar

**Character Coordinate to Screen Position:**
- Screen characters are 8 pixels wide
- Character 5 is at X pixel ~160 (5 × 32 pixels per character column on sprite scale)
- Sprite X coordinates don't directly map to character positions
- Trial and error is needed to find exact trigger points

## Understanding Priority Bitmasks

The priority register uses one bit per sprite:

**Binary to Decimal Conversion:**
```
Bit:     76543210
Sprite:  76543210

00000001 = 1   → Sprite 0 behind
00000010 = 2   → Sprite 1 behind
00000100 = 4   → Sprite 2 behind
00001000 = 8   → Sprite 3 behind
00010000 = 16  → Sprite 4 behind
00100000 = 32  → Sprite 5 behind
01000000 = 64  → Sprite 6 behind
10000000 = 128 → Sprite 7 behind
```

**Combining Sprites:**
To put multiple sprites behind, **add the values**:
- Sprites 0 and 2 behind: 1 + 4 = 5
- Sprites 1, 3, and 5 behind: 2 + 8 + 32 = 42
- All sprites behind: 1+2+4+8+16+32+64+128 = 255

**BASIC Formula:**
```basic
VALUE = 2^SPRITE_NUMBER
```
Examples:
- Sprite 0: 2^0 = 1
- Sprite 3: 2^3 = 8
- Sprite 7: 2^7 = 128

## Technical Limitations

**Priority vs Screen Colour 0:**
- Sprites with priority=1 only go behind colours 1-15
- Screen colour 0 (border/background) is **always** behind sprites
- Cannot make sprites go behind the border or blank areas
- This is why most games use coloured backgrounds for depth areas

**Performance Considerations:**
- Checking sprite position every frame is slow in BASIC
- Use simple boundary checks (IF X>value THEN...)
- Avoid complex calculations like distance formulas
- Consider using fixed zones where priority switches

**Sprite-to-Sprite Priority:**
- $D01B only affects sprite-to-background
- Sprite-to-sprite priority is fixed: sprite 0 = front, sprite 7 = back
- Cannot make sprite 3 appear in front of sprite 1
- Plan your sprite allocation: important foreground objects = lower sprite numbers

## Quick Reference

### Priority Register

| Register | Decimal | Purpose | Values |
|----------|---------|---------|--------|
| $D01B | 53275 | Sprite priority | Bit 0-7 for sprites 0-7 |

**Bit Values:**
- 0 = Sprite in front of background (default)
- 1 = Sprite behind background colours 1-15

### Common Priority Values

| Value | Binary | Sprites Behind |
|-------|--------|----------------|
| 0 | 00000000 | None (all foreground) |
| 1 | 00000001 | Sprite 0 only |
| 2 | 00000010 | Sprite 1 only |
| 3 | 00000011 | Sprites 0 and 1 |
| 4 | 00000100 | Sprite 2 only |
| 128 | 10000000 | Sprite 7 only |
| 255 | 11111111 | All sprites |

### Calculating Priority Value

**For single sprite:**
```basic
VALUE = 2^SPRITE_NUMBER
POKE 53275,VALUE
```

**For multiple sprites (add values):**
```basic
VALUE = 0
IF SPRITE_0_BEHIND THEN VALUE = VALUE + 1
IF SPRITE_1_BEHIND THEN VALUE = VALUE + 2
IF SPRITE_2_BEHIND THEN VALUE = VALUE + 4
POKE 53275,VALUE
```

### Position-Based Priority Switching

```basic
100 REM CHECK SPRITE POSITION
110 X = PEEK(53248):REM GET SPRITE 0 X
120 REM BEHIND OBSTACLE AT X=160-200
130 IF X>=160 AND X<=200 THEN POKE 53275,1:GOTO 150
140 POKE 53275,0:REM IN FRONT
150 REM CONTINUE...
```

## What You've Learnt

- Register $D01B (53275) controls sprite-to-background priority for all 8 sprites
- Bit=0 means sprite in front (default), bit=1 means sprite behind background
- Priority only affects non-zero screen colours (colour 0 always behind sprites)
- Sprites always maintain fixed priority relative to each other (0=front, 7=back)
- Dynamic priority switching creates depth effects like walking behind obstacles
- Calculate priority values: single sprite = 2^n, multiple = add values together
- Commercial games use priority sparingly due to BASIC performance limits
- Position-based priority checks enable convincing layering in platform and adventure games
