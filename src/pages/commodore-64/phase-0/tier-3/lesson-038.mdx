Your platformer has gravity, scrolling, animation, and enemies. But there's no **objective**—no reason to explore, no reward for taking risks. Real platform games have **collectibles** that incentivise exploration and **goals** that structure progression.

**This lesson introduces collectibles and goal-based progression**—the items and objectives that give your game purpose. You'll learn to implement collectible gems for scoring, keys that unlock doors, health pickups for recovery, distance-based collision detection, inventory tracking, and win conditions.

The key insight: **Collectibles are just positions with collision checks**. Each item has world coordinates and a type. Every frame, check distance to player—if close enough, mark collected and apply effect (add score, give key, restore health). Goals work the same way, but check additional conditions (have key? door unlocked?) before triggering progression.

---

## The One-Minute Tour

**Collectible Types:**
- **Gems (Type 1):** Award points, encourage exploration, optional collection
- **Keys (Type 2):** Unlock doors, required for progression, consumed on use
- **Health (Type 3):** Restore HP, risk/reward placement, capped at maximum
- **Custom types:** Power-ups, weapons, extra lives (easy to extend)

**Item Management:**
- **Arrays for storage:** IX(), IY(), IT(), IC() store position, type, collected flag
- **World coordinates:** Items placed in level coordinate space (like enemies)
- **Collision radius:** Distance < 20 pixels triggers collection (forgiving)
- **Type-based effects:** ON IT(I) GOSUB routes to gem/key/health handlers

**Goal Objects:**
- **Locked door:** Requires key to unlock, blocks access to area
- **Exit point:** Touch to win level (only after door unlocked)
- **Win condition:** Distance check + prerequisite check → level complete
- **Lock-and-key pattern:** Classic adventure game progression

**Drawing on Scrolling Screen:**
- **World to screen conversion:** SCREEN_X = WORLD_X - CAMERA_X
- **Culling:** Only draw items visible in current camera view
- **Character codes:** Diamond (4), key (11), heart (3), door (85), exit (88)
- **Colour memory:** 54272 offset from screen address for colours

**What's Happening:**

1. **Item arrays** (lines 70-80): Four parallel arrays store X position, Y position, type, and collected flag for each item
2. **Load level data** (lines 1000-1120): Initialise 5 items with positions and types (1=gem, 2=key, 3=health)
3. **Player inventory** (line 120): Track score (SC), has key flag (KY), and health points (HP)
4. **Joystick input** (lines 2000-2150): Four-way movement with boundary checking
5. **Collision detection** (lines 3100-3180): Calculate distance to each uncollected item, mark collected if within 20 pixels
6. **Type-based effects** (line 3170): ON...GOSUB routes to appropriate handler based on item type
7. **Drawing with culling** (lines 4050-4090): Skip collected items, draw visible ones with character codes

**The key mechanics:**
- **Distance formula:** DS=SQR(DX²+DY²) gives true distance between points
- **Forgiving collision:** 20-pixel radius is larger than sprite, easy to collect
- **Permanent collection:** IC(I)=1 flag prevents re-collecting same item
- **Sound feedback:** Brief SID tone confirms collection (different durations per type)

## Collision Detection Methods

Three approaches to item collection, each with trade-offs:

### Method 1: Circle-Circle (Current)

```basic
DX=PX-IX:DY=PY-IY
DS=SQR(DX*DX+DY*DY)
IF DS<20 THEN [COLLECT]
```

**Pros:** Accurate, natural feeling collision
**Cons:** SQR() is slow (~2ms per call), expensive with many items
**Use when:** Few items (&lt;10), accuracy matters

### Method 2: Bounding Box

```basic
IF ABS(PX-IX)<16 AND ABS(PY-IY)<16 THEN [COLLECT]
```

**Pros:** 10× faster than circle-circle, no SQR()
**Cons:** Square collision (corner hits feel wrong)
**Use when:** Many items (10+), speed critical

### Method 3: Screen Cell

```basic
IF INT(PX/8)=INT(IX/8) AND INT(PY/8)=INT(IY/8) THEN [COLLECT]
```

**Pros:** 20× faster, perfect for tile-based games
**Cons:** 8×8 pixel granularity (imprecise), tile alignment required
**Use when:** Grid-based movement, maximum performance needed

**Recommendation:** Start with circle-circle (Example 1), optimise later if performance suffers.

## Drawing Items on Scrolling Screens

When your game has camera scrolling (L36), items must convert from world to screen coordinates:

```basic
1000 REM DRAW ITEMS
1010 FOR I=1 TO NI
1020 IF IC(I)=1 THEN NEXT I:RETURN
1030 REM WORLD TO SCREEN CONVERSION
1040 SX=IX(I)-CX:SY=IY(I)
1050 REM CULL OFF-SCREEN ITEMS
1060 IF SX<0 OR SX>320 THEN NEXT I:RETURN
1070 REM CALCULATE CHARACTER ADDRESS
1080 CH=1024+(SY/8)*40+(SX/8)
1090 REM DRAW ITEM
1100 ON IT(I) GOSUB [GEM],[KEY],[HEALTH]
1110 NEXT I
```

**Key points:**
- **Camera offset:** Subtract CX (camera X) from world X to get screen X
- **Culling:** Skip items outside 0-320 pixel range (huge performance gain)
- **Y unchanged:** If no vertical scrolling, Y coordinate stays in screen space
- **Character math:** Divide by 8 (character size), add to 1024 (screen start)

**With vertical scrolling:**
```basic
SX=IX(I)-CX:SY=IY(I)-CY
IF SX<0 OR SX>320 OR SY<0 OR SY>200 THEN RETURN
```

## Progression Pattern Examples

Different collectible patterns create different gameplay experiences:

### Pattern 1: Linear Lock-and-Key (Example 2)

```
Start → Find Key → Unlock Door → Find Exit → Win
```

**Design:** Single key, single door, mandatory progression
**Gameplay:** Forces exploration, clear objective
**Use for:** Tutorial levels, linear experiences

### Pattern 2: Optional Collection

```
Start → Collect Gems (optional) → Find Exit → Win
```

**Design:** Exit accessible immediately, gems add score
**Gameplay:** Speed-run friendly, risk/reward exploration
**Use for:** Time trials, competitive scoring

### Pattern 3: Multi-Key

```
Start → Key 1 → Door 1 → Key 2 → Door 2 → Exit
```

**Design:** Chain of locked areas, sequential progression
**Gameplay:** Longer levels, backtracking, Metroidvania-style
**Use for:** Adventure games, complex levels

### Pattern 4: Collection Threshold

```
Start → Collect 5/8 Gems → Door Unlocks → Exit
```

**Design:** Door unlocks after collecting N items
**Gameplay:** Forces partial exploration, clear progress tracking
**Use for:** Collect-a-thon games, educational levels

**Implementation:**
```basic
4000 REM CHECK DOOR
4010 IF DK=1 THEN RETURN:REM ALREADY UNLOCKED
4020 REM COUNT COLLECTED GEMS
4030 CG=0
4040 FOR I=1 TO NI
4050 IF IT(I)=1 AND IC(I)=1 THEN CG=CG+1
4060 NEXT I
4070 IF CG>=5 THEN DK=1:REM UNLOCK AT 5 GEMS
4080 RETURN
```

## Common Pitfalls

Watch out for these mistakes:

1. **Forgetting collected flag:** Items reappear every frame
   - **Fix:** Check IC(I)=1 before drawing (line 4060)

2. **Impossible item placement:** Items in walls or off-platform
   - **Fix:** Test all item positions, ensure reachable

3. **Key consumed without unlocking:** Wrong door distance or missing key check
   - **Fix:** Verify DK=1 and KY=0 happen together (line 4060)

4. **Items collected off-screen:** Distance check includes camera offset
   - **Fix:** Use world coordinates for collision, not screen coords

5. **Collision too strict:** Players miss items they clearly touched
   - **Fix:** Increase radius from 10 to 20 pixels (line 3140)

6. **No collection feedback:** Player doesn't know item collected
   - **Fix:** Add sound effect and score display update

7. **DX/DY variable collision:** DX used for door X and delta X
   - **Fix:** Use unique variable names (DX for door, D1 for delta)

## Performance Considerations

**With 8 items + 3 enemies + scrolling:**
- Item collision checks: ~5ms (8 items × 0.6ms per SQR)
- Enemy updates: ~10ms (from L37)
- Screen redraw: ~100ms (still dominant)
- **Total: ~115ms = 8.7 fps**

**Optimisations if needed:**

1. **Reduce collision checks:** Skip items far from player (Manhattan distance pre-filter)
   ```basic
   IF ABS(PX-IX(I))>50 THEN RETURN
   ```

2. **Square distance:** Avoid SQR() by comparing squared values
   ```basic
   DS=DX*DX+DY*DY
   IF DS<400 THEN [COLLECT]:REM 400 = 20²
   ```

3. **Limit item count:** 8-10 items per screen keeps performance good

4. **Defer non-visible:** Only check items near player or on-screen

**Reality:** Item collision is cheap compared to screen drawing. Don't optimise prematurely.
