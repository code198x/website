# When BASIC Isn't Fast Enough

You've mastered sprites: movement, animation, collision, expansion. But there's a fundamental hardware limitation you can't escape: the VIC-II only provides **eight sprites**. What if you need more?

Professional games like *Uridium*, *Paradroid*, and *Wizball* display dozens of sprites simultaneously. They use a technique called **sprite multiplexing**—reusing the same eight hardware sprites multiple times per frame. But this requires split-second timing that BASIC simply cannot provide.

This lesson is about attempting the impossible and understanding why assembly language exists.

---

## The One-Minute Tour

**The Problem:**
- VIC-II has only **8 hardware sprites**
- Many games need 10, 20, or 50+ objects on screen
- No way to add more sprite hardware

**The Solution:**
- **Sprite multiplexing**: Reuse sprites mid-screen
- As raster beam draws downward, reprogram sprites for lower positions
- Same 8 sprites appear multiple times per frame

**The Challenge:**
- Must update sprite registers BEFORE raster beam reaches them
- Raster beam moves at 63 microseconds per line (PAL)
- BASIC is too slow—you'll see flicker and glitches
- Assembly language can time this precisely

**What You'll Learn:**
- The concept works (you'll prove it)
- BASIC can't execute it smoothly (you'll see why)
- This is where assembly becomes essential

---

## Understanding Sprite Multiplexing

### The Concept

Imagine the VIC-II's raster beam as a horizontal line scanning downward from top to bottom, drawing the screen. It completes one frame in 1/50th of a second (PAL) or 1/60th (NTSC).

**Without multiplexing:**
- Sprite 0 positioned at Y=100 → displays on raster lines 100-120
- Sprite 0 stays there for entire frame
- Maximum 8 sprites total

**With multiplexing:**
- Sprite 0 at Y=50 → displays on raster lines 50-70
- Wait for raster beam to pass line 70
- **Reprogram sprite 0** to Y=150 → now displays on lines 150-170
- Same hardware sprite appears twice per frame!

### The Timing Challenge

The critical requirement: **You must set the new Y-coordinate BEFORE the raster beam reaches that position.**

If you're too slow:
- Sprite doesn't appear at all (missed the window)
- Or displays at wrong position (updated mid-draw)
- Visual glitches and flicker

**Raster timing facts:**
- PAL C64: 312 raster lines per frame, 50 frames/second
- Each raster line: ~63 microseconds
- To reposition sprite 0 from Y=70 to Y=150: You have about 80 raster lines = 5 milliseconds

**BASIC's problem:**
- `POKE 53248,X` takes hundreds of microseconds
- Reading raster position, comparing, branching: even slower
- Multiple sprites to reposition: impossible to fit in the timing window

## Example 1: Reading the Raster Line

Before attempting multiplexing, let's learn to read the raster position:

```basic
10 PRINT CHR$(147):REM CLEAR SCREEN
20 PRINT "RASTER LINE MONITOR"
30 PRINT "PRESS STOP TO EXIT"
40 PRINT
50 REM MAIN LOOP
60 R=PEEK(53266):REM READ RASTER LINE
70 PRINT CHR$(19);:REM HOME CURSOR
80 PRINT "CURRENT RASTER: ";R;"   "
90 GOTO 60
```

![Raster line monitor showing changing values](/images/commodore-64/phase-0/tier-3/lesson-036/example-1.png)

**What's Happening:**
- Register 53266 ($D012) contains current raster line (0-255)
- Value changes constantly as beam scans downward
- By the time BASIC reads, compares, and branches, many lines have passed

**The Reality:**
In assembly language, you can wait for a specific raster line and execute code within microseconds. In BASIC, by the time you've checked the raster position, it's moved on.

## Example 2: Simple Multiplexing Attempt (4 Virtual Sprites)

Let's try multiplexing sprite 0 to appear as 4 separate sprites:

```basic
10 PRINT CHR$(147):REM CLEAR SCREEN
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM SETUP SPRITE 0
70 POKE 2040,13
80 POKE 53287,14:REM YELLOW
90 POKE 53269,1:REM ENABLE SPRITE 0
100 X=100:REM FIXED X POSITION
110 PRINT "ATTEMPTING 4 SPRITES"
120 PRINT "WATCH FOR FLICKER..."
130 REM MAIN LOOP - TRY TO MULTIPLEX
140 REM POSITION 1
150 POKE 53248,X:POKE 53249,60
160 REM WAIT FOR RASTER TO PASS
170 FOR W=1 TO 5:NEXT W
180 REM POSITION 2
190 POKE 53248,X:POKE 53249,100
200 FOR W=1 TO 5:NEXT W
210 REM POSITION 3
220 POKE 53248,X:POKE 53249,140
230 FOR W=1 TO 5:NEXT W
240 REM POSITION 4
250 POKE 53248,X:POKE 53249,180
260 FOR W=1 TO 5:NEXT W
270 GOTO 140
280 REM SPRITE DATA
290 DATA 0,126,0,1,255,128,3,255,192
300 DATA 7,255,224,15,255,240,31,255,248
310 DATA 31,255,248,63,255,252,63,255,252
320 DATA 63,255,252,63,255,252,63,255,252
330 DATA 31,255,248,31,255,248,15,255,240
340 DATA 7,255,224,3,255,192,1,255,128
350 DATA 0,126,0,0,0,0,0,0,0
```

![Flickering multiplexed sprites showing BASIC's timing problem](/images/commodore-64/phase-0/tier-3/lesson-036/example-2.png)

**What You See:**
- Flicker and instability
- Sprites appearing/disappearing
- Positions not consistent frame-to-frame
- Some frames show 2-3 sprites, rarely 4

**Why It Fails:**
- BASIC loop takes ~20-30 raster lines to execute
- By the time position 2 is set, raster has already passed
- Timing varies based on what else the system is doing
- No synchronization with vertical blank

## Example 3: Raster-Synchronized Attempt

Let's try to improve by waiting for specific raster lines:

```basic
10 PRINT CHR$(147):REM CLEAR SCREEN
20 REM LOAD SPRITE DATA
30 FOR I=0 TO 62
40 READ B:POKE 832+I,B
50 NEXT
60 REM SETUP SPRITE 0
70 POKE 2040,13
80 POKE 53287,2:REM RED
90 POKE 53269,1
100 X=120
110 PRINT "RASTER-SYNCHRONIZED"
120 PRINT "STILL FLICKERS..."
130 REM MAIN LOOP
140 REM WAIT FOR RASTER &lt;50 (TOP OF SCREEN)
150 IF PEEK(53266)>50 THEN 150
160 REM POSITION 1 (Y=60)
170 POKE 53248,X:POKE 53249,60
180 REM WAIT FOR RASTER > 80
190 IF PEEK(53266)&lt;80 THEN 190
200 REM POSITION 2 (Y=110)
210 POKE 53248,X:POKE 53249,110
220 REM WAIT FOR RASTER > 130
230 IF PEEK(53266)&lt;130 THEN 230
240 REM POSITION 3 (Y=160)
250 POKE 53248,X:POKE 53249,160
260 GOTO 140
270 REM SPRITE DATA
280 DATA 0,126,0,1,255,128,3,255,192
290 DATA 7,255,224,15,255,240,31,255,248
300 DATA 31,255,248,63,255,252,63,255,252
310 DATA 63,255,252,63,255,252,63,255,252
320 DATA 31,255,248,31,255,248,15,255,240
330 DATA 7,255,224,3,255,192,1,255,128
340 DATA 0,126,0,0,0,0,0,0,0
```

![Slightly better but still flickering sprites](/images/commodore-64/phase-0/tier-3/lesson-036/example-3.png)

**Improvement:**
- Sprites appear more consistently
- Better vertical positioning

**Still Problematic:**
- Noticeable flicker between frames
- IF...THEN checks take too long
- By the time POKE executes, timing window might be missed
- Can't handle moving sprites reliably

## Why Assembly Language Solves This

Assembly language multiplexing uses **raster interrupts**—hardware-triggered events that execute code at exact raster lines with microsecond precision.

**Assembly approach:**
1. Set interrupt to trigger at raster line 70
2. Hardware automatically calls your code when beam reaches line 70
3. Code executes in ~50 CPU cycles (~50 microseconds)
4. Sprite repositioned before beam reaches new position
5. Set next interrupt for line 120, repeat

**BASIC's limitations:**
- No direct interrupt control from BASIC
- Polling PEEK(53266) is too slow and unreliable
- Each POKE statement: hundreds of cycles
- Loop overhead, IF checks: more wasted time

**The fundamental problem:**
BASIC is an **interpreted language**. Every line is parsed, tokens looked up, and executed. Assembly code runs directly on the CPU—no interpreter overhead.

## Game Context: Professional Multiplexing

Games that used sprite multiplexing brilliantly:

**Uridium (1986) - Andrew Braybrook:**
- 20+ enemy ships on screen simultaneously
- Smooth scrolling with zero flicker
- Assembly-coded multiplexer sorted sprites by Y-position
- Raster interrupts repositioned sprites mid-frame

**Paradroid (1985) - Andrew Braybrook:**
- Multiple robots, bullets, explosions
- Perfect multiplexing made action feel fast-paced

**Wizball (1987) - Sensible Software:**
- Dozens of collectables, enemies, and effects
- Multicolour multiplexed sprites

**Green Beret (1986) - Imagine Software:**
- Famous for having many soldiers on screen
- Advanced multiplexer with sprite sorting

All these games were coded entirely in 6510 assembly language. BASIC couldn't come close to their sprite counts.

## What You've Learnt

- Sprite multiplexing reuses 8 hardware sprites to display many virtual sprites
- Requires repositioning sprites BEFORE raster beam reaches new Y-coordinate
- Raster beam timing: ~63 microseconds per line, ~20 milliseconds per frame
- BASIC is too slow—loops, IF checks, and POKEs miss timing windows
- Result: flicker, glitches, inconsistent display
- Assembly language uses raster interrupts for microsecond-precise timing
- Professional games like *Uridium* used assembly multiplexers for 20+ sprites
- **This is BASIC's ceiling—assembly removes the interpreter bottleneck**

## The Honest Truth

You've just encountered BASIC's fundamental limitation: it's an interpreted language designed for ease of use, not real-time performance. Every POKE, PEEK, and IF statement is parsed and executed through layers of code.

**What you've proven:**
- The concept of multiplexing works (sprites can be repositioned)
- Your logic is correct (the code makes sense)
- BASIC simply cannot execute fast enough

**What assembly unlocks:**
- Raster interrupts triggered by hardware
- Code executing in CPU cycles, not milliseconds
- Precise timing for smooth multiplexing
- 20, 30, 50+ sprites with zero flicker

You've built impressive programs in BASIC—text adventures, sprite games, collision detection. But multiplexing reveals the wall. Assembly isn't "better" than BASIC; it's a different tool for different problems.
