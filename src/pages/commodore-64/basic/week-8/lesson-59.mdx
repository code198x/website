## Lesson 59 – When BASIC Breaks

No matter how careful you are, BASIC will eventually shout `?OUT OF DATA` or `?OUT OF MEMORY`. Professional coders caught those errors early, saved state, and displayed friendly messages. We’ll simulate the usual suspects—exhausted `DATA`, overflowing `DIM`, and controller glitches—and show how to soften the impact.

---

### The One-Minute Tour

- Wrap `READ` calls in a routine that checks for an `END` marker and displays a fallback.
- Track memory usage with `FRE(0)` and unload optional features when space gets tight.
- Use `ON ERROR GOTO` cautiously to capture faults, log context, then reset cleanly.

---

### Example Program

```basic
NEW
10 REM *** BREAKPOINT HANDLER ***
20 ON ERROR GOTO 900
30 GOSUB 100
40 GOSUB 200
50 GOSUB 300
60 PRINT "ALL TESTS COMPLETE"
70 END

100 REM *** DATA LOADER WITH SAFETY ***
110 PRINT "LOADING LEVEL DATA..."
120 RESTORE 1000
130 READ ID
140 IF ID=0 THEN PRINT "NO MORE LEVELS." : RETURN
150 READ NAME$:PRINT "LEVEL:";ID;NAME$
160 GOSUB 400
170 GOTO 130

200 REM *** MEMORY PRESSURE TEST ***
210 PRINT "ALLOCATING SPRITE BUFFERS..."
220 BYTES=3000
230 IF FRE(0)<BYTES THEN PRINT "MEMORY LOW - SKIPPING ANIMATION" : RETURN
240 DIM SPRITE$(BYTES)
250 PRINT "SPRITE BUFFER LOADED"
260 RETURN

300 REM *** CONTROLLER EDGE CASE ***
310 PRINT "READING JOYSTICK..."
320 V=PEEK(56320)
330 IF V=255 THEN PRINT "NO JOYSTICK DETECTED" : RETURN
340 PRINT "JOYSTICK VALUE:";V
350 RETURN

400 REM *** SAFE DATA READ ***
410 FOR I=1 TO 3
420 READ TOKEN$
430 IF TOKEN$="END" THEN PRINT "WARN: LEVEL DATA SHORT" : RETURN
440 PRINT "  TOKEN:";TOKEN$
450 NEXT I
460 RETURN

900 REM *** ERROR HANDLER ***
910 PRINT CHR$(147);"
*** BASIC CAUGHT AN ERROR ***"
920 PRINT "ERR";ERR;" AT LINE";ERL
930 PRINT "FRE:";FRE(0)
940 RESUME NEXT

1000 DATA 1,"CAVERN",KEY,SWORD,GEM
1010 DATA 2,"MINE",CART,LAMP,END
1020 DATA 0,"END"
```

Sample output:

```
LOADING LEVEL DATA...
LEVEL: 1 CAVERN
  TOKEN: KEY
  TOKEN: SWORD
  TOKEN: GEM
LEVEL: 2 MINE
WARN: LEVEL DATA SHORT
NO MORE LEVELS.
ALLOCATING SPRITE BUFFERS...
SPRITE BUFFER LOADED
READING JOYSTICK...
NO JOYSTICK DETECTED
ALL TESTS COMPLETE
```

The loader checks for `TOKEN$="END"` so an incomplete `DATA` block becomes a warning, not a crash. The memory test queries `FRE(0)` and skips optional buffers instead of failing. The joystick reader spots the `255` pattern that indicates no stick is present. If anything still slips through, the error handler logs `ERR`, `ERL`, and remaining memory so you can reproduce the bug.

> **Tip:** Keep the handler short—log crucial info, then `RESUME NEXT` or `END`. Complex logic inside the handler risks triggering another error.

---

### Experiment Section

- Force `ERR=4` (`?OUT OF DATA`) by commenting out the `END` marker and see the handler’s output.
- Lower `BYTES` to 0 and let the buffer allocate; note how timing changes.
- Replace the joystick check with keyboard polling to ensure fallbacks work on platforms without sticks.
- Log state to disk by adding `OPEN 1,8,2,"crashlog,s,w"` in the handler and `PRINT#` the details.

### Concept Expansion

Crashes are inevitable. By planning fallback code, you keep playtesters in the game long enough to send useful bug reports. BASIC lacks structured exceptions, but a small handler plus sane checks avoids the dreaded READY prompt mid-demo.

---

### Game Integration

Wrap risky `READ`s:

```basic
READ TOKEN$:IF TOKEN$="END" THEN GOTO SAFE_EXIT
```

Short-circuit optional features when `FRE(0)` dips below a threshold. Your future self will thank you.

### What You’ve Learnt

- Defensive coding keeps BASIC from dropping to READY in front of your players.
- Checking memory and controller state lets you adapt gracefully to missing hardware.
- A compact error handler logs enough detail to fix the bug without spiralling into new errors.
