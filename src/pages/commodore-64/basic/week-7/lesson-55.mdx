## Lesson 55 – Optimising for Speed

BASIC can feel sluggish, but smart choices double performance. We’ll measure a naïve drawing loop, apply three optimisations, and compare the timings using the system clock. These same tricks keep Cosmic Clash’s action snappy.

> [📷 suggested: timing output showing slow vs fast durations]

---

### The One-Minute Tour

- Use `TI` to time sections of code—no guesswork.
- Cache frequently accessed values in variables rather than repeatedly `PEEK`ing memory.
- Precompute address tables so tight loops only poke bytes, not multiply indexes on every iteration.

---

### Example Program

```basic
NEW
10 REM *** SPEED TEST ***
20 GOSUB 900
30 PRINT CHR$(147);"BASIC SPEED LAB"
40 PRINT "1 = Slow star draw"
50 PRINT "2 = Optimised star draw"
60 PRINT "3 = Compare both"
70 INPUT "CHOICE";C
80 IF C=1 THEN GOSUB 1000
90 IF C=2 THEN GOSUB 2000
100 IF C=3 THEN GOSUB 3000
110 IF C=4 OR C=0 THEN END
120 GOTO 30

900 REM *** PRECOMPUTE TABLE ***
910 DIM ADR(40*5-1)
920 N=0
930 FOR Y=0 TO 4
940 BASE=1024+Y*40
950 FOR X=0 TO 39
960 ADR(N)=BASE+X
970 N=N+1
980 NEXT X
990 NEXT Y
1000 RETURN

1000 REM *** SLOW LOOP ***
1010 PRINT CHR$(147);"SLOW VERSION"
1020 TI$="000000"
1030 FOR Y=0 TO 4
1040 FOR X=0 TO 39
1050 POKE 1024+Y*40+X,42
1060 NEXT X
1070 NEXT Y
1080 T=TI
1090 PRINT "TIME:";T;" JIFFIES"
1100 RETURN

2000 REM *** FAST LOOP ***
2010 PRINT CHR$(147);"OPTIMISED VERSION"
2020 TI$="000000"
2030 FOR I=0 TO 199
2040 POKE ADR(I),42
2050 NEXT I
2060 T=TI
2070 PRINT "TIME:";T;" JIFFIES"
2080 RETURN

3000 REM *** COMPARE BOTH ***
3010 PRINT CHR$(147)
3020 TI$="000000":GOSUB 1000:SLOW=TI
3030 TI$="000000":GOSUB 2000:FAST=TI
3040 PRINT
3050 PRINT "SLOW:";SLOW;"  FAST:";FAST
3060 PRINT "SPEED-UP:";INT(SLOW/FAST*10)/10;"x"
3070 RETURN
```

Sample output:

```
SLOW VERSION
TIME: 146 jiffies

OPTIMISED VERSION
TIME: 62 jiffies

SPEED-UP: 2.3x
```

The slow loop multiplies addresses every iteration: `1024 + Y*40 + X`. The optimised version precomputes the 200 addresses once (lines 930–990) and simply pokes them. On a stock C64 the speed doubles. The comparison routine shows the improvement in hard numbers so you can judge whether an optimisation is worth the effort.

> **Tip:** Keep timing code around while you tune. Once you trust the numbers, you can remove the printouts but leave the precomputed tables in your release build.

---

### Experiment Section

- Cache sprite register addresses in a table so multi-sprite updates skip multiplication every frame.
- Replace repeated `PEEK` calls with a variable—capture the value once, then reuse it (`C=PEEK(53280)`).
- Shorten variable names in hot loops; BASIC spends less time looking them up.
- Move complex math out of loops: compute `speedIncrease = 1/(level+2)` once, then reuse.

> [🎥 suggested: clip flicking between slow and fast modes]

---

### Concept Expansion

Optimisation is about moving work from “every frame” to “once”. Precompute, cache, shorten loops, unroll if needed. Combine this with Week 6’s balancing to keep action fast even as levels grow busier.

---

### Game Integration

Apply the pattern everywhere:

```basic
REM Precompute
FOR I=0 TO 7:SPRITEADR(I)=53248+I*2:NEXT

REM Use inside loop
POKE SPRITEADR(I),X
```

Use `TI` to measure the improvements before/after so you know what helped.
