## Memory Map

### Zero Page ($00-$FF)

Zero page is the most precious memory on the 6502—every access is one byte shorter and one cycle faster than absolute addressing.

```asm
; Current zero page allocation
frame_count      = $02          ; Animation timing
song_pos         = $03-$04      ; 16-bit song pointer
score_lo         = $05          ; Score low byte
score_hi         = $06          ; Score high byte
; ... continues to $4E
```

| Range | Purpose | Bytes |
|-------|---------|-------|
| $00-$01 | Reserved (6510 I/O) | 2 |
| $02-$2F | Game variables | 46 |
| $30-$3F | Visual effect state | 16 |
| $40-$4E | UI state (high scores, options, pause) | 15 |
| $4F-$FA | Available | 172 |
| $FB-$FE | Pointer workspace | 4 |
| $FF | Reserved | 1 |

We're using 77 of 254 available zero page bytes—29% utilisation.

### Main Memory

```
$0000-$00FF  Zero Page (CPU fast access)
$0100-$01FF  Stack
$0200-$03FF  System variables
$0400-$07FF  Screen memory (1KB)
$0800-$0FFF  BASIC program area (our code starts here)
$0801-????   SID Symphony code and data (~13KB)
$D000-$D3FF  VIC-II registers
$D400-$D7FF  SID registers
$DC00-$DCFF  CIA1 (keyboard, joystick)
$DD00-$DDFF  CIA2 (serial, interrupts)
```

## Game State Machine

The main loop dispatches to state-specific update routines:

```asm
main_loop:
            lda #$FF
wait_raster:
            cmp $D012
            bne wait_raster         ; Sync to frame

            lda game_state
            cmp #STATE_TITLE
            beq do_title
            cmp #STATE_MENU
            beq do_menu
            cmp #STATE_PLAYING
            beq do_playing
            ; ... etc
```

| State | Value | Primary Routine |
|-------|-------|-----------------|
| STATE_TITLE | 0 | update_title |
| STATE_MENU | 1 | update_menu |
| STATE_PLAYING | 2 | update_playing |
| STATE_RESULTS | 3 | update_results |
| STATE_GAMEOVER | 4 | update_game_over |
| STATE_ATTRACT | 5 | update_attract |
| STATE_OPTIONS | 6 | update_options |

## Hot Path Analysis

The most frequently executed code runs every frame during gameplay:

1. **Raster sync** - Waiting for line 255
2. **Note updates** - Moving notes, checking positions
3. **Input polling** - Reading joystick/keyboard
4. **Display updates** - Score, combo, health bars
5. **Audio updates** - SID register writes

These are prime candidates for optimisation in Unit 51.

## Code Organisation Patterns

### Naming Conventions

```asm
; Routines: verb_noun
update_playing      ; State update
display_score       ; Display routine
check_note_hit      ; Logic check
play_menu_move      ; Audio playback

; Variables: noun or noun_modifier
score_lo            ; Low byte of score
perfect_count       ; Counter
game_paused         ; Boolean flag

; Constants: UPPER_CASE
STATE_PLAYING       ; State constant
SID_VOLUME          ; Hardware register
```

### Label Scoping

Local labels use unique prefixes to avoid conflicts:

```asm
update_paused:
            ; ...
up_pause_up:        ; 'up_' prefix for update_paused
            ; ...
up_pause_down:
            ; ...

draw_pause_cursor:
            ; ...
dpc_not_0:          ; 'dpc_' prefix for draw_pause_cursor
            ; ...
```

## Optimisation Opportunities

### Memory

| Area | Current | Potential Saving |
|------|---------|------------------|
| Duplicate constants | Multiple definitions | ~50 bytes |
| Text strings | Separate null-terminated | Use length-prefixed |
| Song data | Uncompressed | Run-length encoding |

### CPU

| Area | Current | Potential Improvement |
|------|---------|----------------------|
| Raster sync | Busy wait | Interrupt-driven |
| Note movement | Individual updates | Batch processing |
| Score display | Full redraw | Dirty flag updates |

### Code Size

| Technique | Potential Saving |
|-----------|------------------|
| Subroutine extraction | ~200 bytes |
| Macro usage | ~100 bytes |
| Data table optimisation | ~300 bytes |

## Technical Debt

Areas that would benefit from refactoring:

1. **Magic numbers** - Some hardcoded values should be constants
2. **Long routines** - Some update routines exceed 100 lines
3. **Duplicate code** - Similar patterns in menu navigation
4. **Comment gaps** - Some complex sections lack explanation
