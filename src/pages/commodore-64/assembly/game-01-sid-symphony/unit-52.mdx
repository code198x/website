The VIC-II video chip draws the screen line by line, 50 times per second. Understanding this process—and synchronising with it—is fundamental to flicker-free graphics. This unit explains raster timing and documents our synchronisation approach.


## How the VIC-II Draws

The VIC-II draws the screen like an old CRT television—one line at a time, top to bottom:

```
Line 0    ┌────────────────────────┐
          │     Top Border         │
Line 50   ├────────────────────────┤
          │                        │
          │    Visible Screen      │
          │      (200 lines)       │
          │                        │
Line 250  ├────────────────────────┤
          │    Bottom Border       │
Line 311  └────────────────────────┘
          (Then back to line 0)
```

The current line being drawn is stored in `$D012`—the raster register.

## Why Timing Matters

If you update screen memory while the VIC-II is drawing that part of the screen, you get **tearing**—half the old frame, half the new.

```
Without sync:        With sync:
┌──────────┐         ┌──────────┐
│ Old frame│         │          │
├──────────┤ ← Tear  │New frame │
│ New frame│         │          │
└──────────┘         └──────────┘
```

The solution: wait until the VIC-II is drawing the border (where there's no character data), then do your updates.

## Our Synchronisation Point

We sync to line 255 (`$FF`):

```asm
main_loop:
            lda #$FF
wait_raster:
            cmp $D012               ; Compare with current raster line
            bne wait_raster         ; Loop until we hit line 255
```

Why line 255?

| Reason | Explanation |
|--------|-------------|
| In bottom border | No visible content being drawn |
| After all character rows | All screen updates are "committed" |
| Maximum safe time | ~60 lines until visible area starts again |

## The Vertical Blank Period

After line 311, the beam returns to line 0. This "vertical blank" is prime time for updates:

```
Lines 251-311:  Bottom border (~60 lines)
Lines 0-50:     Top border (~50 lines)
Total:          ~110 lines = ~7,000 cycles of safe update time
```

Our entire game logic uses only ~3,000 cycles—well within the safe period.

## Polling vs Interrupts

There are two ways to synchronise with the raster:

### Polling (Our Approach)

```asm
wait_raster:
            cmp $D012
            bne wait_raster     ; Burn cycles waiting
```

**Advantages:**
- Simple to understand
- No complex interrupt setup
- Predictable behaviour

**Disadvantages:**
- CPU does nothing useful while waiting
- Can't do background tasks

### Raster Interrupts

```asm
            ; Set up IRQ to fire at line 255
            lda #$FF
            sta $D012
            lda #<irq_handler
            sta $0314
            ; ... more setup ...
```

**Advantages:**
- CPU free during wait period
- Can do multiple effects per frame
- Essential for advanced demos

**Disadvantages:**
- Complex setup
- Timing-sensitive code
- Harder to debug

## When to Use Each

| Scenario | Recommendation |
|----------|----------------|
| Simple games (like ours) | Polling |
| Multiple raster effects | Interrupts |
| Music players | Interrupts |
| Demo effects | Interrupts |
| Learning | Start with polling |

Our game uses only 16% of the frame budget. Polling is perfect—adding interrupt complexity would gain nothing.

## Double Buffering (Concept)

For games with complex graphics updates, double buffering prevents tearing:

```
Buffer A (visible) ──┐
                     ├── Swap each frame
Buffer B (drawing) ──┘
```

1. VIC-II displays Buffer A
2. Game updates Buffer B
3. At vertical blank, swap pointers
4. Now VIC-II displays Buffer B, game updates Buffer A

We don't need this—our character-based graphics update fast enough within the vertical blank.

## Measuring Timing

To see how much time your code takes:

```asm
main_loop:
            lda #2              ; Red
            sta $D020           ; Border colour

            jsr game_update     ; Your code here

            lda #0              ; Black
            sta $D020

            jmp main_loop
```

The red stripe width shows CPU time. If it extends into the visible area, you're too slow.

## Our Timing Budget

```asm
; PAL screen layout:
; Lines 0-50:     Top border (not visible on most TVs)
; Lines 51-250:   Visible screen area (200 lines)
; Lines 251-311:  Bottom border and vertical blank
;
; We sync to line 255 ($FF) because:
; 1. It's in the bottom border - safe to update screen memory
; 2. All visible content has been drawn this frame
; 3. We have until line 50 next frame before visible drawing starts
```

With ~7,000 cycles of safe time and only ~3,000 cycles of work, we have comfortable headroom.
