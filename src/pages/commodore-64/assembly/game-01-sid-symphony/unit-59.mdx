## Visual Separation

Players need to instantly identify their information:

### Split Screen Approach
```
┌────────────────┬────────────────┐
│   PLAYER 1     │   PLAYER 2     │
│  Score: 1250   │  Score: 980    │
│  Combo: 15x    │  Combo: 8x     │
│  ████████░░    │  ██████░░░░    │
├────────────────┴────────────────┤
│         SHARED PLAY AREA         │
│     ♪        ♪        ♪         │
│  [Z]      [X]      [C]          │
│  [1]      [2]      [3]          │
└─────────────────────────────────┘
```

Clear visual boundaries eliminate confusion.

### Colour Coding

Different colours for each player:

```asm
PLAYER1_COL = 5                 ; Green
PLAYER2_COL = 6                 ; Blue

; Draw P1 score in green
lda #PLAYER1_COL
sta COLRAM + (0 * 40) + 2       ; P1 area

; Draw P2 score in blue
lda #PLAYER2_COL
sta COLRAM + (0 * 40) + 22      ; P2 area
```

Consistent colour throughout reinforces identity.

## Winner Determination

At song end, declare a winner:

```asm
determine_winner:
            ; Compare scores
            lda score_hi
            cmp p2_score_hi
            bcc p2_wins
            bne p1_wins

            ; High bytes equal, compare low
            lda score_lo
            cmp p2_score_lo
            bcc p2_wins
            bne p1_wins

            ; Exact tie!
            jmp draw_tie

p1_wins:
            jsr draw_p1_wins
            rts

p2_wins:
            jsr draw_p2_wins
            rts
```

Ties should be handled gracefully—they're rare but happen.

## Victory Celebration

Make winning feel rewarding:

```asm
draw_winner:
            ; Flash winner's colour
            lda frame_count
            and #$08
            beq .flash_off
            lda #WINNER_COL         ; Bright colour
            jmp .set_col
.flash_off:
            lda #NORMAL_COL
.set_col:
            sta COLRAM + winner_pos

            ; Play victory jingle
            jsr play_victory_jingle
            rts
```

Flashing colours and sound effects create excitement.

## Balance Considerations

Fair competition requires careful design:

| Issue | Solution |
|-------|----------|
| Note stealing | Both players hit same note? First wins or both score |
| Health parity | Same starting health, same damage |
| Position advantage | Mirror layout or random assignment |
| Skill mismatch | Handicap options (health multiplier) |

## Spectator Experience

Multiplayer games are often watched. Consider:

- **Clear score display** - Large, readable numbers
- **Lead indicator** - Show who's ahead
- **Dramatic moments** - Highlight close races
- **Final results** - Comprehensive comparison

```
┌─────────────────────────────────┐
│         RESULTS                 │
├────────────────┬────────────────┤
│   PLAYER 1     │   PLAYER 2     │
│   ★ WINNER ★   │                │
│   1250 pts     │   980 pts      │
│   89% accuracy │   76% accuracy │
│   Max 25x      │   Max 12x      │
└────────────────┴────────────────┘
```

## Input Priority

When both players press simultaneously:

```asm
; Process P1 first, then P2
            jsr check_keys          ; Player 1
            lda two_player_mode
            beq .done
            jsr check_p2_keys       ; Player 2
.done:
```

This creates slight P1 advantage. True fairness would randomise order.

## Memory Efficiency

Two players double most state:

| Single | Two-Player |
|--------|------------|
| 8 bytes | 16 bytes |

Still tiny on a C64 with 64KB. The complexity is in code, not data.
