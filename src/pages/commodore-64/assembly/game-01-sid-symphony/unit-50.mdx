Memory optimisation on the 6502 means one thing above all: zero page. This unit moves frequently-accessed workspace variables to zero page, adds shared temporary storage, and documents the resulting memory layout.


## Why Zero Page Matters

The 6502 treats zero page ($00-$FF) specially:

| Addressing Mode | Bytes | Cycles | Example |
|----------------|-------|--------|---------|
| Absolute | 3 | 4 | `LDA $0300` |
| Zero Page | 2 | 3 | `LDA $50` |

Every zero page access saves one byte and one cycle. In tight loops running thousands of times per second, this adds up.

## The Optimisation

### Before (Unit 49)

```asm
; Workspace variables stored in main memory
work_lo:    !byte 0     ; At $1ABC (example address)
work_hi:    !byte 0     ; At $1ABD
```

Every access to these variables used 3-byte absolute addressing:
```asm
            lda work_lo         ; 3 bytes, 4 cycles
            sta work_hi         ; 3 bytes, 4 cycles
```

### After (Unit 50)

```asm
; Workspace variables in zero page
work_lo          = $53          ; Zero page address
work_hi          = $54          ; Zero page address
```

Now every access uses 2-byte zero page addressing:
```asm
            lda work_lo         ; 2 bytes, 3 cycles
            sta work_hi         ; 2 bytes, 3 cycles
```

## Shared Temporary Workspace

We also added general-purpose temporaries that any routine can use:

```asm
; Unit 50: Shared Temporary Workspace
temp_a           = $50          ; General purpose temp A
temp_b           = $51          ; General purpose temp B
temp_c           = $52          ; General purpose temp C
work_lo          = $53          ; 16-bit workspace low byte
work_hi          = $54          ; 16-bit workspace high byte
```

### Usage Rules

These temporaries follow a simple contract:

1. **Leaf routines only** - Only use in routines that don't call other routines
2. **No persistence** - Values don't survive across JSR calls
3. **Document usage** - Comment which temps a routine uses

```asm
; Example: Uses temp_a, temp_b
my_routine:
            lda some_value
            sta temp_a          ; Save for later
            ; ... do work ...
            lda temp_a          ; Retrieve
            rts
```

## Measuring the Impact

### Code Size

| Metric | Before | After | Savings |
|--------|--------|-------|---------|
| Data storage | 2 bytes | 0 bytes | 2 bytes |
| Access instructions | 3 bytes each | 2 bytes each | ~30 bytes total |

### Execution Speed

The `work_lo`/`work_hi` variables are accessed approximately 50 times during a typical game loop. Each access saves 1 cycle:

| Per frame | Before | After | Savings |
|-----------|--------|-------|---------|
| Cycles | 200 | 150 | 50 cycles |
| Per second (50Hz) | 10,000 | 7,500 | 2,500 cycles |

That's 2,500 cycles per second—not huge, but meaningful in tight timing situations.

## Zero Page Allocation Strategy

Good zero page management follows these principles:

### 1. Prioritise Hot Variables

Variables accessed most frequently get zero page slots:
- Loop counters
- Temporary calculations
- Pointer low/high bytes

### 2. Group Related Variables

Keep related variables adjacent:
```asm
; Score group
score_lo         = $05
score_hi         = $06

; Position group
song_pos         = $04
song_pos_hi      = $05
```

### 3. Reserve Workspace

Always keep some zero page free for temporary use:
```asm
; Reserved for any routine
temp_a           = $50
temp_b           = $51
temp_c           = $52
```

## What We Didn't Optimise

Some optimisations weren't worth the complexity:

| Optimisation | Savings | Why Not |
|--------------|---------|---------|
| Run-length encoding songs | ~500 bytes | Added decode overhead |
| Length-prefixed strings | ~20 bytes | Harder to read/maintain |
| Bit-packed booleans | ~10 bytes | Slower access |

The best optimisation is the one that improves performance without adding complexity.
