A static black background works, but dynamic colour cycling makes the game feel alive. This unit adds subtle background colour shifts during gameplay, with intensity increasing as the combo builds. High performers see dramatic colour changes; beginners see gentle hints of movement.

## Run It

Assemble and run:

```bash
acme -f cbm -o symphony.prg symphony.asm
```

![Unit 40 Screenshot](/images/commodore-64/game-01-sid-symphony/unit-40/screenshot.png)

Start a song and build a combo. At 1x multiplier, the background barely flickers. At 2x, you'll see hints of grey and blue. At 3x, colours shift more visibly. At 4x (50+ combo), the background cycles through blue, purple, and red—a visual celebration of your performance.

## Design Philosophy: Earned Spectacle

Background effects scale with skill:

| Combo | Multiplier | Background |
|-------|------------|------------|
| 0-9 | 1x | Nearly static (black with rare grey) |
| 10-24 | 2x | Subtle (black/grey/blue hints) |
| 25-49 | 3x | Visible (grey/blue/brown cycle) |
| 50+ | 4x | Dramatic (blue/purple/red cycle) |

Beginners focus on notes without distraction. Experts enjoy visual reward for mastery.

## New Variables

```asm
bg_cycle         = $2F          ; Background colour cycle counter
bg_intensity     = $30          ; Background intensity level (0-3)
```

The cycle counter creates slow, smooth transitions. Intensity maps directly to the combo multiplier.

## Respecting Hit Effects

Background cycling must not override hit feedback:

```asm
update_background:
            ; Skip if bg_flash is active (hit effect in progress)
            lda bg_flash
            bne bg_skip_cycle
```

When a perfect hit triggers a background flash, we pause cycling until the flash completes. Hit feedback always takes priority.

## Slow Cycling

We only update every 16 frames to prevent jarring transitions:

```asm
            ; Increment cycle counter (slow cycling)
            inc bg_cycle
            lda bg_cycle
            and #$0F                ; Only update every 16 frames
            bne bg_skip_cycle
```

At 50Hz, this means roughly 3 colour changes per second—perceptible but not distracting.

## Calculating Intensity

We reuse the existing `get_multiplier` routine:

```asm
            ; Calculate intensity based on combo multiplier
            jsr get_multiplier      ; Returns 1-4 in A
            sta bg_intensity        ; 1-4 based on combo
```

This keeps the combo calculation logic in one place, avoiding code duplication.

## Four Colour Palettes

Each intensity level has its own palette:

```asm
; Darkest - barely visible movement (1x combo)
bg_colours_dark:
            !byte 0                 ; Black
            !byte 0                 ; Black
            !byte 11                ; Dark grey
            !byte 0                 ; Black

; Subtle - hints of colour (2x combo)
bg_colours_subtle:
            !byte 0                 ; Black
            !byte 11                ; Dark grey
            !byte 6                 ; Blue
            !byte 11                ; Dark grey

; Medium - visible colour shifts (3x combo)
bg_colours_medium:
            !byte 11                ; Dark grey
            !byte 6                 ; Blue
            !byte 9                 ; Brown
            !byte 6                 ; Blue

; Bright - dramatic cycling (4x combo)
bg_colours_bright:
            !byte 6                 ; Blue
            !byte 4                 ; Purple
            !byte 2                 ; Red
            !byte 6                 ; Blue
```

Note the progression: darkest palette is mostly black, brightest never touches black at all.

## Palette Selection

We branch based on intensity level:

```asm
            ; Choose colour table based on intensity
            lda bg_intensity
            cmp #4
            bcs bg_use_bright
            cmp #3
            bcs bg_use_medium
            cmp #2
            bcs bg_use_subtle
            ; Fall through to darkest

bg_use_darkest:
            lda bg_colours_dark,x
            jmp bg_set_colour
```

Each branch loads from a different colour table using the same X index.

## Why Dark Colours?

The background must never compete with gameplay:

- **Notes are bright** (light red, green, blue) — they must pop
- **Hit zone is yellow** — high contrast against dark backgrounds
- **Text is white/cyan** — remains readable at any intensity

Even the "bright" palette uses dark colours (blue 6, purple 4, red 2) that won't wash out the notes.

## Performance Considerations

This routine is efficient:
- Only runs every 16 frames (minimal overhead)
- Single table lookup per update
- No complex calculations

The effect adds ~20 cycles every 16 frames—completely negligible.

## Try This

1. **Health-based intensity** - Lower health = more dramatic colours (danger feedback)
2. **Beat-synced changes** - Colour changes on beat instead of timer
3. **Track-specific colours** - Different background regions for each track
4. **Border matching** - Border colour follows background for unified look
