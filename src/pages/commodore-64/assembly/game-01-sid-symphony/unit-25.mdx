## High Score Table

We need to store 12 high scores: 4 songs × 3 difficulties. Each score is 16-bit (2 bytes), so:

```asm
; High Score Table (4 songs x 3 difficulties = 12 entries, 2 bytes each)
; Index = (song * 3) + difficulty

high_scores:
            ; Song 1 (First Steps)
            !word 0               ; Easy high score
            !word 0               ; Normal high score
            !word 0               ; Hard high score
            ; Song 2 (Upbeat Groove)
            !word 0               ; Easy
            !word 0               ; Normal
            !word 0               ; Hard
            ; Song 3 (Speed Rush)
            !word 0
            !word 0
            !word 0
            ; Song 4 (Off-Beat)
            !word 0
            !word 0
            !word 0
```

The `!word 0` directive creates a 2-byte value initialised to zero. At startup, all high scores are 0—any score beats them.

## Calculating the Table Index

To find the right high score, we calculate:

```
index = (selected_song × 3 + difficulty) × 2
```

In assembly:

```asm
check_high_score:
            ; Calculate table index: (selected_song * 3 + difficulty) * 2
            lda selected_song
            asl                     ; × 2
            clc
            adc selected_song       ; × 3
            clc
            adc difficulty          ; + difficulty
            asl                     ; × 2 (for 2-byte entries)
            tax                     ; X = table index
```

The multiply-by-3 uses a clever trick: `× 2 + original = × 3`. The final `× 2` accounts for 2-byte entries.

## Multi-Byte Score Comparison

Comparing 16-bit scores requires checking both bytes:

```asm
            ; Compare current score with high score
            ; First compare high bytes
            lda score_hi
            cmp high_scores+1,x     ; Compare high byte
            bcc hs_not_higher       ; Current < high
            bne hs_is_higher        ; Current > high

            ; High bytes equal, compare low bytes
            lda score_lo
            cmp high_scores,x       ; Compare low byte
            bcc hs_not_higher       ; Current < high
            beq hs_not_higher       ; Current = high
```

The comparison works like this:
1. Compare high bytes first
2. If current high byte is less, score is lower
3. If current high byte is greater, score is higher
4. If equal, compare low bytes

## Updating the High Score

When we beat the record:

```asm
hs_is_higher:
            ; New high score! Update table
            lda score_lo
            sta high_scores,x
            lda score_hi
            sta high_scores+1,x

            ; Set flag
            lda #1
            sta new_high_score
```

The `new_high_score` flag tells the results screen to show the celebration message.

## Display Logic

On the game over or results screen:

```asm
            ; Check if this was a new high score
            lda new_high_score
            beq draw_prev_high

            ; Draw "NEW HIGH SCORE!" in bright cyan
            ldx #0
draw_new_hs:
            lda new_hs_text,x
            bne +
            jmp go_draw_retry
+           sta SCREEN + (14 * 40) + 12,x
            lda #3                  ; Cyan
            sta COLRAM + (14 * 40) + 12,x
            inx
            jmp draw_new_hs
```

When you beat the high score, the message appears in cyan. Otherwise, we display the current high score in grey.

## Branch Distance Limits

Notice the `bne +` / `jmp` pattern:

```asm
            lda new_hs_text,x
            bne +                   ; Branch over jump if not zero
            jmp go_draw_retry       ; Far jump when zero
+           sta SCREEN ...
```

The 6502's `beq` instruction can only branch ±127 bytes. When targets are too far, we use a trampoline: branch over a jump instruction. This adds 3 bytes but handles any distance.

## Memory Trade-offs

The high score table uses 24 bytes (12 × 2). We could reduce this by:
- One global high score (2 bytes)
- Per-song only, not per-difficulty (8 bytes)
- Storing only top 3 scores globally (6 bytes)

But 24 bytes is trivial on a 64K machine, and per-song/difficulty tracking provides better motivation. Players can chase records on Easy while learning, then Hard for mastery.

## Session vs. Persistent Storage

Our high scores persist during the session—reset the computer and they're gone. True persistence would require:
- Saving to tape (slow, requires user action)
- Saving to disk (fast, but not all C64s have drives)
- Battery-backed RAM (expensive, rare)

For an educational game, session persistence is sufficient. Players can set records within a play session without the complexity of file I/O.

## Why High Scores Matter

High scores provide:
1. **Replay motivation** - "One more try to beat my record"
2. **Skill measurement** - Concrete feedback on improvement
3. **Per-variant goals** - Different challenges for different modes
4. **Session narrative** - Building towards mastery over time

Without high scores, once you complete a song, there's no reason to replay. With them, every play is an opportunity to improve.
