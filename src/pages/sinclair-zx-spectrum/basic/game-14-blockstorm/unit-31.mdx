This is a reflective unit. No new game features. Instead, you measure the game loop precisely, calculate where the time goes, and understand why the Spectrum BASIC interpreter cannot run a shooter at arcade speed. The same game written in Z80 assembly would run at 50 frames per second with 100 enemies. In BASIC, 20 enemies at 3 frames per second is the ceiling.

## The Measurements

Using PEEK 23672 at the start and end of the main loop, measure the loop time for different scenarios:

| Scenario | Loop time (ticks at 50Hz) | Approximate FPS |
|----------|---------------------------|-----------------|
| Wave 1: 8 drones, no bombs | 3-5 | 10-16 |
| Wave 5: 14 mixed, 3 bombs | 8-12 | 4-6 |
| Wave 10: 20 enemies, 3 bombs | 14-20 | 2-3 |
| Empty screen (no enemies) | 2-3 | 16-25 |

The empty-screen time tells you the baseline cost: input reading, HUD drawing, loop overhead. Everything above that baseline is the cost of processing enemies. Each enemy adds roughly 0.5-1 tick (10-20 milliseconds) of processing time.

## Why BASIC is Slow

### Line Scanning

Every GO SUB and GO TO starts from line 1 and scans forward. The interpreter reads each line number until it finds the target. A program with 250 lines and a GO SUB 400 scans past roughly 100 lines to reach the target. Each scan takes microseconds per line, but dozens of scans per loop iteration add up to milliseconds.

### Variable Lookup

Sinclair BASIC stores variables in a linked list. Accessing variable `px` means searching the list from the beginning, comparing names character by character. The more variables you have, the slower each access becomes. Blockstorm has roughly 30 variables. Each access in the inner enemy loop scans past most of them.

### Floating Point

Every number in Sinclair BASIC is a five-byte floating-point value. Even `LET x = x + 1` performs floating-point addition. In Z80 machine code, integer addition is one instruction taking 4 clock cycles. In BASIC, floating-point addition takes hundreds of cycles, plus the overhead of parsing the expression, looking up the variable, and storing the result.

### PRINT AT

Each PRINT AT call involves: calculating the screen memory address from row and column, setting the attribute byte for colour, and writing the character data. In machine code, this takes about 100 clock cycles. In BASIC, the interpreter must also parse the AT keyword, evaluate the row and column expressions, handle the colour keywords (INK, BRIGHT), and process the character expression.

## The Multiplication Factor

Rough estimates:

| Operation | Machine code | BASIC | Overhead factor |
|-----------|-------------|-------|-----------------|
| Integer add | 4 cycles | ~400 cycles | 100x |
| PRINT AT | 100 cycles | ~3000 cycles | 30x |
| Conditional jump | 10 cycles | ~1000 cycles | 100x |

The BASIC interpreter adds a 30-100x overhead on every operation. For a game loop that runs thousands of operations per frame, this overhead is the performance ceiling.

## What Assembly Solves

The assembly language track builds the same kind of game — sprites, movement, collision, scoring — using Z80 machine code. Direct memory access replaces PRINT AT. Register operations replace variable lookup. No interpreter overhead. The same 3.5 MHz processor that struggles with 20 enemies in BASIC can handle 50+ sprites at 50fps in assembly.

The point is not that BASIC is bad. BASIC is excellent for learning, prototyping, and building games that fit within its performance envelope. But when you push past that envelope — as Blockstorm does in its later waves — you understand exactly why programmers write in assembly. The motivation is not abstract. You have felt it.

## Try This

**Time individual operations.** Write a test program that performs 10,000 additions and time it with PEEK 23672. Then do 10,000 PRINT AT calls. Which is slower? By how much? This breaks down the loop time into its component costs.

**Count operations per frame.** Look at the main loop and count how many variable accesses, comparisons and PRINT ATs happen during a wave 10 frame with 20 enemies. Multiply each count by the approximate cost. Does the total match your measured loop time?
