A ten-floor dungeon crawl takes time. If the player must complete it in a single sitting, every interrupted session means a lost run. Save game writes the current state to tape — stats, equipment, floor, and dungeon layout — so the player can resume later. This is persistence: the game state survives beyond the current session.

## How It Works

The save function is accessible from the inventory screen. Pressing S triggers the save sequence.

**The save process** writes multiple pieces of data:
- Character stats: HP, max HP, attack, defence
- Equipment: weapon bonus, armour bonus, potion count
- Progress: gold, floor number, kill count, turn count
- The current dungeon array `d(16,16)` — all 256 cells
- The visibility array `v(16,16)` — which cells have been explored
- Monster positions, types, and HP

The Spectrum SAVE command writes data to tape as a block. The program constructs a save file by writing variables into a data area and saving it as a bytes block. On load, the same area is read back and the variables are restored.

## What Gets Saved

The save captures everything needed to resume play exactly where the player stopped. The dungeon layout is critical — without it, the player would return to a regenerated floor with different rooms and corridors. Monster positions and HP are saved so the player does not face defeated monsters again, and ongoing fights are not lost.

Equipment bonuses (`w` and `r`) are saved as numbers. The weapon name is derived from the number, so saving the name separately is unnecessary. This economy — saving the minimum data needed to reconstruct the full state — is a fundamental principle of serialisation.

## Tape I/O

The Spectrum tape interface is slow — saving takes real time as data is written to the audio signal. The player must wait for the save to complete before resuming play. A message indicates the save is in progress, and another confirms when it finishes.

In an emulator, tape operations are faster or instant depending on the emulator configuration. The code is the same either way — the program does not know whether it is running on real hardware or an emulator.

## State as Data

Saving a game is an exercise in identifying what constitutes the complete state. If any variable is missed, the loaded game will differ from the saved one. The character stats are obvious. The dungeon array is less obvious but essential. The visibility array might seem optional — the player could re-explore — but losing it changes the gameplay experience.

The process of listing every variable that matters teaches something important: the state of a program is the sum of all its variables. Change one, and the program behaves differently.

## Try This

**List every variable.** Before implementing save, write down every variable the game uses. Group them by category: character, equipment, dungeon, monsters, progress. This list is the save format specification.

**Test partial saves.** Save everything except the visibility array. Load and play — the dungeon is correct but unexplored cells are hidden again. Is that acceptable?
