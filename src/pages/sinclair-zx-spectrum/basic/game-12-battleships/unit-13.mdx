A player should not be able to fire at the same cell twice. It wastes a turn and, worse, could produce confusing results if the program treats it as a new hit. Before processing a shot, the program checks the tracking array. If the cell is already marked as a hit or miss, the shot is rejected.

## How It Works

**Lines 30-50** check the tracking array after parsing the coordinate. For Player 1, this means checking `c(y,x)`. If the value is 6 (hit) or 7 (miss), the cell has already been fired at.

**Lines 60-70** print an error message: "Already fired there!" and loop back to the coordinate prompt. The player does not lose their turn — they simply need to choose a different target.

**Lines 80-100** proceed with the normal hit/miss logic only if the tracking cell is 0 (unfired).

## Why Check the Tracking Array

We check the tracking array rather than the ship array because the tracking array is the definitive record of what this player has done. The ship array might have been modified by the other player damage — the value 6 in the ship array could mean a hit from either player. The tracking array is unambiguous: if `c(y,x)` is non-zero, Player 1 has already fired there.

## Validation Order

The program now runs three checks before processing a shot:

1. **Range check** — column 1-10 and row 1-10
2. **Already fired** — tracking array is 0
3. **Hit or miss** — opponent ship array value

Each check gates the next. If the range check fails, we do not bother checking the tracking array. If the tracking check fails, we do not look at the ship array. This layered validation pattern keeps each check simple and prevents errors from cascading.

## Try This

**Fire at the same cell twice.** Hit a ship at D5, then fire at D5 again. The second shot should be rejected with a message. The tracking grid should not change.

**Test with misses too.** Fire at an empty cell, then fire there again. Both hits and misses should be caught by the duplicate check.
