## How It Works

**Lines 10-150** form the main program flow. Each line calls a subroutine by number. Reading these lines tells you what the game does without knowing how:

- `GO SUB 400` - initialise the board
- `GO SUB 500` - draw the board
- `GO SUB 600` - draw pieces
- `GO SUB 700` - draw labels
- `GO SUB 800` - show status
- `GO SUB 850` - read input
- `GO SUB 900` - validate source
- `GO SUB 950` - check move
- `GO SUB 1000` - make move

**Lines 1200-1240** introduce a new draw-cell subroutine. Instead of duplicating the piece-drawing code in the move and capture sections, both call `GO SUB 1200`. This subroutine clears the old position and draws the piece at the new position, checking the piece value to choose the correct colour.

## The Subroutine Map

The program now follows a clear line-number convention:

| Line range | Purpose |
|-----------|---------|
| 1-99 | Setup and main loop |
| 400-498 | Init board |
| 500-570 | Draw board |
| 600-690 | Draw pieces |
| 700-770 | Draw labels |
| 800-840 | Status display |
| 850-880 | Input reading |
| 900-940 | Source validation |
| 950-995 | Move checking |
| 1000-1090 | Move execution |
| 1100-1190 | Capture checking |
| 1200-1240 | Draw cell |

Each subroutine has a clear purpose, a REM comment naming it, and a RETURN at the end. This structure will hold as we add kings, multi-jumps, and win detection in Phase 2.

## Why Refactor Now

The program works. Why reorganise? Because Phase 2 will nearly double the code. Adding king promotion, mandatory captures, multi-jump chains, and win detection will push the program past 200 lines. Without clean subroutine boundaries, changes in one area break another. Investing in structure now saves time later.

## Try This

**Trace a move.** Follow the execution path through the main loop for a single move. Write down every GO SUB and RETURN. Does the flow make sense?

**Add REM comments.** If any subroutine's purpose is not obvious, add a REM line at the start. Good comments describe what a block does, not how it does it.
