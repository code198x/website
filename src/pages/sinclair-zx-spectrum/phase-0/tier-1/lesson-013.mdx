You can move a character around the screen. Now make the world respond. Walls that block movement. Goals that trigger victory. Items to collect. Every Spectrum game needs collision detection—checking what's at a location before acting on it.

The Spectrum provides SCREEN$(row,col)—a function that reads characters directly from the display. Want to know if there's a wall ahead? Check SCREEN$ at the destination. Returns a space? Safe to move. Returns a block character? Wall detected, stay put. Simple, fast, powerful.

Manic Miner checks platform characters. Knight Lore tests for objects. Jet Set Willy detects deadly sprites. SCREEN$ underlies every collision system. This lesson builds a complete maze game demonstrating the check-before-move pattern that makes interactive worlds possible.

## The One-Minute Tour

- **SCREEN$(row,col)** reads character at screen position
- **Check-before-move pattern** - Test destination before updating position
- **CHR$ 127** creates solid wall blocks (█)
- Store new position in temporary variables (NX, NY)
- Only move if destination contains space character
- Win conditions detect when player reaches goal
- This pattern scales from mazes to platformers to adventure games

## Your First Collision Detection

Type this carefully:

```basic
10 REM Simple Maze
20 REM Basic collision detection demo
30 PAPER 0: INK 7: BORDER 1: CLS
40 REM Draw maze border
50 FOR X=0 TO 31
60 PRINT AT 2,X;CHR$ 127
70 PRINT AT 21,X;CHR$ 127
80 NEXT X
90 FOR Y=3 TO 20
100 PRINT AT Y,0;CHR$ 127
110 PRINT AT Y,31;CHR$ 127
120 NEXT Y
130 REM Draw internal walls
140 FOR Y=5 TO 15
150 PRINT AT Y,10;CHR$ 127
160 NEXT Y
170 FOR X=15 TO 25
180 PRINT AT 10,X;CHR$ 127
190 NEXT X
200 REM Player start position
210 LET PX=15: LET PY=10
220 PRINT AT 0,0;"Use Q/A/O/P to navigate"
230 PRINT AT PY,PX;"@"
240 REM Game loop
250 LET NX=PX: LET NY=PY
260 LET K$=INKEY$
270 IF K$="q" THEN LET NY=NY-1
280 IF K$="a" THEN LET NY=NY+1
290 IF K$="o" THEN LET NX=NX-1
300 IF K$="p" THEN LET NX=NX+1
310 REM Collision check
320 IF SCREEN$(NY,NX)=" " THEN GOSUB 1000
330 GO TO 250
1000 REM Move player
1010 PRINT AT PY,PX;" "
1020 LET PX=NX: LET PY=NY
1030 PRINT AT PY,PX;"@"
1040 RETURN
```

**Run this** and try to walk through the walls. You can't! The maze blocks you.

## How This Works

### The SCREEN$ Function

```basic
320 IF SCREEN$(NY,NX)=" " THEN GOSUB 1000
```

SCREEN$(row,col) reads the character at the specified screen position. Returns a string containing that character—whatever was printed there.

In this maze:
- Walls are CHR$ 127 (solid block: █)
- Empty space is " " (space character)
- Player is "@" (at symbol)

Before moving, check the destination. If SCREEN$ returns a space, the location is empty—safe to move. If it returns anything else (wall block, player character), there's an obstacle—don't move.

**Critical detail:** SCREEN$ uses the same Y,X coordinate system as PRINT AT. Row first (0-21), column second (0-31).

### The Check-Before-Move Pattern

```basic
250 LET NX=PX: LET NY=PY
260 LET K$=INKEY$
270 IF K$="q" THEN LET NY=NY-1
280 IF K$="a" THEN LET NY=NY+1
290 IF K$="o" THEN LET NX=NX-1
300 IF K$="p" THEN LET NX=NX+1
310 REM Collision check
320 IF SCREEN$(NY,NX)=" " THEN GOSUB 1000
```

This is the pattern used by nearly every Spectrum game:

1. **Store current position** - Copy PX, PY to NX, NY (new position)
2. **Read input** - Get key with INKEY$
3. **Calculate new position** - Modify NX, NY based on input
4. **Check destination** - Use SCREEN$(NY,NX) to see what's there
5. **Conditional move** - Only update actual position if destination is valid

**Why NX and NY?** Temporary variables let you calculate where the player *wants* to go without committing to the move. Check first, move second. If destination is invalid (wall, enemy, pit), NX and NY are discarded and player stays at PX, PY.

**Previous lesson** used boundary checking (IF X&lt;0 THEN...). Now we use SCREEN$ checking—more powerful because it detects *any* obstacle character, not just screen edges.

### Building the Maze

```basic
40 REM Draw maze border
50 FOR X=0 TO 31
60 PRINT AT 2,X;CHR$ 127
70 PRINT AT 21,X;CHR$ 127
80 NEXT X
```

Draw horizontal borders (top and bottom) using FOR loops. CHR$ 127 outputs as █—a solid block from the Spectrum's character set. Loop from column 0 to 31, printing blocks at row 2 (top) and row 21 (bottom).

```basic
90 FOR Y=3 TO 20
100 PRINT AT Y,0;CHR$ 127
110 PRINT AT Y,31;CHR$ 127
120 NEXT Y
```

Draw vertical borders (left and right sides). Loop from row 3 to 20, printing blocks at column 0 (left) and column 31 (right).

Result: rectangular maze border with rows 0-1 reserved for instructions, rows 3-20 as playable area, row 2 and 21 as walls.

```basic
130 REM Draw internal walls
140 FOR Y=5 TO 15
150 PRINT AT Y,10;CHR$ 127
160 NEXT Y
170 FOR X=15 TO 25
180 PRINT AT 10,X;CHR$ 127
190 NEXT X
```

Add internal obstacles—vertical wall from rows 5-15 at column 10, horizontal wall from columns 15-25 at row 10. Creates rooms and passages. Player must navigate around these obstacles to explore the maze.

### The Movement Subroutine

```basic
1000 REM Move player
1010 PRINT AT PY,PX;" "
1020 LET PX=NX: LET PY=NY
1030 PRINT AT PY,PX;"@"
1040 RETURN
```

Separated into subroutine at line 1000 (standard pattern—subroutines start at 1000s, 2000s, etc.). Only called when SCREEN$ confirms destination is empty.

1. Erase old position (print space at PY, PX)
2. Update position (copy NX, NY to PX, PY)
3. Draw new position (print @ at PY, PX)
4. Return to game loop

**Why subroutine?** Keeps game loop clean—line 320 reads as "if destination is space, move player". Logic separation. Later you'll add animations, sound effects, scoring to this subroutine. All movement behavior lives in one place.

## Understanding the Complete Game

### Complex Maze Layout

```basic
130 REM Vertical walls
140 FOR Y=5 TO 15
150 PRINT AT Y,8;CHR$ 127
160 PRINT AT Y,23;CHR$ 127
170 NEXT Y
180 REM Horizontal walls
190 FOR X=10 TO 20
200 PRINT AT 8,X;CHR$ 127
210 PRINT AT 18,X;CHR$ 127
220 NEXT X
```

Creates multiple rooms:
- Two vertical walls at columns 8 and 23 (rows 5-15)
- Two horizontal walls at rows 8 and 18 (columns 10-20)
- Forms a grid-like structure with distinct areas

```basic
230 REM Gaps in walls
240 PRINT AT 10,8;" "
250 PRINT AT 13,23;" "
260 PRINT AT 8,15;" "
270 PRINT AT 18,15;" "
```

Critical addition: gaps in the walls. After drawing solid walls, print spaces at strategic positions to create passages between rooms. Without gaps, areas become unreachable—maze unsolvable.

**Maze design principle:** Draw complete structures, then add access points. Easier than trying to draw incomplete walls with FOR loops.

### Goal Detection

```basic
280 REM Goal marker
290 INK 2: PRINT AT 10,25;"X"
```

Place the goal character (X) in cyan (INK 2) at position (10, 25)—inside one of the rooms. Player must navigate through gaps to reach it.

```basic
440 LET CH$=SCREEN$(NY,NX)
450 IF CH$="X" THEN GOSUB 2000
460 IF CH$=" " THEN GOSUB 1000
```

Check destination character. Store in CH$ variable for multiple tests:
- If X → call win condition subroutine (line 2000)
- If space → call move player subroutine (line 1000)
- Anything else (wall block) → do nothing, player stays put

**Pattern evolution:** Simple maze checked for space only. Complete game checks for multiple character types—extensible to items, enemies, hazards, doors, keys...

### Move Counter

```basic
340 LET MOVES=0
...
1030 LET MOVES=MOVES+1
1040 PRINT AT 1,0;"Moves: ";MOVES;"  "
```

Track player efficiency. Initialize MOVES to 0 before game starts. Increment every time movement subroutine executes (valid move made). Display current count at row 1.

**Trailing spaces** in PRINT statement (line 1040) clear previous digits. If counter goes from 99 to 100, without spaces you'd see "10099" (digits overlap). Spaces overwrite remnants.

**Why track moves?** Adds challenge dimension—completing maze in fewest moves. Creates replayability. Players optimize routes, compete for best scores.

### Win Condition Subroutine

```basic
2000 REM Win condition
2010 CLS
2020 PRINT AT 10,8;"YOU FOUND IT!"
2030 PRINT AT 12,6;"Moves taken: ";MOVES
2040 PAUSE 0
2050 STOP
```

Triggered when player reaches X character. Clear screen, display victory message and final move count. PAUSE 0 waits for any keypress (gives player time to read message). STOP ends program, returns to BASIC prompt.

**Subroutine placement:** Line 2000s for game-ending conditions. Later you'll add death handlers, game over screens, victory animations at 2000, 3000, 4000... Organizational pattern scales.

## How SCREEN$ Actually Works

### Reading Display Memory

The Spectrum screen lives in memory at 16384-22527 (display file) and 22528-23295 (attributes—colours). SCREEN$ function reads this memory and converts it back to the character that was printed.

**When you print:**
```basic
PRINT AT 10,15;"X"
```

The ROM routine:
1. Calculates memory address for row 10, column 15
2. Writes character code for "X" (88 in ASCII) as pixel pattern
3. Writes colour attributes (INK/PAPER) to attribute memory

**When you check:**
```basic
LET CH$=SCREEN$(10,15)
```

The ROM routine:
1. Calculates same memory address
2. Reads pixel pattern bytes
3. Matches pattern against character ROM
4. Returns matching character as string

**Performance:** SCREEN$ is fast—single ROM call, direct memory read. No scanning, no iteration. Instant collision detection.

### Character Set Limitations

SCREEN$ returns characters from the Spectrum character set (codes 32-127). If pixel pattern doesn't match any character, results are undefined (usually returns garbage or space).

**This means:**
- Works perfectly for text-based mazes (blocks, letters, symbols)
- Works for simple graphics using CHR$ characters
- Doesn't work for user-defined graphics (UDG)—requires different technique
- Doesn't work for pixel-perfect collision—works at character cell level (8×8 pixels)

**Spectrum games using SCREEN$:**
- **Manic Miner:** Platform detection (solid blocks)
- **Jet Set Willy:** Room transitions (door characters)
- **Chuckie Egg:** Ladder detection (H character)
- **Knight Lore:** Object interaction (item characters)

Games with detailed sprites use memory scanning or sprite overlap calculations instead. SCREEN$ perfect for character-based games—the majority of Spectrum titles.

## Experiment: Treasure Hunt

Extend the game with collectible items:

```basic
285 REM Treasure markers
286 INK 6: PRINT AT 7,5;"$"
287 PRINT AT 15,15;"$"
288 PRINT AT 12,28;"$"
289 LET TREASURE=0
...
455 IF CH$="$" THEN GOSUB 3000
...
3000 REM Collect treasure
3010 PRINT AT PY,PX;" "
3020 LET PX=NX: LET PY=NY
3030 LET TREASURE=TREASURE+1
3040 PRINT AT 1,16;"Treasure: ";TREASURE;"/3  "
3050 PRINT AT PY,PX;"@"
3060 IF TREASURE=3 THEN GOSUB 2000
3070 RETURN
```

Place $ characters around maze. New subroutine at 3000 handles collection—erase treasure, move player into that space, increment counter. If all 3 collected, trigger win condition.

**Game design:** Now player must collect all treasures before reaching X. Or make X only appear after treasures collected (change line 290 to print X inside subroutine 3070).

## Experiment: Timer Challenge

Add time pressure:

```basic
345 LET TIME=300
...
1045 LET TIME=TIME-1
1046 PRINT AT 1,16;"Time: ";TIME;"  "
1047 IF TIME=0 THEN GOSUB 4000
...
4000 REM Out of time
4010 CLS
4020 PRINT AT 10,10;"TIME'S UP!"
4030 PRINT AT 12,8;"You were so close..."
4040 PAUSE 0
4050 STOP
```

TIME starts at 300 (enough moves to solve). Decrements with each move. If reaches 0, game over (subroutine at 4000). Creates urgency—can't explore leisurely, must find efficient path.

**Balancing:** Run through maze yourself, count moves needed for optimal solution. Set TIME to 1.5× that value—allows mistakes but prevents aimless wandering.

## Experiment: Enemy Patrol

Add a moving obstacle:

```basic
295 LET EX=20: LET EY=10
296 LET EDIR=1
...
475 GOSUB 5000
...
5000 REM Move enemy
5010 PRINT AT EY,EX;" "
5020 LET EX=EX+EDIR
5030 IF EX=25 OR EX=15 THEN LET EDIR=-EDIR
5040 PRINT AT EY,EX;"!"
5050 IF EX=PX AND EY=PY THEN GOSUB 4000
5060 RETURN
```

Enemy (!) patrols horizontally between columns 15-25. EDIR controls direction (1=right, -1=left). When reaching boundaries, reverses (toggle EDIR). If enemy position matches player position—game over.

**Game loop evolution:** Each iteration now moves player (if key pressed) and moves enemy (always). Enemy moves independently—doesn't wait for player input. Creates challenge—player must time movements to avoid patrol.

## Why This Pattern Matters

**Foundation of interactive worlds:**

Every Spectrum game with obstacles, objects, or interactions uses variations of check-before-move:

- **Platform games:** Check for solid tiles before moving, check for spikes/enemies, check for collectibles
- **Adventure games:** Check for walls, doors, items, NPCs
- **Puzzle games:** Check for blocks, switches, goals
- **Shoot-em-ups:** Check for enemies, bullets, power-ups

The pattern scales infinitely:
```basic
LET CH$=SCREEN$(NY,NX)
IF CH$="█" THEN REM Wall - stay put
IF CH$="$" THEN REM Coin - collect
IF CH$="!" THEN REM Enemy - take damage
IF CH$="H" THEN REM Ladder - allow climbing
IF CH$="D" THEN REM Door - check for key
IF CH$=" " THEN REM Empty - move freely
```

One function (SCREEN$), unlimited game mechanics.

## Quick Reference: Collision Detection

| Concept | Implementation | Purpose |
|---------|----------------|---------|
| SCREEN$ | `LET CH$=SCREEN$(Y,X)` | Read character at position |
| Check-before-move | NX, NY temporary variables | Test destination before committing |
| Wall character | CHR$ 127 | Solid block for obstacles |
| Empty space | " " (space) | Walkable areas |
| Conditional move | IF SCREEN$=" " THEN GOSUB... | Only move if valid |
| Goal detection | IF SCREEN$="X" THEN... | Win conditions |
| Multiple tests | Store in CH$ variable | Check for different characters |

**Check-Before-Move Pattern:**
```basic
Store current position in temp variables (NX=PX)
Read input (INKEY$)
Calculate new position (modify NX, NY)
Check destination (CH$=SCREEN$(NY,NX))
If valid destination → move
If invalid destination → stay put
```

**Maze Building:**
```basic
Draw complete walls (FOR loops with CHR$ 127)
Add gaps (PRINT AT with spaces)
Place goal markers (PRINT AT with letters)
Set player start position
```

**Character Types for Detection:**
- █ (CHR$ 127) - Walls/obstacles
- " " (space) - Empty walkable space
- Letters (X, $, !, etc.) - Goals, items, enemies
- H - Ladders
- D - Doors
- Any character in set 32-127
