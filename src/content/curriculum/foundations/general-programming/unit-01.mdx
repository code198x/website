This course teaches the *ideas* every programming language is built from, not a language.
Each idea is written in **pseudocode**: plain instructions in a fixed shape, meant for a
person to read rather than a machine to run. Pseudocode is what programmers sketch a
program in before they write it, and what they explain one in afterwards.

The ideas are what you keep for life. The language you eventually write them in — BASIC,
Python, C, assembly — is the clothes they wear that day. When you pick one up, you will
find you already know what its instructions are *for*, and only be learning how that
language spells them.

## A program is a list of instructions

A program is a list of instructions. The computer reads them in order, from the top,
and does **exactly** what each one says — no more, no less, and no guessing at what
you *meant*.

Here is the smallest program there is: one instruction, which shows a word.

```text
SHOW "Hello"
```

Run it, and it produces:

<Output>Hello</Output>

That is the whole of it. You told the computer to show a word, and it did. Nothing else
happened, because nothing else was asked for. That relationship — **you write the
instruction, the machine carries it out** — is what programming *is*. Everything else in
this course is more instructions, and cleverer ones.

`SHOW` is this course's way of writing *output*, and every language has one of its own.
BASIC says `PRINT`. Python says `print`. C says `printf`. The word changes; the idea does
not. That is why the idea is written plainly first: `SHOW` is true everywhere, and each
language's word is only its own spelling of it.

## "Exactly what you say" — not "perfectly"

You will hear it said that a computer never makes mistakes. That is a useful
half-truth. The machine does *exactly* what you told it — but "exactly" is not
"perfectly". Computers are built by people, and people make mistakes, so a handful of
genuine bugs are baked into the silicon and the built-in software of real machines. They
are real — but they are rare, and they are well documented.

In your first months of programming, a program that misbehaves is almost never one
of them. It is the instruction you wrote. So build this habit from your first day:
the moment something goes wrong, **suspect your own code first** — not because the
machine is flawless (it isn't), but because real machine bugs are rare and known,
while your own slips are neither. The computer did what you said; the work is finding
where what you *said* and what you *meant* came apart. That is a craft of its own,
and the last unit of this course is about it.

## When it's wrong, see why

Even a one-instruction program goes wrong in small, recognisable ways:

- **The computer refuses the line.** A quotation mark is missing from one end, or a word
  is misspelt. `SHOW "Hello` is not a program — nothing says where the text was meant to
  stop. The machine is not being difficult; it honestly cannot read what you meant.
- **Nothing happens.** You wrote the program but never ran it. A program sits and waits
  until you tell it to go.
- **Whatever you ran it with has something to say.** Every language and every machine
  reports back when it finishes or gives up — a message, often a line number. That report
  is the first and most honest debugging tool you have. Read it rather than flinch from
  it; the habit starts here and the last unit is built on it.

Reading what the machine did — its output, and whatever it told you — is how you will
find every bug from here on. Not by guessing: by looking.

## What you've learnt

- A **program** is a list of instructions, followed in order, exactly as written.
- **Output** is how a program shows you something — `SHOW` here, `PRINT` in BASIC, a
  different word in every language, the same idea underneath.
- The machine does exactly what you say, which is not the same as perfectly — but
  your own code is the first place to look when something is wrong.
- When a program stops, whatever ran it **tells you something**. That report is your
  first window into a program that has run.
