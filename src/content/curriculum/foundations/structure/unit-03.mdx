The divider from Unit 2 does the same thing every time. That is fine for a divider. Most
jobs are not like that: you want the same work done to a different value each time.

So you give the job something to work on.

## Handing a value in

Put a name in brackets after the job's name. That name stands for whatever the caller hands
over:

```text
DEFINE greet(who)
  SHOW "Hello, ", who
END

CALL greet("Sam")
CALL greet("Ada")
```

<Output>{`Hello, Sam
Hello, Ada`}</Output>

One job, two results. Inside `greet`, the box `who` holds whatever came in with the call:
`"Sam"` the first time, `"Ada"` the second.

That box belongs to the job. It holds its value while the job runs and means nothing
outside, so a `who` anywhere else in your program is a different box that happens to share
a name.

## Handing a value back

A job can also give an answer. `RETURN` hands a value to whoever called, and the job stops
there:

```text
DEFINE double(n)
  RETURN n * 2
END

LET x = double(5)
SHOW x
```

<Output>{`10`}</Output>

`double(5)` runs the job with `n` set to 5, and the `RETURN` sends `10` back. That answer
lands where you wrote the call, so `LET x = double(5)` puts `10` in `x`.

Notice the two shapes are different on purpose. `CALL greet("Sam")` does a job and expects
nothing back. You use `double(5)` for its answer, so it sits where a value belongs.

## Say what the caller can rely on

Compare `greet` with `double`. Before tracing either call, predict which one changes
the display and which one supplies a number we can use in another calculation.

<details>
<summary>Compare their promises</summary>

| Job | Input | Result for the caller | Other effect |
|---|---|---|---|
| `greet` | A name | No returned value | Displays a greeting |
| `double` | A number | Twice that number | Does not print anything |

We can check `double(0)` without drawing a screen: it should return `0`. Changing it
to print the answer instead would break `LET x = double(5)`, even if `10` looked right
on screen. The caller needs the result, not just a visible effect.

</details>

This small agreement is a **contract**: what goes in, what comes back and what else
changes. Later, a drawing or sound routine also needs to say which state it changes
and whether its work is finished when it returns.

Our pseudocode gives parameters local names. A machine language may pass them in
registers or shared memory instead. Sinclair BASIC's `GO SUB` does not create these
local parameter boxes, and its `RETURN` resumes the caller without returning an
expression. We carry the idea across, then explain how that language implements it.

## When it's wrong, see why

- **The job always does the same thing.** You named a value in the brackets but used a
  different name inside the job. The name in the brackets is the one that holds what came
  in.
- **You get nothing back.** The job has no `RETURN`, or the program reached the `END`
  without passing one. A job with nothing to hand back is one you `CALL` instead.
- **You called it without the value it needs.** `CALL greet()` does not meet this
  job’s contract: we must supply a name. Our notation does not invent a value for
  `who`; a real language defines how it reports or handles a missing argument.

## What you've learnt

- A job can take a value: the name in brackets holds whatever the caller hands over.
- **`RETURN`** hands a value back, and the answer lands where you wrote the call.
- A job you **`CALL`** does something. A job you use for its answer goes where a value goes.
- The names inside a job belong to the job.
