The first kind of translator is called an **interpreter**, and it works the way a person
would if you handed them a recipe in a language they half knew.

It reads one line. It works out what that line means. It does it. Then it reads the next
line and starts again.

In this simplified model, notice what it does *not* do. It does not remember having understood the
line. The next time that same line comes round, it works the meaning out again from
scratch.

Real interpreters can keep tokens or other prepared representations. Our model
shows repeated runtime work; it is not a claim that every interpreter reparses
every character on each visit.

## Inside a loop

Most of the time that costs nothing you would notice. Then you write a loop:

```text
LET total = 0
FOR i = 1 TO 1000
  LET total = total + 1
END
SHOW total
```

<Output>{`1000`}</Output>

The line in the middle runs a thousand times. Our model does not translate it once
and run the translation a thousand times. It translates it a thousand times, because each
time round it meets the line fresh.

Count what happened. A thousand additions, which is the work you asked for. And a thousand
translations, which is work you did not ask for and did not know you were paying for.

That translating sits inside the loop whether you wanted it there or not. Nothing in your
program mentions it. It is the price of having a translator work as it goes.

## Why a game notices

A game repeatedly samples input, updates its world and prepares a picture. Its
update rate need not match the display refresh. Repeated interpreter work uses
some of the time available at the update rate the game needs.

The enemy that decides where to move lives inside that loop. So does the check for whether
the player has been hit, and the code that draws every object. Our interpreter model repeats its lookup work as it reaches each operation.

On a small machine that can become a significant part of the budget. There is a fixed amount of time between one
frame and the next, and the translating spends some of it before the game has done
anything at all.

## Why anyone would build it this way

Because it is kind.

You type a line and it runs. You make a mistake and the interpreter, which is reading your
line right now, can tell you where. You can stop, change one line, and carry on. Nothing
has to be rebuilt.

That is exactly the experience the BASIC in these machines gave you, and it is why a
whole generation learned to program on it. An interpreter can support both experimentation and finished games. We look for
a different approach when a measured requirement calls for it.

## When it's wrong, see why

- **The loop is slow and its visible result is small.** Interpreter work is one
  possible cost. Arithmetic, drawing and waiting may matter too; investigate which.
- **You made the loop run fewer times and it got faster.** That is the same fact from the
  other side. Fewer passes, fewer translations.
- **You cannot see where the time goes.** Our listing does not show the interpreter
  implementation. Source inspection and measurements can help expose that extra work.

## What you've learnt

- Our **interpreter model** reads a line, works out its meaning and performs it;
  real implementations may retain prepared information.
- Inside a loop it translates the same line **every pass**, which is work you did not ask
  for.
- Game updates and display refresh are distinct; repeated work uses update time.
- Interpreters make experimentation convenient and can run finished games too.
