Our interpreter model repeatedly reads and handles a stored statement. Another
approach prepares machine instructions before execution.

Translate the whole program first. All of it, before a single line runs. What is left
afterwards is a sequence of instructions. The machine still has to perform their
work; reading and interpreting the source statement is no longer part of each
pass. We translate again when we change the source and rebuild.

A **native-code compiler** translates higher-level source into instructions for
the target processor. For `LET total = total + 1`, it must arrange for the old
value to be read, one to be added, and the result to be stored. It can also
combine or remove operations when that preserves the program's meaning.

The resulting machine code can include calls to library routines for jobs such
as arithmetic or printing. Those routines still do work when the program runs;
compilation does not make that work disappear.

The build may have several stages. For example, a compiler can produce assembly
source, an assembler can encode it, and a **linker** can join the pieces and
library routines into a program. We use “compile” for the overall build in many
tools, but these stages have different jobs.

Not every compiler produces native code before a program starts. Some produce
**bytecode**, instructions for a software machine, and some compile while the
program is running. Here we are following the route that builds native machine
code in advance.

## Where an assembler differs

In assembly source, we have already chosen the processor operations. The
**assembler** encodes those instructions and works out details such as the
addresses named by labels. A higher-level compiler makes more of those
instruction choices for us.

Our invented machine lets us model just the encoding step. Each of its three
instruction names has one code:

| Name | Number |
|------|--------|
| `INC` | 1 |
| `DOUBLE` | 2 |
| `SHOW` | 3 |

Look up each name and write down its number. That is the encoding job for this
tiny machine. Real instructions can occupy several bytes, including values or
addresses used by the operation.

## Build it

We can describe a toy assembler with two lists, a loop that walks a program, and
a question that checks a name. Trace this pseudocode:

```text
LET names = ["INC", "DOUBLE", "SHOW"]
LET codes = [1, 2, 3]
LET program = ["INC", "INC", "DOUBLE", "SHOW"]

FOR EACH word IN program
  FOR i = 1 TO 3
    IF word = names[i] THEN SHOW codes[i]
  END
END
```

Read it through. For each word in the program, look along the list of names. When you
find the one that matches, show the number in the same place in the other list.

`1 1 2 3`. That is the row of numbers from Unit 1, and you just produced it from the
names. You have written an assembler.

This toy shows a name-to-number lookup. A real assembler also handles details
such as operands, labels, addresses and diagnostics. The small model gives us a
starting point for understanding those jobs; it does not implement them.

## What runs afterwards

The machine is handed `1 1 2 3` and runs it without consulting our source-name
table. Add one, add one, double, show. We keep the source separately so we can
edit and rebuild it.

Imagine a native-code compiler produced those same four codes from a
higher-level description. On our tiny machine, given the same starting value,
the result would be identical. The processor follows the instructions it receives;
there is no extra “compiled” step when it executes them.

Both routes can produce **native machine code**. Different tools may choose
different instruction sequences for the same task, so their speed and size can
differ. We need to inspect or measure those sequences to compare them.

Removing the repeated source-name lookup removes that work from execution.
Whether a game keeps up with its intended update rate still depends on the
instructions, data and hardware work that remain.

## When it's wrong, see why

- **A name was not in the table.** The assembler found nothing to match, so it wrote
  nothing down, and the machine got a shorter program than you wrote. A real assembler
  stops and tells you. This toy does not, which is a good reason to make yours do so.
- **You changed the program and nothing changed.** The old numbers are still what the
  machine has. Translating once means translating *again* when you change something.
- **The program runs but gives the wrong result.** Keep the matching source and
  build information so we can connect execution back to our intentions. The next
  unit explains how diagnostics and observation help together.

## What you've learnt

- A **native-code compiler** chooses machine instructions to implement higher-level source.
- An **assembler** encodes instructions selected in assembly source.
- Both can produce **native machine code** for the same processor.
- You built one from **two lists and a loop**.
- Removing runtime translation work does not establish the whole program's speed.
