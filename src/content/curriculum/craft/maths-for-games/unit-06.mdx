A position answers two questions: how far across, and how far up? Move the point using its coordinates before we ask it to travel.

## Choose an origin

The crossing of the axes is our origin: (0, 0). Coordinates are written (x, y), with the horizontal value first. A point at (120, 90) lies 120 units right of the origin and 90 units above it. These are world units; resizing the picture does not change the point’s position.

Make X negative while leaving Y at 90. The point crosses to the left, but stays at the same height. Now make Y negative too. The signs tell us which side of each axis contains the point.

## Position and movement

A position is where something is. A displacement is the change from one position to another. To get from (20, 30) to (120, 90), subtract start from finish: Δx = 120 − 20 = 100 and Δy = 90 − 30 = 60. The symbol Δ means “change in”.

<Question prompt="From (120, 90), move 30 units left and 50 units down. Where will the point end up?">

(90, 40): add −30 to X and −50 to Y. A negative change does not necessarily produce a negative position.

</Question>

Set that result using the controls. If a point moves in the wrong direction, check the coordinate order and the signs. Many screen APIs count Y downwards; this experiment keeps world Y upwards and reverses it only when drawing.

## Put the point in display memory

The Pattern Library’s [pixels, spans and boxes](/patterns/cross-platform/rendering/pixels-and-boxes/)
turn coordinates into actual Spectrum, BBC Micro and Dragon bitmap addresses.
Integer division chooses a byte; the remainder chooses a bit. The routines count
Y down from the top left, so keep that screen position distinct from the upwards
world Y used here.

[Writable characters](/patterns/cross-platform/rendering/custom-glyphs/) gives a
second example: local dot (3,5) inside cell (2,2) becomes screen pixel (19,21).
The machine entries explain the arithmetic alongside reusable code, so you can
try either direction: use the maths to understand the routine, or use a visible
routine to give the maths a purpose.

[Draw with integer error](/craft/maths-for-games/unit-12/) takes the next step:
choose dots for a line or curve, keep rounding consistent, then turn an edge
into row spans. Its [machine routines](/patterns/cross-platform/rendering/geometry/)
include CPC packed colour alongside the three monochrome backends.

[Move a glyph, keep its shape](/craft/maths-for-games/unit-13/) takes coordinates into reusable bitmap text: translate local dots, retain advance when clipping, and account for byte boundaries.

Follow the same point through [linear Atom rows](/patterns/acorn-atom/assembly/rendering/pixels-and-boxes/), [Electron interleaving](/patterns/acorn-electron/assembly/rendering/pixels-and-boxes/), [C64 bitmap colour cells](/patterns/commodore-64/assembly/rendering/pixels-and-boxes/) and [an Amiga Chip RAM plane](/patterns/commodore-amiga/assembly/rendering/pixels-and-boxes/). The point stays (x,y); the address and the ownership rules change.

## A coordinate meets a console

The [Atari 2600 playfield](/patterns/atari-2600/assembly/rendering/playfield-kernel/) gives each independent cell four colour clocks of width and eight scanlines of height. Point (13,19) maps to cell (3,2), with local remainders (1,3). Repeating or reflecting that half-picture changes the image without allocating another independent half.

The [Atari 7800 object builder](/patterns/atari-7800/assembly/rendering/maria-objects/) keeps a different distinction: a glyph's local x3 placed at object x32 appears at logical x35. A capture can add overscan and double horizontal pixels, so capture coordinates and game coordinates need not match.
