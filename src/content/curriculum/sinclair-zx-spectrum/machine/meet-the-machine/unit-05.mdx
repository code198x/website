The Z80 can address 65,536 bytes. On a 48K Spectrum, here is what is at each of them.

## The map

| Range | What's there | Size |
|---|---|---|
| `$0000`–`$3FFF` | ROM — BASIC, the character set, the system routines | 16K |
| `$4000`–`$57FF` | Screen pixels | 6,144 bytes |
| `$5800`–`$5AFF` | Screen colour | 768 bytes |
| `$5B00`–`$5BFF` | Printer buffer | 256 bytes |
| `$5C00`–`$5CB5` | System variables | 182 bytes |
| `$5CB6`–`$FFFF` | Yours: channels, the BASIC program, its variables — and the stacks working down from the top | about 41K |

Two things are worth reading off that immediately.

The first 16K is not memory you own — it is the ROM, and it is why the machine can do anything at all when you switch it on. So "48K" describes the RAM, and the address space is 64K with a quarter of it already spent.

And the first thing in RAM is the screen. Not somewhere convenient, not at the end: 6,912 bytes of picture sit at the very bottom of the memory you were sold, because that is where the ULA reads from.

## The ULA reads the bottom of your RAM

Which connects back to unit 2. `$4000`–`$7FFF` — the whole first 16K of RAM, not just the screen — is the bank the ULA shares with the processor, and everything in it runs slower while the picture is being drawn.

That gives the 48K a shape most machines don't have. It isn't 48K of equivalent memory. It is 16K of *slow* memory with the screen at the bottom of it, and 32K of full-speed memory above `$7FFF`. A program that cares about speed puts its inner loops in the top 32K and treats the bottom 16K as the place the screen lives.

## What the ROM keeps for itself

Above the screen sit a few hundred bytes that BASIC needs and that a program is unwise to trample: the printer buffer, then the system variables — the machine's own notes about itself, including the current colours, the frame counter, and where it thinks the top of memory is.

That last one is `RAMTOP`, and on a cold 48K it starts at 65,367 — not quite the top of the address space, because BASIC reserves what's above it for its own stack and the user-defined graphics.

This is where the standard trick comes from. `CLEAR` with a lower number moves `RAMTOP` down, and everything between the new top and the old one is now memory BASIC has promised not to touch — which is exactly where you put machine code you want to survive.

None of this is enforced by the hardware. The chips do not know what a system variable is. It is all convention the ROM imposes, which is why a program that takes the whole machine over can ignore most of it, and why one that wants to call ROM routines afterwards cannot.

## What you actually get

Start from 48K. The screen takes 6,912 bytes whether you use it or not. The ROM's working area takes a few hundred more. Whatever BASIC is holding takes its share.

A machine-code program on a 48K Spectrum has something like 41K to work in, and that 41K has to hold the code, the graphics, the level data, the music and the running state — with no disk to stream from, because there isn't one.

That is the constraint behind almost every clever thing on this machine: procedurally generated levels because the levels wouldn't fit, tile-based graphics because full screens wouldn't fit, and the compression that appeared on tape loaders because *the game* wouldn't fit.

## That's the briefing

Four limits, and they interlock. A processor with a fixed number of cycles between frames, sharing its fastest-needed memory with the screen. Colour stored eight times more coarsely than pixels. Sound that costs processor time directly. And 48K to hold all of it.

Everything in the Spectrum tracks — BASIC, assembly, whichever you take — is people working inside those four numbers. You now know what they are.
