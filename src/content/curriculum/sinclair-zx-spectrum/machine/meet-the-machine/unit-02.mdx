Fifty times a second the screen is drawn, whether the program is ready or not. Everything a Spectrum program does has to fit between one drawing and the next, and that turns out to be the constraint the whole machine is organised around.

## The clock

The Z80 runs at 3.5 MHz. One tick of that clock is called a T-state, and it lasts about 286 nanoseconds. A single scan line of the picture takes 224 of them; a whole frame takes 69,888.

That last number is the budget. Divide it into the clock and you get the frame rate — a shade over fifty a second.

## Where the clocks come from

There is one 14 MHz crystal in the machine, and no separate clock for the processor or the video. The ULA takes that signal and divides it: by four for the Z80's 3.5 MHz, by two for the 7 MHz that shifts pixels out to the television.

So the ULA is the timekeeper. The processor runs at a speed the ULA hands it, and — as the next section gets to — at the ULA's convenience.

## What instructions cost

Instructions are priced in T-states. The cheapest thing the Z80 can do, copying one register into another, costs 4. Reading a byte from memory costs 7. Reaching one through an index register costs 19.

At four T-states apiece, a frame would hold about 17,000 of the cheapest instructions. Nothing is ever that tidy, but the ceiling is worth carrying around, because it says what kind of problem this is. A Spectrum program is not short of instructions. It is short of time — and those stop meaning the same thing the moment something else wants the memory.

## The ULA shares the memory

The Spectrum's 48K is not one uniform block. Addresses `$4000` to `$7FFF` — the first 16K of RAM — are what the ULA reads to draw the screen. When it is drawing and the processor reaches into that range, the processor is made to wait.

Not occasionally. Through the active picture, the wait lands on six cycles in every eight.

Memory above `$7FFF` is untouched and runs at full speed. This is the most consequential thing to know about where code sits on a Spectrum, and the reason a program that runs well can turn sluggish purely by being loaded somewhere else.

## Clearing the screen

The cost is easiest to see with a real job.

The screen's pixels occupy 6,144 bytes. Clearing them with the Z80's block-copy instruction takes about 129,000 T-states with nothing in the way — about 92% of a frame, to do one thing, once.

With the ULA contending for the same memory while the picture is drawn, that clear takes around 307,000 T-states: more than four frames, a tenth of a second, to blank the screen.

Which is why period code cleared during the border — the 12,544 T-states at the top of the frame, before the picture starts, when the ULA is reading nothing and the memory is entirely the program's. Code that ignored the distinction looked slow, and the reason was never the programmer's arithmetic.

## Why this shapes everything else

Techniques on this machine are mostly responses to that budget. Programs that move whole sprites every frame keep their code above `$7FFF`. Music drivers count T-states rather than trust a loop to take the same time twice. Much Spectrum code is in assembly at all because BASIC spends the budget before the program sees any of it.

Counting T-states is not a prerequisite for starting. Knowing they are countable is, because everything you are about to read was written by someone counting them.
