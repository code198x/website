The Spectrum has one processor, and it is busy.

## The budget

| Measure | Value |
|---|---|
| Processor clock | 3.5 MHz |
| One T-state | about 286 nanoseconds |
| One scan line | 224 T-states |
| One frame | 69,888 T-states |
| Frames per second | about 50 |

That last figure is the one every Spectrum program is written against. Fifty times a second the screen is drawn whether your program is ready or not, and 69,888 T-states is everything you get between one drawing and the next.

## One crystal, and everything divided down

There is a single 14 MHz crystal in the machine. There is no separate clock for the processor and no separate clock for the video: the ULA takes that one signal and divides it down for everything else. Divided by four it gives the Z80 its 3.5 MHz. Divided by two it gives the 7 MHz that clocks pixels out to the television.

That settles who is in charge. The ULA is the timekeeper. The processor runs at a speed the ULA hands it, and it also runs at the ULA's convenience.

## What a T-state buys

A T-state is one tick of that 3.5 MHz clock, about 286 nanoseconds. Instructions are priced in them.

The cheapest thing the Z80 can do — copy one register into another, and nothing else — costs 4 T-states. So in a whole frame, if every instruction were the cheapest available and nothing ever got in the way, you would manage about 17,000 of them.

Nothing is ever that tidy. Reading a byte from memory costs 7. Fetching one through an index register costs 19. But 17,000 is a useful ceiling to carry around, because it tells you the shape of the problem: a Spectrum program is not short of instructions, it is short of *time* — and the two stop meaning the same thing as soon as something else wants the memory.

## Something else wants the memory

The Spectrum's 48K is not one uniform block. The first 16K of it — addresses `$4000` to `$7FFF` — is the memory the ULA reads from to draw the screen. When the ULA is drawing and the processor tries to touch an address in that range, the processor is made to wait.

Not occasionally. While the screen is being drawn, the wait is applied on six cycles out of every eight.

Memory above `$7FFF` is untouched by this and runs at full speed. This is the most important thing to know about where you put code on a Spectrum, and the reason a program that runs perfectly well can become sluggish purely by being loaded somewhere else.

## What that costs, with a real job

Filling the screen.

The screen's pixels occupy 6,144 bytes. Clearing them with the Z80's block-copy instruction takes about 129,000 T-states if nothing interferes — already about 92% of an entire frame, to do one thing, once.

With the ULA contending for that memory while the picture is being drawn, the same clear takes around 307,000 T-states. That is more than four frames: a tenth of a second, to blank the screen.

Which is why period code cleared the screen during the border — the 12,544 T-states at the top of the frame, before the picture starts, when the ULA is not reading anything and the memory is entirely yours. Programs that ignored this looked slow, and the reason was never the programmer's arithmetic.

## Why this shapes everything after

Every technique you'll meet on this machine is a response to that budget. Games that move a lot on screen keep their code above `$7FFF`. Music drivers count T-states rather than trusting a loop to take the same time twice. The reason so much Spectrum code is written in assembly at all is that BASIC spends the budget before your program gets any of it.

You don't need to count T-states to start. You do need to know they are countable, and that on this machine somebody was counting.
