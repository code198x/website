Following immediately behind the guard is about to become a worse plan. At each corner it will look back, face the next corridor, and only then walk on.

Continue from **Keep a patrol moving**. We will replace the corner calculation with a table of guard positions and facings. Capture still requires contact until we add sight.

## A pause can be a record

Each record has three fields: guard column, guard row, facing. The opening record at 8200 is (7,5,1). Subsequent records describe each new phase. Near the first corner, the sequence is:

| Phase | Position | Facing | Action |
|---:|---|---|---|
| 17 | (24,5) | East | Arrive |
| 18 | (24,5) | West | Look back |
| 19 | (24,5) | South | Check the next corridor |
| 20 | (24,6) | South | Walk |

Three records share one position. Their facings tell different stories. Because each phase lasts two player updates, the stationary looks are readable parts of the patrol.

## Find the next record

phase starts at zero. Line 420 advances it; after 60 it returns to one. Line 430 uses `RESTORE 8200+10*phase`, then READ consumes the three fields. Thus phase 18 selects line 8380. RESTORE is explicit because READ otherwise carries on from wherever the last read ended.

The complete circuit has 52 walking phases and eight stationary phases. Phase 60 returns to (7,5), facing east, the same pose as the opening. Its successor is phase one, moving to (8,5). Inserting phase zero at every wrap would add an unwanted extra pause.

The program still prepares a() and b(), but the table now supplies the positions directly. Those arrays no longer drive this guard. Keeping track of which representation owns a decision matters more than the variable names left in the listing.

<Question prompt="Why can this guard look back without walking backwards?">

Its facing is an independent field. A record can change gd while keeping gx and gy unchanged. Direction no longer automatically implies displacement.
