What can the guard see from one square? Hold it at the opening position while we build an answer we can inspect. This temporary version says **SIGHT TEST** at the top; movement and corner scans return in lesson 8.

## Widen the candidate view

The guard at (7,5) faces east. Consider five successive columns in front of it. At distance one there is one candidate square; then three, five, seven and nine. This diagram shows candidates before walls remove any. It is an explanation of the rule, not a game capture.

<img src="/images/sinclair-zx-spectrum/basic/night-patrol/candidate-fan.svg" width="600" height="400" alt="An east-facing guard and five candidate columns, widening from one to nine squares." />

For a target at forward distance depth, its sideways offset runs from `1-depth` through `depth-1`. Check the path towards each candidate one forward step at a time. At step distance, the sideways displacement is `floor(offset * distance / depth + 0.5)`. Here floor means round down to an integer; Sinclair BASIC calls that INT.

Trace this rule; the following is pseudocode, not another program to type:

<pre tabindex="0" aria-label="Sight rule pseudocode"><code tabindex="0">{`For each candidate target:
    previous = guard position
    For distance from 1 through target depth:
        side = floor(offset * distance / depth + 0.5)
        sample = guard + forward * distance + sideways * side
        Reject target if sample is outside the map or in a wall
        If this step changes both column and row:
            Reject target if either square beside that diagonal is a wall
        previous = sample
    If no step rejected the target, mark it visible`}</code></pre>

Forward is (1,0) when facing east; sideways is (0,1). For any forward pair (dx,dy), the sideways pair is (−dy,dx). This rotates the same construction with the guard. Blocking either side of a diagonal prevents sight squeezing between touching wall corners. These are the game's discrete sight rules, not a claim about physically exact vision.

At the opening, (9,4) and (9,6) are visible: the fan reaches beyond its centre line. (13,5) is six columns ahead, so it is outside the range. A different example distinguishes cover from range: from (7,12) facing north, (9,9) lies inside the candidate fan, but a wall blocks its sampled path.

## Store the answer separately

We use a string v$ as a visibility mask: each position holds a space for unseen or `!` for visible. Its index is `32*row+column`, so (9,5) becomes 169. The stride is 32, matching the display's columns, even though our map is only thirty columns wide. DIM reserves 608 characters, including unused margin positions; the last map square uses index 606.

The opening mask has eleven cells. Line 8900 begins with position, facing, visible count and change count, then lists those cell indices. For this first view every change is an addition. Decode 137 as row `INT (137/32)=4`, column `137-32*4=9`: square (9,4).

## Display the mask and use it

The routine at 3000 reads the eleven cells, marks them in v$ and prints yellow paper at their screen positions. The per-square drawing routine also consults v$, so restoring a square preserves its lit background. It uses red paper under a visible player, file or entrance to keep the symbol distinct.

Line 370 checks `v$(y*32+x)="!"` after a player move, alongside contact with the guard. The program reads logical visibility. Changing a screen colour cannot make a hidden square dangerous.

RUN. The guard must stay at (7,5), facing east. Walk into the displayed fan to be spotted. Retry, then use the surrounding walls and unlit passages to fetch the file. A successful return is still possible; this diagnostic stage isolates sight, not the objective.

<Question prompt="Is every unlit square protected by a wall?">

No. Some are outside the fan's direction or range; others are candidates blocked by walls. Both are unseen now, but a turn or step can change which ones are safe.
