The challenge works. Now make it possible for someone else to arrive, understand
what to do, play again and keep a copy. Those are part of the game: a good
round is not much use if its controls or ending leave the player guessing.

Continue from [Grow a new round](../unit-06-grow-a-new-round/), with `cap=16` restored. The target
remains a stock 48K Spectrum with keyboard and beeper. We need no external art
files: the panel arrangement, marker and four note choices are already in the
BASIC source.

## Explain the controls before the first signal

Add **55** and the start-screen block at **2000–2150**:

<CodeFromFile src="sinclair-zx-spectrum/basic/bright-spark/opening/unit-07/snippets/step-01.bas" />

Line 55 jumps away before the board is drawn. The opening instructions can
therefore use the central screen without colliding with panels. They explain
the recurring action, the keys, the finishing point and how to leave. Asking
players to wait for each cue also tells them the input's actual pace.

The start loop uses the same capture-and-test approach as player input, but
accepts s or q instead of a panel number. An unrelated key returns through
the release routine before another attempt. Holding s waits at 2120; releasing
it allows the game to begin. The press that starts a game cannot leak into
its first response.

After release, `CLS` removes the instructions and line 2140 prints the title
again. The jump to **100** builds the board, then reaches the game initialisation
at 280–290. It must not jump to 10: that would send us through line 55 and back
to the start screen we just left.

Run it. Read the screen without starting immediately. Try an unrelated key,
then s. Hold s for a moment: WATCH should begin after release. On another run,
press q at the instructions to check that starting a game is optional.

## Replay without returning to the BASIC prompt

The failure and success blocks currently finish with `STOP`. Replace **1830
and 1870** with jumps to the replay prompt, and add **2200–2270**:

<CodeFromFile src="sinclair-zx-spectrum/basic/bright-spark/opening/unit-07/snippets/step-02.bas" />

Both results now share one decision. The completed count and outcome stay
visible while row 21 offers `r replay, q quit.`. Reusing this prompt keeps
failure and success equally easy to leave or retry.

The routine drains an old key before showing the prompt. Once it is waiting
for a new reading, an empty reading returns directly to 2220. A valid r is
released at 2260, then the jump to 2130 clears the old display and rebuilds the
board. An unrelated key is released and ignored; q takes the ordinary exit.

Follow the replay path through the source:

| Destination | Work |
|---|---|
| 2130–2150 | Clear the old result, print the title, jump to the board |
| 100–270 | Draw four resting panels and their labels |
| 275 | Restore the controls |
| 280–287 | Empty `s$`, reset `done` to 0, set the cap |
| 290, then 980 | Append the first choice of the new game |
| 1000 onward | Present it, then invite the player's response |

Playback and response each initialise `i` with their own `FOR` statement. The
first new input overwrites `k$`; the renderer selects its defaults on every
call. Fresh state is a consequence of these assignments and entry points,
not of naming a block “restart”.

<Question prompt="Why not replay by jumping straight to 980?">

That would append to the old sequence while keeping its completed count.
The board might look ready, but the game state would still belong to the
previous attempt. Returning through the initialisation resets both what is
stored and what is shown.

</Question>

Play, make a deliberate mistake, and choose r. The next game should begin with
one item and 0 completed rounds. Its first item may happen to match the previous
one: a fresh random choice does not guarantee a different result.

For a quick success-and-replay check, temporarily set `cap=2`, finish both
rounds and replay. Restore `cap=16` before saving the finished version. If you
keep a different cap, update the instruction at 2040 to match it. Finally
try q at a result. It should show the exit message and return to BASIC with
the intentional STOP report.

## A new game needs fresh state

Before another replay, predict which values belong to the game we are leaving and
which instructions describe every game:

| State | What replay must do |
|---|---|
| Stored order `s$` | Empty it, then append one new choice |
| Completed count `done` | Set it to 0 |
| Panel display | Rebuild four resting panels and their labels |
| Response position `i` | Start the next playback/response loop at its first item |
| Round limit `cap` | Reapply the configured limit at line 287 |

The panel layout and pitch rules are part of the program. The old random order and
completed count belong to the finished game. Replay must not preserve those merely
because their variables still exist.

Keep the normal version, then use the temporary `cap=2` test above. Predict the
starting count and order length before each of these paths:

1. Start, make a wrong choice, then replay.
2. Finish both rounds, then replay again.
3. Make another wrong choice, wait for the replay prompt, then hold r. Release it
   and replay once more.

## Check the whole experience

Give the controls to someone who has not watched you build the game. Let them
use the start screen before explaining anything aloud. Observe which messages
they notice and when they try their next press. Their questions are evidence
about the instructions; their score is not a test they must pass.

Try these specific cases as well:

- Make a wrong first-round choice. The completed count should be 0. Complete
  three rounds and fail the fourth; it should be 3.
- Hold a number during WATCH. Release it when asked, then make a fresh choice.
  Hold a valid response key: it should echo once and wait for release.
- Press an unrelated key during YOUR TURN, then a valid choice. The unrelated
  key should neither fail the round nor advance the response position.
- Hold q during playback, during a response wait and at a result. During a
  cue, allow its note and repaint to finish. Use one key at a time; do not
  rely on simultaneous-key chords.
- Turn sound off. The labels, asterisks, status and result must still explain
  what is happening. Compare the panels without relying on hue: the active
  marker carries information that colour alone cannot.

There is no input queue during a cue. If someone naturally types the whole
response ahead of the echoed signals, discuss the pace and make the instruction
clearer. Accepting buffered typing would require a different input design;
a longer `PAUSE` alone would not add a queue.

## Refine the signals with a reason

Our note values are 0, 4, 7 and 12. Try changing the third panel's pitch at
**610** from 7 to 9, leaving its visual identity unchanged. Compare how easily
you distinguish the four sounds. There is no required melody to imitate: the
notes form a vocabulary of choices. Restore 7 or keep a tested alternative.

You can also compare `BEEP 0.1,note` with the current `BEEP 0.15,note` at **920**.
Does the shorter cue remain easy to recognise? Check identical neighbouring
choices and held-key playback again after a timing change. Shorter is useful
only if people can still separate the events. Restore 0.15 for the supplied
finished version.

Keep the permanent digits outside the repaint areas and retain the asterisk.
The original colour associations help orientation; neither brightness nor
colour alone should be the only way to identify an active choice. When you
alter one thing, check the behaviour it was supporting.

## Save a recoverable finished game

Save the finished program with `SAVE "spark16"`, using a different tape name
from the earlier `spark` checkpoints. Export the recording as a host file,
then reopen it in a fresh session with `LOAD "spark16"` and `RUN`.
The [tape-saving guide](/systems/sinclair-zx-spectrum/basic/meet-basic/unit-02-remember-and-save/)
covers the recording prompt, export and platform-specific controls.

The name inside the tape and the host filename are different things. An
export can contain earlier recordings too, so distinct program names help
you recover the intended version. A successful SAVE report alone does not
prove that you can load the right program again.

You should arrive at the start screen. Play a round, reach a result, replay
and quit. This checks the recovered program's behaviour, not just its presence.
The `.bas` listing is readable source; the `.tap` file contains tape data the
Spectrum loads. Keep both when sharing your work, with a short note naming
the 48K target and the controls.

### A small handover check

We can use the [supplied finished tape](/experiments/bright-spark/spark16.tap)
as a recovery copy alongside the source below. Its target is a **48K PAL
Spectrum**. Load the named program with `LOAD "spark16"`, start tape playback,
then enter `RUN` after loading. This tape does not start the game automatically.

Write a short note for someone who has not watched us build it: release keys,
press and release **s** to start, repeat the order with **1–4**, **r** to replay
at a result, and hold **q** to quit. Explain that we wait for each echoed cue
before the next press; a brief press during a cue can be missed.

From a fresh load, deliberately choose a different panel in round one. We
should see zero completed rounds. Replay, complete one round, then make a
mistake in round two: the count should be one. Replay again and check that it
returns to zero, the order starts with one choice and every panel rests before
our turn. Try without sound too. The digits, asterisks and result text must
still let us follow what happened.

That checks more than whether the game starts. It checks which state belongs
to one attempt and whether we restore it. Keep the source, tape, controls,
target and known limitations together. Record the emulator and model actually
used; testing there is not evidence of a run on original hardware. Further
ideas can wait once our agreed completion checks pass.
