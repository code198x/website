signals. The string will supply the choices; the cue routine already knows how

characters of `s$` in order.

Line 280 still sets `s$="314"`. The new line 290 replaces the diagnostic order
with WATCH. Since `RUN` clears the screen at line 40, the old length and
first/last diagnostics disappear too.

`FOR i=1 TO LEN s$` visits every position in the string. `i` means **which item
we are visiting**. For this order it takes the values 1, 2 and 3.

The cue needs a numeric `p`, while `s$(i)` supplies a one-character string.
`VAL s$(i)` evaluates that text as a numeric expression. For our stored digits,
`VAL "3"` produces the number 3.

`VAL` can evaluate more than a single digit. It is not a test that arbitrary
text is a safe panel choice. Here we wrote the string ourselves and know that
every character is one of `"1"`–`"4"`. Player input will need checking before
conversion.

| `i` | `s$(i)` | Numeric `p` | Cue |
|---|---|---|---|
| 1 | `"3"` | 3 | Lower-left panel |
| 2 | `"1"` | 1 | Upper-left panel |
| 3 | `"4"` | 4 | Lower-right panel |

`GO SUB 900` plays that panel's cue and returns to `NEXT i`. The next loop visit
reads another character. When all three have been visited, execution reaches
`STOP` at 330.

Run it. Expect 3, 1, 4, with every panel returning to rest. The printed order
has gone: the signals now carry the information the player must remember.

<Question prompt="Why not use p as the loop counter again?">

The old demonstration used panel numbers in counting order, so `FOR p=1 TO 4`
was useful. Now the position and panel number can differ. At position 1 the
panel is 3. Keeping `i` and `p` separate lets the sequence contain any order,
including repeated choices.

The renderer still uses `r` to fill its rows. Changing `i` inside that routine
would disturb the caller's traversal. The cue changes drawing values and
`lit`; it leaves `i` and `s$` alone.

</Question>

## Make two identical choices distinguishable

Replace the quoted text on line **280** with `"22"` and run again. We should
see **two** activations of panel 2, with its asterisk disappearing between
them. Two different locations would reveal the change of choice even with
poor pacing; two identical locations reveal whether the event has an end.

The cue routine already supplies that end. Lines 930–940 repaint the panel at
rest, and line 950 requests an extra ten frames of silence. We keep that
resting interval instead of adding another delay in the caller. At 50 Hz,
ten frames are a fifth of a second; a held or newly pressed key can shorten
`PAUSE`, and BASIC drawing takes time as well.

Try the same order while holding a number key. The extra pause may shorten,
but each note still finishes and the renderer still removes the marker before
the next cue. This is the pacing choice we made in lesson 2. It is not a
promise that every cue takes an identical amount of time.

Listen as well as watch when sound is available. The notes for `"22"` have the
same pitch, but should be separate events. With sound off, the two appearances
of the asterisk must still make sense. If they merge into one long highlight,
check that lines 930–950 remain in the cue routine.

Try `"1234"` to check every position and note association, then restore line
280 to `s$="314"`. We are choosing predictable test data before introducing
chance.

an ordinary quit route now. Add **295, 305, 325 and 1900–1920**:

<CodeFromFile src="sinclair-zx-spectrum/basic/bright-spark/opening/unit-04/snippets/step-02.bas" />

`INKEY$` reads the keyboard and gives text: a recognised character, or the empty
string `""` when no character is returned. We compare that reading with lower-case `"q"`. This direct test
uses one reading; it does not read again to decide what the key was.

`GO TO` transfers
execution to the named line without saving a return point. That suits quitting:
we do not want to return to the loop afterwards. `GO SUB` saves a return point
because a routine is expected to finish and hand control back.

Line 305 checks before every cue. Line 325 checks after the final cue too.
**Hold q until the program finishes.** BASIC cannot check it while executing
`BEEP` or the renderer. A short tap entirely inside a cue can be missed; a
held q is seen at the next check. The extra pause can also shorten while q is
held, but the note and repaint still finish.

The quit block prints a clear message, clears the reserved bottom status row
and stops. Trailing spaces erase longer text already on that row. They do not
change the panel labels, which have their own rows.

Run once without pressing a key, then run again and hold q during a cue.
Expect `Finished. RUN to try again.` and the intentional STOP report. The
active panel should have returned to rest before the quit message appears.

## Compare a longer cue

Keep the working version before this temporary experiment. First run the stored order
without touching a key. Then run it again and hold q as the first panel becomes active.
Watch when the panel returns to rest and when the quit message appears.

Predict what will change if we replace only line 920 with:

```basic
920 BEEP 0.45,note
```

Keep the pitch, stored order and `PAUSE 10` unchanged. Repeat the no-key run, then
the held-q run. Does the longer highlight make the choice easier to follow? Does
waiting to quit make the program feel less responsive? We can prefer different cue
lengths while agreeing about the order of instructions.

<details>
<summary>Explain the comparison</summary>

The requested note lasts 0.30 seconds longer. The active panel also lasts longer,
because the routine restores it only after `BEEP` finishes. Our next `INKEY$` check
still waits for the cue to return. We have changed one number, but its position in
the routine affects sound, picture and input response together.

This does not mean every held-q run takes exactly 0.30 seconds longer to quit.
The moment we press matters, and a held key can shorten `PAUSE`. Drawing and BASIC
instructions also take time. The no-key run helps us compare the intended rhythm;
the held-key run asks a different question about response. Neither is a precise
latency measurement.

</details>

Try the no-key comparison with sound muted too. The panel positions, digits and
asterisks should still communicate the order. Describe what the note adds when it
returns: another way to identify a panel, a clearer rhythm, or perhaps more sound
than we need. We need not make cues flash faster or louder to make them clearer.

Restore `920 BEEP 0.15,note` before saving. Run the order normally and check that
holding q still exits with every panel at rest. Later games may need to service
input while sound continues; this memory game lets us understand the sequential
version first.

<Question prompt="Would checking only at line 305 catch q held during the last cue?">

No. After that cue, `NEXT i` finishes the loop and execution no longer visits
305. Line 325 covers this boundary. A check that works between items can still
miss the transition out of the whole sequence.

</Question>
