## Debouncing with INKEY$

Lines 260–270 look redundant but both are essential:

- Line 260: `IF INKEY$ <> "" THEN GO TO 260` — wait until **no** key is held down.
- Line 270: `IF INKEY$ = "" THEN GO TO 270` — wait until a key **is** pressed.

Why both? Imagine the player presses "2" for the first digit. Without line 260, the program immediately reads "2" again for the second digit — the key is still held down. Line 260 waits for the player to release the key before line 270 waits for the next press. One loop drains, the other fills.

Line 280 captures the key into `k$`. Line 290 rejects anything that is not "1" to "4" — it compares the key *as a character* and jumps back to the release-wait, so pressing "Q" or "7" does nothing. Line 300 then converts the validated key to a number with `VAL`.

The order matters. `VAL` reads its string as a number, and handing it a stray letter would stop the program with an error. Screening the key as a character first — before `VAL` ever sees it — is what keeps a fumbled key press from ending the game.

## Try it

Run the program. Watch the sequence flash, then press the matching keys. The panels flash as you press them — the same `GO SUB 640` subroutine handles both the computer's turn and yours.

Try holding a key down. The debouncing means it only registers once. Now delete line 260 and hold a key — the same digit repeats for every position in the sequence. That single line is the difference between responsive input and chaos.
