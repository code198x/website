Lines 900–905 hold the level. The first DATA line gives the width and height (5,5). The next five lines are strings — `"WWWWW"`, `"W . W"`, and so on — where each character represents a cell: W for wall, space for floor, `.` for target, C for crate, P for player. Line 100 reads the dimensions. Line 150 creates a 2D array `g(h,w)` to hold the grid. The nested loop at lines 200–300 reads each string, picks out each character with `r$(c TO c)`, and writes a number into the array: 1 for wall, 2 for target, 3 for crate. The player's position is stored in `pr` and `pc` instead of the array — the player is not a cell type, but a cursor that moves over cells.

Each character also triggers a PRINT AT with a PAPER colour: blue (1) for walls, white (7) for floor, red (2) for targets, yellow (6) for crates, and green INK (4) for the player letter "P". Lines 120–130 centre the grid on screen by computing offsets `sr` and `sc` from the level dimensions.

## The array is the level

In Sonar, you used a 2D array to track guesses on a pre-existing grid. Here the array *is* the world. Every wall, every floor tile, every crate and target exists as a number in `g(r,c)`. The screen shows PAPER colours, but those are just the display. The array is the authority. When a crate moves later, the array changes first and the screen follows.

This separation — data first, display second — is the architectural idea behind the whole game. The DATA strings are the level design. The array is the live game state. The PRINT statements are the rendering layer. Three roles, clearly divided.

## Why strings, not numbers?

The DATA could have been rows of numbers: `DATA 1,1,1,1,1`. But strings are more readable. `"W . W"` looks like a room. You can sketch a level in a text editor, count the characters, and paste it straight into DATA. The parsing loop at lines 230–280 converts the human-readable format into the machine-readable one. A small cost in code for a large gain in level design.
