Push a crate into a corner and it is stuck forever. Without a restart key, the player's only option is to break out and re-run the program.

Line 153 checks for R after the debounce loop: `IF k$ = "r" OR k$ = "R" THEN GO TO 50`. That single line is the entire restart mechanism. It jumps back to line 50, where RESTORE recalculates the DATA position for the current level (because `lv` has not changed), READ pulls in the level dimensions, DIM re-creates the array from scratch, and the parsing loop redraws the grid from DATA. Every crate returns to its starting position. Every target is uncovered. The player is back at the start.

No state needs to be manually cleared. DIM zeros the array. CLS wipes the screen. The DATA is immutable — it never changes, so re-reading it always produces the original layout.

## Why puzzles need restart

In an action game, mistakes cost a life. In a puzzle game, mistakes cost time — and sometimes they are invisible. A crate pushed into a corner cannot be retrieved, but the player might not realise the level is now unsolvable until several moves later. Without restart, frustration replaces thought. With it, the player can experiment freely: try a path, discover it fails, press R, try again.

Restart changes how people play. Instead of cautious single attempts, players explore. They push a crate speculatively, see what happens, and reset if it goes wrong. The level becomes a laboratory, not an exam. This is particularly important for level 3, where two crates interact and the solution is not obvious on first sight.

## The immutability of DATA

The restart works because DATA is read-only. The program reads from DATA into variables and arrays, but never writes back. The array `g()` is the mutable working copy. The DATA is the immutable master. RESTORE plus READ reconstructs the master copy at any time. This is the same relationship a saved game has to a running game — one is the checkpoint, the other is the live state.
