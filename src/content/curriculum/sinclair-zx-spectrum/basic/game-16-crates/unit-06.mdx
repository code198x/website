The player can push crates onto targets. But the game does not notice when the puzzle is solved.

Lines 650–720 add the win check, running after every push. Line 660 sets `win = 1` (assume victory). The nested loop at lines 670–710 scans every cell in the array. Line 690 checks for value 2 — an uncovered target. If any cell is still 2, the puzzle is not solved: `LET win = 0`. Line 720 tests the result: if `win` is still 1, every target is covered and the level is complete. Lines 730–740 print the message and wait for a key press.

The check only runs after a push (it sits inside the push routine, after line 620). Normal movement cannot change the win state — only pushing a crate onto or off a target can.

## Searching for absence

The win condition is not "all crates are on targets" but "no target is uncovered." These sound identical, but the code searches for the second form. It looks for value 2 (bare target) rather than counting crates in value 4 (crate-on-target). If a single value-2 cell exists anywhere in the array, the puzzle is unsolved.

This is a scan-for-absence pattern. Start optimistic (`win = 1`), scan for a disqualifying condition, and flip the flag if you find one. The loop always runs to completion even after finding the first uncovered target — Spectrum BASIC has no way to break out of a FOR loop early. On a 5x5 grid, scanning all 25 cells is instant. On larger puzzles, the redundant iterations still cost almost nothing.

## Why the array matters again

The win check does not look at the screen. It does not check PAPER colours or character positions. It reads the array — the same `g(r,c)` that the level loader created, the collision code queried, and the push logic updated. One data structure serves loading, display, collision, push mechanics, and now victory detection. That is the return on the investment made in Unit 1.
