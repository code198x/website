A dungeon without monsters is a walking simulator. This unit populates each floor with creatures that the player must fight or avoid. Monsters are stored in parallel arrays — one for x position, one for y position, one for type, one for HP. They appear as red `M` characters in the viewport, blocking the player path.

## How It Works

**Lines 22** dimensions four monster arrays: `j(5)` for x positions, `k(5)` for y positions, `l(5)` for monster type, and `n(5)` for current HP. Up to 5 monsters can exist on a floor.

**Lines 120-134** place monsters after the dungeon generates. The number of monsters (2-4) is chosen randomly. For each monster, the subroutine at line 1600 finds an empty floor cell, and the subroutine at line 1700 picks an appropriate monster type based on the current floor.

**Lines 1600-1610** find an empty cell. It picks random coordinates and checks that the cell is floor (value 0) and not the player position. If not, it tries again. This loop always terminates because the dungeon always has more floor cells than monsters.

**Lines 1700-1730** select a monster type. On floors 1-3, only rats and goblins appear. Floors 4-5 add skeletons. Deeper floors introduce trolls, wraiths, and eventually the dragon on floor 10. The subroutine reads the chosen monster DATA to set its HP.

**Lines 1500-1512** hold the monster DATA. Each entry has a name, HP, attack, defence, and gold reward. Six monster types scale from the humble rat (4 HP, 1 attack) to the fearsome dragon (30 HP, 6 attack, 4 defence).

## Parallel Arrays

Monsters are stored across four separate arrays that share the same index. Monster 1 has position `j(1), k(1)`, type `l(1)`, and HP `n(1)`. This parallel array pattern is how BASIC handles what other languages would represent as a struct or object. The arrays are not linked by the language — the programmer must ensure they stay in sync by always using the same index.

## Monster Visibility in the Viewport

**Lines 322-326** in the viewport renderer check each cell against the monster arrays. For every viewport cell, a loop checks all monsters. If a monster with HP greater than 0 occupies that cell, it renders as a red `M` (INK 2). This is not efficient — every viewport cell checks every monster — but with only 5 monsters and a 7x7 viewport, the cost is negligible in a turn-based game.
