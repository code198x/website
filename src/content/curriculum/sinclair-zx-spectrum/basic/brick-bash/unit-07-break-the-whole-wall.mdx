## Reconnect the query

At line 440, tx/ty receives nx and the old y. The query returns hit and, when hit is 1, a valid br/bc. On a horizontal hit, reverse dx, reject the horizontal displacement and call the removal routine while that address still identifies the brick.

Then line 460 supplies the resolved nx and proposed ny for the vertical check. This query may return a different brick address. Remove it immediately if hit is 1, before another query can overwrite br/bc.

The variables form a small contract:

| Routine | Receives | Returns or changes |
|---|---|---|
| 2000: query | tx, ty and the current g array | hit; br/bc identify a live brick only when hit=1 |
| 2500: remove | Valid br/bc from a successful query | g, left, the brick picture and the count |

These are shared BASIC variables, not private subroutine parameters. The caller must supply the inputs and use the answer at the right time.

## Keep the count honest

Removal sets g(br,bc) to zero before another contact query. It then subtracts one from left and prints spaces at that brick's character position. A repeated visit to an empty slot returns hit=0, so it cannot subtract again.

The count printed at column 28 is followed by a space. When 10 becomes 9, that space clears the old second digit. Without it, the display could read 90 even though the stored count is nine.

Line 480 ends the round when left reaches zero. It runs before erasing the old ball and committing another move. The final brick disappears, the message changes, and the valid ball position freezes.

## Play through the spaces you made

RUN, move and serve. A return still preserves the ball's horizontal direction. The ball can pass through a removed brick's former position and reach another part of the wall. It is possible to clear all eighteen at this stage; aiming in the next lesson gives the player another decision, rather than making destruction work at all.

Try a miss and retry. All three rows and BRICKS 18 must return, with the ball waiting above the centred paddle. A fresh DIM and the initialisation loops rebuild the state instead of relying on values left from the previous attempt.

If the ball bounces off empty space, compare the erased picture with g at that address. If the count decreases twice, check that removal changes g before the second axis query. If the ball flickers after a contact, check that rejecting an axis changes nx or ny, while x/y remains unchanged until the commit.

The stage now does more work than the one-brick game. Its speed is a property of this BASIC loop and configuration, not a fixed frame rate promised by a timer.
