## Eighteen remembered states

`DIM g(3,6)` creates three rows of six numeric entries. The nested loops put 1 in every entry: each brick starts live. left begins at 18. When a hit removes a brick, its entry becomes 0 and left decreases by one.

The drawing loops use the same row r and column c. `PRINT AT 2+2*r,4*c` spaces each three-character brick within a four-character pitch. A blank character column separates neighbours, and a blank character row separates brick rows. inkcol chooses yellow, magenta or cyan for the row; it never decides contact.

| Brick row r | PRINT row | Pixel bottom | Pixel top |
|---|---|---|---|
| 1 | 4 | 136 | 143 |
| 2 | 6 | 120 | 127 |
| 3 | 8 | 104 | 111 |

A brick's pixel left is 32*c and its right is 32*c+23. The 32 comes from four character columns of eight pixels. Its bottom is 152−16*r: each brick row moves sixteen pixels down. Its top is seven pixels above that bottom.

## Find a possible address

Routine 2000 converts tx/ty into a candidate row br and column bc. `INT` rounds down to an integer. In the column calculation, subtracting 32 measures from the first brick's left edge and dividing by 32 counts horizontal pitches. Adding one changes a zero-based count into array columns 1–6.

The calculation uses **tx+1**, the ball's rightmost pixel. A ball beginning at x=31 can touch the first brick at x=32. Using only tx would wrongly put that contact before column 1.

For rows, `143-ty` measures downwards from the first brick's top. Divide by the sixteen-pixel row pitch, take INT and add one. Remember that pixel y grows upwards while brick row numbers grow downwards.

An address is only a possibility. It may describe a gap or lie outside the wall.

## Bounds, gaps, then state

Line 2010 rejects br outside 1–3 and bc outside 1–6 before reading g. An invalid subscript must not reach the array.

Line 2020 rejects the spaces between bricks. If the ball's upper pixel ty+1 is below that row's bottom, it is in a vertical gap. If its left pixel tx is beyond that column's right edge, it is in a horizontal gap. The address calculation has already selected the other two edges of the possible rectangle.

Line 2030 rejects an entry that is already zero. Only after all three kinds of rejection does line 2040 return hit=1.

## Probe the edges

Try these pairs in order, confirming each number with Enter:

| Ball X | Ball Y | Expected result |
|---|---|---|
| 30 | 136 | No hit; ball ends at 31 |
| 31 | 136 | Row 1, column 1 hit and removed |
| 31 | 136 | No hit; that brick is now absent |
| 56 | 136 | No hit; horizontal gap |
| 64 | 134 | No hit; below row 1 |
| 64 | 135 | Row 1, column 2 hit by the upper pixel |
| 255 | 175 | No hit; outside the wall |

The report shows the candidate address even when it is outside the array. HIT distinguishes an actual live brick from that preliminary calculation. A hit also removes the brick, so the order of probes matters. Enter -1 at the X prompt to leave; RUN restores all eighteen bricks.

<Question prompt="Why does a sensible row and column not prove that a brick was hit?">

The ball may be in the blank space within that row or column pitch. Even after the gap checks pass, the brick may already have been removed. Address, overlap and stored state are separate questions.

</Question>

If you get a subscript error, check that the bounds RETURN comes before g(br,bc). If a gap removes a brick, check the two comparisons at 2020 rather than adjusting the artwork. This lookup relies on our regular spacing and small ball; it is not a general search for arbitrary rectangles.
