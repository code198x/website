## Three characters, one rectangle

The brick uses custom characters a, b and c, codes 144–146. The middle is eight rows of 255. The left end uses 127 for its first and last rows and 255 between them; the right uses 254 at its ends. Those missing outer corner pixels soften the shape.

The loader now begins at DATA line 7200 and fills all 48 bytes for the six characters. The existing paddle data follows the three new brick characters. b$ joins the brick's left, middle and right pieces.

PRINT AT 8,24 places this brick at character row 8, column 24. Its logical rectangle is **x=192–215, y=104–111**. Collision includes the tiny unlit corners. That is a choice about the game's shape, not a test of ink colour.

## Ask before changing

`alive=1` means the brick remains. The query routine at 2000 accepts a candidate ball position in tx and ty. It starts with hit=0, returns immediately if the brick is gone, and rejects separation on either axis. If none of those rejections applies, hit becomes 1.

For the vertical check, the ball spans ty to ty+1. For the horizontal check, it spans tx to tx+1. `RETURN` leaves the query with its answer; the query itself does not erase the brick or alter the ball.

## Resolve one axis, then the other

Line 440 tests the proposed horizontal position at the **old height**: tx=nx, ty=y. On contact, line 450 reverses dx, rejects that horizontal displacement by restoring nx=x, and removes the brick.

Line 460 then tests the resolved horizontal position at the **proposed height**. On contact, line 470 reverses dy and restores ny=y before removing the brick.

This order settles diagonal corners. Suppose the ball is at (191,100) and proposes (195,104). The horizontal test at (195,100) is below the brick. The vertical test at (195,104) hits, so y stays 100 and dy reverses. This is a discrete game rule, not an exact calculation of a billiard ball's path.

<Question prompt="If the horizontal test removes the brick, can the vertical test remove it again?">

No. Removal sets alive to 0. The next query returns with hit=0 before testing the rectangle, so the same brick cannot be removed twice.

</Question>

## Make removal visible

Routine 2500 changes the stored flag and remaining count, prints three spaces over the brick and updates the count. State and display change together. The result check at 480 runs before the next ball position is committed, so a win freezes the previous valid ball position.

RUN, serve and break the brick. Retry and serve from another paddle position to change the approach. Watch the count become zero once. A miss should still offer R/Q, and retry must restore the brick.

If an invisible brick keeps bouncing the ball, check alive at removal. If the picture stays after a win, check the erase position at line 2510. Keep the movement size at four pixels while testing these rules; larger steps would need a fresh check for jumping across objects.
