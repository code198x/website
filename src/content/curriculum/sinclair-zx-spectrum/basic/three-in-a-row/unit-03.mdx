The player places crosses, but nothing yet notices a win. "Three in a row" means one of eight
lines — three rows, three columns, two diagonals — holds the same mark in all three cells. Instead
of writing eight checks by hand, store the eight lines as data and scan them in a loop. That table
is the first new idea: the program **reads** the board.

## The lines as a table

Lines 1200–1220 list the eight winning lines as `DATA` — three rows, three columns, two
diagonals — each a triple of cell numbers. You used `DATA` as a list of words in Cipher and reset
it with `RESTORE` to a line number in Quiz Master; here it holds the *structure* of the game. The
code knows nothing about rows or diagonals — it only knows "these three cells form a line", and
the table supplies which three.

## Scan the table

The win-check is a reusable `GO SUB` (lines 420–490). `RESTORE 1200` rewinds to the table, then
`FOR w = 1 TO 8` reads each triple `p, q, f` and tests it: `IF b(p) <> 0 AND b(p) = b(q) AND
b(q) = b(f)` — three matching, non-empty cells means a winner, and `b(p)` says who. Calling it a
subroutine matters because *both* sides will use it — the player's move checks it now (line 300),
and the computer's move will check the same routine later. Writing the rule once, in `DATA` and a
loop, is what makes the rest of the game tractable.

The board can now be read. Next: an opponent that reads it to decide where to play.
