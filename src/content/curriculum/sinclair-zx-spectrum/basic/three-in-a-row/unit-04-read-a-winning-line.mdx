Play 1, 4, 2, 5, 3. X completes the top row on move five. The game should stop accepting moves, report X as the winner and draw a yellow line through the three crosses. R begins again.

## Eight triples

Lines 9500–9520 hold the three rows, three columns and two diagonals. READ p,q,f takes the next three values from that list. These are square numbers, so b(p), b(q) and b(f) find their contents.

Every scan starts with `RESTORE 9500`. READ remembers its position between calls; RESTORE returns it to the beginning of the winning table. Without that reset, the next move would continue beyond the data we intended to scan.

The condition requires b(p) to be nonzero as well as equal to the other two values. Otherwise three empty squares would count as a winning line. AND requires all the comparisons to hold. `winner` records the mark; `wl` records which of the eight triples matched. They are reset on each scan. NEXT is on its own line so it runs even when the IF is false.

## A win can also fill the board

After drawing an accepted mark, the program checks the board. It ends when winner is nonzero **or** moves reaches nine. The result routine begins with a draw message, then replaces it when X or O has won. This makes a win on the last square a win, not a draw.

The highlighting routine reads as far as the winning triple, converts its first and last squares to pixel centres, then draws between them. DRAW needs a displacement, so we subtract the starting centre from the ending centre. The marks remain visible underneath the line.

<Question prompt="What is wrong with checking only whether b(p), b(q) and b(f) are equal?">

At the start, every square contains zero. All eight triples would match. Equal values establish a win only when those values belong to a player.

</Question>

Try 1, 2, 3, 5, 4, 6, 8, 7, 9. It fills the board without completing a line and should report a draw. If the first game works but a later scan fails with a DATA error, inspect RESTORE before changing the table.
