## Two directions, one decision

`dr,dc` describe the current heading. `nd,nc` hold the pending heading. For example, moving right is (0,1), while turning up requests (−1,0). Rows grow downwards, so up subtracts from the row.

While moving horizontally, `dr=0`, so the program can accept I or K. While moving vertically, `dc=0`, so it can accept J or L. Continuing in the same direction needs no change. The opposite direction is ignored; soon there will be a neck behind the head.

The first accepted perpendicular turn sets `turn=1`. Line 180 then skips further direction requests until movement occurs. R and Q are checked before this lock, so they still work. At line 270 the pending direction becomes current; line 460 clears the lock for the following move.

Without that lock, a quick up-then-left request while travelling right could turn through two directions before the head moved, effectively reversing it. We accept one turn for one movement update.

## Show the heading

The graphic DATA now fills five consecutive characters: wall, up head, right head, down head and left head. The head routine starts with code 146 for right, then selects 145 for up, 147 for down or 148 for left. These are character codes, distinct from the eight row bytes that draw each face. The other faces use the same rounded outline with the eye pixels facing the relevant direction; compare their DATA rows before changing them.

<Question prompt="Moving right, you request up and then left before the next move. Which square should the head enter?">

The square above it. Up is the first perpendicular request and locks the pending turn. Left must wait for a later update.

Try a long hold, a short tap, an unrelated key and an opposite direction. `INKEY$` reports a key when the program reads it; it does not store every tap made between reads. With multiple ordinary keys held, do not expect a direction chord. Hold one key at a time and check that turning remains predictable.
