## Propose, check, then draw

Line 110 starts at row 8, column 9. `dr=0` and `dc=1` mean no row change and one column to the right. Line 280 computes `nr` and `nx`, the proposed next row and column. It has not moved the head yet.

Line 290 rejects coordinates outside rows 1–16 or columns 1–24. The result routine displays the wall message and waits for R or Q. A rejected move leaves the last valid head visible.

For an accepted move, line 400 erases the old cell and stores the new coordinates. The routine at 3000 draws the head there. Only the changing cells need drawing; clearing the whole screen on every move would redraw walls that have not changed.

## Wait while checking keys

`PEEK 23672` reads the lowest byte of the Spectrum's FRAMES counter. In this PAL configuration it advances fifty times per second during ordinary program execution. The program stores a reading in `tick`, then subtracts it from a later reading. While fewer than **18 ticks** have elapsed, it returns to line 150 and checks keys again.

That byte counts from 0 to 255 and then returns to zero. If `tick` was 250 and the new reading is 5, the subtraction gives −245. Adding 256 gives **11 elapsed ticks**. Line 250 makes this correction. The method assumes we sample again before 256 ticks have elapsed; it is not a general clock for long pauses.

The threshold is a minimum wait, not a promise of one move every 18 ticks. BASIC still has input, decisions and drawing to perform. Line 270 records the next starting time before that movement work. If the work takes longer, the program cannot recover the lost time by pretending it was faster. Tape operations and BEEP also affect this ROM clock; this game's moving loop is silent and does neither.

<Question prompt="Does reaching 18 ticks mean the head has already been drawn at its new position?">

No. It permits the program to leave the waiting loop. The candidate calculation, boundary check and drawing follow it.

</Question>

Run without touching the keyboard: the head should stop at the right edge. Retry, then hold Q. If the wall message instantly disappears on a retry attempt, release all keys first: the result routine deliberately waits for release before accepting a new R or Q.
