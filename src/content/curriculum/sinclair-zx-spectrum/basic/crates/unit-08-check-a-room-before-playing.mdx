A readable map is inviting to edit. It also makes it easy to lose a character or place two players. We will check the format before the game uses it.

Line 4005 resets three counts and clears `e$`, the error message. Line 4015 checks `LEN m$` before the column loop indexes the string. A short or long row returns immediately with an explanation. Line 4095 does the same if no symbol matched and `v` is still -1.

`RETURN` here leaves the loader, not the entire program. Line 21 checks the message before counting targets or drawing a playable room. An error goes to 4500, which displays the room, the message and a row number when the failure occurred within a row, then stops. Although part of the array may have been filled, input cannot reach it.

The cell loop counts players, crates and goals. P and + each count as a player. Codes 3 and 4 each count as a crate; codes 2 and 4 each count as a target. After all rows, the loader requires exactly one player, at least one crate and equal crate and target totals. The final goal check states that requirement too; with positive crates and equal totals, it is already satisfied.

## Try mistakes one at a time

After each experiment, restore the original line and RUN again. These changes are temporary map data, not additions to the game:

| Temporary edit | Expected result |
|---|---|
| Line 8010: remove one dash inside the quotes | Eight-symbol row error, row 2 |
| Line 8010: add one dash | The same length error, row 2 |
| Line 8010: replace one dash with `?` | Unknown-symbol error, row 2 |
| Line 8050: replace P with a dash | Exactly-one-player error |
| Line 8010: replace one dash with P | Exactly-one-player error |
| Line 8040: replace C with a dash | At-least-one-crate error |
| Line 8010: replace one dash with a dot | Crate/target count mismatch |

The original lines are in the complete program above. RUN after restoring all of them; the original room should play normally.

A missing DATA statement is different. READ can run out of values before our checks can run, and the ROM reports **Out of DATA**. This validator is not a general BASIC error handler. Check that all eight map lines exist and that RESTORE selects the right section.

<Question prompt="A map has eight rows of eight recognised symbols, one player and equal positive numbers of crates and targets. Must it be solvable?">

No. Those checks establish a usable structure, not a route through the puzzle. A crate could be trapped in a corner or a target cut off. We still need to solve and play an edited room.

</Question>

Combined symbols matter to that distinction too. `*` contributes both a crate and a target; `+` contributes a player and a target. A structurally valid map with every crate already delivered starts completed because line 86 sees zero uncovered targets. A malformed map never reaches that line.

If the program enters play after an error, check line 21. If a bad row produces a subscript error instead of our message, check that the length test precedes `m$(c)`. Good diagnostics happen before the operation that would fail.
