Line 4005 resets three counts and clears `e$`, the error message. Line 4015 checks `LEN m$` before the column loop indexes the string. A short or long row returns immediately with an explanation. Line 4095 does the same if no symbol matched and `v` is still -1.

`RETURN` here leaves the loader, not the entire program. Line 21 checks the message before counting targets or drawing a playable room. An error goes to 4500, which displays the room, the message and a row number when the failure occurred within a row, then stops. Although part of the array may have been filled, input cannot reach it.

The cell loop counts players, crates and goals. P and + each count as a player. Codes 3 and 4 each count as a crate; codes 2 and 4 each count as a target. After all rows, the loader requires exactly one player, at least one crate and equal crate and target totals. The final goal check states that requirement too; with positive crates and equal totals, it is already satisfied.

## Investigate one row

Keep the complete working program above as our recovery copy. We will change **only line 8010**, leaving the loader and drawing code alone. If the game is running, press Q to return to BASIC before editing.

First establish the working case:

```basic
8010 DATA "#------#"
```

Enter `RUN`, then press S at the title. Check that the room appears with one player, one crate and one target. Make one legal move, then press R: the original positions and zero steps should return. Press Q before the next edit.

Now predict each result **before running it**. Count the symbols inside the quotes; the quotes themselves are not map cells.

| Case | Line to enter | Our prediction | Observed message and row |
| --- | --- | --- | --- |
| Valid control | `8010 DATA "#------#"` | Room plays | Record the working result |
| Short row | `8010 DATA "#-----#"` | Write this before RUN | Record what actually appears |
| Unknown symbol | `8010 DATA "#--X---#"` | Write this before RUN | Record what actually appears |

For each faulty case, enter its line, `RUN`, and press S. Does the game draw a playable room, or stop with a message? Record the exact message and row number. The error screen stops in BASIC, so we can edit the line there.

Restore the valid line and run it successfully **between the two faults**, and once more after the last fault. That gives us a working comparison each time, rather than letting one broken edit influence the next investigation.

Before opening the explanation, choose a hypothesis: is the loader rejecting the row's **length**, rejecting a **symbol**, or accepting data that the drawing routine cannot display? Which observed message would support or contradict that explanation?

<details>
<summary>Compare our evidence and repair</summary>

The short row has seven symbols. Line 4015 sets `e$` to **Use eight symbols per row.** and returns before indexing its characters. The screen reports **Row 2**.

The X row has eight symbols, so it passes the length check. At column 4, X matches none of the supported symbols, leaving `v` at -1. Line 4095 sets **Unknown map symbol.** and returns. The screen again reports **Row 2**; this version reports a row, not the column. We locate column 4 by inspecting the DATA ourselves.

Neither case reaches room drawing or movement: line 21 directs the returned error to the diagnostic screen. Some earlier cells may already be in `g()`, but the program does not offer that partial room for play. We have evidence of a data-format fault, so changing colours or movement code would not repair its cause.

For each case, restore `8010 DATA "#------#"`, then `RUN` and S. Check the initial room, make a legal move and press R again. A message disappearing is useful evidence; a working move and restart also check that the repaired data still reaches the game correctly.

</details>

Finish by explaining why the two bad rows reach different checks even though they report the same row number. We have described the expected behaviour, reproduced a fault, tested a specific explanation, changed one relevant value and checked the repair.

A missing DATA statement is different. READ can run out of values before our checks can run, and the ROM reports **Out of DATA**. This validator is not a general BASIC error handler. Check that all eight map lines exist and that RESTORE selects the right section.

<Question prompt="A map has eight rows of eight recognised symbols, one player and equal positive numbers of crates and targets. Must it be solvable?">

No. Those checks establish a usable structure, not a route through the puzzle. A crate could be trapped in a corner or a target cut off. We still need to solve and play an edited room.

</Question>

Combined symbols matter to that distinction too. `*` contributes both a crate and a target; `+` contributes a player and a target. A structurally valid map with every crate already delivered starts completed because line 86 sees zero uncovered targets. A malformed map never reaches that line.

If the program enters play after an error, check line 21. If a bad row produces a subscript error instead of our message, check that the length test precedes `m$(c)`. Good diagnostics happen before the operation that would fail.

## Optional: which room did we build?

Once our handwritten DATA works, we can try a small tool on our development computer. This needs Python 3.10 or later; it is optional, and the Spectrum game still uses the same BASIC loader.

Open the [converter and its instructions](https://github.com/Code198x/code-samples/tree/main/sinclair-zx-spectrum/basic/crates/teaching/tools). Keep the original unit-08 program and `room.txt` as recovery copies. Work on a copy named `trial-room.txt`, in the tool's folder. Run:

```sh
python3 map_to_data.py trial-room.txt -o trial-room.bas
```

The output is **eight DATA lines, not a complete game or a tape**. Compare all eight with lines 8000–8070 above: they should match. In particular, authoring row 6 becomes `8050 DATA "#-P----#"`. When the loader reads it, P becomes `pr=6`, `pc=3` and floor in `g(6,3)`.

Press Q to leave the game before editing. Replace only lines 8000–8070 in our working program with the generated lines, then RUN and press S. Move left once and press R. Check that the player returns to row 6, column 3 and the steps return to zero.

### Leave an old output behind

In `trial-room.txt`, change row 2 to `#--X---#`. Before rerunning the command, predict: will it replace the output, remove it, or leave the previous output alone?

Run the command and read its diagnostic. Compare `trial-room.bas` with its earlier contents. For this controlled experiment only, put those remaining DATA lines into BASIC and run the game again. Why can it show a playable room when our authoring file contains X?
