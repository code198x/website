Lines 420–450 add collision detection. Line 420 reads the array value at the destination cell: `LET v = g(nr, nc)`. Line 430 checks if it is a wall — `IF v = 1 THEN GO TO 320`. The player does not move; control returns to the input loop. Line 450 blocks any cell that is not floor (0) or target (2): `IF v <> 0 AND v <> 2 THEN GO TO 320`. That catches crates (3) and any future cell type.

The player can now walk on floors and targets but not through walls or crates.

## The array as collision map

In earlier games, collision meant boundary checks: `IF x < 1` or `IF x > 30`. Each edge was a separate condition. Here, collision is a single array lookup. The level data already encodes what is walkable and what is not. A floor is 0. A wall is 1. The question "can the player move here?" becomes "what number is in this cell?"

This is the payoff of building the level as an array in Unit 1. The same data structure that draws the screen also answers collision questions. No separate wall list, no coordinate checks, no special cases for corners. One lookup, one branch.

## Permissive vs restrictive

Line 450 uses a restrictive check: block everything that is not explicitly walkable. The alternative — permissive, blocking only known obstacles — would let the player walk onto any new cell type added later. The restrictive approach is safer for a puzzle game. If you add a new cell type and forget to update the movement code, the player is blocked rather than allowed somewhere they should not be. The bug shows up immediately rather than corrupting a puzzle.
