## What You Built

A complete two-player battleships game with these systems:

**Data model:**
- `a(10,10)`, `b(10,10)` — ship grids for each player
- `c(10,10)`, `d(10,10)` — tracking grids for each player
- `h(2,5)` — hit counts per player per ship
- `k(2,5)` — sunk flags per player per ship
- `l(5)`, `n$(5,10)` — ship lengths and names

**Placement:**
- Five ships placed in sequence, largest first
- Start coordinate with lowercase handling
- Direction choice (horizontal/vertical)
- Bounds checking and overlap detection
- Visual feedback after each placement
- Layout review with redo option

**Shooting:**
- Coordinate input with full validation
- Already-fired duplicate check
- Hit/miss detection against opponent ship array
- Dual array update (tracking and ship)
- Ship identification and health tracking
- Sunk detection and display
- FLASH feedback on hits
- Sound effects: miss, hit, sunk fanfare, victory melody

**Game flow:**
- CLS handover between turns
- Fleet status display
- Win condition (all 5 sunk)
- Shot counter and statistics
- Rematch option

## What You Learned

This game introduced hidden information — the defining challenge of Battleships. Unlike Draughts where both players share one board, Battleships requires the program to manage four arrays and carefully control what each player sees. The CLS-and-handover pattern is simple but effective for a single-screen two-player game.

The data model grew more complex than any previous game. Parallel arrays for lengths, names, hits and sunk status all indexed by ship number (1-5) and player number (1-2). Keeping these arrays synchronised required discipline — every ship-related operation must use the correct indices.

Input handling became robust enough to survive real players. The validation cascade (empty, length, range, duplicate) catches every class of error with specific, helpful messages. This defensive approach prevents crashes and teaches the player what the program expects.
