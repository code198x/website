The player has typed a move. But before we check whether the destination is valid, we must check the source. Does the source square actually contain one of the current player's pieces? If the square is empty, or holds an opponent's piece, the move is invalid.

## How It Works

**Line 910** checks if the source square is empty. If `b(q,p)` equals 0, there is no piece there. The program prints "No piece there" and jumps back to the input prompt.

**Line 920** checks if it is Player 1's turn but the source piece belongs to Player 2. If `t = 1` and `b(q,p)` is not 1, the piece is not theirs. "Not your piece" appears on screen.

**Line 930** does the same check for Player 2.

Notice the coordinates: `b(q,p)` uses the row first, then the column. This matches how arrays work - row, then column - but it is the reverse of how the player types their move (column letter first, then row number). Keeping this mapping straight is essential.

## Layered Validation

Move validation in draughts happens in layers. Each layer checks one condition and either rejects the move or passes it to the next layer:

1. **Format check** (unit 6) - is the input string the right length?
2. **Range check** (unit 6) - are the coordinates on the board?
3. **Source check** (this unit) - does the source have the player's piece?
4. **Diagonal check** (unit 8) - is the move diagonal?
5. **Direction check** (unit 9) - is the piece moving forward?

If any check fails, the program shows an error and asks for input again. Only when all checks pass does the move execute. This layered approach keeps each check simple and the error messages specific.

## Try This

**Test every error.** Type a move from an empty square. Type a move using the opponent's piece. Confirm each error message appears correctly.

**Add the square value.** Change the error message to show what is actually on the square: "Square holds: 2" when you try to move an opponent's piece. This helps with debugging.
