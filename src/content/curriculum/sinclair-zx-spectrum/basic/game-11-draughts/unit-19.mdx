Kings can move backward, so they should be able to capture backward too. This unit applies the same conditional relaxation to the capture validation. Kings can jump in any diagonal direction.

## How It Works

**Lines 1160-1170** now include the `b(q,p) < 3` check before the forward-only restriction, matching the pattern from unit 18. If the capturing piece is a king (value 3 or 4), the direction check is skipped.

**Lines 1140-1150** also handle king values. When checking if the jumped piece is an opponent, the code now checks for values 2 and 4 (Player 2's pieces and kings) or values 1 and 3 (Player 1's pieces and kings). A king can capture both ordinary pieces and other kings.

## Unified Capture Logic

The capture validation now handles all four piece types consistently:

| Capturing piece | Can jump over | Can jump backward? |
|----------------|--------------|-------------------|
| Player 1 piece (1) | Values 2, 4 | No |
| Player 2 piece (2) | Values 1, 3 | No |
| Player 1 king (3) | Values 2, 4 | Yes |
| Player 2 king (4) | Values 1, 3 | Yes |

The `< 3` check handles the backward restriction. The explicit value checks (checking for both ordinary and king opponent pieces) handle the target identification. Both dimensions - direction and target - are now correct for all piece types.

## Kings Capturing Kings

A king can capture another king. This is important in the endgame when most pieces have been promoted. The captured piece's value (3 or 4) is treated the same as an ordinary piece (2 or 1) for the purposes of capture validation. It is removed from the board just like any other piece.

## Try This

**Backward capture.** Promote a king and position it so that an opponent's piece is diagonally behind it with an empty square beyond. Execute the backward capture.

**King captures king.** Get both players to promote a piece. Then set up a position where one king can jump the other. Does it work correctly?
