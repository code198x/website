The cursor movement from Unit 2 already IS a game loop. Let's name the pattern explicitly:

1. **Input** — check the keyboard (INKEY$)
2. **Erase** — remove the cursor from its old position (PRINT AT y,x;" ")
3. **Update** — change the position variables based on the key
4. **Draw** — show the cursor at its new position (PRINT AT y,x;"+")
5. **Repeat** — GO TO back to step 1

This cycle runs forever. Each pass is one "frame" of the game. The player sees smooth movement because the cycle runs fast — erase and redraw happen so quickly that the cursor appears to slide.

Every real-time game — not just on the Spectrum, but on any platform, in any language — uses this same loop. In Unity it's `Update()`. In JavaScript it's `requestAnimationFrame`. In assembly it's the main loop waiting for VSYNC. The concept is universal. The implementation changes. What you're building in Sinclair BASIC is the same structure a professional game developer uses.

**Boundary checking** is part of the Update step. Hot and Cold checks `IF y>1` before allowing upward movement, `IF x<30` before rightward. Without boundaries, the cursor would walk off the screen and crash the program. Boundaries are constraints — and constraints define the play space. The screen edges are the walls of the world.

## What You've Learnt

- The **game loop**: input → erase → update → draw → repeat
- This pattern is **universal** — every real-time game uses it
- **Boundary checking** keeps the player inside the play area
- The loop runs **continuously** — there's no waiting, no turns
