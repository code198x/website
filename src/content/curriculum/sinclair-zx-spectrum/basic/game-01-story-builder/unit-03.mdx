You have words. Now build a story from them.

Five questions, then a `CLS` to clear the screen, then the story prints fresh — your words dropped into sentences you did not write.

Run it. Type "Dave", "enormous", "hamster", "Tesco", "cheese". The screen clears and prints:

```
Once upon a time, Dave
found a enormous hamster
hiding in Tesco.

They fed it cheese
and it followed them home.

The end.
```

Read it aloud. If it makes someone laugh, the program works.

## How it works

Each INPUT stores a word. Each PRINT weaves those words into fixed text using semicolons:

```
PRINT "Once upon a time, "; n$
```

The computer does not know or care what `n$` contains. It just drops it into the sentence. The comedy comes from the mismatch between the serious story template and the silly words the player chose.

Line 110 uses `PRINT` with nothing after it — that prints a blank line, adding a gap between paragraphs.

## The design lesson

The player provides the *content*. The programmer provides the *structure*. Neither controls the result alone. That split — content versus structure — is how every template, form, and generator works, from Mad Libs to mail merge to web pages.

## Make it better

Try adding more questions. A colour. A number. A verb. The more words you collect, the richer the story.

Try writing a longer story — eight or ten lines of PRINT. The story should make sense grammatically (most of the time) regardless of what the player types. That constraint is the craft: writing sentences where any noun, any adjective, any place still reads as English.

Your program asks, remembers, and assembles. One more step: make it look like something.
