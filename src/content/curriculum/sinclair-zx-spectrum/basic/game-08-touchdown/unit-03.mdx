Line 50: `IF INKEY$ = " " THEN LET spd = spd - 2`. If the player holds the space bar, speed drops by 2 each tick. Gravity adds 1 per tick; thrust subtracts 2. Net effect: the lander slows down.

Line 60: `IF spd < 0 THEN LET spd = 0`. Speed cannot go negative — the lander does not fly upward. Zero is hovering.

## The game exists

Press space and watch the speed number drop. Release and it climbs again. The game is now a negotiation: gravity pulls, thrust pushes, and the player balances the two.

Try landing. Let the speed build to 5 or 6, then tap space a few times. Watch the speed drop to 2 or 3. Stop thrusting. The speed climbs. A gentle landing requires timing — enough thrust to slow down, but not so much that you hover and waste time.

## INKEY$ inside the game loop

This is the same `INKEY$` from Reflex, but used differently. In Reflex, the loop waited *for* a keypress. Here, the loop runs regardless — `INKEY$` is checked in passing, once per tick. If a key is pressed, the game acts on it. If not, the game continues. The key check is *inside* the game loop, not *the purpose of* the game loop.

This is how every real-time game handles input: check the controls once per frame, act on whatever you find, then update the world and draw the screen. The player's input is one factor among many.

Try changing `spd - 2` to `spd - 1`. The thrust is weaker — harder to slow down, harder to land. Try `spd - 3` — landing is easy. The number shapes the feel.
