Hold a direction and the controls behave as before. A recognised short tap during drawing can now survive after you release the key.

## Read the present, then the remembered key

INKEY$ answers the current-key question. The ROM also keeps LAST K at memory address 23560, recording a newly recognised key. PEEK reads that byte; CHR$ turns the code into a string that our existing direction tests can compare.

Line 291 first reads INKEY$. Only if it is empty does the program use the remembered byte. A held key therefore has priority at the sampling point.

Line 292 clears the latch with `POKE 23560,0` after consuming the command. Line 180 clears it when resetting the crossing, so a command from the previous attempt is not carried into the new start. These changes leave the collision queries, lane periods and drawing order alone.

## One remembered key is not a queue

The byte has room for one recognised key code. A newer key can replace it before the game reads it; the program does not replay an entire sequence of taps. Very short presses can still evade keyboard scanning, and simultaneous keys are not guaranteed to behave like successive commands.

Holding a key can also produce further recognised repeats. A move may remain buffered after release. Releasing means you are no longer holding a direction; it does not undo a command already waiting in the latch.

<Question prompt="You tap J and then L while the game is drawing, releasing both before the next update. Must the player make a left step followed by a right step?">

No. There is one remembered key, not two queued events. L can replace J before the update reads the byte, leaving only a rightward command. The program consumes at most one movement command at that update.

</Question>

## Compare the same interruption

Stay on the bottom strip so traffic cannot end the experiment. Tap J briefly while a lane redraws, then release. Compare this with the previous checkpoint, where only a key still held at line 291 could affect that update.

The recorded execution checks used a four-video-frame tap during lane-update work. It was missed in the polling-only version and retained here. Your manual tap is not a four-frame measuring instrument, so repeat the comparison and judge whether short presses are more dependable, rather than expecting every attempt to align identically.

If old movement repeats indefinitely, check that line 292 clears the latch. If a previous attempt's key appears at the next start, check line 180. If a held direction stops repeating, check that INKEY$ still has priority and that the old press-and-release gate has not returned.

<summary>Keyboard note: PEEK and POKE</summary>

In the Spectrum's original keyword entry, POKE is on O in keyword mode. For PEEK, enter extended mode with CAPS SHIFT and SYMBOL SHIFT, then press O. CHR$ is extended U. Use your emulator's documented keyboard mode when entering the listing.
