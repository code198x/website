The game now has its intended rules. Keep a version that can start from its instructions when loaded, then check the whole experience without relying on an already running session.

## Save the completed program

Enter Q to return to BASIC. Use the emulator's tape-recording workflow with this ROM command:

```basic
SAVE "sonar" LINE 10
```

`"sonar"` is the name stored in the tape header. `LINE 10` records where execution should begin after loading. The SAVE command does not go into the numbered program. Follow the ROM's recording prompt and export the captured tape to a file using your emulator. Keep both your readable source and the tape: one is easy to inspect, the other can be loaded by the Spectrum.

Start a fresh 48K session, attach that saved tape and enter:

```basic
LOAD "sonar"
```

Start tape playback using your emulator's controls. After loading, the instructions should appear automatically. If the ROM keeps searching, check the attached tape, playback and the saved program name. If the wrong program appears, check that you exported the latest recording.

## Check a whole visit

Begin from the instructions. Enter an invalid coordinate, reveal two different clues, repeat a probe, find the target, retry, then quit. On retry, check that the new board is empty and the count is zero. A successful save message alone does not check any of those behaviours.

<Question prompt="Why test in a fresh session instead of loading over the running game?">

A fresh session does not already contain the program or its variables. Loading and playing there demonstrates that the saved tape supplies what is needed to begin the game again.

## Optional revisit: return to a program we already know

Put the game aside, then return using the saved source and tape rather than rebuilding
it from the earlier lessons. Load a fresh 48K session as above and repeat the whole-visit
check. Keep that working source and tape unchanged; make a separately named copy for
this experiment.

Our intended change is small: **use `+` instead of `>` to mark the latest probe**.
The clues, target and counting rules should stay the same. Before editing, find these
parts in the complete source and explain their jobs:

| Lines | What to follow |
|---|---|
| 200–240 | Remember the old and new probe positions; redraw both cells |
| 2100–2150 | Read the cell's stored clue and choose its displayed letters |
| 2160–2180 | Start with a blank marker, mark only the latest cell, then print |
| 5060 | Explain the marker on the instruction screen |

Predict what happens to the old marker after the next probe. Which code removes it?
Does moving the marker require changing `g`, the array that stores the clues?

<details>
<summary>Compare the explanation</summary>

The old cell is redrawn after `lr` and `lc` have changed to the latest probe. It no
longer passes line 2170's test, so line 2160's blank marker survives. Its stored clue
still comes from `g(r,c)`. Presentation changes; the remembered clue does not.

</details>

In the experimental copy, change only the marker string in line **2170** from `>`
to `+`. Update the matching marker in the instruction text at **5060**. Keep the
coordinate condition, clue characters and other lines as they are.

Load or run the changed version and compare with the prediction: probe one cell,
probe a different cell, then repeat the first. If either probe finds the target,
retry and choose two non-winning cells for this check. There should be one latest marker;
both clues should remain, and the repeated probe should not add to the count.
Retry and check that the fresh board has no old marker. Read the instructions too.

If two markers remain, inspect the redraw of the old cell and the blank-marker
assignment before changing the counting code. If every cell gains a marker, inspect
the condition at 2170. The visible symptom helps us choose where to look; it does
not justify rewriting the whole display routine.

This is a small **behaviour change**, because the player sees a different symbol.
A **refactor** would reorganise the implementation while preserving the agreed
behaviour. Even then, we would check the affected costs and assumptions: extra
redrawing takes time, and a routine can disturb shared variables despite producing
the right final picture.

Keep a short note of the two edited lines, the intended change and the checks made.
Save the experiment under a distinct name such as `sonarplus`, retaining the original
source and tape. Once we work with source files in Git, a baseline commit and a
small reviewed diff serve the same purpose; Git is not needed to understand this
first revisit.

## A search you can explain

The hidden world is two coordinates. The player's knowledge is a two-dimensional array. Input changes that knowledge, and drawing turns it into a view. That division lets us recover the picture without changing the search and retry without accidentally keeping old clues.

Our game uses text characters and PAPER colours rather than imported artwork. The program and character-based graphics are original course material under the samples repository's MIT licence. Sonar is deliberately silent; its letters and messages provide the essential feedback.

A larger board is a possible extension. Before changing it, sketch how the labels, clues and prompts would fit. Revisit the input range, array dimensions, coordinate conversion and random range together. Also consider what the unchanged far band would tell you on a much larger sea. A bigger search is useful only if its extra decisions are interesting.

[Crates](/systems/sinclair-zx-spectrum/basic/crates/) takes the grid in another direction: it stores a warehouse whose crates move when a push is accepted.
