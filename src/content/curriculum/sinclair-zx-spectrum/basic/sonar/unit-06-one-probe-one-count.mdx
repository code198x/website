## Look before calculating

`seen = g(pr,pc)` reads what the board already knows. If it is -1, this cell is new: calculate the band, store it and add one to `n`. If it is anything else, copy the known code into `d` and jump to line 200. The marker and display still update, but the calculation and increment are skipped.

The test must use the unknown sentinel, not zero. A stored zero is a known discovery and must be recognised as a repeat too. The message at 270 explains a repeated probe; the found message at 280 takes precedence for a hit. New rounds will set `n` back to zero.

The short routine at 2500 prints the count on screen row 1. Both the ordinary probe path and the full redraw call it. Printing the count does not increase it.

<Question prompt="After probing A, then B, then A again, what should change on the third turn?">

The latest marker moves from B to A and the message explains the repeat. Both clues remain. The count stays at two because the third turn did not reveal a new cell.

## Rebuild from knowledge

Try `(1,2)`, `(8,8)`, `(1,2)`. Check that the count is two. Probe `(3,6)` to find the target and bring it to three. Probe the target again; the count should still be three. For now this checkpoint keeps accepting probes after a hit.

Now enter Q to stop. In direct command mode, enter `CLS`, followed by `GO SUB 1000`. The screen should reconstruct all three clues, the latest marker and the count. Direct commands run immediately without replacing numbered lines. Enter `GO TO 100` to resume asking for probes; RUN would instead initialise a new search.

Try a long invalid row answer after revealing several cells. The recovery redraw should produce the same board. Rejecting input and repainting the display are not new probes.

`g` is now enough to reconstruct every revealed clue, but it is not the whole game state. The target coordinates, count and latest marker have their own variables. Keeping these roles separate makes the next job easier: resetting a complete round deliberately.
