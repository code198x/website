Phase 1 puzzles used neat grid layouts — nodes in rows and columns. Real puzzles are more interesting when nodes sit in unexpected positions. An irregular layout forces the player to think about spatial relationships rather than relying on grid patterns. The engine already handles any arrangement, so this is purely a data design change.

## How It Works

**Lines 1000-1060** define a puzzle with nodes placed at irregular positions. Rather than sitting on a grid, the nodes form an asymmetric pattern — some clustered together, others spread wide. The connections cross the gaps in non-obvious ways.

**Lines 10-150** run the same engine as Phase 1. No code changes are needed. The data-driven design means new layouts only require new DATA statements.

## Designing Good Irregular Puzzles

A good Lattice puzzle has these properties:

**Multiple possible orderings.** The player should need to think about which connection to draw first. If there is only one valid order, the puzzle is a sequence, not a challenge.

**Near-crossings.** Lines that pass close to each other but do not cross create tension. The player must judge whether a connection will fit.

**Visual clarity.** Even with irregular positions, nodes should be well separated. Overlapping or nearly-touching nodes make the puzzle confusing rather than challenging.

**Solvability.** Every puzzle must have at least one solution — an order of connections where no line crosses another. Test every puzzle by hand before including it.

## Spacing Considerations

With irregular layouts, some nodes might be very close together while others are far apart. The cursor navigation (nearest-node by direction) still works, but movement might feel uneven. Very close nodes can be hard to distinguish. Keep a minimum spacing of about 30 pixels between any two nodes so they remain visually distinct.

## Try This

**Design an asymmetric puzzle.** Place seven nodes in a pattern that is not a grid and not a circle. Define connections that create an interesting challenge. Test it by hand first.

**Test cursor navigation.** Move between closely-spaced nodes using QAOP. Does the nearest-node algorithm pick the right target? Note any cases where the cursor jumps to an unexpected node.
