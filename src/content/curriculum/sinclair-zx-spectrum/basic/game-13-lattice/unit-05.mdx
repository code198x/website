A puzzle needs to know where its nodes are. Rather than hard-coding positions in the drawing code, we store them in arrays loaded from DATA statements. This separates the puzzle data from the game logic — the same drawing code works for any puzzle, just by changing the DATA.

## How It Works

**Lines 10-20** read the number of nodes for this puzzle and dimension two arrays: `x()` for horizontal positions and `y()` for vertical positions. Each array is indexed from 1 to the number of nodes.

**Lines 30-50** read each node position from DATA into the arrays using a FOR/NEXT loop. After this loop, `x(1)` and `y(1)` hold the position of node 1, `x(2)` and `y(2)` hold node 2, and so on.

**Lines 60-90** draw the puzzle by looping through the arrays. Each node is drawn as a green circle at its stored position.

**Lines 100-130** hold the puzzle data. The first value is the node count, followed by pairs of x,y coordinates. This four-node puzzle places nodes in a diamond shape.

## Data-Driven Design

The key insight here is separation. The drawing loop in lines 60-90 does not know or care about specific positions. It draws whatever the arrays contain. To create a different puzzle, you change only the DATA lines. The game engine stays the same.

This pattern scales well. A puzzle with four nodes and a puzzle with twelve nodes use exactly the same drawing code — only the node count and coordinate values change.

## Array Indexing

Nodes are numbered from 1, not 0. This is a deliberate choice that makes the game logic more readable. When the player selects "node 3", we look up `x(3)` and `y(3)` directly. There is no off-by-one translation.
