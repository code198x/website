The character from Unit 1 used PAUSE for timing. It worked, but PAUSE has a problem: it breaks early if a key is pressed. In a game where the player holds keys to steer, PAUSE would make the snake speed up whenever a key is pressed. That's not consistent.

The Spectrum has a hardware **frame counter** at memory address 23672. It increments by 1 every 1/50th of a second — one tick per frame of the PAL display. Reading it with `PEEK 23672` tells you exactly what frame the hardware is on.

<CodeFromFile src="sinclair-zx-spectrum/basic/game-07-tail-chase/unit-02/peek-timing.bas" />

Lines 80-110 are the timing loop. It waits for the PEEK value to change (`sp` times), then allows one movement step. `sp=8` means the character moves once every 8 frames — about 6 times per second. Change `sp` to 4 and it moves twice as fast. Change it to 16 and it crawls.

The critical difference from PAUSE: **PEEK timing doesn't break on keypress**. The player can mash keys all they want — the snake moves at the same speed. This is **frame-rate independence** — the game's speed is locked to the hardware clock, not to BASIC's execution speed or the player's input.

Every professional game solves this same problem. In Unity it's `Time.deltaTime`. In JavaScript it's tracking `performance.now()`. On the Spectrum it's `PEEK 23672`. The concept is universal: **tie your game's speed to a clock, not to how fast the code runs**.

## What You've Built

- Movement locked to the hardware frame counter
- `sp` controls speed — lower = faster, higher = slower
- Input-independent timing — keys don't affect speed
