The thief walks two rooms. He passes through cyan doors. He doesn't yet *take* anything, and there's no notion of *winning* — the loop is "walk forever, in two rooms." This unit closes the loop.

Two new cell types and a new piece of game state. Gold (already in both rooms as decoration) becomes pickupable: step onto a GOLD cell and the cell becomes FLOOR, both visually and in the room's data. A new EXIT cell appears in the antechamber's east wall — a green square the thief can step on to win. And the win condition gates on a single byte: `gold_taken`. If the count matches the total gold in the keep, the exit triggers victory. If not, the exit refuses.

By the end of the unit the keep has its first complete game state: enter, collect, win. We'll get there in four stages: **gold falls**, **the way out**, **victory**, and **locked until cleared**.

## A new piece of state

Every cell type Shadowkeep has met so far — WALL, FLOOR, GOLD, DOOR_OPEN — is *static*. The room renders, the cells sit there, the hero walks among them. Pickup changes that. Gold *vanishes* when stepped on. The room's state changes during play, not just between rooms.

This requires two related things in memory:

1. **A score counter (`gold_taken`).** One byte. Increments on each pickup. Used in Stage 4 to gate the win condition.

2. **Modification of the room's data table itself.** When a gold cell is picked up, we patch the corresponding byte of `room_data_great_hall` (or `room_data_antechamber`) from `GOLD` to `FLOOR`. Future renders of that room — say, after the thief transitions away and comes back — show the cell as floor. The pickup is *permanent* within a single play session, not just visually-but-undermined-by-the-next-redraw.

The mutation of data-while-the-program-runs is a small thing, but it's the first time we've crossed that boundary. The room data went from constant-table-baked-into-the-binary to game state.

## Stage 1: Gold Falls

Three changes from Unit 5's `try_move`:

```z80
.walk:
            call    restore_under_hero
            ld      a, (target_col)
            ld      (hero_col), a
            ld      a, (target_row)
            ld      (hero_row), a
            call    save_under_hero

            ld      a, (target_attr)
            cp      GOLD
            jr      nz, .skip_pickup

            ld      a, FLOOR
            ld      (player_under_attr), a       ; (1) cell hero is "on" now FLOOR
            ld      a, (gold_taken)
            inc     a
            ld      (gold_taken), a               ; (2) counter ++
            call    cell_addr_in_room_data
            ld      a, FLOOR
            ld      (hl), a                       ; (3) room data table now FLOOR

.skip_pickup:
            call    draw_hero
            ret
```

Three modifications, all conditional on the target attribute being GOLD.

### `target_attr` saved across the move

`try_move` already reads the target cell's attribute byte into A as part of the collision check. Stage 1 saves that byte into a new memory variable, `target_attr`, *before* branching:

```z80
            call    get_attr_addr_bc
            ld      a, (hl)
            ld      (target_attr), a              ; ← save for later
```

After the move completes (the hero now stands on the target cell), we read `target_attr` back. If it's GOLD, we run the pickup branch. The reason for the save: the move clobbers HL and A through the address helpers, so the attribute byte we read earlier would be lost. One extra byte of state buys us the ability to act on what we just walked onto.

### Computing the room-data offset

The third pickup step needs the cell's address *in the room's data table*, not its address on screen. The formula is:

```
  offset_in_room_data = (target_row - 2) * 22 + (target_col - 5)
  data_address = room_data_ptr + offset_in_room_data
```

For target row 3 (the great hall's top altar row), col 21 (the rightmost gold of the top cluster): `(3-2)*22 + (21-5) = 22 + 16 = 38`. The 38th byte of `room_data_great_hall` is that cell's byte.

The `cell_addr_in_room_data` helper does this multiplication by repeated addition (`add hl, de` in a DJNZ loop with DE = 22). For our 16-row room, the loop runs at most 14 times — bounded and cheap. The Z80's lack of a fast 8×8 multiplier means tricks like this are routine; the unrolled mul-by-22 here matches what 1986 game code did for similar lookups.

## Stage 2: The Way Out

Adding the exit is a one-line data change and a one-line collision change.

### The EXIT attribute

```z80
EXIT       equ $20                              ; PAPER 4 (green), INK 0
```

PAPER 4 is green. With INK 0 (black) and no BRIGHT or FLASH, the cell renders solid green against the antechamber's bright blue walls. The visual reads instantly as "exit" — green is the universal go-cell colour on the Spectrum, the way cyan is for doors.

### Punching the exit

We replace the rightmost cell of row 8 in the antechamber (which was WALL) with EXIT:

```z80
            ; Row 8 — west door, east EXIT
            defb    DOOR_OPEN
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    EXIT
```

Row 8 of the antechamber: door on the west, exit on the east. Symmetric placement; the thief walks through one and (eventually, once gold is collected) out the other.

### Collision allows EXIT

The try_move attribute cascade picks up a fourth walkable type:

```z80
            cp      DOOR_OPEN
            jr      z, .door
            cp      FLOOR
            jr      z, .walk
            cp      GOLD
            jr      z, .walk
            cp      EXIT
            jr      z, .walk                    ; new walkable type
            ret
```

Stage 2 stops here. The thief can step onto EXIT — and just stand there. The cell is visible, but inert.

## Stage 3: Victory

Stepping on the exit ends the game.

### The victory routine

```z80
victory:
            ld      a, 4                        ; green BORDER
            out     ($FE), a
.idle:
            halt
            jr      .idle
```

Three instructions. Set BORDER to colour 4 (green), then loop on HALT forever. No more input, no more movement, no more updates. The Spectrum is paused at the moment of victory.

We've met `OUT ($FE), A` in Unit 1 for the BORDER write — it's the same instruction, with `A = 4` this time instead of `A = 0`. The BORDER's lower three bits are `100` (= 4 = green).

The `HALT / JR .idle` pair keeps the program alive between IRQs without spinning the CPU. The BORDER stays green; the screen stays as it was when victory fired; the thief stands on the exit forever.

### Routing victory through `try_move`

```z80
.walk:
            ; ... normal move logic + gold pickup

            ld      a, (target_attr)
            cp      GOLD
            jr      z, .pickup_gold
            cp      EXIT
            jr      z, .exit_step
            jr      .finish

.exit_step:
            call    draw_hero                   ; show hero on the exit first
            jp      victory

.finish:
            call    draw_hero
            ret
```

After the move completes, we re-check `target_attr`. If it's EXIT, we draw the hero (so the screenshot shows him standing on the exit) and tail-call `victory`. `victory` never returns — its halt-loop runs forever.

## Stage 4: Locked Until Cleared

The Stage 3 exit fires regardless of what the thief has collected. The keep is a green cell waiting to be touched; nothing to actually *do*. This stage adds the constraint: **all the gold first.**

### The TOTAL_GOLD constant

```z80
TOTAL_GOLD     equ 15                           ; 13 great hall + 2 antechamber
```

Hand-counted from the data tables. Great hall: 6 gold cells in row 1, 4 in row 2, 3 in row 3 = 13. Antechamber: 2 in row 1. Total = 15.

A more elaborate game would scan the data at boot and count automatically. For two rooms with fixed gold counts, the hand-counted constant is fine.

### The gate

```z80
.exit_step:
            ld      a, (gold_taken)
            cp      TOTAL_GOLD
            jr      z, .victory_now

            ; Locked — flash BORDER red briefly
            ld      a, 2
            out     ($FE), a
            ld      b, 5
.flash:     halt
            djnz    .flash
            ld      a, 0
            out     ($FE), a

            jr      .finish

.victory_now:
            call    draw_hero
            jp      victory
```

Two paths. If `gold_taken == TOTAL_GOLD`, fire victory. Otherwise, flash the BORDER red for five frames (100ms — long enough to register, short enough to feel like a *cue* not an interruption) and continue. The thief stays on the exit cell. He can walk back into the keep and find what he missed.

### Red flash via `DJNZ`

The flash is a tiny five-frame countdown:

```z80
            ld      a, 2                        ; red
            out     ($FE), a
            ld      b, 5                        ; 5 frame countdown
.flash:     halt                                ; wait for IRQ
            djnz    .flash                      ; decrement B, loop if not zero
            ld      a, 0                        ; back to black
            out     ($FE), a
```

`B` is decremented each iteration by `DJNZ`. After five HALTs (five 50Hz frames = 100ms), `B` hits zero and we fall through to the `LD A, 0` that restores the black BORDER. A complete feedback cue in nine instructions.

This is the simplest possible timed visual effect — and the same shape Unit 8 will use for the hit-flash on hazard damage in Phase 2.

## Assemble and run

Each stage has its own `.asm` file. The Makefile builds all four into `.tap` (real-hardware loading) and `.sna` (screenshot capture):

```bash
make
```

Load any of the four `.tap` files into Fuse, your emulator of choice, or a real Spectrum Next. Type `RUN` at the BASIC prompt. Use Q, A, O, P for movement. Stages 3 and 4 are playable; in Stage 4 collect all fifteen gold pieces before stepping on the exit.

## Try this: a free exit

In Stage 4, change `TOTAL_GOLD equ 15` to `TOTAL_GOLD equ 0`. Reassemble. The exit fires the moment the thief touches it — `gold_taken` starts at 0 and matches `TOTAL_GOLD` immediately. The game is winnable in one straight walk to the antechamber.

This is Stage 3 reproduced as a special case of Stage 4. Setting `TOTAL_GOLD = 0` removes the gate; setting it to anything > 0 reinstates it. The number is the rule.

## Try this: a more demanding keep

Change `TOTAL_GOLD equ 15` to `TOTAL_GOLD equ 20`. Reassemble. There are only 15 gold cells, so `gold_taken` can never reach 20. The exit always refuses. The keep becomes unwinnable.

Useful as a "preview phase" — the player explores the rooms freely, watching everything tease victory without granting it. A 1986 demo of Shadowkeep that lets you try the controls but not actually beat the game.

## Try this: visible gold

Change the gold attribute to add a bitmap. In Stage 1, find the `draw_stone` routine and add a sibling `draw_gold` that writes a different pattern (a small filled rectangle, say) to gold cells the same way `draw_stone` does for walls. Then in `draw_current_room`'s second pass, also check for `CP GOLD` after `CP WALL`, and call `draw_gold` for matching cells.

The gold cells now have visible *content* (whatever you choose — a coin, a circle, a sparkle) on top of the yellow background, instead of just the flat yellow. The pickup behaviour is unchanged — when collected, both the attribute *and* the bitmap clear back to floor (because the data-table change overwrites both readings on the next render).

## Try this: a gold counter on screen

In Stage 4, after each pickup, write the current `gold_taken` value to a fixed cell as a single character. The lazy version: convert `gold_taken` to ASCII (`+ '0'`) and write the byte to the cell's attribute address (treating the attribute byte as if it were a character — which paints garbage but proves the data flow).

A proper version would walk the Spectrum's ROM font at `$3D00` and copy the eight bytes of the correct glyph to a fixed HUD cell's bitmap. Phase 2 will do that properly; for now, the lazy version is enough to see `gold_taken` updating in real time.

## If it doesn't work

- **Gold reappears on transition?** The room-data write isn't running. Confirm `cell_addr_in_room_data` is being called after the pickup `inc`, and that the address it returns is inside `room_data_ptr`'s range. A `JR` to `.skip_pickup` before the `call` would short-circuit the patch.
- **Picked-up cell becomes wrong colour?** `player_under_attr` is being set to the wrong value. Confirm `LD A, FLOOR` (not `LD A, GOLD`) before `LD (player_under_attr), A`.
- **Address arithmetic returns wrong cell?** The `cell_addr_in_room_data` helper depends on the multiplication-by-22 loop running the right number of times. Trace: for target row 3 (top altar row), the loop runs `3 - 2 = 1` time, adding 22 to HL. For target row 17 (bottom wall row), it runs 15 times, adding 330. Check the formula against a couple of known cells.
- **Exit doesn't trigger victory even with all gold collected?** Check the `CP TOTAL_GOLD` comparison in `.exit_step`. If `TOTAL_GOLD` is set higher than the actual count of gold cells, the gate is unsolvable.
- **Exit triggers victory immediately?** `TOTAL_GOLD` is probably set to 0. Or `gold_taken` is being initialised to a non-zero value. Confirm the boot routine has `xor a / ld (gold_taken), a`.
- **Victory triggers and then the game keeps running?** The `JP victory` is a tail call. The victory routine is a halt-loop. If victory has a `RET` instead of `JR .idle`, control returns to wherever the caller was, and movement resumes. Verify `victory` has `HALT / JR .idle` and no other `RET`.
- **Red flash too brief to see?** Increase `LD B, 5` to `LD B, 15` for a 300ms flash. Too long becomes annoying; too short becomes unreadable. Five frames is the deliberate Goldilocks zone for "you tried something, here's a cue, get on with it."

## What you've learnt

- **Mutable room data.** The room data table — previously a constant byte-array baked into the binary — is now mutable RAM. Pickup writes FLOOR to a cell of `room_data_great_hall` or `room_data_antechamber`. Subsequent renders see the new value.
- **The `target_attr` save-across-the-move pattern.** Read the cell's attribute once at collision-check time, save it, branch on it after the move. One byte of state to pass information across a function call.
- **8-bit multiplication by repeated addition.** `add hl, de` in a DJNZ loop computes `row * 22`. The Z80 has no MUL instruction; loops like this are the standard idiom for small constants.
- **The cascade of allow rules in `try_move`.** FLOOR, GOLD, DOOR_OPEN, EXIT — four `CP/JR Z` pairs. New walkable types are two-line additions. The list of rules IS the list of compares.
- **Post-move special handling.** After the walk completes, `target_attr` is re-checked for GOLD (pickup), EXIT (victory). The same byte that allowed the move drives what happens next.
- **The win state as a halt-loop.** `OUT ($FE), A` for the BORDER colour, then `HALT / JR .idle`. No input read, no update, just a frozen frame at 50Hz.
- **Tail call to a non-returning routine.** `JP victory` doesn't reserve a return slot on the stack — victory never returns. Cheaper than `CALL victory` (which would push a return address that's never popped).
- **`XOR 1`-like patterns with `OUT`.** Setting BORDER via `LD A, 4 / OUT ($FE), A` is the same shape as setting it via `LD A, 0`. The destination port and the data go through the same instruction.
- **Timed visual cues via `DJNZ`.** `LD B, 5 / HALT / DJNZ` runs the loop body exactly 5 times across 5 IRQs = 5 frames = 100ms. Tiny effects on tiny budgets.

## What's next

The thief takes gold. He wins. He stands silent through all of it.

Unit 7 gives the keep a voice. The Spectrum's BORDER-and-MIC port `$FE` shares one more bit with the [beeper](/vault/techniques/beeper-music) — bit 4 — which the title theme will drive at audio frequencies to produce single-voice melody. We'll meet the beeper composition format from [`shadowkeep-beeper-spec.md`](../../../wiki/curriculum/shadowkeep-beeper-spec.md): byte pairs of `(note, duration)`, terminated by a loop marker. A tiny driver running off the same 50Hz IRQ the rate-limit uses will tick the beeper note-by-note through the composition.

By the end of Unit 7 the title screen plays a beeper theme. The keep's silence is broken.
