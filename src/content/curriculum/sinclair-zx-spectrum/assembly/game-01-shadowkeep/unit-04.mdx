The thief stands. He has shape, he has colour, he stands in the right cell of the right room. What he doesn't have is *agency*. Hold any key — Q, A, O, P, anything — and nothing happens. The keep is silent toward him.

This unit gives him agency.

By the end he walks: one cell up for Q, one cell down for A, one left for O, one right for P. The keep around him stays clean as he moves — the floor he leaves is the floor he leaves, not a smear of red. And the pace at which he walks is the pace the keep deserves: eight cells a second, not the fifty cells a second the Spectrum's frame rate would otherwise inflict on him.

We'll get there in four stages: **the keyboard answers**, **a first step**, **the thief walks**, and **a measured stride**. Each stage adds one idea. Stage 2 deliberately ships a bug; Stage 3 demolishes it in a single technique.

## Port `$FE` reads the keyboard

Unit 1 used `OUT ($FE), A` to set the BORDER. The lower three bits of the byte we sent decided the colour. The same port works *both ways*: `IN A, ($FE)` (or its more flexible `IN A, (C)` cousin) reads from the port. What it returns is the state of the **keyboard**, not the BORDER.

The Spectrum's 40-key keyboard is wired as eight half-rows of five keys each:

```
  Half-row port  Keys (bit 0 = leftmost)
  ─────────────  ────────────────────────
  $FEFE          CAPS  Z   X   C   V
  $FDFE          A     S   D   F   G
  $FBFE          Q     W   E   R   T
  $F7FE          1     2   3   4   5
  $EFFE          0     9   8   7   6
  $DFFE          P     O   I   U   Y
  $BFFE          ENTER L   K   J   H
  $7FFE          SPACE SYM M   N   B
```

The *high* byte of the port selects which half-rows you want to read. Each bit going LOW in the high byte enables one row. So `$FBFE` (high byte `%11111011`, bit 2 clear) reads only the Q half-row.

The low byte's `$FE` (binary `11111110`, bit 0 clear) is what makes this a *keyboard* read rather than some other [ULA](/vault/hardware/ula) register read; the Spectrum's I/O decoder uses bit 0 of the port address to distinguish the ULA from other devices.

When you do `LD BC, $FBFE` followed by `IN A, (C)`, the lower five bits of A come back telling you which keys in the Q row are pressed. Bit 0 = Q, bit 1 = W, bit 2 = E, bit 3 = R, bit 4 = T. A *clear* bit means *pressed* (the keyboard pulls the wire low when contact is made); a *set* bit means released. That inverted convention is one of the few genuinely surprising design choices in the Spectrum.

Our four direction keys live in three rows:

```
  Q (north):  $FBFE, bit 0
  A (south):  $FDFE, bit 0
  O (west):   $DFFE, bit 1
  P (east):   $DFFE, bit 0
```

O and P share the same half-row, so a single `IN A, (C)` from `$DFFE` reads both in one pass.

## Stage 1: The Keyboard Answers

Before the hero moves, we prove the keyboard can be read. Four indicator cells in a `+` arrangement below the great hall sit at **dark cyan** by default and switch to **bright cyan** while their corresponding direction key is held. Cyan because no other game element in Phase 1 is cyan (doors arrive in Phase 2); dark-and-bright pair because both stay visible against the dark-blue stone of the keep — the unpressed indicators read as faint UI even when nothing's happening.

The poll loop, once per frame:

```z80
            ld      bc, KBD_Q
            in      a, (c)
            bit     0, a                       ; Z if Q pressed
            ld      a, IND_OFF
            jr      nz, .q_off
            ld      a, IND_ON
.q_off:
            ld      (IND_NORTH), a
```

Three new ideas in six instructions.

### `LD BC, port` / `IN A, (C)`

The Z80's `IN A, (n)` instruction takes only an 8-bit port number — fine for trivial machines, useless for the Spectrum because the high byte is what selects the keyboard row. `IN A, (C)` is the variant that takes its 16-bit port from `BC`. We load `BC` with the full port address (`$FBFE` for the Q row, etc.), and `IN A, (C)` pumps the entire 16-bit address onto the address bus.

The byte that comes back lands in A.

### `BIT n, r`

`BIT 0, A` tests bit 0 of A — sets the Z flag if the bit is *zero*, clears Z if the bit is *one*. The register itself is untouched. Combined with the Spectrum's inverted convention (pressed = 0), `BIT 0, A` after the keyboard read sets Z exactly when the key is pressed.

We've seen `BIT` in the planning of Unit 3's UDG design but never written it. Here it earns its keep: one instruction, one bit, one test.

### Reading-without-clobbering using `BIT`

The pattern after `BIT 0, A`:

```z80
            ld      a, IND_OFF                 ; default: not-pressed colour
            jr      nz, skip                   ; if Z=0 (not pressed), keep IND_OFF
            ld      a, IND_ON                  ; if Z=1 (pressed), override
skip:
```

`LD A, n` doesn't touch flags, so the `JR NZ` after it tests the *previous* `BIT 0, A` result. We branch on the keyboard bit *after* preloading A with the not-pressed colour. If pressed, we override; if not, we keep the preloaded value.

### O and P share a row

For the P-row read we keep the original byte in `D` so we can test both bits without re-reading:

```z80
            ld      bc, KBD_P
            in      a, (c)
            ld      d, a                       ; save reading
            bit     1, a                       ; O = bit 1
            ...                                 ; handle O
            bit     0, d                       ; P = bit 0 from saved reading
            ...                                 ; handle P
```

One port read, two bit tests. A real-time game on the Spectrum saves cycles wherever it can — every `IN A, (C)` costs 12 t-states (about 3.4 microseconds on a stock 48K), and shared-row reads halve the I/O budget for adjacent keys.

## Stage 2: A First Step

The simplest thing that could possibly work, with one direction (east) and no cell preservation:

```z80
main_loop:
            halt
            ld      bc, KBD_P
            in      a, (c)
            bit     0, a
            jr      nz, main_loop              ; no P, no move

            ld      a, (hero_col)
            cp      HERO_MAX_COL
            jr      z, main_loop               ; at the wall

            inc     a
            ld      (hero_col), a              ; advance one column

            ; ... compute new attribute + bitmap address, draw the hero
```

Hold P and on every frame, the hero's column increments by one. The new cell gets the hero attribute and the eight bytes of sprite bitmap. The old cell is left alone.

### State in RAM

The hero now has *position state*. A single byte `hero_col` lives in RAM (we declare it with `defb` in our source, which assembles into the binary at a known address). The 48K Spectrum has 48 KB of RAM from `$4000`; our code lives at `$8000` (32768), so any `defb` directives after our code allocate bytes in RAM that survive across `LDIR`s, function calls, and frames.

This is the first piece of state the hero owns. By the end of the unit there'll be three more bytes plus an eight-byte bitmap save area; by the end of Phase 1 the state table will hold lives, score, current room, and inventory.

### Computing the new cell's addresses

Since the hero only moves on row 10, the attribute and bitmap addresses simplify:

```
  attribute address = $5800 + 10 × 32 + hero_col = $5940 + hero_col
  bitmap address   = $4000 + $0800 + $0040 + hero_col = $4840 + hero_col
```

In code:

```z80
            ld      a, (hero_col)
            add     a, $40
            ld      e, a
            ld      d, $59                     ; DE = $5940 + hero_col
            ld      a, HERO_ATTR
            ld      (de), a

            ld      a, (hero_col)
            add     a, $40
            ld      l, a
            ld      h, $48                     ; HL = $4840 + hero_col
```

For Stage 2 this hardcoding is fine because the hero only moves along one row. Stage 3 generalises — a four-directional hero needs address computation that works for *any* (col, row).

### The deliberate bug

The Stage 2 code never clears the old cell. Each move writes the hero into a new cell, but leaves the previous cell untouched — still carrying the hero attribute and the eight sprite bytes from when the hero was there. Hold P for nine frames and you get nine cells of identical red hooded silhouette in a row, ending at the right wall.

This is the bug Stage 3 fixes. It's left here because seeing it makes the fix obvious.

## Stage 3: The Thief Walks

Cell preservation in three subroutines and one piece of state.

### Nine bytes of memory

The cell *under* the hero — whatever was there before he stepped on — is fully described by nine bytes: one attribute byte and eight bitmap bytes.

```
player_under_attr:  defb 0
player_under_bitmap:
            defb 0, 0, 0, 0, 0, 0, 0, 0
```

When the hero steps into a new cell, we save the new cell's nine bytes into `player_under_*` *before* drawing him over the top. When he leaves, we copy `player_under_*` back to the old cell — restoring whatever was there.

### General address computation

The hero now moves in both axes, so we need a general (col, row) → address routine for both attribute and bitmap.

**Attribute** is straightforward: `$5800 + row × 32 + col`. Implemented with five `ADD HL, HL`s (which is the fastest 16-bit left-shift on the Z80) to multiply row by 32, then add col and the `$5800` base.

```z80
get_attr_addr:
            ld      h, 0
            ld      a, (hero_row)
            ld      l, a
            add     hl, hl                     ; row * 2
            add     hl, hl                     ; row * 4
            add     hl, hl                     ; row * 8
            add     hl, hl                     ; row * 16
            add     hl, hl                     ; row * 32
            ld      a, (hero_col)
            add     a, l
            ld      l, a
            jr      nc, .ok
            inc     h
.ok:
            ld      a, h
            add     a, $58
            ld      h, a
            ret
```

**Bitmap** is harder because of the Spectrum's three thirds. We reuse Unit 3's `bitmap_rows` lookup table — which already accounts for the thirds — and index into it by `(hero_row - 2)` (because the table starts at room row 0 = screen row 2).

```z80
get_bitmap_addr:
            ld      a, (hero_row)
            sub     2
            add     a, a                       ; * 2 bytes per entry
            ld      e, a
            ld      d, 0
            ld      hl, bitmap_rows
            add     hl, de                     ; HL = table[room_row]
            ld      a, (hl)
            inc     hl
            ld      h, (hl)
            ld      l, a                       ; HL = base address (col 5)
            ld      a, (hero_col)
            sub     5                          ; col offset from room edge
            add     a, l
            ld      l, a
            ret     nc
            inc     h
            ret
```

### Save, restore, draw

Three subroutines that all follow the same shape: get the addresses, then move nine bytes. They differ only in direction.

```z80
save_under_hero:                                ; screen → RAM
            call    get_attr_addr
            ld      a, (hl)
            ld      (player_under_attr), a
            call    get_bitmap_addr
            ld      de, player_under_bitmap
            ld      b, 8
.loop:      ld      a, (hl)
            ld      (de), a
            inc     de
            inc     h
            djnz    .loop
            ret
```

`restore_under_hero` is `save_under_hero` with the source and destination swapped — `(de)` reads, `(hl)` writes. `draw_hero` writes `HERO_ATTR` and the eight bytes of the `hero` sprite data, ignoring whatever was there.

### The move helper

`move_by` is the single point through which all movement flows. It takes a `(dcol, drow)` delta in `BC` and does the full restore → update → save → draw cycle.

```z80
move_by:
            push    bc                         ; save delta across the restore
            call    restore_under_hero         ; clobbers BC
            pop     bc
            ld      a, (hero_col)
            add     a, b
            ld      (hero_col), a
            ld      a, (hero_row)
            add     a, c
            ld      (hero_row), a
            call    save_under_hero
            call    draw_hero
            ret
```

The four direction handlers in the main loop each push their delta into `BC` and call `move_by`:

```z80
.move_right:
            ld      a, (hero_col)
            cp      ROOM_MAX_COL
            jr      z, main_loop               ; at the right wall
            ld      b, 1
            ld      c, 0                       ; dcol=+1, drow=0
            call    move_by
```

`-1` is represented as `$FF` since A is unsigned for our purposes; `ADD A, $FF` decrements A (with the carry flag set, which we don't care about here).

### Bounds, not collision

The bounds check (`CP ROOM_MAX_COL` etc.) keeps the hero inside the rectangular room. It is *not* collision — the hero can still walk over the altar's wall cells in the middle of the room because their attribute is `WALL` but we don't test for that. Attribute-based collision lands in Unit 5 alongside the room transition. For now, the keep is empty enough that even the altar isn't off-limits.

## Stage 4: A Measured Stride

The thief walks. Too fast. At fifty cells a second the great hall is a quarter-second-long stride from end to end. We need to slow him down.

The cleanest approach is to introduce a *frame counter* — a single byte that increments every frame and triggers movement only when it reaches a threshold:

```z80
MOVE_INTERVAL equ 6                             ; cells/sec = 50/6 ≈ 8.3

main_loop:
            halt
            ld      a, (move_tick)
            inc     a
            ld      (move_tick), a
            cp      MOVE_INTERVAL
            jr      c, main_loop               ; not yet — wait another frame
            xor     a
            ld      (move_tick), a             ; reset

            ; ... read keys, move
```

The tick increments on every interrupt. If it hasn't reached `MOVE_INTERVAL`, we jump back to `HALT` and let another frame elapse. When it finally reaches 6, we reset and run the input-and-move code.

### Why six

Six frames between moves at 50Hz is one move every 120ms, or about 8.3 cells per second. [*Atic Atac*](/vault/games/atic-atac) and [*Sabre Wulf*](/vault/games/sabre-wulf) settled on similar paces — fast enough to feel responsive, slow enough that the player can read what's under their next step before pressing a direction. Drop the interval to 3 and the hero feels skittish; raise it to 12 and he feels stuck in treacle.

The right number depends on the cell size and the scene's complexity. A 22×16-cell room with one cell per move at 8 cells/sec means a full edge-to-edge traversal takes about 2.6 seconds — long enough to plan, short enough to commit.

### `XOR A` for "zero this register"

`XOR A` is the canonical Z80 idiom for setting A to zero. XOR-ing any value with itself produces zero, and the instruction is one byte (4 t-states) — shorter and faster than `LD A, 0` (two bytes, 7 t-states). The cost is that it also clears the carry and sets the Z flag, which is usually irrelevant. Whenever you see `XOR A` in real Spectrum code, it's almost always "I want zero in A and I don't care about flags."

### Polling vs acting

A subtle decision in the loop: we *poll* the keyboard inside the elapsed-tick branch, not outside. That means we miss key states between ticks — if you tap and release a key within a single 120ms window, the move won't happen. For continuous movement (hold to walk) this is fine; for tap-to-step (which we don't need yet), you'd want to poll every frame and latch the press.

Phase 2 may revisit this if the game wants different responsiveness for menus and gameplay. For Phase 1, hold-to-walk is the right interaction.

## If it doesn't work

- **No movement at all?** Keyboard ports are easy to mistype. `$FBFE` (Q row) and `$FDFE` (A row) differ by one bit in the high byte. Double-check each port constant; a swapped digit reads the wrong row and the wrong key.
- **Wrong direction moves on each key?** The bit positions within a row are zero-indexed from the leftmost key. Q is bit 0 of the Q row; P is bit 0 of the P row; O is bit 1 of the P row. If P and O are swapped, double-check the bit numbers.
- **Movement happens but only in bursts?** The `move_tick` counter might not be resetting. Confirm the `XOR A; LD (move_tick), A` runs *only* on the "elapsed" branch (after the `CP MOVE_INTERVAL` succeeds), not every frame.
- **Hero leaves trail at start but not on subsequent moves?** The initial `call save_under_hero` is missing or runs in the wrong order. Save *before* the first `draw_hero`. If you draw the hero first and then save, the hero's own bitmap and attribute get saved as "what's underneath", and the first move restores the hero onto the old cell.
- **Hero corrupts the room when walking onto walls?** That's correct for Stage 3 — no collision check. The hero passes through walls, saves the wall, then restores it when he leaves. The room looks correct after he moves on, because the save/restore handles wall cells identically to floor cells. Unit 5 adds a collision check that stops him stepping onto walls in the first place.
- **`IN A, (C)` returns `$FF` always?** The high byte of `BC` might not be set. `IN A, (C)` puts the *whole* of `BC` on the address bus, so `B` must hold the half-row select mask. If you do `IN A, ($FE)` (using the 8-bit immediate form), only the low byte is sent — and the high byte is whatever's lying on the bus, often all-ones, which selects no row.
- **Hero moves on every frame in Stage 4?** The `CP MOVE_INTERVAL` followed by `JR C, main_loop` reads as "if A is less than `MOVE_INTERVAL`, loop back". If the comparison is wrong or the JR condition is wrong (`JR NC` instead of `JR C`), the gate flips and the hero moves every frame except when the tick is in range.
- **Indicator cells stay dark in Stage 1?** The default-then-conditional-override pattern relies on `LD A, n` *not* affecting flags. If you accidentally use a different instruction that does (e.g., `ADD A, n` to clear A by adding zero), the Z flag may be lost between the `BIT` and the `JR NZ`. Stick with `LD A, value`.

## What you've learnt

- **Port `$FE` reads the keyboard.** Same port that drove BORDER in Unit 1; the read side returns key state. Low byte `$FE` selects the ULA's keyboard register.
- **The keyboard's half-row layout.** Eight rows of five keys each. High byte of port selects rows; clear bit = read this row.
- **Pressed = 0.** The Spectrum's keyboard pulls wires *low* when keys are contacted. A clear bit in the read result means pressed; a set bit means released.
- **`IN A, (C)`.** The 16-bit-port read instruction. `BC` holds the address; A receives the data.
- **`BIT n, r`.** Test one bit of a register without modifying it. Sets Z when the bit is zero.
- **The default-then-override pattern.** Preload A with the unconditional value (using `LD A, n` which doesn't touch flags), then branch on the prior `BIT` result to optionally override. Reads cleanly, costs little.
- **Position state in RAM.** `hero_col`, `hero_row`, `player_under_attr`, and the eight-byte bitmap save area are all `defb`'d in the source and live in RAM. Updated each frame, persist across the main loop.
- **General (col, row) → address routines.** `get_attr_addr` and `get_bitmap_addr` work for any cell, not just the hero's starting position. Five `ADD HL, HL`s do an 8-bit-to-16-bit row × 32; the bitmap routine indexes through Unit 3's per-row lookup table.
- **The save → update → restore-on-leave loop.** Nine bytes (one attribute, eight bitmap) describe everything under the hero. Save before drawing; restore before moving; the cell goes back to exactly what it was.
- **Cell preservation, not collision.** The hero can walk over anything because we don't check what's there — we just remember and restore. Collision rules come in Unit 5.
- **The `XOR A` zero idiom.** One byte, four t-states, zeros A. Used throughout retro Z80 code.
- **Frame-counter rate limiting.** A single byte ticked per frame, reset on threshold. Decouples animation speed from frame rate. Six frames at 50Hz gives ~8 cells/sec — the comfortable exploration pace.

## What's next

The thief walks his room. He has nowhere to walk *to*.

In Unit 5 the great hall acquires a neighbour. A second room data table sits next to the first; the keep grows from one room to two. The connection between them lives in a small data structure — a "doors" table that says "the cell at room A's east edge leads to room B, position X". When the thief steps onto an open-door cell, the screen flips: the current room's data is swapped for the destination's, the hero is repositioned at the opposite door, and a beeper SFX marks the transition.

Unit 5 also introduces attribute-based collision: the cell the hero *wants* to step into is read first, and if its attribute is `WALL`, the step doesn't happen. The keep stops being permissive about its walls.

By the end of Unit 5 the thief walks two rooms, can't walk through walls, and transitions between rooms on door cells. That's two of the eight Phase 1 deliverables already in working form.
