The thief walks. In a single room. The keep he walks is bounded by the lazy fiction of *col 25, don't go further* — a numeric fence that has no relationship to what's on the screen. He glides right through the altar walls because they live in the middle of the room, not at its edge. He'd glide right through the doors too, if there were any doors.

This unit lays down the keep's real rule. **Every game rule is a bit-test on the attribute byte of the cell in question.** The thief reads the cell ahead of him before he steps; if it's stone, he doesn't move; if it's gold, he walks across it; if it's a door, the world changes.

By the end of the unit the keep has two rooms — the great hall and a smaller antechamber to its east — connected by a cyan door at each room's middle. The thief walks east, steps onto the door, and the screen flips: same engine, different data, hero deposited inside the antechamber. He walks west and flips back. The first proof that the engine generalises beyond one room.

We'll get there in four stages: **walls refuse**, **a second room**, **a door cell**, and **the screens flip**.

## The mechanic at the centre of Shadowkeep

The brief calls Shadowkeep a remix unit: the same [Atic Atac](/vault/games/atic-atac) tropes you'd expect — top-down adventure, multi-room layout, find-and-escape — built around one specific technical mechanic instead of the usual fleet of separate systems. That mechanic is:

> Every game rule is encoded in the attribute byte at `$5800+`, and every rule lookup is a one-instruction read followed by a bit test or compare.

No separate collision table. No sprite-vs-tile collision math. No map editor that produces a parallel "logic layer." The screen *is* the map. The attribute byte *is* the rule.

This stage is the first place where that mechanic does real work. Walls block because we read their attribute. Doors transition because we read their attribute. By Phase 1 Unit 8 the same one-instruction read will check for treasure (gold), hazards (red FLASH), the exit, and locked doors. A single technique threads through all of them.

## Stage 1: Walls Refuse

Unit 4 used a numeric bounds check (`CP ROOM_MIN_COL` and friends) to keep the thief inside the room. Stage 1 throws that out and replaces it with the attribute read.

### The collision check

```z80
try_move:
            ld      a, (hero_col)
            add     a, b                       ; B = dcol
            ld      (target_col), a
            ld      a, (hero_row)
            add     a, c                       ; C = drow
            ld      (target_row), a

            ; Read attribute at the target cell
            ld      a, (target_col)
            ld      b, a
            ld      a, (target_row)
            ld      c, a
            call    get_attr_addr_bc
            ld      a, (hl)                    ; A = target attribute byte

            cp      FLOOR
            jr      z, .walk
            cp      GOLD
            jr      z, .walk
            ret                                ; anything else blocks

.walk:
            ; ... restore, update position, save, draw
```

Three new things in the flow.

### `try_move` as a single point of decision

Unit 4 had four separate direction handlers, each with its own bounds check and `move_by` call. Stage 1 funnels them all through `try_move`, which:

1. Computes the target cell `(hero_col + dcol, hero_row + drow)`.
2. Reads the target cell's attribute byte.
3. Decides — *based on that byte* — whether to allow the move.

Funnelling means the rule for "what's walkable" lives in one place. Add a new walkable type (say, `DOOR_OPEN` later) and only `try_move` changes; the four direction handlers stay identical.

### `CP` against attribute constants

The collision is two `CP` instructions:

```z80
            cp      FLOOR
            jr      z, .walk
            cp      GOLD
            jr      z, .walk
            ret
```

`CP n` subtracts `n` from A *without* storing the result — it only sets the flags. The Z flag goes on if A equals `n`. Two `CP`/`JR Z` pairs check "is the target FLOOR? — yes, walk. Is it GOLD? — yes, walk. Otherwise, return without moving."

Three possibilities land on "block": WALL (`$48`) — perimeter and altar walls. STONE (`$08`) — dark cells outside the room. Anything else, including any future attribute the keep hasn't met yet. The default is *block*. New cell types have to opt in to walkability.

This is the cleanest version of the brief's central principle. Two instructions per allowed cell type. The list of allowed types is the list of rules.

### Address arithmetic, generalised

Unit 4's address helpers (`get_attr_addr`, `get_bitmap_addr`) implicitly read `hero_col` and `hero_row` from memory. Stage 1 generalises them to take any `(col, row)` in `B` and `C`:

```z80
get_attr_addr_bc:
            ld      h, 0
            ld      a, c
            ld      l, a
            add     hl, hl
            add     hl, hl
            add     hl, hl
            add     hl, hl
            add     hl, hl                     ; HL = row * 32
            ld      a, b
            add     a, l
            ld      l, a
            jr      nc, .ok
            inc     h
.ok:        ld      a, h
            add     a, $58
            ld      h, a                       ; HL = $5800 + row*32 + col
            ret
```

The hero helpers (`save_under_hero` etc.) now load `hero_col` and `hero_row` into B and C before calling. The collision check loads `target_col` and `target_row` instead. Same routine, different callers.

## Stage 2: A Second Room

The render code in Stages 1–4 cares about exactly one thing: where the room data lives. Point it at 352 bytes that describe a great hall and it renders a great hall. Point it at 352 bytes that describe an antechamber and it renders an antechamber. The engine doesn't know either name.

### Two room tables side by side

The Stage 2 source defines both `room_data_great_hall` (the existing layout) and `room_data_antechamber` (a new one — narrower feel, two single-cell pillars at room cols 7 and 14, gold tucked into the upper corners). Both are 352 bytes. Both follow the same byte-per-cell convention.

### A pointer table

To select which one the engine reads, we add a small lookup table:

```z80
room_table:
            defw    room_data_great_hall
            defw    room_data_antechamber
```

Two `defw` entries, four bytes total. Indexed by a one-byte room number:

```z80
            ld      a, (current_room)
            add     a, a                       ; * 2 bytes per entry
            ld      e, a
            ld      d, 0
            ld      hl, room_table
            add     hl, de                     ; HL = &room_table[current_room]
            ld      a, (hl)
            inc     hl
            ld      h, (hl)
            ld      l, a                       ; HL = room_data_X
            ld      (room_data_ptr), hl
```

The eight instructions are the canonical "look up an address in a 16-bit pointer table" idiom on the Z80. Index doubled (two bytes per pointer), table base added, the address read low-byte-first (because the Z80 stores 16-bit values little-endian — low byte at the lower address). HL ends up holding the start of whichever room's data we want.

`room_data_ptr` is then handed to the existing attribute pass and stone pass, which read 352 bytes starting at `(room_data_ptr)` and render whichever room those bytes describe. No code in the render loops changes.

### Boot into either room

The `START_ROOM equ 1` line at the top of the source decides which room the program boots into. Stage 2 sets `START_ROOM = 1` to demonstrate the antechamber. Change it to `0` and the same code boots into the great hall. Same engine, same instructions, different output.

## Stage 3: A Door Cell

A door is one more attribute byte. PAPER 5 (cyan), INK 0, no BRIGHT, no FLASH — `$28`.

We punch one DOOR_OPEN cell into each room's connecting wall:

```
  Great hall:   room (col 21, row 8) — the east wall, mid-height
  Antechamber:  room (col 0,  row 8) — the west wall, mid-height
```

Both at room row 8 — the same horizontal level — so the transition (Stage 4) doesn't need to remap the row. Step east through one door, you arrive on the other side at the same height.

### Editing the room data

Each room's data table now has its `rept`-block split around row 8 to insert the door:

```z80
            rept 3
                defb    WALL, FLOOR, FLOOR, ..., FLOOR, WALL  ; rows 5-7
            endm
            ; Row 8 — east door
            defb    WALL, FLOOR, FLOOR, ..., FLOOR, DOOR_OPEN
            rept 6
                defb    WALL, FLOOR, FLOOR, ..., FLOOR, WALL  ; rows 9-14
            endm
```

The DOOR cell replaces what would have been `WALL` at room col 21. The attribute pass renders it as solid cyan (PAPER 5); the stone pass skips it (because `CP WALL` says no) so its bitmap stays at the zeroes the bitmap-clear left there. The eye sees a cyan rectangle set into the bright blue stone of the east wall — unmistakably a door.

### Doors are walkable

The collision check picks up a third walkable case:

```z80
            cp      FLOOR
            jr      z, .walk
            cp      GOLD
            jr      z, .walk
            cp      DOOR_OPEN
            jr      z, .walk
            ret
```

`DOOR_OPEN` joins the allow list. The hero can step onto a door cell — and just stand there. Stage 3 stops here. The door is plumbing for Stage 4; this stage proves it's correctly placed and visually right.

## Stage 4: The Screens Flip

The door becomes a transit. When `try_move` reads `DOOR_OPEN` at the target cell, it skips the normal walk path and tail-calls `do_transition`:

```z80
            cp      DOOR_OPEN
            jr      z, .door
            cp      FLOOR
            jr      z, .walk
            cp      GOLD
            jr      z, .walk
            ret

.walk:
            ; ... normal restore → update → save → draw
            ret

.door:
            jp      do_transition
```

`JP do_transition` is a tail call — `do_transition`'s `RET` returns directly to `try_move`'s caller, skipping the rest of `try_move` cleanly.

### What the transition does

```z80
do_transition:
            ld      a, (current_room)
            xor     1
            ld      (current_room), a          ; flip 0 ↔ 1

            or      a                          ; new room == 0?
            jr      nz, .into_antechamber

            ; Into great hall — arrival at (25, 10)
            ld      a, 25
            ld      (hero_col), a
            ld      a, 10
            ld      (hero_row), a
            jr      .render

.into_antechamber:
            ; Into antechamber — arrival at (6, 10)
            ld      a, 6
            ld      (hero_col), a
            ld      a, 10
            ld      (hero_row), a

.render:
            call    clear_screen
            call    draw_current_room
            call    save_under_hero
            call    draw_hero
            ret
```

Five things, in order:

1. **Flip `current_room`.** `XOR 1` toggles the low bit — `0 → 1` and `1 → 0`. The cheapest way to flip a boolean.
2. **Decide the arrival point.** Two hardcoded cells. One cell *past* the destination's door, inside the destination room. The hero never lingers on a door; he passes through it.
3. **Clear the screen.** `clear_screen` does the same `LDIR` fills we use at boot — bitmap to zero, attributes to dark stone. The old room disappears in two block operations.
4. **Draw the new room.** Same `draw_current_room` we wrote in Stage 2. It reads `current_room` (which we just flipped), looks up the new pointer, runs the attribute pass and the stone pass.
5. **Place the hero.** `save_under_hero` reads what's under the arrival cell (a FLOOR cell in both directions). `draw_hero` paints him there.

Hold P and the thief glides east through the great hall, reaches col 25, steps onto the door at col 26 — and instead of his cell turning red, the *entire screen* changes. He is now standing in the antechamber, one cell east of the door he just came through.

### Why arrive one cell past the door

If we arrived *on* the destination's door cell, the player would either stand on a door cell (slightly odd visually, since the player is supposed to be passing through it) or accidentally re-transition on the next step in any direction. Placing the hero one cell into the room makes the transition feel deliberate: he walked through the door and into the room beyond.

The cost is asymmetry: the hero's east-bound and west-bound transitions arrive at different columns (25 in great hall, 6 in antechamber). The arrival points are picked to mirror what the player was doing — walking east, he arrives ready to keep walking east (slightly into the new room); walking west, the reverse.

### `XOR 1` as a toggle

`XOR 1` on the accumulator flips bit 0 while leaving the other bits alone. For our two-state `current_room` (values 0 and 1), this is the perfect toggle:

```
  Before XOR 1:   $00 (0)            $01 (1)
  After XOR 1:    $01 (1)            $00 (0)
```

The classic *toggle a single bit* idiom on the Z80. We'll use it again later for things like inverting a "sound on/off" flag or flipping a colour-cycle frame.

### Hardcoding the arrival points

The Stage 4 transition has two hardcoded `JR NZ`/value pairs — one for each direction. A two-room keep doesn't need anything more elaborate; nine rooms (Phase 2) will.

Phase 2's plan is a small "door pairs" table indexed by `(from_room, door_col, door_row)`. Each entry stores the target room and the arrival cell. The transition becomes a lookup-and-jump, the same shape as the room-table lookup we wrote in Stage 2. The principle from this unit — *what to do is a function of the byte you read* — will scale to whatever the keep grows into.

## Assemble and run

Each stage has its own `.asm` file. The Makefile builds all four into `.tap` (real-hardware loading) and `.sna` (screenshot capture):

```bash
make
```

Load any of the four `.tap` files into Fuse, your emulator of choice, or a real Spectrum Next. Type `RUN` at the BASIC prompt. Use Q, A, O, P for movement (stages 1, 3, 4); Stage 2 has no input handling beyond rendering.

## Try this: a third walkable cell type

In Stage 1, after the `CP GOLD / JR Z, .walk` pair, add a check for `$28` (the cyan colour that will later be the door):

```z80
            cp      $28
            jr      z, .walk
```

Reassemble. The thief now walks onto cyan cells — but there *are* no cyan cells in the great hall yet. Run anyway; nothing changes visually. The change has prepared `try_move` for doors before doors exist.

This is what additive design looks like: a new rule is two lines of code, added to a table-of-rules that was already there.

## Try this: an unconnected room

In Stage 4, swap the `DOOR_OPEN` cells in both rooms' data back to `WALL`. Reassemble. The thief can walk around the great hall but never leave it; the antechamber exists in memory but is unreachable. Boot with `START_ROOM equ 1` to see the antechamber instead.

Two rooms, both renderable, no connection. The connection lives entirely in the data — change two bytes to put it back.

## Try this: a hostile door

In Stage 4, after `CP DOOR_OPEN / JR Z, .door`, change the door's attribute constant from `$28` to `$A8` (PAPER 5 + FLASH — the brief's "locked door" cell type). The door starts pulsing — INK and PAPER swapping at the Spectrum's flash rate of about twice a second. The collision check still treats it as walkable (since we compared against `$28` in the equ, not `$A8`), so the thief steps through and transitions.

This is the brief's signposting principle in microcosm: changing one bit of an attribute byte changes what the door *looks like* without changing whether it's passable. Locked doors in Unit 6 will use the FLASH bit to flag "needs a key" — the same visual change, this time with a real rule attached.

## Try this: a thief who can climb

In Stage 1, add `CP WALL` *outside* the block sequence:

```z80
            cp      FLOOR
            jr      z, .walk
            cp      GOLD
            jr      z, .walk
            cp      WALL
            jr      z, .walk                   ; ← new: walls are walkable
            ret
```

Reassemble. The thief now walks through walls — perimeter, altar, anything. He can leave the room into the dark stone outside (which is `STONE`, still blocked). The collision check is a list of rules; what's *not* on the list is blocked. Adding `WALL` makes the keep porous, which is funny for thirty seconds and a useful illustration that rules are additive.

## If it doesn't work

- **Hero refuses to move at all?** The `try_move` collision check probably has the bit pattern of FLOOR or GOLD wrong. `FLOOR equ $38` and `GOLD equ $70` — check both constants. A typo in either makes the check miss the actual floor of the room and treat every cell as a block.
- **Hero walks through walls?** The collision allows cells whose attribute matches FLOOR or GOLD. If you have those constants set wrong (e.g., `FLOOR equ $48`), the check will allow walls. Verify the `equ` directives against the attribute pattern actually used in `room_data`.
- **Antechamber renders as garbage?** The pointer table lookup may be reading off the end of `room_table`. Confirm `current_room` is 0 or 1 (not, say, 2 from a typo).
- **Door cell renders as wall texture?** The stone pass writes stone-block bitmap to every cell whose attribute is `WALL`. If your DOOR_OPEN constant is `$48` (same as WALL) instead of `$28`, the stone pass will texture it. Verify `DOOR_OPEN equ $28`.
- **Transition fires repeatedly?** The arrival point must not be a `DOOR_OPEN` cell. If you accidentally place the hero on the destination room's door, his first move attempt will re-trigger the transition. Move the arrival point one cell off the door — col 6 in antechamber (not 5), col 25 in great hall (not 26).
- **Transition wipes the wrong room?** `clear_screen` doesn't care about rooms — it just LDIRs everything. The order matters: clear *before* draw. Check that `do_transition` calls `clear_screen` first and `draw_current_room` second.
- **Hero invisible after transition?** Look for a missing `call save_under_hero` and `call draw_hero` in `do_transition`'s `.render` block. The cell-clearing wipes the bitmap, so the hero has to be redrawn from scratch — the `save → draw` pair, just like at boot.
- **Stage 2 (and only 2) won't assemble: "Invalid definition"?** Some assemblers (including `pasmonext`) treat dotted labels like `.l` as global, so reusing the same `.l` across multiple subroutines collides. Rename them to be unique per routine: `.sl` in save, `.rl` in restore, `.dh` in draw_hero, `.ds` in draw_stone. The local-vs-global behaviour varies by assembler — when in doubt, make each label unique.

## What you've learnt

- **Attribute-based collision.** One read of one byte. Compare against the constants for allowed cell types. Anything else blocks. The mechanism Shadowkeep is designed around.
- **`CP n` and the Z flag.** Compare without storing. Z set if equal. Two `CP/JR Z` pairs are an allow-list.
- **Generalised address helpers.** `get_attr_addr_bc` and `get_bitmap_addr_bc` take `(col, row)` in `B`, `C`. Hero callers load from `hero_col/hero_row`; collision callers load from `target_col/target_row`. Same routine.
- **`try_move` as a funnel.** Four direction handlers all call one routine. Rules for movement live in exactly one place.
- **Pointer tables for variable-sized data.** Sixteen-bit pointers in a `defw`-table, indexed by doubling the integer key. The Z80's canonical "look up an address" pattern.
- **`current_room` state.** A one-byte room number drives which pointer the render code reads.
- **`XOR 1` as a toggle.** Flips bit 0 without disturbing others.
- **Tail calls with `JP`.** `JP do_transition` instead of `CALL do_transition / RET` saves one byte and one stack push, and reads as "this is the end of my work; do_transition finishes it."
- **The "what to do is a function of the byte you read" principle.** Walls block. Doors transition. Floors walk. The branching lives in the data, not in flag bytes or parallel tables.
- **Arrival points one cell past the destination door.** Prevents the hero from lingering on doors and accidentally re-transitioning.

## What's next

The thief walks two rooms. He passes through doors. He doesn't yet *pick anything up* — the gold in both rooms is decorative, the altar's offerings symbolic at best. There's also no concept of an exit, no "you've finished the level" state, no end to the loop he's in.

Unit 6 adds both. **Pickup**: stepping onto a GOLD cell removes it from the room data, increments a score counter, and the thief continues walking. **Goal**: a single EXIT cell in the antechamber (or wherever the brief settles on); stepping onto it triggers a "the keep stands" state — the win condition that closes the title → play → win → restart loop.

By the end of Unit 6 the thief steals gold, finds the exit, and wins. The first complete game-state loop in Shadowkeep — and the foundation Unit 7 (the beeper sings) hangs SFX off, and Unit 8 (the keep stands) wraps in a title screen.
