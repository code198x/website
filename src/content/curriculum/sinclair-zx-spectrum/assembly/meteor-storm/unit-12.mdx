A pool needs two operations: find somewhere to put a new object, and visit the objects that already exist. Both are short walks through the same memory layout.

Use the same complete program as the previous lesson. Our three events are deliberately small enough to follow: X=80 at speed 2, X=116 at speed 3, then X=170 at speed 4, with twenty course steps between spawns.

## Find a free record

`spawn` sets IX to the first record and B to the twenty-slot capacity. At `spawn_find` it reads offset 2. Zero means free, so the search branches to `spawn_found`. Otherwise `ld de,4` and `add ix,de` advance one record; DJNZ decrements the remaining count.

At a free slot, the routine writes X, Y=24, active=1 and speed, then draws the new meteor. Setting an active flag without initialising position and speed would let old values become a new object.

<AssemblyExcerpt checkpoint="object-pool" from="spawn:" to=" ; XOR removes" />

If every slot is occupied, the routine sets `pool_overflow` and returns. It does not write beyond the reserved pool. This schedule should never fill twenty slots; the flag makes a broken capacity assumption observable.

## Visit occupied records only

`advance_meteors` starts at the first slot and tests active before doing any work. An active object erases its image, advances by its own speed, checks retirement/contact and draws its surviving image. Then IX advances by four and B counts down. Empty slots take the skip path but still advance the pointer and counter.

Drawing changes B, so the caller uses `push bc` and `pop bc` around `draw_meteor`. Without that preservation, the drawing row counter would replace the pool's remaining-slot counter. A routine's clobber list matters most when it is called inside another loop.

<Question prompt="Why does count_objects visit all twenty slots instead of assuming the occupied ones come first?">

Objects leave at different times. Slot 1 can become free while slot 2 is still active, and the next spawn may reuse slot 1. The occupied records need not form one unbroken prefix. Testing each active byte handles those holes.

</Question>

## Make the capacity problem visible

Change `SLOTS equ 20` to `SLOTS equ 1`. Assemble, steer away from the first meteor and watch `pool_overflow` when the next event tries to spawn. This is a deliberate capacity experiment, not a new difficulty mode: failed spawns still consume events in this small implementation. Restore twenty slots before continuing.

<Question prompt="The full pool refuses a spawn safely. Does that preserve the same game?">

No. We stayed inside the reserved memory, but the failed spawn still consumed a
course event. A missing meteor removes a hazard, so the challenge can change.
Memory safety and preserved game rules are different checks.

For this experiment, restore the capacity and confirm that the overflow flag
stays clear for the intended course. A future game could deliberately drop a
decorative effect when busy, but it would need to identify that effect as optional.
We should not silently apply the same policy to collision checks, scoring or
required hazards.

</Question>

A pool makes storage predictable, but it does not prove the chosen capacity is enough. The eventual course is checked against that bound. We have made one explicit allocation rule—first free slot—not built a general-purpose object framework.
