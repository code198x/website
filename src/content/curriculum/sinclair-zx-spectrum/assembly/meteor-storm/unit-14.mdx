A meteor moving sideways every update would cross the screen too quickly. We will give it a small signed drift, applied less often than its downward movement.

Each object gains offset 4: drift. Its five-byte record is now X, Y, active, downward speed, drift. Event records also gain a drift byte, becoming four bytes long. Update every stride together: the pool walk, the reserved pool size and the event-address calculation.

<MeteorExperiment checkpoint="drift" bytes={["ship_x","wave"]} words={["ticks"]} poolStride={5} controls="course" />

The accepted drift values are -1, 0 and +1 pixel. The inspector displays the signed interpretation. In the byte table, -1 is stored as 255: adding it to X has the same low-byte result as subtracting one.

## Use the course counter as a cadence

The code reads the low byte of `ticks` and applies `and 3`. Only a zero result permits horizontal motion. That is once every four course steps. Downward motion still happens on every step, at each object's own speed.

This separates two rates: a meteor falling four pixels per step travels sixteen pixels down while drifting just one pixel sideways. With no boost and 25 steps per second, nonzero horizontal drift averages 6.25 pixels per second.

<AssemblyExcerpt checkpoint="drift" from=" ld a,(ticks)" to="drift_done:" />

The addition uses an ordinary byte operation. At x=80 with stored drift 255, the low byte of 80+255 is 79. We interpret that stored pattern as -1 because of the agreement established by the data, not because memory remembers a signed type.

## Reflect before leaving the playfield

After adding drift, the code clamps X to 8 or 224 if needed and reverses the stored direction. At the left edge it writes +1; at the right edge it writes 255. This gives the next horizontal update a direction back into the playfield.

<Question prompt="A meteor at x=8 has drift -1. What are X and drift after its next horizontal update?">

The proposed X is 7, below the allowed bound. The routine stores X=8 and drift=+1. It does not store 7 for one frame and repair it later. The next drift opportunity moves to 9.

</Question>

Change `and 3` in the drift gate to `and 7`. Sideways movement now happens every eight course steps while downward movement stays unchanged. Try it before making drift stronger: frequency and distance per change are separate design controls.

Restore the accepted four-step cadence. The slight uncertainty should make dodging more interesting without making trajectories unreadable. Stars, when added next, will deliberately ignore drift and fall straight down.
