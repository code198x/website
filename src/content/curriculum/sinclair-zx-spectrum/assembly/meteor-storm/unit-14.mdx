A longer storm can be data rather than a longer sequence of special-case instructions. We will replace the three meteors that `new_game` starts with a prepared course of one hundred meteors, released one at a time.

The event table lives after the sprite data in `assets.inc`, at `meteor_events`. At this stage each event has three bytes: **X, speed, delay until the next event**. `WAVES equ 100` names the number of events. The event index is the new byte `wave`; it counts individual spawns, not a whole row of meteors.

<MeteorExperiment checkpoint="fixed-course" bytes={["wave","active_count","phase","pool_overflow"]} poolStride={4} controls="course" />

The X positions and speeds vary, but the table is fixed. Retry gives the same course. A host-side generator prepared the scattered values; the Spectrum is not choosing new random numbers during each run. Repeatability lets a player learn a route and lets us reproduce a failure.

## Count down, then read a record

A second new byte, `wave_timer`, counts course steps until the next event. In `new_game`, `ld a,20` and `ld (wave_timer),a` take the place of the three spawns. The main loop calls the new `waves` routine once per update, after the hull check. It returns at once when `wave` has reached `WAVES`. Otherwise it decrements the timer, and when that reaches zero it calculates the event address as `meteor_events + wave*3`, reads the three fields, and loads the next delay into the timer. Then it increments wave and jumps to `spawn`, whose RET returns straight to the main loop.

<AssemblyExcerpt checkpoint="fixed-course" from="waves:" to="spawn:" />

The multiplication here is three additions of the index to HL. It is short because the event record is only three bytes. When we later add drift and kind, the event stride must change with the data layout.

A delay belongs to the event just read: it says how long to wait **after this spawn** before reading the next. The initial twenty-step wait comes from `new_game`, before any event has been read.

## Do not finish while the last meteor is falling

Reaching `WAVES` means there are no more events to read. It does not mean the screen is clear. The completion check in the main loop now asks both questions: has `wave` reached `WAVES`, and is `active_count` zero? Either answer "no" branches to the new label `race_continue` and the next update.

<AssemblyExcerpt checkpoint="fixed-course" from=" call waves" to="new_game:" />

Watch the final spawn on a successful route: wave reaches 100 while active_count remains positive. The game keeps updating those objects until they leave. Contact is checked before the completion decision, so a fatal hit does not become a win just because the table is exhausted.

<Question prompt="The final event's speed is 2 and it spawns at y=24. Can the game finish on that spawn's step?">

No. The new meteor is active and still near the top. At that speed it needs seventy-five movement updates to reach retirement at y=174. Event exhaustion and object exhaustion describe different things.

</Question>

For a shorter experiment, set `WAVES equ 3` without deleting the longer table. The program reads only the first three entries. The third, X=42 at speed 4, is read on update 36, but CLEAR SPACE waits until update 74, when that meteor passes y=174. Steer through them and check that it waits for the last object. Restore 100 to play the full meteor-only course. Do not increase WAVES beyond the number of complete records: the routine trusts that bound.
