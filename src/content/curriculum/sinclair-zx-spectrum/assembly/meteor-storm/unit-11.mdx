Three independent meteors need three sets of state. Rather than inventing a new variable name for each one, we will place equal-sized records next to each other.

A **record** is a group of values describing one thing. Our first meteor record has four bytes:

| Offset from its start | Meaning | Example |
|---|---|---|
| 0 | X | 80 |
| 1 | Y | 24 |
| 2 | Active: 0 free, 1 occupied | 1 |
| 3 | Downward speed | 2 |

The pool reserves twenty records with `objects: defs SLOTS*4`. `defs` reserves bytes in the assembled program. Twenty times four is eighty bytes, and that capacity stays fixed while the game runs.

Open **Read the active object records**. Three events create meteors at different X positions and speeds. Each row is a live read of one occupied slot. It is not a prediction of where a meteor ought to be. Q restarts; R retries after a result.

## Let IX identify the current object

IX is a sixteen-bit index register. `ld ix,objects` points it at the first record. `(ix+1)` means the byte one address after IX, so `ld a,(ix+1)` reads this object's Y. The same instruction works for the next object after IX advances by four.

The record layout is an agreement between every routine that reads or writes objects. If spawn writes speed at offset 3 but movement reads offset 2, changing the drawing routine cannot repair it.

<Question prompt="If objects starts at $9000, where are the second record's Y and the third record's speed?">

The second record starts at `$9004`, so its Y is `$9005`. The third starts at `$9008`, so its speed is `$900B`. Add the record stride first, then the field offset. These example addresses explain the layout; use the assembled symbols for the running program's actual addresses.

</Question>

## Separate existence from visibility

The active byte tells us whether a record belongs to an object. A zero byte is a free slot even if old X, Y and speed values remain there. We do not need to erase every field when an object leaves; the next spawn will replace them before setting it in motion.

This replaces `meteor_x`, `meteor_y` and the single `active` variable. The complete checkpoint also contains the loops that operate on these records, which we trace next, and several routines that later lessons explain; [the map at the end of this lesson](#what-else-the-program-now-contains) names them. The ship keeps its own `ship_x` because there is only one player ship and its behaviour differs from falling objects.

Try following two rows at once. A faster meteor can move farther per update even though both receive updates from the same clock. Separate positions and speeds make that independence possible; adding a second drawing call alone would only make a second picture of the same state.

## What else the program now contains

This checkpoint grows from about 330 lines to about 530. Besides the pool, it now runs a whole attempt: a course of events, a result screen and a retry. Those parts work already, but we study them later. This map says what each one does and where it is explained, so nothing in the listing or the inspector is a mystery in the meantime.

| Routine or data | Its job | Explained in |
|---|---|---|
| `spawn`, `advance_meteors`, `count_objects` | Fill the first free record; erase, move, check and redraw each occupied record; count occupied records into `active_count`. Each walks the pool with IX as the current record and B as the slots left. | [Unit 12](../unit-12/) |
| `pool_overflow` | Set to 1 when `spawn` finds no free slot, so a broken capacity assumption shows up instead of writing past the pool. | [Unit 12](../unit-12/) |
| `waves`, `wave_timer`, `meteor_events` | Count down course steps; at zero, read the next three-byte event (X, speed, delay) and call `spawn`. `wave` counts the events read so far. | [Unit 13](../unit-13/) |
| Completion check | After the hull check, the run is won only when every event has been read (`wave` equals `WAVES`) and `active_count` is zero. | [Unit 13](../unit-13/) |
| `hull` | The ship's one life. `new_game` sets it to 1, contact clears it, and the main loop leaves for `lost` when it reads zero after moving the meteors. | [Unit 22](../unit-22/) |
| `erase_ship`, `draw_ship`, `ship_visible` | `draw_ship` draws the ship and sets `ship_visible`; `erase_ship` removes it only while that flag says an image is on screen, so an XOR erase never draws a ship onto an empty screen. | Builds on [unit 5](../unit-05/) |
| `title`, `new_game` | `title` waits for keys to be released, then calls `new_game`. That routine clears the screen, zeroes every byte from `state_start` to `state_end`, then sets `phase` to 1 and restores the ship position, `hull`, the first event delay and the frame baseline. | [Unit 21](../unit-21/) |
| `last_frame`, `frame_delta`, `ticks` | Each accepted update stores how many frames passed since the last one; `ticks` counts course steps. Nothing reads `frame_delta` yet: it is a measurement. | [Unit 17](../unit-17/) |
| `lost`, `won`, `result`, `release_keys` | `lost` sets `phase` to 2 and `won` sets 3; both show one result screen where R starts a new run and Q returns to `title`. `release_keys` waits until Space, Q and R are all up, so a held key cannot trigger the next phase. It changes AF and BC. | [Unit 22](../unit-22/) |
