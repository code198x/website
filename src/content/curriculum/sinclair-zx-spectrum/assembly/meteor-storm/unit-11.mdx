Three independent meteors need three sets of state. Rather than inventing a new variable name for each one, we will place equal-sized records next to each other.

A **record** is a group of values describing one thing. Our first meteor record has four bytes:

| Offset from its start | Meaning | Example |
|---|---|---|
| 0 | X | 80 |
| 1 | Y | 24 |
| 2 | Active: 0 free, 1 occupied | 1 |
| 3 | Downward speed | 2 |

The pool reserves twenty records with `objects: defs SLOTS*4`. `defs` reserves bytes in the assembled program. Twenty times four is eighty bytes, and that capacity stays fixed while the game runs.

Open **Read the active object records**. Three events create meteors at different X positions and speeds. Each row is a live read of one occupied slot. It is not a prediction of where a meteor ought to be. Q restarts; R retries after a result.

## Let IX identify the current object

IX is a sixteen-bit index register. `ld ix,objects` points it at the first record. `(ix+1)` means the byte one address after IX, so `ld a,(ix+1)` reads this object's Y. The same instruction works for the next object after IX advances by four.

The record layout is an agreement between every routine that reads or writes objects. If spawn writes speed at offset 3 but movement reads offset 2, changing the drawing routine cannot repair it.

<Question prompt="If objects starts at $9000, where are the second record's Y and the third record's speed?">

The second record starts at `$9004`, so its Y is `$9005`. The third starts at `$9008`, so its speed is `$900B`. Add the record stride first, then the field offset. These example addresses explain the layout; use the assembled symbols for the running program's actual addresses.

</Question>

## Separate existence from visibility

The active byte tells us whether a record belongs to an object. A zero byte is a free slot even if old X, Y and speed values remain there. We do not need to erase every field when an object leaves; the next spawn will replace them before setting it in motion.

This replaces `meteor_x`, `meteor_y` and the single `active` variable. The complete checkpoint also contains the loops that operate on these records; we will trace those next. The ship keeps its own `ship_x` because there is only one player ship and its behaviour differs from falling objects.

Try following two rows at once. A faster meteor can move farther per update even though both receive updates from the same clock. Separate positions and speeds make that independence possible; adding a second drawing call alone would only make a second picture of the same state.
