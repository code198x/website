We can move a row one pixel by shifting it. To draw a moving ship repeatedly, we will prepare the possible offsets once and select the one we need.

Keep the same sixteen-pixel pair from the previous lesson. Shift it by zero, one, two and up to seven places. Eight offsets cover every position inside a byte; the next position starts a new byte column.

## Make a table before using one

Replace the previous program with this complete checkpoint. `rows` contains eight pairs, each made by shifting `$8100` right by the row number. `defb` stores those byte values; it does not execute a drawing instruction.

## Read a pair, then move down

HL points into `rows`. DE points into screen memory, initially `$480C`. The loop copies the first byte, increments both pointers, then copies the second. `dec e` returns to the original screen column. `inc d` selects the next scanline in this eight-row group. B counts eight rows; `djnz` decrements it and repeats while it is nonzero.

That address shortcut works for this one group. It is not a general way to move down the Spectrum screen: crossing from the eighth scanline to the next group needs different address changes. The next experiment tackles the general layout.

## A table is a trade-off

Drawing can now look up bytes rather than shift each image while the game runs. We spend memory to save repeated work. The final ship has sixteen rows, four bytes per stored row and eight offsets: `16 × 4 × 8 = 512` bytes. Unshifted artwork alone would need only `16 × 3 = 48` bytes.

Why four stored bytes for artwork that is three bytes wide? Shifting can spill pixels into a fourth byte, just as our one-byte pattern spills into a second. We keep every stored row the same size so the next row is easy to locate.

<Question prompt="If the ship moves from x=15 to x=16, do we need a ninth shifted copy?">

No. At x=15 the byte column is 1 and the offset is 7. At x=16 the byte column is 2 and the offset returns to 0. The same eight copies work across the screen.
