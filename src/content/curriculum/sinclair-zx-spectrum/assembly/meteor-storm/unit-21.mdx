A fast run and a high-scoring run need not be the same run. We will remember separate session records and make a successful finish worth more when it is faster.

`best_time` is a word outside the per-run state range. It begins at 65535, hexadecimal `$FFFF`, meaning **no successful time yet**. `best_score` is a byte that begins at zero. Retry clears the run's state, not these records.

<MeteorExperiment checkpoint="records" bytes={["score","finish_points","best_score","phase"]} words={["elapsed","best_time"]} controls="boost" />

The inspector shows the stored sentinel as 65535 until a successful finish. The result screen represents it with dashes. Those are two views of the same “not set” condition, not a 1310-second record to beat.

## Award the finish bonus once

On success, convert elapsed to whole seconds and compute `max(0,100-seconds)`. Add that many score units. Each unit is ten points, so a 41.84-second run receives 590 finish points. A 20.92-second run receives 800.

The subtraction clamps a negative result to zero. The bonus is calculated on the win path, once, before displaying the result. A failed run gets no finish bonus.

## Compare words without an old carry

To consider a time record, load elapsed into HL and best_time into DE. Clear carry with `or a`, then use `sbc hl,de`. If the elapsed time is smaller, subtraction borrows and carry is set. Reload elapsed and store it as the new record. Otherwise keep the previous record.

A score record uses the opposite preference: larger is better. `save_score` compares the byte values and stores the run's score unless it is lower. It is called for both outcomes, so a failed run can still establish a high score.

<Question prompt="A failed run lasts only three seconds. Should it replace a successful twenty-second time?">

No. It did not complete the course. Only the won path considers best_time. The comparison is not enough by itself; the point at which it is called expresses what the record means.

</Question>

## Reset the right lifetime

Find `state_start` and `state_end`. `new_game` fills that range with zero, then restores the run's initial ship position, life and spawn countdown. The record bytes are outside the range. Moving them inside would make R forget them; failing to clear elapsed inside it would make the next run inherit old time.

Test a loss and retry: run state should reset. After a successful finish, retry again and check that the records survive. Returning to a title will also keep them once we add that phase. Reassembling deliberately creates a new machine and loses them. These are RAM records for one session, not data saved to tape or disk.

The accepted course keeps score within a byte: even twenty boosted stars plus the largest possible bonus is at most 140 units. Adding more rewards later would require checking that bound again.
