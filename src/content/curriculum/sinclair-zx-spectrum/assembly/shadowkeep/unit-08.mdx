Across seven units we built a thief, a keep, doors between rooms, gold to collect, an exit gated on completion, a victory state, and a beeper voice. Each unit shipped a piece. None of them shipped *the game*.

A game has a beginning before play starts and an end that returns to a beginning. A title screen the player sees first. A press-a-key moment that begins the work. A win condition that resolves the story. And — critically — a way *back* to the beginning, because a game played once is a demo; a game played twice is software.

This unit closes the loop. We add the title screen Unit 7 deliberately deferred, route victory back to it, and reset the room state so the next playthrough finds the keep restored. By the end Shadowkeep is a complete game: title → play → win → title → play, indefinitely. The keep stands.

## Stage 1: A title card

The title needs *text* — a recognisable "SHADOWKEEP" rendered in the centre of the screen. The Spectrum's ROM contains an 8 × 8 character bitmap for every printable ASCII character, starting at address `$3D00`. Each character is 8 bytes long. To draw 'S' at a screen cell, we copy its 8 bytes from `$3D00 + ('S' - 32) * 8` into the bitmap area at that cell's 8 successive scanlines.

The technique is two routines: `draw_string` walks a null-terminated text string and calls `draw_char` for each character; `draw_char` does the actual bitmap copy.

```z80
draw_char:
            push    de
            sub     32                  ; ASCII 32 ('space') is char 0 in ROM font
            ld      l, a
            ld      h, 0
            add     hl, hl              ; multiply by 8
            add     hl, hl
            add     hl, hl
            ld      bc, $3D00
            add     hl, bc              ; HL = ROM font byte 0 for this char

            ; Compute the destination bitmap address for cell (D=row, E=col).
            ; addr = $4000 | ((row & $18) << 8) | ((row & $07) << 5) | col
            push    hl                  ; save font ptr
            ld      a, d
            and     $18
            or      $40
            ld      h, a
            ld      a, d
            and     $07
            rrca
            rrca
            rrca
            or      e
            ld      l, a
            ex      de, hl              ; DE = bitmap dest, HL = saved row/col
            pop     hl                  ; restore HL = font ptr

            ; Copy 8 bytes from font to bitmap, advancing destination
            ; by $100 per byte (one scanline down within the cell).
            ld      b, 8
.line:
            ld      a, (hl)
            ld      (de), a
            inc     hl
            inc     d                   ; DE += $100 — one scanline lower
            djnz    .line

            pop     de
            ret
```

The bitmap address formula `$4000 | ((row & $18) << 8) | ((row & $07) << 5) | col` is the Spectrum's [non-linear screen layout](/vault/hardware/ula) compressed into a single bit-twiddle. Three `RRCA`s implement the `<< 5` (equivalent to shifting right 3 in the destination because we rotate, not shift). The `inc d` in the copy loop advances the bitmap address by exactly $100 — which, in the Spectrum's screen layout, is one scanline downward within the same character cell. Eight increments draws all eight scanlines of the character.

Beyond the bitmap, we also need to set the attribute byte for each cell under the title — otherwise the painted pixels are invisible (`PAPER 0 INK 0`). `draw_title` fills 10 attribute cells starting at row 6 col 11 with `$07` (INK 7 white on PAPER 0 black) before walking the text.

## Stage 2: Title with music

Unit 7 built a beeper driver that plays a looping title theme. This stage glues it onto Stage 1's title — title shows, music plays — by appending Unit 7's `play_theme`, `play_note`, and `melody` table to the file and calling `play_theme` after `draw_title`. Six bytes of new control flow; a hundred-odd bytes of music driver.

```z80
start:
            ; ...
            call    clear_to_black
            call    draw_title
            jp      play_theme          ; runs forever; no return
```

The `jp` (rather than `call`) reflects that `play_theme` never returns in Stage 2 — the music loops indefinitely via the `$FF` marker at the end of its melody table. Reset the machine to escape; Stage 3 will add a SPACE-to-start gate.

## Stage 3: Title to game

A title with music is presentation. To make it a *game* we need to act on the player's "press space to begin." This stage adds two things:

1. **A prompt line.** A second piece of text — "PRESS SPACE TO BEGIN" — rendered in cyan below the title. Same `draw_string` machinery, different row/col/attribute.

2. **SPACE polling between notes.** The music driver is CPU-blocking — while a note plays, the CPU is in the `play_note` inner loop and can't read the keyboard. We poll SPACE in the `play_theme` dispatcher, between notes, and `RET` if it's down. Worst-case response latency is one note duration (~500 ms); typical is half that.

```z80
play_theme:
            ld      hl, melody
.next_note:
            ; Check SPACE before each note.
            ld      bc, $7FFE           ; keyboard half-row with SPACE on bit 0
            in      a, (c)
            bit     0, a
            ret     z                   ; SPACE down → return to caller
            ; ... normal note dispatch ...
```

Once `play_theme` returns, control flows into the gameplay path. We bring in Unit 6's locked-until-cleared logic verbatim — `clear_to_stone`, `draw_current_room`, `try_move`, `do_transition`, `victory` and friends. The keep we built across six units is now what the title screen leads into.

The victory routine is still Unit 6's halt-forever — collect everything, step on the exit, the BORDER goes green, the program stops. Stage 4 will route victory back to the title instead.

## Stage 4: The keep stands

Two changes from Stage 3 turn a one-shot playthrough into a complete looping game.

### Change 1: Restorable room data

Stage 3's gold pickup mutates `room_data_great_hall` in place — when the thief steps on a gold cell, the byte at the cell's position in the table is overwritten with `FLOOR`. After a complete playthrough the table is permanently emptied. A second playthrough would find an already-stripped keep.

The fix: keep the source table immutable, and copy it to a RAM workspace before each playthrough. Rename `room_data_great_hall` → `room_data_great_hall_src`; reserve 352 bytes of zero-initialised RAM at `room_data_great_hall`; LDIR copy source → workspace each time the game starts.

```z80
init_state:
            ld      hl, room_data_great_hall_src
            ld      de, room_data_great_hall
            ld      bc, 352
            ldir
            ld      hl, room_data_antechamber_src
            ld      de, room_data_antechamber
            ld      bc, 352
            ldir
            ret
```

Two `LDIR`s. 704 bytes copied each playthrough; 28 T-states per byte = under 20,000 T-states = less than one frame. Free.

The `room_table` (which `draw_current_room` and `cell_addr_in_room_data` index into) keeps pointing at the workspace addresses. The source data is read only by `init_state`.

### Change 2: Victory returns to title

The Stage 3 victory routine set BORDER green and halted. Replace `HALT / JR .idle` with a brief celebration and a jump back to the title loop:

```z80
victory:
            ld      a, 4                ; green BORDER
            out     ($FE), a

            ; A three-note rising cheer.
            ld      a, 112              ; D6
            ld      de, 250
            call    play_note
            ld      a, 75               ; F6
            ld      de, 250
            call    play_note
            ld      a, 56               ; A6
            ld      de, 500
            call    play_note

            ; Hold the green BORDER briefly so the player registers victory.
            ld      b, 60
.hold:      halt
            djnz    .hold

            ld      a, 0
            out     ($FE), a
            jp      title_loop          ; the keep is replayable
```

The chord is three half-second notes on the green BORDER — a small period-appropriate fanfare. After the hold, BORDER returns to black and `JP title_loop` re-enters the title-and-music presentation, which plays until the player presses SPACE for another playthrough.

The whole structure:

```z80
title_loop:
            call    clear_to_black
            call    draw_title
            call    draw_prompt
            call    play_theme          ; returns when SPACE pressed
            ; ... brief settle delay ...
            call    init_state          ; restore room data
            call    init_game           ; reset hero, gold_taken, etc.
            jp      main_loop           ; play

; ... game loop, try_move, all the Unit 6 routines ...

victory:
            ; ... fanfare ...
            jp      title_loop          ; close the loop
```

`title_loop` is the program's main spine. The game runs through `main_loop`. Victory unwinds back via `jp title_loop`. The thief can replay the keep as many times as the player wants.

## Assemble and run

Each stage has its own `.asm`. The Makefile builds all four into `.tap` (for real-hardware load) and `.sna` (for screenshot and audio capture):

```bash
make
```

Load any of the four `.tap` files into your Spectrum emulator (Fuse, Spectaculator, Emu198x) or onto a real Spectrum Next. Type `RUN` at the BASIC prompt. Stages 1 and 2 are presentation-only; Stage 3 transitions to gameplay on SPACE; Stage 4 is the complete loop.

Stages 3 and 4 use Q, A, O, P for movement (the QAOP convention from [Quazatron](/vault/people/steve-turner) and many other Spectrum games). SPACE starts and re-starts the game.

## Try this: a longer prompt

In Stage 3 or 4, replace `"PRESS SPACE TO BEGIN"` with `"PRESS SPACE TO ENTER THE KEEP"`. The new string is 29 characters; the existing `PROMPT_COL` (6) places it just within the 32-column screen. The attribute fill loop's `PROMPT_LEN` constant needs updating to match — change it to 29 — otherwise the last seven characters will be drawn invisibly (correct bitmap, but no attributes turning them on).

Try other phrasing: "BEGIN THE WATCH", "ENTER, THIEF", "SHADOWKEEP AWAITS". The keep's identity is partly the writing on the title card.

## Try this: a different victory chord

The three-note chord in Stage 4's `victory` is D6 → F6 → A6 (an ascending D-minor arpeggio in octave 6). Try other resolutions:

- **C major** (bright resolution): C6 (126), E6 (105), G6 (84) — duration 300 each. A cheery "well done."
- **Held single note** (sombre triumph): D5 (227), duration 1500. One long bass note. Funereal.
- **Quick four-note flourish** (busy victory): C6, D6, E6, G6 with shorter durations (200 each). A racing-game-style "GOAL!"

The chord shapes the emotional register of victory. The same gameplay with three different chords feels like three different games.

## Try this: keep the title theme during victory

Currently the victory chord plays once, then the program returns to `title_loop` which restarts the music. The transition is abrupt — chord ends, brief silence, music begins again. For a smoother feel, you could *not* play a special chord on victory and let the music continue uninterrupted into the next title loop. (Just delete the `call play_note` calls in `victory` and leave only the green-BORDER hold.)

Alternatively, play a *truncated melody* on victory — a half-bar fragment of the title theme starting on the tonic — so the chord feels continuous with the title music rather than separate from it. This is a small composition exercise that improves the audio polish considerably.

## Try this: track playthrough count

Add a one-byte `playthrough_count` variable to game state. Increment it in `init_state`. On the title screen, after `draw_title` and `draw_prompt`, render the count to a fixed cell — single ASCII digit (`+ '0'`) at row 17 col 16. The player can see how many times they've completed the keep.

For multi-digit counts, walk the digits with a small printable-digit routine (divide by 10 to get each digit). Phase 2's high-score table will reuse this pattern.

## Try this: a slower title music

The current title theme has tempo wobble — the same `DURATION` byte plays for different wall-clock times depending on pitch (since higher notes finish more cycles per millisecond). For a more stately title-screen feel, double every duration in the melody table. The theme plays at half-speed; the keep feels more imposing.

Or pick a third — change duration 64 to 96, 128 to 192, 32 to 48 — for a tempo that splits the difference. Composition is partly tempo selection.

## If it doesn't work

- **Title doesn't render?** Check that `draw_title` is being called (`call draw_title` in `title_loop`, not `jp draw_title`). Without the title call, the screen stays uniformly black after `clear_to_black`.
- **Title characters look corrupted?** The bitmap-address arithmetic in `draw_char` is sensitive to register state. Confirm `D` holds the row and `E` holds the column at every call to `draw_char`. If a previous instruction clobbered DE before calling draw_char, the addresses will be wrong.
- **Pressing SPACE does nothing?** Check the keyboard half-row constant. SPACE is on port `$7FFE`, bit 0. `LD BC, $7FFE / IN A, (C) / BIT 0, A` followed by `JR Z, ...` (active low — bit reads 0 when pressed). Wrong port or wrong bit means SPACE either never fires or fires constantly.
- **Game starts on SPACE but immediately returns to title?** The `space_settle` debounce loop is too short. Eight frames of `HALT` (160 ms) is usually enough but you may need 16 if the user holds SPACE longer. Without debounce, the game's keyboard polling immediately sees SPACE still held and `play_theme` is exited back to title before the player can act.
- **Second playthrough has empty rooms?** `init_state` isn't being called between playthroughs. Confirm `victory` ends with `jp title_loop` (not `jr` — distance may exceed 8-bit range) and that `title_loop` calls `init_state` before `init_game`.
- **Game crashes after victory?** Stack imbalance. The victory routine is reached via `jp victory` (a tail call) from `try_move.victory_now`. The caller of `try_move` (the keyboard handler in `main_loop`) expects `try_move` to return normally. If `victory` doesn't terminate cleanly via `jp title_loop`, returning would unwind to a stale frame. The clean path is: `try_move.victory_now` → `jp victory` → `jp title_loop` (never returning to the stale frame). The stack is reset implicitly by re-entering `title_loop` from the top of the program.
- **No music?** Check that `play_theme` is reachable from `title_loop` and that no instruction before it modifies the speaker bit unexpectedly. Output to port `$FE` with bit 4 stuck high or low silences the beeper.
- **Victory chord sounds wrong?** Each `play_note` call needs A=pitch and DE=duration before the call. Confirm both registers are loaded — common mistake is omitting `LD DE, ...` between chord notes, leaving DE at whatever the previous note left it (typically 0, which makes the next note silent).

## What you've learnt

- **The title screen as software.** A title screen is not a special engine feature; it's a normal program state (with its own rendering and its own input handling) that the game returns *to* as well as *from*.
- **Rendering text from the ROM font.** The Spectrum's character bitmaps at `$3D00` are public domain via the ROM. Eight bytes per character; `inc d` advances one scanline. Same technique works for any 8x8 font you supply in RAM.
- **The non-linear bitmap address formula.** `addr = $4000 | ((row & $18) << 8) | ((row & $07) << 5) | col` compresses the Spectrum's bizarre screen layout into a single bit-twiddle. Once written you almost never touch it again.
- **Setting attributes alongside bitmap.** Drawing pixels without setting the attribute byte gives invisible content. Drawing attributes without setting pixels gives coloured-but-empty cells. Both are needed for text.
- **The press-a-key gate.** A title screen needs an input event to advance. Poll the keyboard between music notes; return from the music loop when SPACE fires. The latency is tolerable for a "press any key" use case.
- **Source vs working-buffer pattern.** Mutable game state lives in a workspace; the *initial* state lives in a separate source table. `LDIR` copies source → workspace at game start. This is the foundation for any non-trivial game-state reset (save states, level select, retry-after-death).
- **The game loop's main spine.** `title_loop` → `play_theme` → `init_state` → `init_game` → `main_loop` → ... → `victory` → `title_loop`. The whole program's structure is captured in this chain. Every Spectrum game from 1982 onwards has some version of it.
- **`JP` for tail calls.** Where the called routine never returns (victory → title), `JP` is correct (no stack frame). Where it might return, `CALL` is correct. The distinction prevents stack overflow on long loops.
- **Tail-calling from victory back to title.** `JP title_loop` from inside `victory` doesn't unwind the stack — it just jumps. Acceptable because `title_loop` doesn't depend on any caller state, and the stack pointer is implicitly reset by long enough play (the SP wraps via the SP=$FFFF at boot down to wherever the SNA initial state put it; for our purposes the stack never grows beyond a few hundred bytes per playthrough).
