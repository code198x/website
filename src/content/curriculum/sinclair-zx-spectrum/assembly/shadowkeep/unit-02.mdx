The keep wakes with three torches against dark stone. That was Unit 1. The keep remembers it had lights.

Now it remembers it had *rooms*.

By the end of this unit there's a great hall: twenty-two cells wide, sixteen rows tall, sitting in the middle of the keep's dark stone like a room that's been there all along. Bright blue walls. Clean white floor. A stepped altar at the top centre with gold cascading down both sides. Drawn in 352 attribute writes, executed by a nested loop just twelve instructions long — and the same twelve instructions will draw every other room in the keep, all the way to Phase 2's full nine-room layout.

We'll get there in four stages: **one row of stone**, **the grid**, **the room**, **the great hall**. Each stage adds one idea.

## What's in front of you

The room is a 22-column × 16-row region of the attribute grid, positioned at row 2, column 5 of the full 32×24 Spectrum screen. That leaves:

- 5 cells of margin on each side — the off-room frame.
- 2 rows above the room — the future HUD strip (Phase 2 will put lives, score, and the room's name here).
- 6 rows below the room — atmospheric framing space.

```
Full Spectrum attribute grid: 32 columns × 24 rows

  cols:  0 ─ 4 │ 5 ─────────────── 26 │ 27 ─ 31
        ┌─────┼──────────────────────┼─────────┐
  rows  │     │                      │         │
   0-1  │     │       (HUD strip)    │         │
        │     ├──────────────────────┤         │
   2    │     │ $5845    THE ROOM    │         │
        │     │                      │         │
   3    │     │                      │         │
        │     │      22 cols ×       │         │
   ...  │     │      16 rows         │         │
        │     │                      │         │
   17   │     │                      │         │
        │     ├──────────────────────┤         │
  18-23 │     │     (atmosphere)     │         │
        └─────┴──────────────────────┴─────────┘
```

The room's top-left attribute address:

```
  address = $5800 + (row × 32) + column
          = $5800 + (2 × 32) + 5
          = $5800 + 64 + 5
          = $5845
```

This is the address we'll load into `DE` at the start of every drawing pass.

## Stage 1: One Row of Stone

The simplest possible use of DJNZ: lay 22 cells of wall in a single horizontal line.

```z80
            ld      a, WALL                ; WALL = $49, bright blue stone
            ld      de, $5845              ; row 2, col 5 — top-left of the room
            ld      b, 22                   ; loop counter: 22 columns

.row_loop:
            ld      (de), a                 ; write a wall cell
            inc     de                      ; advance to the next column
            djnz    .row_loop               ; loop until B reaches 0
```

Four instructions in the loop, twenty-two iterations, twenty-two wall cells. The keep is starting to remember.

### DJNZ — the Z80's tightest loop

`DJNZ target` does two things in one opcode:

1. **D**ecrement the **B** register.
2. **J**ump to `target` if the result is **N**ot **Z**ero.

That's the entire conditional-decrement-and-branch idiom in one instruction. To use it: load `B` with the iteration count, write the loop body, end with `djnz target`. The CPU handles the rest.

```
  Before the loop:  B = 22
  
  Iteration 1:  (loop body runs) → DJNZ: B becomes 21, not zero, jump back.
  Iteration 2:  (loop body runs) → DJNZ: B becomes 20, not zero, jump back.
  ...
  Iteration 22: (loop body runs) → DJNZ: B becomes 0, IS zero, fall through.
  
  After the loop:   B = 0
```

The body of our row_loop is `LD (DE), A` (write the byte) and `INC DE` (advance the destination pointer). After 22 iterations, we've written WALL into 22 consecutive attribute cells starting at `$5845` — the top row of the room.

## Stage 2: The Grid

One row was nice. We want a 22×16 area filled with walls — the full footprint of the room, every cell a wall (we'll hollow it out in Stage 3).

```z80
            ld      de, $5845              ; row 2, col 5 — room's top-left
            ld      b, 16                   ; outer counter: 16 rows

.row_loop:
            push    bc                      ; save outer counter
            ld      b, 22                   ; inner counter: 22 columns
            ld      a, WALL

.col_loop:
            ld      (de), a                 ; write a wall cell
            inc     de                      ; advance to the next column
            djnz    .col_loop               ; loop columns

            ; advance DE past the cells outside the room (skip 32-22=10)
            ld      a, e
            add     a, 32 - 22
            ld      e, a
            jr      nc, .no_carry
            inc     d
.no_carry:

            pop     bc                      ; restore outer counter
            djnz    .row_loop               ; loop rows
```

Twelve instructions, two new ideas: **nested DJNZ** and **the stack**.

### Nested DJNZ

We have two counters — outer (rows) and inner (columns). But DJNZ only knows about `B`. If we use `B` for both, the inner loop clobbers the outer.

```
  Outer loop sets B = 16  ← outer count
  Outer loop body starts
    Inner loop sets B = 22 ← outer count obliterated
    Inner loop runs 22 times, B = 0 after
  Outer DJNZ runs — but B is now 0, so it falls through immediately!
  Outer loop has run exactly once.
```

That's the bug. We need to *save* the outer count before the inner loop runs, and *restore* it after.

### Push and pop — the stack

The Z80 has a stack: a region of memory that grows downward, addressed by the SP (stack pointer) register. `PUSH BC` writes the BC register pair onto the stack and decrements SP by 2. `POP BC` reads BC back off the stack and increments SP by 2.

```
  Before PUSH BC:
    SP = $FF50 (say)
    BC = $1000 (B=$10=16, the outer count)
    
  After PUSH BC:
    SP = $FF4E (decremented by 2)
    Memory at $FF4E-$FF4F = $1000 (saved BC)
    BC = $1000 (unchanged, but now also on the stack)
    
  Now the inner loop can use B freely. After it finishes:
    BC could be anything.
    
  After POP BC:
    SP = $FF50 (back to where it was)
    BC = $1000 (restored from the stack)
```

The stack lets us "borrow" registers — save them, use them for something else, restore them. Push and pop come in pairs; each push must have a matching pop, or the stack drifts.

### Advancing DE between rows

After the inner loop draws 22 cells, `DE` points one past the right edge of the row — column 27 of the same row. We need it to point to column 5 of the *next* row.

The screen is 32 cells wide; the room is 22 cells wide; so we need to skip `32 - 22 = 10` cells to reach the next row's leftmost room cell.

```
                ←─── 32 columns ───→
  cols:   0 1 2 3 4 5 6 7 ... 26 27 28 29 30 31
  
   row 2:        └─── 22 room cols ─┘└── 10 ──┘
                                     skip these
   row 3:        ↑
                 we want to land here
```

`DE` is a register pair: `D` is the high byte, `E` is the low byte. We can't `ADD DE, n` with an 8-bit immediate, but we can add to E via the accumulator, then handle the carry into D manually:

```z80
            ld      a, e
            add     a, 32 - 22          ; A = E + 10
            ld      e, a                 ; E = E + 10
            jr      nc, .no_carry        ; if E didn't wrap, skip the next instruction
            inc     d                    ; E wrapped 0xFF → 0x00, so bump D
.no_carry:
```

Most of the time `E + 10` fits within a byte and `JR NC` jumps past `INC D`. Occasionally the addition wraps (E was 0xF8 or higher), and the carry flag is set; we fall through to `INC D` to bump the high byte. This is the Z80 way: small instructions, careful flag handling, the programmer always in charge.

## Stage 3: The Room

Same nested loop, same 16 × 22 iteration. What changes is the loop body. Instead of writing a constant value, we read each byte from a data table.

```z80
            ld      hl, room_data          ; source: room data
            ld      de, $5845              ; destination: attribute memory
            ld      b, 16                   ; outer: 16 rows

.row_loop:
            push    bc
            ld      b, 22                   ; inner: 22 columns

.col_loop:
            ld      a, (hl)                 ; read attribute byte from data
            ld      (de), a                 ; write to attribute memory
            inc     hl                      ; next source byte
            inc     de                      ; next destination cell
            djnz    .col_loop

            ; (row advance — same as Stage 2)
            ld      a, e
            add     a, 32 - 22
            ld      e, a
            jr      nc, .no_carry
            inc     d
.no_carry:

            pop     bc
            djnz    .row_loop
```

Two new ideas: **HL as a source pointer** alongside DE, and **data-driven rendering**.

### Two pointers — HL and DE

HL and DE are both 16-bit register pairs. They can both hold memory addresses. The Z80 has dedicated instructions to read through HL (`LD A, (HL)`) and write through DE (`LD (DE), A`). Used together, they form the canonical "copy a region of memory to another region" pattern:

```
  At every iteration:
  
    A ← byte at (HL)       ← read source
    byte at (DE) ← A       ← write destination
    HL = HL + 1             ← source pointer forward
    DE = DE + 1             ← destination pointer forward
```

After 352 iterations (22 × 16), 352 bytes have been copied from `room_data` (somewhere in our program) to attribute memory starting at `$5845`. Every cell of the room takes whatever value the data table says it should.

### Data-driven rendering

This is the framework lesson of Phase 1. The drawing code knows nothing about the room — it doesn't know where the walls are, doesn't know about the altar, doesn't know about gold. It just copies bytes. The room's identity lives entirely in `room_data`.

```
  room_data:
    [row 0:  22 bytes describing the top row's cells]
    [row 1:  22 bytes describing row 1's cells]
    [row 2:  22 bytes ...]
    ...
    [row 15: 22 bytes describing the bottom row's cells]
    
  Total: 352 bytes. Layout matches the screen exactly:
  byte at offset (row × 22) + column = cell at room (row, column).
```

Stage 3's data is a uniform room — walls all around the perimeter, white floor inside. The `rept 14` block makes this compact:

```z80
            rept 14
                defb    WALL
                defb    FLOOR, FLOOR, ..., FLOOR  ; 20 floors
                defb    WALL
            endm
```

That single block, assembled, produces 14 identical rows of `[WALL, 20×FLOOR, WALL]` — 308 bytes from four lines of source. Plus a top wall row and a bottom wall row (22 walls each), bringing the data table to 352 bytes total.

## Stage 4: The Great Hall

The drawing code does not change. Not a line different from Stage 3.

What changes is the data. The uniform room becomes the great hall — with a stepped altar at the top centre and gold cascading down each side.

```z80
            ; Row 1 — broad altar (3 cells wide) flanked by gold arcs
            defb    WALL
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    GOLD, GOLD, GOLD
            defb    WALL, WALL, WALL
            defb    GOLD, GOLD, GOLD
            defb    FLOOR, FLOOR, FLOOR, FLOOR
            defb    WALL

            ; Row 2 — altar shoulders narrow, gold continues
            defb    WALL
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    GOLD, GOLD
            defb    WALL, WALL, WALL
            defb    GOLD, GOLD
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    WALL

            ; Row 3 — altar steps: columns separated by aisle, single gold each side
            defb    WALL
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    GOLD
            defb    WALL
            defb    GOLD
            defb    WALL
            defb    GOLD
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    WALL

            ; Row 4 — altar columns frame the aisle (no gold)
            defb    WALL
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    WALL
            defb    FLOOR
            defb    WALL
            defb    FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR, FLOOR
            defb    WALL
```

Four rows of altar geometry, descending from row 1 to row 4. Then rows 5 through 14 are the same uniform `WALL + 20 FLOORS + WALL` we used in Stage 3, and row 15 is the bottom wall.

The altar reads as a *structure*: a wide top tier of three wall cells, narrowing shoulders (two), then two parallel columns that frame an aisle of one floor cell. Gold cascades down each side: three across the top, two on the shoulders, one at the steps. The eye lands on the altar; the gold reads as sacred offerings; the aisle invites a hero forward.

## Assemble and run

Each stage has its own `.asm` file. The Makefile builds all four into `.tap` (real-hardware loading) and `.sna` (screenshot capture):

```bash
make
```

Load any of the four `.tap` files into Fuse, your emulator of choice, or a real Spectrum Next. Type `RUN` at the BASIC prompt to see each stage.

## Try this: an empty room

Open `04-the-great-hall.asm`. Find the rows 1–4 altar block. Replace all four rows with the uniform `WALL + 20 FLOORS + WALL` pattern. Reassemble.

The great hall becomes a plain rectangular room — no altar, no gold, just walls and floor. The drawing code is unchanged. Only the data changed. That's the point.

## Try this: a different palette

Find the `WALL equ $49` line. Change `$49` to `$09` (no BRIGHT). Reassemble. The walls drop from vivid bright blue to a darker, more muted blue — closer to the dark stone outside the room. The visual contrast that made the room *pop* against the keep is gone; the room and the keep blend together more.

This is what palette restraint costs you when you don't take it seriously. The BRIGHT bit on the walls is what makes the room read as a distinct space rather than a continuation of the keep's stone. One bit in one constant, and the entire visual identity shifts.

## Try this: a smaller room

In all four stages, change `ld de, $5845` to `ld de, $5867` — that's $5845 + 34, or 32+2, which moves the top-left right by 2 columns and down by 1 row. The room shifts. The dark stone outside it grows on the top and left. The keep's framing of the room changes.

You can move the room anywhere in the keep with one address change. In Phase 2 we'll use this technique to draw nine rooms in nine positions, all from the same drawing code — but with nine different `room_data` tables.

## Try this: a tiny room

Change `ld b, 16` (outer counter) to `ld b, 4`. Change `ld b, 22` (inner counter) to `ld b, 8`. The room is now 8 columns by 4 rows. You'll also need to change the row-advance constant: `add a, 32 - 22` becomes `add a, 32 - 8` (or `add a, 24`).

The room is now tiny — closer to a cupboard than a hall. The drawing code accommodates it without complaint. Loop dimensions are data too; we just happen to load them into registers rather than store them in tables.

## If it doesn't work

- **Only one row drawn?** The outer DJNZ probably isn't seeing B correctly. Confirm the `push bc` / `pop bc` pair surrounds the inner loop. If you accidentally `pop bc` *inside* the inner loop, the outer count won't be there when DJNZ runs.
- **Room drawn in the wrong place?** Check the `ld de, $5845` line. Off-by-32 means wrong row; off-by-1 means wrong column. Recompute: `$5800 + (row × 32) + col`.
- **Room renders as a diagonal stripe?** The row-advance arithmetic is broken. After each inner loop completes, DE should advance by `32 - 22 = 10`. If you forgot to advance DE between rows, every row draws from where the last one ended, producing a wrapping diagonal.
- **Room renders too short or too tall?** Check the outer counter is 16 and the inner is 22. Swapping them produces a 22-row × 16-column room — which won't fit at the original `$5845` and overflows.
- **Walls present but interior is dark stone?** The data table is being read but most cells happen to be `$08`. Confirm the `rept 14` block has the correct WALL/FLOOR pattern and check the constants at the top of the file.
- **Assembly error on `push bc`?** Make sure `bc` is lowercase or matches your assembler's preferred case. `pasmonext` accepts both.
- **Memory garbled below the room?** The room draws 352 bytes starting at `$5845`. The 16th row's last cell lands at row 17, col 26 — `$5800 + (17 × 32) + 26 = $5C1A`... wait, that's past `$5AFF`. Actually attribute memory ends at `$5AFF`. The room's bottom-right at row 17 col 26 is `$5800 + 544 + 26 = $5A22` — comfortably inside attribute memory. If you ever see corruption *below* the room, double-check your row/col counts.

## What you've learnt

- **The room's position on the screen.** Top-left at `$5845` = row 2, col 5. Five-cell margins on either side, two rows above for the HUD, six rows below for atmospheric framing.
- **`DJNZ target`.** The Z80's tightest two-instruction loop. Decrement B, jump if not zero. One register, one branch, one byte of opcode.
- **Nested DJNZ.** The 2D iteration pattern — outer DJNZ wraps inner DJNZ. Both counters use B, so the outer count is saved with `push bc` and restored with `pop bc`.
- **The stack.** A region of memory addressed by SP that grows downward. `push` saves a register pair; `pop` restores it. Push and pop come in matched pairs.
- **16-bit pointer arithmetic from 8-bit pieces.** Adding to DE via the accumulator: `LD A, E` / `ADD A, n` / `LD E, A`, then `JR NC, skip` / `INC D` to handle the carry into the high byte.
- **HL and DE as a read/write pointer pair.** `LD A, (HL)` reads, `LD (DE), A` writes, `INC HL` / `INC DE` advance. The canonical Z80 region-copy idiom.
- **Data-driven rendering.** The drawing code is room-agnostic; the room's identity lives in `room_data`. Same engine, any room — the foundation Phase 2 will lean on to draw all nine rooms.
- **`rept N ... endm`.** Assembler-level repetition. The block expands at assembly time; the source stays compact, the binary contains all the copies.
- **The framework lesson.** Code and data are separate concerns. Build the engine once; describe each room as data. By Phase 2 this pays off ninefold.

## What's next

The keep has light. The keep has a room. What it doesn't have is anyone *in* the room.

In Unit 3 a hero arrives — a hooded thief, eight pixels wide, eight pixels tall, drawn as actual pixel art rather than as a coloured cell. We'll meet the Spectrum's bitmap memory for the first time: `$4000` through `$57FF`, the 6144 bytes that hold the actual pixels of every cell on screen. We'll learn how to design a 1-cell sprite at the Spectrum's smallest unit, how to write 8 bytes of bitmap data into the right place in memory, and how to put a recognisably *human* figure into the great hall.

We'll also use the same technique to give the walls *texture* — a stone-block bitmap pattern underneath the attributes, so the walls read as actual stone rather than just blue rectangles. The keep is about to look like a real place.
