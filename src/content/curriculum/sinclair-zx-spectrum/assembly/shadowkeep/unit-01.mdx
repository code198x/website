The great hall is silent. Stone walls darker than they should be. The keep's lights have been out since the night the shadows came.

You write your first sixteen [Z80](/vault/hardware/z80) instructions, and the keep begins to remember it was once a home.

By the end of this unit there are three torches on the wall — one steady, one bright, one struggling to hold its flame. The BORDER of the screen is black, the way the keep wants it. Every byte you wrote is one you can point at, and every byte on the screen is one you put there. Nothing is hidden setup; nothing is mystery. The keep is built byte by byte.

Three torches in a row, mid-screen. The leftmost flickers — the magic taint hasn't fully released its grip on it. The middle holds steady. The rightmost burns bright. Around them, eight hundred-odd attribute cells of dark stone. Outside the playable area, a black BORDER frames the whole.

We'll get there in four stages: **the dark**, **the first torch**, **two torches**, **the flickering torch**. Each stage is a small program that builds on the last; each stage adds one new idea.

## The keep's vocabulary

Before we touch any code, the language of the keep. Every cell on the screen is one of eight types — distinguished entirely by the attribute byte at its address. The whole game's rules will read these bytes and act on them.

| Cell | Look | Attribute byte |
|---|---|---|
| Stone | Dark blue PAPER, INK 0 | `$08` |
| Floor | White PAPER, INK 0 | `$38` |
| Wall | Blue (INK 1) on blue PAPER | `$09` |
| Door (open) | Cyan PAPER, INK 0 | `$28` |
| Door (locked) | Cyan PAPER + FLASH | `$A8` |
| Treasure | Yellow PAPER + BRIGHT | `$70` |
| Key | Yellow PAPER + BRIGHT + FLASH | `$F0` |
| Hazard | Red PAPER + FLASH | `$90` |
| Exit | Green PAPER, INK 0 | `$20` |

This unit places three of these: stone (everywhere), a yellow PAPER cell, and a bright yellow PAPER cell — and one flickering bonus, the FLASH bit applied to bright yellow. The eight-cell vocabulary will fill out over the rest of Phase 1.

## The screen and its memory

The [ZX Spectrum](/vault/systems/zx-spectrum) has a strange and generous agreement with its programmer.

The 256-by-192-pixel screen is divided into a 32-by-24 grid of *character cells*, each one 8 pixels square. Every cell shares **one foreground colour and one background colour** — two colours per cell, no more, no fewer. Those colours live in their own block of memory, **attribute memory**, running from `$5800` to `$5AFF`. One byte per cell, 768 bytes in total.

```
Spectrum attribute memory: $5800 → $5AFF (768 bytes)

  col:   0   1   2   ...  31
  row 0  $5800 $5801 $5802 ... $581F
  row 1  $5820 $5821 $5822 ... $583F
  row 2  $5840 ...                $585F
  ...
  row 12 $5980 ...   $5990 ...    $599F   ← we'll use $5990
  ...
  row 23 $5AE0 ...                $5AFF
```

To find the address of any cell:

```
  address = $5800 + (row × 32) + column
```

For row 12, column 16:

```
  $5800 + (12 × 32) + 16
  $5800 + 384 + 16
  $5990
```

The Spectrum's video hardware reads that byte fifty times every second when it paints the cell at row 12, column 16. Write a value there and the hardware paints with it. Write a different value and the cell changes colour next frame. There is no "draw cell" function. There is the address, and there is the byte.

## The attribute byte

Each of those 768 bytes is eight bits, and each bit has a job:

```
  bit  │ 7    │ 6      │ 5  4  3 │ 2  1  0 │
       │ FLASH│ BRIGHT │  PAPER  │   INK   │
       │      │        │  (0-7)  │  (0-7)  │
```

- **INK** (bits 0–2): the foreground colour, 0–7. Whatever pixels in this cell are *lit* draw in this colour.
- **PAPER** (bits 3–5): the background colour. Pixels that are *unlit* draw in this colour.
- **BRIGHT** (bit 6): when set, both INK and PAPER use brighter versions of their colours.
- **FLASH** (bit 7): when set, the hardware alternates INK and PAPER about twice a second.

The eight colour numbers used by INK and PAPER are the same:

| 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| Black | Blue | Red | Magenta | Green | Cyan | Yellow | White |

This unit will write four different attribute byte values. Here's the bit decomposition of each — referenced when we use them:

```
  $08 (dark stone):    0 0 001 000   PAPER 1, INK 0
  $30 (yellow torch):  0 0 110 000   PAPER 6, INK 0
  $70 (bright torch):  0 1 110 000   PAPER 6 + BRIGHT, INK 0
  $F0 (flickering):    1 1 110 000   PAPER 6 + BRIGHT + FLASH, INK 0
```

Four bytes. Three torches and a stone. The keep's first chapter.

## Stage 1: The Dark

Before any single cell of meaning, the world is set. Two acts:

```z80
            ld      a, 0
            out     ($FE), a

            ld      hl, $5800
            ld      de, $5801
            ld      (hl), $08
            ld      bc, 767
            ldir
```

Seven instructions. Two new ideas: **OUT** for talking to ports, and **LDIR** for filling memory.

### OUT — the BORDER goes black

`OUT (port), A` sends the byte in register A to the named I/O port. Memory and ports are separate address spaces on the Z80; memory is where data lives, ports are where the hardware listens.

Port `$FE` is the Spectrum's main I/O port. When you *write* to it, the lower bits of the byte control three things:

```
  bit 4 │ bit 3 │ bits 2–0
  ─────┼───────┼──────────
  spkr │  MIC  │  BORDER
        │       │   (0-7)
```

The speaker (bit 4) we'll meet in Unit 7 when the title theme plays. The MIC line we'll ignore — it's for cassette saving. The BORDER bits — the lowest three — set the colour of the screen's outer frame, the area outside the playable 256×192 area. Same colour numbers as INK and PAPER.

When we load `A` with `0` (`0000 0000` in binary) and `OUT` to `$FE`, the lowest three bits are zero, so the BORDER becomes colour 0: **black**.

### LDIR — wash the screen in stone

The interior of the screen needs to be dark stone. We want every one of the 768 attribute cells from `$5800` to `$5AFF` to hold the value `$08` (PAPER 1 blue, INK 0 black). That's 768 identical writes, and a loop of 768 individual `LD` instructions would be ugly. The Z80 gives us a single instruction that does it: `LDIR`.

`LDIR` reads three register pairs:

```
  HL = source address
  DE = destination address
  BC = byte count
```

And then it performs this loop in hardware:

```
  while BC > 0:
      copy the byte at (HL) to (DE)
      HL += 1
      DE += 1
      BC -= 1
```

That's *one* Z80 opcode. The processor does all 767 iterations on its own.

The trick — and it's a beautiful one — is that you can use `LDIR` to *fill* memory with a constant value, not just copy it. Set `HL` to the first address. Set `DE` to the *next* address (`HL + 1`). Write the constant value once at `(HL)`. Then `LDIR` copies `(HL)` to `(HL+1)`, then `(HL+1)` to `(HL+2)`, then `(HL+2)` to `(HL+3)`, and so on. The first byte propagates forward through the entire range, like a wave.

```
  Before LDIR:
    $5800: $08    $5801: ??    $5802: ??    ...   $5AFF: ??
                                              
  Step 1:  copy ($5800) → ($5801)
    $5800: $08    $5801: $08    $5802: ??    ...   $5AFF: ??
                                              
  Step 2:  copy ($5801) → ($5802)
    $5800: $08    $5801: $08    $5802: $08    ...   $5AFF: ??
                                              
  ... 765 more iterations ...
                                              
  Final:
    $5800: $08    $5801: $08    $5802: $08    ...   $5AFF: $08
```

768 bytes filled, in one instruction.

## Stage 2: The First Torch

The keep is dark. Time to light the first torch.

```z80
            ld      a, $30
            ld      ($5990), a
```

Two instructions added on top of Stage 1. We've met both before in spirit — `LD A, value` loads an immediate value into the accumulator; `LD (address), A` stores A's value at a memory address.

What changed: one byte at `$5990`. Was `$08` (dark stone, set by Stage 1's `LDIR`). Now `$30` (PAPER 6 yellow, INK 0). The video hardware reads `$30` on its next pass and paints the cell at row 12, column 16 in yellow.

```
  Memory state after Stage 2:
  
    $5800 ─── $598F:   $08    (unchanged dark stone)
    $5990:             $30    ← we wrote this
    $5991 ─── $5AFF:   $08    (unchanged dark stone)
```

767 cells are still dark stone. One cell is a torch. Every byte the screen displays is one we put there.

## Stage 3: Two Torches

The first torch glows. Now we ask the keep what byte we wrote, brighten it, and place a brighter torch beside the first.

```z80
            ld      a, ($5990)
            or      $40
            ld      ($5991), a
```

Three more instructions on top of Stage 2.

### Reading is a question

`LD A, ($5990)` is the opposite of `LD ($5990), A`. The brackets work the same way — they mean *the contents at this address* — but the data flows the other direction. We're asking the Spectrum: *what byte is at $5990?* The Spectrum answers with whatever's there. In our program the answer is `$30`, the byte we wrote two instructions earlier.

In future units, when the hero is about to step into a cell, the game asks the same question. *What's at the cell the hero wants to walk into?* The answer is one byte, and the game decides what to do based on its bits — wall, door, treasure, hazard. Every collision check, every pickup, every door lock in Shadowkeep is a read followed by a bit test. The unit you're writing contains the *read* half of all of it.

### OR for setting bits

`OR n` looks at every bit of A. For each bit, it forces the result to 1 if either A or `n` had a 1 there; otherwise it leaves it alone. Mathematically:

```
  A     = $30 = 0 0 1 1 0 0 0 0    (PAPER 6, INK 0)
  OR $40 = 0 1 0 0 0 0 0 0    (bit 6 = BRIGHT)
  ─────────────────────────
  Result = 0 1 1 1 0 0 0 0 = $70    (PAPER 6 + BRIGHT)
```

Bit 6 of A was 0; now it's 1. All other bits unchanged. PAPER and INK are still 6 and 0. BRIGHT is now set.

`OR` is how you *set* specific bits in a byte without disturbing the others. Its sibling, `AND`, is how you *clear* or *test* specific bits. We'll meet `AND` properly in Unit 4 when the hero asks the keep *am I about to step into a wall?*

### Writing the modified byte next door

`LD ($5991), A` writes A (now `$70`) to the cell at `$5991` — one column to the right of `$5990` (same row).

```
  Memory state after Stage 3:
  
    $5800 ─── $598F:   $08    (unchanged dark stone)
    $5990:             $30    (the first torch — plain yellow)
    $5991:             $70    ← we wrote this (read $30, OR'd with $40)
    $5992 ─── $5AFF:   $08    (unchanged dark stone)
```

## Stage 4: The Flickering Torch

Two torches glow steadily. But the keep is still magic-tainted, and the next torch we add can't hold its flame.

```z80
            ld      a, $F0
            ld      ($598F), a
```

Two instructions. One byte. The FLASH bit is set.

### FLASH — the hardware twitches

FLASH (bit 7 of the attribute byte) is the Spectrum's blinking warning light. When the hardware sees a cell whose attribute has bit 7 set, it doesn't paint INK and PAPER in their usual roles — instead, it swaps them about twice a second. INK becomes PAPER, PAPER becomes INK, the cell appears to *pulse*.

```
  $F0 = 1 1 1 1 0 0 0 0
        │ │ │     │
        │ │ │     └── INK 0 (black)
        │ │ └──────── PAPER 6 (yellow)
        │ └────────── BRIGHT
        └──────────── FLASH

  At time t=0:   foreground = INK 0 (black), background = PAPER 6 BRIGHT (vivid yellow)
                   → cell looks bright yellow
  At time t=0.5: foreground = PAPER 6 BRIGHT (yellow), background = INK 0 (black)
                   → cell looks black with implied yellow elsewhere
  ... and so on ...
```

To the eye, the cell flickers between bright yellow and dark. A torch struggling to hold against the dark.

We write this attribute byte to `$598F` — one cell to the *left* of the first torch (same row 12, but column 15 instead of 16). Three torches in a row now.

```
  Memory state after Stage 4:
  
    $5800 ─── $598E:   $08    (unchanged dark stone)
    $598F:             $F0    ← we wrote this (FLASH + BRIGHT + yellow)
    $5990:             $30    (the steady torch)
    $5991:             $70    (the bright torch)
    $5992 ─── $5AFF:   $08    (unchanged dark stone)
```

Three torches lit, 765 cells of dark stone, every byte accounted for.

## Assemble and run

Each stage has its own `.asm` file. The Makefile builds all four into `.tap` (for real-hardware loading) and `.sna` (for the screenshot pipeline):

```bash
make
```

Load any of the four `.tap` files into Fuse, your emulator of choice, or a real Spectrum Next. Type `RUN` at the BASIC prompt to see each stage on its own.

## Try this: a torch of a different colour

Find this line in `04-flickering.asm`:

```z80
            ld      a, $30
```

Change `$30` to `$10` (PAPER 2 red, INK 0). Reassemble, reload. The steady torch is now red — a deeper, more alarming colour. The BRIGHT and FLASH variants we built next to it inherit *their* PAPER from `$30` though, because we wrote them with separate bytes, not by OR-ing from this one. The three torches now disagree on what colour they are.

That's the lesson the read step is teaching: when you read `$5990` back at Stage 3, you got whatever you wrote there in Stage 2. Change Stage 2's value, and Stage 3's brightened version inherits it automatically — *because we computed it from the read*. The FLASH torch in Stage 4 was written with a fresh literal value, so it doesn't inherit.

## Try this: silence the FLASH

Change `$F0` to `$70`. Reassemble. The leftmost torch is now a *third* steady bright torch. The FLASH bit going from 1 to 0 quiets the cell entirely. One bit, one switch, the difference between a flickering and a steady cell.

## Try this: the keep stays dark

Comment out the `ldir` block:

```z80
;            ld      hl, $5800
;            ld      de, $5801
;            ld      (hl), $08
;            ld      bc, 767
;            ldir
```

Reassemble. The BORDER is still black, but the playable area reverts to whatever the BASIC ROM left it in at boot — typically a mix of white-on-black and grey, with the `Bytes:` loader header at the top if you ran the `.tap` version. Three yellow cells appear on that messy canvas. The atmosphere collapses.

That's `LDIR` earning its place. Without it, our three torches sit in clutter; with it, they sit in *the keep*.

## If it doesn't work

- **BORDER stays grey?** Check the `OUT ($FE), A` instruction. The brackets around `$FE` are mandatory in the assembler's port syntax (`OUT` to a port, like `LD` to memory, uses brackets to mean *this address*). Without them the assembler may emit a different opcode.
- **Screen stays grey-white instead of dark blue?** Check the `LDIR` cascade. The pattern is `LD HL, source` / `LD DE, source+1` / `LD (HL), value` / `LD BC, count` / `LDIR`. Setting `DE` to anything other than `HL + 1` breaks the cascade — you'll either copy uninitialised memory or only fill one cell.
- **Block count off by one?** The cascade fills `count + 1` cells total — the seed cell at `HL`, plus `count` cells copied to. For 768 cells of attribute memory, `BC = 767` (seed + 767 = 768).
- **One torch missing?** Each torch is one `LD (address), A` instruction with the right address. Off-by-one errors land easily: `$5990` is row 12 col 16, `$5991` is col 17, `$598F` is col 15.
- **Flickering torch looks steady?** The FLASH bit only flickers on the live machine — the screenshot pipeline captures a single frame and freezes whatever phase of the flash cycle the cell was in. Run the program in Fuse or on real hardware to see the flicker.
- **Returns to BASIC instantly?** The `halt` / `jr .loop` pair must be at the end. Without it the program runs off the end of our code into whatever's beyond and exits noisily.

## What you've learnt

- **Attribute memory.** 768 bytes at `$5800–$5AFF`. One per cell. The address formula `$5800 + (row × 32) + column`.
- **The attribute byte.** FLASH (bit 7), BRIGHT (bit 6), PAPER (bits 5–3), INK (bits 2–0). Eight bits encoding the full visual state of one cell.
- **The keep's vocabulary.** Eight cell types, each a specific bit pattern. This unit lit three of them; the rest fill out across Phase 1.
- **`LD A, value` / `LD (address), A`.** Load an immediate into A, store A to memory. Single-byte write.
- **`LD A, (address)`.** Read a byte from memory into A. Read is the foundation of every collision and pickup check the game will ever do.
- **`OR n`.** Set specific bits of A. The BRIGHT bit set via `OR $40` is the canonical example.
- **`LD HL, addr` / `LD DE, addr` / `LD BC, count`.** Loading 16-bit register pairs with immediate values, the building blocks of pointer-based operations.
- **`LDIR`.** The Z80's block-fill / block-copy instruction. One opcode, 767 cells filled. The cascade idiom (`DE = HL + 1`, seed at `HL`) for filling memory with a constant.
- **`OUT (port), A`.** Talking to hardware via I/O ports. Port `$FE` controls the BORDER (bits 2–0); we'll see it again in Unit 7 when the same port drives the [beeper](/vault/techniques/beeper-music) (bit 4).
- **The 50 Hz halt loop.** `halt` / `jr .loop` keeps a program alive between frames without burning CPU.

Sixteen instructions, sixteen lessons, three torches and a dark stone keep. The first real chapter of Shadowkeep.
