Our loop draws one character. To draw another, we could copy its instructions. Instead, we will put the loop in a **routine** and call it twice, with different destinations. Both pictures use the same drawing code and the same eight pattern bytes.

## Give the routine a job

The routine is named `draw_character`. Its caller prepares HL with the address of eight pattern bytes and DE with a screen destination, then calls it:

```z80
 ld hl,patterns
 ld de,$4000
 call draw_character
```

`call draw_character` saves the address of the instruction after the call, then transfers execution to the routine. Inside it, the familiar loop draws eight rows. A new instruction, `ret`, returns to the saved address.

The main program prepares another destination and calls the **same label** again. This time RET returns after the second call. A routine does not have one fixed place to return to: each call supplies its own return address.

## What CALL keeps for us

The saved address lives on the **stack**, an area of RAM used to keep return addresses and other temporary values. **SP**, the stack pointer, identifies the top of that stack.

On the Z80, CALL stores a two-byte return address and reduces SP by two. RET reads that address and increases SP by two. The browser and the local tape loader use the ROM to establish a working stack before our program starts.

CALL and RET do not automatically preserve HL, DE, A or B. If a routine changes those registers, the caller sees the changed values after it returns.

## State the contract

A routine’s **contract** tells its caller what to supply and what to expect afterwards. Here is ours:

| Part of the contract | `draw_character` |
|---|---|
| Pattern input | HL points to eight readable pattern bytes. |
| Destination input | DE is `$4000`–`$401F`, the top row of a cell in the first character row. |
| Environment | A valid return stack; the caller has chosen the cell’s colours. |
| Work | Write eight bitmap rows, advancing the destination by `$100` each time. |
| Changed registers | HL advances by 8; D advances by 8 while E stays unchanged; B becomes 0; A holds the last pattern byte. Flags may change. |
| Return | Execution resumes after the calling instruction; balanced CALL/RET restores SP to its value before CALL. |

The routine sets B to 8 itself, so B is not an input the caller must prepare. It does not set attributes or clear other screen memory. The main program sets bright white ink on black paper for the first three cells, covering the destinations we will try.

## A return is not a reset

At the first return, HL is eight bytes past `patterns`. That is useful evidence: the routine consumed all eight source bytes. But it means the caller must reload HL before drawing that same picture again.

Likewise, DE has advanced beyond the eight destinations just written. Reloading DE chooses the next character’s position. Passing new inputs is what makes one piece of code useful in different places.

<Question prompt="If both calls use DE = $4000, will two characters appear side by side?">

No. Both invocations write the same eight screen bytes. The second drawing replaces the first. The replay still records two calls and two returns, but both groups of writes use `$4000`, `$4100`, through `$4700`.

</Question>

<Question prompt="Could we replace CALL with JP because both transfer execution to a label?">

Not while relying on this routine’s RET. JP does not save a return address. RET would use whatever address was already on the stack, not the instruction after that JP. CALL and RET form a pair because they agree on how the return address is stored and recovered.

</Question>

## Keep code and data separate

The main program’s `hold` loop appears before the routine. That prevents normal execution from falling into it after the second return. The routine ends with RET, and its pattern table follows it. Neither the caller nor the routine should continue into those data bytes as instructions.
