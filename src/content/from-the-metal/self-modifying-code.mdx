## There is no line between code and data

An instruction like `lda $d020` is three bytes in memory: the opcode, then the low and high bytes of the address. Nothing stops you writing to those last two bytes — they're RAM like everything else. Change them and you've changed where the *next* run of that instruction reads from:

## Why anyone would do this

Speed, when every cycle counted. Baking a value straight into the instruction skips loading it from memory each pass — patch the operand once, outside the loop, and the inner loop runs leaner forever after. In a tight rendering routine that saving, multiplied by thousands of iterations, was the difference between hitting the frame and missing it. It was an optimisation, not a party trick.

And the idea never died — it just moved up the stack and put on a suit. A JIT compiler writes fresh machine code into memory and jumps to it. A V8 or a JVM does exactly that, millions of times a second. Generating code at runtime is mainstream; the 6502 just let you do it to *yourself*, in place, with no safety net.

## Why it's "forbidden" now

Three things changed. Instruction caches mean the CPU may be running a stale copy of code you just edited. Memory protection — W^X — lets a page be writable or executable, never both, precisely because self-modifying code is also how attackers inject theirs. And a modern pipeline hates it: rewriting code ahead of the program counter forces expensive flushes. The technique didn't become wrong — the costs and the threat model moved.

> "Code is data" sounds like a slogan until you've watched a program reach down and rewrite its own next instruction. Every JIT, every runtime codegen, every page you're not allowed to write-then-execute is a descendant of that one liberty the 6502 took for granted — and of the reasons we later took it away.
