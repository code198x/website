# Custom Character Sets: Creating Your Visual Universe
**From generic text to unique game worlds**

Every C64 shipped with the same character ROM - 256 characters including letters, numbers, and PETSCII graphics. Yet "Boulder Dash" created a world of diamonds and butterflies. "Impossible Mission" rendered sleek robots and platforms. "Paradroid" built a high-tech spaceship interior. How did they transform the same 256 characters into completely different visual experiences?

The answer lies in one of the C64's most powerful features: the ability to redefine every single character. By copying the ROM charset to RAM and modifying it, developers could create entirely custom graphics using the same text mode that displayed "READY." This technique powered thousands of games, turning simple character displays into rich, animated worlds.

## The Character Graphics Revolution

In 1982, most computers offered either text or graphics - not both efficiently. The C64's character mode was different. Each character was an 8×8 pixel bitmap that could be redefined on the fly. This meant games could have the memory efficiency of text mode (1 byte per character) with the visual flexibility of bitmap graphics.

Tony Crowther used this to create the underground worlds of "Loco." Jeff Minter transformed characters into psychedelic patterns in "Gridrunner." The Darling brothers built entire fantasy realms in "BMX Simulator" and "Dizzy." All using redefined characters.

## Understanding Character Memory

Each character is defined by 8 bytes, one per row:

```asm
; How characters are stored in memory
; Each byte represents one row of 8 pixels
; Bit 7 = leftmost pixel, Bit 0 = rightmost pixel

; Example: Creating a smiley face (character 128)
; Memory location: $3000 + (128 × 8) = $3400

smiley_face:
    .byte %00111100  ; ..****..
    .byte %01000010  ; .*....*. 
    .byte %10100101  ; *.*..*.* 
    .byte %10000001  ; *......*
    .byte %10100101  ; *.*..*.* 
    .byte %10011001  ; *..**..*
    .byte %01000010  ; .*....*.
    .byte %00111100  ; ..****..

; To understand the bit patterns:
; 1 = pixel on (foreground color)
; 0 = pixel off (background color)
```

The magic happens when you realize these 8 bytes can represent anything - game tiles, sprites, UI elements, even pseudo-bitmap graphics.

## Copying ROM to RAM

The character ROM lives at $D000-$DFFF, but it's hidden beneath the I/O area. Here's how to access it:

```asm
; Professional character set initialization
; Used by countless C64 games

init_custom_charset:
    ; First, tell VIC-II where our charset will be
    ; $D018 controls both screen and character memory
    lda $d018
    and #$f0        ; Keep screen memory location
    ora #$0c        ; Character memory at $3000-$37FF
    sta $d018
    
    ; Now copy ROM characters to RAM
    sei             ; Disable interrupts - critical!
    
    ; Switch out I/O to reveal character ROM
    lda $01
    pha             ; Save current memory configuration
    and #$fb        ; Clear bit 2 - reveal character ROM
    sta $01
    
    ; Copy 2048 bytes (256 characters × 8 bytes)
    ldx #0
.copy_page:
    ; Copy 256 bytes at a time for speed
.copy_byte:
    lda $d000,x     ; Read from character ROM
    sta $3000,x     ; Write to RAM
    lda $d100,x
    sta $3100,x
    lda $d200,x
    sta $3200,x
    lda $d300,x
    sta $3300,x
    lda $d400,x
    sta $3400,x
    lda $d500,x
    sta $3500,x
    lda $d600,x
    sta $3600,x
    lda $d700,x
    sta $3700,x
    dex
    bne .copy_byte
    
    ; Restore memory configuration
    pla
    sta $01
    cli             ; Re-enable interrupts
    
    ; Now we can modify characters!
    jsr create_custom_tiles
    rts
```

This is the exact technique "Boulder Dash" used. Copy the ROM, modify what you need, leave the rest intact. Players could still read text while enjoying custom graphics.

## Animated Character Effects

Static tiles are just the beginning. Animation brings worlds to life:

```asm
; Animated water effect - cycles through 4 frames
; This technique was used in "Rainbow Islands" and many others

water_frames:
    ; Frame 1 - waves moving right
    .byte %10001000,%00100010,%10001000,%00100010
    .byte %10001000,%00100010,%10001000,%00100010
    
    ; Frame 2 - waves shifted
    .byte %01000100,%00010001,%01000100,%00010001
    .byte %01000100,%00010001,%01000100,%00010001
    
    ; Frame 3 - waves shifted more
    .byte %00100010,%10001000,%00100010,%10001000
    .byte %00100010,%10001000,%00100010,%10001000
    
    ; Frame 4 - waves shifted again
    .byte %00010001,%01000100,%00010001,%01000100
    .byte %00010001,%01000100,%00010001,%01000100

animate_water:
    ; Called every frame
    inc water_timer
    lda water_timer
    and #$07        ; Change every 8 frames
    bne .done
    
    ; Next frame
    inc water_frame
    lda water_frame
    and #$03        ; 4 frames total
    
    ; Calculate source offset
    asl
    asl
    asl             ; × 8 bytes per frame
    tax
    
    ; Copy frame to character 131
    ldy #7
.copy:
    lda water_frames,x
    sta $3000+(131*8),y
    inx
    dey
    bpl .copy
    
.done:
    rts

water_timer: .byte 0
water_frame: .byte 0

; Animated fire effect
fire_frames:
    ; Frame 1 - flames low
    .byte %00000000,%00010000,%00010000,%00111000
    .byte %00111000,%01111100,%01111100,%11111110

    .byte %01111100,%01111100,%11111110,%01111100
    
    ; Frame 3 - flames high

    .byte %11111110,%01111100,%00111000,%00010000
    
    ; Frame 4 - flames falling
    .byte %00010000,%00111000,%00111000,%01111100
    .byte %01111100,%11111110,%01111100,%00111000

    ; Similar to water but faster

    dey

.done:
    rts
```

## Building Tile-Based Worlds

With custom tiles, entire game worlds emerge:

```asm
; Level design using custom characters
; This is how "Boulder Dash" and "Boulderdash" worked

; Level map (20×12 section)
level_map:
    .byte 128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128  ; Top wall
    .byte 128,032,032,032,032,032,032,032,032,133,133,032,032,032,032,032,032,032,032,128  ; Gems
    .byte 128,032,129,129,129,032,032,032,129,129,129,129,032,032,129,129,129,032,032,128  ; Platforms
    .byte 128,032,032,032,032,032,032,032,032,032,032,032,032,032,032,032,032,032,032,128  ; Open
    .byte 128,130,130,130,032,032,132,032,032,032,032,032,132,032,032,130,130,130,032,128  ; Grass/ladder
    .byte 128,128,128,128,032,032,132,032,133,032,032,133,132,032,032,128,128,128,032,128  ; Solid/gems
    .byte 128,032,032,032,032,032,132,032,032,032,032,032,132,032,032,032,032,032,032,128  ; Ladders
    .byte 128,032,129,129,129,129,129,129,129,129,129,129,129,129,129,129,129,032,032,128  ; Long platform
    .byte 128,032,032,032,032,032,032,032,032,032,032,032,032,032,032,032,032,032,135,128  ; Exit door
    .byte 128,134,134,134,032,032,032,032,131,131,131,131,032,032,032,134,134,134,128,128  ; Spikes/water
    .byte 128,128,128,128,130,130,130,130,131,131,131,131,130,130,130,128,128,128,128,128  ; Ground
    .byte 128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128,128  ; Bottom

draw_level:
    ; Draw level at screen position (10,5)
    ldx #0              ; Level data index
    lda #5              ; Start row
    sta current_row
    
.row_loop:
    lda #10             ; Start column
    sta current_col
    ldy #0              ; Column counter
    
.col_loop:
    ; Calculate screen address
    lda current_row
    jsr calculate_screen_pos  ; Returns address in ptr
    
    lda level_map,x
    ldy current_col
    sta (screen_ptr),y
    
    ; Set color based on tile type
    lda level_map,x
    jsr get_tile_color
    ldy current_col
    sta (color_ptr),y
    
    inc current_col
    inx
    iny
    cpy #20             ; 20 columns
    bne .col_loop
    
    inc current_row
    lda current_row
    cmp #17             ; 12 rows + 5 start = 17
    bne .row_loop
    rts

get_tile_color:
    ; Return appropriate color for each tile type
    cmp #128            ; Rock
    bne .check_brick
    lda #$0b            ; Dark gray
    rts
    
.check_brick:
    cmp #129            ; Brick
    bne .check_grass
    lda #$02            ; Red
    rts
    
.check_grass:
    cmp #130            ; Grass
    bne .check_water
    lda #$05            ; Green
    rts
    
.check_water:
    cmp #131            ; Water
    bne .check_ladder
    lda #$0e            ; Light blue
    rts
    
.check_ladder:
    cmp #132            ; Ladder
    bne .check_gem
    lda #$08            ; Orange
    rts
    
.check_gem:
    cmp #133            ; Gem
    bne .check_spike
    lda #$07            ; Yellow
    rts
    
.check_spike:
    cmp #134            ; Spike
    bne .check_door
    lda #$02            ; Red
    rts
    
.check_door:
    cmp #135            ; Door
    bne .default
    lda #$0d            ; Light green
    rts
    
.default:
    lda #$06            ; Blue (sky)
    rts

calculate_screen_pos:
    ; Calculate screen RAM address for row in A
    ; Returns result in screen_ptr
    tax
    lda row_table_lo,x
    sta screen_ptr
    lda row_table_hi,x
    sta screen_ptr+1
    
    ; Calculate color RAM address
    lda row_table_lo,x
    sta color_ptr
    lda #>$d800
    sta color_ptr+1
    rts

; Lookup tables for fast row calculation
row_table_lo:
    .byte <($0400+0*40),<($0400+1*40),<($0400+2*40),<($0400+3*40)
    .byte <($0400+4*40),<($0400+5*40),<($0400+6*40),<($0400+7*40)
    .byte <($0400+8*40),<($0400+9*40),<($0400+10*40),<($0400+11*40)
    .byte <($0400+12*40),<($0400+13*40),<($0400+14*40),<($0400+15*40)
    .byte <($0400+16*40),<($0400+17*40),<($0400+18*40),<($0400+19*40)
    .byte <($0400+20*40),<($0400+21*40),<($0400+22*40),<($0400+23*40)
    .byte <($0400+24*40)

row_table_hi:
    .byte >($0400+0*40),>($0400+1*40),>($0400+2*40),>($0400+3*40)
    .byte >($0400+4*40),>($0400+5*40),>($0400+6*40),>($0400+7*40)
    .byte >($0400+8*40),>($0400+9*40),>($0400+10*40),>($0400+11*40)
    .byte >($0400+12*40),>($0400+13*40),>($0400+14*40),>($0400+15*40)
    .byte >($0400+16*40),>($0400+17*40),>($0400+18*40),>($0400+19*40)
    .byte >($0400+20*40),>($0400+21*40),>($0400+22*40),>($0400+23*40)
    .byte >($0400+24*40)

current_row: .byte 0
current_col: .byte 0
screen_ptr:  .word 0
color_ptr:   .word 0
```

This tile-based approach powered hundreds of games. Level designers could create worlds using simple byte arrays. Memory usage was minimal - a 256×256 tile world used just 64KB.

## Memory Management

Character sets use precious RAM:

```asm
; Smart memory layout for character graphics
; Reserve different ranges for different purposes

; Memory map:
; $3000-$30FF: Characters 0-31 (keep some original for text)
; $3100-$31FF: Characters 32-63 (keep numbers and letters)
; $3200-$32FF: Characters 64-95 (can modify)
; $3300-$33FF: Characters 96-127 (can modify)
; $3400-$34FF: Characters 128-159 (game tiles)
; $3500-$35FF: Characters 160-191 (animated tiles)

organize_charset:
    ; Keep essential characters readable
    ; Modify only what you need
    ; Group similar tiles together

    rts
```

## Quick Reference

### Character Memory
- **Character size**: 8×8 pixels (8 bytes)
- **Total characters**: 256
- **Charset size**: 2048 bytes
- **ROM location**: $D000-$D7FF (hidden under I/O)
- **Common RAM locations**: $3000, $3800, $2000, $2800

### $D018 Register
- **Bits 7-4**: Screen memory (× $0400)
- **Bits 3-1**: Character memory (× $0800)
- **Bit 0**: Unused

### Memory Banking for Characters
```
$01 Register:
- Bit 2 = 0: Character ROM visible at $D000
- Bit 2 = 1: I/O visible at $D000 (normal)
```

### Design Tips
- Keep characters 0-31 for system use
- Preserve numbers (48-57) for scores
- Group related tiles together
- Use 128-255 for game graphics
- Animate by modifying character data
- Combine characters for larger objects

Master character graphics, and every byte becomes a brushstroke!
