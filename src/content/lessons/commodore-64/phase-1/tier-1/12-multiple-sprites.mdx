# Multiple Sprites: Orchestrating On-Screen Action
**From solo performance to full symphony**

Eight sprites. That's all the C64 gives you. When "Gauntlet" needed dozens of enemies on screen, when "Commando" filled the battlefield with soldiers and grenades, when "Bubble Bobble" created chaos with bubbles, enemies, and fruit - they all faced this same limitation. The difference between amateur and professional C64 games wasn't having more sprites; it was managing them brilliantly.

This lesson reveals the sprite management techniques that powered the C64's greatest games. You'll learn to juggle multiple sprites like a master performer, creating the illusion of bustling game worlds within the hardware's constraints. These aren't just programming techniques - they're the creative solutions that defined an era of gaming.

## The Eight Sprite Challenge

In 1982, eight hardware sprites seemed generous. The Atari 2600 had two. The Intellivision had eight, but they were monochrome. The C64's sprites were 24×21 pixels, multicolor capable, with collision detection. But game designers quickly wanted more.

Jeff Minter needed swarms for "Attack of the Mutant Camels." Andrew Braybrook required formations for "Uridium." The Bitmap Brothers demanded armies for "Speedball." They all discovered the same truth: it's not about having more sprites, it's about using them intelligently.

## Building a Sprite Management System

Professional C64 games don't handle sprites individually - they use management systems. Here's how to build one:

```asm
; Professional sprite management structure
; Each sprite gets 16 bytes of data for flexibility

SPRITE_TYPE      = 0   ; Object type (player/enemy/bullet/etc)
SPRITE_STATE     = 1   ; Current state/behavior
SPRITE_X_LO      = 2   ; X position low byte
SPRITE_X_HI      = 3   ; X position high byte (bit 0)
SPRITE_Y         = 4   ; Y position
SPRITE_VX        = 5   ; X velocity (signed)
SPRITE_VY        = 6   ; Y velocity (signed)
SPRITE_FRAME     = 7   ; Current animation frame
SPRITE_ANIM      = 8   ; Animation sequence pointer
SPRITE_TIMER     = 9   ; General purpose timer
SPRITE_HEALTH    = 10  ; Hit points (for enemies)
SPRITE_COLOR     = 11  ; Sprite color
SPRITE_FLAGS     = 12  ; Various flags
SPRITE_DATA1     = 13  ; Type-specific data
SPRITE_DATA2     = 14  ; Type-specific data
SPRITE_DATA3     = 15  ; Type-specific data

; 8 sprites × 16 bytes = 128 bytes total
sprite_table:
    .res 128

; Sprite type definitions
TYPE_INACTIVE    = 0   ; Sprite not in use
TYPE_PLAYER      = 1   ; Player character
TYPE_ENEMY_WALKER= 2   ; Walking enemy
TYPE_ENEMY_FLYER = 3   ; Flying enemy
TYPE_BULLET      = 4   ; Player bullet
TYPE_ENEMY_SHOT  = 5   ; Enemy projectile
TYPE_POWERUP     = 6   ; Collectible item
TYPE_EXPLOSION   = 7   ; Explosion effect
TYPE_PARTICLE    = 8   ; Particle effect
```

This structure gives each sprite enough data for complex behavior. The 16-byte alignment makes calculations faster - you can shift instead of multiply.

## Initializing the System

A robust initialization ensures clean starts:

```asm
init_sprite_system:
    ; Clear entire sprite table
    ldx #127
    lda #0
clear_loop:
    sta sprite_table,x
    dex
    bpl clear_loop
    
    ; Disable all sprites initially
    sta $d015
    
    ; Set default colors
    ldx #7
    lda #1          ; White default
color_loop:
    sta $d027,x
    dex
    bpl color_loop
    
    ; Clear collision registers
    lda $d01e       ; Sprite-sprite collision
    lda $d01f       ; Sprite-background collision
    
    ; Initialize sprite pointers to safe area
    ldx #7
    lda #$ff        ; Empty sprite pattern
init_pointers:
    sta $07f8,x
    dex
    bpl init_pointers
    
    ; Set up empty sprite pattern at $3fc0
    ldx #62
    lda #0
empty_sprite:
    sta $3fc0,x
    dex
    bpl empty_sprite
    
    rts
```

Starting with all sprites disabled and cleared prevents visual glitches. Reading the collision registers clears any pending collisions.

## Dynamic Sprite Allocation

The heart of the system - finding and assigning sprites dynamically:

```asm
; Allocate a sprite for a new object
; Input: A = object type
;        X = initial X position
;        Y = initial Y position
; Output: X = sprite index (0-7), carry set if failed

allocate_sprite:
    sta temp_type
    stx temp_x
    sty temp_y
    
    ; Find first inactive sprite
    ldx #0
find_inactive:
    lda sprite_table,x      ; Check TYPE field
    beq found_sprite        ; TYPE_INACTIVE = 0
    
    ; Move to next sprite
    txa
    clc
    adc #16                 ; Next sprite's data
    tax
    cpx #128               ; Checked all 8 sprites?
    bne find_inactive
    
    ; No sprites available
    sec                     ; Set carry for error
    rts
    
found_sprite:
    ; X contains offset to sprite data
    lda temp_type
    sta sprite_table,x      ; Set type
    
    lda #1                  ; Default active state
    sta sprite_table+SPRITE_STATE,x
    
    lda temp_x
    sta sprite_table+SPRITE_X_LO,x
    lda #0
    sta sprite_table+SPRITE_X_HI,x
    
    lda temp_y
    sta sprite_table+SPRITE_Y,x
    
    ; Type-specific initialization
    lda temp_type
    cmp #TYPE_PLAYER
    beq init_player
    cmp #TYPE_ENEMY_WALKER
    beq init_enemy
    cmp #TYPE_BULLET
    beq init_bullet
    jmp init_done
    
init_player:
    lda #5                  ; Green
    sta sprite_table+SPRITE_COLOR,x
    lda #10                 ; Full health
    sta sprite_table+SPRITE_HEALTH,x
    lda #$80                ; Player sprite at $2000
    sta sprite_table+SPRITE_FRAME,x
    jmp init_done
    
init_enemy:
    lda #2                  ; Red
    sta sprite_table+SPRITE_COLOR,x
    lda #3                  ; Enemy health
    sta sprite_table+SPRITE_HEALTH,x
    lda #$84                ; Enemy sprite at $2100
    sta sprite_table+SPRITE_FRAME,x
    
    ; Random initial direction
    lda $d41b               ; Hardware random
    and #$01
    beq enemy_left
    lda #1                  ; Move right
    bne store_velocity
enemy_left:
    lda #$ff                ; Move left (-1)
store_velocity:
    sta sprite_table+SPRITE_VX,x
    jmp init_done
    
init_bullet:
    lda #1                  ; White
    sta sprite_table+SPRITE_COLOR,x
    lda #$88                ; Bullet sprite at $2200
    sta sprite_table+SPRITE_FRAME,x
    lda #$fc                ; Upward velocity (-4)
    sta sprite_table+SPRITE_VY,x
    
init_done:
    ; Enable this sprite
    txa
    lsr                     ; Divide by 16 to get sprite number
    lsr
    lsr
    lsr
    tay
    lda bit_table,y
    ora $d015
    sta $d015               ; Enable sprite
    
    txa
    lsr
    lsr
    lsr
    lsr                     ; Return sprite index in X
    tax
    clc                     ; Clear carry for success
    rts

temp_type:  .byte 0
temp_x:     .byte 0  
temp_y:     .byte 0

bit_table:
    .byte $01,$02,$04,$08,$10,$20,$40,$80
```

This allocation system finds available sprites automatically. Games like "Commando" used similar systems to manage soldiers, grenades, and vehicles dynamically.

## The Update Loop

Updating all sprites efficiently in a single pass:

```asm
update_all_sprites:
    ldx #0                  ; Start with sprite 0
    
sprite_update_loop:
    lda sprite_table,x      ; Check type
    beq next_sprite         ; Skip if inactive
    
    ; Update based on type
    cmp #TYPE_PLAYER
    beq update_player_sprite
    cmp #TYPE_ENEMY_WALKER
    beq update_enemy_sprite
    cmp #TYPE_BULLET
    beq update_bullet_sprite
    cmp #TYPE_EXPLOSION
    beq update_explosion_sprite
    jmp next_sprite
    
update_player_sprite:
    jsr handle_player_input
    jsr apply_player_physics
    jmp update_sprite_position
    
update_enemy_sprite:
    jsr update_enemy_ai
    jsr check_enemy_boundaries
    jmp update_sprite_position
    
update_bullet_sprite:
    ; Apply velocity
    lda sprite_table+SPRITE_Y,x
    clc
    adc sprite_table+SPRITE_VY,x
    sta sprite_table+SPRITE_Y,x
    
    ; Check if off screen
    cmp #50
    bcs update_sprite_position
    
    ; Bullet went off top - deactivate
    lda #TYPE_INACTIVE
    sta sprite_table,x
    jsr disable_hardware_sprite
    jmp next_sprite
    
update_explosion_sprite:
    ; Animate explosion
    inc sprite_table+SPRITE_TIMER,x
    lda sprite_table+SPRITE_TIMER,x
    lsr                     ; Every 2 frames
    clc
    adc #$90                ; Explosion frames start at $2400
    sta sprite_table+SPRITE_FRAME,x
    
    lda sprite_table+SPRITE_TIMER,x
    cmp #16                 ; 8 frames of animation
    bne update_sprite_position
    
    ; Explosion finished
    lda #TYPE_INACTIVE
    sta sprite_table,x
    jsr disable_hardware_sprite
    jmp next_sprite
    
update_sprite_position:
    ; Apply velocity to position
    lda sprite_table+SPRITE_X_LO,x
    clc
    adc sprite_table+SPRITE_VX,x
    sta sprite_table+SPRITE_X_LO,x
    
    ; Handle carry for X high bit
    bcc no_x_overflow
    lda sprite_table+SPRITE_X_HI,x
    eor #$01
    sta sprite_table+SPRITE_X_HI,x
    
no_x_overflow:
    lda sprite_table+SPRITE_Y,x
    clc  
    adc sprite_table+SPRITE_VY,x
    sta sprite_table+SPRITE_Y,x
    
    ; Update hardware registers
    txa
    lsr                     ; Get sprite number
    lsr
    lsr
    lsr
    tay
    
    ; Set X position
    lda sprite_table+SPRITE_X_LO,x
    asl                     ; Multiply sprite number by 2
    tya
    rol
    tay
    lda sprite_table+SPRITE_X_LO,x
    sta $d000,y
    
    ; Set Y position
    lda sprite_table+SPRITE_Y,x
    sta $d001,y
    
    ; Handle X MSB
    lda sprite_table+SPRITE_X_HI,x
    beq clear_msb
    
    txa
    lsr
    lsr
    lsr
    lsr
    tay
    lda bit_table,y
    ora $d010
    sta $d010
    jmp update_sprite_visual
    
clear_msb:
    txa
    lsr
    lsr
    lsr
    lsr
    tay
    lda bit_table,y
    eor #$ff
    and $d010
    sta $d010
    
update_sprite_visual:
    ; Update color
    txa
    lsr
    lsr
    lsr
    lsr
    tay
    lda sprite_table+SPRITE_COLOR,x
    sta $d027,y
    
    ; Update sprite pointer
    lda sprite_table+SPRITE_FRAME,x
    sta $07f8,y
    
next_sprite:
    ; Move to next sprite
    txa
    clc
    adc #16
    tax
    cpx #128
    beq sprites_done
    jmp sprite_update_loop
    
sprites_done:
    rts
```

This unified update loop handles all sprite types efficiently. Each sprite type has its own behavior, but they all share the same position update and hardware register code.

## Sprite Pooling for Bullets

Games often need multiple instances of the same object. Pooling pre-allocates sprites for specific purposes:

```asm
; Bullet pool system - reserves sprites 4-6 for bullets
BULLET_POOL_START = 4
BULLET_POOL_SIZE  = 3

fire_player_bullet:
    ; Check if we can fire (cooldown)
    lda bullet_cooldown
    beq can_fire
    rts
    
can_fire:
    ; Find available bullet sprite
    ldx #BULLET_POOL_START
    
find_bullet_sprite:
    txa
    asl
    asl
    asl
    asl                     ; Multiply by 16
    tay
    lda sprite_table,y
    cmp #TYPE_INACTIVE
    beq found_bullet_slot
    
    inx
    cpx #BULLET_POOL_START+BULLET_POOL_SIZE
    bne find_bullet_sprite
    
    ; No bullets available
    rts
    
found_bullet_slot:
    ; Get player position for bullet start
    lda sprite_table+SPRITE_X_LO   ; Player is sprite 0
    clc
    adc #12                 ; Center of player sprite
    tax
    
    lda sprite_table+SPRITE_Y
    sec
    sbc #8                  ; Above player
    tay
    
    lda #TYPE_BULLET
    jsr allocate_specific_sprite
    
    ; Set cooldown
    lda #10                 ; Can fire every 10 frames
    sta bullet_cooldown
    
    ; Sound effect
    jsr play_shoot_sound
    rts

; Allocate a specific sprite (for pooling)
; Input: A = type, X = x pos, Y = y pos
;        Current X register = sprite to allocate
allocate_specific_sprite:
    stx temp_sprite
    sta temp_type
    stx temp_x
    sty temp_y
    
    lda temp_sprite
    asl
    asl
    asl
    asl
    tax
    
    lda temp_type
    sta sprite_table,x
    ; ... rest of initialization
    rts

bullet_cooldown: .byte 0
temp_sprite:     .byte 0
```

Pooling ensures bullets are always available when the player fires. "Defender" and "Robotron" used similar pooling for their intense bullet patterns.

## Multi-Sprite Collision System

Checking collisions between different sprite groups:

```asm
check_all_collisions:
    ; Read hardware collision register
    lda $d01e               ; Sprite-sprite collisions
    beq no_collisions       ; Early exit if none
    
    ; Check player collisions (sprite 0)
    and #$01
    beq check_bullets
    
    ; Player hit something - find what
    lda $d01e
    and #$fe                ; Check all other sprites
    ldx #1
    
find_player_collision:
    lsr
    bcc next_collision_check
    
    ; Sprite X hit the player
    txa
    asl
    asl
    asl
    asl
    tay
    
    lda sprite_table,y      ; What type hit us?
    cmp #TYPE_ENEMY_WALKER
    beq player_hit_enemy
    cmp #TYPE_ENEMY_SHOT
    beq player_hit_bullet
    cmp #TYPE_POWERUP
    beq player_got_powerup
    jmp next_collision_check
    
player_hit_enemy:
    jsr damage_player
    jsr destroy_enemy
    jmp next_collision_check
    
player_hit_bullet:
    jsr damage_player
    lda #TYPE_INACTIVE
    sta sprite_table,y
    jmp next_collision_check
    
player_got_powerup:
    jsr collect_powerup
    lda #TYPE_INACTIVE
    sta sprite_table,y
    
next_collision_check:
    inx
    cpx #8
    bne find_player_collision
    
check_bullets:
    ; Check bullet-enemy collisions
    ldx #BULLET_POOL_START
    
bullet_collision_loop:
    txa
    asl
    asl
    asl
    asl
    tay
    
    lda sprite_table,y
    cmp #TYPE_BULLET
    bne next_bullet_check
    
    ; Check if this bullet hit anything
    txa
    tay
    lda bit_table,y
    and $d01e
    beq next_bullet_check
    
    ; Bullet hit something - check what
    jsr check_bullet_targets
    
next_bullet_check:
    inx
    cpx #BULLET_POOL_START+BULLET_POOL_SIZE
    bne bullet_collision_loop
    
no_collisions:
    rts
```

This system efficiently processes collisions by type, allowing different responses for different collision pairs.

## Enemy Wave Management

Creating patterns and formations:

```asm
; Wave spawning system
wave_timer:      .byte 0
wave_pattern:    .byte 0
enemies_spawned: .byte 0
wave_complete:   .byte 0

update_wave_system:
    lda wave_complete
    bne check_new_wave
    
    ; Current wave active
    dec wave_timer
    bne wave_done
    
    ; Time to spawn next enemy
    lda #30                 ; Reset timer
    sta wave_timer
    
    ; Spawn based on pattern
    lda wave_pattern
    cmp #PATTERN_LINE
    beq spawn_line_enemy
    cmp #PATTERN_V_FORMATION
    beq spawn_v_enemy
    cmp #PATTERN_RANDOM
    beq spawn_random_enemy
    
spawn_line_enemy:
    lda enemies_spawned
    asl
    asl
    asl                     ; Multiply by 8 for spacing
    clc
    adc #40                 ; Starting X position
    tax
    ldy #30                 ; Y position
    jsr spawn_enemy
    jmp check_wave_end
    
spawn_v_enemy:
    ; Calculate V formation position
    lda enemies_spawned
    cmp #4
    bcc left_side
    
    ; Right side of V
    sec
    sbc #4
    asl
    asl
    asl
    clc
    adc #160
    tax
    
    lda enemies_spawned
    sec
    sbc #4
    asl
    asl
    asl
    clc
    adc #30
    tay
    jmp do_spawn
    
left_side:
    ; Left side of V
    lda #160
    sec
    sbc enemies_spawned
    asl
    asl
    asl
    tax
    
    lda enemies_spawned
    asl
    asl
    asl
    clc
    adc #30
    tay
    
do_spawn:
    jsr spawn_enemy
    
check_wave_end:
    inc enemies_spawned
    lda enemies_spawned
    cmp #8                  ; 8 enemies per wave
    bne wave_done
    
    ; Wave complete
    lda #1
    sta wave_complete
    lda #0
    sta enemies_spawned
    
wave_done:
    rts
    
check_new_wave:
    ; Check if all enemies destroyed
    ldx #0
    ldy #0                  ; Enemy count
    
count_enemies:
    lda sprite_table,x
    cmp #TYPE_ENEMY_WALKER
    bne not_enemy
    iny
not_enemy:
    txa
    clc
    adc #16
    tax
    cpx #128
    bne count_enemies
    
    cpy #0                  ; No enemies left?
    bne still_enemies
    
    ; Start new wave
    lda #0
    sta wave_complete
    lda #60                 ; Initial delay
    sta wave_timer
    
    ; Next pattern
    inc wave_pattern
    lda wave_pattern
    cmp #3
    bne pattern_ok
    lda #0
    sta wave_pattern
    
pattern_ok:
still_enemies:
    rts

; Pattern definitions
PATTERN_LINE      = 0
PATTERN_V_FORMATION = 1  
PATTERN_RANDOM    = 2
```

Wave patterns keep gameplay fresh. "Galaga" and "Phoenix" mastered this, creating memorable attack patterns with limited sprites.

## Performance Optimization

With eight sprites all updating every frame, optimization matters:

```asm
; Optimized position update using lookup tables
; Faster than multiple ASL instructions

sprite_x_reg_offset:
    .byte 0,2,4,6,8,10,12,14    ; $d000 + offset

sprite_y_reg_offset:  
    .byte 1,3,5,7,9,11,13,15    ; $d001 + offset

sprite_color_offset:
    .byte 0,1,2,3,4,5,6,7       ; $d027 + offset

fast_update_positions:
    ldx #7
    
fast_position_loop:
    txa
    asl
    asl
    asl
    asl
    tay                     ; Y = sprite table offset
    
    lda sprite_table,y      ; Check if active
    beq skip_sprite
    
    ; Update X position
    ldy sprite_x_reg_offset,x
    lda sprite_table+SPRITE_X_LO,y
    sta $d000,y
    
    ; Update Y position
    ldy sprite_y_reg_offset,x
    lda sprite_table+SPRITE_Y,y
    sta $d000,y
    
    ; Update color
    ldy sprite_color_offset,x
    lda sprite_table+SPRITE_COLOR,y
    sta $d027,x
    
skip_sprite:
    dex
    bpl fast_position_loop
    rts
```

Lookup tables eliminate calculations in tight loops. When "Armalyte" needed every cycle for its intense action, optimizations like these made the difference.

## Advanced Techniques

### Sprite Multiplexing Preview
While full multiplexing is an advanced topic, understanding the concept helps design better sprite systems:

```asm
; Simple sprite recycling during screen draw
; Reuse sprites that are off-screen

check_sprite_recycle:
    ldx #0
recycle_loop:
    lda sprite_table+SPRITE_Y,x
    cmp #250                ; Off bottom?
    bcc check_next
    
    ; This sprite is off-screen, can reuse
    lda #30                 ; Reset to top
    sta sprite_table+SPRITE_Y,x
    
    ; Change type to create illusion of new enemy
    lda $d41b               ; Random
    and #$03
    clc
    adc #TYPE_ENEMY_WALKER
    sta sprite_table,x
    
check_next:
    txa
    clc
    adc #16
    tax
    cpx #128
    bne recycle_loop
    rts
```

This simple recycling creates the illusion of more than 8 sprites. Full multiplexing (covered in advanced lessons) can display dozens.

## Complete Game Example

Here's everything working together in a playable game:

```asm
* = $0801
    .byte $0c,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

* = $080d
main_game:
    jsr init_screen
    jsr init_sprite_system
    jsr init_game
    
main_loop:
    ; Wait for raster
    lda #250
wait:
    cmp $d012
    bne wait
    
    ; Update game
    jsr read_joystick
    jsr update_all_sprites
    jsr check_all_collisions
    jsr update_wave_system
    jsr update_score_display
    
    ; Check game over
    lda player_lives
    bne main_loop
    
    jmp game_over

init_game:
    ; Set up player (always sprite 0)
    lda #TYPE_PLAYER
    ldx #160                ; Center screen
    ldy #200                ; Near bottom
    jsr allocate_sprite
    
    ; Initialize game variables
    lda #3
    sta player_lives
    lda #0
    sta score_lo
    sta score_hi
    sta wave_pattern
    sta wave_complete
    
    lda #60
    sta wave_timer
    
    rts

read_joystick:
    ; Player is always sprite 0
    ldx #0
    
    lda $dc00
    sta joy_state
    
    ; Check directions
    and #$01                ; Up
    bne check_joy_down
    
    lda sprite_table+SPRITE_Y
    cmp #50                 ; Top boundary
    bcc check_joy_down
    dec sprite_table+SPRITE_Y
    
check_joy_down:
    lda joy_state
    and #$02
    bne check_joy_left
    
    lda sprite_table+SPRITE_Y
    cmp #220                ; Bottom boundary
    bcs check_joy_left
    inc sprite_table+SPRITE_Y
    
check_joy_left:
    lda joy_state
    and #$04
    bne check_joy_right
    
    lda sprite_table+SPRITE_X_LO
    cmp #24                 ; Left boundary
    bcc check_joy_right
    dec sprite_table+SPRITE_X_LO
    
check_joy_right:
    lda joy_state
    and #$08
    bne check_joy_fire
    
    lda sprite_table+SPRITE_X_LO
    cmp #255-24             ; Right boundary
    bcs check_joy_fire
    inc sprite_table+SPRITE_X_LO
    
check_joy_fire:
    lda joy_state
    and #$10
    bne joy_done
    
    lda fire_pressed        ; Prevent auto-fire
    bne joy_done
    
    jsr fire_player_bullet
    lda #1
    sta fire_pressed
    jmp joy_done
    
joy_done:
    lda joy_state
    and #$10
    beq fire_held
    lda #0
    sta fire_pressed
fire_held:
    
    ; Update bullet cooldown
    lda bullet_cooldown
    beq cooldown_done
    dec bullet_cooldown
cooldown_done:
    rts

; Game variables
player_lives:   .byte 3
score_lo:       .byte 0
score_hi:       .byte 0
joy_state:      .byte 0
fire_pressed:   .byte 0
```

- [ ] Add collision detection between groups

### Performance Tips
- Use 16-byte alignment for fast indexing
- Batch similar operations together
- Early-exit from loops when possible
- Use lookup tables instead of calculations
- Disable unused sprites completely

### Common Pitfalls
- Forgetting to clear collision registers
- Not handling X position MSB correctly
- Sprite flicker from poor update order
- Memory corruption from bad indexing
- Visual glitches from partial updates

The eight sprite limit inspired creativity, not limitation. Master these techniques, and you'll create magic!
