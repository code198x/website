## Understanding the Hardware

The Commodore 64 gives you direct access to its hardware through memory-mapped I/O. This means specific memory addresses connect directly to hardware functions. Write a value to the right address, and the hardware responds instantly.

### The VIC-II Chip

The VIC-II (Video Interface Chip II) is the C64's graphics processor. It handles everything you see on screen:

- **16 colors** - Each with a specific code (0-15)
- **40×25 text display** - 1000 character positions
- **Hardware sprites** - 8 independent moving objects
- **Smooth scrolling** - Hardware-accelerated movement

Key VIC-II registers we'll use today:

| Register | Function | Values |
|----------|----------|--------|
| $D020 | Border color | 0-15 |
| $D021 | Background color | 0-15 |

### Screen Memory

The C64's screen is a grid of 40 columns × 25 rows = 1000 characters. Each position on screen corresponds to a byte in memory:

| Memory Range | Function | Description |
|--------------|----------|-------------|
| $0400-$07E7 | Screen memory | What character to display |
| $D800-$DBE7 | Color memory | What color to use |

When you write a value to screen memory, a character appears. It's that direct!

### The 6502 Processor

The 6502 is an 8-bit processor with:
- **Accumulator (A)**: Main working register
- **X and Y registers**: Index registers for loops
- **256-byte pages**: Memory organized in pages
- **Simple, elegant instruction set**: Easy to learn, powerful to use

### Why Memory-Mapped I/O Was Revolutionary

In 1982, most computers required complex system calls to change colors or display text. The C64's design was radical: want to change the border color? Write a single byte to memory address $D020. The VIC-II chip monitors that address and responds instantly.

This wasn't just convenient - it was blazingly fast. While other computers struggled with graphics, C64 programmers could create real-time visual effects by rapidly writing to VIC-II registers. This is how Jeff Minter created the psychedelic effects in "Gridrunner" and how the demoscene pushed the machine far beyond its apparent limits.

**The Engineering Genius:**
The 6502 processor sees $D020 as regular memory, but the VIC-II chip "listens" to writes at that address. This elegant design meant no special instructions needed - just normal memory operations that happened to control hardware. Brilliant!

### The BASIC Launcher

Here's something fascinating: the C64 always boots into BASIC, expecting BASIC programs. But we're writing assembly! The clever solution? We embed a tiny BASIC program that launches our assembly code.

Think of it like a springboard - a one-line BASIC program whose only job is to say "jump to the assembly code at address 2061." Once BASIC makes that jump, our assembly takes complete control of the machine.

**A note about hexadecimal:** In assembly, we often use hexadecimal (base 16) numbers. The `$` symbol means "this is a hex number." So `$0A` = 10 in decimal, `$10` = 16 in decimal, and `$FF` = 255 in decimal.

<CodeBlock title="BASIC Launcher - The Trojan Horse" language="asm" code={`; BASIC launcher: 10 SYS 2061
        !byte $0b,$08          ; Next line pointer
        !byte $0a,$00          ; Line number: 10
        !byte $9e              ; SYS token
        !byte $32,$30,$36,$31  ; "2061" as text characters
        !byte $00              ; End of line
        !byte $00,$00          ; End of program

start:
        ; Your assembly code goes here!`} />

This creates the smallest possible BASIC program: `10 SYS 2061`. When you type `RUN`, BASIC jumps to address 2061 ($080D in hex) where your assembly code begins. 

**Note:** The `!byte` directive tells the assembler (we're using ACME) to insert raw byte values into the program. Different assemblers use different directives, but the concept is the same.

### Step 2: Changing Colors - Your First Hardware Control

Now for the magic moment - you're about to control the C64's hardware directly. No operating system calls, no library functions. Just you writing a number to a memory address that connects straight to the VIC-II chip.

<CodeBlock title="Direct Hardware Control - Colors" language="asm" code={`        ; Set border color to cyan
        lda #$03               ; Load 3 (cyan) into accumulator
        sta $d020              ; Store to border color register
        
        ; Set background to black
        lda #$00               ; Load 0 (black) into accumulator
        sta $d021              ; Store to background register`} />

Let's understand what's happening here:

1. **`lda #$03`** - Load the value 3 into the accumulator (the 6502's main working register). The `#` means "immediate mode" - use this actual number, not a memory address.

2. **`sta $d020`** - Store the accumulator's value to memory address $D020. But $D020 isn't regular memory - it's wired directly to the VIC-II's border color circuit. The instant this instruction executes, the border changes color!

This is fundamentally different from modern programming. You're not asking an API to change colors. You're not calling a function. You're literally flipping electronic switches inside the VIC-II chip by writing to its control registers. This direct hardware access is what made the C64 so responsive and what enabled programmers to achieve "impossible" effects.

### Step 3: Clearing the Screen - Understanding Memory Layout

The C64 screen is a 40×25 grid of characters - that's 1000 positions total. Each position needs two things: what character to show (screen memory) and what color to use (color memory). We need to clear both.

Here's where assembly shines. Instead of clearing 1000 positions one by one, we use a clever trick:

<CodeBlock title="Professional Screen Clearing - The 4-Page Technique" language="asm" code={`        ; Clear all 1000 screen positions
        ldx #0                 ; Start at position 0
clear_loop:
        lda #$20               ; Space character (blank)
        sta $0400,x            ; Screen positions 0-255
        sta $0500,x            ; Screen positions 256-511
        sta $0600,x            ; Screen positions 512-767
        sta $0700,x            ; Screen positions 768-999
        
        ; Also set color to white
        lda #$01               ; White color code
        sta $d800,x            ; Color positions 0-255
        sta $d900,x            ; Color positions 256-511
        sta $da00,x            ; Color positions 512-767
        sta $db00,x            ; Color positions 768-999
        
        inx                    ; Next position
        bne clear_loop         ; Loop until X wraps to 0`} />

This is brilliant optimization! We write to four different pages of memory in each loop iteration. The X register counts from 0 to 255, and when it increments past 255, it wraps back to 0. The `bne` (branch if not equal to zero) instruction detects this wraparound and exits the loop.

With just 256 iterations, we clear all 1000 screen positions (the last 24 positions of $0700 get cleared even though we only need 232 of them - but that's fine). This same technique appears in countless C64 programs because it's so efficient.

**Professional Technique Spotlight:**
This four-page screen clearing method wasn't just documented in the Programmer's Reference Guide - it became the industry standard. When you examine the source code of classic games like "Impossible Mission" or "Beach Head," you'll find this exact technique. It's not just educational; it's authentic C64 craftsmanship.

The technique also demonstrates 6502 addressing mastery. By writing to `$0400,x`, `$0500,x`, `$0600,x`, and `$0700,x` in the same loop, we're using indexed addressing to efficiently cover multiple memory pages. This is the kind of optimization that separated professional C64 programmers from hobbyists.

**Historical Note**: This screen-clearing technique was documented in the Commodore 64 Programmer's Reference Guide and became the standard way to clear the screen in assembly. It's 4x faster than clearing each position individually!

### Step 4: Displaying Your Message

**Important:** The C64 doesn't use ASCII codes for screen display. Instead, it uses "screen codes" where A=1, B=2, C=3, etc. This is why we use numbers like 14,5,15,14 to spell "NEON".

Time to create our title screen with "NEON NEXUS" and game text:

<CodeBlock title="Displaying Text - Screen Codes" language="asm" code={`        ; Display "NEON NEXUS" centered on row 8
        ldx #0                 
title_loop:
        lda title_text,x       ; Get character from title
        beq display_subtitle   ; If 0, move to subtitle
        sta $0400+8*40+15,x    ; Row 8, Column 15 (screen position formula: base + row*40 + column)
        inx                    
        jmp title_loop         
        
display_subtitle:
        ; Display "GRID PROTOCOL" on row 10
        ldx #0
subtitle_loop:
        lda subtitle_text,x    
        beq display_prompt     
        sta $0400+10*40+13,x   ; Row 10, Column 13
        inx
        jmp subtitle_loop
        
display_prompt:
        ; Display "PRESS FIRE TO START" on row 20
        ldx #0
prompt_loop:
        lda prompt_text,x      
        beq done               
        sta $0400+20*40+10,x   ; Row 20, Column 10
        inx
        jmp prompt_loop
        
done:
        ; Program complete - infinite loop
        jmp done               ; Stay here forever

; Our messages using screen codes (not ASCII!)
title_text:
        !byte 14,5,15,14,32      ; "NEON "
        !byte 14,5,24,21,19      ; "NEXUS"
        !byte 0                   ; End marker
        
subtitle_text:
        !byte 7,18,9,4,32         ; "GRID "
        !byte 16,18,15,20,15      ; "PROTO"
        !byte 3,15,12             ; "COL"
        !byte 0
        
prompt_text:
        !byte 16,18,5,19,19,32    ; "PRESS "
        !byte 6,9,18,5,32         ; "FIRE "
        !byte 20,15,32            ; "TO "
        !byte 19,20,1,18,20       ; "START"
        !byte 0`} />

Remember, screen codes work like this:
- Letters: A = 1, B = 2, C = 3... Z = 26
- Numbers: 0 = 48, 1 = 49... 9 = 57  
- Space = 32 (same as ASCII)
- Different from ASCII where A = 65!

## Common Issues and Solutions

### "Nothing happens when I RUN"
- Check your BASIC stub bytes are exactly right
- Make sure you're assembling to $0801
- Verify the SYS address matches your code start

### "Wrong colors appear"
- Remember: color codes are 0-15
- Some assemblers need decimal, others hex
- `#03` in some assemblers, `#$03` in others

### "Garbage on screen"
- Screen codes aren't ASCII!
- A=1, B=2, not A=65, B=66
- Use the screen code reference table

### "Program crashes"
- Make sure your infinite loop is in place
- Check you're not writing past screen memory
- Verify all branches and jumps are correct
