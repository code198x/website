# Sprites: Making Things Move
**Bring graphics to life on the Commodore 64**

Picture this: It's 1982, and most home computers can barely display a moving dot without flickering. But the Commodore 64? It could display eight independent graphics objects - sprites - that moved as smoothly as silk across the screen, never interfering with each other or the background. This wasn't magic; it was brilliant engineering.

The C64's hardware sprites are what separated it from every other home computer of its era. While other systems struggled to move a single character without tearing or flicker, the C64's VIC-II chip handled sprite movement at the hardware level, freeing the CPU for game logic. This is why games like "Impossible Mission," "Paradroid," and "Bubble Bobble" looked so incredibly smooth and responsive.

Today, you're about to tap into this same power. You'll create your first sprite and watch it glide across the screen with the same smoothness that amazed a generation of gamers.

## Understanding Hardware Sprites: The Magic Behind the Movement

Think of hardware sprites as independent actors on a stage. While the background scenery (the screen display) remains static, these actors can move freely without disturbing anything behind them. This is fundamentally different from how most computers of the 1980s handled moving graphics.

The VIC-II chip provides 8 hardware sprites, numbered 0-7. Each sprite is:
- **24×21 pixels** in size (high-resolution mode) - roughly the size of a game character
- **Independent** - moves without affecting background or other sprites
- **Multi-colored** - can use up to 4 colors (we'll start with single color for simplicity)
- **Hardware-accelerated** - the VIC-II chip handles all the drawing automatically

### Why Hardware Sprites Were Revolutionary

Before hardware sprites, creating moving graphics was a nightmare of programming complexity. Here's what other computers had to do:

**The Old Way (Software Sprites):**
1. Save the background area behind the sprite
2. Draw the sprite over the background
3. When moving, erase the sprite by restoring the saved background
4. Save the new background area
5. Draw the sprite in its new position
6. Repeat every frame...

This process was slow, flickery, and consumed massive amounts of CPU time. The C64's hardware sprites eliminated all of this complexity. The VIC-II chip composites sprites over the background in real-time during the video scan, creating perfectly smooth animation with zero CPU overhead for the actual drawing.

This is why C64 games could have multiple characters moving smoothly while the CPU focused on game logic, AI, and physics. Andrew Braybrook's "Uridium" had dozens of enemy ships swarming the screen. Jeff Minter's "Attack of the Mutant Camels" featured smooth, enormous sprites that would have been impossible with software rendering. These weren't just games - they were demonstrations of hardware mastery.

The principle lives on in modern graphics cards - dedicated hardware for what it does best. Your GPU's sprite-like texture units are direct descendants of the VIC-II's sprite system.

### Sprite Memory Layout: Understanding the Grid

Every sprite is essentially a 24×21 pixel bitmap stored in memory. But why these specific dimensions? The answer lies in the C64's architecture and the clever way the VIC-II chip organizes data.

**The Mathematics of Sprite Storage:**
- 21 rows of pixels (the height)
- 3 bytes per row (24 pixels ÷ 8 bits per byte = 3 bytes)
- Total: 21 × 3 = 63 bytes

The brilliant part is the 64th unused byte. By making each sprite exactly 64 bytes, they align perfectly on memory boundaries that the VIC-II can access efficiently. This isn't wasted space - it's strategic design that makes sprite addressing lightning-fast.

**Why 24×21 Pixels?**
These dimensions weren't arbitrary. They provide enough detail for recognizable game characters while keeping memory usage reasonable. At 63 bytes per sprite, you can fit all 8 sprites' graphics in just 512 bytes - less than what a single high-resolution photo pixel takes today!

**Binary Art:**
Each pixel in a sprite corresponds to a single bit in memory. This means you can literally "draw" your sprite using binary notation, where each 1 represents a visible pixel and each 0 is transparent. It's like creating pixel art with mathematical precision.

## Creating Your First Sprite: From Concept to Animation

Now comes the exciting part - creating your very own moving sprite! We'll build an arrow that slides smoothly across the screen, demonstrating every key concept of sprite programming.

This process mirrors how professional game developers created iconic C64 characters. From the spaceship in "Defender" to the bouncing ball in "Arkanoid," every sprite started with the same fundamental steps you're about to learn.

### Step 1: Setting Up the Foundation

Every great sprite animation begins with a solid foundation. We need to prepare the C64's memory and registers before we can bring our sprite to life:

```text
*=$0801
        ; BASIC launcher: 10 SYS 2061
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        ; Clear screen first
        lda #$00
        sta $d020              ; Black border
        sta $d021              ; Black background
        
        ; Tell VIC-II where to find sprite data
        lda #$80               ; Sprite 0 data at $2000 (128 * 64)
        sta $07f8              ; Sprite 0 pointer
```

**Understanding Sprite Pointers:**
The sprite pointer at $07F8 is like giving someone directions to your house. The VIC-II needs to know where in memory to find your sprite's graphics data. The value 128 might seem arbitrary, but it's actually an elegant addressing scheme: 128 × 64 = 8192 (or $2000 in hexadecimal).

This system allows the VIC-II to address any 64-byte-aligned location in the first 16KB of memory with just a single byte value. It's the same principle used in modern virtual memory systems - a compact way to represent large addresses.

### Step 2: Designing the Sprite

Let's create an arrow pointing right. Each row is 24 pixels (3 bytes):

```text
; Place sprite data at $2000
*=$2000
sprite_data:
        ; Arrow sprite (24x21 pixels)
        !byte %00000000,%00000000,%00000000  ; Row 1
        !byte %00000000,%00001000,%00000000  ; Row 2
        !byte %00000000,%00011100,%00000000  ; Row 3
        !byte %00000000,%00111110,%00000000  ; Row 4
        !byte %00000000,%01111111,%00000000  ; Row 5
        !byte %00000000,%11111111,%10000000  ; Row 6
        !byte %00000001,%11111111,%11000000  ; Row 7
        !byte %00000011,%11111111,%11100000  ; Row 8
        !byte %00000111,%11111111,%11110000  ; Row 9
        !byte %00001111,%11111111,%11111000  ; Row 10
        !byte %00011111,%11111111,%11111100  ; Row 11 (middle)
        !byte %00001111,%11111111,%11111000  ; Row 12
        !byte %00000111,%11111111,%11110000  ; Row 13
        !byte %00000011,%11111111,%11100000  ; Row 14
        !byte %00000001,%11111111,%11000000  ; Row 15
        !byte %00000000,%11111111,%10000000  ; Row 16
        !byte %00000000,%01111111,%00000000  ; Row 17
        !byte %00000000,%00111110,%00000000  ; Row 18
        !byte %00000000,%00011100,%00000000  ; Row 19
        !byte %00000000,%00001000,%00000000  ; Row 20
        !byte %00000000,%00000000,%00000000  ; Row 21
        !byte 0                               ; Padding byte (unused)
```

The `%` prefix lets us use binary - perfect for visualizing sprite graphics! Each 1 is a pixel, each 0 is transparent.

### Step 3: Enabling and Positioning

Now let's make our sprite visible:

```text
        ; Enable sprite 0
        lda #%00000001         ; Bit 0 = sprite 0
        sta $d015              ; Sprite enable register
        
        ; Set sprite color (white)
        lda #$01               ; White
        sta $d027              ; Sprite 0 color
        
        ; Position sprite (X=100, Y=100)
        lda #100
        sta $d000              ; Sprite 0 X position (low byte)
        lda #100
        sta $d001              ; Sprite 0 Y position
        
        ; Clear X position high bit (for X < 256)
        lda #$00
        sta $d010              ; MSB of X positions
```

The X position needs 9 bits (0-511 pixels), so positions above 255 use the MSB register at $D010.

### Step 4: Making It Move - The Dance of Timing and Motion

Now for the moment of truth - bringing our sprite to life! This is where the magic happens, where static pixels become dynamic animation. The technique you're about to learn is the same one used in every smooth C64 game from "International Karate" to "The Last Ninja."

The secret to smooth animation is synchronization with the video display. The C64's screen refreshes 50 times per second (PAL) or 60 times (NTSC). By timing our sprite movements to match this refresh rate, we achieve butter-smooth motion without any flicker or tearing.

```text
main_loop:
        ; Wait for raster line (smooth animation)
        lda #250               ; Wait for line 250
wait_raster:
        cmp $d012              ; Current raster line
        bne wait_raster
        
        ; Move sprite right
        inc $d000              ; Increment X position
        bne check_edge         ; If it didn't wrap to 0, check edge
        
        ; Handle X > 255 (set MSB)
        lda $d010
        ora #%00000001         ; Set bit 0 (sprite 0 MSB)
        sta $d010
        
check_edge:
        ; Check if sprite went off right edge
        lda $d000
        cmp #88                ; Right edge minus sprite width
        bne main_loop
        lda $d010
        and #%00000001         ; Check MSB
        beq main_loop          ; If MSB=0, keep going
        
        ; Reset to left side
        lda #0
        sta $d000              ; X = 0
        sta $d010              ; Clear MSB
        
        jmp main_loop
```

**The Raster Synchronization Magic:**
The `$D012` register tells us which line the electron beam is currently drawing on your TV or monitor. By waiting for a specific line (250, near the bottom of the visible screen), we ensure our sprite position updates happen during the vertical blank period - the brief moment when the beam resets to the top of the screen. This prevents any visual artifacts.

**The 9-Bit X Position Challenge:**
The C64's screen is 320 pixels wide, but sprites can move beyond the visible area (up to position 511). Since a byte can only hold values 0-255, Commodore's engineers used a clever solution: an extra register ($D010) holds the 9th bit for each sprite's X position. When our sprite's X coordinate wraps from 255 to 0, we set its corresponding bit in $D010 to indicate it's now in the 256-511 range.

This creates smooth, continuous animation that:
1. **Synchronizes with the display** - Updates happen between screen refreshes
2. **Moves pixel by pixel** - One pixel per frame for smooth motion
3. **Handles the full coordinate space** - Manages the 9-bit X position elegantly
4. **Wraps seamlessly** - Returns to the left edge after leaving the right

**Historical Note:** This raster synchronization technique was discovered early in the C64's life and became fundamental to game programming. Archer Maclean used it in "Dropzone" to achieve arcade-perfect scrolling. Without this timing precision, sprites would appear to jump or flicker - destroying the illusion of smooth motion.

### Different Movement Patterns

**Vertical Movement:**
```text
        inc $d001              ; Move down instead of right
        lda $d001
        cmp #229               ; Bottom edge
        bne continue
        lda #50                ; Reset to top
        sta $d001
```

**Diagonal Movement:**
```text
        inc $d000              ; Move right
        inc $d001              ; And down
```

**Bouncing:**
```text
direction:
        !byte 1                ; 1=right, 255(-1)=left
        
        ; In movement code:
        lda $d000
        clc
        adc direction          ; Add direction
        sta $d000
        
        ; Check edges and reverse
        cmp #24                ; Left edge
        beq reverse
        cmp #255-24            ; Right edge
        bne continue
reverse:
        lda direction
        eor #$fe               ; Toggle between 1 and 255
        sta direction
```

## Understanding Sprite Mechanics

### The Raster Beam

The VIC-II draws the screen line by line with an electron beam (on CRT monitors). The raster register ($D012) tells you which line is currently being drawn. By waiting for specific lines, you ensure smooth animation without tearing.

### Sprite Priorities

- Sprites have priority order: 0 (highest) to 7 (lowest)
- Lower numbered sprites appear in front of higher ones
- You can also control sprite-to-background priority with $D01B

### Collision Detection

The VIC-II automatically detects collisions:
- **$D01E**: Sprite-to-sprite collision
- **$D01F**: Sprite-to-background collision

Reading these registers tells you which sprites collided!

## Common Issues and Solutions

### "Sprite doesn't appear"
- Check sprite is enabled in $D015
- Verify sprite pointer is correct
- Ensure sprite data exists at the right address
- Check X/Y positions are on screen

### "Sprite looks garbled"
- Sprite data must be exactly 63 bytes
- Each row must be exactly 3 bytes
- Check you're using the right pointer value

### "Movement is jerky"
- Always wait for raster before moving
- Move by small amounts (1-2 pixels)
- Keep animation loop simple and fast

### "Sprite disappears at edges"
- Remember X position is 9 bits (0-511)
- Use $D010 for the high bit
- Account for sprite width when checking edges

## Quick Reference

### Sprite Registers
- **$D000-$D00E**: X positions (even addresses)
- **$D001-$D00F**: Y positions (odd addresses)
- **$D010**: X position MSBs (9th bit)
- **$D015**: Sprite enable
- **$D017**: Y expansion (double height)
- **$D01B**: Sprite-to-background priority
- **$D01C**: Multicolor mode
- **$D01D**: X expansion (double width)
- **$D01E**: Sprite-sprite collision
- **$D01F**: Sprite-background collision
- **$D027-$D02E**: Individual sprite colors

### Sprite Pointers
- **$07F8-$07FF**: Sprite data pointers (one per sprite)
- Value = address / 64 (e.g., $2000 / 64 = 128)

### Sprite Data Format
- 63 bytes per sprite
- 21 rows × 3 bytes per row
- Binary format perfect for design
- 64th byte unused (padding)
