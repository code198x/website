## Understanding Sprite Animation

Before we code, let's understand the approach:

### Frame-Based Animation
```
Frame 0: Idle stance (standing still)
Frame 1: Left foot forward
Frame 2: Mid-stride
Frame 3: Right foot forward
(repeat 1-2-3 while moving)
```

### Animation Timing
```
Movement: 2 pixels per frame
Animation: Change frame every 4 updates
Result: Smooth walk cycle during movement
```

## Building the Animation System

Let's add life to our Grid Protocol sprite!

### Step 1: Define Animation Frames
**"Four frames of walking goodness!"**

```text
; Animation frame definitions
FRAME_IDLE = 0
FRAME_WALK1 = 1
FRAME_WALK2 = 2
FRAME_WALK3 = 3

; Animation control
current_frame:    !byte 0
frame_timer:      !byte 0
FRAME_DELAY = 4   ; Updates between frame changes
```

**Key Point**: Frame timer controls animation speed!

### Step 2: Store Sprite Data
**"Each frame gets its own sprite pattern!"**

```text
; Sprite data locations (64 bytes each)
; $0340 - Frame 0 (idle)
; $0380 - Frame 1 (walk 1)
; $03C0 - Frame 2 (walk 2)
; $0400 - Frame 3 (walk 3)

*=$0340
sprite_data_frame0:
    ; Simple character - idle stance
    !byte %00111000
    !byte %00111000
    !byte %00010000
    ; ... (rest of sprite data)

*=$0380
sprite_data_frame1:
    ; Left foot forward
    !byte %00111000
    !byte %00111000
    !byte %00010000
    ; ... (different leg position)
```

**Key Point**: Each frame is a complete 21×24 sprite!

### Step 3: Animation During Movement
**"Cycle frames while moving!"**

```text
update_animation:
    ; Only animate while moving
    lda movement_state
    cmp #STATE_MOVING
    bne set_idle_frame
    
    ; Increment frame timer
    inc frame_timer
    lda frame_timer
    cmp #FRAME_DELAY
    bcc animation_done
    
    ; Reset timer and advance frame
    lda #0
    sta frame_timer
    
    ; Cycle through walking frames (1-3)
    inc current_frame
    lda current_frame
    cmp #4
    bcc update_sprite_pointer
    lda #1              ; Back to walk frame 1
    sta current_frame
    jmp update_sprite_pointer
    
set_idle_frame:
    lda #FRAME_IDLE
    sta current_frame
    lda #0
    sta frame_timer
```

**Key Point**: Only frames 1-3 cycle during walking!

### Step 4: Update Sprite Pointer
**"Tell VIC-II which frame to display!"**

```text
update_sprite_pointer:
    ; Calculate sprite block number
    ; Frame 0: $0340 / 64 = $0D
    ; Frame 1: $0380 / 64 = $0E
    ; Frame 2: $03C0 / 64 = $0F
    ; Frame 3: $0400 / 64 = $10
    
    lda current_frame
    clc
    adc #$0D            ; Base sprite block
    sta $07F8           ; Sprite 0 pointer
    
animation_done:
    rts
```

**Key Point**: Sprite pointer = memory address / 64!

### Step 5: Direction Awareness
**"Face the way you're moving!"**

The C64 has no hardware sprite flipping, so we use pre-stored mirrored frames:

```text
; IMPORTANT C64 LIMITATION:
; The C64 has NO hardware sprite flipping!
; We're using solution #1: Pre-stored mirrored sprites
;
; Memory layout for 8 frames:
; Right-facing (frames 0-3): $0340-$0400
; Left-facing (frames 4-7): $0440-$0500
; Total memory: 512 bytes (64 bytes × 8 frames)

handle_direction:
    ; Track movement direction
    lda joystick_state
    and #$08            ; Right?
    beq check_left_dir
    lda #0              ; 0 = facing right
    sta facing_direction
    rts
    
check_left_dir:
    lda joystick_state
    and #$04            ; Left?
    beq direction_done
    lda #1              ; 1 = facing left
    sta facing_direction
    
direction_done:
    rts

; In animation update, select correct frame set:
update_sprite_pointer:
    lda facing_direction
    beq use_right_frames
    
    ; Left-facing: use frames 4-7 (blocks $11-$14)
    lda anim_frame
    clc
    adc #$11            ; Base for left frames
    sta $07f8
    jmp animation_done
    
use_right_frames:
    ; Right-facing: use frames 0-3 (blocks $0D-$10)
    lda anim_frame
    clc
    adc #$0d            ; Base for right frames
    sta $07f8
```

**Learning Moment**: This doubles our sprite memory usage but provides proper directional facing. This is exactly what professional C64 games like Impossible Mission and The Last Ninja did - they pre-stored both left and right versions of every animation frame!

## Understanding the Animation

### Frame Timing
With FRAME_DELAY = 4:
- **50 FPS PAL**: Frame changes 12.5 times per second
- **Walk cycle**: Complete cycle every 0.24 seconds
- **Natural feel**: Matches typical walking pace

### Memory Layout
```
Right-facing frames:
$0340-$037F: Frame 0 (idle right)
$0380-$03BF: Frame 1 (walk right 1)
$03C0-$03FF: Frame 2 (walk right 2)
$0400-$043F: Frame 3 (walk right 3)

Left-facing frames (mirrored):
$0440-$047F: Frame 4 (idle left)
$0480-$04BF: Frame 5 (walk left 1)
$04C0-$04FF: Frame 6 (walk left 2)
$0500-$053F: Frame 7 (walk left 3)
```

Total: 512 bytes for complete bidirectional animation.

## Technical Reference

### Animation Settings
- **FRAME_DELAY**: 4 updates between changes
- **Animation frames**: 0-3 (right), 4-7 (left)
- **Frame rate**: 12.5 changes per second at 50 FPS

### Sprite Memory
- **Right frames 0-3**: $0340-$0400 (blocks $0D-$10)
- **Left frames 4-7**: $0440-$0500 (blocks $11-$14)
- **Total memory**: 512 bytes (8 frames × 64 bytes)

### C64 Sprite Limitations
- **No hardware flipping**: Must store or generate flipped versions
- **No rotation**: Rotation requires pre-computed frames
- **8 sprites max**: Without multiplexing techniques

### Animation States
- **Idle**: Frame 0, no timer
- **Moving**: Frames 1-3 cycling, timer active
