# Display Your First Sprite
**Your first graphics object on the Commodore 64**

Picture this: December 1982. You're at a computer shop in the UK watching demonstrations of different machines. The ZX Spectrum shows its colorful graphics, but moving objects flicker badly due to its attribute clash issues. The BBC Micro displays solid graphics, but character movement is clearly just redrawing text positions - you can see the slight delays.

Then someone fires up the newly arrived Commodore 64 and loads up "Omega Race" - and you're stunned. Perfect little spacecraft sprites move smoothly across the star field, never flickering, never disturbing the background graphics. Eight independent objects that could move simultaneously without any visual artifacts. This was the moment many people realized the C64 was in a different league entirely.

What you witnessed was the power of hardware sprites - dedicated graphics objects that the VIC-II chip composites over the background in real-time. No calculating positions, no erasing and redrawing - the hardware does it all for you.

Today, you're going to create your very own hardware sprite and experience that same magical moment!

## Understanding Hardware Sprites

The VIC-II chip can display 8 sprites (numbered 0-7). Each sprite is:
- **24×21 pixels** in single-color mode
- **Independent** from the background
- **Positioned** with X,Y coordinates

Think of sprites like cardboard cutouts you can place anywhere on a painted background - they don't affect what's behind them.

## Why Hardware Sprites Were Revolutionary

Before the C64, moving graphics meant software sprites - a programming nightmare. Here's what other computers had to do for a simple moving character:

**The Painful Process:**
1. Save background data where sprite will appear
2. Draw sprite over background  
3. When moving: restore saved background (erase sprite)
4. Save new background data at destination
5. Draw sprite at new location
6. Repeat 50-60 times per second...

This consumed enormous CPU time and caused flicker. The C64's hardware sprites eliminated this entirely. The VIC-II chip handles all sprite drawing during the video scan, with zero CPU overhead for the actual graphics.

**Why 24×21 Pixels?**
This wasn't arbitrary. At 63 bytes per sprite, you could fit sophisticated character graphics while keeping memory usage reasonable. The dimensions provided enough detail for recognizable game characters - from the spaceship in "Defender" to Mario-style platformer heroes.

**The 64th Byte Mystery:**
Each sprite uses 64 bytes but only 63 contain graphics data. The extra byte isn't wasted - it ensures sprites align on 64-byte boundaries for lightning-fast VIC-II access. This is the kind of engineering elegance that made the C64 special.

## Designing Your Sprite

A sprite is defined by 63 bytes of data. Each byte represents 8 pixels (bits), with 3 bytes per row, and 21 rows total. Think of it as a grid where each bit is either on (1) or off (0).

### Professional Design Methods

The binary sprite design method you're about to use is exactly how legendary C64 artists worked. Jeff Minter would sketch sprites on graph paper, then convert each row to binary. Andrew Braybrook famously designed the Uridium ship using this exact technique.

**Professional Tip:** Many developers used character sets (like Commodore's character ROM) as reference for proportions. A sprite is roughly the same size as a 3×2 grid of characters - perfect for game elements that need to interact with text-based mazes or platforms.

## The Code

Here's the complete program to display a sprite:

```asm
; Display a sprite - Lesson 2
; Displays a diamond-shaped sprite on the screen

        ; BASIC stub: 10 SYS 2064
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$34,$00,$00,$00

start:
        ; Step 1: Copy sprite data to sprite area
        ldx #62                 ; 63 bytes (0-62)
copy_sprite:
        lda sprite_data,x       ; Get byte from our data
        sta $2000,x             ; Store at sprite location
        dex
        bpl copy_sprite         ; Loop until done

        ; Step 2: Set sprite pointer
        ; Sprite 0 pointer is at $07F8
        ; $2000 / 64 = $80
        lda #$80
        sta $07F8               ; Tell VIC-II where sprite 0 data is

        ; Step 3: Set sprite color
        lda #$03                ; Cyan color
        sta $D027               ; Sprite 0 color register

        ; Step 4: Position the sprite
        lda #$AC                ; X position (center of screen)
        sta $D000               ; Sprite 0 X position
        lda #$C8                ; Y position (lower part of screen)
        sta $D001               ; Sprite 0 Y position

        ; Step 5: Enable sprite 0
        lda #$01                ; Bit 0 = sprite 0
        sta $D015               ; Sprite enable register

        ; Done! Sprite should be visible
        rts

; Sprite data - diamond shape (63 bytes)
; Note: % means binary number (1=pixel on, 0=pixel off)
sprite_data:
        !byte %00000000,%00011000,%00000000  ; Row 1
        !byte %00000000,%00111100,%00000000  ; Row 2
        !byte %00000000,%01111110,%00000000  ; Row 3
        !byte %00000000,%11111111,%00000000  ; Row 4
        !byte %00000001,%11111111,%10000000  ; Row 5
        !byte %00000011,%11111111,%11000000  ; Row 6
        !byte %00000111,%11111111,%11100000  ; Row 7
        !byte %00001111,%11111111,%11110000  ; Row 8
        !byte %00011111,%11111111,%11111000  ; Row 9
        !byte %11000011,%11111111,%11000011  ; Row 10
        !byte %11100111,%11111111,%11100111  ; Row 11
        !byte %01111110,%11111111,%01111110  ; Row 12
        !byte %00111100,%11111111,%00111100  ; Row 13
        !byte %00011000,%01111110,%00011000  ; Row 14
        !byte %00000000,%00111100,%00000000  ; Row 15
        !byte %00000000,%00000000,%00000000  ; Row 16
        !byte %00000000,%00000000,%00000000  ; Row 17
        !byte %00000000,%00000000,%00000000  ; Row 18
        !byte %00000000,%00000000,%00000000  ; Row 19
        !byte %00000000,%00000000,%00000000  ; Row 20
        !byte %00000000,%00000000,%00000000  ; Row 21
```

## How It Works

1. **Copy sprite data** - We copy our 63-byte sprite design to memory location $2000
2. **Set sprite pointer** - We tell the VIC-II where to find sprite 0's data
3. **Set color** - Make the sprite yellow (color 7)
4. **Position sprite** - Place it at coordinates (128, 128)
5. **Enable sprite** - Turn on sprite 0

## Key Memory Locations

```
$D000-$D001: Sprite 0 X,Y position
$D015:       Sprite enable register (bit 0 = sprite 0)
$D027:       Sprite 0 color
$07F8:       Sprite 0 pointer (screen RAM + $03F8)
$2000:       Where we put our sprite data
```


### Multi-Sprite Formations

**Classic Game Patterns:**
```asm
        ; Enable multiple sprites like "Galaga"
        lda #%00000111         ; Sprites 0, 1, 2
        sta $d015

        ; Formation flying positions
        lda #100
        sta $d000              ; Leader X
        lda #120
        sta $d002              ; Wingman 1 X
        lda #80
        sta $d004              ; Wingman 2 X
```

### Sprite Color Effects

**Rainbow Cycling (like "Wizball"):**
```asm
color_cycle:
        ldx #0
cycle_loop:
        txa
        and #$0f               ; Keep in 0-15 range
        sta $d027              ; Change sprite color

        ; Professional delay routine
        ldy #100
delay_outer:
        ldx #255
delay_inner:
        dex
        bne delay_inner
        dey
        bne delay_outer

        inx
        jmp cycle_loop
```

## Common Issues

**Sprite doesn't appear?**
- Check that sprite enable bit is set ($D015)
- Verify sprite pointer is correct ($07F8)
- Make sure sprite is on screen (X: 24-343, Y: 50-249)

**Sprite is garbage?**
- Sprite data must be aligned on 64-byte boundary
- Check that all 63 bytes are defined
