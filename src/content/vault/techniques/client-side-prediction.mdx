**Client-side prediction** lets an online game respond to your movement input before the server's answer arrives. Your computer calculates a provisional result; the server remains authoritative. Prediction hides some of the delay you feel, but does not make packets travel faster.[^bernier]

[Quake](/vault/games/quake)'s *QuakeWorld* update provides a documented example. *Computer Gaming World* previewed John Carmack's work in October 1996, distinguishing smaller packets from changes which made play **feel** faster. *PC Gamer* subsequently reported a free release in mid-December 1996.[^cgw][^pcg]

## How it works

Think of pressing forward while waiting for a network round trip. A client that waits for every server reply feels slow. A predicting client can show movement immediately, using its local movement simulation.[^bernier]

The released *QuakeWorld* code makes the process concrete:

1. Start from the last player state received from the server.
2. Run subsequent stored input commands through the movement simulation.
3. Use the resulting position to draw the player's view.

`CL_PredictMove` performs this work, calling `CL_PredictUsercmd`, which in turn calls `PlayerMove`. When another server update arrives, it supplies a new starting point. Replaying the remaining commands brings that authoritative state towards the present.[^code]

The client and server can disagree. A correction may therefore move the view away from its earlier predicted position. Valve's Yahn Bernier describes this trade-off in his account of *Half-Life* networking: responsive local movement still needs correction from the server.[^bernier]

## What players could adjust

In March 1997, *Computer and Video Games* told *QuakeWorld* players to set `PUSHLATENCY` to the negative of their ping. Its report praised the improvement in character control while noting that rockets and doors could still respond late.[^cvg]

In the released code, `pushlatency` helps set the time towards which the client predicts, capped at the current time. It changes the local simulation's timing; it does not remove network delay.[^code]

## Three different problems

Predicting **your own movement** uses inputs your computer already knows. Displaying **other players** is a different problem: your computer does not yet know their next input. Bernier discusses extrapolating their motion or interpolating between received positions separately.[^bernier]

**Lag compensation** is another operation again. In Bernier's account, the server considers earlier world positions when resolving a delayed command such as a shot. Responsive movement on your screen does not, by itself, solve hit detection across a network.[^bernier]
