**FLD**, flexible line distance, pushes the Commodore 64's picture down the screen without moving any of it. The program never touches screen memory. It changes one register on each raster line so that the [VIC-II](/vault/hardware/vic-ii) keeps putting off the start of its next character row, and every row below the gap arrives later. The gap can be any number of raster lines, so the picture moves one pixel at a time, and it can be different on every frame: the screen bounces, or opens up between its rows.

FLD is also the easy one among the C64's badline tricks. [VSP](/vault/techniques/vsp) and [FLI](/vault/techniques/fli) need a register write on an exact cycle. FLD only needs the write to land somewhere on the right line, and not even on every line. And the demo scene's own list of firsts records it in commercial games before any demo.

## How it works

The VIC-II builds its text and bitmap display out of character rows, and it starts each row on a **badline**: the raster line on which it stops the processor and reads that row's 40 character codes. Christian Bauer's 1996 description of the chip gives the rule. A line is a badline when the raster is between `$30` and `$F7`, the display was switched on during line `$30`, and "the lower three bits of RASTER are equal to YSCROLL", the vertical scroll value in bits 0 to 2 of `$D011`. Normally that happens every eighth line.

After a row's eighth line the chip drops into what Bauer calls the **idle state**, and it stays there until the next badline. So a program that keeps changing YSCROLL, always to a value that does not match the current line, can stop the next row from starting for as long as it likes. In Bauer's words, "The distance between two text lines can be arbitrarily increased if only you hold back the next Bad Line long enough." When the program lets YSCROLL settle, the next badline comes and the chip carries on with the row after the last one it showed. Nothing is skipped: the rows below simply appear lower down. Bauer's example allows only three badlines on the whole screen, at lines `$50`, `$78` and `$A0`, so the VIC-II shows three text rows with gaps between them. Delay only the first badline and "you can scroll down the complete graphics display by large distances without moving a single byte in display memory."

Several things follow from the rule:

- **The gap is not empty.** In the idle state the VIC-II still fetches graphics, always from the last byte of its 16K bank (`$3FFF` in the default bank), and shows that byte across the whole line. If the byte is zero the gap shows the background colour; if not, it fills with vertical stripes.
- **The step is one raster line.** The block that moves is a whole character row, but the gap can be any height.
- **Bitmaps move too.** Bitmap modes use the same row counters, so FLD pushes a bitmap picture down in exactly the same way. In standard bitmap mode the gap shows the idle byte in black.
- **Rows can fall off the bottom.** No badline can start below line `$F7`, so rows pushed that far down are not shown at all.
- **The gap is cheap.** A line that is not a badline does not stop the processor, so the lines in the gap give back the 40 to 43 cycles a badline would have taken.

## The forgiving one

The timing is loose because YSCROLL only has to stay out of step with the raster. A program that sets YSCROLL to the value of the line that has just passed has seven lines before the two match again. The Codebase64 wiki's FLD page, signed by HCL, puts it this way: "FLD does not require exact timing and doesn't even have to be updated each rasterline (only every ~6:th rasterline is ok). FLD can even be done with periodic interrupts instead of looped code that just wastes all the precious rastertime." [Linecrunch](/vault/techniques/linecrunch), which cuts rows short to move the screen up, has to hit a short window at the same point on every line.

That tolerance makes FLD a good first raster trick. The routine below uses the same method as HCL's example. It waits for the top of the frame, then adds one to YSCROLL on each raster line, so YSCROLL always stays two ahead of the bottom three bits of the raster line and the next badline never comes. The number of lines grows from 0 to 63 and back, so the screen bounces.

```asm
; FLD bouncer (ACME syntax). SYS 49152 to start;
; RUN/STOP and RESTORE to stop.
        * = $c000
        sei             ; no interrupts: this loop owns the machine
frame   bit $d011       ; wait for raster line 256 or later
        bpl frame       ; (bit 7 of $D011 is bit 8 of the raster)
top     bit $d011       ; then for the start of the next frame
        bmi top
        lda #$1b        ; normal $D011: screen on, 25 rows, YSCROLL 3
        sta $d011
        jsr bounce      ; A = size of this frame's gap, 0-63 lines
        tax
        beq frame       ; no gap this frame
        lda #$31        ; wait for raster line $31, before the
wait    cmp $d012       ; first badline at $33
        bne wait
fld     lda $d012       ; wait for the next raster line
same    cmp $d012
        beq same
        clc             ; move YSCROLL one line on, so it keeps
        lda $d011       ; the same lead over the raster line and
        adc #1          ; the next badline never comes
        and #7
        ora #$18        ; screen on, 25 rows, text mode
        sta $d011
        dex
        bne fld
        jmp frame
bounce  lda count       ; count 0-127 as a triangle: 0..63..0
        inc count
        and #$7f
        cmp #$40
        bcc up
        eor #$7f
up      rts
count   !byte 0
```

Run on a PAL C64 in the VICE emulator, it moves the BASIC start-up screen up and down between its normal place and 63 lines lower. `POKE 16383,85` before starting it turns the gap into stripes, which is the idle state showing through.

## In print

Magazine readers could type FLD in for themselves. In November 1989 *Commodore Disk User* followed Miles Barry's introduction to raster effects in the previous issue with Andy Partridge's "Rasters and Colour", whose disk included a routine for "bouncing portions of the screen up and down". He described the trick as shifting "the video matrix down, leaving gaps between the 25 screen lines", with each change to `$D011` making the chip miss a line, "thereby shifting the screen down one pixel". He also named an inventor: "'White' of Holland".

Four years later the American *Compute!* printed a type-in, "Screen Bouncer" by Bob Broderick, "using a technique known as flexible line distance" to bounce the screen "down and up". Its explanation had the mechanism backwards. It said the routine kept the VIC chip "so busy that it won't have time to send any video information"; Bauer's description shows that during the gap the chip is idle and the processor has more time, not less. The program also came with a POKE to clear "the streaks the program leaves in the empty areas at the top of the screen", which match the idle-state stripes described above.

## Games first, demos second

The Codebase64 wiki's list of demo firsts, a collaborative record that began as a list posted to the CSDb forum, starts its FLD section with two commercial games:

| Release | Kind | Date in the list |
|---|---|---|
| *The Vikings*, Thomas Larsen ("full screen FLD") | game | before March 1987 |
| *Tiger Mission*, Thomas Larsen | game | before March 1987 |
| *Mega Jive*, Mule of The Cream Crackers | demo | "around march 1987" |

Both games came from Kele Line, a young Danish publisher. *Zzap!64* visited in February 1987 and reported that the company had been founded the previous August and that *The Vikings* had been launched at a party at its offices outside Copenhagen "just before Christmas". Its C64 credits, as quoted by the Finnish Retro Game Comparison Blog, include a "C64 hi-res scroll-routine by Thomas Larsen" alongside the main programmer Søren Grønbech. The company told the magazine that for *The Vikings* "we added the full-screen picture at the start, came up with the little play for the opening sequence", and its review gave the presentation 93% for the "Full-screen loading picture, and very pretty attract sequence", though only 55% overall. *Tiger Mission*, a vertically scrolling helicopter shoot-'em-up, got 51% in March. Neither review names the technique. CSDb lists *Mega Jive* as a 1987 one-file demo with code by Mule and music by Rob Hubbard.

The list's compilers warn that "It is not always straightforward to determine who did what and when", and that "some of these issues are subject to dispute". Their own entry records a disagreement over whether "before March" means February. *Commodore Disk User*'s credit to "White" of Holland is a different answer again, and no public source found for this entry connects the two.

FLD also led to another trick. JCB of The Mean Team said that [VSP](/vault/techniques/vsp), first shown in October 1987, began as "a bugged FLD routine that started to make the screen move around". Bauer later described combining the two with linecrunch: "you can scroll complete graphics screens without using much computing time by almost arbitrarily large distances in all directions", the combination known as [AGSP](/vault/techniques/agsp).

## Later games

FLD kept turning up in games. Martin Piper's game *Tusari* went out on a *Zzap!64* cover tape in October 1992 as a reader's game, which the magazine called "Arguably the best reader game we've ever had". The Codebase64 wiki publishes a reverse-engineered version of its FLD parallax, describing *Tusari* as "the first documented game to use FLD with parallax in vertical scrolling sections" and noting that "The original game used mainline code without any IRQ/NMI action", in other words a plain loop rather than raster interrupts.
