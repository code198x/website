A 6502 or Z80 puts out a 16-bit address, so it can see 65,536 bytes and no more. The Atari 2600's cut-down 6507 sees only 8K, and gives its cartridge 4K of that. Programs outgrew those windows almost at once. Bank switching is the way round: fit more ROM or RAM than the processor can address, put a latch outside the processor, and let the program tell the latch which bank should answer a given range of addresses. The processor never knows. It reads `$8000` as it always did, and gets a different byte because something outside it changed its mind.

How the program tells the latch is where the machines differ, and some of the answers are strange. On an Atari 2600 cartridge, reading a particular address is enough. On many NES boards the program writes a bank number into its own ROM. On the Commodore 64 it clears a bit in a port built into the processor. On the Spectrum 128 it sends a byte to an I/O port that can never be read back, and on the CPC6128 to a port whose values one of the first books about the machine had to work out by experiment.

## Atari 2600: switching by looking

The 2600's cartridge slot gives a game 4K. *Electronic Games* explained the way past it to a reader in November 1982: "as of *Missile Command* and *Asteroids*", the VCS "is capable of up to 8K, using a special bank switch that flip-flops two 4K programs".

The cartridge's own logic watches the address bus. In Atari's 8K scheme, known as F8, two addresses near the top of the cartridge space, `$1FF8` and `$1FF9`, select the two 4K halves, and in Kevin Horton's 1990s survey of cartridge types, "any access to either one of these locations switches banks". A read is as good as a write. Parker Brothers split its 8K into 1K slices, three of which the program can choose independently from `$1FE0-$1FF7`, while the last 1K stays fixed so that the game can always start.

[Activision](/vault/companies/activision)'s scheme for *Decathlon* and *Robot Tank* made the switch happen by itself. Horton's description: "You set the stack pointer to FF, and then a JSR switches banks one way, while RTS switches you back to the original bank." A call into the other bank was an ordinary subroutine call.

## NES: mappers on the cartridge

The NES gives the cartridge `$8000-$FFFF` for program ROM, 32K, and 8K of the PPU's address space for tile graphics. Anything larger needs a **mapper**: logic on the cartridge board that decides which part of the ROM appears where. The iNES file format for emulators numbers them, and the numbers are how programmers usually name them.

| Mapper | Board family | What it switches | Examples |
|---|---|---|---|
| 0 | NROM | Nothing: 16K or 32K of program ROM, 8K of graphics | *[Super Mario Bros.](/vault/games/super-mario-bros)* |
| 2 | UxROM | A 16K program bank at `$8000`; `$C000-$FFFF` fixed to the last bank. 128K on UNROM, 256K on UOROM | *[Mega Man](/vault/games/mega-man)*, *[Castlevania](/vault/games/castlevania)* |
| 3 | CNROM | 8K of graphics at a time, up to 32K; program ROM fixed at 32K | |
| 1 | [MMC1](/vault/hardware/mmc1) | 16K or 32K program banks, 4K or 8K graphics banks, mirroring. 256K of program ROM (512K on the SUROM board) | *[The Legend of Zelda](/vault/games/legend-of-zelda)*, *[Metroid](/vault/games/metroid)* |
| 4 | [MMC3](/vault/hardware/mmc3) | 8K program banks, 1K and 2K graphics banks, a scanline interrupt counter. Up to 512K of program ROM and 256K of graphics | *[Super Mario Bros. 3](/vault/games/super-mario-bros-3)* |
| 5 | MMC5 | Up to 1024K each of program ROM and graphics, extended attributes, extra sound channels | *Castlevania III* |

The 6502 fetches its reset and interrupt vectors from `$FFFA-$FFFF`, so the switching mappers above keep the top of the map fixed, or start up in a mode that does. The code that must always be reachable lives there: the reset routine, the interrupt handlers and the code that switches banks.

### UxROM: write the bank number, carefully

UxROM has a single register that answers anywhere in `$8000-$FFFF`. There is a catch. Nintendo's original UxROM boards do not stop the ROM driving the data bus when the processor writes to it, so on a write the ROM and the processor both put a byte on the bus. NESdev calls this a bus conflict. The safe way is to write the bank number to a ROM byte that already holds the same number, so the two agree:

```asm
banktable: .byte 0, 1, 2, 3, 4, 5, 6   ; in the fixed bank

bankswitch_y:          ; select 16K bank Y at $8000-$BFFF
    sty cur_bank       ; keep a copy: the register cannot be read back
    tya
    sta banktable,y    ; ROM already holds Y here, so no conflict
    rts
```

CNROM has the same conflict. The MMC chips do not: Nintendo's MMC1 specification explains that the chip gates the ROM's select line with the read/write signal, so the ROM stays silent during a write.

### MMC1: five writes for one register

MMC1 saves pins by taking its data one bit at a time. Each write to `$8000-$FFFF` shifts bit 0 of the value into a 5-bit register, least significant bit first. On the fifth write the whole value goes into one of four internal registers, chosen by the address of that fifth write. A write with bit 7 set resets the sequence.

```asm
    lda #%10000000   ; bit 7 set = reset shift register
    sta $8000        ; (use this to abort a partial write sequence)

    ; Now write the 5 bits of the bank number, LSB first
    lda #1           ; bit 0
    sta $E000
    lda #1           ; bit 1
    sta $E000
    lda #0           ; bit 2
    sta $E000
    lda #0           ; bit 3
    sta $E000
    lda #0           ; bit 4 (0 = PRG RAM enabled on MMC1B)
    sta $E000        ; fifth write to $E000-$FFFF latches PRG bank %00011 = 3
```

Two details matter in practice. NESdev notes that "when the serial port is written to on consecutive cycles, it ignores every write after the first", which is why read-modify-write instructions such as `INC` behave oddly here. And an interrupt handler that switches banks in the middle of the main program's five writes leaves the register half-filled, so a program has to keep its handlers from switching banks mid-sequence, or have them put the switch right afterwards.

### MMC3: select, then set

MMC3 splits the job across a pair of addresses. An even address in `$8000-$9FFF` chooses which of eight bank registers to set; the odd address after it takes the bank number.

```asm
    lda #$06         ; index 6 = PRG bank at $8000 (PRG mode 0, bit 6 clear)
    sta $8000        ; bank select
    lda #$0A
    sta $8001        ; bank data: PRG bank $0A now at $8000
```

The select write also carries two mode bits, bit 6 for the program ROM layout and bit 7 for the graphics layout, so every select write has to include the modes the program wants. The [MMC3](/vault/hardware/mmc3) entry has the full register map and its scanline counter.

### Calling code in another bank

Code in one switchable bank cannot simply `JSR` into another. The moment it switches, the instructions it is running disappear, and an `RTS` from the other bank would return into whatever bank happens to be mapped. The usual answer is a small routine in the fixed bank, often called a trampoline, that switches, calls, and switches back. The 6502 has no indirect `JSR`, but a `JSR` to a `JMP (indirect)` does the same job. For UxROM, using `bankswitch_y` from above:

```asm
; Run the routine at far_ptr in bank far_bank, then restore
; the caller's bank. The routine's result comes back in A.
far_call:
    lda cur_bank
    pha              ; remember the caller's bank
    ldy far_bank
    jsr bankswitch_y
    jsr jump_far     ; JSR to a JMP (indirect) acts as an indirect call
    tax              ; keep the result
    pla
    tay
    jsr bankswitch_y ; back to the caller's bank
    txa
    rts
jump_far:
    jmp (far_ptr)
```

## Commodore 64: ROM over RAM

The C64 has the opposite problem. It has a full 64K of RAM, and 20K of ROM, and I/O chips that need addresses of their own. The 6510 processor has a small I/O port at addresses `$00` and `$01`, and three of its bits decide what the processor sees in the upper part of the map:

| Bit of `$01` | Name | Controls |
|---|---|---|
| 0 | LORAM | BASIC ROM or RAM at `$A000-$BFFF` |
| 1 | HIRAM | KERNAL ROM or RAM at `$E000-$FFFF` |
| 2 | CHAREN | I/O chips or character ROM at `$D000-$DFFF` |

The bits combine rather than act alone. BASIC needs the KERNAL, so clearing HIRAM removes BASIC as well. With both LORAM and HIRAM clear there is RAM at `$D000-$DFFF` too, whatever CHAREN says. The usual value, `$37`, gives BASIC, the KERNAL and I/O with "38K contiguous bytes of user RAM"; `$35` gives "60K bytes of RAM and I/O devices", for which "the user must write his own I/O driver routines"; `$34` gives "access to all 64K bytes of RAM". The [6510](/vault/hardware/6510) entry has the full table. Two lines on the cartridge port, GAME and EXROM, also feed the logic, which is how a cartridge puts its ROM at `$8000` or replaces BASIC or the KERNAL.

The *Programmer's Reference Guide* points out the rule that makes this cheap to live with: "a WRITE (a POKE) to a ROM location will store data in the RAM 'under' the ROM". Only reads see the ROM. So "a hi-resolution screen [can] be kept underneath a ROM, and be changed without having to bank the screen back into the processor address space." Switching the KERNAL out has a cost, though: it takes the interrupt vectors with it, so a program that does so needs interrupts disabled or vectors of its own at `$FFFA-$FFFF`.

## Spectrum 128, +2 and +3: one port, write-only

The 128K Spectrum keeps the 48K machine's layout for the bottom 48K and adds a switchable 16K at the top. RAM page 5 is always at `$4000-$7FFF`, where the screen lives, and page 2 at `$8000-$BFFF`. Any of the eight 16K pages can be switched in at `$C000-$FFFF`. Amstrad's +3 manual gives the bits of port `$7FFD` (32765):

| Bits | Function |
|---|---|
| 0-2 | RAM page at `$C000-$FFFF` |
| 3 | Screen select: page 5 or page 7 |
| 4 | ROM select |
| 5 | Disable paging |

Bit 3 gives a second screen in page 7 that "can only be used by machine code programs", so a program can draw one screen while showing the other. Bit 5 is a one-way switch: "once this bit has been set, no further paging operations will work", and only switching off or pressing reset undoes it. The manual suggests `OUT 32765,48` for 48K games that refuse to run.

The port is write-only, so the manual tells programmers to "keep a copy of the current bank register setting in unpaged RAM", which the ROM does in the system variable BANKM at 23388. It also lists the usual traps: check "that your stack is not being paged out during interrupts, and that your interrupt routine is always where you expect it to be (it is advisable to disable interrupts during paging operations)."

The +2A and +3 add a second port, `$1FFD` (8189). With its bit 0 clear, its bit 2 joins bit 4 of `$7FFD` to choose one of four ROMs. With bit 0 set, the machine switches to one of four all-RAM layouts, which the manual says are "not used by +3 BASIC but are provided for authors of operating systems/games". Where a page sits also affects speed: on the +3, pages 4 to 7 share time with the video circuitry, and "executing NOPs in contended RAM will give an effective clock frequency of 2.66MHz as opposed to the normal 3.53MHz".

## Amstrad CPC6128: values found by experiment

The CPC6128 has two 64K banks of RAM. The switching is done by a small programmable logic chip that shares the gate array's port, `&7Fxx`, and answers when the top two bits of the byte are both set, so the values run from `&C0` to `&C7`.

Amstrad supplied a program called BANK MAN to use the extra memory. When the authors of *La Bible du CPC 6128* (Micro Application, 1985) set out to explain the switching, BANK MAN was the only thing they had to go on, and it was copy-protected, so they worked the values out by experiment. The useful ones swap a 16K block of the second bank in at `&4000-&7FFF`:

| Value | At `&4000-&7FFF` |
|---|---|
| `&C0` | Bank 0, block 1 (the normal setting) |
| `&C4` | Bank 1, block 0 |
| `&C5` | Bank 1, block 1 |
| `&C6` | Bank 1, block 2 |
| `&C7` | Bank 1, block 3 |

The other values rearrange almost the whole map, and the program doing the switching can vanish from under itself. The authors wrote that they had not been able to work out what `&C1` to `&C3` did, and suspected they mattered to CP/M 3.0, which uses the second bank to give programs 61K.

## What it costs

Every machine above leaves the same jobs to the programmer:

- **Keep a copy.** Apart from the C64's port, none of these bank registers can be read back, so the program has to remember what it last wrote.
- **Keep the essentials still.** Interrupt handlers, the stack and the switching code itself must sit in memory that never moves, or be switched in before they are needed.
- **Plan the layout.** Code that calls between banks goes through a routine in fixed memory, and data is arranged so that what a routine needs is in its own bank or a fixed one.
