Commodore gave each C64 sprite one way to grow taller: set its bit in `$D017`, the Y-expansion register, and every row of the 24-by-21-pixel image is drawn twice. **Sprite stretching** turns that on-off switch into a free choice. By clearing and setting the bit again on each raster line, a program makes the [VIC-II](/vault/hardware/vic-ii) draw a row three, four or twenty times, a different number for each row if it likes. Pasi Ojala, explaining the trick in the online magazine [*C=Hacking*](/vault/magazines/c-hacking) in 1993, asked readers to "imagine a sprite scroller with 6-times expanded sprites", and added that with a table of stretch values "it is possible to make easy sinus effects and constantly expanding and shrinking letters."

The trick needs a register write on every line the sprite covers, but unlike most raster tricks the writes do not have to land on one exact cycle.

## How it works

Ojala's verdict on the cause was "It is not really a bug, but a feature". The chip's Y-expansion is built as simply as possible, and the simple design can be steered. Christian Bauer's 1996 description of the VIC-II gives the rules for a PAL 6569. Each sprite has a 6-bit counter, MCBASE, that points at the start of the row being drawn, and an **expansion flip-flop** that decides whether MCBASE moves on:

1. While the sprite's bit in `$D017` is clear, the flip-flop is held set.
2. In cycle 55, near the end of each raster line, the flip-flop is inverted if the bit in `$D017` is set.
3. In cycles 15 and 16 of the next line, MCBASE advances by three bytes, one row of sprite data, but only if the flip-flop is set. When MCBASE reaches 63, the sprite ends.

With the bit left set, the flip-flop inverts on every line, MCBASE advances on every other line, and each row appears twice: ordinary Y-expansion. Stretching breaks the rhythm. Somewhere between cycle 16 and cycle 54, the program clears the bit, which sets the flip-flop, and then sets the bit again. At cycle 55 the flip-flop is inverted back to reset, so MCBASE does not advance and the chip reads the same row again. In Bauer's words, the VIC-II "thinks" it is still on the first line of an expanded row. Do the same on the next line and the row is drawn once more. Leave the bit clear on a line and the chip moves on to the next row.

A stretcher therefore runs a loop with one entry per raster line, taken from a table: repeat this row, or move on. Ojala's routine writes the table value to `$D017` and then its inverse, so that a zero in his table means "stretch". The Codebase64 wiki describes the same pair of writes from the other side, setting the bits "to 1, and then back to 0 on the next rasterline". Either way, what counts is that the bit has been clear for a moment during the line and is set when cycle 55 arrives.

### The window, and what lies outside it

The clear has to come after the increment in cycle 16. Bauer describes what happens when it comes a fraction earlier, in the second half of cycle 15: MCBASE advances by only one byte instead of three, every later row is read one byte out of step, and the sprite misses its end marker and is "effectively displayed twice in sequence". Ojala noticed the same oddity and wrote, "I don't think the distorted counter effect can be used for anything". Demo coders later used it on purpose as [sprite crunching](/vault/techniques/sprite-crunching), which needs the write on that one cycle. The Codebase64 wiki's page on crunching says it can stretch sprites too, "but that can be done much easier with normal $d017-stretching."

The window has another limit. On a badline, the first line of each character row, the VIC-II takes the bus from cycle 15 to cycle 54 to read the row's character codes, and stops the processor from a few cycles before that: the whole of the stretch window. A stretcher that runs over a normal text or bitmap screen therefore also moves the badlines out of the way, rewriting the vertical scroll bits of `$D011` on every line. That is [FLD](/vault/techniques/fld). Ojala's demonstration program does it in the same loop ("Move the screen (bad lines)"), and so does the Codebase64 wiki's example ("Step d011 each line to avoid badlines").

## A stretcher to type in

The routine below stretches sprite 0 by the same amount on every row, from 1 line per row to 6 and back again. It waits in the lower border to fill the table for the next frame, then runs one pass of its loop on each raster line from line `$40`, where the sprite starts. Each pass does three things: FLD to keep badlines away, a clear of `$D017`, and a write of the table entry.

```asm
; Sprite stretcher (ACME syntax) for a PAL C64.
; SYS 49152 to start; RUN/STOP and RESTORE to stop.
        * = $c000
        sei             ; no interrupts: this loop owns the machine
        ldx #62         ; copy the sprite to $0340
copy    lda sprite,x
        sta $0340,x
        dex
        bpl copy
        lda #$0d        ; sprite 0 data at $0340 (13 * 64)
        sta $07f8
        lda #160        ; x position
        sta $d000
        lda #$40        ; y position: DMA starts on line $40
        sta $d001
        lda #1          ; white
        sta $d027
        sta $d015       ; sprite 0 on
frame   bit $d011       ; wait for raster line 256 or later
        bpl frame
        lda #0          ; no stretching outside the loop
        sta $d017
        lda #$1b        ; normal $D011: screen on, 25 rows, YSCROLL 3
        sta $d011
        jsr build       ; fill the table for this frame
top     bit $d011       ; wait for the start of the next frame
        bmi top
        lda #$3f        ; wait for raster line $3f
wait    cmp $d012
        bne wait
        ldx #0
line    lda $d012       ; wait for the next raster line
same    cmp $d012
        beq same
        clc             ; FLD: keep YSCROLL ahead of the raster,
        lda $d011       ; so no badline stops the processor
        adc #1          ; while the loop runs
        and #7
        ora #$18
        sta $d011
        lda #0          ; clear the Y-expand bit: this sets
        sta $d017       ; the expansion flip-flop
        lda table,x     ; 1: set it again, so the flip-flop resets
        sta $d017       ; at the end of the line and the VIC-II
        inx             ; draws the same sprite row once more
        cpx length      ; 0: leave it clear and move on a row
        bne line
        lda #0
        sta $d017
        jmp frame

build   lda count       ; pick this frame's stretch, 1 to 6 lines
        inc count       ; per sprite row, changing every 8 frames
        lsr
        lsr
        lsr
        and #15
        tay
        lda sizes,y
        sta size
        ldx #0          ; X = position in the table
        lda #21         ; 21 sprite rows
        sta rows
row     ldy size        ; each row gets size-1 repeats...
        dey
        beq last
rep     lda #1
        sta table,x
        inx
        dey
        bne rep
last    lda #0          ; ...and one line that moves on
        sta table,x
        inx
        dec rows
        bne row
        stx length
        rts

sizes   !byte 1,1,2,3,4,5,6,6,6,5,4,3,2,1,1,1
count   !byte 0
size    !byte 0
rows    !byte 0
length  !byte 0
sprite  !for r, 0, 20 {         ; stripes: solid rows and
          !if r & 1 {           ; hollow rows alternate
            !byte $c0,$00,$03
          } else {
            !byte $ff,$ff,$ff
          }
        }
table   = $c200         ; up to 126 entries
```

Run on a PAL C64 in the VICE emulator, it shows a striped white sprite that grows from its normal 21 lines to 42, 63, 84, 105 and 126 and shrinks back, with every stripe the same height at each step. The BASIC start-up text below the sprite moves down and up with it: the loop's FLD holds back the next character row for as long as the loop runs. The polling loop leaves a few cycles of jitter, which does not matter here, because both writes to `$D017` land well inside the window between cycles 16 and 54.

## The cost

Stretching is cheap per line and expensive per frame. The loop must run on every line the sprite covers, and a program that wants a different shape each frame also has to rebuild its table. Ojala measured his own work. Calculating the stretch data for eight individually stretched sprites took "slightly less than 80 lines, which is one fourth of the total raster time", with the fastest routine he had, taken from the *Fore!* part of *Megademo92*. Displaying a 128-line stretcher took about 130 more lines. That left "100 lines (6300 cycles) free for other activities in a PAL system. In a NTSC system you would have only 50 lines left." He had tried to make an NTSC version of his demonstration program, "but I couldn't get it to synchronize."

## Who did it first

The Codebase64 wiki's list of demo firsts, a collaborative record begun from a list posted to the CSDb forum, gives the first sprite stretching to Bob of [Triad](/vault/groups/triad), in the demo *Cocktail*, released on 26 February 1989. CSDb lists *Cocktail* as a demo shown at the Rawhead, Bros, Suppliers party, where it came sixth, with code credited to Bob and four others. The list's compilers warn that "some of these issues are subject to dispute", and no second source found for this entry confirms the first.

The trick reached type-in readers within two years. In its March/April 1991 issue the American magazine *RUN* printed Richard Penn's "Sprite Stretch 64" in its Magic column, calling it "one of the ultimate sprite demos of all time". It did the job from BASIC: a single line `POKE`s 255 and then 0 into register 53271, which is `$D017`, over and over until a key is pressed. BASIC is far too slow to keep in step with the raster, so the sprites stretch by different amounts from moment to moment, and the magazine warned that the program was "sensitive to timing, especially on older versions of the C-64." Ojala's *C=Hacking* article, dated May 1991 and translated for the magazine's March 1993 issue, explained the timed version with a table. Bauer's 1996 document gave the full cycle-level account, and credited Ojala among the programmers whose tests it was based on.
