A home computer's text screen is a grid of character codes. On a Commodore 64 the screen holds 1,000 of them, 40 across and 25 down, and the video chip looks up the 8×8 pattern of dots for each code in a character set as it draws the picture. Change the patterns and every letter on the screen changes with them. Programmers found that by replacing the alphabet with pieces of wall, ladder and water, they could build a game's world out of "text" and move it around as cheaply as text.

That is the whole technique. A level is not stored as a picture but as a list of character codes, and the character set decides what each code looks like.

## Why it paid

**Memory.** A full-screen bitmap on the C64 needs 8,000 bytes for its 320×200 dots, Commodore's *Programmer's Reference Guide* explains, and the colours for each 8×8 square then come from the 1,000 bytes of screen memory. A character screen needs those 1,000 bytes and a character set of 2,048 bytes, "256 characters in which each character is defined by 8 bytes", and the set can be shared by every screen in the game. In character mode each cell's colour comes from colour memory at `$D800`, a separate chip that takes nothing from the 64K.

**Speed.** To scroll a C64 screen by a whole character, a program moves 1,000 bytes of codes, and colours if they change, instead of 8,000 bytes of bitmap. To print an enemy in a new place it writes a few codes, not dozens of bytes of pixels.

**Design.** A level designed in characters is small enough to build by rule. Peter Liepa told *Retro Gamer* that he wrote no cave editor for *[Boulder Dash](/vault/games/boulder-dash)*, only "a simple cavern definition language that allowed me to draw points, lines and rectangles consisting of characters, along with specifying random densities". His original caves were 40 by 24 character blocks, before a publisher's complaint that the hero was too small to recognise led him to make everything bigger.

## On the Commodore 64

The [VIC-II](/vault/hardware/vic-ii) reads its character patterns from wherever register `$D018` points. Bits 1 to 3 choose one of eight 2K blocks in the 16K of memory the chip can see; bits 4 to 7 choose where screen memory is, in 1K steps. Pointing the character bits at RAM is a single write:

```asm
        lda #$1c        ; screen at $0400 (bits 4-7 = 1), characters at $3000 (bits 1-3 = 6)
        sta $d018
```

This is the write the figure above makes. The value is `$1C`, not the character bits alone, because both pointers share the register: bits 1–3 are `%110`, giving 6 × 2,048 = `$3000`, and bits 4–7 are `%0001`, giving 1 × 1,024 = `$0400`. Commodore's guide warns that `$D018` is "the same register that determines where screen memory is located so avoid disturbing the screen memory bits", and gives the BASIC form `POKE 53272,(PEEK(53272)AND240)OR A`.

Each character is eight bytes, one per row, with a set bit for each dot drawn in the character's colour. With the set at `$3000`, character 0 is `$3000`–`$3007`:

```asm
; Make character 0 a solid block.
        lda #$ff
        ldx #7
fill    sta $3000,x
        dex
        bpl fill
```

The guide also sets out the catch. Switching to RAM is "an all or nothing process": once the pointer leaves ROM, "you must copy any letters, numbers, or standard Commodore 64 graphics you intend to use into your own character memory in RAM. You can pick and choose, take only the ones you want, and don't even have to keep them in order!" Games did exactly that, copying in the digits and a few letters for the score and giving the rest of the 256 codes to scenery.

### Multicolour characters

Setting bit 4 of `$D016` turns on multicolour character mode. Each character then decides for itself: if bit 3 of its colour-memory value is set, it is drawn in multicolour. Its dots are read in pairs, twice as wide, giving 160 across the screen instead of 320. Each pair picks one of four colours: the screen background (`$D021`), two more shared background colours (`$D022` and `$D023`), or the character's own colour from colour memory, which in this mode is limited to the first eight colours, since its fourth bit is now the multicolour flag.

## On other machines

| Machine | How the screen is made | How to redefine characters |
|---|---|---|
| Commodore 64 | Character mode: the video chip reads codes and patterns as it draws | Point bits 1–3 of `$D018` at a 2K set in RAM |
| Commodore VIC-20 | Character mode, one colour per character from colour memory | Point register 36869 (`$9005`) at RAM; the set must be in the internal RAM, as the video chip cannot see expansion memory |
| Sinclair ZX Spectrum | Always a bitmap; the ROM's print routine draws each character's dots into it | 21 user-defined graphics (codes 144–164), or point the `CHARS` system variable at a whole new set |
| BBC Micro | Modes 0–6 are bitmaps that the operating system prints into; mode 7 is teletext | `VDU 23` defines a character in modes 0–6; mode 7's character set is stored in the teletext chip |

**The VIC-20** works like the C64. Its *Programmer's Reference Guide* explains that the standard characters are in ROM, "no way to change them", but that "the memory location that tells the VIC where to find the characters is a RAM location in the VIC chip". Programmed characters "cannot be put into expansion RAM, since the VIC chip doesn't have access to that memory", so they have to sit between 4096 and 7168, where BASIC must be told to leave them alone.

**The Spectrum** has no character mode. Its manual describes the display file as a picture in which "each character position on the screen has an 8x8 square of dots", stored as eight bytes spread through the screen; printing a character copies its eight bytes into those places. Redefining characters still works, because the print routine takes its patterns from wherever the system variable `CHARS` (23606) points: "256 less than address of character set", normally in ROM, "but you can set up your own in RAM and make CHARS point to it". The set covers codes 32 to 127. For smaller jobs the 48K machine offers 21 [user-defined graphics](/vault/techniques/udg) at codes 144 to 164; in 128 BASIC, the last two of those codes became the keywords `SPECTRUM` and `PLAY`. Because the picture is a bitmap, a Spectrum game can draw 8×8 blocks of its own wherever it likes, keeping a map of block codes in memory much as a C64 game keeps its screen.

**The BBC Micro** also prints characters into a bitmap in modes 0 to 6. Acorn's operating system lets a program define 32 characters with `VDU 23` by default, codes 128 to 159, and the command `*FX 20` "explodes" the allocation so that every code from 32 to 255 can be redefined, using up to 1,536 more bytes of memory. Mode 7 is different: it is a teletext display, and its character set is stored in the SAA 5050 teletext chip, not in memory.

## Animating characters

Two kinds of change bring a character screen to life:

- **Change the pattern.** Rewriting the eight bytes of one character changes every copy of it on the screen at once, which is how a whole sea of water tiles can ripple for the cost of a few bytes.
- **Change the code.** Writing a different code into screen memory replaces the block in one place, which is how an object moves across a character screen a whole character at a time.

## Limits

Characters snap to an 8×8 grid, so objects that need to move smoothly are usually drawn with [sprites](/vault/techniques/sprites) on top. A set holds 256 patterns, so a large level reuses the same blocks; a C64 program can switch to a second set partway down the screen with a [raster interrupt](/vault/techniques/raster-interrupts). And each 8×8 cell has a limited number of colours: on the C64 one colour of its own plus the shared backgrounds, and on the Spectrum the two-colour attribute cell that causes [colour clash](/vault/techniques/colour-clash).
