In July 1985 *Your Spectrum* printed Mike Leaman's machine-code 3D sprite system, and a month later he admitted the sprites were "a little flickery". His fix was a short extra routine he called the "3D Turbo Charger". From then on, "all the printing is done in this new area of memory, and that means that the entire 6K of memory is copied to the real screen, updating the whole screen at once." It was, he wrote, "a trick that you'll find on many commercial pieces of software though it has the disadvantage of taking up another 6K of memory", and it made the sprites "completely flicker-free".

That trick is double buffering. The video chip reads screen memory continuously, line by line, while the program is changing it. If the program erases a sprite and redraws it one place along while the beam is passing over that spot, the player sees the gap: a flicker, or a sprite cut in two where the beam overtook the drawing. Double buffering keeps two pictures. The display shows one, the **front buffer**, while the program draws the next frame into the other, the **back buffer**. When the frame is finished, the program swaps them.

## The swap

There are two ways to make the finished picture visible.

- **Flip.** If the video chip can be told where to read the screen from, the program points it at the back buffer. The swap is one or two register writes, however big the screen. The C64, the Amiga and the Spectrum 128 work this way.
- **Copy.** If the screen is at a fixed address, as on the 48K Spectrum, the program copies the back buffer into it. Leaman's routine ends with exactly that: its machine code loads BC with 6,144 and runs `LDIR`.

Either way, two rules keep the swap clean. Make the change while the display is not reading the area concerned, usually during vertical blank or in the border below the picture. And after a flip, wait until the hardware has actually started showing the new buffer before drawing into the old one; until then, the old one is still on screen.

## Commodore 64

### Text screens: $D018

The [VIC-II](/vault/hardware/vic-ii)'s register `$D018` (53272) holds two pointers, each an offset inside the chip's current 16K bank:

- Bits 7–4: screen memory, in 1K steps (value × `$0400`).
- Bits 3–1: character set, in 2K steps.
- Bit 0: unused.

At power-up it reads `$15`: screen at `$0400`, character set at `$1000`, which in bank 0 is where the VIC-II sees the character ROM. A second screen at `$0800` needs bits 7–4 set to 2 with the character bits left alone, so the two values to flip between are `$14` and `$24`:

```asm
; Two screen buffers in VIC bank 0 ($0000-$3FFF)
; Screen 1 at $0400, screen 2 at $0800, character ROM image at $1000

screen1 = $0400
screen2 = $0800

; $D018 values: screen in bits 7-4, character base 2 in bits 3-1
D018_SHOW_SCREEN1 = (1 << 4) | (2 << 1)    ; = $14
D018_SHOW_SCREEN2 = (2 << 4) | (2 << 1)    ; = $24

current_screen: .byte 0
draw_ptr_lo:    .byte <screen2   ; start drawing into screen2 while screen1 displays
draw_ptr_hi:    .byte >screen2

; Call below the display window, once the next frame is ready
swap_screens:
    lda current_screen
    eor #1
    sta current_screen
    bne .show_screen2

.show_screen1:
    lda #D018_SHOW_SCREEN1
    sta $d018
    lda #<screen2
    sta draw_ptr_lo
    lda #>screen2
    sta draw_ptr_hi
    rts

.show_screen2:
    lda #D018_SHOW_SCREEN2
    sta $d018
    lda #<screen1
    sta draw_ptr_lo
    lda #>screen1
    sta draw_ptr_hi
    rts
```

Always write the whole register, with the character bits included. Storing only a screen value such as `$10` sets the character base to 0, and the VIC-II then takes its character shapes from `$0000`–`$07FF` of the bank. In bank 0 that is zero page, the stack and the screen itself, so the text turns to rubbish.

The screen's 1K block also holds the sprite pointers in its last eight bytes, so a program that flips screens has to keep the sprite pointers the same in both.

### Bitmaps and banks: $DD00

A bitmap is 8,000 bytes, and bit 3 of `$D018` can only put it at the start or the middle of the 16K bank. In banks 0 and 2 the VIC-II sees the character ROM image at `$1000`–`$1FFF` of the bank, which overlaps the lower position, so each of those banks has room for only one usable bitmap, at `$2000`. To flip between two bitmaps, a program can keep one in each of two banks, each with its own 1K of screen memory for the colours, and switch banks with bits 0 and 1 of CIA 2's port A at `$DD00` (56576). The bits count backwards: 3 selects `$0000`, 2 `$4000`, 1 `$8000` and 0 `$C000`. The *Programmer's Reference Guide* reminds the reader that the character ROM is not visible to the VIC-II at all in banks 1 and 3.

### What the flip leaves behind

Colour memory at `$D800` is a separate chip that neither register moves, so, in Lasse Öörni's words, it "can't be doublebuffered" and has to be updated while the rows concerned are not being displayed. The [Scrolling](/vault/techniques/scrolling) entry describes how C64 games scheduled that around the flip.

The flip also simplifies a scrolling copy. With one screen, Öörni writes, "one must be careful in what direction the shifting loops should go, to not wipe out the entire screen data"; with two, the data "is always being copied from the currently visible screen to the other, hidden screen", and by using X for the source index and Y for the target "all 8 directions can be achieved by simply adjusting the initial index register values". The price is two copy loops, one for each direction between the screens. Malcolm Bamber's 4-way scroller on Codebase64 keeps its pair at 1024 and 3072, with a zero-page flag recording which one is showing.

### When to flip

With 25 text rows, the VIC-II's display window runs from raster line 51 to line 250. Once the raster is past line 250, the chip has finished reading the screen for this frame, and a `$D018` or `$DD00` write takes effect cleanly from the top of the next. A raster interrupt set for line 251 or later, in `$D012` with the ninth bit in bit 7 of `$D011`, is the usual place (see [Raster Interrupts](/vault/techniques/raster-interrupts)). Polling works too:

```asm
; Wait until the raster is below the display window (line 251 or later)
wait_bottom:
    lda $d011
    bmi .done             ; bit 7 set: raster is 256 or more
    lda $d012
    cmp #251
    bcc wait_bottom       ; lines 0-250: keep waiting
.done:
```

A PAL C64 has 312 raster lines and an NTSC one 263, so the time between line 251 and the top of the next display window is much longer on PAL.

## ZX Spectrum

### 48K: copy

The 48K Spectrum's [ULA](/vault/hardware/ula) always reads its picture from `$4000`: 6,144 bytes of bitmap and 768 of attributes. A back buffer anywhere else has to be copied in. With `LDIR` at 21 T-states a byte, the bitmap alone takes about 129,000 T-states and the whole 6,912 bytes about 145,000, roughly two frames of 69,888 T-states each, before the ULA's contention slows writes to the screen.

That is far longer than the gap before the picture starts. Each line takes 224 T-states, and the 192 display lines are preceded by 56 lines of top border and 8 of vertical flyback, so the interrupt that starts each frame comes 64 × 224 = 14,336 T-states before the ULA reads its first screen byte. A copy that starts at the interrupt and works down the screen outruns the beam at first, but the beam draws a line every 224 T-states and `LDIR` moves only about ten bytes in that time, so the beam soon overtakes it. Games therefore copied less than the whole screen:

```z80
; Copy the whole shadow screen to the display: about 145,000 T-states
copy_full_screen:
    ld   hl, shadow_screen
    ld   de, $4000
    ld   bc, 6912            ; bitmap and attributes
    ldir
    ret

; Copy only the bitmap: 6,144 bytes, about 129,000 T-states
copy_bitmap_only:
    ld   hl, shadow_bitmap
    ld   de, $4000
    ld   bc, 6144
    ldir
    ret
```

- **Copy the play area only.** A window of 24 × 16 characters is 3,072 bytes, half the bitmap.
- **Copy only what changed.** [Dirty Rectangles](/vault/techniques/dirty-rectangles) keeps a list of the areas each frame touched.
- **Copy faster.** Unrolled `LDI` costs 16 T-states a byte, and stack-based copies with `POP` and `PUSH` about 10.5; [Software Scrolling](/vault/techniques/software-scroll) explains the stack method.

### 128K: flip

The Spectrum 128 and +2 have a second screen. Amstrad's +2 manual gives the paging port at `$7FFD` (32765): bits 0–2 choose which 16K RAM page appears at `$C000`, bit 3 selects the screen, bit 4 the ROM, and bit 5 locks the machine into 48K mode. "D3 switches screens; screen 0 is held in RAM 5 (beginning at 4000h) and is the one that BASIC uses, screen 1 is held in RAM 7 (beginning at C000h) and can only be used by machine code programs."

So a 128K program can draw into RAM 7 while RAM 5 is shown, then flip with one `OUT`. The ROM keeps a copy of the last value written to the port in the system variable BANKM at 23388, so a program that works from that copy, and keeps it up to date, never has to guess which ROM and RAM pages are in:

```z80
; Show screen 1 (RAM 7), keep RAM 7 paged in at $C000 for drawing
show_screen_1:
    ld   a, (23388)          ; BANKM: last value written to $7FFD
    and  %11110000           ; keep ROM select and the lock bit
    or   %00001111           ; screen 1 (bit 3), RAM 7 at $C000
    ld   (23388), a
    ld   bc, $7FFD
    out  (c), a
    ret
```

Screen 1 is only reachable at `$C000`, which the +2 manual allows for: RAM 5 normally sits at `$4000`, but "there's no reason why" it could not be paged in at `$C000` as well. A program that pages in whichever of RAM 5 and RAM 7 is hidden can then always draw at `$C000`, whichever screen is the back buffer. Two costs remain. The manual notes that the 128 BASIC editor uses RAM 7 "for various buffers and 'scratchpads'", so a program that uses screen 1 has to leave the editor alone. And both screens are in contended RAM, so drawing into either is subject to the same delays as drawing into the 48K screen.

## NES

The NES has no framebuffer to flip. Its [PPU](/vault/hardware/ppu) builds each frame from tile patterns, nametables and a sprite list, and the program can safely update the PPU's memory only during vertical blank or with rendering turned off. Two parts of that still work like double buffering.

- **Sprites.** Games build the 256-byte sprite list in CPU RAM during the frame, conventionally at `$0200`–`$02FF`, then copy it to the PPU in one go during vertical blank by writing the page number to `$4014`. The DMA copy takes 513 or 514 CPU cycles and stops the CPU while it runs.
- **Nametables.** The console has 2K of nametable RAM, enough for two screens. Bits 0–1 of PPUCTRL (`$2000`) choose which nametable the picture starts from, so a program can fill the hidden one a little at a time over several vertical blanks and then switch to it with one write. Scrolling games use the same pair to write new rows or columns just out of view.

```asm
; Sprite list built in CPU RAM at $0200-$02FF during the frame;
; copy it to the PPU in the vertical blank (NMI) handler
nmi:
    lda #$00
    sta $2003                 ; OAMADDR = 0
    lda #$02
    sta $4014                 ; OAM DMA from page $02: 513-514 cycles
    ; ... nametable updates, then scroll and PPUCTRL ...
    rti
```

## Amiga

The Amiga's display is a set of bitplanes, and each plane has a pointer register pair, BPLxPTH and BPLxPTL, "12 registers in all" for six planes, at custom-chip offsets `$0E0` to `$0F6` (addresses `$DFF0E0`–`$DFF0F7`). Plane 1's pointer is at `$0E0` (high word) and `$0E2` (low word), plane 2's at `$0E4` and `$0E6`, and so on. The pointers count up as the display is fetched, so the *Amiga Hardware Reference Manual* says each one "must be reinitialized by the processor or copper to point to the beginning of bit plane data every vertical blank time", adding that this "is usually the Copper's task".

That makes the flip almost free. The [Copper](/vault/hardware/copper) list already reloads the pointers at the top of every frame, so the program only has to change the values in the list. The manual also recommends the method for [Blitter](/vault/hardware/blitter) animation, which it says "works best with beam-synchronized blits or double buffering".

```asm
; Two screen buffers, each screen_size bytes, in chip RAM
buffer1:        ds.b    screen_size
buffer2:        ds.b    screen_size

display_ptr:    dc.l    buffer1     ; currently displayed
draw_ptr:       dc.l    buffer2     ; currently being drawn

; Copper list fragment (bitplane 1):
; coplist:
;   dc.w  $00E0,0        ; MOVE to BPL1PTH; the data word is at coplist+2
;   dc.w  $00E2,0        ; MOVE to BPL1PTL; the data word is at coplist+6

swap_buffers:
    move.l  display_ptr,d0
    move.l  draw_ptr,display_ptr
    move.l  d0,draw_ptr

    ; Patch the Copper list with the new display pointer
    move.l  display_ptr,d0
    move.w  d0,coplist+6        ; low word into the BPL1PTL move
    swap    d0
    move.w  d0,coplist+2        ; high word into the BPL1PTH move
    rts
```

A Copper MOVE is two words, the register offset and then the value, so the values sit at offsets 2 and 6. Getting the high and low words the wrong way round is an easy mistake. For five bitplanes, patch five pairs, each plane's start being the buffer address plus the size of the planes before it. The new pointers take effect when the Copper next runs the list at the top of the following frame, so the program should wait for that vertical blank before drawing into the buffer it has just hidden.

## Memory cost

| Display | One screen | Two screens | Notes |
|---|---|---|---|
| C64 text (40×25) | 1,000 bytes + colour memory | 2,000 bytes + colour memory | Colour memory is a separate 1,000-nybble chip and cannot be doubled |
| C64 bitmap (320×200) | 8,000 + 1,000 bytes | 18,000 bytes | Bitmap and its screen memory both need a copy; two banks |
| ZX Spectrum | 6,912 bytes | 13,824 bytes | 48K: the copy comes out of the user's RAM. 128K: the second screen is RAM 7 |
| NES nametables | 1K | 2K | The console's built-in nametable RAM holds exactly two |
| Amiga lo-res, 5 planes, 320×256 | 51,200 bytes | 102,400 bytes | A fifth of the 512K of chip RAM the original chipset can address |

## Triple buffering

With two buffers, a program that finishes a frame early has to wait for the vertical blank before it can start the next one, because both buffers are busy until the swap. A third buffer removes the wait: one is displayed, one holds a finished frame waiting to be shown, and the program draws into the third. The cost is a third screen's worth of memory.

## Flip, copy or dirty rectangles

| Method | Time per frame | Memory | Use when |
|---|---|---|---|
| Flip | One or two register writes | Two screens | The video chip's screen address can be changed |
| Full copy | The whole screen, every frame | Screen plus back buffer | The screen address is fixed (48K Spectrum) |
| Dirty rectangles | Only the changed areas | Back buffer plus a list | Most of the screen stays still between frames |
