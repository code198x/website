Scrolling a Commodore 64 screen sideways by a character normally means moving it: 1,000 bytes of character codes and 1,000 colour values, shifted one place along, before the beam comes round again. **VSP** gets the same result by moving nothing. A write to the VIC-II's control register `$D011`, placed on exactly the right cycle of one raster line, makes the chip start fetching the screen late, and from then on it reads every row of the display a few characters out of step. The picture moves sideways as a whole, colours and all, and the processor time a copy would have cost is left over for the game.

The price is precision and, on some machines, safety. The write has to land on an exact cycle, and on a minority of C64s the trick corrupts memory and crashes the machine.

## Several names

The effect has more than one name. The Codebase64 wiki files it as "Horizontal Screen Positioning (HSP)" and "DMA-Delay", and notes that its list of demo firsts calls it VSP, "Variable Screen Positioning". Christian Bauer's 1996 technical description of the VIC-II gave it the name **DMA delay**, which describes the mechanism: the chip's direct memory access for the screen starts later than usual. **VSP** and **HSP** describe the result.

## How it works

The VIC-II fetches the 40 character codes of each text row, with their colours, on the first raster line of the row, a **badline**. It keeps its place with an internal counter, VC, which advances by one for each character fetched and so moves on by 40 for each row. A badline happens when the bottom three bits of the raster line number equal YSCROLL, the vertical scroll value in bits 0 to 2 of `$D011` (see [VIC-II](/vault/hardware/vic-ii#where-the-cycles-go-badlines)).

Bauer's description sets out what happens if a program creates that condition in the middle of a line instead, "within cycles 15-53 of a raster line in the display window in which the graphics data sequencer is in idle state", by writing `$D011` so that YSCROLL matches the line:

1. The VIC-II claims the bus from the next cycle and starts reading character codes, partway along the line.
2. It carries on until its usual stopping point, cycle 54, so it makes fewer than 40 fetches. VC has advanced by less than 40.
3. Every later row starts from that misaligned count. In Bauer's words, "the whole screen seems to be scrolled to the right by as much characters as the number of cycles the $d011 access was done after cycle 14."

One cycle of delay moves the screen one character, eight pixels. Because the bitmap modes use the same counter, the trick moves bitmap pictures as well as text. The fine scroll bits of `$D016` still move the screen by 0 to 7 pixels, so a program can combine the two to position the display to the pixel. Bauer also describes a second route to the same effect, turning the display-enable bit of `$D011` on in the middle of raster line `$30` with YSCROLL set to 0.

The start of the delayed fetch reads rubbish. For the first three cycles the processor still has the bus, so the VIC-II reads `$FF` as the character codes and takes its colours from the low four bits of whatever instruction the processor fetches next. Only then does it read the real screen.

### What a program has to do

The write must land on the chosen cycle every frame, so VSP sits on top of a [stable raster](/vault/techniques/stable-raster) routine that removes the few cycles of jitter in a raster interrupt. The routine then waits a variable number of cycles, one for each character of shift, before touching `$D011`. Martin Piper's example on the Codebase64 wiki does this by jumping into a row of `NOP` instructions at a point worked out from the scroll position, then makes the write:

```asm
        lda #$1b
        dec $d011       ; YSCROLL 1 -> 0 on raster line $30: a badline starts here
        inc $d011       ; YSCROLL back to 1
        sta $d011       ; restore the normal value, $1B
```

On the line before, his routine has set `$D011` to `$11`, so that YSCROLL is 1. Decrementing the register makes YSCROLL 0, which matches raster line `$30` (48), and the badline begins on that cycle. The two instructions after it put the register back before the next row.

The timing depends on the length of the raster line, so the same code does not work on every machine. Piper's code is for PAL machines, and he notes that for NTSC "you have to do some minor timing modifications for each scan-line". *C=Hacking*'s 1998 guide to converting PAL programs for NTSC listed VSP with FLI and colour bars as the effects that break, adding that "VSP effects will often be shifted the wrong amount".

Run on a PAL C64 in the VICE emulator, Piper's program slides the ordinary BASIC start-up screen sideways by whole characters, to a new position each frame as its counter runs from 0 to 39. Text pushed off the right-hand end of a row reappears at the start of the row below, because the chip is reading the same screen memory from a different starting point, and the bottom row fills with stray characters.

## First use

The first recorded use is a one-file demo called *VSP&IK+*, released by The Mean Team on 30 October 1987 with code by JCB and Rob Hubbard's music from *[International Karate+](/vault/games/international-karate-plus)*. JCB later described finding the effect by accident: "It was a bugged FLD routine that started to make the screen move around and when I realised that might actually be controllable I started trying to stabalise it then found out that 1 cycle would move the screen 1 character." ([FLD](/vault/techniques/fld) is a related trick that holds badlines back to push the screen down.) The same list of firsts credits Exilon of MDT and Horizon with combining VSP and [linecrunch](/vault/techniques/linecrunch) in the demo *Bonanza* in November 1988; its compilers warn that "some of these issues are subject to dispute".

Bauer saw where the combination led: "If you now combine DMA Delay with FLD and Linecrunch, you can scroll complete graphics screens without using much computing time by almost arbitrarily large distances in all directions." That combination became known as [AGSP](/vault/techniques/agsp). In 1995 Pasi Ojala used linecrunch and DMA delay to scroll a BFLI picture, a taller variant of [FLI](/vault/techniques/fli), in a viewer published in *C=Hacking*.

## In games

VSP reached commercial games late in the C64's life. The developer Jon, who writes as Kodiak64, lists *Creatures* and *Mayhem in Monsterland* by John and Steve Rowlands among the games that used it for "full-screen, full-colour scrolling". The period press recorded the speed without naming the method. In his development diary in *Commodore Format* in December 1992, John Rowlands described going through "the Creatures source code, extracting the routines needed for the Mayhem scroller". When the game was nearly finished, *Commodore Force* listed "super-fast, fullscreen, bi-directional scrolling — 8 times faster than the Creatures scroll" among its specifications.

## The VSP crash

On some C64s, VSP crashes the machine. Kodiak64 describes it as affecting "a tiny minority of machines", and on anecdotal evidence most often the later C64C. In 2013 the programmer Linus Åkesson traced the cause, starting from a crash that another scener, Zer0-X, had captured with a logic analyser.

The fault is in the DRAM, not in the program. On the cycle where VSP starts the fetch, the VIC-II "sets the internal bus lines to 11111111 in preparation for an idle fetch, but suddenly changes its mind and tries to read from an address with an LSB of 00000111." If the RAM's row address strobe falls while those lines are changing, the RAM chips can latch an address that is neither one value nor the other. Åkesson found that the damage follows a rule. He called memory locations whose addresses end in 7 or F "fragile": when the crash happens, "each bit in a fragile memory cell might be changed into the corresponding bit of another fragile cell within the same page." Whether a given machine suffers depends on nanosecond timing, which varies with "temperature, VIC revision, parasitic capacitance and resistance of the traces on the motherboard, power supply ripple" and more, so "on many machines the critical situation simply doesn't occur."

Knowing the rule made a safe VSP possible. Åkesson proposed keeping the bytes at fragile addresses identical within each page, or keeping code and data out of them, and demonstrated the method in a demo, *Safe VSP*, at the Datastorm party in 2013. The hardware maker Individual Computers built a fix into its C64 Reloaded motherboard: a latch that holds the address lines steady around the moment the row address strobe falls, crediting Åkesson and Tommi Lempinen for the analysis.
