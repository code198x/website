A game that plays its own music has two jobs that both want the processor at once. The tune needs attention at exact, regular moments, or its tempo wobbles. The game needs as much time as it can get, and how much it uses changes from one frame to the next. The answer the 1980s settled on was to let the hardware keep time. An interrupt stops the main program fifty or sixty times a second, a short routine called the music driver updates the sound chip, and the main program carries on from where it stopped without knowing anything happened.

The idea was already being sold in 1980. An advertisement in the December 1980 issue of *MICRO* offered a sound board for the Ohio Scientific C1P that "can be interrupt driven so that you can use it for gaming purposes". *Commodore Force* summed up the attraction for its C64 readers in 1994: "By setting an interrupt, you can get constantly updating sound effects, or a wonderful 3-voice piece of music without slowing down the rest of your program!"

## What the interrupt buys

Without an interrupt the music has to be fitted into the main loop, and the tune runs at whatever speed the game does. Matthew Smith's *[Jet Set Willy](/vault/games/jet-set-willy)* on the Spectrum is the famous example: its music "does not use an interrupt", he told *Sinclair User*, it is "just move-a-tiny-little-bit, BEEP-a-tiny-little-bit" (see [Beeper Music](/vault/techniques/beeper-music)).

With an interrupt the shape changes:

```
at start-up:
    initialise the tune
    point the interrupt at the music handler

every frame, in the interrupt:
    acknowledge the interrupt
    call the music driver once
    return to whatever was running

main loop, the rest of the time:
    read the controls, move everything, draw
```

The driver is called at a fixed rate and does a small amount of work each time. It counts down the length of the current note, starts new notes when their time comes, and between notes changes pitches, volumes and waveforms a little on every call to make vibrato, slides, arpeggios and drum sounds. Martin Walker, keeping a development diary for *ZZAP!64* in 1988, described building chords on one voice "by swapping between several notes every 50th of a second".

The rate of the interrupt sets the resolution of everything the driver does. A driver called fifty times a second cannot place an event closer than 20 milliseconds to another, and it shapes its sounds around that. C64 composers' "hard restart", which stops a note shortly before the next so that the [SID](/vault/hardware/sid-chip)'s envelope starts cleanly, is timed in frames for exactly this reason: "Sound-routines are often called once per frame," a Codebase64 article on the technique explains, and the restart begins "2 full frames before next note" (see [Hard Restart](/vault/techniques/hard-restart)).

The cost is that every call comes out of the game's time, including the frames when the game is busiest. On a PAL C64 a frame is 19,656 processor cycles (see [The Game Loop](/vault/techniques/game-loop)), and a driver that takes a thousand of them has used about a twentieth of the machine. Programmers could watch the cost directly by changing the border colour just before the call and back afterwards, which draws a coloured band as tall as the driver's running time; Anthony McSweeney's 1993 listing of Rob Hubbard's routine does exactly that.

## Commodore 64

The C64 offers two sources of a regular interrupt, both counting the same processor clock of 985,248 Hz on a PAL machine and 1,022,727 Hz on an NTSC one. The [VIC-II](/vault/hardware/vic-ii) can interrupt once a frame at a chosen raster line, which ties the music to the picture: fifty calls a second on PAL, sixty on NTSC. CIA 1's Timer A can interrupt at any rate the program chooses (see [CIA 6526](/vault/hardware/cia)).

Both arrive on the same IRQ line, and the usual way in is the KERNAL's RAM vector at `$0314`–`$0315`. The KERNAL's own entry code has already saved A, X and Y on the stack before it jumps through that vector, so the handler must leave through one of the KERNAL's exits, not with its own `RTI`:

- `JMP $EA31` runs the KERNAL's regular interrupt work, the clock, cursor and keyboard scan, and then restores the registers and returns. It also reads `$DC0D`, which acknowledges a CIA interrupt.
- `JMP $EA81` only restores A, X and Y and returns.

A handler that ends with `RTI` on this route returns with three bytes still on the stack and crashes the machine. `RTI` is correct only for a handler reached through the processor's own vector at `$FFFE`, with the KERNAL ROM switched out, and that handler must save and restore its own registers. [Raster Interrupts](/vault/techniques/raster-interrupts) covers both routes in detail.

### A raster interrupt, once a frame

This is the pattern most C64 tunes were written for, and the one Codebase64's example player uses. It assumes a tune already loaded at `$1000` with its set-up routine at `$1000` and its play routine at `$1003`. That layout is common among C64 music editors, and Hubbard's routine used the same pattern of entry points, but it is not universal, so check the tune's own addresses. A `.sid` file from the High Voltage SID Collection has a header in front of the C64 data, `$76` bytes long in version 1 files and `$7C` in later ones, followed by the two-byte load address; strip them before loading the data at `$1000`.

```asm
; play a tune once a frame from a raster interrupt (ACME syntax)
; start with SYS 49152; returns to BASIC with the tune playing
music_init = $1000
music_play = $1003

        * = $c000
start   sei                 ; no interrupts while we change things
        lda #$7f
        sta $dc0d           ; switch off CIA 1's timer interrupts
        lda $dc0d           ; and clear any that are waiting
        lda #<irq
        sta $0314           ; point the KERNAL's IRQ vector at our handler
        lda #>irq
        sta $0315
        lda #251
        sta $d012           ; interrupt on line 251, below the display window
        lda $d011
        and #$7f
        sta $d011           ; bit 8 of the line number clear
        lda #$01
        sta $d01a           ; enable the raster interrupt
        sta $d019           ; clear any raster interrupt already flagged
        lda #0              ; tune number 0
        jsr music_init
        cli
        rts

irq     lda #$01
        sta $d019           ; acknowledge the raster interrupt
        jsr music_play      ; one frame of music
        jmp $ea31           ; KERNAL clock and keyboard, then restore and return
```

Line 251 exists on both PAL and NTSC machines. Because CIA 1's interrupt is off, the KERNAL's own routine now runs only when the handler jumps to `$EA31`, once a frame, so the keyboard still works. The play routine may use A, X and Y freely: the KERNAL saved them before the handler began, and `$EA31` restores them.

The same program on an NTSC C64 calls the driver sixty times a second, and a tune written for PAL plays a fifth too fast. McSweeney warned about exactly this with Hubbard's routine: "The music is supposed to run at 50Hz", and on NTSC machines it "will sound much to fast".

### A CIA timer, at any rate

A timer interrupt runs at a rate the program sets, independent of the video standard. That fixes the NTSC problem, and it lets a tune call its driver more than once a frame; such "multi-speed" tunes are common enough that the SID file format records, for each tune, whether it expects a vertical blank interrupt or a CIA timer.

The KERNAL already runs CIA 1's Timer A, at a count of `$4025` on a PAL machine and `$4295` on NTSC, which gives about sixty interrupts a second on both. A player can simply change the count and point the vector at its handler:

```asm
; play a tune fifty times a second from CIA 1 Timer A (ACME syntax)
; start with SYS 49152; returns to BASIC with the tune playing
music_init = $1000
music_play = $1003
count      = 19705          ; 985,248 / 50 on PAL; use 20455 on NTSC

        * = $c000
start   sei
        lda #<irq
        sta $0314
        lda #>irq
        sta $0315
        lda #<count
        sta $dc04           ; Timer A latch, low byte
        lda #>count
        sta $dc05           ; Timer A latch, high byte
        lda #$81
        sta $dc0d           ; bit 7 set = "set", bit 0 = Timer A interrupt
        lda $dc0e
        and #$80            ; keep bit 7, the time-of-day clock's 50/60 Hz choice
        ora #$11            ; load the latch into the counter and start the timer
        sta $dc0e
        lda #0
        jsr music_init
        cli
        rts

irq     jsr music_play
        jmp $ea31           ; reads $DC0D to acknowledge the timer, scans the keyboard
```

The control register write is the one most often forgotten: without bit 0 set in `$DC0E` the timer never runs. The last three instructions before `sta $dc0e` are the ones the KERNAL itself uses when it starts the timer. Because the KERNAL routine now runs fifty times a second instead of sixty, BASIC's `TI` clock runs slow while the tune is playing.

### Who wrote the drivers

On the C64 the composer usually wrote the driver too, and a good one was a selling point. *The Games Machine* explained in 1987 that games typically left "about 4K of memory for sound", and credited [Rob Hubbard](/vault/people/rob-hubbard)'s success partly to "the library of self-written routines that he has built up". McSweeney, who disassembled the routine from *[Monty on the Run](/vault/games/monty-on-the-run)* for *C= Hacking* in 1993, found that Hubbard "used this routine to make music for a very long time, only changing it _slightly_ over time", from *Confuzion* through *Thing on a Spring*, *Monty on the Run*, *[Commando](/vault/games/commando)*, *International Karate* and many more; the code itself was "a mere 900 or 1000 bytes".

[Martin Galway](/vault/people/martin-galway) worked the other way, with no editor at all: "I had an all assembly language, no fancy editors, hard-work approach to putting in tune data," he told *Retro Gamer*, which let him change the player code for each tune. On the Spectrum 128 and elsewhere, [David Whittaker](/vault/people/david-whittaker) described the driver to *CRASH* in 1987 as "the piece of code that makes the music data run"; his routines took from half a kilobyte for a jingle to 3K including the driver.

## ZX Spectrum

The Spectrum's ULA interrupts the Z80 fifty times a second. In the normal interrupt mode 1 that runs the ROM's routine at `$0038`, which counts frames and scans the keyboard, so a program that wants its own routine on every frame switches to interrupt mode 2.

On the 48K machine interrupt-driven music was possible but thin, because the beeper makes a sound only while the processor is toggling it. Timothy Closs's *Backboogie*, printed in *Your Computer* in July 1985, used the frame interrupt to play "a short musical sound before returning to your game" every fiftieth of a second, relying on the fact that "a series of short sounds ... in quick succession ... give the impression of a continuous musical note". 
The 128K models changed that. Their [AY-3-8912](/vault/hardware/ay-3-8912) sound chip holds a note on its own, so a driver only has to update its registers once a frame. David Jones's routines for 128 programmers in *Your Sinclair* in December 1987 installed an interrupt mode 2 handler that called the music player on every interrupt.

In mode 2 the Z80 forms an address from the I register (high byte) and a byte read from the data bus (low byte), and fetches the handler's address from there. On a Spectrum that byte is not defined: with no peripheral attached it usually reads `$FF`, but programmers who wanted to be safe filled 257 bytes with the same value so that any byte gives the same answer, as the [Game Loop](/vault/techniques/game-loop) entry explains.

```z80
; 128K: call the music player on every frame interrupt
setup:  di
        ld   hl,$FE00
        ld   de,$FE01
        ld   bc,256
        ld   (hl),$FD
        ldir                ; $FE00-$FF00 all hold $FD
        ld   a,$C3          ; JP
        ld   ($FDFD),a
        ld   hl,music_irq
        ld   ($FDFE),hl     ; every vector reads $FDFD: jp music_irq
        ld   a,$FE
        ld   i,a
        im   2
        ei
        ret

music_irq:
        push af
        push bc
        push de
        push hl
        push ix
        call play_frame     ; one frame of music: write the AY registers
        pop  ix
        pop  hl
        pop  de
        pop  bc
        pop  af
        ei
        ret
```

The handler saves every register the player might use, since it can interrupt the game anywhere. A program that goes back to BASIC and still wants the keyboard can end the handler with `JP $0038` in place of `EI` and `RET`: the ROM's routine then counts the frame, scans the keyboard and returns for it, provided IY still holds `$5C3A` as the ROM expects.

The cost of the interrupt shows most clearly on a busy Spectrum game. *Sinclair User* reported in 1989 that the scrolling in Software Creations' Spectrum *[Ghouls 'n' Ghosts](/vault/games/ghouls-n-ghosts)* left so little processor time that music could only have been updated 25 times a second. "Rather than have sub-standard music", the team played three-channel sound effects during the game and kept "high quality 50Hz music" for the menus ([Tim Follin](/vault/people/tim-follin)).

## NES

The NES's [PPU](/vault/hardware/ppu) raises a non-maskable interrupt at the start of every vertical blank once bit 7 of PPUCTRL (`$2000`) is set, and most NES games run their sound engine from that NMI. The [APU](/vault/hardware/apu) has an interrupt of its own, from its frame counter, but it drifts against the picture and most games leave it switched off.

The NMI is also where the game updates the screen, so the sound engine shares the handler with the PPU writes. Nintendo's *[Metroid](/vault/games/metroid)* (1986) shows why the NMI suits music. If the main loop has not finished its frame when the NMI arrives, the handler skips the screen updates but still copies the sprites and runs the sound engine, so the game slows down and the music does not.

```asm
; NMI handler: the processor saves only the program counter and status,
; so the handler saves A, X and Y itself
nmi:    pha
        txa
        pha
        tya
        pha
        ; ... sprite DMA and screen updates for this frame ...
        jsr sound_update    ; one frame of music and sound effects
        pla
        tay
        pla
        tax
        pla
        rti
```

## Amiga

The Amiga's sound chip, [Paula](/vault/hardware/paula), plays samples from memory by DMA without the processor's help. A driver's job is to tell each of its four channels which sample to play, at what period and volume, and then to adjust those values as the song goes on.

Two interrupts drive it. The vertical blank interrupt, bit 5 (VERTB) on level 3, arrives once a frame; the *Amiga Hardware Reference Manual* describes it as occurring "at line 0 (start of vertical blank)". The CIA timers can interrupt at any rate. The early trackers advanced a song once per video frame. *[ProTracker](/vault/tools/protracker)* could instead drive its player from a CIA timer, which let its `F` command set a true tempo in beats per minute; a tempo of 125 reproduces the old 50 Hz rate. Either way the player runs once per tick, by default six ticks to a row of the pattern (see [MOD Format](/vault/techniques/mod-format)).

A game that has taken over the machine installs its own level 3 handler and clears the request itself:

```asm
; level 3 handler with the operating system switched off
        move.l  #level3,$6c.w      ; level 3 interrupt vector
        move.w  #$7fff,$dff09a     ; INTENA: switch every interrupt off
        move.w  #$c020,$dff09a     ; INTENA: SET + INTEN + VERTB
main:   bra.s   main               ; the game runs here

level3: move.w  #$0020,$dff09c     ; INTREQ: clear the VERTB request
        movem.l d0-d7/a0-a6,-(sp)
        jsr     music_play         ; one tick of music
        movem.l (sp)+,d0-d7/a0-a6
        rte
```

Bit 15 of `INTENA` and `INTREQ` decides whether the other bits written as 1 are set or cleared. `$C020` sets the master enable and VERTB; `$4020` would clear them. The request stays set until the handler clears it, and a handler that returns without doing so is called again at once.

Amiga composers also wrote their own systems. [Chris Hülsbeck](/vault/people/chris-huelsbeck)'s TFMX, which *The Games Machine* reported in 1990 he had developed "over years" to get the best sound from the least memory and processor time, gave *X-Out* its music and was sold to other programmers the same year. Whittaker wrote his own Amiga driver, which could play synthesised sounds alongside samples.

## Later

The same arrangement carried on after the period. Modern trackers for the old machines, such as *[SID-Wizard](/vault/tools/sid-wizard)* on the C64 and *[FamiTracker](/vault/tools/famitracker)* for the NES, export the music with a player routine for a game or demo to call from its own code. *SID-Wizard* offers the player in several sizes, so a composer can trade features for processor time.
