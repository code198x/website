*CRASH* graded Spectrum games on their colour. From its first issue in February 1984, each review's comments box carried a "Use of colour" line, and the reviewers learnt to look for one problem in particular. In November 1984 they praised Avalon because its playing area "avoids messy attribute problems". Later in the same issue, Zombie Zombie was "not the ideal game because of attribute problems". When Ultimate's Knight Lore arrived, the review explained why it looked so clean: "only one colour is used per screen which avoids any attribute problems."

The problem was built into the hardware, and the manual that came with every Spectrum explained it: "you cannot possibly have more than two colours in a given block of 64 dots." Attribute-aware design is the set of ways Spectrum programmers and artists found to live with that rule. The [colour clash](/vault/techniques/colour-clash) entry covers the artefact itself.

## The rule

The Spectrum keeps shape and colour in separate places. The 6,144 bytes from address 16384 (`$4000`) hold the pixels: a 1 bit is drawn in the cell's ink colour, a 0 bit in its paper colour. The 768 bytes from 22528 (`$5800`) hold the colours, one byte for each of the 32 × 24 character cells, "stored line by line in the order you'd expect". The manual calls these bytes attributes. Each one packs four settings, and BASIC's `ATTR` function returns it as a sum:

| Bits | Value | Setting |
|---|---|---|
| 7 | 128 | FLASH: swap ink and paper on a timer |
| 6 | 64 | BRIGHT: a brighter version of both colours |
| 5–3 | paper × 8 | PAPER colour, 0–7 |
| 2–0 | ink | INK colour, 0–7 |

A moving sprite does not have its own colour. Wherever its pixels land, they take the ink of the cell they are in. When a sprite that should be yellow walks into a cell of green scenery, one of the two has to give way: either the sprite turns green, or the whole cell turns yellow and the scenery in it changes colour too. Reviewers called the result clash.

## What the renderer decides

Every Spectrum game makes a choice about attribute memory, whether its programmer thought of it that way or not:

- **Rewrite the attribute.** The sprite routine sets each cell it touches to the sprite's colour. The background pixels in that cell change colour too, and the sprite drags a block of recoloured scenery with it. Anything printed through the ROM behaves this way by default: "any printing will set the corresponding attribute at all the character positions it uses."
- **Leave the attribute alone.** The sprite routine changes only the pixels, and the sprite takes whatever ink each cell already has. The scene's colours never move. The sprite changes colour as it crosses them.
- **Design so the question never arises.** Arrange the screen so that a sprite never shares a cell with a different colour.

## Six ways of living with it

**1. One colour per room.** Give every cell on the screen the same ink and paper, and the sprites can go anywhere. Knight Lore (Ultimate Play The Game, 1984) drew each room of its castle in a single ink on black, sprites included, and changed the ink from room to room. *CRASH* noticed that the game still did not look drab: "each screen has its own colour."

**2. Colour where the sprites are not.** Put the colour in places the moving objects never go. Avalon kept its "borders very colourful" and its playing area "quite simple". Ultimate's Sabre Wulf (1984) did the same thing on a larger scale. Its jungle is dense, multicoloured foliage that forms the walls of the maze, while the paths the explorer walks are black.

**3. Let the sprite wear the background.** Change only the pixel bytes and never the attributes, so the sprite takes the colour of each cell it enters. The scenery stays intact, and the sprite changes colour as it crosses it. Sinclair BASIC has a version of this built in. `INK 8` and `PAPER 8` mean "transparent": "the old attribute shows through". A BASIC program can therefore print over a coloured scene without recolouring it.

**4. Black masks.** Surround the sprite with a band of black pixels wide enough that the scenery behind it is blanked out. The cells around the figure then hold the sprite and black, so the sprite's colour has nothing to clash with. The cost moves to the scenery, which gets cut away around the figure. *Your Sinclair* spotted the technique in an August 1986 preview of Dark Sceptre from Beyond: "Look at the size of that mask — no attribute problems here."

**5. Move in whole cells.** If a sprite only ever moves in steps of eight pixels, it always fills whole cells. Each cell it enters can take the sprite's colours outright and get the scenery's colours back when it leaves, so colour never bleeds past the sprite's edge. The cost is movement that jumps rather than glides.

**6. Accept it.** Some games decided that smooth movement or detailed backgrounds mattered more. *CRASH* found that the main character of Frankie Goes to Hollywood "clashes a great deal with the background", and gave its colour "excellent once you accept the attribute problems". In 1989 the Software Creations team explained the choice they had made for Ghouls 'n' Ghosts: "The design of the backgrounds is severely limited by the scrolling technique, but the continuous smooth scrolling adds so much to the gameplay that this limitation can be endured."

## BRIGHT and FLASH

BRIGHT gives each of the eight colours a brighter version, applied to the ink and the paper of a cell together. A cell can be normal green or bright green, but not normal green ink on bright green paper. Black looks the same at both brightness levels, so the Spectrum shows fifteen distinct colours, not sixteen.

FLASH is "done by swapping the ink and paper colours". The ULA does the swapping by itself on a timer, so a flashing cell costs the program nothing once its attribute is set.

## The attribute as data

Because there is exactly one attribute byte per cell, the attribute area also works as a map of the screen. A program can read a cell's byte to find out what is there, as well as what colour it is. If walls, floors and doors each have their own colour, one `LD A,(HL)` tells the program both how a cell looks and how it behaves. *CRASH* singled out Mike Follin's Vectron, published by Firebird and reviewed in January 1986, for doing this with its maze: "Using the attribute file to overlay a map of the maze was an inspired idea."
