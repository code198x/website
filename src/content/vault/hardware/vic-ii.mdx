Al Charpentier, who led the design of the Commodore 64's video chip at MOS Technology, started from a budget. A television line lasted about 63 microseconds, and the memory he planned to use allowed "only 114 memory fetches per line—period." Those fetches had to be shared between the processor, the characters on screen and the sprites. Three bytes per sprite per line was what was left, and that fixed the size of a sprite: "The 3 bytes per sprite determined the horizontal size of the sprite—24 pixels." Twenty-one lines made 63 bytes, which fits a 64-byte block.

That budget is the key to the VIC-II. The chip and the 6510 processor share one memory bus. Most of the time they take turns so neatly that the processor never notices. But on every eighth line of the picture the VIC-II needs more than its share, and it stops the processor to get it. Every C64 programmer who wanted something to happen at an exact moment, such as a colour change halfway down the screen or a smooth-scrolling playfield under a fixed score panel, had to write code around those stolen cycles.

The chip is the MOS 6567 in NTSC machines and the 6569 in PAL ones. Commodore's preliminary data sheet lists the features: 47 control registers, up to 16K of display memory, 16 colours generated on the chip, and "up to eight independent movable image blocks", which everyone else called sprites.

## Fast facts

- **Text:** 40×25 characters of 8×8 pixels, each with its own foreground colour from colour RAM.
- **Bitmaps:** 320×200 with two colours in each 8×8 cell, or 160×200 with up to four colours in each 4×8 cell.
- **Colours:** a fixed palette of 16.
- **Sprites:** eight, each 24×21 pixels (12×21 in multicolour), with double-width and double-height options, priority against the background, and collision detection.
- **Scrolling:** hardware fine scroll of 0–7 pixels in each direction.
- **Interrupts:** on a chosen raster line, on sprite collisions and on the light pen.
- **Registers:** 47, at `$D000`–`$D02E` (53248–53294).

## PAL and NTSC

The chip generates the video timing and the processor clock, so the two versions give the whole machine different timing. The processor runs at 985,248 Hz on a PAL C64 and 1,022,727 Hz on an NTSC one.

| Chip | TV standard | Lines per frame | Cycles per line |
|---|---|---|---|
| 6569 | PAL | 312 | 63 |
| 6567R8 | NTSC | 263 | 65 |
| 6567R56A | NTSC | 262 | 64 |

The data sheet gives the NTSC figure from the other end: "one horizontal raster line is 520 video clock cycles", and the processor clock is the video clock divided by eight, which gives 65. Bauer singles out the 64-cycle 6567R56A as the one NTSC stepping whose timing differs from the others. Commodore's data sheet also names PAL-N (6572) and PAL-M (6573) versions. Later C64 boards use the 8562 (NTSC) and 8565 (PAL), which Bauer describes as functionally equivalent; Commodore's 1992 service manual lists the 8562 on the C64C board.

Most programs behave the same on every version. Anything that counts cycles, such as raster effects, sprite multiplexers or music players that are called once per frame, needs values for each.

## Where the cycles go: badlines

Each raster line gives the VIC-II one memory access per cycle in the half of the cycle the 6510 does not use. That is enough to fetch the pixel data for 40 characters, refresh the dynamic RAM and read the eight sprite pointers. It is not enough to fetch the 40 character codes as well. So on the first pixel line of each character row the VIC-II pulls its BA (bus available) line low, waits three cycles for the processor to finish any writes, and then takes the bus for 40 consecutive cycles. Programmers call these lines **badlines**.

Christian Bauer's 1996 description of the chip, compiled from tests by Marko Mäkelä, Andreas Boose, Pasi Ojala, Wolfgang Lorenz and others, puts the cost at 40 to 43 cycles. On a 63-cycle PAL line that leaves the processor about 20. Sprites cost more: each sprite shown on a line takes two cycles in the processor's half, again with a three-cycle warning. The [Commodore 64](/vault/systems/commodore-64#the-raster-beam-as-a-clock) entry sets out the whole budget. The short version is that a PAL line with no badline and no sprites leaves all 63 cycles, and a badline with all eight sprites leaves almost none.

Bauer defines the condition exactly. A line is a badline when all three of these are true:

1. The raster line is between `$30` and `$F7` (48–247).
2. The bottom three bits of the raster line equal YSCROLL, the vertical scroll in bits 0–2 of `$D011`. With the default YSCROLL of 3 the first badline is `$33` (51) and they follow every eight lines.
3. The DEN bit (`$D011` bit 4, display enable) was set during some cycle of raster line `$30`.

The third condition is checked once per frame. If DEN was clear on line `$30`, the frame has no badlines and the display area shows only border colour. Clearing DEN later in the frame does not stop that frame's badlines.

The second condition is not checked once. Bauer's definition applies "at any arbitrary clock cycle", so a program that changes YSCROLL partway through a line can create a badline where there would not have been one, or remove one. Scrolling the screen vertically moves the badlines with it. Most of the famous VIC-II tricks are this rule used on purpose:

- **[FLD](/vault/techniques/fld)** (flexible line distance) holds a badline back by changing YSCROLL, so the next character row starts lower down. The screen can be pushed down a long way without moving a byte of screen memory.
- **[FLI](/vault/techniques/fli)** (flexible line interpretation) forces a badline on every raster line. In a bitmap mode the colours come from screen memory, which is read only on badlines, so every line now gets fresh colours. The screen memory address does not advance, so the program also switches `$D018` to a different screen each line, cycling through eight screens. Bauer notes the price: the forced badline starts too late for the first three fetches, which read `$FF`, and that shows as a 24-pixel stripe down the left edge.
- **[Linecrunch](/vault/techniques/linecrunch)** cuts a badline short, so a whole character row collapses to one raster line, which scrolls the screen up quickly.
- **DMA delay** starts a badline partway through a line, which shifts the whole screen sideways by whole characters. Demo coders call it [VSP](/vault/techniques/vsp).

When timing matters, the simplest escape is to turn the screen off: clearing DEN removes badlines from the next frame. The stolen cycles caught out Commodore's own engineers. *IEEE Spectrum*'s account of the machine's design records that "because the processor in the C-64 is turned off for 40 microseconds every 512 microseconds, it kept missing the interrupt signals that control the disk interface."

## Sprites

The VIC-II reads each sprite's data three bytes at a time, one line at a time, into a 24-bit shift register. That design explains both what sprites can do and what they cannot.

A sprite can be moved anywhere with two registers, in front of or behind the background with one bit, and its shape can be changed on any line by changing its pointer. Commodore's own documentation calls them MOBs, "movable object blocks". Sprite 0 always has the highest priority among the sprites and sprite 7 the lowest.

The chip will show only eight sprites on one line. Bauer explains why: after 24 pixels the shift register "has run empty", and moving a sprite sideways within the same line does not refill it. Vertically it is different. Once a sprite has finished drawing, a program can give it a new Y position lower down the screen, and the chip will draw it again there with whatever X position, colour and shape the program has set by then. That is [sprite multiplexing](/vault/techniques/sprite-multiplexing), and it is how C64 games show far more than eight moving objects. It costs processor time and precision. Writing his diary of *Morpheus* for *ZZAP!64* in 1987, Andrew Braybrook noted that with his multiplexer running on the title screen "the sprite positioning had to be pixel perfect to actually work properly, there's no room for any play in the vertical positioning at all, the sprites are just re-cycled in time." A few months earlier he had been comparing his with another programmer's: "Having seen Gary Liddon's sprite multiplexor on Saturday, I can't understand why his runs faster".

The Y-expansion bit can be abused too. Bauer describes how toggling it at the right cycle makes the chip repeat a sprite line three or more times, stretching a sprite by any amount ([sprite stretching](/vault/techniques/sprite-stretching)).

## Raster interrupts

The VIC-II can interrupt the processor when the beam reaches a chosen line. The program writes the line number to `$D012` (with bit 8 in bit 7 of `$D011`) and enables the interrupt in `$D01A`. When the interrupt fires, the handler has to acknowledge it by writing a 1 to bit 0 of `$D019`, or it will fire again straight away.

This is what split screens are made of. *ZZAP!64*'s machine-code column explained it to readers in September 1987: "all those games that have the top half of the screen scrolling and the bottom half of the screen stationary are using raster interrupts." The scroll registers are set for the playfield at the top of the frame, and a raster interrupt partway down resets them for the status panel. See [raster interrupts](/vault/techniques/raster-interrupts), and [stable raster](/vault/techniques/stable-raster) for removing the few cycles of jitter that remain.

## The border

The border is not a frame around the picture. The chip switches it on and off at fixed beam positions, and the positions depend on whether the display is set to 25 or 24 rows (RSEL, `$D011` bit 3) and 40 or 38 columns (CSEL, `$D016` bit 3). If a program switches from 25 to 24 rows after the beam has passed the 24-row switch-on line but before it reaches the 25-row one, the chip misses both and never turns the bottom border on. Bauer gives the window as raster lines 248 to 250. The side borders open the same way with CSEL, but the switch must land in exactly cycle 56 of the line. In the [opened border](/vault/techniques/open-borders) the only graphics that normally show are sprites.

Programmers were not sure at first that this was safe. Braybrook wrote in his April 1987 diary that he was "unhappy about using sprites in the border as it could be exploiting a video-chip bug. This may not work on some machines or it could cause damage." By September 1988 Martin Walker, writing his own *ZZAP!64* diary, called it "the much used sprites in the border trick", and had used it for the information bars in *Hunter's Moon*. In January 1989 *Commodore Disk User* printed a border-sprite routine for its readers, saying that until two or three years earlier "sprites in the border were absolutely unheard of and for a long while after, only the top games programmers, such as Jeff Minter, knew the secret".

## Register map

The registers live at `$D000`–`$D02E` (53248–53294). The names are the ones in *Mapping the Commodore 64*.

The chip has only six address inputs, so the whole block repeats every 64 bytes up to `$D3FF`: `$D040` is `$D000` again, and a write to any copy reaches the chip. The 17 unused addresses in each copy, `$D02F`–`$D03F`, read as `$FF` and ignore writes.

| Address | Name | Purpose |
|---------|------|---------|
| $D000–$D00F | SP0X, SP0Y … SP7X, SP7Y | Sprite X and Y positions, sprites 0–7 |
| $D010 | MSIGX | Bit 8 of each sprite's X position |
| $D011 | SCROLY | Vertical scroll, 24/25 rows, display enable, bitmap mode, extended colour mode, raster bit 8 |
| $D012 | RASTER | Current raster line (read); raster interrupt line (write) |
| $D013–$D014 | LPENX, LPENY | Light pen position |
| $D015 | SPENA | Sprite enable |
| $D016 | SCROLX | Horizontal scroll, 38/40 columns, multicolour mode |
| $D017 | YXPAND | Sprite double height |
| $D018 | VMCSB | Screen memory and character set addresses |
| $D019 | VICIRQ | Interrupt flags (write 1 to acknowledge) |
| $D01A | IRQMSK | Interrupt enable |
| $D01B | SPBGPR | Sprite behind background |
| $D01C | SPMC | Sprite multicolour |
| $D01D | XXPAND | Sprite double width |
| $D01E | SPSPCL | Sprite–sprite collisions |
| $D01F | SPBGCL | Sprite–background collisions |
| $D020 | EXTCOL | Border colour |
| $D021–$D024 | BGCOL0–BGCOL3 | Background colours 0–3 |
| $D025–$D026 | SPMC0, SPMC1 | Shared sprite multicolours |
| $D027–$D02E | SP0COL–SP7COL | Sprite colours |

Bits the chip does not use read back as 1. So `PEEK` often returns a different number from the one that was written, and code that compares a register with an expected value needs to mask those bits off first.

## Border and background colours

The simplest registers to use:

```basic
POKE 53280,0  : REM Border colour (black)
POKE 53281,1  : REM Background colour (white)
```

**Colour values (0–15):**

```
0=Black   1=White    2=Red      3=Cyan
4=Purple  5=Green    6=Blue     7=Yellow
8=Orange  9=Brown   10=Lt Red  11=Dk Grey
12=Grey  13=Lt Grn  14=Lt Blue 15=Lt Grey
```

## Screen and character memory ($D018)

Register `$D018` (53272) tells the VIC-II where to find screen memory and the character set. Both addresses are inside the 16K bank the chip is currently using.

```
Bits 7-4: Screen memory address (value × $0400)
Bits 3-1: Character set address (value × $0800)
Bit 0:    Unused (reads as 1)
```

At power-up the upper half is 1, so screen memory is at `$0400` (1024), and the lower half selects the character ROM, which the VIC-II sees at `$1000`. The Programmer's Reference Guide gives the two values BASIC programmers need: `POKE 53272,21` for the upper-case and graphics characters, and `POKE 53272,23` for lower case.

**Example: move screen memory to `$0C00`:**

```basic
POKE 53272,(PEEK(53272) AND 15) OR 48
```

`$0C00 / $0400 = 3`, and 3 in the upper four bits is 48. Switching between two screens this way is how C64 programs [double-buffer](/vault/techniques/double-buffering) a character display. The sprite pointers move with the screen, because they are its last eight bytes.

## Display control ($D011)

Register `$D011` (53265):

```
Bit 7:    Raster line bit 8 (read: current line; write: interrupt line)
Bit 6:    Extended colour mode (ECM)
Bit 5:    Bitmap mode (BMM)
Bit 4:    Display enable (DEN; 0 = whole screen shows border colour)
Bit 3:    25/24 rows (RSEL; 1 = 25 rows)
Bits 2-0: Vertical fine scroll (YSCROLL, 0-7)
```

*Mapping the Commodore 64* gives its start-up value as 155 (`$9B`): 25 rows, display on, text mode, YSCROLL 3, and bit 8 of the interrupt line set. Reading bit 7 returns bit 8 of the *current* raster line instead, so `PEEK(53265)` usually gives 27 (`$1B`), and 27 is the value programs write to restore a normal screen.

**Example: switch on bitmap mode:**

```basic
POKE 53265,PEEK(53265) OR 32
```

## Horizontal control ($D016)

Register `$D016` (53270):

```
Bits 7-6: Unused (read as 1)
Bit 5:    Keep at 0
Bit 4:    Multicolour mode (MCM)
Bit 3:    40/38 columns (CSEL; 1 = 40 columns)
Bits 2-0: Horizontal fine scroll (XSCROLL, 0-7)
```

It is set to 8 at power-up: 40 columns, multicolour off, no scroll. Commodore's documentation says to keep bit 5 clear. *Mapping the Commodore 64* calls it a chip reset bit, but Bauer's tests found it does nothing on the 6567 and 6569.

**Example: switch on multicolour text:**

```basic
POKE 53270,PEEK(53270) OR 16
```

Only characters whose colour RAM value is 8 or more become multicolour, and they can use only colours 0–7 for their own colour. Others stay in normal high resolution, so the two kinds can share a screen.

## Display modes

Three bits choose the mode: ECM and BMM in `$D011`, and MCM in `$D016`.

| Mode | ECM | BMM | MCM | Resolution | Colours |
|------|-----|-----|-----|------------|---------|
| **Standard text** | 0 | 0 | 0 | 40×25 characters | Own colour on a shared background |
| **Multicolour text** | 0 | 0 | 1 | 4×8 pixels per character | Up to 4 per character |
| **Standard bitmap** | 0 | 1 | 0 | 320×200 | 2 per 8×8 cell |
| **Multicolour bitmap** | 0 | 1 | 1 | 160×200 | Up to 4 per 4×8 cell |
| **Extended colour text** | 1 | 0 | 0 | 40×25, 64 characters | Own colour on 1 of 4 backgrounds |

The other three combinations are invalid, and in them the chip draws the text or bitmap black. Bauer suggests using one to blank out unwanted lines, such as the rows that linecrunch piles up at the top of the screen.

## Raster register ($D012)

Reading `$D012` (53266) gives the low eight bits of the current raster line: 0–311 on a PAL machine, 0–262 on a 6567R8. Bit 8 is in `$D011`. The visible display lines are 51 to 250.

```basic
10 IF PEEK(53266)<>100 THEN 10
20 POKE 53280,2  : REM Change the border once line 100 is seen
```

This works, but only just. BASIC takes far longer than one raster line to go round even that one-line loop, so it may miss line 100 for several frames, and the colour change lands well after the beam has moved on. Changing a colour on an exact line needs machine code, and ideally a [raster interrupt](/vault/techniques/raster-interrupts).

## Sprite enable ($D015)

Each bit switches one sprite on: bit 0 for sprite 0, bit 7 for sprite 7.

```basic
POKE 53269,7  : REM Binary 00000111 = sprites 0-2 on
POKE 53269,PEEK(53269) AND 253  : REM Clear bit 1: sprite 1 off
```

## Sprite positions ($D000–$D010)

Each sprite has an X and a Y register, giving the position of its top-left corner. Y is eight bits. X needs nine, so the ninth bits of all eight sprites share `$D010`, bit 0 for sprite 0 and so on. The Programmer's Reference Guide gives the visible range as X 23–347 and Y 50–249; positions outside it let a sprite slide smoothly on and off the screen.

**Example: sprite 0 at (150, 100):**

```basic
POKE 53248,150  : REM X low byte
POKE 53249,100  : REM Y position
POKE 53264,PEEK(53264) AND 254  : REM Clear X bit 8
```

**For X above 255:**

```basic
POKE 53248,260 AND 255  : REM Low byte (260-256=4)
POKE 53264,PEEK(53264) OR 1  : REM Set bit 0 in $D010
```

## Sprite data

A sprite is 63 bytes: 21 rows of three bytes, each byte eight pixels. Sprites are stored in 64-byte blocks, so a one-byte pointer can select any of 256 blocks in the VIC-II's 16K bank.

**Sprite pointers:** the last eight bytes of screen memory, screen + `$03F8` to `$03FF`. With the screen at 1024, the pointer for sprite 0 is at 2040 and for sprite 7 at 2047.

**Example: a solid 24×21 block from block 13 (address 13 × 64 = 832, in the cassette buffer):**

```basic
10 FOR I=832 TO 894
20 POKE I,255  : REM All 63 bytes: every pixel on
30 NEXT I
40 POKE 2040,13  : REM Sprite 0 uses block 13
50 POKE 53287,1  : REM Sprite 0 colour: white
60 POKE 53248,150  : REM X position
70 POKE 53249,100  : REM Y position
80 POKE 53269,1  : REM Enable sprite 0
```

To draw a shape instead, set only the bits for the pixels you want. A vertical line down the left edge is `POKE I,128` for the first byte of each row (832, 835, 838 and so on) and zero everywhere else.

## Collision detection

- **Sprite–sprite:** `$D01E` (53278)
- **Sprite–background:** `$D01F` (53279)

Each bit belongs to one sprite. A collision needs non-transparent pixels to overlap; in multicolour modes the `01` bit pair counts as background, so it never collides.

```basic
10 C=PEEK(53278)  : REM Sprite-sprite
20 IF C AND 1 THEN PRINT "SPRITE 0 HIT ANOTHER SPRITE"
30 B=PEEK(53279)  : REM Sprite-background
40 IF B AND 1 THEN PRINT "SPRITE 0 HIT BACKGROUND"
```

**Important:** reading either register clears it. Read each one once per frame and keep the value if you need it more than once. The collision interrupts fire only on the first collision after the register was last cleared.

## A raster bar in machine code

Changing the border colour on every line needs machine code. This loop waits for the raster line to change and then steps the border colour:

```asm
        sei             ; stop the KERNAL's own interrupt
loop    lda $d012       ; note the current raster line
wait    cmp $d012
        beq wait        ; wait until the next line starts
        inc $d020       ; next border colour
        jmp loop
```

The result is bands of colour one line deep. Their left edges are ragged, because the change happens at a slightly different point on each line and much later on badlines, when the processor has been stopped. Getting the edges straight is the problem [stable raster](/vault/techniques/stable-raster) routines solve.

## Where the chip came from

The chip project began at MOS Technology in 1981, before there was a computer to put it in. *IEEE Spectrum*'s 1985 account of the C64's design says Charpentier worked on the graphics chip for nine months with two draftsmen and one computer-aided-design operator. The team surveyed the competition first. "We looked heavily into the Mattel Intellivision," Charles Winterble recalled. When the first silicon came back, Winterble said, "it functioned except for one bad sprite."

*Compute!*'s first look at the machine in August 1982 explained sprites to its Atari-owning readers by comparison with Atari's player-missile graphics. The comparison fits the idea, and the C64's sprites added their own colours, expansion and collision detection in hardware. The tricks came later, from programmers working out what the chip did rather than what Commodore said it did. Bauer's document, written in its own words for "C64 programmers and authors of C64 emulators", calls FLI "probably the most outstanding example of 'unconventional' VIC programming".
