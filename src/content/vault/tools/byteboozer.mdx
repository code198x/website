**ByteBoozer** compresses programs and data for the [Commodore 64](/vault/systems/commodore-64). It was written by **HCL** of [Booze Design](/vault/groups/booze-design), the group behind *[Edge of Disgrace](/vault/demos/edge-of-disgrace)*. A small decompressor, or **decruncher**, restores the packed bytes on the C64.

The preserved assembly routine dates the original ByteBoozer decruncher to May 2003 and its later **B2** form to December 2014. Those names identify related formats; a programmer needs the routine that matches the packed data.

## Copy new bytes, reuse old ones

B2 alternates between literal runs and matches. A literal run supplies bytes directly. A match gives a length and a position from which to copy bytes already produced. Repeated pictures, instructions or other sequences can therefore take fewer bytes to describe. This is the central idea behind [LZ-style compression](/vault/techniques/compression).

The assembly source makes the practical cost visible. It needs zero-page working storage and changes addresses inside its own instructions as it reads the stream. A programmer integrating it must reserve that storage and place the routine in writable memory. A short routine still has requirements.

## Put compression into the build

The separately developed **KickAss Cruncher Plugins** provide a Java implementation of ByteBoozer and support for B2 inside Kick Assembler. Several memory blocks can be gathered into one packed region, with gaps filled with zeroes. The plug-in’s **B2exe** variant adds a decruncher and BASIC startup code.

That separates two jobs: a host computer prepares the compressed file; the C64 restores it. Whether that is a useful saving depends on the packed bytes, the routine added to them, the memory available and the time allowed for unpacking. [Exomizer](/vault/tools/exomizer) and [Pucrunch](/vault/tools/pucrunch) offer other choices within the same constraints.
