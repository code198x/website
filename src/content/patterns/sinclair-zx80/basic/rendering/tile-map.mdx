Before your game draws a wall, it needs to know where the wall is. A map can answer that question without touching the screen. Set column C to 0 and row R to 1, call line 1000, and this room returns **tile 3 with success flag E=1**.

These are reusable **ZX80 BASIC** routines. The unchanged readable public caller has now run on **2 KiB RAM** with the original ROM. Keep it for its flexible descriptors and explicit contracts; a separately qualified **stock 1 KiB** option appears below. The [assembly version](/patterns/sinclair-zx80/assembly/rendering/tile-map/) has its own calling contract and execution record.

## Know what a call changes

| Call | Supply | Read back |
| --- | --- | --- |
| GOSUB 1000 | C=column, R=row | E=1,T=tile,D=flat offset; invalid gives E=0,T=-1,D=0 |
| GOSUB 1100 | C,R,V=new tile | A valid write gives E=1,T=V; failure gives E=0 and leaves storage alone |
| GOSUB 1200 | T=tile ID | E=1,F=property; invalid gives E=0,F=-1 |
| GOSUB 1300 | X,Y=world position, S=units per cell | C,R=cell and E,T from the checked lookup |

Always test E before using a returned value. A rejected write with an invalid ID leaves T unchanged; a rejected position gives T=-1. A world input rejected before division gives C=R=T=-1. If division succeeds but selects an outside cell, C and R retain that calculated coordinate while E=0,T=-1.

W,H,L and S hold the width, height, largest tile ID and positive whole-number cell size. M is the map array; P is the property array. Allocate W×H cells and L+1 properties, then initialise every map ID within 0..L. Bounds checks cannot rescue a descriptor that claims more storage than you allocated. They do not revalidate your entire room on every lookup.

Reserve scalar C,R,V,X,Y for arguments and E,T,D,F for results and scratch. Reading changes E,T,D; writing also changes M; property lookup changes E,F; world conversion changes C,R and calls the reader. Other scratch may retain its old value after an early return. These global variables make the routines non-reentrant: save any result you need before another call overwrites it. The caller owns the arrays and their lifetime; the library does not reserve a fixed screen area or install an interrupt.

## Keep coordinates separate from array subscripts

Both the first column and the first row are numbered zero. The row-major offset is `R*W+C`: moving down a row skips W cells. On this machine the BASIC array starts at **0**, so the final access is **M(D+0)**. The property lookup similarly uses P(T+0).

The original ZX80 ROM works with signed whole numbers. `X/S` truncates towards zero, so rejecting negatives first gives us the round-down result we want. There is no INT call here. Keep values and intermediate arithmetic within −32768 to 32767; width, height and their product must fit.

With S=8, world positions 0–7 select cell 0 and 8–15 select cell 1. The same routine also works with S=3: position (6,3) selects cell (2,1). This is the grid, division and coordinate-space work from [Maths for Games](/craft/maths-for-games/) in a form you can use immediately. The units need not be screen pixels. Query a world map with world coordinates; subtracting the camera first asks about a different position.

The world contract accepts non-negative positions up to 32767 and a positive whole S. Signed worlds, wrapping, rectangular cells and very large coordinates need an explicit extension. A cell query also differs from [box collision](/patterns/cross-platform/physics/aabb-collision/): an actor can touch several cells, so its centre alone may miss a wall.

## What the readable version costs

The 35 map elements, four properties and one guard use **80 bytes of numeric element payload**, at 2 bytes each. Array headers, scalars, the program, display file and interpreter stacks/workspace need further RAM. This is element accounting, not a measured free-memory figure.

The ZX80 stops generating its normal display while computing. The caller prints its results and stops so you can read them; this is a useful fit for command-driven work, not evidence of smooth action graphics.

Each successful read calculates a row offset. Precomputed row offsets exchange storage and setup work for a different query path. Byte or packed maps can reduce data RAM, but extraction and updates become more involved. The assembly entry offers a separately verified byte-map route. None of these alternatives is automatically faster for every workload.

## How little RAM does it actually need?

The earlier 16 KiB setting was a diagnostic configuration, not a measured minimum. We entered the unchanged listings through the ROM and counted the stored, tokenised lines:

| Component | Bytes |
| --- | ---: |
| Reusable routines | 331 |
| Explicit room initialiser | 475 |
| Public caller | 175 |
| Total program | **981** |

The complete public caller succeeds on **2 KiB**. The ROM rejects entry of the unchanged listing on **1 KiB** with error 4: out of memory. These are exercised configurations, rather than an exact byte-by-byte minimum.

On 2 KiB, the stopped caller has 124 bytes of variables, a 67-byte display file and a separate 40-byte system area. The stopped caller has an **832-byte gap** between the data frontier and CPU stack pointer. The retained sample is already at STOP; it does not measure the range during execution.

Those gaps are sampled headroom, not an instruction-level peak or a promise that your game has that much spare space. Editing, INPUT, extra variables, nested calls and output all need workspace. The measurements retain the actual system pointers and CPU stack pointer alongside the program bytes.

Every original API remains: E still indicates success, W/H/L/S remain configurable, and P remains data-driven. Reserve J too. Generating a room adds interpreted setup work, and a room with many exceptions may be cheaper to list explicitly. We have measured storage and behaviour, not a speed improvement. There is little room here for a larger game or verbose diagnostics without measuring again.

### Mistakes still cost real data

The stock verification uses a small real BASIC INPUT/GOSUB caller, replacing the public demonstration. It checks every cell, room edges, writes and rejection, properties, world conversion, customisation and deliberately broken lines. ZX81 also rejects fractional cell coordinates and IDs. Immediate commands do not replace a program's GOSUB return context. Each fault and repair starts in a fresh ROM session; an INPUT prompt is not the listing editor.

With a six-cell stride, reading (0,2) returns **0 instead of 2**. A row-zero check would miss it. Removing the return guard after a failed lookup lets an outside write damage the first cell. Restoring the stride and guard fixes those symptoms; always check both returned status and unchanged storage after rejection.
