## Overview

The Spectrum has no hardware sprites and no drawing chip — every pixel is placed by the CPU, straight into the screen bitmap at `$4000`. And that bitmap is laid out unlike any other: **consecutive screen lines are not consecutive addresses.** The [ULA](/vault/hardware/ula) stores pixels interleaved by third-of-screen and character row, so moving one pixel *down* the screen can jump the address by 256 bytes or by thousands. Every Spectrum graphics routine begins by taming this — turning an `(x, y)` into the right byte, and then stepping between lines without recomputing from scratch. Get this right and the rest of Spectrum drawing follows; get it wrong and your sprite scatters itself across the screen.

## The routine's contract

`pixel_addr` takes Y in D (0–191) and X in E (0–255), and returns the byte address in HL. It changes A, H, L and flags; B, C, D and E are preserved. The pixel mask is separate: `$80 >> (x AND 7)`.

`pixel_down` takes an address in `$4000`–`$57FF` belonging to a bitmap row **0–190**, and returns the same byte column on the next row. It changes A, H, L and flags, preserving B, C, D and E. Neither routine checks its inputs. Stop before stepping from row 191: that step reaches attribute memory at `$5800`, not another bitmap row.

## Trade-offs

| Aspect | Cost |
|--------|------|
| CPU | `pixel_addr`: 117 T-states; `pixel_down`: 26, 46 or 65, depending on the row boundary |
| Memory | No lookup data; an optional 192×2-byte line-address table needs 384 bytes |
| Limitation | The layout resists straight-line arithmetic; plan routines around it |

These are uncontended Z80 instruction totals, including each routine's `RET` and excluding the caller's `CALL` (17 more T-states). `pixel_down` takes 26 within a character cell, 46 across a 64-line third, and 65 across another character-row boundary. Memory contention and interrupts can increase elapsed time; the [retained verification](https://github.com/code198x/code-samples/blob/main/sinclair-zx-spectrum/patterns/assembly/rendering/bitmap-addressing/verification/results.json) matches these totals in Emu198x with code at `$8000`, stack at `$FF00` and interrupts disabled. The routines compute addresses without reading or writing screen RAM. These measurements do not cover contention or physical hardware.

**When to use:** Every pixel-level draw — [sprites](/patterns/sinclair-zx-spectrum/assembly/rendering/masked-sprites), lines, plotting, scrolling.

**When to avoid:** Character-cell work; [printing](/patterns/sinclair-zx-spectrum/assembly/rendering/character-printing) and colour move a whole 8×8 block at a time and dodge the pixel maths.

## Why the layout is this way

The address decomposes into three pieces of the `y` coordinate scattered across the two bytes: the **third** of the screen (`y7 y6`), the **character row** within that third (`y5 y4 y3`), and the **pixel row** within the character (`y2 y1 y0`). It reads as chaos, but it exactly matches the order the ULA fetches bytes to build the display, which let Ferranti shave gates off the address logic. The cost landed on the programmer: there's no `base + y*32`, so serious code either computes the address with the bit-shuffle above or, more often, looks it up in a precomputed 192-entry table of line addresses.

## Stepping down is the common case

You rarely need a fresh address per line — you need the line *below* the one you have, which is what `pixel_down` gives cheaply. Inside a character cell, `y2 y1 y0` live in the low three bits of the high byte, so the next line down is just `inc h`. Only when those bits overflow — every eighth line, at a cell boundary — do you move to the next character row (`L += 32`) and, unless you've crossed into a new third, undo the carry the `inc h` left behind. That asymmetry — seven cheap steps then one expensive one — is the shape of every Spectrum draw loop.
