## Four states, one update loop

A title screen should not keep moving the player behind the menu. Pausing should freeze the current game, then resume it rather than start another one. This small caller makes those choices visible with the border: blue for title, green for play, yellow for pause and red for game over.

Build `demo.tap` with the adjacent Makefile and load it on a 48K Spectrum. Space starts, pauses and resumes; Q ends a running game; Space returns from game over to the title. Reset the machine to leave. The caller starts at `$8000`, owns its stack at `$FF00`, keeps the 48K ROM visible for IM 1 interrupts, and uses the maintained QAOP/Space reader and frame waiter.

## Fit it into a game

Sample controls once per update. Compute new presses from that sample and the previous sample, then dispatch the current state. The history survives transitions: holding Space must not start a game and immediately pause it on the next update. Seeding history on entry also prevents a key held during loading from becoming a new press.

`update_state` changes AF, BC and HL, preserves DE, IX and IY, and consumes writable `game_state`, `pressed` and `game_ticks`. States are 0–3; an invalid value deliberately halts for diagnosis. Q takes priority if loss and pause arrive together. Replace those demo actions with your game's rules.

`game_ticks` increments only in play. Starting a fresh session clears it; resuming preserves it. It is a wrapping 16-bit demonstration counter, not a permanent score or wall clock. The transition update counts as a playing update before entering pause or game over. `draw_state` also changes DE and writes the border/MIC/beeper port; replace it if another routine owns that output.

Keep drawing separate from state updates. Menus, play and pause can share drawing without sharing movement. Add work incrementally and measure the complete update before assuming it fits the frame.
