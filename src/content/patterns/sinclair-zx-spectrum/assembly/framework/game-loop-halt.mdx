Watch the border change, then hold Space. The deliberate CPU workload slows the updates. The ROM clock keeps advancing while that work runs, so the next update can see that more than one frame passed.

## Use the wait in your project

Call `initialise_clock` once, then `wait_frame` once per update. AF and B change; other registers survive. Interrupts must be enabled on entry and are enabled on return. The helper briefly disables them to sample state safely. `last_frame` belongs to this consumer. `frame_delta` is the number of serviced ROM interrupts since its previous accepted sample.

## Start the complete example

Load the TAP through the 48K ROM or open the SNA. The complete caller uses IM1, keeps ROM interrupts enabled, sets its stack in high RAM and reads QAOP/Space with the existing reader. It owns the border. Reset to leave. The ROM keyboard and timing service remains active; this is not the custom-IM2 approach used later in Meteor Storm.

With Asm198x available, keep the sample folders together and run:

```sh
make -C sinclair-zx-spectrum/patterns/assembly/framework/game-loop
```
The Amiga Makefile also needs Build198x. Open the generated file under build using the machine’s normal loading route.

The loop keeps four jobs visible: wait, read input, update state, draw. `expensive_work` is an optional CPU workload to expose missed deadlines; remove it when building your own game. The changing colour or digit is a small observable result, not a rendering engine.

## What happens when work runs late

The clock uses the low byte of ROM FRAMES and wraps modulo 256. Fewer than 256 frames may pass between samples. A delay of exactly 256 would be indistinguishable from no change. The example counts one game update for the accepted sample; it does not replay every missed update or automatically multiply motion by `frame_delta`. A HALT with interrupts disabled would wait forever.
