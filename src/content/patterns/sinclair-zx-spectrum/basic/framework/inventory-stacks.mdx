Picking up five arrows should not quietly credit one arrow unless the game has chosen a partial-pickup rule. These routines accept or reject the whole requested quantity. They are useful for ammunition, keys, ingredients or other fixed categories of counted objects.

## Include and initialise

Reserve DIM Q(4), select a common integral per-category capacity C from 1 to 255, combine the numbered listings and call **3000**. It clears Q(1)..Q(4), S/A/M/O/E, retaining C. Reserve lines **3000–3260** and private loop variable I. Do not wrap the call in a caller's FOR I loop. END, STOP or a jump must prevent falling into the helpers.

The four slots are **fixed categories**, not four interchangeable item stacks. Your game defines what slot zero, one, two and three mean. A public slot S=0 maps to Q(1). C64/BBC arrays also allocate an unused element zero; Spectrum arrays start at one. Spectrum spells calls GO SUB; C64/BBC use GOSUB. The supplied build.py combines source lines and rejects duplicates.

## Add or remove a quantity

Supply S=0..3, A=0..255 and M=0 to add or M=1 to remove, then call **3100**. O=1 means the complete quantity was applied. O=0 with E=0 means insufficient stock or insufficient free capacity. No quantity changes on rejection. A zero request is a successful no-op.

E=1 rejects invalid capacity or any damaged retained count before touching a slot. E=2 rejects an invalid slot, amount or mode. Every count and input is integral, with each Q between zero and C. Validating all four categories costs time but prevents a request from mutating an already inconsistent inventory.

## Ownership and customisation

The helper owns S/A/M/C/O/E, Q and scratch I. It owns no item names, icons, prices, carry weight or object handles. To display “arrows”, the caller looks up its own name for that category. Separate inventories need separate arrays, globals and numbered references; sharing Q would share the contents.

The custom caller lowers C from 99 to 9. DIM Q(4) remains unchanged, so there is no claimed allocation saving. Different capacities per item need a capacity array and matching validation. More categories require changing DIM, the clear/validation loops, slot bounds and tests together. The current interface rejects slot 4 instead of guessing that a fifth category exists.

A partial pickup can be useful, but it needs an output reporting the accepted quantity and a caller that leaves the remainder in the world. Silently reducing A changes the meaning of success. Likewise, a weighted inventory or an equipment-slot system is a different contract, not just another title for these four counters.

## Mistake and repair

The wrong caller clips the requested addition from two to one before calling. That smaller request succeeds and fills the stack. Its saved checks are 0,0: it was not rejected, and stock no longer equals its original value. The helper cannot know the original request was larger.

The repair passes the original amount and handles failure explicitly. Its source and loaded program match the working caller exactly.

## Costs and alternatives

Every call validates four counts, then updates at most one. The fixed four-category scan is bounded; expanding the category count grows validation work. Numeric arrays are not packed bytes. A simple scalar is cheaper for a single ammunition count; typed stacks with item IDs are useful when categories are not fixed. A transfer between inventories must validate both sides before either changes. [The Craft](/craft/) is the place to choose the player's pickup/capacity rules; [Maths for Games](/craft/maths-for-games/) develops the bounds and conservation checks.

## Machine and measured size

Spectrum numeric arrays start at one. AND/OR in these listings join comparisons; neither is being used as a bitwise operator. The diagnostic reserves its mailbox above CLEAR 59999.

The numbered helper occupies **525 tokenised program bytes** on this interpreter, including line headers. This excludes the caller, test tables, numeric scalar/array storage, interpreter stacks and ROM. Tokenised size is not machine-code size or a hardware-cycle count. No real-time or whole-game performance budget is inferred from the diagnostic. The caller's W/Z/G, Y/D and RAM mailbox are observation machinery, not required game state.
