Press fire and the background changes colour. Keep holding it: nothing more happens. Release and press again, and the first colour returns. The game has accepted two actions, while the display has kept running throughout.

That small difference is worth getting right. A player waiting for their next move should not accidentally stop the picture, and a held button should not become hundreds of moves.

## Include and initialise the reusable state

Copy `turn.inc` and its neighbouring `edge-filter.inc` together, and include the routine once after your main code. Define `T` as seven private, consecutive RAM bytes. The caller uses **$90–$96**; choose another valid allocation if your game owns that memory already.

Call `init_turn` with the starting progress counter in A. It clears the previous/current samples, accepted flag and 16-bit service count, and sets the step to 1. Change `T+5` after initialisation when you want another step. These routines require **decimal mode clear**; the complete reset caller uses `CLD`.

<CodeFromFile src="cross-platform/patterns/framework/atari-turn-loops/edge-filter.inc" lang="6502" title="Keep only bits that became pressed since the last sample" />

| Entry or state | Contract |
| --- | --- |
| `init_turn` | A is the initial 8-bit counter; initialises all seven bytes |
| `sample_turn` | A is the active-high button mask; accepts newly pressed bits |
| `T+0` | Progress counter, increased by `T+5` on acceptance; wraps modulo 256 |
| `T+1`, `T+4` | Previous/current samples; keep the same bit convention each call |
| `T+2`, `T+3` | Little-endian 16-bit service count, independent of turns |
| `T+5`, `T+6` | Step size and the current call’s accepted flag (1 or 0) |
| `service_tick` | Increment the service count once per accepted display field |

The init/sample routines change A and flags; `service_tick` changes flags. All preserve X/Y. A direct `JSR` needs two stack bytes, plus your surrounding caller and interrupt depth. The routines have no nested calls, hardware access, frame wait, private stack or interrupt masking. Their shared context is not re-entrant.

Use one primary-button bit as the caller does. With a multi-bit mask, any newly pressed bit commits one update, even if another bit remains held; this routine does not queue separate actions for each button. A zero step can still report an accepted action without changing progress. Neither helper decides your game rules or imposes a deadline.

## Fit it into the machine’s caller

<CodeFromFile src="atari-2600/patterns/assembly/framework/turn-loop/demo.asm" lang="6502" title="Reset, input conversion, rule update and machine-specific display service" />

`sample_turn` reports acceptance only for that call. Read `T+6` before another sample replaces it, then let your own rules respond. `service_tick` does not change that flag. The two counters have different meanings: one counts accepted progress, the other counts serviced fields.

The guards immediately outside the seven-byte allocation are diagnostic caller state, not part of the reusable routine. The reset caller takes over the stack and display interfaces. Keep its ownership separate from other routines that scan input, alter interrupt enables or own the same video registers.

## The picture is part of the loop

The TIA does not keep a framebuffer for us. This caller generates **3 sync, 37 blank, 192 visible and 30 overscan lines**, repeatedly. Waiting for a player means continuing that work while leaving the rules alone.

The first overscan wait leaves one line for the input read and `sample_turn`. A second leaves a line for the service tick and colour selection. A third finishes that work, then the remaining 27 waits complete overscan. Keep those jobs within their allotted lines: adding an expensive world update there can change the field even if every loop count still looks right.

`WSYNC` stalls the CPU to a scanline boundary. The input read uses **INPT4 bit 7** at `$0C`: the electrical pressed state is low, so the caller inverts it before calling `sample_turn`. The `$01` write is VBLANK, and `$09` is COLUBK. These addresses are TIA interfaces, not portable 6502 facilities.

Native measurements at the same CPU field marker give **59,736 colour clocks** both idle and pressed: 262 × 228. That proves this caller’s schedule under this workload. It does not establish spare time for your game, a PAL schedule or original-television behaviour.

## What was checked

**Code status: assembled and emulator-executed** with Asm198x **0.0.71** and Emu198x **0.44.0**. Seven independent builds/runs cover the working caller, step-two customisation, **254 → 255 → 0** wrap, both deliberate faults and both repairs. The checks use real button input, 120 idle frames, a 30-frame hold, a second press, protected state boundaries and native captures. The repairs restore the working executable and captured results.

The records retain source, tool and executable identities.
