## Include it, then draw a string

Reserve **96 bytes at T plus 48 at BP**, separate from code, stack, font, string and bitmap. This complete caller uses 320×200 pixels, T at $4400 and BP at $4300. Include the CPC `geometry/cpc.inc` backend, not the Spectrum include. The caller owns Gate Array, CRTC, palette and the $C000–$FFFF display allocation, including its unused gaps.

Define `TEXT_WIDTH`, `TEXT_HEIGHT`, `TEXT_PEN_MAX` and `TEXT_PACKED` as shown in the caller. Include the text CPU component and its existing span backend once. Mono targets use pen maximum 1 and packed 0; CPC uses 3 and 1. BP must be zero page on 6502; T need not be. Scratch needs no initialisation; public inputs do.

After the display setup, this is an ordinary game call. The mailbox which follows is just how the verifier submits more requests.

Call `text_string`, then read T+17. Change X/Y and the string address/length to draw another label. For one character, set T+9 and call `text_char`; string address and length are then ignored. There is no retained scene, cursor or game loop inside the routine.

## The calling contract

Words and the 32-bit count use **little-endian** order. The origin is the cell's top-left corner, with Y downwards. Pens are 0–3, selecting palette indices. The fixture maps them to black, white, green and blue. Both pen inputs must be valid, even when transparent mode does not draw the background.

| T offset | Supply or read |
| --- | --- |
| 0,2 | Signed 16-bit X,Y origin, each −512..511 |
| 4 | Font address word |
| 6,8 | String address word and byte length 0..255 |
| 9 | Single code byte for `text_char` |
| 10,11 | First code byte and glyph-count **word**, 1..256 |
| 13 | Fallback code, which must exist in the font |
| 14 | 0 transparent, 1 opaque |
| 15,16 | Foreground and background pen bytes |
| 17 | Output: 1 accepted, 0 rejected |
| 18,20,22,24 | Scissor left,top,right,bottom words; right/bottom exclusive |
| 26 | Output signed word: next X |
| 28,29 | Output bytes: codes consumed, substitutions |
| 30 | Output word: backend span calls |
| 32 | Output 32-bit destination-byte writes |
| 36–95 | Private scratch |


A string is counted, not zero-terminated. A zero byte is a code; there is no newline, wrapping or implicit case conversion. An empty string is accepted without source reads or drawing, after declaration checks. A glyph always advances by eight: `nextX = inputX + 8*consumed`, including blank, substituted and fully clipped glyphs. That output is signed 16-bit, not a byte that wraps at 255.

The scissor must be nonempty and inside this physical bitmap. The routine intersects glyph runs with it before calling the backend. A completely clipped valid string still succeeds. Bad coordinates, mode, pens, font range, fallback, scissor or a source/font end beyond $10000 reject **before destination writes**, with the original X returned and zero counters. An allocation ending exactly at $10000 is allowed by the arithmetic check.

Inputs 0–16 and 18–25 survive. Source ranges must actually be readable in your machine's current mapping: arithmetic checks cannot establish memory ownership or negotiate a bank switch. Keep the font/string stable and disjoint from code, contexts, stack and destination for the whole call.

## Supply a font you own

Each glyph is eight bytes, top row first, bit 7 leftmost. The address of a row is `font + (code-first)*8 + row`. The optional **original Code198x font** supplies 64 glyphs for ASCII 32..95, occupying 512 bytes under the sample repository's MIT licence. It was drawn for these examples, not copied from a machine ROM. Its visible design is five columns by seven rows inside each 8×8 cell.

You can supply a ten-digit font in just 80 bytes, or a contiguous 256-code font in 2,048. First code plus glyph count must not exceed 256; fallback must belong to that range. Unsupported codes use the fallback and increase the substitution count, even when clipped. Lowercase needs its own glyphs or explicit conversion in your caller.

## Translation and byte boundaries

Glyph-local (3,5) at origin (21,37) lands at **(24,42)**. The next cell starts at X=29. A blank space moves the next cell too: ink, cell bounds and advance are different things. [Move a glyph, keep its shape](/craft/maths-for-games/unit-13/) works through that translation, clipping and division/remainder without requiring an algebra course.

Eight pixels at an arbitrary X can touch two mono bytes, or three four-pixel CPC bytes. The component finds foreground runs in each glyph row and sends them to `bp_hspan`. Transparent mode leaves zero font bits alone. Opaque mode paints the cell's background row first, then its foreground runs; it replaces the visible clipped cell, including the blank rows/columns.

For the ten-code `PIXEL TEXT`, transparent drawing at X=24 and X=31 makes 90 / 84 destination-byte writes; opaque makes 250 / 324. Foreground uses 77 spans; opaque adds 80 background spans. Gaps and edge masks affect those counts, so an unaligned cell is not automatically more expensive in every workload.

This baseline favours understandable composition. Opaque drawing touches foreground bytes again after clearing their background. A masked KEEP/image blitter could combine those operations; pre-shifted glyph phases trade more font storage for less shifting/address work. Compare [masked sprites](/patterns/sinclair-zx-spectrum/assembly/rendering/masked-sprites/) and [pre-shifted sprites](/patterns/cross-platform/rendering/pre-shifted-sprites/). Those are design choices to measure, not invisible upgrades to this routine.

The text component assembles to **2,268 bytes**, plus **578** for the backend, the chosen font/string and the contexts.  Reset setup, display and stack are additional. These are storage and byte-write measurements, not cycle counts or a frame-budget promise.

## Own the display and scratch

Clobbers: AF/BC/DE/HL and flags. Reserve a conservative **64-byte stack budget** beyond your other calls/interrupts. T and BP are non-re-entrant. No call changes interrupt state, waits for a frame or synchronises video. On 6502, text temporarily uses BP+46/47 for indirect source reads, with no live source pointer carried over a span call. The caller owns banks, display access and interruption/coexistence policy.

## Make the letters bigger

A title need not use the same tiny cells as a score. Repeat each source pixel twice in both directions and an 8×8 cell becomes 16×16. Use different factors for deliberately wide or tall lettering: 3×2 gives a 24×16 cell. The font still stores just eight bytes per glyph.

Verified native reset capture; borders and horizontal sampling are preserved." />

Choose `scaled-text/z80.inc` **instead of** the fixed bitmap-text CPU include. It exports the same `text_char` and `text_string` labels, so include only one. Keep this machine's existing backend and required helper/tables. The allocations remain **96 bytes at T plus 48 at BP**. Add two explicit inputs: **T+68 is scale X and T+69 is scale Y**, each an integer from 1 to 4. Set both, even for 1×1; an old fixed-width caller leaves those bytes uninitialised.

The existing font/range, fallback, source/count, mode, pens and scissor contract still applies. Inputs T+0..16, +18..25 and +68..69 survive. T+17 reports acceptance; T+26 returns `X + length×8×scaleX` as a word. Clipped, blank and fallback codes still advance. At scale X=4, 255 codes advance 8,160 pixels; a byte would lose most of that result. A rejected declaration preserves the original X and returns zero consumed, fallback, span and write counts before any destination writes.

Each font pixel becomes a rectangle, rather than a smoothed edge. For a destination-local pixel, the source position is `(x div scaleX, y div scaleY)`. Equivalently, source column 3 at scale X=2 occupies local columns 6 and 7. Add the cell origin, then clip. A cut-off letter keeps that sampling phase: it does not start again at font column zero at the clipping edge. [Integer division and remainders](/craft/maths-for-games/unit-06/) and [glyph-local coordinates](/craft/maths-for-games/unit-13/) explain those two steps.

The native code scales the endpoints of each foreground run and repeats source rows. The independent checker instead samples destination pixels using integer division. Transparent zero bits preserve the picture underneath; opaque mode paints the enlarged background cell first, then its ink. Opaque spaces therefore clear their whole enlarged cells. Neither mode clears unused panel space.

### Size has a drawing cost

The scaled component uses **2,878 code bytes** with the qualified assembler; the backend remains 578. The original sample font is still 512 bytes, and T/BP remain 96+48. BBC scanline tables, display memory, caller, string and stack remain separate. Keep a conservative 64-byte stack budget plus your caller/interrupt depth, and the renderer's CPU/register obligations above.

For the same original W! label at (21,37), opaque mode and the same pens, native counters report. Cell dimensions are logical pixels:

| Scale | Cell (px) | Spans | Byte writes |
| --- | --- | ---: | ---: |
| 1×1 | 8×8 | 38 | 70 |
| 2×2 | 16×16 | 76 | 248 |
| 3×3 | 24×24 | 114 | 432 |
| 4×4 | 32×32 | 152 | 760 |

Doubling both factors quadruples a cell's background area. Horizontal enlargement widens runs and changes byte crossings; vertical enlargement repeats rows and spans. CPC packs four pen indices per byte while the mono backends pack eight pixels, so their write counts differ. Counters include repeated writes to a byte. They measure drawing work, **not cycles or a frame budget**.

A separate pre-rendered size costs more assets but can avoid runtime expansion. Pre-shifted/masked blitters or precomposed hardware characters offer other trade-offs. Fully clipped cells skip raster work after resolving fallback, retaining logical advance and consumed/missing counts. This avoids expanding invisible rows in long offscreen strings.

The component owns T/BP, is non-re-entrant and supplies no OS negotiation, banking, interrupt protection or safe display interval. Keep source, font, code, contexts, stack and bitmap distinct and stable. This is a direct character/string renderer: the current fixed/proportional text-layout wrappers assume eight-pixel cells and row heights and **cannot simply be placed over this include**. A scaled layout must agree on both dimensions. Wrapping, baselines, kerning, fractional sizes, shrinking, flips and rotation remain separate work.

Full bitmap allocations, neighbours, public outputs, counted source/font immutability and selected entire native frames match independent expectations. Coverage includes all scale pairs, every horizontal bit phase, pens, partial/full clipping, empty/255-code input, a 256-glyph declaration and invalid declarations. Qualified tools are Asm198x 0.0.71 and Emu198x 0.41.0 for this named reset/display path; original hardware, stock-OS coexistence, live tearing and other modes need separate checks.
