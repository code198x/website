Type the shared BASIC loader and RUN it. A digit changes as the game updates. Hold Space to slow it with excessive CPU work, then release it to recover.

## Reuse a service contract

This is the same executable as the [BBC Micro example](/patterns/bbc-micro/assembly/framework/mos-game-loop/). It calls MOS instead of reaching directly into the BBC’s VIA or the Electron’s ULA. Shared services make that reuse possible; the common CPU alone would not.

Call `wait_frame` once before input/update/draw. The wrapper leaves A=19 and does not preserve X/Y/flags. Keep the MOS IRQ service and interrupts enabled. The wait accepts the next display sync; it supplies no missed-frame count and does not replay updates.

## Start the complete example

run the following command:

```sh
make -C acorn-electron/patterns/assembly/framework/game-loop
```
. That builds the shared sources in `bbc-micro/patterns/assembly/framework/game-loop`; type its `build/loader.bas` on the Electron and RUN it.

The loader selects MODE 6 and reserves memory above `HIMEM=&3000`. It installs our own executable at &3000 using DATA statements. This is a typed program route, not a snapshot of an already-running machine. Reset to leave.

## What happens when work runs late

The MOS interface is shared, but the amount of work that fits is not assumed to match the BBC. The same deliberate workload produced fewer updates on the tested Electron. That is a result for this caller and configuration, not a ranking of the machines or an isolated CPU benchmark.

The source comparison waits for installation to finish, with a bounded timeout. It does not assume both machines’ BASIC loaders complete after the same short delay. A new graphics mode, peripheral or direct hardware routine needs its own evidence.
