## Include it, initialise it, call it

PMODE 4 uses a 256×192 one-bit bitmap at $0600 in this reset caller. Its linear rows keep the backend small. Public words are big-endian: a left coordinate of 21 is stored as $00,$15.

Reserve **64 bytes at TL=$0480**, **96 at T=$0400** and **48 at BP=$0380** for this caller. Keep them separate from source, font, bitmap, code and stack. Include the unchanged bitmap-text component before `text-layout/6809.inc`; the layout uses its aliases and renderer. Keep the existing backend and its helper/table. The [complete source](https://github.com/code198x/code-samples/tree/50a33a0f1ef1bc027ead0d9115a559f1158e33c1/dragon-32/patterns/assembly/rendering/text-layout) shows every include and allocation.

T supplies the font pointer, first code/count, fallback, transparent/opaque mode and foreground/background pens. Layout takes ownership of T and BP while running, including the scissor. Initialise those font/pen choices as in `caller.inc`, then supply TL:

| Offset | Input |
| --- | --- |
| 0, 2 | Words: panel left, top |
| 4, 6 | Words: panel width, height |
| 8 | Byte: alignment, 0 left / 1 centre / 2 right |
| 9 | Byte: line pitch, 8..255 scanlines |
| 10 | Word: source address |
| 12 | Byte: source length, 0..255 |

## Measure before subtracting

`layout_measure` needs only TL+12. It returns `8*length` as a **word** at TL+18, accepted=1, and zeroes the other documented outputs. It reads no string or font. A 255-code line therefore measures 2,040 pixels rather than wrapping into a byte.

<CodeFromFile src="cross-platform/patterns/rendering/text-layout/6809.inc" from="layout_measure" to="layout_line" lang="asm" title="Counted-line measurement without a string scan" />

Five glyph cells need 40 pixels. A 177-pixel panel has 137 spare pixels. Centre alignment uses `left + floor(137/2)`: at left 21, the first cell begins at **89**, leaving the odd spare pixel on the right. Right alignment starts at 158. These are cell bounds; the visible ink can have blank columns inside them. [Coordinates and remainders](/craft/maths-for-games/unit-06/) and [glyph-local positions](/craft/maths-for-games/unit-13/) explain the calculations.

A line wider than its panel rejects before drawing. Do not subtract first and hope an unsigned result stays sensible. A block also plans every row before rendering: a message too tall for its panel leaves the previous bitmap intact. Supply readable, stable, non-overlapping source/font allocations and keep mappings unchanged throughout both passes.

## Decide what a line break means

Block mode uses `width div 8` cells per line. It keeps spaces and **can split a word**. Byte 10 is LF; byte zero remains a character code and uses the configured fallback if unsupported. Line mode instead treats every byte, including 10, as a glyph slot. This counted-line rule is also what `layout_measure` measures.

A full chunk consumes an immediately following LF as its own break. Consecutive LFs retain interior empty lines. A final LF ends its line without creating another trailing row. Empty input has zero lines and no drawing. The whole rectangle must fit the physical bitmap and be at least 8×8; an empty request still validates its declaration.

Pitch is the distance between row origins. Five rows at pitch 16 need `(5-1)*16+8=72` scanlines. Opaque mode paints actual glyph cells, not the unused width or an empty line. Clear the panel you own before replacing a longer message, or old letters may remain. Use the word-aware variant below when words should stay together. Incremental reveal is a separate technique.

## Costs, ownership and results

The layout adds **1,463 code bytes and 64 context bytes**. The reused text renderer is 2,058 bytes and its backend 470; their 96+48 context bytes, the 512-byte sample font, messages, video allocation and stack are separate. Reserve a conservative 80-byte stack budget plus caller/interrupt depth. The 6809 keeps U and DP; D, X, Y and condition codes may change.

Block mode makes two planning passes, then the renderer adds source/font reads and glyph/span work. The second pass interleaves planning and rendering after the complete first pass has qualified the request. TL+26 reports total span calls; TL+28 reports a 32-bit destination-byte-write count. These are work counts, not cycle measurements. Byte alignment, pen packing, glyph shapes and opacity affect them. Static labels can be cheaper to position or render once.

Accepted calls return consumed bytes at TL+14, logical lines at +15, last-line glyph count at +16, maximum logical width at +18, first origin X at +20, last line end X at +22 and its origin Y at +24. Rejected calls return zero for all documented outputs and leave the bitmap untouched. T/BP scratch may change. Blank lines affect line count and position but cause no glyph/background writes.

The component is non-re-entrant. It supplies no frame wait, OS negotiation, interrupt protection or video synchronisation. The reset caller owns the machine; a real game must choose safe display access and coordinate other users of T/BP, video, banks and interrupts. Native completion does not establish stock-OS loading, live tearing behaviour, original-hardware timing or a frame budget.

## Keep words together

For a paragraph or message panel, word-aware wrapping can be easier to read. Choose the maintained `word-wrap/6809.inc` variant over the same bitmap-text renderer. It adds 101 code bytes (1,564 total) and keeps the **same 64-byte TL allocation and public contract**. The original character-wrap component above remains useful for compact labels and fixed grids.

In seven columns, `ONE THREE FIVE` becomes `ONE` / `THREE` / `FIVE`. In two columns, `ABCDE` still becomes `AB` / `CD` / `E`: a word wider than the panel has to split if the routine is to make progress.

The exact policy matters when preparing messages:

- Fit at most `width div 8` cells. If an LF or space follows a full line, consume that delimiter as the break.
- Otherwise, break at the last space **after the first byte** of the current line, omitting that one separator. If there is none, split at the cell limit.
- Preserve every other space. Leading, repeated and trailing spaces remain data; this is not whitespace normalisation. Three spaces in a one-column panel occupy two rows because the middle space becomes a break.
- Byte 10 is LF in block mode. Consecutive LFs retain interior empty lines; a final LF adds no extra trailing row. Byte zero is a glyph code, not a terminator.

`layout_line` and `layout_measure` retain their counted-line behaviour: LF occupies a glyph cell there. Unsupported codes use the configured fallback. Empty input has zero rows and no drawing but still validates the declaration.

Both layout components deliberately export the same entry labels. **Include one of them**, after bitmap-text, rather than including both. The TL contract and single-line calls stay the same. Words can require more rows than character wrapping: the complete first pass checks the height **before drawing**, so a panel that is now too short rejects without partial text.

Pitch measures the distance between row origins. Five rows at pitch 16 need `(5-1)*16+8=72` scanlines. Opaque mode paints actual glyph cells, not the unused panel width or empty rows. Clear the panel you own before replacing a longer message, or old letters may remain.

### What does word wrapping cost?

The extra work is scanning for a separator and possibly rescanning the start of a word on the next row, in both planning passes. Every row consumes at least one source byte; counted input is bounded at 255. There is no extra context or font allocation. This is not proportional text, kerning or whitespace normalisation.

For the same custom message and panel, changed line breaks and two omitted spaces reduce span calls from **709 to 693**. Destination-byte writes change from **1,117 to 1,085**. Those are observed drawing-work counts, not a total-speed comparison: planning costs more, and placement changes byte phase too. Measure the complete call before claiming a frame budget.

The word-aware component retains **63 positive native calls**, the customisation and three faults with executed repairs on this machine. Full memory, inputs/outputs, guards, unchanged source/font and selected native frames match independent expectations. The four-machine total is 320 observations with Asm198x 0.0.71 and Emu198x 0.41.0.
