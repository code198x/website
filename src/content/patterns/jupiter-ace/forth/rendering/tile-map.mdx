Give a room a byte per cell and it can answer a useful question before you draw anything: **what is at this position?** On the supplied seven-wide room, `0 1 MGET` reads column zero of row one. It leaves **3 1** on the stack: tile 3, followed by success flag 1.

These are actual Jupiter Ace FORTH words. Compile the routines, supply your map, and call them from your own game. The [Z80 assembly entry](/patterns/jupiter-ace/assembly/rendering/tile-map/) solves the same problem through a different language and startup path; its evidence does not substitute for this one.

## Read the stack contract

In FORTH, words consume values from the top of the data stack and leave their results there. Read each effect below from left to right, with the rightmost value on top. The dash separates inputs from outputs.

| Word | Stack effect | What it does |
| --- | --- | --- |
| MINIT | base width height properties max-ID -- | Select the map and property storage |
| MCELL | column row -- address valid | Check a coordinate and compute its address |
| MGET | column row -- tile valid | Read a cell; failure returns 0 0 |
| MSET | tile column row -- valid | Change a cell only if both position and ID are valid |
| MFLAGS | tile -- flags valid | Read a tile's property byte; failure returns 0 0 |
| MXY | X Y -- tile valid | Divide non-negative world positions by eight and query |

The valid flag is on top, ready for `IF` to consume. Tile zero is ordinary floor data, so it cannot double as a failure flag. Consume or discard the value beneath the flag on both paths. MSET returns only one item; the other queries return two. Values below the arguments are preserved.

For a write, put the new tile ID before the column and row, then call MSET and check its result. The verifier changes column 0, row 0 to tile 3, reads it back, and checks every other map byte. The map and its following guard also remain unchanged after all rejected writes.

The map must contain width×height addressable bytes, and its product and final address must not wrap the 16-bit address space. Width and height are positive native-cell values, rather than an artificial eight-bit machine limit. The allocated RAM is still a real limit. The map must be writable for MSET; read-only data needs another change policy. Max-ID is 0–255, and the property table needs max-ID+1 readable bytes.

## Coordinates are not screen addresses

The address calculation is **base + row × width + column**. Multiplying by the screen width would quietly query another cell. MCELL treats coordinates as unsigned FORTH cells; on this small map, -1 has the bit pattern 65535 and fails the comparison with width or height.

MXY deliberately accepts **non-negative signed-cell positions, 0–32767**. It rejects a negative X or Y before using the ROM's signed division. An unsigned 16-bit world needs a corresponding conversion; `/` does not become unsigned because you intended a positive coordinate.

For eight-unit cells, world positions 0–7 belong to cell zero, 8–15 to cell one. Positive integer division rounds down here. Position (31,23) therefore queries cell (3,2). These are the coordinate, grid and representation ideas from [Maths for Games](/craft/maths-for-games/) in a small working routine. The units need not be physical screen pixels. Use world coordinates for the world map; subtracting the camera first asks a different question.

MFLAGS now returns **5 1** for tile 3. The map bytes stay the same. Both versions ran from fresh ROM starts; only that property byte changes, and this immediate store compiles no new word. Your game must interpret the flags when deciding whether movement is allowed.

Use `C@` and `C!` for these byte arrays. `@` and `!` access a two-byte FORTH cell. Replacing C! with ! would also write a neighbour; that is a different operation, not an alternative spelling.

## State, lifetime and costs

MB/MW/MH/MP/MM hold the active map descriptor; MC/MR are scratch coordinates. Those seven variables use **14 payload bytes**, plus their dictionary headers. A query changes MC/MR. There is one active descriptor: call MINIT again to select another map, and keep its storage alive while selected. Do not FORGET or overwrite words/data that the descriptor still references.

The global state makes this version non-reentrant. Do not interrupt a query with another one using the same variables. The words use the ROM's data and return stacks; they do not mask interrupts or own a frame clock. MSET temporarily saves an address with >R and balances it on every branch. EXIT is never used while that address remains on the return stack.

Measured on the stock ROM, the reusable definitions increase HERE by **448 bytes**. The room and FLAGS definitions add **63**, giving **511 dictionary bytes** in total. That includes their 40 data bytes and two CREATE headers. It excludes the demonstration/observer words, interpreter workspace and both stacks. The complete diagnostic still executes on the unexpanded 3 KiB machine, whose user dictionary and stacks share the upper 1 KiB. Space above HERE is not all free for map data.

Each query uses the ROM's multiplication plus bounds checks. Row-address tables would trade two bytes per row for avoiding that multiplication. Packed IDs could reduce map RAM at the cost of extraction and update code; decoded rooms or a changes overlay offer other choices. These are possible later variants, not implemented optimisations or measured frame rates.

## Run and adapt it

The native verifier boots the pinned stock ROM, enters the actual FORTH definitions through the keyboard, and executes **59 indexed operations per variant**. It reads every cell of the non-square room, rejects outside coordinates and invalid IDs, checks properties and world conversions, and verifies writes and the following guard. Each operation prints a distinct case number and recovers a value placed below its arguments. Stale output, an unfinished call or a stack leak fails the check.

The four runs cover the normal routine, the closed-exit customisation and both completed faults. Actual display bytes, full map/guard snapshots, dictionary measurements and source/tool/ROM identities are retained. CI decodes those observations and rejects altered records; fresh emulator execution remains a separate check. This establishes FORTH byte-map behaviour on **Emu198x 0.44.1**, not native drawing, a frame deadline or original-hardware behaviour.
