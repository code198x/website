Draw a door once and put it in two places. Open that shared picture, and both doors open. Change just one screen cell's number, and only that door changes. These routines let you choose which job you mean.

## Supply a source, slot and cell

Words are little-endian. `glyph_install` copies a contiguous range; `glyph_replace` copies one slot and ignores count. `glyph_select` writes one cell's code; `glyph_init` blanks all 2,048 font bytes and 768 name bytes.

| Offset | Supply or read |
| --- | --- |
| 0 | Word: readable CPU source pointer |
| 2, 3 | First slot and nonzero glyph count |
| 4 | Code to select |
| 5 | Word: linear cell index |
| 7 | Output: 1 accepted, 0 rejected |
| 8 | Output word: destination data bytes written |
| 10, 11 | Write data and control ports |

Inputs 0–6 and the two port bytes survive. Slots/codes are 0–255, cells 0–767 and install counts 1–255. A range ending exactly at 256 is valid; a zero count, overflowing range or invalid cell rejects before writing. Status and cost reset on rejection. Two calls can install all 256 pictures.

Keep the complete source readable and stable in CPU ROM or RAM, separate from `G`, with no address wrap or bank change. It is a trusted pointer; the component does not validate arbitrary mappings. Init/select ignore the source. The context is non-re-entrant. Calls clobber AF/BC/DE/HL/flags and need ten stack bytes including nested calls, plus your own callers and interrupts.

## Count rows, slots and places

An 8×8 sketch stores eight row bytes, bit 7 on the left. Row `10000001` is **129**. Slot 255 starts at `255*8 = 2040`, or $07F8; its final row is $07FF. The [Crates opening](/systems/sinclair-zx-spectrum/basic/crates/unit-01-draw-a-wooden-crate/) shows the same dots-to-byte arithmetic with another machine's upload rules.

At column 31, row 23, the cell index is `23*32+31 = 767`, at $1AFF. Cell 768 would run into other video data. For local dot (3,5) in cell (2,2), the screen pixel is `(2*8+3, 2*8+5) = (19,21)`. [Place a point](/craft/maths-for-games/unit-06/) explores those coordinate choices; [move a glyph](/craft/maths-for-games/unit-13/) compares shared character cells with drawing a label at any pixel.

## Own the video interface

Patterns occupy VRAM $0000–$07FF and names $1800–$1AFF. They are reached through ports, not through an invented CPU bitmap address. **Two control writes choose an address** before the data transfer. Coordinate every other VDP user for the whole call; an interrupt changing the latch can send bytes to the wrong place. These routines do not mask interrupts or change banks. DI does not mask a console NMI.

Graphics I shares a foreground/background colour byte among **eight slots**. Slot 7 uses $2000; slot 8 uses $2001. Replacing bits does not choose colours, and replacing one glyph does not select a new screen code. The complete caller sets white-on-black colours separately and owns its VDP configuration.

This caller reserves G at $7200, starts its stack at $7FF0 and uses an original 8,192-byte rom image. Its diagnostic buffer is only 256 bytes, so the test fits the selected 1 KiB CPU RAM on the two small-RAM consoles. That buffer is not required by a game calling the routine.

The component retains conservative fixed port spacing. The native check qualifies this emulator's selected default clock/video configuration. Physical access timing, accelerated CPUs, tear-free live animation and VBlank transfer budgets need their own measurements. A running-game upload queue is a useful next component.

## Replace a shared picture, or change one instance

Point G+0 at a new sketch, put 1 in G+2 and call `glyph_replace`: both cells containing code 1 show it. Put 2 in G+4, the first cell's index in G+5, and call `glyph_select`: the other cell keeps code 1.

## Pay for the change you need

Changing one cell writes **1 name byte plus 2 control bytes**. Replacing a glyph writes **8 pattern bytes plus 2 control bytes**. A 255-glyph upload writes 2,040 data bytes; init writes 2,816. G+8 counts data writes only. The control-byte counts follow the listing's address setup. These are amounts of work, not measured frame times.

The unchanged routine takes **205 code bytes**, plus the **24-byte context**. Reserve the 2 KiB font, 768-byte name table and eight source bytes per sketch separately. Reset setup, diagnostic machinery and ROM padding are excluded. Replacing one shared wall can save editing many cells; opening one door often calls for selecting a different code in one cell.

For larger screen changes, use [native map regions](/patterns/sord-m5/assembly/rendering/tile-region/). [Bitmap text](/patterns/cross-platform/rendering/bitmap-text/) solves a different job: drawing labels away from character-grid positions. Graphics II, pattern caches and four-plane Sega Mode 4 need their own contracts.

Cases cover shared replacement, single-cell selection, first/last slots, largest transfers, rejected ranges/cells, reset and reuse after reset. ## Make a larger character from four tiles

A score digit or a title can grow beyond one cell without a bitmap renderer. Prepare four ordinary 8×8 tiles, put them in four consecutive slots, and select them as a **2×2 character**. The VDP still draws its usual tiles; your picture now occupies 16×16 stored dots.

The two copies share their picture bytes, just as ordinary characters do." />

Run `python3 cross-platform/patterns/rendering/character-quads/prepare.py source.bin large.bin` with exactly eight source bytes. The result is **32 bytes**: top-left, top-right, bottom-left, bottom-right, eight rows each. The supplied original F and arrow are also checked in as assembler data:

Passing eight bytes to an upload declaring four patterns would read 24 bytes beyond your asset: the upload API trusts its source pointer. Keep all 32 bytes readable, non-wrapping and stable in the selected CPU bank.

Call **quad_select** directly in your own project. Set Q+0 to the first slot and the little-endian word Q+1 to the top-left cell. These three input bytes survive. Q+3 returns 1 for an accepted call or 0 for rejection; Q+4 returns four name data writes or zero. Q+5–7 are private. All G bytes survive placement, including the upload results and ports.

AF/BC/DE/HL/flags are clobbered. Reserve twelve stack bytes including the call, plus your caller/interrupt needs. The routine is non-re-entrant, changes no interrupt-enable or bank state, and needs the same exclusive VDP latch ownership as the upload component. A console NMI is not masked by DI. The reset fixture's mailbox and 256-byte readback buffer are verification tools, not requirements for a game.

Accepted origins have **column 0–30 and row 0–22**. The last is `22*32+30 = 734`, whose lower-right cell is 767. Column 31, row 23 and word indices outside the screen reject **before any VDP access**. First slot 252 is valid; 253–255 would run past slot 255 and reject. Both outputs reset even after a previous successful call. There is no clipping or automatic allocation. Install the four slots first; erase an old instance separately when moving one.

### Count tiles, names and work

Tile (tx,ty) uses code `first + ty*2+tx`; its screen cell is `origin + ty*32+tx`. Inside the 16×16 result, output dot (x,y) comes from source `(x div 2,y div 2)`. [Translation and character grids](/craft/maths-for-games/unit-13/) connects those local and screen coordinates; [integer division](/craft/maths-for-games/unit-06/) explains choosing the containing source cell. These are stored dots, not a promise of physically square pixels on every TV.

A prepared character needs **32 asset bytes and four pattern slots**, four times its eight-byte source. Upload once for **32 pattern data bytes plus two control bytes**. Each placement writes **four name bytes plus four control bytes**. Q+4 counts only name data; none of these counts is elapsed cycles or a frame budget. The placement adds **92 code bytes and eight RAM bytes** to the existing 205-byte upload component and its 24-byte context. Video setup, stack and diagnostics are additional. There is no runtime pixel resampling.

At most 64 disjoint four-tile characters fit before you reserve blank, UI and game tiles. A string API, non-consecutive tile sharing, banks, a VBlank queue and larger grid shapes need separately verified contracts. [Bitmap text](/patterns/cross-platform/rendering/bitmap-text/) offers arbitrary placement and other sizing choices at a different draw/storage cost. Keep ordinary one-cell text when it does the job cheaply.
