## Include the two operations

Include `scroll.inc` once and supply four bytes: `scroll_x`, `scroll_y`, `nametable` and `ppu_ctrl_shadow`. Y is 0–239 and nametable is 0–3. `scroll_right` increments X and flips only the horizontal nametable bit when X wraps from 255 to zero. A and flags change; the other registers survive.

<CodeFromFile src="nintendo-entertainment-system/patterns/assembly/rendering/nametable-scrolling/scroll.inc" lang="asm" title="Advance a camera and apply its PPU scroll" />

`set_scroll` resets the shared address/scroll write latch, writes X and Y, then combines the nametable selection with the other settings in `ppu_ctrl_shadow`. It changes A and flags. Call during vblank, after all `$2006/$2007` writes; those writes use the same internal state and would otherwise disturb scroll.

Cartridge wiring matters. This caller uses vertical mirroring, giving `$2000` and `$2400` separate physical tables for a 512-pixel-wide world. Horizontal mirroring aliases those two addresses. Four logical nametable addresses do not guarantee four independent screens of RAM.

## Publish a whole picture

Main computes the next scroll state and builds OAM while `ready=0`, then sets `ready=1` last. NMI transfers that finished OAM page, applies the matching scroll snapshot and clears ready. Main waits for that acknowledgement before changing it again. NMI saves A/X/Y and leaves the previous picture alone when no update is ready.

```asm
    ; Main owns the state only after acknowledgement.
    jsr scroll_right
    jsr build_oam
    jsr advance_priority
    lda #1
    sta ready
```

This protocol lets main take more than a frame without publishing half a picture. It does not make slow logic faster. NMI owns DMA and scroll; the caller owns NMI, all OAM, palettes, CHR and both nametables. DMC and audio servicing are absent from this example.

## The complete cartridge

`make` in the source folder creates `build/demo.nes`. The scene boots without external firmware. The new background is deliberately finite and repeating: both nametables are filled once with rendering off. Reset to leave.

The [OAM builder](/patterns/nintendo-nes/assembly/rendering/multi-sprite-oam/) deliberately submits twelve objects at the same Y. The PPU can display only eight sprite entries on one scanline. Changing OAM order shares which ones drop out; it does not raise that capacity.

## Beyond the two prepared screens

[Column feeding](/patterns/nintendo-nes/assembly/rendering/column-feeding/) adds new tiles as the camera crosses tile boundaries. It must also merge palette attribute quadrants without destroying their neighbours, and account for DMA, audio and other VRAM writes in the same vblank. That entry remains illustrative; this cartridge does not implement an endless map streamer.

Useful later versions include a fixed status panel, vertical scrolling, a camera dead zone and a bounded VRAM-update queue. Keep camera policy and display service separate so a different scrolling game can reuse the low-level code.

Register and sprite behaviour is documented in Ricoh's *RP2C02 development specification* (KA-A002-B), sections on CTLR0, SCC and object evaluation; the [NESdev register reference](https://www.nesdev.org/wiki/PPU_registers) provides an accessible register-by-register account.
