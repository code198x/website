Load the NTSC NROM cartridge. The background colour advances with the update counter. Hold controller 1 A to add excessive CPU work; release it to restore the normal update pace.

## Use the wait in your project

Call `initialise_clock` before enabling NMI, then `wait_frame` once per update. A/X/flags change. NMI owns `frame_clock`; main owns `last_frame` and `frame_delta`. The ISR changes no general register and RTI restores flags. The helper accepts a single captured clock value, preventing one frame from being consumed repeatedly.

## Start the complete example

Reset disables rendering, DMC, APU channels and the frame IRQ, clears writable RAM and waits through PPU warm-up. It initialises the clock before enabling NMI. NMI only increments `frame_clock`: it does not read controls, update the game or draw. Reset to leave.

With Asm198x available, keep the sample folders together and run:

```sh
make -C nintendo-entertainment-system/patterns/assembly/framework/game-loop
```
The Amiga Makefile also needs Build198x. Open the generated file under build using the machine’s normal loading route.

The loop keeps four jobs visible: wait, read input, update state, draw. `expensive_work` is an optional CPU workload to expose missed deadlines; remove it when building your own game. The changing colour or digit is a small observable result, not a rendering engine.

## What happens when work runs late

Both clocks are bytes: keep the gap between samples below 256 frames. The returned delta records missed announcements, but the sample deliberately runs one update instead of an unbounded catch-up loop. Rendering is off, so its palette writes are not a template for unrestricted PPU writes during a rendered game. OAM DMA, buffered nametable work and their VBlank budgets belong in the next composition.
