A score need not live on the character grid. Put a number above an enemy, centre a room name or slide a message into view. These entries give you the code to draw a fixed-width glyph or counted string into your bitmap, using a font and memory you own.

## A cell, its ink and its advance

<Figure src="/images/patterns/glyph-translation.svg" kind="image" rendering="smooth" alt="An eight-by-eight glyph cell at origin (21,37), with local dot (3,5) translated to screen (24,42), and the next cell starting at X29" caption="Moving the origin moves every dot by the same amount. Blank columns still occupy part of the eight-pixel advance." />

A glyph is eight row bytes. Bit 7 is leftmost. Translate local pixels by the cell origin, clip against an exclusive scissor, then draw foreground runs with the existing span routine. Transparent mode preserves zero bits; opaque paints each clipped cell background before its foreground.

The API accepts signed origins −512..511 and counted strings up to 255 codes. No terminator, newline handling or wrapping is hidden inside it. Unsupported codes use an explicit fallback. Blank or clipped glyphs still advance by eight. [Move a glyph, keep its shape](/craft/maths-for-games/unit-13/) works through the maths with actual screen positions.

## Choose how much work to buy

The original optional 64-glyph font costs 512 bytes. Ten digits need only 80. A full 256-glyph contiguous font needs 2,048. These are font-data choices; the sample design is original MIT-licensed Code198x work, not a ROM extraction.

| Ten-code PIXEL TEXT | Transparent X24 / X31 | Opaque X24 / X31 |
| --- | ---: | ---: |
| Spectrum, BBC, Dragon | 77 / 77 byte writes | 157 / 237 |
| CPC MODE 1 | 90 / 84 | 250 / 324 |

These are observed destination stores, not cycles or a cross-machine speed ranking. Glyph gaps matter as well as cell alignment. Opaque drawing revisits foreground bytes after its background spans. This simple composition reuses a checked renderer; a dedicated masked glyph blitter could do less work.

For a character-grid display, [Spectrum character printing](/patterns/sinclair-zx-spectrum/assembly/rendering/character-printing/) or [writable characters](/patterns/cross-platform/rendering/custom-glyphs/) may be the right tool. For bitmap text, [masked sprites](/patterns/sinclair-zx-spectrum/assembly/rendering/masked-sprites/) show KEEP/image composition, while [pre-shifted phases](/patterns/cross-platform/rendering/pre-shifted-sprites/) trade asset space for draw-time work. Amiga's existing word-aligned sprite paths offer another comparison; the [Amiga text component](/patterns/commodore-amiga/assembly/rendering/bitmap-text/) now supplies an independently checked CPU path with a distinct 32-bit-pointer context.

Proportional widths, scaling and paragraph layout can build on a clear glyph/advance contract later. The current component reserves 96 text bytes plus the backend's 48, owns no game loop and changes no interrupt policy. The machine pages spell out the display and stack obligations.

Across the five fixtures, **397 calls completed**, with full bitmap/source/guard comparisons and selected native-image comparisons. Ten completed faulty builds were detected. Read each entry's evidence and limits before changing its display allocation or OS integration.


## Make the letters bigger

The four span-backed implementations above now include a selectable integer-enlarged renderer. Each original font pixel becomes a rectangle: factors 2×2 turn an 8×8 cell into 16×16; 3×2 makes it 24×16. X and Y factors are independently 1..4. The font still stores eight bytes per glyph.

Keep the existing machine backend, original font and 96-byte T/48-byte BP allocations. Include either bitmap-text or scaled-text, set both additional scale inputs at T+68/+69, then call text_char or text_string. Counted source, fallback, pens and physical scissor stay explicit. The advance is now `8×scaleX`; glyph height is `8×scaleY`. These direct calls do not make the existing eight-pixel layout wrappers scale-aware.

Each entry includes the original and changed-scale callers, a native wrong/fixed advance example, exact code/work costs and captures. A large bitmap font is not a new character mode: BBC retains zero-page BP and scanline tables, Spectrum attributes remain separately owned, Dragon fields are big-endian, and CPC retains packed four-pen pixels. Equal enlargement factors preserve native pixel proportions rather than correcting non-square physical pixels.

The independent oracle samples source coordinates with integer division, while the native routines scale foreground runs and repeat rows. [Division and remainders](/craft/maths-for-games/unit-06/) explain sampling; [local-to-screen coordinates](/craft/maths-for-games/unit-13/) explain placement before clipping. A partially clipped glyph keeps its sampling phase.

Larger cells paint more pixels. Compare the same W! workload across scales in each entry; byte crossings and repeated row work differ by backend. Span/write counts are not cycle timings. Pre-rendered sizes, pre-shifted/masked glyphs and precomposed character cells offer other CPU/asset trade-offs. Fractional sizes, shrinking, flips, rotation and scale-aware layout remain further variants.
