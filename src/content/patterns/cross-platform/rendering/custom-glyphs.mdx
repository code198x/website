A character does not have to be a letter. It can be a wall, a door, a brick or a piece of a larger picture. Give that picture a slot number, and the screen can use it in many places.

The byte-indexed components have `glyph_init`, `glyph_install`, `glyph_replace` and `glyph_select`. Sega Mode 4 uses `pattern_` entries and a word-sized context, preserving its ninth pattern-index bit. The entries show how to reserve the context, establish video, include the real code and call it. They preserve differences in colour and access; an identical calling name does not make hardware identical.

## Picture, number, place

Install a picture in slot 1. Put code 1 in two cells. Replacing slot 1 changes both cells; selecting code 2 in only one cell leaves the other alone. That can make a wall change everywhere, or make one door open, depending on which operation you choose.

A single cell selection writes one name byte, or two on Sega Mode 4. A glyph replacement writes eight bytes on Ace, Oric, Atari, C64, VIC and the seven TMS targets, sixteen on DMG/NES, or thirty-two on Sega Mode 4. Every TMS port also needs two control-port writes to choose its VRAM address. The native checks exercise both operations, compare the complete pattern/name memory and check their visible effects independently.

## Turn the sketch into bytes

Eight dots have weights 128, 64, 32, 16, 8, 4, 2 and 1. Row `10000001` is therefore 129: light the two outer dots. Stack eight such rows to make an 8×8 glyph. DMG adds a second bitplane, so two bits choose a palette index for each pixel.

[Crates](/systems/sinclair-zx-spectrum/basic/crates/unit-01-draw-a-wooden-crate/) turns a sketch into four user-defined characters. The same powers-of-two arithmetic applies to these machines, with different upload rules. At cell (2,2), local dot (3,5) becomes screen pixel `(2*8+3, 2*8+5) = (19,21)`. [Place a point](/craft/maths-for-games/unit-06/) explores the coordinate idea further.

These routines handle fixed-grid character pictures. They do not implement proportional text, arbitrary pixel placement, scaling or a running-game upload queue. Fixed-ROM systems such as PET and Aquarius also need a different route: screen codes can select existing ROM pictures, but cannot upload new ones into ROM. A software bitmap or writable display mode is a different capability to investigate, not something to hide behind a common API.

For a pixel-addressed display, [pixels and boxes](/patterns/cross-platform/rendering/pixels-and-boxes/) starts with individual bits. For map-to-screen transfers, use [native regions](/patterns/cross-platform/rendering/tile-region/).

For labels away from the character grid, [bitmap text](/patterns/cross-platform/rendering/bitmap-text/) supplies callable fixed-width glyph/string routines on five qualified displays. It draws into bitmap memory rather than redefining shared character cells.

The six additional TMS callers reuse the MSX include unchanged, with **24 calls per target** and independent full 16 KiB VRAM/native-picture checks. SVI-328 has separate data read and write ports; ColecoVision and SG-1000 fit the diagnostic buffer into their small RAM allocations. Shared silicon does not replace separate execution or make a Sega Mode 4 pattern a one-bit glyph.

The [Ace](/patterns/jupiter-ace/assembly/rendering/custom-glyphs/), [Oric](/patterns/oric-atmos/assembly/rendering/custom-glyphs/) and [Atari XL](/patterns/atari-800/assembly/rendering/custom-glyphs/) show why stored slots and selectable codes differ. Ace/ANTIC 2 use 128 shapes with inverse forms. Oric's lower codes are serial attributes rather than pictures; its six-dot rows and reserved screen columns need their own placement maths. The Ace capture uses the explicitly identified corrected emulator build, not an unchanged release.
