Put a picture address, width and position in a list, and MARIA fetches the dots for you. Your CPU can get on with something else. The price is a different kind of budget: headers and picture bytes must fit into each scanline's DMA time.

## Include, initialise, append

Copy `objects.inc` and include it once. Set `ML_CAPACITY` to 1..31. Reserve **10 private zero-page bytes** at `ML` ($80 here), and a **page-aligned RAM list** of `4*capacity+2` bytes. The caller uses four slots: 18 bytes at $1900. These allocation rules are trusted preconditions; the routine does not validate arbitrary RAM pointers.

Put the list pointer at ML+0/1 and call `maria_begin`. It resets count at +7 and writes a two-byte terminator. It does not erase the old tail. Then supply a graphics pointer at +2/3, byte width at +4, palette at +5 and logical x at +6. Call `maria_append`; +8 returns 1 accepted or 0 rejected. This maintained example includes a right-edge fit and a rejected overrun:

Widths are 1..31 bytes; palette is 0..7; x is 0..159. A row must fit visibly: `x+4*width<=160`. Its source bytes must stay within one page: `low-address+width<=256`, including an exact end at the boundary. This API rejects rather than clips or wraps. Full capacity also rejects. Every check precedes any list write; rejection preserves the list and count.

ML+0..6 survive. The routine owns count +7, status +8 and scratch +9. Begin again when changing the list pointer. A/X/Y/flags are clobbered; clear decimal mode and reserve two stack bytes per direct call, plus caller/interrupt depth. Keep the context in valid zero-page RAM and out of 6532 RAM. Do not share a live context between interrupts and foreground code. The helpers change no interrupt, video, bank or DMA state.

## Own the zone and the data

A direct header has four bytes: graphics low address, palette/negative width, graphics high address, horizontal position. Width two encodes as 30 in the low five bits. In 160A, four 2-bit pixels fit in a byte. Zero is transparent; a palette supplies three nonzero colours.

The caller supplies a 48-byte DLL at $1800, a populated list at $1900 and an empty list at $1920. Its sixteen zones each use OFFSET=15: sixteen rasters. Only zone 3 selects the populated list. MARIA adds the descending OFFSET to the graphics address's high byte, so row zero lives at base+15*256 and row fifteen at base. **Adjacent visible rows are a page apart in memory.**

This simple fixture spends 16 pages to hold one eight-pixel-wide shape with 32 useful bytes. Several shapes can share the unused columns. The original A uses only colour 1 and transparent zero; the selected palette also initialises colours 2 and 3. The builder supports all eight palette numbers, but it does not choose or initialise your colours.

The complete caller disables DMA, copies the DLL into RAM, builds the lists, sets palettes and both nonadjacent display-pointer registers, waits for VBlank, then enables normal 160A DMA. The lists stay immutable afterwards. This is an original 48 KiB reset cartridge, without commercial BIOS authentication. It does not demonstrate that boot path.

For animation, build an inactive list/DLL and publish it during VBlank, coordinating both pointer writes and interrupts. That publisher is outside this component and has not been verified here. Writing a header while MARIA fetches it risks displaying an unfinished object. The DLL, zones, palettes, DMA mode, graphics lifetime and bank state need one coordinated owner.

## Count work, not just objects

The builder is **121 code bytes**. Context takes 10 bytes; four slots take 18 RAM bytes; the DLL takes 48 and the empty list two. Each append writes four header bytes and two terminator bytes. The populated list occupies ten bytes for two objects and its terminator.

Each populated raster fetches two four-byte headers, a two-byte terminator and four graphics bytes. That repeats for sixteen rasters. Empty zones still have DMA setup, termination and shutdown work. Four is this caller's allocation capacity, not a hardware object limit.

Atari's *7800 Software Guide*, Appendix 3, uses **7.16 MHz cycles**: eight per four-byte header and three per direct graphics byte, plus startup and shutdown. Startup ranges from 5–9; shutdown from 4–7, or 10–13 at a zone end. These clock and accounting boundaries differ from CPU instruction timing and other MARIA specifications. The retained measurement is list/data workload, not an exact elapsed-DMA benchmark. Wider rows, indirect data and more headers cost more time even when they fit in RAM.

## Connect the coordinates

For local x, byte index is floor(x/4) and the shift is `6−2*(x mod 4)`. At object x32, local pixel x3 appears at logical x35. The native capture doubles horizontal pixels and starts the active area at capture x27: the first object's left edge is x91. Its selected zone appears at capture y50. These observed viewport offsets belong to the capture, not the reusable game API.

[Place a point](/craft/maths-for-games/unit-06/) connects local, object and screen coordinates. [Move a glyph](/craft/maths-for-games/unit-13/) connects row packing with stored shapes. The page-stepped rows add another useful distinction: a picture's visible geometry and its storage stride can be very different.

Indirect character maps, 320-pixel modes, holey DMA, arbitrary vertical movement, priority composition and split objects deserve separate contracts. A display-list builder alone is not a framebuffer or a general line/circle/text renderer. [The 2600 playfield kernel](/patterns/atari-2600/assembly/rendering/playfield-kernel/) shows why even closely related consoles need different reusable components.

## What was verified

Asm198x 0.0.71 and released Emu198x 0.41.0 execute this NTSC direct 160A reset caller. Every native frame pixel and each populated header/terminator byte are compared with independent expected results. Seven rejected native calls preserve the surrounding 256-byte list page, including full capacity and page overflow. Guards and completed CPU markers are checked. Completed wrong-width and wrong-position controls fail the same destination/image checks. The website's pinned Asm198x 0.0.65 also assembles it.

This does not establish stock BIOS loading, original-hardware timing, live publication, every palette/mode or a maximum-load benchmark.
