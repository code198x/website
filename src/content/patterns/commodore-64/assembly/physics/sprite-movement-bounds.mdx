## Move the sprite

This example puts a white 24×21-pixel sprite on a black screen. Use **joystick port 2** to move it. Hold a direction and it reaches the edge, then stays there. Move diagonally and both coordinates change. Release the stick and the sprite stops.

The movement rule takes two pixels per update and clamps each coordinate to its permitted range. If Y=51 and you move up, the proposed position is 49, so the result is **50**. Rejecting that step would leave a one-pixel gap; clamping reaches the edge.

## Run it

Use the maintained samples checkout, keeping its folder structure. The demonstration reuses the setup routine and shape from [Hardware Sprites](/patterns/commodore-64/assembly/rendering/hardware-sprites).

```sh
git clone https://github.com/code198x/code-samples.git
cd code-samples/commodore-64/patterns/assembly/physics/sprite-movement-bounds
make
```

`make` uses Asm198x to produce `build/demo.prg`. Load it in a PAL or NTSC C64 emulator, type `RUN`, and map your controls to port 2. Reset to leave.

The standalone program takes over the screen, VIC bank, sprites, CIA port directions and interrupt masks. It maps out BASIC and KERNAL and does not return to BASIC. It is not a subroutine you can drop into a program that still relies on those services.

The caller reads `$DC00` once per update. Its direction switches are active low, so `EOR #$FF` turns pressed switches into set bits. Both CIA1 ports are configured as inputs and keyboard scanning is disabled. That ownership matters when combining joystick code with a keyboard reader.

## The movement contract

`move_sprite` takes pressed direction bits in **A**: up=1, down=2, left=4, right=8. It reads and updates `sprite_x_lo`, `sprite_x_hi` and `sprite_y`, then writes sprite 0's VIC position. It changes A and flags, preserves X and Y, and keeps its input in `joy_state`.

Call with the processor in binary arithmetic mode (decimal flag clear). State must start inside **X=24..320, Y=50..229**, inclusive, with X's high byte equal to 0 or 1. The routine assumes a normal-size sprite and the display window set up by this caller.

Opposite directions cancel on their axis. Up+down therefore leaves Y alone; left+right leaves X alone. A diagonal applies both axes, moving two pixels horizontally and two vertically. It covers more distance than a straight move; there is no diagonal speed normalisation. Fire does nothing here.

## Crossing X=255

The VIC-II splits a sprite's X coordinate between a low-byte register and a bit in `$D010`. Moving right from 254 gives 256: the low byte becomes 0 and the high bit becomes 1. Moving left from 256 gives 254: the borrow clears that high bit again.

`update_sprite_pos` clears only bit 0 of `$D010`, then inserts sprite 0's high bit. Bits 1–7 belong to the other sprites and remain unchanged. The routine also leaves their positions, colours and modes alone. The caller must exclude a competing writer during the read/modify/write; preserving bits does not make the sequence atomic.

## Inclusive screen bounds

These are sprite coordinates for the normal 40-column, 25-row window:

| Axis | Visible coordinates | Sprite size | Last fully visible origin |
|------|---------------------|-------------|---------------------------|
| X | 24 through 343 | 24 pixels | `343 - (24 - 1) = 320` |
| Y | 50 through 249 | 21 lines | `249 - (21 - 1) = 229` |

An origin plus `size - 1` gives the final occupied coordinate. That is why the lower bound includes Y=229, rather than stopping at 228. Expansion or a different display window needs different bounds.

## One update per frame

The caller polls the raster and updates below the displayed area, after the sprite has been drawn. Its frame counter and register snapshot make progress observable to the verifier. This is a small polling loop with exclusive hardware ownership, not an interrupt-driven game framework.

Two pixels **per frame** means about 100 pixels per second on PAL and 120 on NTSC for straight movement. Keeping the same speed per second would require a separate regional timing policy. This example preserves the simple frame-based rule.

## Trade-offs

| Aspect | Cost or limit |
|--------|---------------|
| Code | 160 assembled bytes for the movement routine, excluding the caller and sprite setup |
| State | Four bytes for X low/high, Y and the sampled direction mask |
| Display | A 64-byte sprite block plus its pointer; sprite DMA still takes CPU bus time |
| CPU | Work depends on the selected directions and clamping path; no measured cycle bound is claimed |
| Movement | Normal-size sprite 0, fixed bounds, two pixels per update; diagonals and PAL/NTSC have the speed differences described above |

## What has been checked

The [verification recipe](https://github.com/code198x/code-samples/tree/301cb16b1ee2df7f5d6d383ae22dd45bf9807966/commodore-64/patterns/assembly/physics/sprite-movement-bounds) compares Asm198x and ACME output, then executes **6,144 arithmetic/register cases** across Emu198x and VICE on PAL and NTSC. It covers both sides of every boundary, odd and even coordinates, X=255/256, all direction/fire combinations and preservation of seeded high bits belonging to other sprites.

A separate sequence drives the emulator control ports and checks **48 captures**, including held input, release, both X-byte transitions, corners, diagonals and opposite directions. It reads state first, then releases the controls for one unchanged frame before checking every lit pixel in the completed picture. Injected direction-mask tests alone do not establish joystick wiring.

The old listing's boundary failures are reproduced, and deliberately removing a clamp fails the same observer. These are configuration-specific emulator checks, not physical joystick or original-hardware tests.
