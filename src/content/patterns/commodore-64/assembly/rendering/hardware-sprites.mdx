The [recorded checks](https://github.com/code198x/code-samples/blob/daacb295441b54fc239b63c6229347308ec18dd2/commodore-64/patterns/assembly/rendering/hardware-sprites/verification/results.json) identify the tested sources and observations. They establish these cases on those configurations; original-hardware checks are separate.

## A sprite on screen

Run this example and a white **24×21-pixel outline with a central cross** appears at VIC-II coordinates X=160, Y=120 on a black screen. The VIC-II draws it from its shape data while the CPU runs an observation loop.

The C64 has eight hardware sprites. Each has a position, colour and shape pointer. The CPU does not paint their pixels into the background, but display is not free: **sprite DMA takes bus time from the CPU**. Moving or recolouring a sprite also requires CPU writes.

## Run it

Save these three files together: `demo.asm`, `sprite.inc` and `shape.inc`. Assemble the demonstration, load the resulting PRG in a PAL or NTSC C64 emulator, and type `RUN`:

```sh
asm198x --dialect acme --prg demo.asm -o demo.prg
```

Reset to leave. This standalone demonstration takes over the screen, VIC bank, sprites and interrupt setup. It maps out BASIC and KERNAL and does not return to BASIC.

Try changing `DEMO_X` to 296 and rebuilding. That position needs X bit 8 as well as its low byte. `DEMO_Y` is the raster coordinate, not a row counted from the top of the text area. Leave `SHARED_SEED` at zero for the demonstration; the verifier uses it to check ownership of the shared registers.

## The routine's contract

`sprite0_show` takes the X position's low byte in **A**, its high bit (0 or 1) in **X**, and raster Y (0–255) in **Y**. It changes A and flags and preserves X and Y. It expects I/O visible, VIC bank 0 (`$0000–$3FFF`), screen RAM at `$0400`, and the complete shape at `$2000`.

The routine owns sprite 0. It sets white, normal size, single-colour mode and foreground priority, then enables the sprite. It preserves bits 1–7 of the shared sprite registers, so it does not disable or change the modes of sprites 1–7.

<CodeFromFile src="commodore-64/patterns/assembly/rendering/hardware-sprites/sprite.inc" lang="6502" />

The caller must exclude competing writes while these read/modify/write sequences run. Preserving bits does not make an interrupted update atomic. The demonstration initialises once; calling midway through display can expose a partly updated position or mode. Raster-safe movement is a separate timing problem.

## All 21 rows

Each row uses three bytes: 24 bits, most significant bit first. A set bit draws the sprite's colour; a clear bit leaves the background visible. This shape has a border and a central cross. The loops supply repeated rows, so all 63 bytes are present.

<CodeFromFile src="commodore-64/patterns/assembly/rendering/hardware-sprites/shape.inc" lang="6502" />

The final byte pads the shape to a 64-byte block. It is not a twenty-second row. In the caller, the following blank block supplies transparent shapes for the other sprites during verification.

## Trade-offs

| Aspect | Cost |
|--------|------|
| CPU | Setup and movement writes; the VIC-II composites pixels, but sprite DMA takes CPU bus time |
| Memory | 63 shape bytes in a 64-byte-aligned block, plus one screen-relative pointer per sprite |
| Limitation | Eight hardware sprites, each 24×21 pixels before expansion; more visible objects need reuse or software drawing |

**When to use:** Players, enemies, bullets and cursors that move independently of the background.

**When to avoid:** Large or numerous moving areas. Reusing sprites further down the screen needs a schedule such as the [two-band multiplexer](/patterns/commodore-64/assembly/rendering/sprite-multiplexing); it cannot create unlimited overlapping sprites on one raster line.

## Sprite registers

All live in the VIC-II at `$D000`. For sprite *n*, replace the index:

| Register | Purpose |
|----------|---------|
| `$D000 + 2n` / `$D001 + 2n` | X / Y position |
| `$D010` | X bit 8 (one bit per sprite — X positions 256–511) |
| `$D015` | Enable (one bit per sprite) |
| `$D027 + n` | Colour |
| `$D01D` / `$D017` | Expand X / Expand Y (double width / height) |
| `$D01B` | Priority — set bit *n* to draw the sprite *behind* the background |
| `$D01C` | Multicolour select (one bit per sprite) |
| `$D025` / `$D026` | The two shared multicolour sprite colours |

## The pointer is a block number

A sprite pointer is a 64-byte block number **relative to the selected 16 KB VIC bank**:

```
pointer = (shape address − VIC bank base) / 64
```

Here the bank starts at `$0000` and the shape at `$2000`, so the pointer is `$80` (128). Shape addresses must be aligned to 64 bytes and accessible to the VIC-II in that bank. The CPU's memory map alone does not tell you what the VIC-II will fetch.

The eight pointers occupy screen base + `$3F8` through `$3FF`: `$07F8–$07FF` with the screen at `$0400`. Moving the screen moves its pointer table; changing the VIC bank changes where the same pointer value fetches its shape.

## Multicolour sprites

Setting a sprite's bit in `$D01C` switches it to **multicolour** mode: pixels are read in pairs, giving four colours (transparent, the two shared colours in `$D025`/`$D026`, and the sprite's own colour) at half the horizontal resolution — 12 fat pixels instead of 24. The trade is colour for detail, and it's how most C64 game characters were drawn.

## What has been checked

The [source and verification recipe](https://github.com/code198x/code-samples/tree/daacb295441b54fc239b63c6229347308ec18dd2/commodore-64/patterns/assembly/rendering/hardware-sprites) compares Asm198x and ACME output, then checks five positions in Emu198x and VICE on PAL and NTSC: **20 captures**. It checks every lit pixel and guest register snapshots, including the X=255/256 boundary, colour, shape and preservation of the other sprites' shared bits. Removing the ninth X-bit update must fail the picture check. These observations do not measure DMA cost or establish multicolour, expansion or original-hardware behaviour.
