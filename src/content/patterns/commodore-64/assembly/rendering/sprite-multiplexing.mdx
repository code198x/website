## Sixteen sprites from eight

Run this example and you get eight solid sprites near the top of the screen
and eight outlines further down. The same eight hardware sprites draw both
bands. Once the VIC-II finishes the upper band, a raster interrupt changes
their positions, pointers and colours before the lower band starts.

This is a complete **two-band multiplexer** for a PAL or NTSC C64. Each band
holds zero to eight unexpanded, single-colour sprites. The fixed spacing makes
the timing easy to inspect before attempting a scheduler for freely moving
sprites.

## Run it

Save these two files together, assemble `demo.asm`, load the PRG and type `RUN`:

```sh
asm198x --dialect acme --prg demo.asm -o demo.prg
```

The upper band starts at raster Y=64; the lower band starts at Y=176. Each
sprite is 24 pixels wide and 21 lines high. The two rightmost positions exceed
255, so both bands exercise the ninth X bit in `$D010`.

## The IRQ and its tables

<CodeFromFile src="commodore-64/patterns/assembly/rendering/sprite-multiplexing/multiplexer.inc" lang="6502" />

`mux_counts` contains one count for each band. Try changing `8, 8` to `4, 6`.
The first eight entries of each sprite table belong to the upper band, and the
next eight belong to the lower band. `mux_xhi` holds zero or one for each X
coordinate. Each pointer selects a 64-byte sprite block in VIC-II bank 0.

The handler uses two indices: twice the slot number for the interleaved X/Y
registers, and the slot number for colour and pointer writes. It rebuilds the
whole `$D010` mask each time, clearing high bits that belonged to the preceding
band. It also rebuilds `$D015`, so reducing a count disables unused sprites.

Zero skips the table loop. A count above eight disables that band and sets
its `mux_errors` byte; it cannot read beyond the eight entries. The next valid
count clears the error. Each IRQ saves and restores A, X and Y; `RTI` restores
the interrupted flags.

## Why the timing fits

| Band | Setup IRQ | Sprite lines | Observed final write |
|------|----------:|-------------:|---------------------:|
| Upper | 32 | 64–84 | 45 |
| Lower | 144 | 176–196 | 158 |

Those final-write lines were measured with all eight sprites enabled in
Emu198x and VICE, on both PAL and NTSC configurations with display DMA active.
The setup finishes 19 or 18 lines before drawing starts. The earlier band has
also finished before its registers are reused. The IRQ does not need to land
on one exact CPU cycle for this deliberately generous schedule.

The [maintained source and verification recipe](https://github.com/code198x/code-samples/tree/main/commodore-64/patterns/assembly/rendering/sprite-multiplexing)
compares Asm198x output with ACME, checks every visible sprite pixel, and tests
counts 0, 1, 7, 8, 9 and 255, separate empty bands, and an 8→0→8 transition.
Removing the X-high-bit write makes the picture check fail. These are emulator
observations, not measurements from an original C64.

## What the example owns

The demo takes over the machine. It selects VIC-II bank 0, screen `$0400`,
ordinary 40-column text and RAM interrupt vectors, disables CIA interrupts,
and owns the raster IRQ and all sprite registers. Sprite data occupies
`$2000` and `$2040`. It does not return to BASIC or share interrupt ownership
with a cartridge or another raster handler.

A foreground routine may change a count with a single-byte write; the next
IRQ for that band picks it up. Keep the descriptor tables unchanged while the
multiplexer runs. Updating a whole moving-sprite list would require a separate
publication scheme so the IRQ cannot see half an update.

Keep the fixed Y positions, unexpanded sprites and IRQ lines together. This
example does not handle arbitrary Y positions, more than eight overlapping
sprites, expansion, or sprites that cross the bottom of the frame. A general
multiplexer must schedule around those cases; sorting by Y alone does not
make an impossible overlap fit.
