## Include it, then draw a box

Reserve **48 bytes at BP**, in zero page at $70. Define PIXEL_WIDTH/HEIGHT as 320/200, and PIXEL_BYTE_STEP as 8. Include `6502.inc` once and retain the complete caller’s bitmap_lo/hi row tables. Code, stack, tables, BP and the bitmap must not alias. Scratch needs no initialisation; public request fields do.

After the named display setup, this is a normal direct call. The excerpt stops before the diagnostic marker/mailbox; your game does not need those stores.

Read BP+9: one means accepted, zero rejected. Change the fields and call again. There is no retained drawing list or game loop inside the component.

## The calling contract

Words use **little-endian** order. Origin is top left, Y downwards. Call `bp_pixel`, `bp_read`, `bp_hspan`, `bp_vspan`, `bp_fill` or `bp_box`.

| BP offset | Supply or read |
| --- | --- |
| 0,2 | Unsigned x0,y0 words |
| 4,6 | Exclusive x1,y1 words |
| 8 | Operation 0 set, 1 clear, 2 XOR; read requires 0 |
| 9 | Accepted 1, rejected 0 |
| 10 | Stored read bit 0/1; otherwise 0 |
| 11 | Ignored and preserved |
| 12–39,42–47 | Private scratch |
| 40 | Output word: destination-byte stores |

Pixel/read ignore both ends; hspan ignores y1; vspan ignores x1. Fill and box use [x0,x1)×[y0,y1). A box [5,13)×[20,24) is eight pixels wide and four high. The effective rectangle must be ordered, nonempty and inside 320×200; invalid requests reject before destination writes, with zero read/write outputs. Public inputs 0–8 and 11 survive.

This is strict rejection rather than clipping. Intersect with your display before calling if you want partially visible shapes. An outline visits a shared corner once, including a 1×1 box; XOR therefore leaves its corner visible instead of toggling it twice.

## A bitmap still has character-sized colour cells

The caller selects VIC bank 0, the bitmap at $2000 and screen memory at $0400, with D011/D016/D018 establishing **standard HIRES bitmap** mode. Pixels are 320×200, but screen RAM now supplies colour pairs for 8×8 areas:

- High nibble: the colour of a stored one.
- Low nibble: the colour of a stored zero.

The fixture sets every screen byte to $10, giving white ink and black paper. These colours come from **screen RAM**, rather than colour RAM in this mode. The routine edits only bitmap bits. Set, clear and read do not select an arbitrary colour: another cell's colour pair could make the same stored bit look different.

`address = $2000 + (y div 8)*320 + (x div 8)*8 + (y mod 8)`

At (13,20), that is **$228C**, mask **$04**. Use PIXEL_BYTE_STEP=8 and the 400-byte scanline tables. The picture uses 8,000 bytes in an 8,192-byte reservation; all **192 tail bytes** remain untouched. The 1,024-byte screen reservation remains unchanged too.

The caller owns CPU-port mapping, CIA2 bank selection, sprites, interrupts and colours. BP is $70; the mailbox is $0800, outside the screen colours. Its KERNAL, BASIC and character images are original diagnostic data, not vendor firmware. Multicolour bitmap, character-backed drawing and hardware sprites have different representations and costs; they are useful alternatives, not extra pen values for this API.


## Division chooses a byte; remainder chooses a bit

At X13, `13 div 8 = 1` picks byte-column one and `13 mod 8 = 5` picks its sixth pixel. With bit 7 leftmost, `128 >> 5 = 4`. OR sets the mask, AND with its inverse clears it, and XOR toggles it. Replacing the byte with just $04 would erase seven neighbours.

[Place a point](/craft/maths-for-games/unit-06/) explains the origin and local/screen distinction. [Draw with integer error](/craft/maths-for-games/unit-12/) shows how points and spans build curves. A qualified primitive does not automatically qualify those higher-level adapters on this display; their machine entries name their own evidence.

## What it costs, and what to try next

A 32×8 fill takes **32 byte stores at X24 and 40 at X25** on this backend. Full-display fills take 8,000 stores. Spans protect their two edges and write full interior bytes, avoiding repeated per-pixel work. These are observed destination stores, not elapsed cycles or a frame-budget promise.

The backend assembles to **537 bytes**, plus 400 bytes of row tables and the 48-byte context. Reset setup, bitmap, stack and assets are additional. The row tables spend storage to avoid deriving the complete display address during every call. A character-backed or sprite display may fit a game's actual job better than painting bitmap shapes.

Clobbers A/X/Y/P. **Decimal mode must be off on entry**; the caller uses CLD during setup. Reserve a conservative **64-byte stack budget** beyond your other calls/IRQs. BP is non-re-entrant. The routine changes no interrupt enables, acquires no OS display and synchronises no video access. Your caller owns that integration.

## What was verified

**173 calls completed** using Asm198x 0.0.71 and native Emu198x 0.39.0 in the stated original reset configuration. Every call compares the complete bitmap allocation, guards, public inputs, acceptance/read and byte-store counts with an independent selected-pixel model. Cases cover every horizontal phase, set/clear/XOR/read, tiny and full rectangles, last pixels, row boundaries, rejected declarations and aligned/unaligned fills. Selected whole native frames match independently composed images.

All 192 bitmap tail bytes and 1,024 screen bytes are preserved. Wrong-mask and wrong-row executables each complete accepted calls and fail both memory and picture checks. Retained records bind exact source/tools and have evidence-corruption failure tests. Stock-OS loading, original-hardware timing and tear-free coexistence remain separate checks.
