A single door picture can appear in many places. Replacing it changes every cell using its number. Changing one cell's number affects only that instance. Here is reusable code for both jobs.

## Include, initialise and call

Reserve **24 private zero-page bytes** at `G`. Clear decimal mode, include the machine's component and establish the caller-owned video configuration before calling `glyph_init`.

Init clears the owned patterns and names. It destroys their old contents; call it during your setup, not before every tile change. The complete caller establishes the video state. Then install two original sketches and put the first in two cells:

To replace both instances, point the source at a new sketch, set first=1 and call `glyph_replace`. To change only one cell, select code 2 there. Games call these entries directly; the later mailbox and readback buffer are optional verification transport.

## The calling contract

Words are little-endian. `glyph_install` uploads a range, `glyph_replace` uploads one picture and ignores count, `glyph_select` changes one name. Status and data-write count reset on every call, including rejection.

| Offset | Supply or read |
| --- | --- |
| 0 | CPU source address, word |
| 2, 3 | First slot and nonzero count, bytes |
| 4 | Selected code, byte |
| 5 | Linear cell, word |
| 7 | Output: 1 accepted, 0 rejected |
| 8 | Output: destination bytes written, word |
| 10–23 | Private scratch |

Valid slots/codes are **0–255**, cells **0–999**. Counts are bytes, **1–255**; an exclusive range end of 256 is legal. Zero counts, overflowing ranges and invalid cells reject without destination writes. Use multiple calls to install all 256 pictures.

Keep the source readable, stable, long enough, non-wrapping and separate from the context and destination. These are trusted pointers, not a memory sandbox. The context is non-re-entrant. Inputs 0–6 survive; A/X/Y and flags are clobbered. Reserve six stack bytes including the direct call. Add space for your own calls and interrupts.

## Respect the display

The caller selects VIC bank 0 with CIA2, $D018=$18, $D011=$1B and $D016=$08. Pictures occupy **$2000–$27FF**, names **$0400–$07E7**. A character number is a screen code, not PETSCII. The component preserves the 24 padding bytes after the names and the separately owned colour RAM at $D800–$DBFF. Set high-resolution colours yourself; multicolour changes what the bits mean.

The original reset caller uses CPU mapping $37 and blank RAM. It supplies its own pictures; it does not copy a ROM font or keep BASIC/KERNAL running. The stock-ROM wrapper below keeps the standard letters while adding private pictures. Your project must reserve the same RAM and avoid another renderer, OS or interrupt using it.

## Turn a sketch into stored pixels

Each picture has eight bytes, one row per byte, bit 7 on the left. Row `10000001` is 128+1 = **129**. Slot n, row r lives at `$2000+n*8+r`. Slot 255 begins at $27F8 and ends at $27FF.

For cell (2,2), the index is `2*40+2 = 82`. Dot (3,5) within it appears at screen pixel `(2*8+3, 2*8+5) = (19,21)`. The colour byte belongs to that cell, while the shared picture belongs to its slot.

[Move a glyph](/craft/maths-for-games/unit-13/) connects these bit weights and cell indices with text drawing. [Place a point](/craft/maths-for-games/unit-06/) covers local-to-screen coordinates. These routines place fixed-grid pictures; they do not provide proportional text or arbitrary-size letters.

## Pay for what changes

A single name costs **1 destination byte**; replacing a picture costs **8**. Full init writes **3,048 bytes**. The assembled component takes **238 code bytes** and 24 context bytes; each source picture takes 8 bytes. These exclude the reset caller, video setup and assets.

If many cells use one picture and all should change, a replacement can save writes. If one door should open, change its name. These are storage and data-write counts, not elapsed time. Colour updates are separate work. Measure inside your actual game before promising a frame rate. Upload queues, caches and alternate allocations are useful further components.

## What was verified

**20 calls completed per build** with Asm198x 0.0.71 and Emu198x 0.39.0. Checks compare complete font, names, padding and colour RAM, guards, inputs, status and actual destination-write counts. They cover shared replacement, single-cell selection, last slots/cells, maximum uploads, zero/overflow requests and reset.

Selected whole native frames match a separate compositor. Completed **wrong-slot** and **wrong-name** builds fail both memory and visible-output comparisons. Retained checks independently rederive the expectations; corruption tests reject rehashed wrong memory and pictures. Colour RAM is read by CPU code into a private buffer; debugger reads intentionally show underlying RAM.

This is an original reset fixture, not proof of stock-OS loading, interrupt coexistence, hardware timing or tear-free live updates. Palette RGB values describe the pinned emulator release. Code and source pictures are MIT licensed.

## Keep the standard letters and add your own pictures

You do not have to redraw an alphabet to add a door or a character. `glyph_init_rom` copies one 2 KiB half of the machine's character ROM into the existing $2000 font allocation. Then use the same `glyph_install`, `glyph_replace` and `glyph_select` routines above. Unchanged letters retain their familiar shapes; every cell using a replaced slot changes together.

The new `rom-demo.asm` is a **stock-ROM-loaded PRG**, separate from the original reset-ROM fixture. Load it and RUN. The first Fire press and release installs an original sketch in slot 1 and selects it in cells 82 and 83. The next Fire press replaces that sketch in both cells; holding the button adds no further replacement. `rom-custom.asm` chooses the lowercase ROM half. This is a standalone takeover program and stays in its own loop.

### Include and call the ROM initializer

Define G as 24 private zero-page bytes, ROM_WRONG=0 for the working initializer, and include `glyphs.inc` followed by `rom-init.inc`. Keep the code, context and stack below $A000. Supply **A=0 or 1** for the ROM half and **X=your known $01 output-latch shadow**. After the call, G+7 is accepted/rejected and G+8/9 is the destination-byte count, as with the other glyph routines. Inputs G through G+6 survive; A/X/Y change. The caller's processor flags, including decimal and interrupt state, are restored.

The wrapper requires the three banking DDR bits to be outputs and KERNAL to be already banked out. It checks those conditions and that the shadow matches the port's output bits before making any destination writes. It cannot discover an incorrect shadow for a pin configured as an input: keep the real latch shadow yourself. Reading $01 is not a substitute for that shadow.

**Own NMI handling too.** Disable CIA2 NMI sources and provide a safe RAM NMI vector and handler before calling. The handler must tolerate I/O being hidden. SEI only masks IRQ; it does not mask NMI. This wrapper keeps KERNAL out so the RAM vector stays visible. It is not an OS-friendly routine that can borrow arbitrary BASIC/KERNAL state and return safely.

The temporary mapping selects character ROM rather than the VIC/SID/CIA registers. The exact caller-supplied latch value is restored afterwards; $00 is untouched. The initializer writes **2,048 font bytes**, without clearing the screen or colour RAM. Configure VIC bank 0 and the $2000 font as in the complete caller. See the [Commodore Programmer's Reference Guide, memory management](https://www.commodore.ca/manuals/c64_programmers_reference/c64-programmers_reference_guide-05-basic_to_machine_language.pdf) for the bank-control port.

### Why the screen must survive

The old blank-font initializer fills names with code zero. Doing that with a copied ROM font would fill the screen with @ characters. This variant deliberately leaves every name alone. The caller fills its screen with **screen-code 32** spaces, adds its caption and later selects the two original sketches. Screen codes and PETSCII still have different jobs.

### Common error: copying I/O instead of ROM

The wrong build changes one immediate mask from 1 to 5, leaving CHAREN set. The bounded copy completes, but reads I/O-register values rather than the alphabet. Its status and 2,048-byte write count alone cannot prove success. Comparing the full private native font with the selected ROM half catches the error; the native image shows damaged letters. The repaired PRG is byte-for-byte identical to the working PRG.

Restoring an all-RAM CPU mapping also hides I/O. The boundary fixture checks exact restoration, then explicitly selects its I/O-visible map before reading the next joystick handshake. Restoring ownership is not the same as choosing a mapping suitable for the caller's next operation.

### Customisation, cost and evidence

Choose ROM half 0 or 1; change the installed slot and eight source bytes to suit your picture. Reserve slots carefully: replacing a letter also changes every occurrence of that letter. Move the fixed RAM font allocation only by adapting the existing component and VIC configuration together. Proportional text, arbitrary positions, multicolour and a different VIC bank need different allocation/rendering choices.

The wrapper adds **102 code bytes**, uses the existing 24-byte context and copies 2,048 bytes during setup. The complete stock-ROM PRG is 780 bytes including its two-byte load address. One later shared replacement still writes only eight bytes. This is startup work, not a claim that a whole font fits your VBlank budget. The wrapper needs eight stack bytes including its direct call and nested copy helper; allow more for the surrounding caller and any interrupts.

Five native runs on Emu198x 0.44.2 with Asm198x 0.0.72 verify stock-PRG identity before RUN, both ROM halves, untouched screen, complete private font comparison, shared install/replacement, held input, guards and native pixels. A separate six-case guest caller checks invalid half, banking DDR, shadow mismatch, KERNAL visibility, all-RAM restoration and the lowercase half, including preserved decimal/interrupt/carry flags. Nineteen corruption controls reject altered evidence, including a coupled wrong displayed glyph. Complete licensed ROM/font dumps remain private; the retained evidence records hashes and only the few glyphs visible in each capture. This does not establish arbitrary interrupt coexistence or physical-hardware timing.
