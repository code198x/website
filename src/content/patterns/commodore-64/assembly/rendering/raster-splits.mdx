## Split the background

The example shows a black upper background and a blue lower background. It uses two raster interrupts per frame: one near the top to restore black, and one to select blue farther down.

The VIC-II requests an interrupt when its raster counter matches the programmed value. The CPU still has to enter the interrupt, run the KERNAL prologue and reach our colour write. **The compare line and the visible colour change are different events.** In this caller, compare line 130 gives a first blue displayed line of **131**.

## Run it

```sh
git clone https://github.com/code198x/code-samples.git
cd code-samples/commodore-64/patterns/assembly/rendering/raster-splits
make
```

`make` uses Asm198x to produce `build/demo.prg`. Load it in a PAL or NTSC C64 emulator and type `RUN`. Reset to leave.

The caller selects a normal 40-column, 25-row text display, clears it to spaces and disables sprites. It owns the screen, VIC bank, colours, IRQ vector and CIA interrupt masks. KERNAL ROM stays mapped, but its normal keyboard scan and software clock service are no longer called. There is no BASIC return or RESTORE-key interface.

## The interrupt routine

Call `split_init` with IRQs masked, KERNAL and I/O visible, CIA2 sources disabled and the display already configured. It changes A and flags, preserves X and Y, and leaves IRQs masked. The caller executes `CLI` when ready.

<CodeFromFile src="commodore-64/patterns/assembly/rendering/raster-splits/split.inc" lang="6502" />

Four connections make this work:

1. **KERNAL entry.** The ROM IRQ prologue saves A, X and Y before jumping through the RAM vector at `$0314`/`$0315`. Our handler exits through `$EA81`, which restores those saved registers and returns from the interrupt. This pairing requires the expected C64 KERNAL ROM; it is not a direct hardware-vector handler.
2. **Exclusive interrupt ownership.** Writing `$7F` to CIA1's `$DC0D` disables its interrupt sources; reading the register acknowledges pending ones. The caller also disables and acknowledges CIA2 sources. Do not enable another IRQ source or execute `BRK` while this handler owns the vector.
3. **Raster comparison.** Writing `$D012` sets the low eight compare bits; reading it returns the current line. Bit 7 of `$D011` has the same distinction for bit 8. Both scheduled lines here are below 256.
4. **Acknowledgement.** Writing 1 to bit 0 of `$D019` clears the raster interrupt latch. Writing `$01` to `$D01A` enables only that VIC interrupt source.

The handler reads the current line to choose the region, changes `$D021`, then schedules the other interrupt. This assumes prompt service: masking IRQs across a split or adding a long handler can miss the intended schedule. `$D021` changes the background behind the spaces; it does not change the border colour in `$D020`.

## Where the change appears

The verification runs the same caller with four compare values. These are **observations of this program**, not general latency guarantees:

| Compare line | First visible blue pixels | First fully blue display line |
|--------------|---------------------------|-------------------------------|
| 64 | 65 | 65 |
| 130 | 131 | 131 |
| 131 | Part-way across 132 | 133 |
| 200 | 201 | 201 |

Both emulators and both video standards produce these row ranges. The numbers are hardware raster lines, not screenshot rows or sprite Y coordinates.

With this display's vertical scroll setting, line 131 is a **badline**: the VIC-II fetches a row of screen pointers and stalls the CPU. The extra delay moves the colour write farther across the following line. The remaining pixels on that line become blue; pixels already drawn stay black.

Foreground instruction timing can also vary the horizontal position of a write. These sampled frames do not measure the full jitter range under arbitrary workloads. Enabling sprites, changing the display mode or moving code can alter timing too.

## Trade-offs and alternatives

| Aspect | Cost or limit |
|--------|---------------|
| Code | 81 assembled bytes for setup and handler, excluding the caller and KERNAL routines |
| State | No private handler state; two diagnostic bytes in the caller |
| CPU | Two interrupts per frame, including CPU entry, KERNAL work and possible DMA stalls; no universal cycle bound is claimed |
| Timing | A delayed, unstabilised register write; no guarantee of a fixed horizontal edge |
| Ownership | Exclusive raster IRQ use; normal KERNAL keyboard and clock servicing is suspended |

Use this approach to learn mid-frame register changes or create regions where the exact horizontal transition is unimportant. A fixed score panel above a scrolling playfield also needs separate screen/scroll configuration and careful scheduling; changing the background alone does not build that panel.

For a static display, [polling in the basic game loop](/patterns/commodore-64/assembly/framework/game-loop-basic) is simpler. For several colour bands, a handler can advance through line/colour pairs, provided each next compare is installed before its deadline. The verified example here has only two regions.

For an edge that must land at a fixed horizontal position, use a [stable raster](/vault/techniques/stable-raster) technique with a measured, model-specific schedule. Adding a few `NOP`s alone does not remove unknown interrupt-entry delay.

## What has been checked

The [verification recipe](https://github.com/code198x/code-samples/tree/ffec9e93b5c1a537b91aeb67b4b26a81fd386421/commodore-64/patterns/assembly/rendering/raster-splits) compares Asm198x and ACME binaries and checks **48 captures** of the maintained example, plus 12 captures of the original listing. It checks frame progress, A/X/Y preservation and every coloured pixel, including the partial-line transition. Fixed capture origins account for each emulator's border crop. Emu198x runs normally after debugger observations to emit a fresh frame; a live colour-change control verifies that refresh and reproduces the stale debugger-only image.

Twelve deliberately broken captures replace the blue write with black; the same picture observer rejects all of them. The observations establish the displayed result under the stated conditions, not the exact CPU bus cycle of the write or behaviour on every C64 revision.
