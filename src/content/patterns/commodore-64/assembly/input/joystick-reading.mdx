The [recorded checks](https://github.com/code198x/code-samples/blob/f67d4aeb6921d5fefa87b529f996c20bf39de211/commodore-64/patterns/assembly/input/joystick-reading/verification/results.json) identify the sources and observations. A separate reverse-keyboard-scan discrepancy is recorded below; these checks do not establish complete keyboard coexistence or original-hardware behaviour.

## See held controls and new presses

The example displays one row for each joystick port. White blocks under **U D L R F** show which controls are held. **NEW FIRE** counts presses in hexadecimal: hold Fire and the number stays still; release and press again and it increases.

These are different questions. Movement usually needs “is Left held?” A menu action often needs “was Fire newly pressed?” Sampling the same closed switch every frame should not automatically mean a new press every frame.

## Run it

```sh
git clone https://github.com/code198x/code-samples.git
cd code-samples/commodore-64/patterns/assembly/input/joystick-reading
make
```

`make` uses Asm198x to create `build/demo.prg`. Load it in a PAL or NTSC C64 emulator, type `RUN`, and configure joystick controls for either port. Release keyboard keys while using the joysticks. Reset to leave.

The standalone program owns the screen, CIA1 port directions and latches, CIA1 timer controls and CIA interrupt masks. It maps out BASIC/KERNAL and disables keyboard scanning. It does not return to BASIC or preserve the normal keyboard service.

The caller polls once per video frame. The hexadecimal counters wrap from `FF` to `00`. Their purpose is to make press/hold/release behaviour visible.

## Read the five switches

The joystick switches are active low: a closed switch reads as 0. The reader inverts the byte and masks it with `$1F`, returning only the five pressed bits.

| Bit | Value | Control |
|-----|-------|---------|
| 0 | 1 | Up |
| 1 | 2 | Down |
| 2 | 4 | Left |
| 3 | 8 | Right |
| 4 | 16 | Fire |

The case-labelled **port 1** is CIA1 port B at `$DC01`. **Port 2** is CIA1 port A at `$DC00`. The upper three bits are not part of this direction/fire result.

Call `joy_init` once with I/O visible, keyboard scanning stopped and timer outputs on CIA1 PB6/PB7 disabled. It configures both ports as inputs, leaves released values in their output latches and clears the six state bytes. `joy_poll` then reads each port once. Both routines change A, X and flags and preserve Y.

<CodeFromFile src="commodore-64/patterns/assembly/input/joystick-reading/joystick.inc" lang="6502" />

`joy1` and `joy2` contain the held bits. Opposite directions remain separate bits; the reader does not decide whether movement cancels them, prioritises one or rejects the combination. [Sprite Movement with Bounds](/patterns/commodore-64/assembly/physics/sprite-movement-bounds) makes that choice in its movement rule.

## Find a new press

`joy1_new` and `joy2_new` use **current AND NOT previous**. A bit appears when it changes from released to pressed. Continuing to hold it produces no further new-press bits; releasing and pressing again produces another.

The first poll compares against released state. Starting with Fire already held therefore counts as a press. Resetting this software state while the button remains held has the same policy. A game that requires release before accepting input would need a different initialisation rule.

This edge rule is not physical switch debouncing. Contact bounce can produce several sampled transitions, and an entire press/release between samples can be missed. The example also provides no automatic menu repeat. PAL and NTSC sample at their respective frame rates.

## Share the CIA deliberately

The joysticks and keyboard share CIA1 pins. Writing `$7F` to `$DC00` while its bits are outputs drives keyboard column 7 low; it does **not** disable scanning. In the recorded probes, holding `1` then looks like joystick-1 Up, and holding Space looks like Fire, with no joystick pressed. Both emulators reproduce these cases on PAL and NTSC.

This caller releases both port drivers and keeps keyboard scanning stopped. That prevents the program from selecting a keyboard column during its reads. It cannot disconnect the physical keyboard: held keys can connect shared lines, including lines grounded by another control. The demonstrated operating condition is therefore **joystick input with keyboard keys released**.

If a program also needs a keyboard reader, agree who owns the port directions, output latches and interrupt timing, and verify that combined configuration. A routine that temporarily borrows the ports must restore the state expected by its owner; writing one constant is not a universal isolation trick.

## Costs and limits

| Aspect | Cost or limit |
|--------|---------------|
| Code | 100 assembled bytes for initialisation and polling, excluding the caller and display routines |
| State | Six bytes: two held masks, two new-press masks and two fire counters |
| CPU | Two CIA reads per poll, plus state and counter work; elapsed time also depends on VIC-II bus contention |
| Timing | One sample per frame; short pulses may be missed |
| Ownership | Exclusive CIA1 port use, with keyboard scanning and timer port outputs disabled |

For continuous movement, use the held masks. For one action per sampled press, use the new-press masks. Keep repeat timing and physical debouncing as separate policies with their own requirements.

## What has been checked

The [verification recipe](https://github.com/code198x/code-samples/tree/f67d4aeb6921d5fefa87b529f996c20bf39de211/commodore-64/patterns/assembly/input/joystick-reading) compares Asm198x and ACME output. It checks all 32 masks on each port, simultaneous controls and hold/release/repress history against an independent calculation. The matrix gates input sampling for observation; a separate run executes the unchanged once-per-frame demonstration.

The matrix provides **412 state/display checks** across the two engines and video standards. Together with the unchanged demonstration, the runs check **48 native captures** of the input indicators. Emu198x receives input events through normal execution; VICE uses simulated external control-port pins. Deliberately breaking the previous-state mask must fail the held-fire check.

Held-key probes use Emu198x key events and VICE keyboard-matrix snapshots, with selected-column reads as controls. They expose one **remaining Emu198x discrepancy**: with PB1 driven low, PA configured as input and Return held, VICE sees PA0 low but Emu198x does not. A forward scan detects Return in both engines, confirming that the key event arrived. This reverse-scan case is marked as a mismatch in the record. It is outside the standalone caller's configuration and prevents a claim of complete keyboard/joystick parity.
