The background changes as updates advance. Hold Fire on physical joystick port 2 and a deliberately long CPU loop slows those changes. Release it and the caller returns to one update per display frame in the tested scene.

## Use the wait in your project

Call `wait_frame` once per update with A5 unchanged. D6 and condition codes change; other registers survive. It clears the pending VERTB request, then polls for a newly asserted one. No interrupt handler may consume that same request. Clearing old pending work is deliberate: this helper waits for a new boundary rather than treating a stale request as another update.

## Start the complete example

Boot the ADF on the tested A500 OCS PAL/Kickstart 1.3 configuration. The caller disables custom interrupts and DMA, sets A5 to `$DFF000`, configures the Fire input and owns the background colour. It takes the machine over; it does not restore Workbench. Reset to leave.

With Asm198x available, keep the sample folders together and run:

```sh
make -C commodore-amiga/patterns/assembly/framework/game-loop
```
The Amiga Makefile also needs Build198x. Open the generated file under build using the machine’s normal loading route.

The loop keeps four jobs visible: wait, read input, update state, draw. `expensive_work` is an optional CPU workload to expose missed deadlines; remove it when building your own game. The changing colour or digit is a small observable result, not a rendering engine.

## What happens when work runs late

The request is a latch, not a count of every missed frame. Slow work reduces update frequency and the loop does not catch up. This is one hardware-owning approach; Flock also explains a two-phase beam-position wait. Neither is an AmigaDOS-friendly scheduling API. Other models, regions, display arrangements and DMA loads need their own qualification.
