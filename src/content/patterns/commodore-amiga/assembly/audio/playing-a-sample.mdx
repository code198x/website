## Four registers and a switch

The Amiga has four audio channels. Each one has an 8-bit digital-to-analogue converter fed by DMA: the custom chips fetch sample words from chip RAM by themselves. To start a channel, we tell it where the sample is, how long it is, how fast to play it and how loud. Then we switch its DMA on. The channel then repeats the sample until we switch it off.

This example targets a **PAL Amiga 500 with Kickstart 1.3**, started from its own boot disk. It uses channel 0. To change that channel safely, the program has to own it. Here, it takes over the whole machine.

## The routine's contract

Before calling `play_sample`, put the custom-chip base `$DFF000` in **A5** and the sample's address in **A0**. Put its length **in words** in **D0**, the period in **D1** and the volume in **D2**. The routine writes the four channel registers, then sets the master and channel-0 bits in `DMACON`. It changes no registers.

The sample must be in **chip RAM**, starting on an even address. Audio DMA reads only chip RAM, and it fetches one word, two 8-bit signed samples, at a time. So the length is the number of bytes divided by two. Volume runs from 0 to 64: 64 is full level, and 32 is 6 dB quieter.

`AUD0LC` and `AUD0LEN` are read once at the start of each pass. When the length runs out, the channel goes back to the same location and plays the sample again. That repeat is the normal behaviour, not something we set up.

Channel 0 must be off when we call `play_sample`. A channel that is switched off for less than two sample periods may carry on where it stopped instead of starting again. The demo waits a whole frame between tones.

## Period is not pitch

`AUDxPER` is the number of colour clocks between output **samples**. It is not a note. On a PAL machine the colour clock runs at 3,546,895 Hz, so the period sets the sample rate:

```
sample rate (Hz) = 3546895 / period
tone (Hz)        = 3546895 / (period × samples per cycle)
```

The pitch we hear depends on how many samples make up one cycle of the waveform. Our 16-byte sine at period 424 plays 8,365 samples a second, which is 523 Hz. The demo plays three tones a second apart:

| Waveform | Period | Sample rate | Tone |
|---|---|---|---|
| 16 bytes per cycle | 424 | 8,365 Hz | 522.8 Hz |
| 16 bytes per cycle | 212 | 16,731 Hz | 1,045.7 Hz |
| 32 bytes per cycle | 212 | 16,731 Hz | 522.8 Hz |

Halving the period raises the tone by an octave. Doubling the samples per cycle at the same period brings it back down. The Hardware Reference Manual's note table uses the same arrangement: with a 16-byte cycle, PAL period 212 gives a C at 1,045.7 Hz.

A recorded sound works the same way. Play it at the rate it was recorded and it sounds at its original pitch. A tracker's note names are a separate convention: they depend on how each instrument sample was tuned.

The period has limits. Below 123 on PAL (124 on NTSC), DMA cannot fetch the next word in time, and the channel reuses old samples. The manual recommends 124–256 for single-cycle waveforms like these, using a different sample for each octave, to keep aliasing noise down.

<Question prompt="A 32-byte single-cycle waveform plays at period 424. What tone should we hear?">

3546895 / (424 × 32) is about 261.4 Hz, an octave below the demo's first tone. Doubling the samples per cycle halves the tone, just as doubling the period does.

</Question>

## What it costs

Each channel fetches at most **one word per scan line**, in one of four time slots set aside for audio in every line. That word holds two samples, so a channel can output at most two samples per line. The 68000 uses only the even-numbered bus cycles, and Abacus's *System Programmer's Guide* places the audio slots among the odd cycles reserved for DMA. So audio DMA does not take the processor's time.

The verification check measures this in Emu198x. A polling loop running from chip RAM completed the same number of passes in ten frames with no DMA as with all four channels fetching at period 124. As a control, six low-resolution bitplanes cut the count by about a quarter. That is an emulator observation, not a measurement on hardware.

The CPU still does some work. It writes the registers to start each sound. Anything beyond a steady repeat needs more: changing sounds, stopping after one pass, or joining waveforms. That means responding to the channel's interrupt. Paula can also be fed a word at a time without DMA, but the manual describes that as processor-intensive and does not recommend it.

With every interrupt and DMA channel off, nothing else can change channel 0, its `DMACON` bit or its interrupt. The demo never returns to AmigaDOS. The manual's own audio example makes the same assumption of exclusive access. It says that example will not work directly in a multitasking system.

A program that keeps the operating system running should instead allocate channels through `audio.device`, which shares them between programs, and use only the ones it is given.

## Looping, and playing once

Each time the channel copies `AUD0LC` and `AUD0LEN` into its working registers, it requests the channel-0 audio interrupt (`INTREQ` bit 7). The first request comes as soon as DMA starts, before the first sample is heard. After that, a request comes as **the last word of each pass starts playing**, not at the start of the next pass. At each request, the values just copied are in use, so we can write the next location and length without disturbing the current pass.

The check measures this with the demo's 16-byte sample at period 424. One pass is 8 words × 2 samples × 424 = 6,784 colour clocks. The first request arrived 164 colour clocks after the `DMACON` write. The second arrived 5,908 later, close to the 5,936 that seven words take. Later requests came about 6,784 apart, within one scan line.

To play a sound once, write a silent one-word sample's location and a length of 1 when the **first** request arrives. The sample plays through, then the channel repeats silence. In the check, an eight-cycle burst played exactly eight cycles this way. [One-Shot Samples](/patterns/commodore-amiga/assembly/audio/one-shot-samples) builds this into an interrupt handler.

## Left and right

Paula's four channels are mixed onto two stereo outputs, two channels each. Primary sources disagree about which pair reaches which jack. The Hardware Reference Manual's audio chapter gives one assignment, while its own connector description and Abacus's guide give the reverse. Until a recording from a real machine settles it, this pattern makes no left/right claim.

## Run the complete example

Assemble and master a boot disk with the maintained files side by side:

```sh
asm198x --dialect vasm --exe demo.asm -o demo
build198x adf demo -o demo.adf --volume Sample --name demo
```

Boot `demo.adf` on a PAL A500 configuration with Kickstart 1.3. After AmigaDOS starts the program, the screen turns blue and the three tones play for about a second each. The screen turns green when they finish. Amiga emulators take a few seconds to boot from disk.

Change the first tone's `424` to `428` and it drops to about 518 Hz. Change any `moveq #64,d2` to `moveq #32,d2` and that tone plays 6 dB quieter.
