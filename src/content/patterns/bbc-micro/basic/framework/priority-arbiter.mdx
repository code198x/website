A pickup sound and a death sound may be requested in the same update. If only one can play, decide which request wins before touching the sound hardware. This small selector works just as well for choosing a message, animation request or another single shared resource.

## Include and initialise

Combine the numbered routine with your caller, reserving lines **3000–3200**. Call **3000 once before a batch of requests**. It clears F/I/P/R/A/O/E. F says whether a winner exists; I holds its ID and P its priority. Callers may use IDs and priorities from 0 to 255. Zero is a valid ID and priority, so F must distinguish no request from request zero.

Spectrum uses GO SUB, while C64 and BBC use GOSUB. Keep END, STOP or an explicit jump before the helper. The supplied build.py combines numbered files and rejects duplicate lines; it does not depend on a BASIC MERGE command.

## Submit and read

Put a request ID in R and its priority in A, then call **3100**. A larger priority wins. O=1 means this request became the winner; O=0 means the previous winner remains. **An equal priority keeps the first request.** After all producers have submitted, check F and use I to dispatch the winner once. Do not dispatch every time O=1 or lower-priority work may already have escaped before a later request wins.

E=1 rejects damaged F/I/P state and E=2 rejects an invalid request. Numeric IDs and priorities must be integral 0–255; F must be exactly zero or one. Invalid calls clear O but preserve the winner. An empty selector can contain stale I/P, but F=0 means the next valid request wins regardless of those stale values.

## Ownership and customisation

The helper owns F/I/P/R/A/O/E, with no private loop scratch. It does not own sound channels, sprites or messages. This selects one winner, not one winner per channel; use a separate state set for each independently arbitrated resource. Rename all references and line numbers for a second instance. The diagnostic's W/Z/G and Y/D are not required by a game.

The custom caller changes the game-chosen priority values while keeping the same ordering and tie policy. Agree on priority bands across producers: for example, reserve a higher range for events that must interrupt ordinary feedback. The actual numbers have no built-in meaning. Reordering producers can change the winner of a tie, so make that ordering deliberate. To prefer the last equal request, change the comparison and add tests/captures that establish that different contract.

## Mistake and repair

The wrong caller initialises before **each** request. Every request looks like the first, so the last low-priority request wins. Both saved checks become 0,0: the winner's ID and priority are wrong. The selector itself is obeying the empty-state contract.

The repair initialises once at the batch boundary and retains state through all submissions. Its source and loaded tokenised program match the working caller.

## Costs and alternatives

Each request takes constant scalar work and a comparison; a batch of N requests is O(N). It stores a winner instead of an entire queue. That loses information deliberately: if every request must eventually run, use an event queue or priority queue. A long-running sound also needs its own rule for whether a new batch may interrupt it; this selector has no playback timer. [The Craft](/craft/) helps choose what deserves precedence; [Maths for Games](/craft/maths-for-games/) connects stable maximum selection to ordering and ties.

## Machine and measured size

This helper uses scalar variables and needs no array allocation. Its diagnostic uses MODE 7 and HIMEM=&6000 to separate program storage, mailbox and screen. The helper itself changes neither mode nor HIMEM.

The numbered helper occupies **318 tokenised program bytes** on this interpreter, including line headers. This excludes the caller, test tables, numeric scalar/array storage, interpreter stacks and ROM. Tokenised size is not machine-code size or a hardware-cycle count. No real-time or whole-game performance budget is inferred from the diagnostic. The caller's W/Z/G, Y/D and RAM mailbox are observation machinery, not required game state.

## Execution evidence

Working, custom, deliberately wrong and exact repaired callers executed through BBC Micro's stock BASIC interpreter under Emu198x 0.44.2. Build198x 0.2.9 tokenises C64 PRG and Spectrum TAP programs. C64 enters stock RUN, Spectrum uses ROM tape loading, and BBC enters every numbered source line through MOS/BASIC. Actual loaded program bytes, complete state packets, positive completion/count/guards and visible result pixels are checked. Firmware is not distributed.

An independent mathematical/order model checks the trace and rejects altered source, configuration, loaded program, state, completion and image evidence. Host exhaustive checks complement the native boundary/sequential examples; those host ranges are not claimed as natively exhaustive.
