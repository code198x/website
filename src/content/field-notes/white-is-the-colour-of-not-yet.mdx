I was capturing a Paula audio unit headless — no window, just the emulator running a disk for a fixed number of frames and dumping the result. The capture came back blank. White screen, flat silence, a copper list that appeared to be doing nothing. Every symptom of a program that had crashed on load or never set up its display at all. I read it as a dead unit and started looking for the bug.

There was no bug. I'd photographed the machine before it woke up.

## The thirty seconds before anything

An Amiga booting from disk does plenty of unglamorous work before a single instruction of *your* program runs. Kickstart initialises, hands off to the bootblock, the bootblock loads the executable, the executable finally starts. Headless, at PAL rates, that whole chain takes something like **1,500 frames — roughly thirty seconds** — before the program you care about has drawn or played anything. Capture at 200 or 300 frames and you haven't captured your program failing. You've captured the machine still clearing its throat.

The screen is white in that window for a reason that makes the trap worse: `COLOR00`, the background register, hasn't been set yet, and its uninitialised state reads as white. So the blank frame isn't neutral grey static that announces "nothing here yet" — it's a confident, fully-painted white screen that looks exactly like a program which cleared the display and then died.

## Same disk, same code

The unit I thought was dead was a Paula tone in one of the sound units. At frame 300 the audio buffer was flat and the copper looked inert — silent, dead, broken. I gave the same disk the frames it needed and captured again at 1,500. Clean ±8151 square wave. Copper running exactly as written. Nothing about the disk had changed; nothing about the code had changed. The only variable was whether I'd let the machine finish starting before I decided it had failed.

That's the whole trap in one comparison. Two captures of an identical system, one reading "dead" and one reading "correct," and the difference is entirely in the number 300 versus 1,500.

## The most ambiguous signal there is

The reason this one bites is that a blank screen is the single most overloaded state a machine can be in. It is *simultaneously*:

- the program crashed on load,
- the program is running but drew nothing (a genuine copper or init bug),
- and the program hasn't started yet.

You cannot tell those three apart by looking, because they render the same pixels. Eyeballing a headless capture — the natural instinct — is precisely the method that can't distinguish "broken" from "not yet." So the fix isn't a sharper eye, it's two habits. First, **give the machine its full boot budget before you believe a blank result** — default the capture window to ~1,500 frames and only shorten it once you've seen the program appear. Second, **measure, don't gaze**: sample the audio buffer's amplitude, read the pixel colours out of the frame, check `COLOR00` for a value the program would have written. A number tells you which of the three states you're in. A glance never will.

## "Broken, or just not done?"

This isn't an Amiga quirk so much as the Amiga making a universal question physical. "Is it broken, or is it just not finished yet?" is the most expensive question in any asynchronous system, and it's everywhere the moment things stop being instant: a request that's slow versus one that's failed; a job that's queued versus one that's dead; a container mid-boot versus one that's crash-looping. The wrong move is always the same — treating *latency* as *failure* and killing the thing a second before it would have succeeded. The Amiga just puts a number on the cost of that mistake. Twelve hundred frames of confident white screen, and the machine was fine the whole time.
