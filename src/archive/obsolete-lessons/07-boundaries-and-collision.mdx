# Collision Detection: Making Things Interact
**The heart of game mechanics**

Collision detection brings your game to life - it's what makes a sprite bounce off walls, collect items, or get hit by enemies. The C64 provides hardware collision detection that's fast and accurate. Today you'll master both hardware collision and boundary checking to create complete game interactions.

Think about it: every game you've ever loved depends on collision. Mario jumping on enemies. Pac-Man eating dots. Space Invaders hitting your shields. The C64 makes this fundamental game mechanic effortless through dedicated hardware that automatically detects when sprites overlap - something that required complex calculations on other computers.

## What You'll Build

A complete collision system with:
- Hardware sprite-to-sprite collision
- Sprite-to-background collision
- Screen boundary detection
- Collision response (bouncing, collecting, destroying)

This is where your game becomes real!

## Hardware Collision Detection

The VIC-II chip automatically detects collisions between sprites and backgrounds - you just need to read the registers! This happens in hardware, parallel to your code running, which means zero CPU overhead for basic collision detection.

### Understanding Collision Registers

The magic happens in two registers:

```text
$D01E - Sprite-to-sprite collision
$D01F - Sprite-to-background collision

Each bit represents a sprite (0-7)
Reading clears the register!
```

That last point is crucial - reading the collision register clears it. This means you must store the value if you need to check multiple collision types. It also means collision detection is naturally frame-based: you check what collided since the last time you looked.

The hardware checks every pixel, every scanline. If any non-transparent pixel of one sprite overlaps any non-transparent pixel of another sprite, the corresponding bits are set. This happens whether you're paying attention or not - the VIC-II is always watching.

### Basic Sprite Collision

Let's build a simple collision system with a player and enemy:

```text
; Sprite Collision Detection
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        ; Setup two sprites
        lda #$80
        sta $07f8              ; Sprite 0 - player
        lda #$81
        sta $07f9              ; Sprite 1 - enemy
        
        lda #%00000011         ; Enable both sprites
        sta $d015
        
        ; Different colors
        lda #$01               ; White player
        sta $d027
        lda #$02               ; Red enemy
        sta $d028
        
        ; Initial positions
        lda #100
        sta $d000              ; Player X
        lda #100
        sta $d001              ; Player Y
        
        lda #200
        sta $d002              ; Enemy X
        lda #100
        sta $d003              ; Enemy Y
```

We've set up two sprites - a white player and red enemy. Now comes the game loop where collision magic happens:

```text
main_loop:
        ; Wait for raster
        lda #250
wait:   cmp $d012
        bne wait
        
        ; Move player with joystick
        jsr move_player
        
        ; Move enemy toward player
        jsr move_enemy
        
        ; Check collision
        lda $d01e              ; Read collision register
        and #%00000011         ; Check sprites 0 and 1
        cmp #%00000011         ; Both involved?
        bne no_collision
        
        ; COLLISION!
        inc $d020              ; Flash border
        jsr handle_collision
        
no_collision:
        jmp main_loop
```

The collision check is elegant. We read $D01E, which gives us a byte where each bit represents whether that sprite collided with any other sprite. If sprite 0 hit sprite 1, both bit 0 and bit 1 will be set. By checking for %00000011, we confirm both sprites were involved in the same collision.

```text
move_player:
        ; Read joystick
        lda $dc00
        sta temp
        
        lsr temp
        bcs no_up
        dec $d001
no_up:
        lsr temp
        bcs no_down
        inc $d001
no_down:
        lsr temp
        bcs no_left
        dec $d000
no_left:
        lsr temp
        bcs no_right
        inc $d000
no_right:
        rts
```

Standard joystick movement - nothing new here. But the enemy AI is where it gets interesting:

```text
move_enemy:
        ; Simple AI - move toward player
        lda $d000              ; Player X
        cmp $d002              ; Enemy X
        beq check_y_move
        bcc move_enemy_left
        inc $d002              ; Move right
        jmp check_y_move
move_enemy_left:
        dec $d002              ; Move left
        
check_y_move:
        lda $d001              ; Player Y
        cmp $d003              ; Enemy Y
        beq enemy_done
        bcc move_enemy_up
        inc $d003              ; Move down
        rts
move_enemy_up:
        dec $d003              ; Move up
enemy_done:
        rts
```

This creates a relentless enemy that always moves toward the player. Simple, but effective for testing collision! The enemy compares its position to the player's and moves one pixel closer each frame.

```text
handle_collision:
        ; Push sprites apart
        lda $d000
        sec
        sbc #5
        sta $d000              ; Player back
        
        lda $d002
        clc
        adc #5
        sta $d002              ; Enemy forward
        
        rts

temp: !byte 0
```

The collision response pushes the sprites apart. This prevents them from getting stuck inside each other - a common problem in early game development. Without this separation, sprites can overlap and trigger continuous collisions.

### Sprite-to-Background Collision

The C64 can also detect when sprites hit background graphics. This uses the same principle but checks against character graphics:

```text
; Background Collision Demo
setup_background_collision:
        ; Draw some walls
        ldx #0
draw_walls:
        lda #160               ; Solid block character
        sta $0400,x            ; Top wall
        sta $0400+24*40,x      ; Bottom wall
        inx
        cpx #40
        bne draw_walls
```

Character 160 is a solid block in the C64's character set. We're drawing horizontal walls at the top and bottom of the screen. The math here: screen memory starts at $0400, and each row is 40 characters wide. So $0400 + 24*40 gives us row 24.

```text
        ldx #0
draw_sides:
        lda #160
        sta $0400+40,x         ; Left wall (each row + 0)
        sta $0400+39+40,x      ; Right wall (each row + 39)
        inx
        inx
        cpx #48                ; 24 rows * 2
        bne draw_sides
```

Creating vertical walls is trickier. We need to place a character at position 0 and position 39 of each row. The loop increments by 2 because we're drawing two characters per iteration, and we need 48 iterations for 24 rows.

```text
        ; Enable sprite
        lda #$80
        sta $07f8
        lda #%00000001
        sta $d015
        
        ; Position in center
        lda #160
        sta $d000
        lda #125
        sta $d001
        
movement_loop:
        ; Store old position
        lda $d000
        sta old_x
        lda $d001
        sta old_y
        
        ; Move based on input
        jsr read_joystick
        jsr move_sprite
        
        ; Check background collision
        lda $d01f              ; Background collision register
        and #%00000001         ; Sprite 0?
        beq no_bg_collision
        
        ; Hit background - restore position
        lda old_x
        sta $d000
        lda old_y
        sta $d001
        
        ; Visual feedback
        inc $d020
        dec $d020
        
no_bg_collision:
        jmp movement_loop

old_x: !byte 0
old_y: !byte 0
```

The key difference: we read $D01F instead of $D01E. When a sprite's non-transparent pixels overlap with background graphics (any character with foreground color), the corresponding bit is set. The restoration technique - saving position before moving, then restoring if collision occurs - is a classic pattern that prevents sprites from entering solid objects.

## Boundary Detection

Hardware collision is great, but you also need to keep sprites within screen limits. The C64's visible screen area is approximately 320×200 pixels, but sprites can actually move beyond these boundaries.

### Basic Boundary Checking

```text
; Screen Boundary Detection
check_boundaries:
        ; Check left edge
        lda $d000              ; Sprite X
        cmp #24                ; Left border width
        bcs check_right
        lda #24
        sta $d000              ; Clamp to edge
```

The visible screen doesn't start at pixel 0 - there's a border. The left border is 24 pixels wide. If our sprite's X position is less than 24, it's entering the border, so we clamp it to 24.

```text
check_right:
        ; Check if X wrapped (>255)
        lda $d010              ; X MSB register
        and #%00000001         ; Sprite 0 MSB
        beq check_normal_right ; No MSB, normal check
        
        ; X is > 255
        lda $d000
        cmp #64                ; Right edge when MSB set
        bcc check_top
        lda #64
        sta $d000
        jmp check_top
```

Here's where it gets tricky. The C64 uses 9 bits for sprite X positions (allowing 0-511), but we can only store 8 bits in a register. The 9th bit (MSB - Most Significant Bit) for all sprites is packed into $D010. When this bit is set, the sprite's actual X position is 256 + value in $D000.

```text
check_normal_right:
        ; X is < 256
        lda $d000
        cmp #255-24            ; Right edge (320 - 24 - sprite width)
        bcc check_top
        lda #255-24
        sta $d000
        
check_top:
        ; Check top edge
        lda $d001              ; Sprite Y
        cmp #50                ; Top border height
        bcs check_bottom
        lda #50
        sta $d001
        
check_bottom:
        ; Check bottom edge
        lda $d001
        cmp #229               ; Bottom edge (250 - 21 for sprite height)
        bcc boundaries_done
        lda #229
        sta $d001
        
boundaries_done:
        rts
```

Y positions are simpler - they fit in 8 bits. The visible area runs from approximately line 50 to line 250. We stop at 229 to account for the sprite's 21-pixel height.

### Bouncing Off Boundaries

Static boundaries are boring. Let's make sprites bounce:

```text
; Bouncing Ball Physics
bouncing_ball:
        ; Initialize velocity
        lda #2
        sta x_vel
        lda #1
        sta y_vel
        
bounce_loop:
        ; Wait for frame
        lda #250
wait2:  cmp $d012
        bne wait2
        
        ; Apply velocity
        lda $d000
        clc
        adc x_vel
        sta $d000
        
        lda $d001
        clc
        adc y_vel
        sta $d001
```

Basic physics: position += velocity each frame. The sprite moves by x_vel pixels horizontally and y_vel pixels vertically every frame.

```text
        ; Check X boundaries
        lda $d000
        cmp #24                ; Left edge
        bcs check_right_bounce
        lda #24
        sta $d000
        ; Reverse X velocity
        lda x_vel
        eor #$ff
        clc
        adc #1
        sta x_vel
        jmp check_y_bounce
```

When we hit a boundary, we reverse velocity. The EOR #$FF + ADC #1 pattern performs two's complement negation, turning 2 into -2 (or technically, 254 in unsigned representation).

```text
check_right_bounce:
        cmp #255-24
        bcc check_y_bounce
        lda #255-24
        sta $d000
        ; Reverse X velocity
        lda x_vel
        eor #$ff
        clc
        adc #1
        sta x_vel
        
check_y_bounce:
        ; Check Y boundaries
        lda $d001
        cmp #50                ; Top edge
        bcs check_bottom_bounce
        lda #50
        sta $d001
        ; Reverse Y velocity
        lda y_vel
        eor #$ff
        clc
        adc #1
        sta y_vel
        jmp bounce_loop
        
check_bottom_bounce:
        cmp #229
        bcc bounce_loop
        lda #229
        sta $d001
        ; Reverse Y velocity
        lda y_vel
        eor #$ff
        clc
        adc #1
        sta y_vel
        
        jmp bounce_loop

x_vel: !byte 2
y_vel: !byte 1
```

This creates a perfect bounce - the angle of incidence equals the angle of reflection. Real physics would include gravity and energy loss, but this simple model works great for games like Breakout or Pong.

## Advanced Collision Techniques

### Pixel-Perfect Collision

Hardware collision is great, but sometimes you need more precision. What if you want a smaller hitbox than the full sprite?

```text
; Pixel-perfect collision check
pixel_collision:
        ; Get sprite positions
        lda $d000
        sta sprite1_x
        lda $d001
        sta sprite1_y
        lda $d002
        sta sprite2_x
        lda $d003
        sta sprite2_y
        
        ; Calculate distance
        lda sprite1_x
        sec
        sbc sprite2_x
        bpl positive_x
        ; Make positive
        eor #$ff
        clc
        adc #1
positive_x:
        cmp #20                ; Within sprite width?
        bcs no_pixel_collision
```

We're calculating the absolute difference between X coordinates. The BPL (Branch if PLus) instruction checks if the result is positive. If negative, we negate it to get the absolute value. This gives us the distance between sprites.

```text
        lda sprite1_y
        sec
        sbc sprite2_y
        bpl positive_y
        ; Make positive
        eor #$ff
        clc
        adc #1
positive_y:
        cmp #21                ; Within sprite height?
        bcs no_pixel_collision
        
        ; Collision detected!
        lda #1
        rts
        
no_pixel_collision:
        lda #0
        rts

sprite1_x: !byte 0
sprite1_y: !byte 0
sprite2_x: !byte 0
sprite2_y: !byte 0
```

This creates a rectangular hitbox. You could make it smaller than the sprite for more forgiving gameplay, or check circular distance for round objects.

### Collision Response System

Different collisions should trigger different responses:

```text
; Different collision responses
handle_collision_type:
        ; Determine collision type
        lda $d01e              ; Sprite collision
        sta collision_mask
        
        ; Check player vs enemy
        lda collision_mask
        and #%00000001         ; Player sprite?
        beq check_pickup
        
        lda collision_mask
        and #%00000010         ; Enemy sprite?
        beq check_pickup
        
        ; Player hit enemy!
        jsr player_damage
        jmp collision_done
```

We're using bit patterns to identify which sprites collided. If both sprite 0 (player) and sprite 1 (enemy) have their bits set, they collided with each other.

```text
check_pickup:
        ; Check player vs pickup
        lda collision_mask
        and #%00000001         ; Player?
        beq check_projectile
        
        lda collision_mask
        and #%00000100         ; Pickup sprite?
        beq check_projectile
        
        ; Collected item!
        jsr collect_item
        jmp collision_done
        
check_projectile:
        ; Check projectile vs enemy
        lda collision_mask
        and #%00001000         ; Projectile?
        beq collision_done
        
        lda collision_mask
        and #%00000010         ; Enemy?
        beq collision_done
        
        ; Hit enemy!
        jsr enemy_damage
        
collision_done:
        rts
```

This system checks multiple collision types in priority order. Player damage is checked first (most important), then pickups, then projectile hits. Each collision type triggers a different response function.

```text
player_damage:
        ; Flash screen
        inc $d020
        ; Reduce health
        dec player_health
        ; Knockback
        lda $d000
        sec
        sbc #10
        sta $d000
        rts

collect_item:
        ; Play sound
        lda #15
        sta $d418              ; Volume max
        lda #17
        sta $d401              ; Frequency low
        ; Hide pickup
        lda $d015
        and #%11111011         ; Disable sprite 2
        sta $d015
        ; Increase score
        inc score
        rts

enemy_damage:
        ; Flash enemy
        lda #$02
        sta $d028
        ; Reduce enemy health
        dec enemy_health
        bne enemy_alive
        ; Destroy enemy
        lda $d015
        and #%11111101         ; Disable sprite 1
        sta $d015
enemy_alive:
        rts

collision_mask: !byte 0
player_health:  !byte 3
enemy_health:   !byte 2
score:          !byte 0
```

Each response provides appropriate feedback: damage flashes the screen and knocks back, collecting items plays a sound, hitting enemies changes their color. These immediate responses make the game feel responsive and alive.

## Complete Collision System

Here's how it all comes together in a real game:

```text
; Complete Collision Game
*=$0801
        !byte $0b,$08,$0a,$00,$9e,$32,$30,$36,$31,$00,$00,$00

*=$080d
start:
        jsr init_game
        
game_loop:
        ; Timing
        lda #250
wait3:  cmp $d012
        bne wait3
        
        ; Update
        jsr handle_input
        jsr update_enemies
        jsr update_projectiles
        
        ; Collision checks
        jsr check_all_collisions
        jsr check_boundaries_all
        
        ; Render
        jsr update_display
        
        ; Check game over
        lda player_lives
        bne game_loop
        
        jmp game_over
```

A proper game loop: wait for frame sync, process input, update game objects, check collisions, render graphics, check win/lose conditions. This pattern scales from simple games to complex productions.

```text
check_all_collisions:
        ; Read collision registers
        lda $d01e              ; Sprite collisions
        sta sprite_collisions
        lda $d01f              ; Background collisions
        sta bg_collisions
        
        ; Process sprite collisions
        lda sprite_collisions
        beq check_bg
        
        ; Player vs enemies
        and #%00000001         ; Player involved?
        beq check_projectiles
        
        lda sprite_collisions
        and #%00001110         ; Any enemy sprites?
        beq check_projectiles
        
        jsr player_hit
```

Storing collision registers lets us check multiple collision types. We prioritize player collisions because they're most important for gameplay.

```text
check_projectiles:
        ; Projectile vs enemies
        lda sprite_collisions
        and #%00010000         ; Projectile sprite?
        beq check_bg
        
        lda sprite_collisions
        and #%00001110         ; Enemy sprites?
        beq check_bg
        
        jsr projectile_hit
        
check_bg:
        ; Background collisions
        lda bg_collisions
        beq collisions_done
        
        ; Any sprite hit wall
        jsr wall_collision
        
collisions_done:
        rts
```

The collision check cascade handles all possible collision types. Order matters - player safety comes first, then combat resolution, then environmental collisions.

## Optimization Tips

### Efficient Collision Checking

Not all sprites need to check collision with all other sprites:

```text
; Fast bounding box check
fast_collision:
        ; Early exit if too far apart
        lda sprite1_x
        sec
        sbc sprite2_x
        bpl check_distance
        eor #$ff
        clc
        adc #1
        
check_distance:
        cmp #30                ; Max collision distance
        bcs no_collision_fast ; Too far
        
        ; Now check Y
        lda sprite1_y
        sec
        sbc sprite2_y
        bpl check_y_distance
        eor #$ff
        clc
        adc #1
        
check_y_distance:
        cmp #30
        bcs no_collision_fast
        
        ; Close enough - detailed check
        jsr detailed_collision
        rts
        
no_collision_fast:
        lda #0
        rts
```

This "broad phase" collision first checks if sprites are even close enough to possibly collide. Only if they're within 30 pixels do we bother with detailed checking. This can save huge amounts of processing time.

### Collision Groups

Use bit patterns to define which sprites can collide:

```text
; Use bit patterns for collision groups
PLAYER_GROUP  = %00000001
ENEMY_GROUP   = %00001110
PICKUP_GROUP  = %00110000
WALL_GROUP    = %11000000

check_collision_groups:
        ; Player only collides with enemies and pickups
        lda #PLAYER_GROUP
        and collision_mask
        beq check_enemies
        
        lda collision_mask
        and #ENEMY_GROUP|PICKUP_GROUP
        beq check_enemies
        
        jsr handle_player_collision
        
check_enemies:
        ; Enemies collide with player and walls
        ; ... similar pattern
        rts
```

This system prevents unnecessary collision checks. Enemies don't need to check collision with pickups, projectiles don't collide with each other, etc.

## Common Issues and Solutions

### "Collision detection seems off"
- Remember sprites have transparent areas - collision only triggers on non-transparent pixels
- The sprite's position is its top-left corner, not its center
- Consider using smaller bounding boxes for more forgiving gameplay

### "Multiple collisions trigger"
- Collision registers accumulate hits until read - always read and clear
- Use collision flags to prevent the same collision triggering multiple times
- Add invulnerability timers after taking damage

### "Sprites get stuck together"
- Always push sprites apart after collision
- Store previous position to restore if collision occurs
- Add minimum separation distance between sprites

## Quick Reference

### Collision Registers
- **$D01E**: Sprite-to-sprite collision (read clears)
- **$D01F**: Sprite-to-background collision (read clears)

### Collision Check Order
1. Read collision registers (store values!)
2. Determine collision type
3. Apply appropriate response
4. Clear collision flags

### Common Responses
- **Damage**: Flash, reduce health, knockback
- **Collect**: Hide sprite, increase score, play sound
- **Bounce**: Reverse velocity, apply physics
- **Block**: Restore previous position

Remember: Good collision makes games feel solid and responsive! The C64's hardware collision was a game-changer (literally) in 1982.
